# 测试专家审查方法

Review 的测试职责不是“把已有测试再跑一遍”，而是从需求和失败风险出发，判断**现有证据是否足以支持当前结论**。

同仓存在 Coding Skill 时，Validation Matrix 和各测试层完整定义以 Coding 当前 references 为准；本文只定义 Review 如何从测试专家视角审查，不建立第二套测试规范。

## 1. 先从行为和风险推导测试，不先看测试数量

先独立列出当前功能或变更的可观察行为：

```text
正常成功路径
输入边界与空值
非法/不支持输入
错误与异常传播
状态转换
重试/取消/恢复
并发/幂等/事务
缓存/刷新/顺序
兼容性
用户可见反馈
权限/安全边界
资源生命周期/性能
构建/启动/打包
外部依赖事实
```

只保留当前项目真实适用的项。

然后为每项问：

```text
如果这里错了，谁会先看到？
错误会发生在哪一层？
什么最小测试能稳定制造这个失败？
现有测试是否真的运行了那一层？
```

## 2. 测试绿色不等于覆盖充分

`测试绿色` 只能证明：

- 当前运行的测试没有触发失败；
- 这些测试实际执行和断言的范围符合预期。

它不能自动证明：

- 没写测试的行为正确；
- Mock 与真实依赖一致；
- 数据库事务真的工作；
- UI 与真实 API 已接通；
- 一条成功链覆盖所有错误状态；
- 外部 Provider 当前在线；
- public Contract 没有漂移。

Review 必须把“测试结果”和“测试充分性”分开判断。

## 3. 建立 Test Gap Matrix

对重要 Requirement/Risk 使用最小表：

```text
Requirement / Risk
→ Expected observable behavior
→ Existing evidence
→ Evidence boundary
→ Gap
→ Smallest useful next test
```

例如：

```text
取消后的按钮必须不可再次提交
→ 用户看到 disabled
→ 只有后端 Unit
→ 未运行 Browser
→ UI 状态未验证
→ Browser Mock Acceptance 加取消态用例
```

Test Gap Matrix 是审查思路，不要求项目新建固定文档。

## 4. Web / Full-stack 项目的专项审查

当项目真实存在对应边界，且 Coding 当前分层规则适用时，重点检查以下层是否各自证明了自己该证明的事实：

### Browser Mock Acceptance

适合广覆盖用户可见行为、页面状态和前端请求语义。Review 重点检查：

- 用户能否完成关键动作；
- loading / empty / success / failure / retry / cancel 等当前真实状态是否覆盖；
- disabled/enabled 资格是否正确；
- method / URL / query / payload 是否断言关键字段；
- 错误提示、轮询、刷新、跨页结果是否符合需求；
- Mock 是否从正式 Contract/生成 Client/当前真实字段获得依据，而不是手写第二套接口事实。

Browser Mock Acceptance 不能被 Review 写成真实 Backend、PostgreSQL、Worker 或 Provider 证明。

### Backend / API / PostgreSQL Integration

Review 检查真正的服务器业务规则和持久化风险是否由真实后端/持久层承担，例如：

- HTTP status 与错误 Contract；
- 事务与数据库约束；
- 幂等、锁、并发、状态机；
- Job/Worker/Repository 最终事实；
- 查询、分页、资格判断和持久化结果。

项目实际不使用 PostgreSQL 时，不机械要求 PostgreSQL；名称以 Coding 当前项目映射为准。

### Contract / Generated Client

Review 检查生产者和消费者是否共享同一机器 Contract，尤其防止：

```text
Browser Mock 使用字段 A
真实后端已经改成字段 B
两边各自测试都绿
```

Contract 测试不代替业务行为测试。

### Real Full-stack Golden Path

Review 只要求足够证明关键真实接线的少量高价值路径。重点是：

```text
真实入口
→ 真实关键组件
→ 真实持久化/运行边界
→ 最终用户或 consumer 结果
```

不要为了覆盖状态空间把所有 Browser Mock 场景复制成真实 Full-stack。

### Real Provider Probe

只有当前变更真正依赖外部 Provider 的现时字段、分页、错误、费用或能力事实时才考虑。Review 必须检查：

- 是否有明确授权；
- 是否有界；
- 是否避免暴露 Secret；
- 是否区分供应商/网络问题与代码缺陷；
- 是否仍保留稳定 Fixture/Fake 回归。

普通 CI 不应因为 Review 想“更真实”就被迫加入不稳定或付费 Probe。

## 5. 其他项目形态的映射

Review 不把 Browser 术语强加到所有项目。

### Library / SDK

重点：

- public API/ABI；
- consumer compile/invoke；
- serialization/compatibility；
- package/install smoke；
- examples 是否真实可运行。

### CLI

重点：

- command/flag/stdin；
- stdout/stderr；
- exit code；
- filesystem/process/environment 副作用；
- 安装后的真实命令工作流。

### Data / ETL / ML

重点：

- 输入 Schema；
- deterministic transform；
- data quality；
- checkpoint/idempotency；
- batch 重跑；
- 模型/Artifact/版本可复现性。

### Mobile / Desktop

重点：

- View/State；
- simulator/device；
- permission/storage/network；
- build/package/signing（项目真实适用时）。

### Infra / IaC / Release

重点区分：

```text
lint/validate
plan/diff/dry-run
artifact/build
真实 apply/deploy
```

它们是不同证据等级，Review 不能用更弱层冒充更强层。

## 6. 如何设计最小新增测试

当 `review-and-test` 有授权时：

1. 优先选择能稳定复现 Finding 的最低成本层；
2. 断言可观察行为，而不是内部调用次数；
3. 只 Mock 当前测试不负责证明的外部边界；
4. 测试名称描述业务行为/失败条件；
5. Bug 修复场景应能证明修复前失败、修复后通过；
6. 不为了 Review 新增与项目现有体系重复的新框架。

## 7. 测试数据和 Fixture

检查：

- 是否只覆盖“完美数据”；
- null/empty/large/boundary 是否需要；
- Fixture 是否仍符合当前 Contract；
- 时间、排序、分页、ID、枚举是否有真实边界；
- 并发测试是否真的存在并发，而不是串行循环；
- Mock 是否因过度宽松导致错误字段也能通过。

## 8. 反脆弱性与可维护性

高质量测试应尽量：

- 稳定复现业务行为；
- 少依赖实现细节；
- 失败时能定位原因；
- 不依赖随机时间或未控制外部网络；
- 不要求开发者为了测试关闭真实安全/数据库约束；
- 不通过 sleep 堆叠隐藏竞态；
- 不把 Snapshot 更新当成默认修复。

## 9. Review 输出测试结论时的措辞

推荐精确表述：

```text
Browser Mock Acceptance passed for X/Y states.
Backend integration was not run, so persistence is unverified.
Contract drift check passed at current HEAD.
One Real Full-stack Golden Path passed; error-state breadth remains covered only by Mock.
```

不要笼统写：

```text
E2E 全通过
测试很充分
系统已完整验证
```

除非实际证据确实支持这些更强结论。
