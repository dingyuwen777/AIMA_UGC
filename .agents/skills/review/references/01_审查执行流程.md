# 审查执行流程

这份规则只定义 Review 怎样独立执行，不重新定义 Coding 的研发规范。

同仓存在 `.agents/skills/coding/SKILL.md` 时，先读取 Coding，并按当前任务触发其 references；Review 只负责把这些规范当作审查基线，再从独立审查者角度验证实现和证据。

## 1. 建立 Review Target

开始前明确：

```text
Review Target：PR / branch diff / commit range / working tree / module / feature
Base / Head：适用时记录真实 SHA/ref
模式：review-only / review-and-test / review-and-fix
授权：允许读、跑测试、写测试、改代码、提交、PR、合并到什么程度
上游事实：用户决定 / Spec / Roadmap / Change / Contract / Schema
项目事实：AGENTS / Manifest / locks / build / tests / CI / runtime
```

没有明确 Target 时先从仓库和当前任务自行恢复；能从 PR、branch、diff 或代码确认的事实不要反问用户。

## 2. 先恢复规则，再看 diff

顺序：

```text
上位指令
→ 仓库 AGENTS/CONTRIBUTING
→ Coding（同仓存在时）
→ 当前任务触发的 Coding references
→ Review Target 相关需求/Contract/代码/测试
→ diff
```

不要先看 diff 后再凭个人习惯挑问题，否则容易把项目明确允许的实现误报成问题，也容易漏掉上游要求。

## 3. 独立重建上游要求

复杂 Review 不接受“作者已经写好了 checklist”作为需求全集。

重新建立：

```text
用户/业务已确认目标
→ 正式 Spec/Roadmap/Change 上游来源
→ public Contract / Schema / compatibility
→ 用户或 consumer 可观察结果
→ 必须保持不变
→ 非目标
```

然后分别检查：

```text
A1：上游要求 → Change / 实现，有没有漏项？
A2：Change / 实现 → 测试 / 文档 / 运行证据，有没有空证据？
```

如果 Coding 已定义 Requirement Traceability / Completion Audit，直接使用它的当前规则，不另造第二份格式。

## 4. 从影响面而不是文件数量判断风险

对每个变更问：

- 谁调用它？
- 它调用谁？
- 输入/输出/错误/状态有没有变化？
- public API/ABI/CLI/Schema/文件格式是否变化？
- 是否涉及事务、并发、重试、幂等、缓存或资源生命周期？
- 用户能看到什么变化？
- 部署/配置/依赖/运行时是否受影响？
- 现有测试最可能漏掉哪个失败模式？

“只改 5 行”不能自动判成低风险。

## 5. 先设计风险，再读测试

在读现有测试结果之前，先独立写出本次高价值风险：

```text
正常路径
边界输入
非法输入
错误/异常传播
状态转换
重试/取消/恢复
并发/幂等/事务
兼容性
安全/权限/Secret
用户可见状态
构建/启动/打包
外部依赖变化
```

不适用的项有事实依据地跳过。

这样可以避免看到“测试全绿”后产生确认偏差。

## 6. 审查测试证据

读取 [03_测试专家审查方法.md](03_测试专家审查方法.md)。

对每个重要要求建立最小映射：

```text
Requirement / Risk
→ 哪个测试或检查在证明？
→ 它实际运行了哪些真实边界？
→ 它断言了什么可观察结果？
→ 哪些边界仍是 Mock/Fake/未运行？
```

测试名称、覆盖率数字或 CI 绿色本身不是充分证据。

## 7. 主动验证高风险假设

`review-only` 可以运行已有、非破坏性的验证；`review-and-test` 可在授权范围内新增最小测试。

优先顺序：

```text
能快速证伪 Finding 的目标测试
→ 相关模块测试
→ 必要 Contract / Integration / Workflow
→ 少量关键 Golden Path
→ 只有必要且授权时的外部真实 Probe
```

不要为了显得“全面”默认跑最贵、最慢、最脆的测试层。

## 8. 形成 Findings

每个 Finding 按 [02_Findings与严重度.md](02_Findings与严重度.md) 输出。

形成 Finding 前至少做一次反证检查：

```text
有没有项目规则允许这种行为？
有没有上游决定说明它是刻意设计？
有没有调用链证据证明我理解错了？
有没有测试已经覆盖，只是我还没读到？
```

无法排除时降低确定性，写成待验证风险，而不是确定缺陷。

## 9. 修复回路

### review-only

只报告，不修改。

### review-and-test

只在授权范围补测试。测试证明生产缺陷后，停止生产实现修改并报告需要进入 Coding。

### review-and-fix

```text
Finding 已确认
→ 返回 Coding
→ 重新读取 `.agents/skills/coding/SKILL.md`
→ Coding 建立失败证据并实施最小修复
→ Coding 完成新鲜验证
→ 返回 Review
→ 对原问题、相邻风险和新 diff 做 re-review
```

Review 不直接维护自己的生产修复规则。

## 10. re-review 不是只看“那一行改了”

至少复核：

- 原 Finding 是否真正消失；
- 新增修复是否改变了其他合法行为；
- 回归测试是否能在修复前失败、修复后通过（适用时）；
- 修复是否引入新的兼容、安全、并发或测试真实性问题；
- 文档/Contract/generated 是否同步（受影响时）。

如果修复导致范围明显扩大，停止滚雪球式修改，返回 Coding/上游重新界定。

## 11. 结束条件

Review 完成不以“没有更多想法”为标准，而以：

```text
目标和上游要求已覆盖
高风险调用链已读取
测试充分性已评估
必要验证有新鲜证据
Findings 有触发条件和证据
未验证项明确
权限边界没有越过
```

没有证据支持“可合并/可发布”时，不得给这种结论。
