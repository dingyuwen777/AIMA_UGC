## 项目治理校准状态

- 状态：待校准
- 本节属于**项目自有 Overlay**，不是安装器受管区。首次接入时，当前宿主大模型必须先调查仓库真实实现并完成一次有界的项目治理校准；完成后把本行状态改为“状态：已校准”，再继续原始研发任务。
- 后续普通开发不为形式重复全量调查；只有项目长期治理事实发生变化、现有 `AGENTS.md` 与当前事实疑似漂移，或用户明确要求刷新项目规则时，才做 targeted 校准。

## 项目 Overlay 维护规则

1. 项目语言、Runtime、框架、数据库、目录、模块职责、Contract、Schema/Migration、CI、部署和发布方式，只能依据当前仓库文件、实际运行结果或用户/Owner 已确认决定补充；
2. 自动发现到 Manifest、锁文件、README、Spec、Contract、Migration 或 CI 入口，只能作为“去哪里继续核实”的导航，不能直接推导未被证据证明的架构结论；**不能单凭文件名推出 React、FastAPI、PostgreSQL** 或其他具体技术路线；
3. 修改现有规则前先区分**规范性规则、描述性事实和未确认事项**：规范性规则不能因为当前实现没有遵守就被自动删除或弱化；描述性事实只有在当前仓库有充分反证时才修正；无法确认的内容保持未确认，不猜；
4. 项目规则新增、修改或删除时，应保持已有仍有效约束、例外、失败处理、验证责任、安全与兼容边界，禁止为了让文档更短而丢失原文语义；
5. 如果项目后续建立更具体的子目录 `AGENTS.md` 或同等规则，进入该目录工作时同时遵守更具体规则；
6. 项目级研发治理能力可以维护本地可失效导航缓存；该缓存不是项目事实源，不应提交 Git，当前代码、Contract、Schema/Migration、测试和运行结果始终优先；
7. 项目治理校准和后续定向维护应使用当前项目自己的模块、Contract、Schema、测试、CI、部署、业务和设计术语表达规则；除非属于本项目正式维护对象，不把通用治理能力自身的执行、分发或实现说明转写成项目长期规范。

## 当前工程基线

项目治理校准完成后，只记录已经由当前仓库或 Owner 确认、且对长期研发导航有价值的语言、Runtime、Manifest/lock、构建/测试入口等基线。没有充分证据时保持为空或明确“未确认”，不要为了模板完整性发明技术栈。

## 架构与模块边界

只记录稳定模块职责、Owner、主要入口和跨模块边界；精确类、函数、字段和易变调用细节仍以真实代码为准，不在本文件维护第二套实现镜像。

## Contract / Schema / Migration

只记录真实存在的 Contract、Schema、Migration 事实源与长期兼容边界。项目没有对应机制时不要创建占位制度；已有机器事实时优先链接/导航到真实 Owner，不手抄第二套定义。

## 开发与验证入口

只记录项目真实存在、长期稳定的构建、测试、静态检查、调试或最小运行入口，以及项目自己的特殊验证要求。具体任务仍根据当前代码和 CI 读取最新命令，不把旧命令长期固化成不可校准事实。

## CI / Git / Release / 部署

只记录当前项目真实存在或 Owner 明确建立的 CI、分支/PR、Release、部署、回滚和恢复边界。平台当前没有强制某项机制，不等于可以删除项目已经明确规定的规范性要求。
