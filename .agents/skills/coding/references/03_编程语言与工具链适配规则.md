# 编程语言与工具链适配规则

这份规则用于让 Coding 在不同语言、不同构建系统和不同包管理器中保持同一套质量流程，同时避免把某个生态的命令、目录或框架当成全球默认。

核心原则只有一个：**先读取仓库事实，再选择工具；profile 是导航，不是替仓库做决定。**

## 1. 所有语言都先做的事实调查

在写代码、安装依赖或决定验证命令之前，按任务范围确认以下事实：

1. 目标路径适用的 `AGENTS.md`、`CONTRIBUTING`、README、CI/开发规范；
2. Runtime / compiler / SDK 版本文件；
3. Manifest / workspace / project file；
4. 锁文件以及它实际对应的包管理器；
5. build system、wrapper、task runner、Make/Just 等入口；
6. test、lint、format、type/static analysis 的仓库实际命令；
7. package/build artifact 与发布方式；
8. generated code、schema、migration、native binding 等特殊边界；
9. CI 当前怎样安装、构建和测试；
10. 多语言仓库中当前改动影响哪些 workspace/module/consumer。

不要因为机器上安装了某个工具就使用它。优先使用：

```text
仓库 wrapper / script
→ 仓库声明的 package manager / build tool
→ 对应锁文件的 frozen / locked 模式
→ 语言原生命令（仓库确实以它为正式入口时）
```

必须保持：

- 不得擅自升级 Runtime、Compiler、SDK、Framework、Package Manager 或依赖；
- 不得擅自把 npm 换成 pnpm、Maven 换 Gradle、pip 换 uv、CMake 换 Meson等；
- 不同时维护多套相互竞争的锁文件，除非仓库明确就是这样设计；
- 不删除锁文件来“解决依赖问题”；
- 不用全局安装版本替代仓库 wrapper/版本文件；
- 不因为 profile 中出现示例命令就宣称该命令在目标仓库可用；
- 验证结论必须来自仓库实际命令和本轮新鲜执行结果。

## 2. 如何解释本文件中的命令

下面的命令都是**候选发现线索**，不是无条件执行清单。

例如看到 Python 项目时：

```text
pytest
ruff
mypy
```

只代表“这些是常见入口，应检查仓库是否使用”；如果仓库实际使用 `tox`、`nox`、`hatch`、`poetry run`、`uv run`、`pyright` 或完全不同的机制，就必须跟随仓库。

同理，看到 JavaScript 项目不能只因为存在 `package.json` 就运行 `npm install`；先看 `packageManager`、锁文件、workspace 和 CI。

## 3. Python

### 优先读取

常见事实源包括：

```text
.python-version
pyproject.toml
uv.lock
poetry.lock
requirements*.txt
Pipfile / Pipfile.lock
setup.cfg
setup.py
tox.ini
noxfile.py
pytest.ini
ruff.toml
mypy.ini
pyrightconfig.json
```

只读取仓库实际存在、且与任务有关的文件。

### 需要确认

- Python 精确/最小/最大支持版本；
- 单工程还是 workspace/monorepo；
- `src/` layout、flat layout 或其他结构；
- uv / Poetry / pip / pip-tools / Pipenv / Hatch / PDM 等实际管理方式；
- lock 是否是正式事实源；
- test runner；
- type checker；
- formatter/linter；
- wheel/sdist/native extension 构建方式。

### 常见验证候选

```text
python -m pytest ...
uv run pytest ...
python -m unittest ...
ruff check / ruff format --check
mypy / pyright
python -m build
```

必须改成仓库实际命令。

### Python 专项风险

- import path/package discovery；
- editable install 与真实 wheel 行为差异；
- async/event loop；
- typing/runtime 行为差异；
- optional dependency / extras；
- C extension/platform wheel；
- serialization/schema；
- migration/ORM 版本。

禁止用临时 `PYTHONPATH`、`sys.path` hack 或改变工作目录掩盖真实 packaging 问题，除非该仓库正式设计本来如此。

- generated client/types；
- bundler tree-shaking/code splitting；

## 15. Monorepo

Monorepo 不是语言。它是多个技术栈共享一个仓库时的额外 profile。

开始前确认：

```text
root rules
→ workspace/project rules
→ target directory nested rules
```

还要确认：

- root lock vs per-project lock；
- shared toolchain/version；
- dependency graph；
- affected/changed build mechanism；
- shared generated Contract；
- root CI 与 package CI；
- cross-language consumer。

验证不能只跑“最靠近改动的单元测试”就结束；如果修改共享 Contract、schema、build plugin 或公共 library，要验证实际受影响消费者。

同样不要反过来跑整仓最昂贵测试来替代影响分析。先确定 changed scope，再按仓库正式门禁扩大。

## 16. Container / IaC

这也是叠加 profile，可与任何语言共存。

### Container

先读：

```text
Dockerfile / Containerfile
compose*.yaml
.dockerignore
image/version pin
entrypoint/healthcheck
CI image build/publish
```

验证候选：

```text
docker build / buildx build
container smoke
health/readiness
compose config
SBOM/signature/provenance checks（项目已建立时）
```

禁止为了“修构建”把 base image 改成 `latest`、删除锁定或绕过证书/安全检查。

### Terraform / OpenTofu

先读：

```text
*.tf
*.tfvars.example（不要读取/泄露真实 Secret）
.terraform.lock.hcl
required_version / required_providers
module docs/tests
```

验证候选：

```text
fmt -check
validate
plan
policy/test framework
```

`plan` 不是 `apply`。真实 apply 需要明确环境和授权。

### Helm / Kubernetes / Kustomize

确认 chart/version/value schema、overlay、render/validate、policy、target cluster。不要默认需要 Kubernetes，也不要为了验证连接生产 cluster。

### Ansible / Cloud SDK / Deployment Scripts

先区分 dry-run/check、sandbox、真实生产动作。Secret、inventory、credential 不能写入日志或提交。

## 17. 未列出的语言或工具链

本文件不试图穷举所有语言。Objective-C、Scala、Clojure、Haskell、OCaml、Lua、R、Julia、Zig、Nim、Erlang、Solidity 或未来语言均使用同一算法：

```text
仓库规则
→ Runtime/Compiler/SDK 版本事实
→ Manifest/Workspace
→ 锁文件/依赖解析
→ Build/Test/Lint/Format/Static Analysis
→ Package/Artifact
→ CI/Release
→ 任务实际调用链
```

如果生态没有锁文件，不要伪造一个“必须有锁文件”的要求；改为确认它实际使用的可复现依赖与版本机制。如果生态没有静态类型检查，也不要为了填清单新增类型工具。

## 18. 依赖变更的统一规则

任何语言都遵守：

1. 优先标准库和现有依赖；
2. 为少量代码不轻易新增依赖；
3. 新增前说明必要性、维护状态、许可证、体积/构建影响和替代方案；
4. 修改 Manifest 后同步仓库正式锁文件；
5. 不使用 `latest` 作为运行时可变解析策略；
6. 普通功能任务不顺手升级；
7. 安全升级/大版本升级单独评估 breaking change 与回归范围；
8. 不删除失败测试、lock、integrity/signature 检查来“让安装通过”。

## 19. 工具链不可用时

如果当前宿主缺少项目要求的 compiler/SDK/device/database/container engine：

- 先确认仓库是否提供 wrapper/container/CI 可验证路径；
- 能在受控 CI/runner 验证时使用仓库既有机制；
- 不能运行的验证必须明确写成“未验证”，不能用代码阅读替代执行结论；
- 不为方便而擅自升级/降级到当前机器已有版本；
- 不声称另一个平台的成功等价于目标平台成功。

最终验证使用的必须是**仓库实际命令**、实际支持版本和本轮新鲜证据。

## 网络下载源与镜像选择

这条规则在任务会触发网络下载时生效，包括但不限于：安装 Runtime / Compiler / SDK、系统包或语言依赖，执行启动/初始化/bootstrap 脚本，构建 Docker/OCI 镜像，准备 CI 环境，或准备部署/恢复环境。它解决的是**下载链路在目标环境能否稳定工作**，不是重新选择软件、版本或供应链身份。

### 先确认目标执行环境，而不是 Agent 所在位置

选择下载源之前至少确认：

1. **目标执行环境**在哪里运行：开发者中国大陆机器、中国大陆服务器、海外服务器、GitHub Hosted Runner、自建 Runner、离线构建机等；
2. 项目是否已有 registry/index/mirror/proxy/source policy，以及哪些配置属于用户可覆盖项；
3. 当前 package manager / build tool 是否会把 index/source 信息写入锁文件、生成物或缓存元数据；
4. 当前需要下载的对象是什么：官方基础镜像、系统包、语言包、Runtime 安装器、Release artifact 等；
5. 软件身份和完整性由什么证明：固定版本、lock、checksum、hash、digest、签名、SBOM/provenance 等。

如果任务明确面向**中国大陆网络**，且需要新增或修改这些下载行为，必须先**联网核验**当前可用的国内源，再决定默认值或 fallback。不能仅凭历史经验、旧脚本或模型记忆写一个镜像地址。

### 国内镜像只能作为当前候选，不是永久白名单

联网核验优先查看镜像运营方自己的**官方帮助**、状态页、目录更新时间或**同步状态**，必要时再做有界下载/HEAD/metadata Probe。可调查的候选例如：

- 阿里云镜像站；
- 清华 TUNA；
- 中科大 USTC；
- npmmirror；
- 目标生态当前实际存在、维护状态可确认的其他国内镜像或企业内部可信代理。

这些名字**不是永久白名单**。例如某个站点可能仍提供 PyPI，但已经停止 Docker Hub 或 npm 服务；同一镜像的 security 仓库也可能比主仓同步更慢。用户点名的阿里云、中科大、网易或其他候选同样必须按本轮当前事实核验，不能因为“以前常用”就直接写入正式脚本。

### 中国大陆与海外环境不要一刀切

推荐判断：

```text
目标环境明确在中国大陆，并且当前国内镜像已核验稳定
→ 优先国内源 / registry mirror / proxy

目标是 GitHub Hosted Runner、海外服务器或其他海外网络
→ 优先该环境当前稳定且项目允许的官方上游或近端镜像
→ 不机械绕回中国大陆源

目标环境不明确
→ 先从部署事实、Runner/CI 配置或用户已确认运行环境确定
→ 不能从 Agent 自己的网络位置猜
```

如果同一个项目既要支持中国大陆本地构建，又要在海外 CI/Release 构建，优先把源设计成**可覆盖配置**，由环境选择；不要强迫所有环境共享一个远端源。

### 加速下载不能改变供应链事实

镜像/代理通常只允许改变传输路径，必须保持：

- 包名、模块名、Runtime、基础镜像等 **canonical identity**；
- 精确版本、Manifest 与正式**锁文件**；
- checksum / **hash** / **digest** / 签名等完整性检查；
- 项目已有 SBOM、provenance、license、安全扫描和 Release 身份；
- `frozen` / `locked` / immutable dependency policy。

Docker/OCI 场景中，如果项目已经用官方 canonical image reference，优先通过 Docker daemon 的 registry mirror、可信 proxy/cache 或构建参数改善下载，不为了加速就把 `FROM python:...`、`postgres:...` 等身份静默改成来源不明的第三方 registry。项目正式设计本来就使用企业私有 registry 时则遵守其现有身份和签名策略。

有些工具会把 registry/index URL 写进 lock。比如切换 Python index 可能引起 `uv.lock` 等机器事实变化。遇到这种情况不能为了“国内源”顺手重写 lock；先判断项目是否把 source 作为 dependency policy。若会形成持久依赖语义变化，就把它按依赖/构建策略变更处理并单独验证，而不是伪装成纯网络优化。

### 系统与安全更新源要检查新鲜度

系统包尤其是 security/update 仓库不能只比较下载速度。至少检查：

- 当前发行版是否完整支持；
- Release/metadata 是否持续同步；
- security 仓库的更新时间和滞后风险；
- HTTPS / 证书、签名和 repository metadata 验证是否正常；
- 镜像不可用时是否有清晰 **fallback**。

如果国内镜像当前同步异常、已停止服务、缺少目标架构/版本或安全更新明显滞后，应使用另一个已验证候选或项目允许的官方源，并记录判断依据。**禁止**为了下载成功关闭 TLS、GPG、checksum、hash、digest、签名或锁文件校验。

### 实施与验证

新增/修改启动脚本、镜像构建或依赖安装后，验证至少覆盖实际受影响层：

```text
配置可以解析
→ 目标环境能解析/访问所选源
→ locked/frozen 安装或镜像构建能完成
→ 软件/镜像身份和版本未漂移
→ 完整性校验仍有效
→ fallback/override 机制符合项目设计（存在时）
```

无法联网确认候选镜像当前状态时，不要编造“国内稳定源”。保留项目既有可信源或官方源，明确当前未验证项和中国大陆网络风险，等待具备网络条件时再固化默认镜像。
