# 多人和多 Agent 并行协作

## 支持范围

通过 Git 可见的 Change 元数据提供责任划分、依赖表达、冲突预警和集成门禁。不要把它描述成实时协同基础设施。

只对仓库已有或当前 Change 已确认建立的边界执行协作约束。没有前后端分离、API/事件 Contract、Schema、数据 Owner、Migration 或契约测试时，不创建占位机制；继续按真实文件、模块和行为范围协作。

## 开始工作前

1. 同步用户已授权同步的仓库状态；不要擅自 pull、push 或切换分支。
2. 读取所有 `changes/active/*/CHANGE.md` 的元数据。
3. 确认当前 Change 的唯一 ID、Owner、分支和状态。
4. 写清 `affected_areas`、`affected_paths`、`contracts`、`data_changes` 和 `depends_on`。
5. 执行显式冲突检查：

```text
python <skill>/scripts/coding.py conflicts --root <repo> --json
```

退出码 `2` 表示发现需要协调的显式重叠，不代表脚本故障。

同步、切换分支、rebase、共享 Contract 更新或其他 Active Change 元数据变化后重新执行。旧的“无冲突”结果不能覆盖新状态。

## 冲突维度

不要只比较源码目录。至少检查：

- 相同文件、相同目录或父子路径；
- 同一模块 Owner 或跨模块边界；
- 同一 API、事件、消息格式或其他 Contract；
- 同一表、字段、索引、Migration 链或持久化语义；
- 同一配置键、环境变量、权限或部署资源；
- 同一快照、测试数据、固定端口或共享外部环境；
- 一个 Change 依赖另一个尚未完成的行为。

某一维度在有界发现中不存在时跳过；不要因为检查清单列出它就推断项目应当拥有它。

## 处理结果

- 无重叠：允许并行，但各自保持独立分支、成功标准和验证。
- 可协调重叠：明确先后顺序、接口冻结点、共同 Owner 或拆分后的文件边界，并记录决策。
- Contract、Schema 或数据语义冲突：阻止静默并行；先统一设计和 Migration 顺序。
- 信息不足：不要写“无冲突”，写“基于当前可见状态未发现冲突”，并列出不可见范围。

仓库已有共享边界时额外遵守：

- 前端、后端或其他生产者/消费者不得分别猜测字段、枚举、错误、时间、单位、分页和兼容语义；以同一已确认 Contract 为准。
- 共享 Contract、Schema 或 Migration 的语义修改使用一个明确 Owner，或先完成共同变更再并行消费者实现；不要让多个 Change 静默定义同一语义。
- 只在仓库已有流程或协作者明确同意时设置并行冻结点；记录具体版本、提交、Schema 或决策，不能只写“接口已定”。
- 使用仓库已有契约测试或兼容检查；不存在时不引入新框架。若风险需要新增验证，按设计门禁提出最小测试方案。

## 多 Agent 派发

只并行派发真正独立的任务：

- 没有顺序依赖；
- 不写相同文件、接口或共享状态；
- 每个任务能独立验证；
- 给子 Agent 最少但充分的目标、范围、事实源和验收标准。

不要给子 Agent 整段会话历史代替任务契约。子 Agent 返回后，主 Agent 必须：

1. 检查实际 diff 和工作区；
2. 复核需求符合性；
3. 检查任务之间重叠和集成风险；
4. 运行目标及整体相关验证；
5. 只依据实际证据更新 Change 状态。

## 分支与工作区

多人或高风险并行优先使用项目既有的隔离分支或 worktree 流程，但只有用户和仓库规则授权时才能创建。创建隔离环境后先运行基线测试；基线失败时区分既有失败和本次回归，不把失败隐藏或归因给错误对象。

## 固有限制

- 本地独占创建只能防止同一工作区同时使用相同 Change ID，不能锁住远端克隆。
- 看不到另一克隆尚未提交或推送的 Change。
- 两个 Agent 从相同基线同时启动时可能都判断无冲突；记录同步后必须重新检查。
- Owner 和影响范围是协作约定，Skill 不能强制执行。
- 没有通知、看板、在线状态、租约或自动合并能力。

跨克隆可靠协作要求团队及时提交并共享 Active Change；同步策略、Branch Protection 和 PR 门禁由仓库自身负责。
