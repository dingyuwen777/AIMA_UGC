# Figma 页面布局与真实可用性审计

这份 reference 负责回答：

> 页面不仅要“结构正确”，还要真正美观、好用、符合使用者习惯，并且在真实浏览器、真实数据和真实前后端接线下仍然成立。

它重点审查：

```text
页面尺寸 / Viewport
→ App Shell / 页面区块位置
→ 对齐与间距
→ 图片 / 图表 / 标注
→ 表格 / 表单 / KPI 信息密度
→ Overlay / Drawer / Modal / Toast
→ 滚动与可视区域
→ 用户任务路径
→ 动态数据来源与刷新
→ 后端 / 数据库真实接线
→ 浏览器和 Design-to-Code 可实施性
```

---

# 1. 页面尺寸必须来自真实使用环境

Figma Frame 尺寸不是为了“方便画图”随便选一个值。

开始前先确认：

```text
主要设备：桌面 / 平板 / 手机？
主要容器：普通浏览器 / 内嵌 WebView / 大屏？
目标最小宽度是多少？
是否存在固定 Sidebar / TopBar？
是否有响应式断点？
主要操作在常见浏览器首屏能否访问？
```

## 1.1 设计基准尺寸 ≠ 生产固定宽高

桌面产品可以选择一个固定 Frame 作为设计基准，但必须明确：

```text
Figma Frame 基准
≠
生产代码 width: 1440px; height: 900px;
```

前端应按真实布局语义实现：

```text
Sidebar / TopBar 按当前 App Shell
Main flex: 1
Content 使用设计 Token 的 Padding / Gap
Card / Table / Form 使用可用内容宽度
```

禁止为了像素复制把整个页面写死成固定画布。

## 1.2 演示不应依赖人工缩放才能正常使用

如果 Prototype 在目标浏览器中：

- 默认明显放大或看不全；
- 每次都要手动 `Fit width` 才正常；
- 主按钮、Footer 或关键内容在初始可视区外；

必须检查：

- Frame 尺寸是否符合目标设备；
- Prototype scaling 设置；
- 内容区是否错误使用固定宽高；
- Modal / Drawer 是否超出视口；
- 是否存在双层滚动。

不能把“手动缩放”当成正式产品解决方案。

---

# 2. App Shell 与页面区块位置必须统一

同一个产品中的正式页面如果共用 App Shell，就应共享稳定的空间规则：

```text
Sidebar
TopBar
Main
Page Header
Content
```

至少检查：

- Sidebar 宽度是否一致；
- TopBar 高度是否一致；
- Page Header 的标题、说明、操作区是否按统一栅格；
- Main 左右 Padding 是否一致；
- 同级页面内容起点是否一致；
- Tab、Filter、Table、Card 是否共享同一左边界和内容宽度；
- 不同页面有没有无理由整体偏左或偏右。

如果某一页偏移，优先检查父容器、Auto Layout、Constraints 和实例尺寸，不逐页写补偿坐标。

---

# 3. 间距要有稳定节奏

页面美观不是“留白越多越高级”，而是空间层级稳定。

使用项目现有 Spacing Token 表达：

```text
小间距
→ Icon ↔ Text、Label ↔ Control

中间距
→ 同一业务组内的字段 / Button / Tag

大间距
→ 不同 Section / Card / Page Block
```

实际数值以当前设计系统 Token 为准，不在 Skill 里写死另一套 8/16/24 规则。

审查时重点找：

- 同类 Card 之间 gap 不一致；
- 标题、副标题、内容距离失衡；
- Button group 间距不同；
- 表单字段过挤或过松；
- Card 内 padding 与外部 gap 混乱；
- Absolute Position 破坏整体节奏。

## 3.1 视觉安全距离

任何两个独立可读或可操作元素都不应无意粘连：

```text
图标 ↔ 文字
图片 ↔ 标题
图片 ↔ 标注
Tag ↔ 相邻字段
按钮 ↔ 按钮
Toast ↔ 头像 / 导航 / 主按钮
Tooltip / Popover ↔ 关键操作元素
```

安全距离优先使用现有 Token。

---

# 4. 对齐必须结构化

重点检查：

```text
左边界
文字基线
控件中心线
卡片网格
表格列网格
```

典型问题：

- 同一列 Label 起点不同；
- KPI 数值不在同一基线；
- Button 图标与文字中心不齐；
- Tab 与下方表格左边界错开；
- Header Cell 和 Data Cell 不是同一列宽；
- 页面标题和正文使用两套左边界。

能由 Auto Layout、Grid、统一 Cell 宽度解决时，不靠手工坐标“看起来差不多”。

---

# 5. 图片、图表与标注

## 5.1 图片不能失真

检查：

- 保持宽高比；
- Crop / Fit / Fill 策略明确；
- 重要主体不被错误裁掉；
- 同类图片尺寸、圆角、边距一致；
- 动态图片比例有容器策略。

如果业务可能出现横图、竖图、极端长图，设计至少要定义容器和裁切规则，而不是只展示一张理想图片。

## 5.2 图片、文字、按钮、标注不能无意重叠

必须检查真实 Bounding Box：

```text
Image
Text
Button Hit Area
Badge / Tag
Hover / Selected Overlay
Annotation
```

无明确设计目的的重叠视为 Finding。

特别注意：中文文案变长后，原先英文长度下不重叠的布局可能失效。

## 5.3 图表标注不能堆叠

图表、地图、词云等需要检查：

- Label 不互相遮挡；
- Legend 不盖住图；
- Tooltip 有可用空间；
- 长标签有换行/省略/旋转策略；
- 极端数据下标注不会堆成一团；
- 数据极少时仍不显得空洞；
- 无数据时有 Empty State，不是一块空白图。

如果 Figma 只展示理想数据，开发状态规格必须补少量数据、空数据或长标签策略。

## 5.4 开发标注不要压在正式 UI 上

开发说明、箭头、尺寸标注优先：

- 放在独立规格区；或
- 使用 Figma Annotation；
- 不成为正式业务 UI；
- 不遮挡 Button/Text/Image/Table；
- 不让 Codex 误读成生产元素。

正式 Frame 中的文字如果用户不会实际看到，就不应作为业务层可见文本存在。

---

# 6. 表格必须按真实数据设计

列宽不能机械平均分。

按真实内容长度考虑：

```text
身份 / 名称列
状态列
时间列
统计列
操作列
```

## 6.1 长文本策略

真实数据可能超过示例时，必须定义：

- 自动换行；
- 单行省略；
- Tooltip；
- 最大宽度；
- 详情入口。

不能因为示例名短就认为列宽正确。

## 6.2 操作列

操作按钮应：

- 保持可识别宽度；
- 高频操作和危险操作有层级；
- 不把所有操作都用主色；
- 条件操作只在真实业务资格满足时出现。

## 6.3 分页 / Cursor 与后端一致

Figma 分页必须对应后端真实模型：

```text
page / offset
或
cursor / has_more
```

后端没有 `total` 时，不应凭空展示“共 N 条”。

---

# 7. 表单要符合用户任务顺序

不只检查“有没有 Input”，还要从真实使用者操作顺序反推：

```text
用户先知道什么？
→ 先选什么？
→ 后一个字段是否依赖前一个？
→ 默认值是否符合真实常用流程？
→ 错误在哪里出现？
→ 提交前能否知道会发生什么？
```

## 7.1 有限合法选项优先选择控件

如果业务只有固定合法集合，优先 Select/Radio，而不是要求用户输入机器表达式。

但合法选项必须由当前后端真实能力支持，不能为了“好用”发明不存在的选项。

## 7.2 默认值必须有事实依据

默认值可以来自：

- 产品明确决定；
- Contract default；
- Capability default；
- 当前用户配置；
- 已确认高频工作流。

没有依据时，不把设计师个人偏好写成产品默认。

## 7.3 危险操作

删除、停用、取消、覆盖等操作：

- 与普通操作有清晰层级；
- 必要时有确认；
- 不可操作时展示真实原因；
- 不只依赖颜色传递风险。

---

# 8. 信息密度与视觉层级

页面优先帮助用户完成任务，而不是展示所有可得字段。

检查：

- 用户进入页面最先要知道什么；
- KPI 是否真的有决策价值；
- 重复信息是否每行重复展示；
- 技术字段是否抢占主视觉；
- 主操作是否容易找到；
- 次要说明是否喧宾夺主；
- 大卡片是否只有极少信息；
- 内容过多时是否应分组、折叠或进入详情。

典型优化可以是：

```text
三张巨大 KPI 卡
→ 单一摘要条 + 多指标区
```

前提是业务语义不变。

---

# 9. 浮层位置与层级

Toast、Dropdown、Popover、Tooltip 必须有统一安全区和层级规则。

检查：

- Toast 是否挡住头像、导航、主按钮；
- 同一模式在不同页面位置是否一致；
- Dropdown 是否被父容器裁切；
- Tooltip 是否超出 Viewport；
- Popover 是否盖住用户下一步必须操作的字段；
- Modal/Drawer 上方的 Toast 层级是否正确；
- Auto Layout 中浮层是否需要 Absolute Position。

不能只写 x/y 后假设不会被重新布局。

---

# 10. Drawer / Modal 与滚动

常见合理结构：

```text
Header 固定
Body 唯一滚动
Footer 固定
```

具体采用项目设计系统，但必须避免多层滚动：

```text
页面滚动
+
Drawer 整体滚动
+
Drawer Body 再滚动
```

检查：

- 小屏高度下 Footer 是否仍可访问；
- 最长表单是否能滚到最后；
- Dropdown 是否能正确越过滚动容器显示；
- Overlay 是否被裁切；
- 关闭/返回路径是否符合用户预期。

---

# 11. 动态数据必须标注真实来源

凡是 Figma 中显示的动态业务数据，都应在 Figma Annotation / 开发规格中给出最小来源说明。

推荐结构：

```text
字段：启用计划数量
类型：API_DYNAMIC
来源：当前 Feature Store / Summary API
刷新：页面进入 + 用户刷新（如果真实支持）
示例值：18，仅代表设计状态
空态：0
错误态：公共错误提示
```

运行时字段：

```text
字段：下次运行时间
类型：SERVER_RUNTIME
来源：后端调度结果
格式：产品展示格式
示例值：仅用于排版
```

如果真实值来自数据库，也不应让前端直接访问数据库；必须标注当前正式调用链：

```text
PostgreSQL
→ Repository / Service / API
→ generated client / Feature API
→ Store
→ Page
```

Figma 中“来自数据库”表示最终业务事实来源，不表示前端可以越过 API 直接查询数据库。

---

# 12. 页面必须能真正接入后端

每个重要页面区块都应能回答：

```text
用户动作
→ 前端事件
→ Store / Feature API
→ Generated Client / Public Contract
→ Backend Service
→ Persistence / Runtime（适用时）
→ 返回状态
→ 页面如何刷新 / 展示结果
```

如果某个按钮只有视觉，没有真实后端动作或本地 UI 行为定义，就不能作为正式开发基线。

如果后端已有能力但 Figma 没有入口，要判断用户是否需要入口；如果需要，则是 Coverage Finding。

---

# 13. 真实使用习惯审计

页面应按“业务用户怎样完成任务”而不是“数据库表有哪些字段”组织。

检查：

- 常用操作是否在首要位置；
- 低频技术信息是否放到详情；
- 用户是否需要理解内部 ID；
- 默认排序是否符合工作习惯；
- 筛选条件是否有实际价值；
- 重置是否真正恢复默认筛选，而不是制造空结果；
- 保存成功反馈是否短暂、明确且位置稳定；
- 错误提示是否告诉用户下一步怎么办；
- 操作完成后用户能否找到最终结果。

对没有实际用户价值的字段，即使后端返回，也不要求在主界面展示。

---

# 14. 页面布局 Ready 门禁

`baseline-ready` 额外检查：

```text
[ ] Frame 尺寸与目标设备/浏览器有明确依据
[ ] 设计基准未被误定义成生产固定宽高
[ ] App Shell / Page Header / Content 左右边界一致
[ ] 同级 Section 的间距和对齐符合现有 Token
[ ] 正常状态无无意重叠
[ ] 图片比例、裁切和容器策略明确
[ ] 图片 / 图表 / 标注 / Label 不互相遮挡
[ ] 表格列宽适应真实长文本
[ ] 表单顺序符合用户任务依赖
[ ] Overlay / Toast / Dropdown / Tooltip 有稳定安全区
[ ] Modal / Drawer 无双层滚动
[ ] 关键操作在目标 Viewport 可访问
[ ] 动态数据均有 API/Runtime 来源标注
[ ] 页面动作可以映射到真实前后端调用链
[ ] Fresh Screenshot 覆盖主要状态和关键浮层
```

存在会导致用户无法正常操作、Codex 误实现或真实数据布局崩坏的问题时，应按实际影响标记 P0/P1，而不是简单归为“视觉优化”。
