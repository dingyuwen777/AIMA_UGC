# Figma 通用适用性与项目形态

这份 reference 的目标是防止 Figma Skill 被某一个项目、某一种技术栈或某一类后台系统绑死。

本 Skill 应适用于：

```text
Web 应用
移动端 App
桌面端 App
内部管理系统
数据看板
内容/媒体产品
电商/交易产品
表单/工作流系统
营销/品牌站
静态内容站
设计系统 / 组件库
原型验证项目
```

以及其它能够用 Figma 表达界面、交互和产品流程的项目。

---

# 1. 先识别项目形态，再决定审什么

Figma 审查不是默认套“前端 + 后端 + 数据库”。

开始前先判断当前目标属于哪一种或哪几种形态：

## Design-only / Concept Prototype

只有产品需求和设计，没有代码仓库。

重点：

- 用户任务；
- 信息架构；
- 页面尺寸与布局；
- 视觉层级；
- 组件复用；
- Prototype；
- 状态完整性；
- 可实施性假设。

没有后端事实时，不伪造“当前 API 已支持”。需要的系统能力应标记为 `implementation_required` 或待确认。

## Static / Marketing / Content Site

页面主要是静态内容或 CMS 内容。

重点：

- 响应式布局；
- 图片/视频；
- 内容层级；
- SEO/可访问性相关结构意图；
- CTA；
- CMS/内容来源（如果存在）。

不要为了模板要求强行寻找数据库或异步任务。

## Web / Full-stack Application

存在 Route、State、API、服务端或持久化。

重点：

- UI → Store/State → API/Contract；
- 动态数据来源；
- 用户输入与服务端能力；
- Loading/Empty/Error；
- 异步任务；
- 权限和错误；
- Design-to-Code 共享组件边界。

## Mobile / Desktop Application

重点：

- Screen / Navigation；
- 设备尺寸和安全区；
- 系统控件习惯；
- 键盘/鼠标/触控行为；
- 权限；
- 本地存储；
- 网络状态；
- 原生平台能力。

不要机械使用 Web Route、Browser Viewport、Hover 等概念。

## Data / Dashboard / Analytics

重点：

- 数据来源和刷新频率；
- 指标定义；
- 聚合口径；
- 大数据量；
- 图表极端值；
- 空数据/延迟/部分数据；
- 表格分页和筛选；
- 图片、图表、Label 不重叠。

## Form / Workflow / Admin System

重点：

- 字段依赖；
- 默认值；
- 校验；
- 权限；
- 提交/审批/撤回/重试；
- 业务状态机；
- 批量操作；
- 长表单滚动与保存反馈。

## Design System / Component Library

重点：

- Token；
- Component Set；
- Variant；
- Component Property；
- Instance Swap；
- Slot；
- 组合规则；
- 跨产品复用边界；
- 可访问状态；
- 消费者回归。

---

# 2. 事实源按项目形态选择

有仓库时，优先读取项目真实机器事实；没有某一类事实就不要生造。

可能的机器事实包括：

```text
Web Route / Store / API / Generated Client
Mobile Navigation / ViewModel / SDK
Desktop Command / State / Local Storage
Public Contract / Schema
CMS Model
Device Capability
Feature Flag
Permission Model
Background Job / Queue
Database / Repository
Static Content Source
```

核心原则：

```text
只加载当前项目真实存在的边界
```

而不是：

```text
Figma Skill 提到了 API
→ 每个项目都必须有 API
```

---

# 3. 通用六类 UI 事实

任何项目都可以把设计内容归类为：

```text
STATIC_UI
→ 固定内容 / 纯视觉

USER_INPUT
→ 用户输入

SYSTEM_DYNAMIC
→ 由系统能力或数据源提供

RUNTIME_STATE
→ 当前运行时状态

DESIGN_EXAMPLE
→ 代表性示例

SYSTEM_FIXED
→ 系统固定规则
```

在 Web 项目中 `SYSTEM_DYNAMIC` 可能来自 API；在 Mobile 中可能来自本地数据库/SDK；在静态站中可能来自 CMS；在 Design-only 项目中可能只是未来实现需求。

---

# 4. Design-to-Code 目标技术栈必须现场确认

Figma Skill 不假设：

```text
React
Vue
Angular
Flutter
SwiftUI
Jetpack Compose
Electron
Tailwind
任何具体 UI Library
```

Design Context 返回什么代码只代表参考表达。

真正实施时应根据目标仓库当前技术栈、组件库、状态管理和路由体系映射。

---

# 5. 通用用户习惯原则

用户习惯不是某一个项目的历史约定，而是当前目标用户完成任务的自然顺序。

审查时先问：

```text
谁在用？
他来这里完成什么任务？
最常用动作是什么？
最危险动作是什么？
什么信息是决策必须的？
什么信息只是内部实现细节？
```

不要把某个项目的术语、颜色、菜单顺序、平台列表或字段集合推广成通用标准。

---

# 6. 通用 Skill 与项目本地规则的关系

```text
通用 Figma Skill
→ 定义怎样审查

项目 AGENTS / Design Guide / Design System / Product Spec
→ 定义这个项目具体应该是什么
```

项目本地规则可以定义：

- 页面基准尺寸；
- 品牌色；
- 字体；
- Sidebar 宽度；
- Button 高度；
- 术语；
- Route；
- 组件名；
- 后端能力。

通用 Skill 不复制这些易失值，只要求审查时读取当前项目事实。
