# Figma 业务能力与前后端映射

这份 reference 负责回答：

> 一个 Figma 字段、按钮、状态或选项，怎样确认它在真实系统里有对应能力？

目标是避免两类错误：

```text
Figma 创造后端不存在的能力
```

以及：

```text
后端有实现细节
→ 机械暴露给普通用户
```

---

# 1. UI 字段六分类

任何会影响业务行为的 UI 字段至少归入一类：

| 类别 | 含义 | 典型来源 |
| --- | --- | --- |
| `STATIC_UI` | 固定产品文案/纯视觉 | Figma / 产品文案 |
| `USER_INPUT` | 用户输入后进入真实请求/命令 | Request Contract |
| `API_DYNAMIC` | 服务端返回的业务事实 | Response / Store |
| `SERVER_RUNTIME` | 当前服务器/数据库实时值 | API / DB / Runtime |
| `DESIGN_EXAMPLE` | 只用于设计 Data State | Figma 示例 |
| `SYSTEM_FIXED` | 后端固定策略，用户只读 | Service / Domain Rule |

关键字段如果无法归类，不得给 `READY`。

---

# 2. UI → Contract 映射模板

对重要字段建立最小映射：

```text
UI 名称：采集渠道
用户语义：本次外部采集使用哪一个已配置采集服务
Figma 类型：Select
真实来源：Capability / Provider Config Response
真实提交：provider_config_id
是否静态选项：否
空集合行为：阻塞创建
单项行为：可自动选择
多项行为：用户选择
```

不要求把完整 Schema 复制进 Figma 或文档；只记录决定 UI 行为所需的语义。

---

# 3. 前后端双向审计

必须做两个方向。

## A. Figma 动作 → 后端真实支持

例如：

```text
按钮：取消任务
```

检查：

- 后端是否有 cancel 行为；
- 哪些状态允许；
- 调用后是否立即终态还是进入 cancelling；
- 错误如何返回；
- UI 是否需要继续轮询。

## B. 后端能力 → Figma 是否需要入口/状态

例如后端有：

```text
queued / running / partial_success / failed / cancelled
```

如果这些状态会影响用户决策，Figma不能只设计“成功 / 失败”。

但后端内部枚举如果用户完全无需感知，也不要求机械全部显示。

---

# 4. Provider / 渠道 / 来源 / 平台不能混淆

这些概念经常在设计中被错误合并。

## 数据来源

回答：数据从哪里进入系统。

例如：

- 用户上传文件；
- 服务器批准目录；
- 外部网络采集；
- 未来其它正式入口。

## 采集渠道

回答：外部采集通过哪个已配置 Provider/Adapter 执行。

UI 可以使用业务语言“采集渠道”，但必须映射当前机器事实，如 `provider_config_id`。

## 目标平台

回答：内容属于哪个业务平台，如小红书、抖音等。

硬规则：

```text
文件导入
≠ 自动成为 Provider Config

Provider Config
≠ 目标平台
```

除非当前 Contract 正式统一了这些模型，否则 Figma 不得为了简化 UI 把它们塞进同一个选项集合。

---

# 5. Capability 动态配置

如果当前系统使用 Capability 表达 Provider/Platform 的合法能力，Figma 应设计“动态表单形态”，而不是复制一套静态机器配置。

正确：

```text
后端 Capability
→ 当前渠道支持的平台
→ 当前平台支持的排序/时间/内容类型
→ UI 动态展示
```

Figma 可展示一个代表性平台的展开状态，但 Annotation 应明确：

- 字段集合来自 Capability；
- 选项来自 Capability；
- 默认值来自 Capability；
- 不允许 Codex 按 Figma 示例硬编码平台分支。

---

# 6. 调度设计

任何用户可见“每N小时 / 每天 / 每周”选项必须检查当前调度 Contract 和解析器。

审查问题：

```text
它是 cron、interval、fixed time 还是其它模型？
前端提交的真实字段是什么？
该表达式能严格实现用户看到的自然语言吗？
跨天是否仍保持间隔？
时区是什么？
停机恢复语义是什么？
```

例如五字段 Cron 的 `*/9` 不能自动解释为“从任意起点严格每隔9小时”，因为它可能在日界重新对齐。

原则：

```text
机器表达式语义 ≠ 产品文案语义
```

产品选项必须由当前后端严格支持。

如果产品明确需要后端当前不能表达的新调度方式：

```text
Finding
→ code_issue / feature_required
→ Coding Change
→ Contract + Scheduler 扩展
→ Figma targeted re-review
```

# 7. 版本字段

不要机械认为版本号“技术化所以应隐藏”。

先问版本承担什么业务语义：

- 配置快照身份；
- 可复现性；
- 审计；
- 乐观锁/并发；
- 发布版本；
- 用户可理解的配置历史。

如果有实际用户价值，可以保留熟悉表达：

```text
v1 / v2 / v3 / v4
```

但裸 `v4` 在主列表是否有价值，还要看信息密度；可能更适合详情或关联选择器。

不同版本必须命名清楚：

```text
词包版本
调度版本
配置版本
```

不能因为数字相似就混为一个版本。

---

# 8. 异步任务

异步任务 Figma 应按真实状态机设计。

至少检查：

```text
创建中
queued
running
partial success
succeeded
failed
cancelling
cancelled
retry
```

具体状态以当前 Contract 为准，不使用这份清单反向要求所有项目都具备。

还要检查：

- progress 是否 determinate；
- 总量未知时不能伪造百分比；
- cancel 是否即时结束；
- retry 是全量还是失败项；
- 关闭页面是否影响后台执行；
- 用户最终结果在哪里查看。

---

# 9. 错误与安全

用户可见错误只展示当前公共 Error Contract 允许的安全信息。

默认禁止直接展示：

```text
Secret / Token / API Key
Provider Raw
内部文件路径
数据库连接信息
完整异常栈
内部 Request Payload
```

如果公共 Error Contract 提供 `request_id` / correlation id，并且用户需要报障，可以用产品语言展示“请求编号”。

内部 error code 是否展示取决于用户角色和产品价值，不因后端有字段就自动显示。

---

# 10. 示例数据

示例数据应满足：

1. 结构符合 Contract；
2. 状态组合合法；
3. 跨页面一致；
4. 不冒充服务器当前事实；
5. 不泄露真实生产 Secret/ID/PII；
6. 不使用明显 Stage/test 脏数据破坏产品可信度。

代表性 ID 可以使用明确 demo/示例语义，或者产品化编号样式；不要把真实数据库 UUID 外观当成普通用户必须理解的产品字段，除非确有使用价值。
