# Figma 业务能力与真实系统映射

这份 reference 负责回答：

> 一个 Figma 字段、按钮、状态、选项或页面动作，怎样确认它能和当前项目的真实系统能力接起来？

它不假设项目一定有“前端 + 后端 + 数据库”。真实系统能力可能来自：

```text
HTTP / RPC / GraphQL API
本地 SDK
移动端系统能力
桌面端本地服务
CMS
本地数据库 / 缓存
后台任务
第三方平台
文件系统
设备权限
静态内容配置
```

只检查当前项目实际存在的边界。

---

# 1. UI 事实分类

对会影响用户行为的内容，至少判断它属于：

| 类别 | 含义 | 可能来源 |
| --- | --- | --- |
| `STATIC_UI` | 固定产品文字或纯视觉 | 产品文案 / Design System |
| `USER_INPUT` | 用户可编辑并进入真实业务流程 | Form / Command / Request |
| `SYSTEM_DYNAMIC` | 系统或数据源返回的动态事实 | API / SDK / CMS / Local Store |
| `RUNTIME_STATE` | 当前执行中的运行状态 | Job / Device / Network / Process |
| `DESIGN_EXAMPLE` | 只用于设计展示的代表值 | Figma |
| `SYSTEM_FIXED` | 系统固定规则，用户只读 | Domain / Config / Platform Rule |

关键字段如果无法判断来源和语义，不能宣称正式开发基线已经闭环。

---

# 2. UI → 系统能力映射模板

对重要字段建立最小映射即可，不复制完整 Schema。

```text
UI 名称：<产品语言>
用户语义：<用户认为它做什么>
控件类型：<Select / Input / Toggle / Button / ...>
来源：<API / SDK / CMS / Local State / Config / ...>
真实机器字段/命令：<如适用>
是否静态选项：是 / 否
空集合行为：<隐藏 / 禁用 / 错误 / 空状态>
默认值来源：<产品决定 / 系统默认 / 用户配置 / 动态能力>
错误行为：<用户看到什么>
```

机器字段应存在于 Annotation/开发规格中，而不一定暴露给最终用户。

---

# 3. 双向能力审计

## A. Figma 动作 → 系统是否真实支持

例如设计里有“取消”“删除”“导出”“刷新”“重试”：

检查：

- 系统是否真的有该动作；
- 哪些状态允许；
- 是否有权限约束；
- 动作是同步还是异步；
- 成功/失败后页面怎样更新；
- 是否存在不可逆副作用。

## B. 系统能力 → Figma 是否需要入口或状态

如果系统已有某个状态/能力，并且用户需要理解或操作它，Figma 应有适当表达。

但内部状态如果用户完全不需要感知，不要求机械全部展示。

---

# 4. 数据来源、执行通道、目标对象不要混淆

很多产品都有多层概念，例如：

```text
数据从哪里来
通过什么机制执行
作用于哪个业务对象/平台/设备
```

这些层不能因为 UI 看起来更简单就自动合并。

例如：

```text
文件导入
≠ 自动等于外部网络采集渠道

支付渠道
≠ 商品来源

登录方式
≠ 用户角色
```

只有当前系统 Contract/Domain 明确统一时才合并。

---

# 5. 动态能力驱动

如果系统存在 Capability / Feature Flag / Permission / Device Support / Plan Tier 等动态能力：

```text
系统能力
→ 可见选项
→ 默认值
→ 可操作状态
→ 保存资格
```

UI 应由真实能力驱动。

Figma 可以画代表性状态，但 Annotation 要明确：

- 哪些选项是动态的；
- 动态集合来自哪里；
- 不允许实现方把示例列表硬编码成机器事实。

---

# 6. 时间、调度和周期

任何用户可见的：

```text
每N分钟
每N小时
每天
每周
定时发送
自动刷新
```

都必须检查当前系统的真实时间模型。

需要确认：

- cron / interval / fixed time / timer / OS scheduler / remote job；
- 时区；
- 跨日/跨月语义；
- 停机恢复；
- 前端/客户端提交的机器值；
- 用户文案是否与真实执行完全一致。

机器表达式能解析，不代表产品文案就一定成立。

---

# 7. 版本、型号和技术词不要机械处理

版本号、产品型号、标准名称是否展示，应按用户价值判断。

可以保留：

```text
v1 / v2 / v3
产品型号
协议/标准名
用户熟悉的品牌名
```

如果它有：

- 配置身份；
- 审计；
- 发布版本；
- 可复现性；
- 用户沟通价值。

但内部对象名、机器字段、调试代码如果用户没有价值，应留在 Annotation/开发规格。

---

# 8. 异步和后台任务

如果页面涉及异步执行，应按真实状态机设计，而不是固定套一个枚举。

检查实际可能出现的：

```text
创建中
排队
运行中
部分成功
成功
失败
取消中
已取消
重试
```

具体状态以当前项目机器事实为准。

还要检查：

- progress 是否有总量；
- 总量未知时不能伪造百分比；
- 关闭页面是否影响任务；
- Retry 是全量还是失败部分；
- 用户最终结果在哪里查看。

---

# 9. 数据库或持久化数据

如果 Figma 展示的数据最终存于数据库：

```text
数据库是事实来源
≠ 客户端直接连接数据库
```

应标注真实调用链，例如：

```text
Database / Repository
→ Service / API / SDK
→ Client State
→ Page
```

具体层级按项目实际架构映射。

Figma 只需要标清数据事实和消费路径，不复制数据库 Schema。

---

# 10. 错误、安全和权限

设计只展示用户有权看到的错误信息。

默认检查：

- Secret / Token / API Key；
- 内部文件路径；
- 数据库连接信息；
- 完整异常栈；
- 原始第三方响应；
- PII / 敏感业务数据；
- 权限不足状态。

如果系统提供 correlation/request/troubleshooting id，并且用户确实需要报障，可以用产品语言显示。

---

# 11. 示例数据

代表性数据应：

1. 结构符合当前真实数据形态；
2. 状态组合合法；
3. 跨页面一致；
4. 不冒充线上当前值；
5. 不泄露生产 Secret/真实敏感 ID/PII；
6. 不使用明显测试脏数据破坏产品可信度。

如果实际数据量、长文本、图片比例、列表长度会影响布局，Figma 应使用足以暴露这些问题的代表性样例，而不是只画“最理想的一条”。
