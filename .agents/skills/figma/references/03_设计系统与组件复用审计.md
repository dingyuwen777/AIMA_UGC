# Figma 设计系统与组件复用审计

这份 reference 负责判断：

> 什么应该做成公共组件，什么应该留在 Feature，当前 Figma 是否真的复用了同一设计系统，而不是“看起来一样”。

---

# 1. 四层边界

## Global Shared Component

跨 Feature 稳定复用、没有单一业务 Owner 的组件，例如：

```text
App Shell
Sidebar
TopBar
Page Header
Button
Input
Select
Checkbox
Switch
Tabs
Feedback
Empty State
Modal Shell
Drawer Shell
```

## Feature Component

带明确业务语义，但在同一 Feature 内稳定复用，例如：

```text
采集策略指标摘要
平台能力配置卡
运行任务进度卡
```

## Page Pattern

一个页面内重复出现的组合模式，例如：

```text
Filter + Table + Pagination
详情事实区
搜索 + 筛选 + 重置
```

## Page-private Composition

只在单一页面出现、没有稳定复用价值的业务布局。

原则：

```text
稳定复用事实
→ 决定抽象层级
```

不是：

```text
以后可能会用
→ 先做万能组件
```

---

# 2. 真复用与假复用

## 真复用

Figma 层面至少满足：

- 页面使用 `INSTANCE`；
- 主组件/组件集唯一；
- 可变字段用 Component Property / Variant；
- 视觉 Token 绑定相同变量；
- 不在业务页面复制内部视觉层。

## 假复用

典型表现：

```text
三页都有一样的按钮
但其实是三个 Frame
```

或者：

```text
使用公共 Select
但在上面盖一层独立 Text 改显示值
```

或者：

```text
组件被 Detach
再手工改成相似样子
```

这些都会让 Design-to-Code 产生多套实现。

---

# 3. Component Property 审计

可变内容应优先通过 Property 表达：

```text
Button.Label
Input.Text
Select.Text
Checkbox.Text
PageHeader.Title
PageHeader.Description
Feedback.Message
```

重点检查：

- `componentPropertyReferences` 是否仍绑定真实文本节点；
- 重排 Auto Layout 后引用是否被清掉；
- Instance override 是否真实生效；
- Variant 是否承担视觉状态而不是后端业务状态；
- Text Property 是否被额外覆盖文字绕过。

修改源组件后必须重新检查所有消费者实例。

---

# 4. Variant 设计

Variant 适合稳定视觉轴：

```text
State = Default / Hover / Disabled
Type = Primary / Secondary
Checked = On / Off
Tone = Success / Info / Warning / Error
```

不要为动态业务数据制造 Variant，例如：

```text
Provider=TikHub
Provider=FutureProvider
```

这种数据应由 Property / Runtime State / API 驱动。

Variant 矩阵过大时应拆分组件或使用 Instance Swap，不追求“一组件包含全部世界”。

---

# 5. Design Token 审计

稳定语义值优先使用：

```text
Color Variable
Typography Style
Spacing Variable
Radius Variable
Effect Style
```

审查时注意：

## 同值不等于同语义

两个颜色 Hex 接近或相同，不代表必须绑定同一个 Token。

例如：

```text
Success
Brand Primary
```

即使当前值恰好相同，语义仍可能不同。

## 同语义不应多套 Raw 值

如果明确都是 `Primary`，却出现：

```text
#E6005C
#F50057
```

应形成 Finding。

## Token 与代码映射

Figma Token 是设计事实；代码 Token 仍需按目标仓库现有样式系统映射。

不能因为 MCP 输出 CSS 变量名就静默改变仓库的 token 架构。

---

# 6. 图标

设计中使用 Unicode 字符作为临时视觉占位时，应明确：

```text
Figma glyph
≠ 生产 Icon Asset
```

生产代码应：

- 复用当前项目已有图标库；或
- 使用 Figma 导出的真实资产；
- 不手写一个“看起来差不多”的 SVG。

Figma 图层名应使用语义：

```text
图标槽/刷新
图标槽/采集策略
```

而不是用字符本身命名。

---

# 7. Auto Layout 与浮层

相关内容优先放在 Auto Layout 中，减少文本变长后的重叠。

但以下元素通常需要脱离 Auto Layout 流：

```text
Toast
Dropdown Menu
Popover
Overlay
绝对定位状态浮层
```

如果浮层放在 Auto Layout 父级却没有 `ABSOLUTE`，坐标可能随兄弟内容重新排布而漂移。

审查时同时检查：

- `layoutMode`；
- `layoutPositioning`；
- `clipsContent`；
- scroll container；
- overlay 层级。

---

# 8. 信息密度与组件抽象是两回事

视觉问题不要总靠新增组件解决。

例如三个 KPI 卡太松散，可以：

```text
改现有 Feature KPI 组件源
→ 单摘要条 + 三指标区
```

而不是：

```text
新建 Global MetricCard
→ 再把所有页面都迁过去
```

只有真实跨 Feature 复用后才升级抽象层级。

---

# 9. 组件审计输出

至少给出：

| 模式 | 当前层级 | 建议层级 | 证据 |
| --- | --- | --- | --- |
| Sidebar | Shared | Shared | 多页面真实实例复用 |
| Feature KPI | Feature | Feature | 只有目标 Feature 使用 |
| Filter Bar | Page Pattern | Page Pattern | 布局复用但业务字段不同 |

并明确：

- 哪些已有公共组件应复用；
- 哪些业务组件不应全局化；
- 是否存在重复公共实现；
- 修改公共 Owner 后需要复核哪些消费者。
