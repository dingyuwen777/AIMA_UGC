# Figma 设计系统、组件与业务逻辑复用审计

这份 reference 负责判断：

> 什么应该做成公共组件，什么应该留在 Feature，哪些业务规则应该只有一个 Owner，以及当前 Figma 是否真的复用了同一套设计和业务能力，而不是“看起来一样”。

---

# 1. 四层边界

## Global Shared Component

跨 Feature 稳定复用、没有单一业务 Owner 的基础 UI，例如：

```text
App Shell
Navigation
Page Header
Button
Input
Select
Checkbox
Switch
Tabs
Feedback
Empty State
Modal / Drawer Shell
```

## Feature Public Component / Logic

带明确业务语义，但在同一 Feature 或多个紧密相关页面中稳定复用，例如：

```text
Feature 指标摘要
Feature 详情事实区
同一业务资格判断
同一状态到产品文案的映射
同一动态字段生成规则
同一表单校验和默认值规则
```

这里的“公共”是**在真实复用范围内只有一个 Owner**，不等于必须提升为全局 Shared。

## Page Pattern

一个页面内重复出现的组合模式，例如：

```text
Filter + Table + Pagination
搜索 + 筛选 + 重置
详情区块布局
```

## Page-private Composition

只在单一页面出现、没有稳定复用价值的业务布局。

原则：

```text
真实复用事实
→ 决定抽象层级
```

不是：

```text
以后也许会用
→ 先做万能组件
```

---

# 2. 真复用与假复用

## 真复用

Figma 视觉层至少满足：

- 页面使用 `INSTANCE`；
- 主组件/组件集唯一；
- 可变字段用 Component Property / Variant；
- Token 绑定相同语义变量；
- 不在业务页面复制组件内部视觉层。

业务能力层至少满足：

- 同一业务规则有唯一 Owner；
- 多页面消费同一来源；
- 状态、资格、默认值、字段集合由同一机器事实或共享逻辑驱动；
- Figma Annotation 能指出真实 Owner，避免实现方复制规则。

## 假复用

典型表现：

```text
多个页面都有一样的按钮
但其实是多个手画 Frame
```

```text
使用公共 Select
但页面再盖一层独立 Text 改显示值
```

```text
组件被 Detach
再手工改成相似样子
```

```text
两个页面需要同一动态字段/权限/资格逻辑
却各自维护一套 if/else
```

这些都会导致实现分叉和长期漂移。

---

# 3. 视觉公共组件与业务公共逻辑分开

```text
Shared UI Component
≠
Business Rule Owner
```

例如：

```text
Button
→ 负责视觉、尺寸、状态、交互壳

“什么时候允许提交”
→ 业务资格判断
→ 由 Feature/Domain/Service 的唯一 Owner 决定
```

基础组件不应拥有：

- API endpoint；
- 业务权限；
- Feature 状态机；
- 数据库查询；
- 业务专属默认值。

这些通过 props/events/state 与上层业务 Owner 连接。

---

# 4. 跨页面业务逻辑复用

如果多个页面真正使用同一业务语义，例如：

```text
权限 → 可见操作
系统能力 → 可选项
状态 → 产品文案
同一表单校验
同一数据格式化
同一默认值规则
```

审查时必须确认是否已有共享 Owner：

- shared domain helper；
- feature public composable/view-model；
- shared state selector；
- backend/service capability；
- SDK/adapter；
- shared feature component。

如果没有，而 Design-to-Code 会让多个页面各写一套，应形成 Finding。

## 同一 Feature 多页面复用

进入 Feature Public Layer，不必为了“公共”提升到全局 Shared。

## 同外观不同语义

两个页面都有“停用”按钮，不代表停用规则一样。

可以共享 Button 视觉，但 Handler/资格仍由各自 Domain Owner 决定。

# 5. Component Property 审计

可变内容优先用 Property：

```text
Button.Label
Input.Text
Select.Text
Checkbox.Text
PageHeader.Title
Feedback.Message
```

重点检查：

- `componentPropertyReferences` 是否仍绑定真实节点；
- 重排 Auto Layout 后引用是否被清掉；
- Instance override 是否生效；
- Variant 是否承担稳定视觉状态；
- Text Property 是否被额外覆盖文字绕过。

修改源组件后必须检查关键消费者实例。

---

# 6. Variant 设计

Variant 适合稳定视觉轴：

```text
State = Default / Hover / Disabled
Type = Primary / Secondary
Checked = On / Off
Tone = Success / Info / Warning / Error
```

动态业务数据不应制造成 Variant，例如：

```text
Plan=A
Plan=B
```

这类数据应由 Property / State / Runtime Data 驱动。

---

# 7. Design Token 审计

稳定语义值优先使用项目现有：

```text
Color Variable
Typography Style
Spacing Variable
Radius Variable
Effect Style
```

注意：

```text
同值 ≠ 同语义
同语义 ≠ 多套 Raw 值
```

Figma Token 需要映射目标项目现有样式系统，不能因为工具输出某个 CSS 变量就静默改变代码 Token 架构。

---

# 8. 图标和资产

临时 Unicode glyph 不自动等于生产 Icon Asset。

生产实现应复用当前项目已有图标体系或正式资产。

组件图层用语义命名，例如：

```text
图标槽/刷新
图标槽/搜索
```

而不是用字符本身命名。

---

# 9. Auto Layout 与浮层

正文内容优先 Auto Layout，减少真实文案变长后的重叠。

以下通常需要独立定位：

```text
Toast
Dropdown
Popover
Tooltip
Overlay
```

检查：

- `layoutMode`；
- `layoutPositioning`；
- `clipsContent`；
- scroll container；
- z-order。

浮层放在 Auto Layout 父级却未脱离布局流时，位置可能回弹。

---

# 10. 信息密度与抽象层级是两回事

视觉问题不要总靠新增组件解决。

例如某 Feature 的指标卡太松散，可以改现有 Feature Component，而不是新建全局万能 MetricCard。

只有真实跨 Feature 稳定复用后才升级抽象层级。

---

# 11. 审计输出

至少给出：

| 模式/逻辑 | 当前层级 | 建议 Owner | 证据 |
| --- | --- | --- | --- |
| Navigation | Shared | Shared | 多页面真实复用 |
| Button | Shared | Shared | 无业务 Owner |
| Feature Summary | Feature | Feature Public | 只属于目标 Feature |
| 权限/能力动态字段 | duplicated/shared | Shared Domain / Feature Public | 多页面同语义 |
| Filter Layout | Page Pattern | Page Pattern | 布局复用但业务字段不同 |

并明确：

- 哪些公共视觉组件必须复用；
- 哪些业务逻辑必须收敛到唯一 Owner；
- 哪些组件应留在 Feature；
- 哪些不应为了形式全局化；
- 修改公共 Owner 后需要复核哪些消费者。
