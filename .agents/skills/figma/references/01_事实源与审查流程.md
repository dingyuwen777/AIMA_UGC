# Figma 事实源与审查流程

这份 reference 解决两个最常见的误区：

1. 只看 Figma 截图就判断设计“没问题”；
2. 只看当前代码就要求设计机械迎合实现。

Figma 审查必须先恢复当前事实，再判断设计与实现之间到底是“正确映射”“待实现设计”“文档过期”还是“实现缺陷”。

---

# 0. 宿主 Figma 工具边界

本 Skill 定义的是**审查方法、事实源和交付门禁**，不替代当前宿主环境自己的 Figma 工具规则。

如果宿主提供 Figma MCP、插件 Skill、设计写入 API 或 Design-to-Code 工具：

```text
先遵守宿主工具的前置技能 / 权限 / 调用规范
→ 再按本 Skill 决定应该读取什么、检查什么、怎样判断 Ready
```

例如宿主要求写 Figma 前先加载特定工具 Skill，或 Design Context 有专门前置规则，就必须遵守；本 Skill 不得用仓库文本绕过这些约束。

如果当前环境只能读 Figma、不能写 Figma：

- `review-only` 仍可执行；
- `review-and-fix` 必须明确报告写入能力缺失，不得假装已经修改；
- `baseline-ready` 仍需满足其余实际可验证门禁，缺失的必要验证必须如实标记。

# 1. 开始前的最小事实恢复

仓库相关任务按以下顺序：

```text
适用 AGENTS.md / 项目本地规则
→ 同仓 Coding Skill（存在时）
→ 项目 Figma / Frontend Guide
→ 目标 Route / Page / Store / API
→ 相关 Contract / Capability / Service / Scheduler / Provider Registry
→ 目标 Figma Page / Section / Frame / Prototype
```

只读取当前任务需要的事实，不为了“全面”机械扫描整个仓库或整个 Figma 文件。

## 1.1 什么情况下必须读后端

只要 Figma 中出现以下任意内容，就必须检查对应机器事实：

- 用户可配置字段；
- 状态枚举；
- 运行进度；
- 启用/停用资格；
- 调度周期；
- Provider / Channel / Platform；
- 动态 Search 参数；
- 文件上传或目录限制；
- 批次、任务、Run、Retry、Cancel；
- 计费/费用提示；
- 用户可见错误。

如果只是纯排版、字号、间距、颜色，不需要为了形式读取无关后端模块。

# 2. 三类事实源

## 2.1 设计事实

来源：

```text
Figma Frame
Component / Component Set
Component Property
Variable / Style
Prototype Variable / Reaction
Annotation
Flow Starting Point
```

它回答：

> 页面应该怎样表达、怎样交互、哪些模式应该复用。

它不自动回答：

> 后端是否已有字段、服务器当前有多少数据、第三方现在是否可用。

## 2.2 业务机器事实

来源优先级按项目实际情况：

```text
Public Contract / Schema
→ Generated Client
→ Service / Domain / Repository
→ Store / Feature API
→ Tests
```

它回答：

> 系统当前真正支持什么输入、输出、状态、约束和错误。

## 2.3 当前运行事实

来源：

```text
真实 API Response
数据库查询
服务器配置
Runtime / Worker / Scheduler 当前状态
有界外部 Probe
```

它回答：

> 此刻具体值是什么。

Figma 示例只能表达布局，不能替代当前运行事实。

# 3. Review Target

每次正式审查先写清：

```text
File:
Page:
正式 Section:
Frame / Node:
Prototype Starting Point:
对应 Route / Feature:
模式: review-only | review-and-fix | baseline-ready
```

如果存在多个候选：

```text
正式开发基线
历史参考
备份
废弃归档
```

必须先确定唯一当前目标。

## 3.1 不从文件名猜正式状态

“最新”“V2”“最终版”之类名称不能单独证明它是正式事实源。需要结合：

- Section / Page 说明；
- Guide；
- Flow Starting Point；
- 用户本轮明确决定；
- 是否使用当前设计系统组件。

---

# 4. 审查顺序

推荐顺序固定为：

```text
A. 页面信息架构
B. 字段与后端能力映射
C. 动态数据来源
D. 公共组件 / Feature 组件边界
E. 静态视觉和布局
F. 状态覆盖
G. Prototype Variable / Reaction / Flow
H. 用户术语
I. Fresh Screenshot
J. Codex Design Context
```

不要从 J 倒推 A；Design Context 是最后的开发视角复核，不是业务需求事实源。

# 5. 冲突分类

发现 Figma 与代码不一致时，先归类。

## `design_outdated`

当前正确业务事实已稳定，Figma 仍表达旧行为。

处理：修 Figma。

## `code_issue_detected`

正式需求/Contract/设计已经确认，但当前实现明显错误。

处理：停止让 Figma 迎合 Bug；返回 Coding 修复实现，再做 targeted re-review。

## `future_design`

Figma 表达已确认的未来产品方向，但当前代码尚未实现。

处理：可以保留设计，但必须标明 Target IA / Future State；Design-to-Code 当前不得制造伪实现。

## `decision_required`

设计和实现存在真实业务取舍，仓库没有批准事实。

处理：给出证据和方案，等待 Owner 决策；不静默选择。

## `runtime_only`

设计结构正确，但具体值必须来自服务器。

处理：保留代表性示例，同时明确 API/服务器事实源。

---

# 6. review-and-fix 的最小 Owner 原则

有 Figma 修改授权时，先找真正 Owner：

```text
Design Token？
公共 Component？
Feature Component？
Page Pattern？
单一 Frame？
Prototype Variable？
```

优先改最小公共 Owner。

错误示例：

```text
三个页面的 Select 都叠字
→ 三个页面分别移动 Text
```

正确：

```text
检查公共 Select 是否缺 TEXT Property
→ 修 Select
→ 重新验证三个消费者
```

# 7. 证据等级

## 只读 Metadata

证明：节点、尺寸、父子结构、实例关系、名称。

不能证明：最终视觉无错位。

## Screenshot

证明：当前可见视觉结果。

不能证明：隐藏状态、Component Property、Reaction 正确。

## Prototype / Plugin API 结构扫描

证明：Variable、Reaction、Flow、Overlay、定位和隐藏状态。

不能证明：生产 API 会真正成功。

## Design Context

证明：Codex/Design-to-Code 侧实际看到的结构、组件、Annotation 和参考代码。

不能证明：目标仓库后端支持 Figma 中所有行为。

## Repo / Contract / Runtime

证明：机器能力和当前运行事实。

不能证明：设计视觉正确。

因此 Ready 必须组合证据，而不是用其中任一层替代其它层。
