# 事实源与同步判断

技术文档同步的第一步不是“看代码然后改 Markdown”，而是先回答：**这类事实到底由谁负责？当前哪一份证据最能证明它？**

## 1. 先区分三类信息

### 当前已经实现的事实

例如：

- 当前 API 请求/响应结构；
- 数据库表、约束和 Migration；
- 当前模块入口和调用链；
- 当前配置、命令、依赖版本；
- 当前真实测试行为。

这类事实优先由**机器事实**证明，例如代码、Contract、Schema/Migration、generated artifact、锁文件、测试和实际运行结果。

文档负责解释这些事实的目的、边界、使用方式和定位方式，不重新手抄一份完整机器定义。

### 已批准但尚未实现的设计

有些项目会用正式 Roadmap、Spec、ADR、Change 或设计文档记录已经批准但尚未完成的目标。

这类内容不能因为代码里暂时没有就自动删除；但文档必须明确它是“计划/待实现”，不能写成当前已经支持。

### 历史原因

历史 Change、ADR、Release Notes、Git history 负责回答“为什么当时改成这样、当时怎样验证”。

当前 README、架构说明或使用文档不应要求读者按时间顺序阅读所有历史记录才能理解现在的系统。

## 2. 机器事实不是“代码永远正确”

文档和实现冲突时，不能机械认为代码永远正确。

先按项目本地规则和当前任务事实判断：

```text
实现偏离已批准约束？
→ 代码有问题，返回 Coding 修实现

实现已经按新的已批准决定变化，文档落后？
→ 更新当前文档

正式设计描述未来能力，代码尚未实现？
→ 保留未来状态，但明确“尚未实现”

双方都缺乏足够证据？
→ 继续调查或提请上游决定
```

Docs 的职责是找到正确事实，不是让两份错误内容表面一致。

## 3. 怎么避免第二套事实

以下内容如果已有可靠机器事实，通常不要在 Markdown 中完整复制：

- 完整 API 字段清单；
- 完整 JSON Schema；
- 完整数据库列/索引/约束；
- 完整函数签名；
- 精确依赖版本全集；
- generated client；
- 枚举全集；
- 可以由工具直接生成的结构。

文档更适合说明：

```text
这个 Contract 为什么存在
哪些字段最影响业务理解
调用者应该怎样使用
失败/兼容边界是什么
最新精确定义在哪里
```

例如，不需要把一个 80 字段 OpenAPI Response 全抄进 README；可以说明“列表接口返回分页结果，精确字段以 generated OpenAPI 为准”，再解释读者真正需要理解的分页、身份和状态语义。

## 4. 什么时候应该引用代码、表、类或函数

判断标准只有两个：

1. **是否明显帮助读者理解或定位；**
2. **是否不会制造第二套需要同步维护的事实。**

推荐：

```text
“AI 打标的生产入口在 backend/.../content_labeling.py；
该模块负责把 Prompt 输出校验后写入 Analysis Repository。”
```

不推荐：

- 把整段生产函数复制进文档；
- 把每个 private helper 都列成目录；
- 手工维护和 Schema 一模一样的 Markdown 字段表；
- 只列类名，却不解释它为什么存在和在链路中的作用。

如果路径本身频繁变化且对读者没有长期价值，宁可描述稳定模块职责，并指向项目已有代码导航。

## 5. Docs Impact 的三档判断

### `not_applicable`

只有当变化不改变人类需要理解、操作、调用、维护或排障的事实时使用。

常见例子：

- 内部变量改名；
- 保持行为完全不变的局部重构；
- 增加测试覆盖但没有新行为；
- 格式化或无语义生成物刷新。

必须给出事实依据，不允许只写“无影响”。

### `targeted`

有文档影响时的默认模式。

先从变化边界反推：

```text
谁的行为变了？
→ 谁生产/消费这个行为？
→ 哪个机器事实证明它？
→ 哪几份当前文档承担解释责任？
```

只读取这些直接相关内容，再根据真实依赖向上下游扩一层；没有证据不要扩成全仓扫描。

### `full`

只在影响确实跨越一个完整文档域时使用，例如：

- 核心架构发生系统变化；
- 主数据链路被重构；
- 多模块公共 Contract 体系调整；
- 部署/恢复/运行模型变化；
- 文档治理结构本身大规模调整。

`full` 不是“读取所有 Markdown”，而是“把受影响的完整文档域覆盖到位”。

## 6. 候选文档不是必改清单

Coding、Change、用户或搜索结果给出的文档路径都只是候选导航。

Docs 必须继续判断：

```text
这篇文档是否真的承担该事实？
当前内容是否已经正确？
改它会不会重复别处机器事实？
不改它会不会让读者产生错误理解？
```

只有答案支持修改时才产生 diff。

## 7. 同步完成的最低证据

按任务实际情况验证：

- 引用路径真实存在；
- 链接没有明显断裂；
- 文档描述和当前正确事实一致；
- 示例与当前公共行为兼容；
- 命令确实是项目当前入口；
- 如果声称运行过示例/命令/测试，必须有本轮执行证据；
- 没有把待实现能力写成已实现；
- 没有为了“同步”把代码 Bug 写成正式设计。
