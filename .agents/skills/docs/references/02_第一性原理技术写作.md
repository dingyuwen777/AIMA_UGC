# 第一性原理技术写作

技术文档的目标是让读者理解并完成真实任务，不是让作者展示术语储备。

## 1. 先讲问题，再讲方案

优先回答：

```text
为什么需要它？
没有它会出现什么具体问题？
它解决哪一段问题？
它明确不负责什么？
```

然后再介绍架构、类、表、接口或设计模式。

不推荐：

> 系统采用 Repository Pattern、DDD 和 Hexagonal Architecture，实现高度解耦。

推荐先说明实际机制：

> 不同数据来源的字段不一样，如果后续分析代码直接识别每个平台格式，所有模块都会和 Provider 耦合。因此系统先把外部数据转换成统一结构，后面的入库和分析只依赖这一种结构。

如果项目确实使用 Repository、DDD 等术语，再在读者已经理解问题后说明这些术语在当前项目中对应什么职责。

## 2. 先解释真实流动，再解释内部名字

大多数系统文档最容易理解的顺序是：

```text
输入
→ 关键处理步骤
→ 状态/数据怎么变化
→ 输出/持久化/下游消费者
```

例如：

```text
用户上传 Excel
→ API 创建导入任务
→ Worker 读取文件
→ 转成统一数据
→ 去重
→ 写数据库
→ 前端查询结果
```

读者理解这条链后，再解释 Import Batch、Job、Mapper、Canonical 等名字会更容易。

如果主题不是数据处理，就用真实控制流或状态流，例如：

```text
CLI 参数
→ parser
→ command handler
→ 文件系统副作用
→ exit code
```

不要为了符合模板硬造“数据流”。

## 3. 术语后置，术语必须用白话解释

重要术语第一次出现时至少说明：

```text
它在当前上下文是什么意思？
为什么需要这个概念？
它和读者已经知道的东西有什么关系？
```

例如：

> `Canonical` 可以理解为系统内部统一的数据格式。抖音、小红书、Excel 等来源先转成它，后续代码就不用分别理解每个平台自己的字段。

这比只写“Canonical Model 是领域标准化层”更有帮助。

允许保留标准名、库名、协议名和领域术语，但不要用缩写或专业词替代解释。

## 4. 最小例子只解决一个理解障碍

能用最小例子明显降低理解成本时就给例子。

例如解释幂等：

```text
第一次提交：request_id = abc
→ 创建任务 #1

网络超时后重试：request_id 仍然是 abc
→ 返回任务 #1
→ 不再创建任务 #2
```

这个例子只解释“重复请求为什么不会产生第二个任务”，不需要把完整数据库表、HTTP Request 和 Worker 代码都复制出来。

例子必须明确是说明机制的示意时，就不要让读者误以为这些值来自生产环境。

## 5. 是否写代码位置，看它是否真的帮助理解

代码路径适合回答：

- 生产入口在哪；
- 哪个模块真正拥有这个行为；
- 想修改这个行为应该先从哪里看；
- 当前描述可以去哪里验证。

代码路径不适合用来：

- 枚举所有内部 helper；
- 代替职责解释；
- 复制整段实现；
- 制造一个和真实代码结构同步维护的“文件树镜像”。

类名、函数名、表名、接口名同理。

## 6. 不同文档有不同读者任务

不要把所有技术文档写成同一种结构。

### README

优先帮助读者快速回答：

```text
这个模块做什么
为什么存在
怎么运行/使用
输入输出是什么
核心代码入口在哪
常见修改点和限制是什么
```

### Architecture / Blueprint

优先解释：

```text
为什么采用这个长期边界
模块怎么协作
哪些决定不能被普通任务静默改变
主要数据/调用链
机器事实在哪
```

不要复制每个类和字段。

### API Guide

优先解释：

```text
调用者为什么用这个接口
请求/响应的业务语义
关键状态、错误、幂等、分页或兼容规则
完整机器定义在哪里
```

已有 OpenAPI/Schema 时，不再手写一份完整字段镜像。

### Debug / Operations Guide

优先解释：

```text
出现什么现象
从哪里开始查
正常链路是什么
哪些日志/状态/命令能证明哪一层
常见失败边界
如何安全恢复
```

### Design / Decision

优先解释：

```text
问题和硬约束
真实可选方案
为什么选当前方案
代价和边界
什么时候需要重新评估
```

不要用“先进、企业级、高可用、可扩展”这类无法单独证明机制的形容词替代设计依据。

## 7. 当前说明不要写成历史流水账

不推荐：

```text
Stage 3 加了 A
Stage 4 改成 B
PR #52 又补了 C
后来我们又重构成 D
```

如果读者只想知道现在怎么工作，这些历史会增加理解成本。

当前文档应该直接说明 D 现在为什么存在、怎么工作。真正影响当前理解的历史原因可以简短保留并链接 ADR/Change/Git；其余历史放到历史事实源。

## 8. 白话不等于删掉技术细节

“适合基础较差的人”不等于把重要机制全部简化掉。

正确做法是：

```text
先用白话解释目的和因果
→ 再给必要技术名词
→ 再给真实实现定位
→ 再给边界、失败和验证
```

事务、锁、幂等、Migration、Contract、状态机等如果确实影响系统行为，必须保留，只是要先解释它们为什么必要。

## 9. 文档完成后的读者测试

针对目标读者问：

1. 他是否知道这个东西为什么存在？
2. 他是否知道它解决和不解决什么？
3. 他是否能复述主要数据/调用/状态流？
4. 他是否知道真实代码或机器事实在哪里？
5. 重要术语是否能不用更多术语解释清楚？
6. 他是否知道怎么验证、使用、修改或排障？
7. 文档有没有复制大量机器事实，让未来维护者必须同步改两处？

如果主要问题答不上来，文档即使格式漂亮也需要继续修改。
