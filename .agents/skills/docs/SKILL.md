# Docs

Docs 的目标不是“让 Markdown 看起来更完整”，而是让读者能够**正确理解当前系统，并知道真实实现在哪里**。

一个合格的技术文档应优先帮助读者回答：

```text
为什么存在？
解决什么问题？
不解决什么问题？
输入和输出是什么？
数据或调用怎么流？
当前代码在哪实现？
关键边界和限制是什么？
怎么验证、使用或排障？
精确机器事实去哪里看？
```

本 Skill 既可以独立用于文档 Review / 编写 / 更新，也可以由 Coding 在判断存在文档影响后按需加载。

核心执行链：

```text
恢复当前事实
→ 明确任务授权和文档目标
→ 判断 Docs Impact
→ 选择 not_applicable / targeted / full
→ 读取最少充分事实源与目标文档
→ 审查或编写
→ 对照事实、读者任务和第二套事实风险复核
→ 只交付证据支持的结论
```

详细规则分布在 `当前场景所需完整约束/`。命中对应情形时必须读取相关 完整约束；不要只读本文件后凭印象补流程。

## 1. 固定原则

1. **上位规则优先。** 先遵守系统、用户、项目 `AGENTS.md`、贡献规范、文档目录本地规则和当前任务授权。Docs 不能降低 Coding、项目 CI、Review、Git 或安全门禁。
2. **当前事实优先，但不能机械认为代码永远正确。** 文档与代码、Contract、Schema/Migration、配置、测试或正式设计冲突时，先判断是实现缺陷、文档过期、已批准但尚未实现的设计，还是新的上游决定，再修正确的一方。详见 当前场景所需完整约束。
3. **从第一性原理解释。** 文档先解释“为什么存在、解决什么问题、数据怎么流、代码在哪实现”，再介绍必要术语。这里的“数据”也包括请求、事件、文件、任务状态或控制流；没有数据流的主题就解释真实调用/状态流，不为了模板生造流程。
4. **术语必须用白话解释。** 首次出现的重要术语要说明“它在这里实际代表什么、为什么需要它”。允许使用领域术语，但禁止用术语替代因果解释，禁止为了显得专业堆概念、缩写、设计模式或形容词。
5. **例子服从理解目标。** 能用最小例子明显降低理解成本时就给最小例子；例子只解释一个关键点，不复制一套生产实现，不把示例数据写成真实当前事实。
6. **是否引用代码由理解价值决定。** 代码路径、表名、类名、函数名、接口名、配置项只有在帮助读者理解、定位修改点或验证当前实现时才引用；如果引用会快速过期、重复机器事实或制造第二套规范，就改为指向真实事实源并解释其职责。
7. **不会制造第二套事实。** 完整 Schema、完整 API 字段、完整函数签名、精确依赖版本、生成物、枚举全集等已有机器事实时，文档主要解释含义、边界、用法和事实源位置，不手工复制一份需要同步维护的镜像。
8. **当前说明与历史记录分开。** README、架构说明、Guide、Appendix 等当前文档主要描述“现在为什么这样、现在怎么工作”；Change、ADR、Release Notes、Git history 等承担必要的历史原因。不要把提交/PR/Stage 流水账当成当前技术说明。
9. **不为完整而制造文档。** 文档数量、目录、模板和章节由项目实际需求决定；没有独立读者任务或长期维护价值时，不新增文档来满足形式。
10. **默认 targeted，不全仓扫。** 有文档影响时默认只读受影响事实源、调用链和相关文档。只有确实存在广泛长期架构、主数据流、跨模块运行边界或部署体系变化时才使用 `full`；`full` 也只覆盖相关文档域，不等于机械读取仓库全部 Markdown。
11. **Review 默认不等于修改授权。** 用户只要求审查时只报告；只有任务明确允许修改时才能进入 Review + Fix 或 Write / Update。未经授权不提交、推送、开 PR、合并或发布。
12. **发现代码问题时不让文档迎合 Bug。** 如果当前证据表明实现偏离正式要求，Docs 应报告实现问题并返回 Coding；代码修正后再做一次针对性复核。不要通过改文档把错误实现合法化。
13. **以实用性为结束条件。** 读者看完应知道为什么、怎么流、去哪里找真实实现、怎么验证或排障。文档没有帮助读者完成真实任务时，即使术语很多、章节很多也不算高质量。
14. **仓库内具体文件引用必须同时可定位、可点击。** 当 Markdown 文档引用当前仓库内一个已确认存在的具体文件，且该引用承担实现定位、事实验证、进一步阅读、修改入口或排障导航职责时，不论文件类型，统一使用**完整仓库相对路径 + 可点击链接**。`.md`、`.py`、`.json`、`.yaml/.yml`、`.toml`、`.sql` 以及其他源码、测试、配置、Contract、Schema、Migration、脚本文件遵循同一原则；显示文字保留完整仓库相对路径，链接目标使用从当前文档位置可解析的相对路径并验证真实存在。不得只写不可点击的 inline-code 路径，也不得用“这里”“详情”等隐藏真实目标；命令、目录树、glob、占位路径、协议/流程示例、生成路径、代码字面量等非导航内容不机械链接化。模板或生成型文档必须按最终输出位置重新验证相对链接。详细写法见 当前场景所需完整约束，审查与修复见 当前场景所需完整约束。

## 2. Docs Impact：让同步有效但不变重

每次调用先确定文档影响范围：

### `not_applicable`

适用：当前变化不改变任何需要人类理解或使用的事实，例如纯内部变量重命名、无行为变化的局部 helper 重构、只增加测试覆盖等。

要求：

- 给出简短事实依据；
- 不加载无关文档；
- 不制造“为了有文档 diff 而改文档”的变化。

### `targeted`

这是**有文档影响时的默认模式**。

适用：单个功能、API 行为、配置、模块职责、调试方式、用户操作或局部数据流发生变化。

执行：

```text
变化边界
→ 对应机器事实/正式设计
→ 直接相关文档
→ 必要上下游消费者
→ 审查/更新
```

不要因此读取整个 docs 目录。

### `full`

仅在变化确实跨越较大长期边界时使用，例如：

- 核心架构调整；
- 主数据/调用链重构；
- 多模块公共 Contract 体系变化；
- 部署、恢复或运行模型系统变化；
- 大规模文档治理本身。

`full` 表示“完整覆盖受影响文档域”，不是“全文库扫描”。仍要先界定事实边界，再读取相关集合。

详细判断见 当前场景所需完整约束。

## 3. 工作模式

### Review Only

只审查，不改文件。重点检查：

- 事实是否正确；
- 是否遗漏读者完成任务所需的关键说明；
- 是否从第一性原理解释；
- 术语是否真正解释；
- 是否存在第二套事实；
- 是否把历史流水账当当前说明；
- 是否能定位真实实现和验证方式。

### Review + Fix

先完成 Review，再只修确认有问题且在授权范围内的文档。不要边猜边改，也不要顺手重写无关章节。

### Write / Update

新建或更新文档时，先确定读者是谁、他需要完成什么任务、真实事实源是什么，再组织内容。不要先套固定模板后填术语。

完整步骤见 当前场景所需完整约束。

## 4. 第一性原理技术写作

技术文档通常优先按以下思路组织，但它不是强制模板：

```text
问题 / 背景
→ 为什么需要这个机制
→ 它负责什么、不负责什么
→ 输入 / 输出
→ 数据 / 调用 / 状态如何流动
→ 当前实现位置与关键边界
→ 必要术语的白话解释
→ 最小例子（确实有帮助时）
→ 验证 / 调试 / 当前限制
→ 精确机器事实位置
```

不同文档只保留对读者有价值的部分。README 可以更强调入口和使用；架构文档更强调原因和边界；调试文档更强调现象、路径和验证；API Guide 更强调调用语义而不是复制完整 OpenAPI。

详细写作规则见 当前场景所需完整约束。

## 5. Review 的六个检查维度

至少按实际任务检查：

1. **Fact Correctness**：描述是否与当前正确事实一致；
2. **Coverage**：是否遗漏必要边界、流程、限制、验证或使用方法；
3. **First-principles Clarity**：是否先解释为什么和怎么工作，而不是直接堆实现名词；
4. **Terminology**：术语是否有白话解释，是否存在无意义概念堆叠；
5. **Source-of-truth Safety**：是否复制机器事实形成第二套需要同步的定义；
6. **Usability**：基础较弱的目标读者看完后，能否实际理解、定位、使用、修改或排障。

不是每篇文档都要写出这六个标题；这是审查视角，不是新的文档模板。

## 6. 与 Coding 协作

Coding 与 Docs 的职责保持分离：

```text
Coding
→ 判断代码/行为变化是否产生 Docs Impact
→ 无影响：记录 not_applicable 依据
→ 有影响：读取 .agents/skills/docs/SKILL.md

Docs
→ 恢复受影响事实
→ 决定 targeted / full
→ 决定真正相关文档
→ Review / Fix / Write
→ 如果发现实现问题，返回 Coding

Coding 修复实现（如需要）
→ Docs targeted re-review
→ Completion / Review / CI
```

Coding 提供的候选文档只是导航线索，不是“必须全部修改”的清单；Docs 必须自己根据当前事实判断。

Docs 不复制 Coding 的需求、TDD、调试、验证、Git、Review、安全等研发规则，也不能替代它们。详细协作边界见 当前场景所需完整约束。

### 6.1 `code_issue_detected` 反向硬路由

Docs 一旦确认“正确的正式要求/机器事实”与当前实现冲突，并判断需要修改实现时，必须先明确输出：

```text
code_issue_detected
→ 正确事实及其来源
→ 当前实现冲突位置
→ 需要返回 Coding 的原因
```

然后按以下规则处理：

- 如果同一仓库存在 [`.agents/skills/coding/SKILL.md`](../coding/SKILL.md)，在**任何实现代码修改之前必须读取它**，并切回 Coding 的完整需求、风险、调试/TDD、验证、Review、Git 和完成门禁；Docs 不得用自己的文档规则代替 Coding 去直接修实现；
- 如果 Coding Skill 不存在、无法读取，或当前授权只允许文档 Review，则 Docs **不得修改实现代码**；只报告 `code_issue_detected`、证据和阻塞，让上游决定后续研发动作；
- Coding 完成修复且取得自己的新鲜验证后，再返回 Docs 执行 `targeted re-review`，只复核原受影响文档和必要事实源；
- 如果第二次 targeted re-review 又发现新的业务决定、Contract 冲突或明显范围扩大，不继续自动循环，而是回到上游需求/决策流程重新界定任务。

这条反向路由是协作门禁，不代表 Docs 自己获得代码修改授权，也不降低 Coding 的任何原有规则。

## 7. 完成前复核

完成文档任务前至少确认：

```text
事实源已实际读取，而不是从聊天猜
目标读者和真实任务明确
重要因果链可理解
必要数据/调用/状态流解释清楚
代码/Contract/Schema 等引用真实且有理解价值
仓库内具体文件导航引用显示完整仓库相对路径并可点击，且链接已从当前文档或最终生成位置验证
术语首次出现已有白话解释
最小例子没有伪装成生产事实
没有无意义复制机器事实
当前说明没有退化成历史流水账
受影响文档已覆盖，无关文档没有被顺手改
发现的实现缺陷没有通过改文档掩盖
实际执行了适用的链接/路径/示例/命令/测试检查
```

只能陈述本轮实际验证过的结果；没有运行的链接检查、命令、示例、测试或构建，不得写成“已验证”。
