# Docs Skill 使用说明

`docs` 用来解决一个核心问题：**怎样让技术文档与当前正确事实保持一致，同时让基础较弱的读者真正看懂系统为什么这样设计、数据或调用怎么流、代码在哪里实现。**

它不是 Markdown 美化器，也不是固定模板生成器。Docs 会先恢复当前事实，再判断哪些文档真正受影响；写作时先解释问题和因果，再介绍必要术语。

> 本 README 只说明怎么使用 Docs。正式规则以 [`SKILL.md`](SKILL.md) 和命中的 [`references/`](references/) 为准；README 不复制全部规则，也不能替代正式规则。

## 1. 什么时候应该用 Docs

以下任务适合直接使用 Docs：

- 检查技术文档和当前代码是否一致；
- 检查 README、Blueprint、Architecture、API Guide、运维/调试文档是否过期；
- 只做文档 Review，不修改文件；
- Review 后修正确认有问题的文档；
- 新写模块 README；
- 更新架构说明、API 使用说明、调试指南、部署/运维说明；
- 检查文档是否堆术语、缺少因果、对基础读者不友好；
- 检查文档是否手抄 Schema、API、类、函数或依赖版本，形成第二套事实；
- 在 Coding 完成代码变化后，按 Docs Impact 做针对性文档同步。

如果主要任务是功能开发、Bug 修复、重构、Code Review、PR/CI 或 Release，应使用 [`coding`](../coding/README.md)。

## 2. Docs 写文档时最先回答什么

一个技术文档不应该先从框架名、模式名或类名开始。

Docs 优先帮助读者回答：

```text
为什么存在？
解决什么问题？
不解决什么问题？
输入和输出是什么？
数据、请求、事件或状态怎么流？
当前代码在哪里实现？
关键边界和限制是什么？
怎么使用、验证或排障？
精确机器事实应该去哪里看？
```

然后再解释必要术语。

例如，不要只写：

```text
系统采用 Canonical Model 和 Repository Pattern。
```

应该先让读者知道：

```text
不同平台和 Excel 的原始字段不一样。
如果后续分析代码分别理解每种来源，所有模块都会和外部格式耦合。
所以系统先把不同来源转换成统一内部结构，后面的入库和分析只依赖这一种结构。
```

读者理解这个问题后，再解释 `Canonical`、`Repository` 等术语在当前项目里实际代表什么。

## 3. 三种工作模式

### 3.1 Review Only

只检查，不修改文件。

适合：

```text
我想先知道文档有哪些问题
我还没决定是否修改
我要先做文档审计
```

典型请求：

```text
使用 docs 检查当前技术文档和真实实现是否一致。
只 Review，不修改文件；给出事实源、问题、影响和建议。
```

Review 不只是检查错别字或 Markdown 格式，还会检查：

- 事实是否正确；
- 是否遗漏关键流程、边界、限制和验证方法；
- 是否先讲原因和流动，再讲术语；
- 术语是否能用白话解释；
- 是否制造第二套事实；
- 是否把历史 PR / Stage 流水账当成当前系统说明；
- 代码路径、命令、链接和示例是否仍然真实；
- 是否把尚未实现的能力写成已经支持。

### 3.2 Review + Fix

先审查，再只修改确认有问题且在授权范围内的文档。

典型请求：

```text
使用 docs 检查并修正这份文档。
先确认当前正确事实，再修改真正过期或难懂的内容；不要顺手重写无关章节。
```

如果发现代码本身错了，Docs 不会为了“文档一致”把错误代码写成正式设计，而是走 `code_issue_detected → Coding` 路由。

### 3.3 Write / Update

用于新写或更新文档。

典型请求：

```text
使用 docs 为这个模块补 README。
目标读者是第一次接手项目的人；说明为什么存在、负责什么、不负责什么、主要数据/调用流、真实实现入口、怎么使用和排障。
```

写之前先确定：

```text
谁会读？
他为什么需要这篇文档？
读完以后要能做什么？
当前正确事实源是什么？
哪些精确机器事实只应该链接，而不应该手抄？
```

## 4. `not_applicable`、`targeted`、`full` 怎么选

这三个词描述的是**文档影响范围**，不是文档质量等级。

### `not_applicable`

当前代码变化没有改变任何需要人理解、使用、维护、部署或排障的事实。

例如：

- 内部变量改名；
- 行为完全不变的局部 helper 重构；
- 只增加测试覆盖。

必须给出具体原因，不能只写“无影响”。

### `targeted`

这是有文档影响时的默认方式。

```text
变化入口
→ 当前真实实现 / Owner
→ 受影响 Contract / Schema（如果有）
→ 直接消费者
→ 真正承担该事实的文档
→ 审查或更新
```

只读取和当前变化直接相关的内容，不因为仓库里还有 TikHub、Scheduler、Word Report 等其他模块就全部扫描。

### `full`

只在变化影响完整长期文档域时使用，例如：

- 核心架构调整；
- 主数据/调用链整体重构；
- 多模块公共 Contract 体系变化；
- 部署、恢复或运行模型系统变化；
- 大规模文档治理本身。

`full` 的意思是“完整覆盖受影响文档域”，**不是全文库扫描**。

详细判断见 [`references/01_事实源与同步判断.md`](references/01_事实源与同步判断.md)。

## 5. 在 AIMA_UGC 中能不能单独用 Docs

可以。

Docs 本身支持独立 Review / Fix / Write / Update。但 AIMA_UGC 的仓库级规则规定，所有仓库任务先从根 [`AGENTS.md`](../../../AGENTS.md) 进入。

所以单独做文档任务时，实际链路是：

```text
AGENTS.md
→ Coding 只完成仓库级事实恢复、风险、权限和 Git 路由
→ Docs 成为当前任务的主要工作流
→ Review Only / Review + Fix / Write / Update
```

这不是让 Coding 代替 Docs 写文档，而是保留 AIMA_UGC 的统一仓库门禁。

## 6. 最常用的请求方式

### 6.1 全面检查某一份文档

```text
使用 docs 检查 docs/xxx.md。
以当前仓库代码、Contract、Migration、配置和测试为事实源；只 Review，不修改。
检查事实正确性、关键遗漏、第一性原理解释、术语、第二套事实风险和实用性。
```

### 6.2 检查并修复某个文档域

```text
使用 docs targeted 检查并修复 Excel 导入相关文档。
只读取与 Excel 导入真实数据流直接相关的代码、Contract、测试和当前文档，不扫描无关专题。
```

### 6.3 做一次较大的文档审计

```text
使用 docs 做 full 文档审计，但先界定受影响文档域。
检查核心架构、主调用链、模块 README 和相关运维说明是否与当前实现一致；不要机械扫描所有 Markdown。
```

### 6.4 把文档改得更容易理解

```text
使用 docs 改写这份技术说明。
不要删除必要技术细节；先用白话讲清为什么存在、问题是什么、调用/数据怎么流，再解释术语和实现位置，必要时给一个最小例子。
```

### 6.5 新增模块 README

```text
使用 docs 为 backend/src/... 模块补 README。
先读取真实入口和调用链；README 面向基础较弱的新开发者，说明职责、边界、输入输出、主要流动、实现位置、使用/调试方式和当前限制。
```

## 7. 什么叫“不要制造第二套事实”

如果精确内容已经有可靠机器事实，通常不要在 Markdown 里完整复制一份。

例如已有：

- OpenAPI / JSON Schema；
- Pydantic Contract；
- Alembic Migration；
- 数据库表定义；
- generated client；
- 锁文件；
- 完整函数签名或枚举。

Docs 更应该解释：

```text
它为什么存在
最重要的业务语义是什么
调用者应该怎么用
主要边界和失败方式是什么
最新精确定义在哪里
```

例如，不需要把 80 个 API 字段再手抄成 README 表格；可以解释这个接口的业务目的、分页/状态/身份语义，并链接当前 OpenAPI 机器定义。

详细规则见 [`references/01_事实源与同步判断.md`](references/01_事实源与同步判断.md)。

## 8. 是否要引用代码、类、表和函数

只问两个问题：

1. 它是否明显帮助读者理解或定位真实实现？
2. 引用它是否不会制造第二套需要手工同步的事实？

适合写：

```text
生产入口在哪
哪个模块真正拥有这个行为
想修改这个行为应该先从哪里看
当前文档可以去哪里验证
```

不适合写：

```text
枚举所有 private helper
把生产函数整段复制进 README
手写一份和 Schema 一模一样的字段表
只列一串类名但不解释它们为什么存在
```

## 9. Docs 发现代码错了怎么办

Docs 不负责用文档规则直接修代码。

当证据表明正确正式要求与当前实现冲突时：

```text
Docs
→ code_issue_detected
→ 说明正确事实和来源
→ 说明当前实现冲突位置
→ 返回 Coding
```

如果同仓存在 `../coding/SKILL.md`，任何实现代码修改前必须先读取 Coding，并切回完整研发、测试、Review、Git 和交付门禁。

修复后：

```text
Coding 新鲜验证通过
→ Docs targeted re-review
```

如果二次复核发现新的业务决策、Contract 冲突或明显范围扩大，就回到上游需求/决策流程，不无限往返。

详细规则见 [`references/04_与Coding协作.md`](references/04_与Coding协作.md)。

## 10. Docs 有没有 CLI

当前 **没有 Docs CLI**。

Docs 的主要入口是 Agent 读取 [`SKILL.md`](SKILL.md) 并按当前任务执行。不要自行假设存在 `docs.py` 或其他命令。

需要项目发现、Active Change、冲突或 Ready Check 等研发辅助命令时，使用 Coding 自带的 [`../coding/scripts/`](../coding/scripts/) 工具，并遵守 Coding 规则。

## 11. 一个好的 Docs 结果通常应该包含什么

Review Only 通常至少说明：

```text
Docs Impact 和实际范围
读取了哪些关键事实源
发现了什么问题
哪些候选文档本身已经正确、不需要改
是否发现实现问题或未决事实
哪些内容没有实际验证
```

Review + Fix / Write / Update 还应说明：

```text
实际修改了哪些文件
每个修改解决什么理解或事实同步问题
实际执行了什么验证
还有什么剩余风险
```

不要只给一句“文档已同步”。

## 12. 目录怎么读

```text
docs/
├── README.md      # 人类使用说明
├── SKILL.md       # Docs 正式主规则
├── agents/        # Agent metadata / 默认提示
└── references/
    ├── 01_事实源与同步判断.md
    ├── 02_第一性原理技术写作.md
    ├── 03_审查编写与修复流程.md
    └── 04_与Coding协作.md
```

不同任务只读取命中的最少充分 reference；不要为了“完整”机械扩成全仓阅读。
