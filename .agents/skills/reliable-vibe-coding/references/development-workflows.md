# 设计、实施与根因调试

## 现状调查

修改已有项目之前，只读取与任务直接相关的：

- README、规则、需求和架构导航；
- 入口、调用链、数据流和模块 Owner；
- Contract、Schema、Migration、配置和依赖锁定版本；
- 相关实现、测试、错误处理和正常参照；
- 构建、运行、测试和 CI 命令；
- 当前分支、工作区和近期相关变更。

不要依据单个文件重构架构。能从仓库确认的事实先自行检查。

不同语言和工具链的 Manifest、锁文件、wrapper、构建、测试、打包入口按 [language-and-toolchain-profiles.md](language-and-toolchain-profiles.md) 调查；该文件提供导航，不替代当前仓库实际规则和命令。

## 设计门禁

对 L2 先形成最小任务契约；对 L3 先形成 2–3 个方案，比较正确性、兼容性、维护成本、迁移、回滚和验证。只询问一个当前最上游且会改变结果的问题。

在这些信息明确前不要实现 L3：

- 目标与非目标；
- 成功标准；
- 公共接口和数据边界；
- 必须保持不变；
- Migration、部署与回滚策略；
- 用户负责作出的业务取舍。

保持已确认方案连续性。新事实使原方案不可行时，先解释证据、影响和替代方案，再改变路线。

## 第一性原理与约束下最优解

不要把“第一性原理”当口号，也不要把“最优”理解为不计成本的理论极值。按以下顺序形成可复核的工程判断：

1. 用可观察行为重述真正目标，区分用户想达到的结果与其预设实现方式。
2. 列出不可违反的硬约束：安全、数据正确性、公共兼容、仓库规则、已确认需求、版本和授权边界。
3. 追踪根因或必要机制，拆掉仅因惯例、历史偶然或工具偏好形成的假设；对每个关键推断说明证据和可证伪条件。
4. 至少考虑保留现有路线的最小增量方案；复杂任务再比较 2–3 个真实可行方案，不为凑数制造伪方案。
5. 按正确性、兼容性、简单性、可维护性、可逆性、性能、交付成本和可验证性比较。只有任务有实际性能目标时，才用测量结果主张性能最优。
6. 选择满足全部硬约束、机制最少且证据最充分的方案。更复杂的架构必须由已观察到的规模、风险、第二实现或故障模式证明必要。
7. 用失败测试、最小实验、原型或现有正常参照验证关键假设；证据推翻方案时回到约束重新推导，不在错误前提上叠补丁。

“行业最佳实践”只能作为候选和风险清单。若它与项目实际版本、架构或兼容边界不一致，以当前事实和经确认的目标为准；需要改变既有路线时先完成设计门禁。

## 实施计划

每一步采用：

```text
[步骤] → 修改范围：[文件/模块]
       → 预期结果：[行为/接口]
       → 验证方式：[完整命令/检查项]
```

步骤必须小而完整、可独立验证，并明确依赖。不要使用 `TBD`、`TODO` 或“补充适当测试”等不可执行占位。

## 测试驱动

新功能、Bug 修复、重构和行为变化默认执行：

1. Red：写一个表达真实行为的最小测试；
2. Verify Red：实际运行，确认它失败而不是环境报错，并且因目标行为尚未实现而失败；
3. Green：只写使测试通过的最少代码；
4. Verify Green：运行目标测试及相关测试，读取完整输出和退出码；
5. Refactor：只在绿色后整理重复和命名，不增加行为；
6. Re-verify：重构后再次运行验证。

测试真实行为，避免只验证 Mock、调用次数或内部实现。必须 Mock 时先理解依赖副作用，并把原因写进测试或 Change。

允许的例外包括纯文档、纯配置、生成代码、一次性探索或环境确实无法自动测试。明确说明例外、替代验证和剩余风险。探索代码不能冒充已验证生产实现。

完整验证层级和证据职责按 [validation-strategy.md](validation-strategy.md)；项目真实存在 Web/API/PostgreSQL/Provider 边界时再叠加 [testing-strategy.md](testing-strategy.md) 专项规则。

## 根因调试

遇到 Bug、测试失败、构建失败、性能问题或异常行为时：

1. 读取完整错误、警告和调用栈；
2. 稳定复现并记录精确条件；
3. 检查近期变更和环境差异；
4. 跨组件边界跟踪输入、输出、配置和状态；
5. 在仓库中寻找同类正常参照并列出差异；
6. 提出一个可证伪假设，说明“根因是 X，因为证据 Y”；
7. 用最小实验一次改变一个变量；
8. 确认根因后建立失败用例，再实施单一修复；
9. 运行回归及相关验证。

假设失败时回到证据，不在旧补丁上继续叠加。连续三次修复假设失败后停止，重新审视架构、前提、环境和观测手段，并向用户报告原始错误与下一步证据需求。

## 最小、精准、兼容

- 优先复用标准库和现有依赖；
- 不为少量代码引入依赖或抽象层；
- 不顺手格式化、改名或优化无关代码；
- 删除仅因本次修改失效的内容；
- 保持公共 API/ABI、导入路径或模块路径、CLI、配置、默认值、数据/序列化格式、启动方式、错误类型和关键错误信息兼容；
- 破坏性变化先说明版本策略、迁移、回滚和验证。

不要为了显得完整而创建仓库没有的前后端分层、Repository/Service 抽象、Owner 表、Schema、事件总线、Migration 框架或契约测试基础设施。任务确实需要建立新边界时，把它作为设计决策处理，不把通用建议伪装成仓库现状。

## 代码组织原则

函数拆分以“是否降低理解和维护成本”为判断，不使用固定行数、调用次数或语句数量作为硬门槛。

1. 优先保持主流程清晰：主流程应按业务阶段自然展开，读者能从上到下理解关键路径；不要为了形式上的“整洁”把连续业务逻辑打散，也不要把多个独立责任堆在一个函数中。
2. 在下列情况提取函数，前提是提取后边界更清楚且没有引入额外绕行：
   - 逻辑具有独立、可命名的业务语义；
   - 可以隔离 I/O、网络、数据库事务、文件系统或其他副作用边界；
   - 能显著降低条件分支、嵌套或主流程的认知复杂度；
   - 形成值得独立测试、复用或替换的行为单元；
   - 同一逻辑出现真实重复，提取后能消除重复而不隐藏差异。
3. 不因以下单一因素决定“必须拆”或“禁止拆”：
   - 函数超过某个固定行数；
   - 新函数只有少量语句；
   - 辅助函数当前只调用一次；
   - 为满足“单一职责”、DRY 或其他原则的形式要求。
   这些都只能作为信号，最终以可读性、语义边界、副作用隔离、测试价值和维护成本判断。
4. 提取后如果只是增加跳转层级、转发参数、包装单个已有调用，且没有增加业务语义、边界隔离、测试价值或复用价值，则保持内联，不创建无意义 wrapper/helper。
5. 函数命名表达真实业务或领域意图，避免 `doStep3`、`handleThing` 之类过程性或含糊命名。若无法给提取出的逻辑起一个清楚名字，优先重新审视边界是否成立。
6. 作用域保持最小但不要机械使用闭包：仅模块内部使用的函数不导出；只有确实需要捕获局部上下文且不会降低测试、调试和类型分析能力时才使用嵌套函数。单次调用不是使用闭包的理由。

## 独立可验证能力

独立验证的目的不是增加测试文件数量，而是让有价值的行为在不依赖完整系统启动的情况下能够被快速、重复、可信地验证。

### 什么时候应当建立独立验证闭环

满足以下任一情况时，优先把该能力视为独立验证单元：

- 有明确、可描述的输入和输出；
- 具有独立业务价值或可被其他能力复用；
- 对接网络、数据库、文件系统、消息、外部 SDK 等副作用边界；
- 包含数据转换、分页、状态机、幂等、重试、错误分类等可独立失败的规则；
- 故障排查时需要区分“本能力失败”与“上下游失败”；
- 启动完整系统的成本显著高于验证该能力本身。

不要因为目录叫“module”、类是 public、函数很长或当前只有一个调用方，就机械创建独立测试单元。测试粒度由行为边界、风险、依赖和失败模式决定。

### 一个独立验证闭环至少回答什么

在计划、实现、README/测试说明或现有等价事实源中明确：

1. **生产入口**：正式实现从哪里进入，测试不得复制另一套业务逻辑；
2. **显式输入**：参数、Contract、Fixture、文件、数据库前置状态等；
3. **可观察输出**：返回值、持久化状态、Artifact、事件、错误或其他可断言结果；
4. **可控边界**：哪些依赖使用真实隔离环境，哪些使用 Fake/Stub/Fixture，为什么；
5. **测试层级**：行为/Unit/Component、Contract、Integration、Workflow Acceptance、Golden Path、External Probe、Build/Runtime 或仓库已有等价层级中，哪一层最能证明目标行为；
6. **运行入口**：一个明确命令或最小步骤能够重复执行；
7. **成功判据**：什么结果算通过，什么仍未覆盖；
8. **人类说明**：后续维护者能够快速找到测试位置、依赖和运行方式。

测试代码和本轮执行结果是验证事实；README、测试指南等人类文档负责导航和解释，不复制第二套断言、Schema 或期望值清单。仓库已有统一测试文档或模块 README 规范时沿用它；没有时，只在确有持续维护价值时建立最小说明，不为每个函数新建文档。

### Fixture、Fake 与真实 Probe

- **Fixture**：固定、可复现输入，用来验证转换、Contract 和边界行为；不要把未经脱敏的生产数据直接提交到仓库。
- **Fake/Stub**：隔离不属于当前目标的外部依赖，但测试仍应通过正式生产入口调用目标能力；不要只验证 Fake 自己。
- **真实 Probe**：用于确认真实外部边界、版本或 Provider/设备/远端环境行为；默认不替代普通自动化测试。若有费用、写操作、安全或速率风险，必须显式受控并说明，不默认进入普通 CI。

如果一个能力只能通过复制生产逻辑才能“独立测试”，先修正边界或测试方法，而不是接受两套实现长期漂移。

## 独立调试复用生产实现

调试工具、Raw Probe、示例入口或测试夹具只负责：

- 准备显式输入；
- 注入可控边界；
- 调用正式生产入口；
- 捕获并展示输出。

不得复制正式分页、映射、校验、状态转换、重试、错误处理或写库逻辑。若调试需要不同实现，先证明边界真实存在，并保持同一 Contract。

## Git、依赖与安全

- 开始前记录分支和工作区状态；
- 不覆盖或混入用户修改；重叠无法安全隔离时停止并请求方向；
- 未经授权不建分支、不提交、不推送、不建 PR、不合并、不部署；
- 先确认语言、运行时/SDK/Compiler、包管理器、Manifest、锁文件和实际版本；
- 不因网上有新版本而升级依赖、Runtime 或工具链；
- 不硬编码、打印、提交或上传凭据；
- 如果执行 Git 提交，提交信息的语言和格式遵循项目本地规则；项目没有明确规则时，优先跟随仓库近期相关提交的稳定风格和用户当前语言，不引入新的提交规范；
- 不关闭认证、授权、证书、输入校验或安全检查来制造通过。

AIMA_UGC 等项目如果在 `AGENTS.md` 明确要求中文提交信息，属于项目 Overlay，在该项目中仍必须执行；通用 Skill 本身不把中文强加给其他仓库。

## 代码注释

注释的目标是降低维护者恢复上下文的成本，不是提高注释覆盖率。默认使用项目既有语言和风格；仓库没有明确约定时，跟随目标文件附近代码、同模块公开接口和该语言生态中已经实际采用的稳定风格，不为了使用本 Skill 强行切换注释语言。

以下位置优先提供简短 docstring 或定点 inline comment：

- public/exported 接口需要解释稳定 Contract、重要前置条件、副作用或非显然返回/异常语义时；
- 内部/private/helper 函数包含非显然业务规则、关键不变量、状态机/状态转换、算法取舍、兼容原因、重试/幂等边界或重要 I/O/事务副作用时；
- 一段代码之所以“必须这样写”来自外部协议、历史兼容、安全约束、性能测量或容易被未来维护者误删的原因时。

注释优先回答：

```text
为什么这样做？
必须保持什么约束？
失败/状态转换边界是什么？
为什么不能采用看起来更简单的写法？
```

不要：

- 给简单 getter/setter、单行 wrapper、名称已经完整表达行为的 helper 机械补 docstring；
- 逐行翻译 `if`、循环、赋值或调用；
- 在注释复制会漂移的 Schema、配置默认值或业务事实，应该引用其正式事实源；
- 用长注释掩盖糟糕命名、过深嵌套或错误函数边界。

AIMA_UGC 等项目如果对注释语言有更具体规则，以目标路径适用的 `AGENTS.md`/仓库规范为准。

## 可观测性与日志

实现功能时先确认仓库是否已经存在正式 logging/event/telemetry 体系。只有存在可复用基础设施，并且观测对理解运行过程、调试或后期排障有实际价值时，才增加日志/事件；不要为了通用“最佳实践”给没有这类体系的项目新造框架。

优先考虑这些观测点：

- 低频但重要的业务生命周期开始/完成/终止；
- API/Worker/Scheduler/Job、CLI command、batch stage、device operation 等真实存在的异步或长流程阶段和关键状态转换；
- 外部网络、数据库、文件、Provider、模型、SDK、设备等 I/O 的安全摘要与结果；
- Retry、backoff、降级、部分失败、跳过、取消、接管和永久失败；
- 会显著缩短“问题发生在哪一步”定位时间的关键分支。

日志内容应尽量使用仓库已有稳定 event 名和关联字段，例如项目真实存在的 `request_id`、`job_id`、`run_id`、`batch_id`、trace/span、task/device/content ID、stage/status/error_code 等标识；不要为了日志凭空设计第二套业务 ID。

级别遵循仓库现有约定；没有更具体规则时可参考：

```text
DEBUG   高频正常细节、轮询、逐批/逐页诊断信息
INFO    低频重要生命周期与真实业务结果
WARNING 可恢复异常、Retry、部分失败、需要关注但仍能继续
ERROR   永久失败、非法配置、需要人工介入或未预期异常
```

控制噪声和重复：

- 不在 INFO 为每条记录、每次循环或每个正常轮询刷屏；批量处理优先记录批次/阶段摘要，必要的逐条细节放 DEBUG；
- 同一异常优先在真正拥有处理/终止责任的边界记录一次，避免 Router/Service/Repository 或其他分层每层重复打印相同 traceback；
- 日志是解释执行过程的辅助证据，不替代项目正式业务事实（例如数据库记录、文件/Artifact、事件账本）、Health、Metric 或 Audit 机制。

安全边界：

- 复用仓库现有 logger、结构化 event、Formatter、脱敏和轮转/输出机制；不创建平行 FileHandler/日志目录或第二套 telemetry 管线；
- 禁止记录 Secret、Token、密码、Cookie、Authorization、完整连接串、未脱敏 PII、原始敏感 Payload/Raw；
- 错误上下文只记录定位所需的最小安全字段；已有脱敏机制也不能成为主动打印 Secret 的理由。

如果一个重要功能故障时现有观测无法回答“执行到了哪一步、使用了哪个已有业务标识、为什么失败/重试/跳过”，应把缺失观测点作为实现质量问题修正；反之，如果正式状态、已有事件或现有日志已经足够，就不要重复增加消息。

## 文档同步

代码改变后检查正式需求、README、API/ABI、Contract、Schema、Migration、配置示例、架构、构建/打包、运行和运维说明等文档。只更新真正受影响的当前事实，保持术语、路径和示例与实现一致。行为不变时不要制造历史叙事或无关文档改动。

项目如果存在自己的文档目录、编号、命名、ADR/Blueprint/Roadmap 职责或历史不可改写规则，遵守项目 Overlay；通用 Skill 不替所有仓库规定 AIMA 的文档组织方式。
