# 仓库边界、数据交换与条件式约束

## 适用原则

只执行仓库当前真实存在，或本次需求经过确认后明确建立的约束。先通过项目索引、适用规则、需求、架构、Contract、Schema、Migration、代码和测试做有界检查，再决定哪些条目适用。

- 找到事实：记录路径、适用范围、当前或目标状态、Owner（若有）和版本依据，并严格执行。
- 未找到且任务不依赖：标记“不适用”或“在本次检查范围内未发现”，然后跳过。
- 未找到但任务依赖：不要补造接口、Owner、分层或流程；把缺口作为上游设计问题处理。
- 材料冲突：列出各自证据和影响。未解决会改变接口、数据、兼容或验收结果的冲突前停止写入。

“未发现”不等于证明“不存在”。报告实际搜索范围，不声称读取了全部仓库。

## 条件式事实地图

仅在存在相应证据时建立以下映射：

| 维度 | 需要确认的事实 |
|---|---|
| 模块边界 | 目录、职责、允许的依赖方向、公共入口、模块或代码 Owner |
| 前后端边界 | UI 与服务端职责、鉴权位置、校验责任、调用入口、生成客户端或 BFF 约定 |
| API Contract | 路由/方法、请求响应、错误、版本、分页、兼容与弃用规则 |
| 事件与消息 | Topic/事件名、生产者、消费者、Schema、顺序、重试、幂等和失败处理 |
| Schema 与文件格式 | 字段、类型、空值、枚举、默认值、时间、时区、单位、编码和版本 |
| 数据 Owner | 唯一事实源、读写责任、完整性约束、派生数据和缓存失效方式 |
| Migration | 迁移链、前后兼容窗口、部署顺序、回填、回滚和恢复 |
| 共享验证 | 契约测试、Schema 校验、生成物检查、固定夹具和集成环境 |

不要把表中的条目当成项目必须采用的架构清单。

## 执行既有边界

仓库存在相关约束时：

1. 沿正式入口调用，不从前端、脚本、测试或相邻模块绕过既有服务边界直接读写内部状态。
2. 让生产者和消费者引用同一 Contract 或生成来源；不要在两端手写含义不同的重复类型、枚举、错误或转换规则。
3. 前端校验服务于交互体验，不能替代服务端已有的安全和完整性校验；后端也不要复制只属于展示层的状态。
4. 保持字段含义、空值、默认值、时间、时区、单位、精度、分页、排序、错误和幂等语义一致。
5. 遵守既有数据 Owner 和唯一事实源。缓存、索引、报表和 UI 状态不得静默变成第二写入源。
6. 复用正式生产逻辑。调试入口、适配器和测试夹具只准备输入、调用正式入口并观察输出，不复制业务规则。
7. 遵守仓库实际定义的依赖方向。没有前后端分离或分层架构时，不强行套用这些规则。

## 改变共享语义的门禁

修改既有 API、事件、Schema、文件格式、配置 Contract 或持久化语义前：

1. 找出生产者、消费者、Owner、文档、生成物、测试、Migration 和部署入口。
2. 明确目标行为、兼容窗口、版本策略、部署顺序、数据回填、失败恢复和回滚。
3. 比较保留兼容、分阶段迁移和破坏性切换等真实可行方案；没有用户或仓库确认，不静默选择破坏性路线。
4. 把同一语义变更映射到实现、测试、Contract/Schema 和受影响文档，避免只改一端。
5. 使用仓库已有契约测试、Schema 验证或生成命令。不存在时不为形式新增框架；如果风险需要验证，创建最小行为测试或先请求设计决策。

任务本身明确要求建立新 Contract 或边界时，将其视为 L3 设计，而不是把通用模板当成既有事实。

## 并行开发

- 开始前比较 Active Change 的路径、模块、Contract、数据、Migration、配置和共享验证资源，只检查实际适用的维度。
- 不同工作可并行的前提是没有未解决的语义依赖，并且能够独立验证。
- 多个工作触及同一共享语义时，指定一个 Owner，或先完成并验证共同 Contract，再让各消费者基于明确版本继续。
- 只有仓库已有机制或协作者明确同意时才建立冻结点；冻结点写清版本、提交、Schema 或决策及解除条件。
- 同步、rebase、切换分支、Contract 更新或 Active Change 变化后重新检查冲突。
- 只能声明“基于当前可见状态未发现冲突”，不能声称看见未提交、未推送或无权限访问的工作。

## 计划与交付记录

在计划或 Change 中只记录适用项：事实来源、受影响生产者/消费者、保持不变、兼容和 Migration、验证命令、并行依赖及冻结点。不存在的维度不创建空洞章节；会改变结果但无法确认的维度列为待决策项。
