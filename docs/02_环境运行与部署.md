# 环境、运行与部署

本文是 AIMA_UGC 的日常运行入口。优先回答：**拿到源码以后，怎样用最少步骤在 Windows 或 Linux 上把真实后端、PostgreSQL、Worker 和 Vue 前端跑起来，以及怎样用同一套 Docker Runtime 在本地和服务器运行完整容器栈。**

架构、Schema、Contract 和生产部署边界仍分别以 `AGENTS.md`、`docs/blueprint/`、Migration、代码和 Roadmap 为准。本文明确区分源码开发、完整容器 Runtime 与正式不可变 Production Release，不把其中一种入口误写成另一种。

---

# 1. 本地开发快速开始

本地源码调试只需要记两个命令。Windows 和 Linux 使用**完全相同**的正式入口。

## 1.1 前提

开发机已经具备仓库锁定版本的：

```text
Python
uv
Node.js
npm
Docker CLI + Docker Engine
```

精确版本事实源：

- [`.python-version`](../.python-version)
- [`.uv-version`](../.uv-version)
- [`.node-version`](../.node-version)
- [`frontend/package.json`](../frontend/package.json)
- [`uv.lock`](../uv.lock)
- [`frontend/package-lock.json`](../frontend/package-lock.json)

Windows 第一次准备工具链可继续使用：

- [`scripts/setup_dev_environment.cmd`](../scripts/setup_dev_environment.cmd)

Linux 的工具链安装与应用启动是两件事。仓库现有 [`scripts/setup_dev_environment.sh`](../scripts/setup_dev_environment.sh) 是 CentOS Stream 9 x86_64 的特定宿主初始化脚本；不应把它当成应用日常启动命令。只要目标 Linux 已准备正确版本的 Python/uv/Node/npm/Docker，下面两个 Python launcher 与 Windows 共用同一实现。

## 1.2 终端 1：启动完整本地后端

从仓库根执行：

```bash
uv run python scripts/dev/backend.py
```

这个命令不是“只启动 FastAPI”。它会把本地业务运行所需的基础组件准备好，再启动正式 API/Worker。

成功后主要地址：

```text
API          http://127.0.0.1:8090
Readiness    http://127.0.0.1:8090/health/ready
```

## 1.3 终端 2：启动前端

从仓库根执行：

```bash
uv run python scripts/dev/frontend.py
```

浏览器访问：

```text
http://127.0.0.1:5173/
```

Vite 会把 `/api` 和 `/health` 代理到本地 FastAPI。

因此日常源码开发的心智模型固定为：

```text
终端 1：backend.py
终端 2：frontend.py
浏览器：127.0.0.1:5173
```

不再要求开发者手工拼接 PostgreSQL、Migration、多个 Secret 和 Worker 启动命令。

# 2. 第一次运行 Backend 会自动做什么

第一次执行：

```bash
uv run python scripts/dev/backend.py
```

启动器按顺序处理：

```text
检查/创建 env.local
→ 创建 .runtime 本地目录
→ 在 .runtime/internal-secrets 自动生成仍缺失的数据库密码和三个 Cursor signing key
→ 检查 Docker Engine
→ 创建或启动 PostgreSQL 18.4 本地容器
→ 等 PostgreSQL ready
→ alembic upgrade head
→ 按 env.local 设置历史迁移批准根并准备 TikHub / LLM 外部 Secret
→ 幂等维护本地 TikHub Provider Config
→ 启动正式 Worker
→ 按需启动 Scheduler
→ 启动 FastAPI
→ 等待 /health/ready = 200
→ 输出当前功能可用状态
```

本地 PostgreSQL 固定使用：

```text
image      postgres:18.4
container  aima-ugc-postgres-dev
volume     aima-ugc-postgres-dev-data
host       127.0.0.1
port       5432
database   aima_ugc
user       aima_ugc
```

数据库密码由启动器随机生成，不要求开发者填写，也不写入 Git。密码文件固定为：

```text
.runtime/internal-secrets/postgres_password
```

PostgreSQL 数据保存在 Docker named volume 中。正常关闭 [`scripts/dev/backend.py`](../scripts/dev/backend.py) 时，launcher 会停止 API / Worker / Scheduler，再停止 `aima-ugc-postgres-dev` PostgreSQL 容器并在控制台输出停止结果；container 本身和 `aima-ugc-postgres-dev-data` named volume 都会保留，数据库数据不会被删除。

## 2.1 后续启动

以后再次运行同一命令时：

```text
既有 PostgreSQL 容器在运行
→ 直接复用

容器已停止
→ 自动启动

Migration 已在 head
→ upgrade head 幂等返回

已有内部 Secret
→ 继续复用，不静默轮换
```

因此不需要每次重新配置数据库。

### 旧 `.runtime/secrets/postgres_password` 已废弃

旧版本曾把 PostgreSQL 密码放在：

```text
.runtime/secrets/postgres_password
```

当前 launcher **不再读取、迁移或兼容**这个旧路径。新的唯一运行时路径是：

```text
.runtime/internal-secrets/postgres_password
```

密码只是 PostgreSQL Role 的认证凭据，不代表一份独立数据。不同密码不会在同一个数据库容器里自动对应不同数据副本；如果应用使用的密码与数据库内 Role 实际密码不一致，只会认证失败。

因此，如果旧本地环境同时保留了 `aima-ugc-postgres-dev-data` volume，但新的 `.runtime/internal-secrets/postgres_password` 不存在，launcher 会 fail closed：不会读取旧路径密码，也不会生成一个新密码去猜既有数据库。对于可丢弃的本地开发数据，按第 12 节显式重置本地数据库即可。若确实要保留旧本地数据，只能由开发者自行确认数据库 Role 的真实密码，并把匹配值放到新的内部路径；这不是 launcher 自动兼容能力。

# 3. [`env.local`](../env.local) 到底是什么

仓库提交的是：

- [`env.local.example`](../env.local.example)

真实本地文件：[`env.local`](../env.local)。

已经加入 [`.gitignore`](../.gitignore)。

第一次运行 Backend 或 Frontend 时，如果 [`env.local`](../env.local) 不存在，launcher 会自动从 [`env.local.example`](../env.local.example) 复制一份；开发者不需要先手工创建。

[`env.local`](../env.local) **只属于源码开发 launcher 的输入界面，不是 Docker Compose/生产运行时 Contract**。

正式 API/Worker/Scheduler 在本地和生产都使用同一类双 Secret 根语义：

```text
非敏感运行配置
→ AIMA_* 子进程环境

AIMA 内部 Secret
→ AIMA_SECRET_DIR
→ 本地 .runtime/internal-secrets/

外部 Provider / LLM Secret
→ AIMA_EXTERNAL_SECRET_DIR
→ 本地 .runtime/secrets/

Provider Config
→ PostgreSQL 只保存 secret_ref
```

Dev launcher 读取 [`env.local`](../env.local) 后会把历史迁移批准根传给 API 和 Worker；同时把 TikHub/LLM API Key 写到 `.runtime/secrets/`，并从正式子进程环境中移除本地明文 Key。PostgreSQL password 和三个 Cursor signing key 只位于 `.runtime/internal-secrets/`。Docker Compose 则读取 `env.production` 并通过持久挂载 / Compose Secret 实现同样的内部/外部分层，不读取 [`env.local`](../env.local)。

# 4. [`env.local`](../env.local) 现在只需要配置什么

默认文件非常短：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=

AIMA_LLM_BASE_URL=
AIMA_LLM_PROVIDER_NAME=
AIMA_LLM_MODEL=
AIMA_LLM_API_KEY=

AIMA_HISTORICAL_IMPORT_ROOT=.runtime/historical-input

AIMA_DEV_ENABLE_SCHEDULER=false
```

其中 `AIMA_HISTORICAL_IMPORT_ROOT` 是源码开发模式下批准给“导入数据 → 服务器目录”枚举的专用根目录。默认相对路径按仓库根解析，launcher 会创建 `.runtime/historical-input`；页面仍只能使用其下相对路径，不会开放任意文件系统访问。本地电脑来源不读取这个配置，由用户通过浏览器显式选择多文件或文件夹。

数据库 Host、Port、用户名、密码、数据目录、日志轮转、Cursor Key、Migration、Worker lease 等其他内部运行细节不属于日常本地配置，不再要求开发者填写。

## 4.1 什么都不填也能做什么

TikHub 和 LLM 都留空时，Backend 仍正常启动：

```text
Excel Import     AVAILABLE
Voice Plaza      AVAILABLE
Excel Export     AVAILABLE
TikHub           NOT CONFIGURED
AI Analysis      NOT CONFIGURED
Scheduler        DISABLED
```

`NOT CONFIGURED` 是 Warning，不是整个系统的启动错误。

真正会阻止 Backend 启动的是基础依赖失败，例如：

```text
Docker CLI / Docker Engine 不可用
PostgreSQL 容器创建或启动失败
PostgreSQL 无法 ready
Alembic Migration 失败
Worker/API 启动失败
/health/ready 无法通过
```

# 5. 要测试 TikHub 时怎么配置

只修改本机 [`env.local`](../env.local)：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=<你的本地调试 Key>
```

然后重启：

```bash
uv run python scripts/dev/backend.py
```

启动器会：

```text
env.local 的 Key
→ .runtime/secrets/tikhub_api_key

PostgreSQL Provider Config
→ provider=tikhub
→ display_name=TikHub Local Dev
→ base_url=<env.local>
→ secret_ref=tikhub_api_key
→ enabled=true
```

数据库不保存真实 API Key。

如果把 `AIMA_TIKHUB_API_KEY` 再清空并重启，launcher 会删除对应本地 Secret，并禁用自己的 `TikHub Local Dev` Provider Config，避免前端继续把一个不可执行的本地 Provider 暴露成可用配置。

普通 CI 不读取你的真实 Key，也不会因为本地启动功能增加付费 TikHub 请求。

# 6. 要测试 AI 打标时怎么配置

只修改本机 [`env.local`](../env.local)：

```dotenv
AIMA_LLM_BASE_URL=https://your-provider.example/v1
AIMA_LLM_PROVIDER_NAME=your-provider
AIMA_LLM_MODEL=your-model
AIMA_LLM_API_KEY=<你的本地调试 Key>
```

其中 `AIMA_LLM_PROVIDER_NAME` 可以在当前 Adapter 能从 Base URL 明确推导时留空；Base URL、Model、API Key 是实际启用 AI 所需的核心项。

重启 Backend 后：

```text
API Key
→ .runtime/secrets/llm_api_key

Base URL / Provider / Model
→ 正式 AIMA_LLM_* Runtime 配置

Worker
→ 正式 Content Analysis Job
→ LLM Adapter
```

如果只填了一部分 LLM 配置，Backend 会显示 Warning，并把 AI 视为未配置；不会让一组半完成配置污染正式 Worker Runtime。

声音广场同时通过正式能力接口读取安全布尔能力；浏览器不会收到 Secret 原值。Import 和普通 TikHub Collection 不会因为 LLM 配置存在就自动发起 AI 付费调用，只有显式创建 AI Analysis Job 才调用模型。

能力接口和 Worker 都从 `AIMA_EXTERNAL_SECRET_DIR`（源码开发默认 `.runtime/secrets/`）读取 `llm_api_key`；不要把它指向只保存 PostgreSQL/Cursor Secret 的 `.runtime/internal-secrets/`。如果 [`env.local`](../env.local) 四项已经完整但页面仍显示未配置，先重启 Backend，再检查 `.runtime/secrets/llm_api_key` 是否存在以及 `/api/v1/content-analysis-capabilities` 是否返回 `configured=true`，不要在浏览器或日志中输出 Key 原值。

# 7. Scheduler 为什么默认关闭

本地默认：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=false
```

原因是本地数据库可能保留 enabled Collection Plan。若启动源码环境时自动开启 Scheduler，旧 Plan 可能立即创建真实 TikHub Run 并产生费用。

需要专门调试周期采集时才改为：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=true
```

然后重启同一个 [`scripts/dev/backend.py`](../scripts/dev/backend.py)。不需要记第三条 Scheduler 启动命令。

手工 TikHub Discovery / Batch Supplement 不依赖 Scheduler；它们依赖 API + Worker。

# 8. 前端第一次运行需要“编译”吗

本地开发不需要先执行 production build。

第一次执行：

```bash
uv run python scripts/dev/frontend.py
```

launcher 会：

```text
检查 Node/npm 精确版本
→ 检查 frontend/node_modules
→ 检查 package-lock.json 指纹
→ 首次或 lock 变化时自动 npm ci
→ npm run dev
→ Vite Development Server
```

Vite 在开发时实时处理 Vue / TypeScript / CSS，并提供热更新。修改 `.vue` / `.ts` 后保存，浏览器会自动更新。

只有正式构建才执行：

```bash
npm --prefix frontend run build
```

它会生成生产 `frontend/dist/`。CI 会直接验证这个构建；Internal V1-A 的根 [`Dockerfile`](../Dockerfile) 也在 Frontend build stage 执行同一构建，并只把 `dist` 复制到 Nginx Runtime。日常源码调试不需要先做 production build。

# 9. 本地数据、文件、日志和 Secret 在哪里

本地源码调试的主要持久状态：

```text
PostgreSQL
→ Docker volume: aima-ugc-postgres-dev-data

Excel 输入 / Raw / Export 等 Artifact
→ .runtime/data/artifacts/

统一数据导入的服务器来源文件（源码开发默认）
→ .runtime/historical-input/

应用日志
→ .runtime/logs/
   ├─ api.log
   ├─ worker.log
   └─ scheduler.log（启用时）

AIMA 内部 Secret
→ .runtime/internal-secrets/
   ├─ postgres_password
   ├─ import_batch_cursor_signing_key
   ├─ content_cursor_signing_key
   └─ collection_runtime_cursor_signing_key

外部 Provider / LLM Secret
→ .runtime/secrets/
   ├─ tikhub_api_key（配置时）
   └─ llm_api_key（配置时）

Frontend 依赖锁指纹
→ .runtime/dev/frontend-package-lock.sha256
```

`.runtime/` 和 [`env.local`](../env.local) 都被 Git 忽略。

旧版本遗留在 `.runtime/secrets/` 下的 `postgres_password` 不属于当前运行时布局，launcher 不读取它；确认不再需要旧本地数据后可以人工删除。

上传的 Excel 原文件作为 Input Artifact 保存到 Local ArtifactStore，Import Batch、Job、Content 等业务事实保存到 PostgreSQL；因此完整 Excel Web 调试确实需要 PostgreSQL + Worker，而 [`scripts/dev/backend.py`](../scripts/dev/backend.py) 已自动把这两者包含在启动流程里。

# 10. 第一次导入 Excel 前还需要一个业务配置

本地运行配置可以自动准备，但**业务配置不能被 launcher 猜测**。

正式 Import/Collection 使用全局 Rule Relevance。一个全新数据库第一次使用时，请在前端：

```text
采集策略
→ 新建关键词包
→ 添加业务关键词（例如当前真正要监测的关键词）
→ 全局相关性
→ 选择该关键词包
```

然后再去：

```text
采集运行中心
→ 导入 Excel
```

不自动创建“爱玛”默认词包，是为了避免 dev launcher 变成业务配置的第二事实源。

# 12. 停止、重新启动和重置本地数据库

Backend 终端按 `Ctrl+C`，或者主运行阶段收到 `SIGTERM`，会先停止 API、Worker 和本次启动的 Scheduler，再停止 `aima-ugc-postgres-dev` PostgreSQL 容器，并输出对应 `[STOP]` / `[SKIP]` 容器状态。PostgreSQL container 与 `aima-ugc-postgres-dev-data` named volume 都保留，因此本地数据库数据不会因正常退出被删除；下次启动会自动重新启动并复用同一容器。Frontend 终端按 `Ctrl+C` 停止 Vite。

如果明确要**破坏性清空本地源码开发数据库**，先停止 Backend，再手工执行：

```bash
docker rm -f aima-ugc-postgres-dev
docker volume rm aima-ugc-postgres-dev-data
```

随后删除与这个本地数据库绑定的当前内部密码：

```text
.runtime/internal-secrets/postgres_password
```

如果还存在旧文件：

```text
.runtime/secrets/postgres_password
```

它已经不被 launcher 使用，可以一并人工删除。下次 [`scripts/dev/backend.py`](../scripts/dev/backend.py) 会重新创建空数据库、生成新的内部随机密码并执行全部 Migration。这只允许用于本地源码开发数据，不要把这组命令用于完整 Compose 或包含真实业务数据的服务器。

Windows Docker Desktop 完整 Compose 的停止/重置方式见第 15.2 节；它使用 Host Root + 独立 PostgreSQL/Secret named volumes，不等于上面的源码 launcher 数据。

# 13. 高级开发：直接启动正式进程

日常优先使用两个 launcher。只有调试具体进程边界时才直接运行正式进程。

API：

```bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090 --reload --reload-dir backend/src
```

Worker：

```bash
uv run python -m aima_ugc.entrypoints.worker_main
```

Scheduler：

```bash
uv run python -m aima_ugc.entrypoints.scheduler_main
```

Migration：

```bash
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

直接启动这些正式进程时，调用者仍需自己提供它们要求的 `AIMA_*` 和 Secret File；这是高级调试路径，不是普通开发者快速开始。

# 15. 源码开发、完整 Docker Runtime 与 Internal V1-A 的边界

仓库按**运行方式**维护入口，不机械按“本地/生产”拆第二套业务配置：

```text
源码开发 / 热更新
→ env.local
→ scripts/dev/backend.py + scripts/dev/frontend.py

Linux / WSL 完整 Docker Runtime
→ env.production + compose.yaml
→ AIMA_HOST_ROOT 全量 bind mount

Windows Docker Desktop 原生 CMD / PowerShell
→ 同一个 env.production
→ compose.yaml + compose.windows.yaml
→ AIMA_HOST_ROOT bind Artifact/日志 + named volume PostgreSQL/内部 Secret

公司 Linux 服务器 / 后续 Production Runtime
→ env.production + canonical compose.yaml
→ AIMA_HOST_ROOT=/data/AIMA_UGC
```

[`compose.windows.yaml`](../compose.windows.yaml) **不是第二套业务 Compose**。它只调整 Windows 的持久 storage source，并让 bootstrap 对 `runtime/data`、`runtime/logs` 使用 bind-compatible 权限检查；API/Worker/Scheduler/Migration command、环境、Health、depends_on、网络、端口和外部 Secret 仍由根 [`compose.yaml`](../compose.yaml) 定义。

Internal V1-A 当前容器拓扑始终是：

```text
bootstrap
→ 只负责持久目录/volume 和内部随机 Secret

postgres
→ PostgreSQL 18.4

migrate
→ alembic upgrade head，一次性独立进程

configure
→ 幂等维护 Internal V1 Provider Config / 校验 LLM 配置，一次性独立进程

api / worker / scheduler
→ 正式后端进程

frontend
→ Vue build + 非 root Nginx，同源代理 /api 与 /health
```

## 15.1 Linux / WSL 本地完整 Docker：仓库相对 Host Root

如果本地文件系统具备 Linux POSIX owner/mode 语义，可以继续使用 canonical Compose：

```bash
cp env.production.example env.production
```

在本机 `env.production` 里设置：

```dotenv
AIMA_HOST_ROOT=./.runtime/compose
```

之后始终运行：

```bash
docker compose --env-file env.production up -d --build --wait
```

持久状态：

```text
.runtime/compose/
├─ postgres/
├─ runtime/
│  ├─ data/
│  └─ logs/
└─ shared/
   └─ secrets/
```

`.runtime/` 已被 Git 和 Docker build context 忽略。Linux 永久 CI 会真实验证仓库相对 Host Root 的 startup/readiness/persistence。

## 15.2 Windows Docker Desktop：CMD / PowerShell 标准 Compose CLI

Windows 原生模式不要求进入 WSL 终端。它保留相同业务 Runtime，并采用混合持久化：Artifact 与应用日志继续 bind 到 `AIMA_HOST_ROOT`，便于在 Windows 本地直接查看；PostgreSQL 与内部 Secret 继续使用 Docker Desktop 管理的 Linux named volumes，不把这两类严格 POSIX 状态直接放到 NTFS。

第一次从仓库根创建本机配置：

```cmd
copy env.production.example env.production
```

或 PowerShell：

```powershell
Copy-Item env.production.example env.production
```

Windows 本地推荐在 `env.production` 设置：

```dotenv
AIMA_HOST_ROOT=./.runtime
```

此时宿主可见：

```text
.runtime/runtime/data
.runtime/runtime/logs
```

CMD 与 PowerShell 使用完全相同的正式启动命令：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production up -d --build --wait
```

查看服务、宿主文件与 stdout：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production ps
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production logs -f api
```

应用正式 `.log` 可直接在：

```text
${AIMA_HOST_ROOT}/runtime/logs/api.log
${AIMA_HOST_ROOT}/runtime/logs/worker.log
${AIMA_HOST_ROOT}/runtime/logs/scheduler.log
```

查看；Artifact 文件位于 `${AIMA_HOST_ROOT}/runtime/data`。

日常停止并删除容器/网络，同时保留 Host Root 文件和 named volumes：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down
```

Windows 原生持久状态：

```text
${AIMA_HOST_ROOT}/runtime/data
→ Artifact

${AIMA_HOST_ROOT}/runtime/logs
→ 应用 .log

windows_postgres
→ PostgreSQL 18 数据

windows_internal_secrets
→ PostgreSQL password + Cursor signing keys
```

实际 volume 名会带 Compose project 前缀。可用 `docker volume ls` 查看 PostgreSQL/Secret volumes。

只有显式执行下面命令才会删除 Windows 本地 PostgreSQL、内部 Secret named volumes 与 AIMA service images：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down -v --remove-orphans --rmi all
```

`-v` **不会删除 bind-mounted 的 Artifact 和应用日志**。如果连这些文件也要破坏性清空，必须另外显式删除 `${AIMA_HOST_ROOT}/runtime/data` 与 `${AIMA_HOST_ROOT}/runtime/logs`。完整步骤见 [`docs/guides/03_Windows Docker Desktop Compose运行.md`](guides/03_Windows%20Docker%20Desktop%20Compose运行.md)。

旧版本曾使用 `windows_runtime_data` / `windows_runtime_logs` named volumes。升级后它们不会自动迁移到 Host Root，也不会自动删除；存在需要保留的历史文件时应人工确认并迁移。

永久 CI 的证据边界是：Windows Runner 直接验证标准 Compose CLI 在 CMD/PowerShell 下可解析同一 `compose.yaml + compose.windows.yaml + env.production`；Ubuntu Docker Engine 真实运行 merged hybrid Runtime，验证 data/log bind、host-visible 文件、严格 Secret mode、PostgreSQL/Migration/Readiness 和重启持久化。GitHub Hosted Windows Runner 本身不提供可依赖的 Docker Desktop Linux-container Runtime，因此首次在具体开发机使用时仍应执行一次本机 smoke。

## 15.3 公司服务器 Internal V1：canonical Compose + 数据盘 Host Root

服务器从同一个模板生成自己的 `env.production`：

```bash
cp env.production.example env.production
chmod 0600 env.production
```

服务器保持：

```dotenv
AIMA_HOST_ROOT=/data/AIMA_UGC
```

canonical [`compose.yaml`](../compose.yaml) 固定推导：

```text
PostgreSQL        → /data/AIMA_UGC/postgres
Artifact          → /data/AIMA_UGC/runtime/data
应用日志          → /data/AIMA_UGC/runtime/logs
AIMA 内部 Secret → /data/AIMA_UGC/shared/secrets
```

然后编辑公司内网 bind IP、TikHub/LLM 等机器配置并运行：

```bash
docker compose --env-file env.production up -d --build --wait
```

Internal V1-A/B 当前仍允许服务器现场 `--build`，因为这一阶段目标是验证仓库级最小部署栈和真实公司服务器。`/data/AIMA_UGC` 是持久 Data Root，不属于某个应用版本 Release；后续升级应用不能删除、移动或替换这个目录。

Windows storage override **不得**用于公司服务器，Production 也不依赖它。

## 15.4 Secret 为什么仍然分层

运行平台不同，Secret 分类不变：

```text
AIMA 内部随机 Secret
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
→ AIMA_SECRET_DIR=/run/internal-secrets

外部凭据
AIMA_TIKHUB_API_KEY
AIMA_LLM_API_KEY
→ Compose Secret
→ AIMA_EXTERNAL_SECRET_DIR=/run/secrets
```

Linux/服务器：内部 Secret 持久于 `${AIMA_HOST_ROOT}/shared/secrets`。

Windows Docker Desktop：内部 Secret 持久于 Docker named volume `windows_internal_secrets`，bootstrap 仍在 Linux 容器内施加相同的 `root:11001 / 0440` 文件权限；bind-compatible 模式只作用于 Artifact/日志目录，不降低 Secret 权限。

TikHub/LLM Key **不是**业务容器普通环境变量；Provider Config 继续只保存 `secret_ref`，不保存真实 Key。

PostgreSQL password 不要求管理员配置。无论 Linux bind 还是 Windows named volume，都遵守：

```text
空数据库 + 密码不存在
→ bootstrap 自动生成

已有 PostgreSQL 18 数据 + postgres_password 存在
→ 复用原密码，不轮换

已有 PostgreSQL 18 数据 + postgres_password 丢失
→ bootstrap fail closed
→ 禁止生成一个无法与既有数据库匹配的新密码
```

## 15.6 GitHub 一键离线 Release：构建源与本地环境隔离

仓库新增 [`.github/workflows/release.yml`](../.github/workflows/release.yml) 后，正式发布由 GitHub Actions 的 `Release` Workflow 手工触发：

```text
GitHub → Actions → Release → Run workflow
Branch: main
version: vMAJOR.MINOR.PATCH
```

正式 Workflow 只接受当前远端 `main` 最新 SHA 和标准 SemVer，拒绝重复 Tag/Release，并检查要求的 `main` CI 门禁。它在 GitHub Hosted Linux Runner 上构建 `linux/amd64` Backend/Frontend，并**只在这个 Workflow 内**显式把构建下载源覆盖为：

```text
Docker 基础镜像 / PostgreSQL → Docker Hub 官方 canonical reference
Debian                       → deb.debian.org
PyPI                         → pypi.org
npm                          → registry.npmjs.org
```

这不会修改 [`Dockerfile`](../Dockerfile)、[`compose.yaml`](../compose.yaml)、[`env.production.example`](../env.production.example) 的本地默认值。因此 Windows/Linux 本地仍按现有国内镜像和 Docker mirror 配置构建，Release Runner 的海外下载源不会反向影响开发机。

正式发布会：

```text
固定 main SHA
→ build linux/amd64 Backend / Frontend
→ 拉取官方 postgres:18.4，并记录 digest
→ 生成 images.tar
→ 生成 release-manifest.json / migration-manifest.json / SHA256SUMS / DEPLOY.md
→ 删除 Runner 上本地候选运行镜像 tag
→ 从 images.tar 重新 docker load
→ canonical compose.yaml --no-build --pull never --wait
→ readiness / Migration / 持久目录 smoke
→ 正式 workflow_dispatch 的 publish job 复用这组已回放候选，发布版本 + SHA tag 到 GHCR 并记录 registry digest
→ 创建 Git Tag + GitHub Release
```

Release 页面可下载：

```text
AIMA_UGC-vX.Y.Z-deploy.tar.gz
release-manifest.json
migration-manifest.json
SHA256SUMS
```

离线包内包含：

```text
images.tar
compose.yaml
env.production.example
release-manifest.json
migration-manifest.json
SHA256SUMS
DEPLOY.md
```

服务器解压并校验后，运行：

```bash
sha256sum -c SHA256SUMS
docker load -i images.tar
cp env.production.example env.production
chmod 0600 env.production
# 编辑 env.production，生产/公司服务器保持 AIMA_HOST_ROOT=/data/AIMA_UGC
docker compose --env-file env.production config --quiet
docker compose --env-file env.production up -d --no-build --pull never --wait
```

应用镜像/Release 可以升级或回滚，而 PostgreSQL、Artifact、日志和内部 Secret 保持在 Release 外部的同一持久根：

```dotenv
AIMA_HOST_ROOT=/data/AIMA_UGC
```

Release Bundle **不携带**当前 PostgreSQL 数据、Artifact、日志、真实 `env.production` 或 Secret。因此重复发布/重新加载 `postgres:18.4` 镜像不会删除 `/data/AIMA_UGC/postgres` 中的数据库数据；真正的数据生命周期仍由 Host Root 与后续 Backup/Restore 负责。

当前这一步建立的是“一键不可变离线 Release 基础”，仍不等于完整 Production Go-Live。当前仍待后续正式 Change/真实环境验收的内容包括：

```text
更高规模的真实 TikHub / LLM 有界运行与费用审计
SBOM 与独立来源签名 / provenance
企业认证 / 授权 / HTTPS 正式入口
PostgreSQL + Artifact 同时点协调 Backup / Restore
完整生产发布/回滚与恢复演练
```

# 16. 常见问题

## Docker 未启动

源码开发 Backend 会直接报错并停止。Compose 启动同样要求 Docker Engine / Docker Desktop 正常且当前用户有执行 Docker Compose 的权限。

## Windows 可以直接从 CMD / PowerShell 启动吗

可以。Docker Desktop 已启动后，从仓库根执行：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production up -d --build --wait
```

首次没有 `env.production` 时先从 [`env.production.example`](../env.production.example) 复制一次并编辑。[`compose.windows.yaml`](../compose.windows.yaml) 只负责 Windows 混合存储适配，不需要额外 wrapper。

## Windows 的 PostgreSQL 文件为什么不在 `AIMA_HOST_ROOT`

Windows 原生模式刻意让 PostgreSQL 与内部 Secret 使用 Docker-managed named volume，避免把这两类严格 Linux 状态直接放在 NTFS bind mount 上。Artifact 与应用日志不同，它们现在会按 `AIMA_HOST_ROOT` 落到：

```text
${AIMA_HOST_ROOT}/runtime/data
${AIMA_HOST_ROOT}/runtime/logs
```

## Windows `down` 后数据会丢吗

普通：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down
```

不会删除 Host Root 文件，也不会删除 PostgreSQL/Secret named volumes。即使显式加 `-v`，也只删除本项目 named volumes，bind-mounted 的 Artifact/日志仍保留；完全清空需要额外显式删除 Host Root 下的 `runtime/data` 与 `runtime/logs`。

## 本地升级后提示旧 `.runtime/secrets/postgres_password` 不再受支持

这只针对源码开发 launcher：本机还保留已有 `aima-ugc-postgres-dev-data` volume，但新的 `.runtime/internal-secrets/postgres_password` 不存在。launcher 不再把旧路径密码迁移到新目录，也不会生成一个新密码去尝试连接既有数据。

如果旧源码开发数据可以丢弃，按第 12 节重置；若必须保留旧数据，需要先自行确认数据库 Role 的真实密码，并把匹配值放到 `.runtime/internal-secrets/postgres_password`。

## 正式 Compose 启动失败并提示已有 PostgreSQL 数据但缺少 `postgres_password`

不要删除数据库目录，也不要手工生成新密码。恢复与这份 PostgreSQL 数据匹配的原 `postgres_password`，再重新执行同一条 Compose 启动命令。自动生成新值不能修改既有数据库账户密码，只会造成应用与数据库不匹配，因此系统会主动拒绝这种恢复方式。

## `/health/live` 正常但 `/health/ready` 失败

`live` 只表示 API 能响应；`ready` 才检查 PostgreSQL、ArtifactStore 和日志目录。源码开发查看 `.runtime/logs/`；Linux Compose 查看 `${AIMA_HOST_ROOT}/runtime/logs`；Windows Docker Desktop 也直接查看 `${AIMA_HOST_ROOT}/runtime/logs`，并可辅助执行：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production logs -f
```

## AI/TikHub 显示未配置

源码开发按本文第 5/6 节填写 [`env.local`](../env.local)；完整 Compose 填写 `env.production` 中相应 Base URL/Model/API Key 后重新启动。没有显式业务动作时不会因为 Key 存在就自动发起 AI 付费调用。

## Excel 上传后一直 queued

正常源码开发与完整 Compose 都会启动 Worker。持续 queued 时检查 Worker 进程/容器和对应 `worker.log`，不要用历史测试 harness 代替正式 Worker。

## 怎样让“导入数据”选择服务器历史 Excel

这里的“选择”是枚举管理员批准的专用根目录，不是让浏览器打开服务器操作系统的任意目录选择器。

源码开发模式修改本机 [`env.local`](../env.local)：

```text
AIMA_HISTORICAL_IMPORT_ROOT=.runtime/historical-input
```

launcher 会创建该默认目录。首次增加或修改该配置后需要重启 [`scripts/dev/backend.py`](../scripts/dev/backend.py)，API 和 Worker 才会获得新配置；配置已生效时，只往 `.runtime/historical-input/` 或其子目录放入待迁移 `.xlsx` 无需重启，刷新页面即可重新枚举。如果数据已在其他本地专用目录，可以把该值改成实际绝对路径；该路径必须已存在、不能是 Symlink/Junction，也不应指向包含其他敏感文件的通用共享盘根。

完整 Compose 运行时，管理员先把源文件放进宿主只读目录，并在 `env.production` 配置：

```text
AIMA_HISTORICAL_IMPORT_HOST_ROOT=/data/aima-historical-input
```

Compose 固定把它挂到容器 `/data/aima-historical-input:ro`。[`env.local`](../env.local) 不会影响 Compose，`env.production` 也不会影响源码开发 launcher。网页“导入数据 → 服务器目录”只枚举批准根目录内的相对路径，不支持输入任意服务器路径，也不能上传、删除、移动或改名源文件。选择“本地电脑”时可以多选 `.xlsx`，或使用文件夹选择器递归上传该目录中的 `.xlsx`；浏览器不会把本机绝对路径交给页面。`AIMA_HISTORICAL_CHUNK_ROWS` 和 `AIMA_HISTORICAL_MAX_IN_FLIGHT_JOBS` 必须依据容量报告调整；默认分别为 1000 和 2。

AI Run 的 `AIMA_ANALYSIS_RUN_SHARD_SIZE` 默认 1，`AIMA_ANALYSIS_RUN_MAX_IN_FLIGHT_JOBS` 默认 2。Shard=1 是真实付费 Gold Set 批量质量基准完成前的保守值，不应只为吞吐静默放大。
