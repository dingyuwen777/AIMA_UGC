# 环境、运行与部署

本文是 AIMA_UGC 的**运行总入口**。高频任务先看下面的启动/停止速查；首次准备、配置、存储、安全边界和排障再进入后文或专项文档。

**推荐原则：除“源码热更新”外，完整 Compose / Release 的日常启动和停止统一优先使用 [`scripts/deploy/start_compose.py`](../scripts/deploy/start_compose.py) / [`scripts/deploy/stop_compose.py`](../scripts/deploy/stop_compose.py)。** `docker compose` 主要用于首次准备镜像、底层调试，以及明确需要 `down` 删除容器/网络的场景。

> 除“公司服务器 / Release”外，下面本地命令都默认在**源码仓库根目录**执行。

## 1. 启动 / 停止速查

### 1.1 日常源码开发（热更新）

启动需要两个终端：

~~~bash
# 终端 1：Backend + Worker + 本地 PostgreSQL
uv run python scripts/dev/backend.py

# 终端 2：Frontend
uv run python scripts/dev/frontend.py
~~~

停止：分别在两个终端按 `Ctrl+C`。Backend launcher 会停止本轮启动的 API、Worker、Scheduler（如已启用）和本地 PostgreSQL 容器，但保留数据库 volume。

详细说明：继续看本文第 2～9 节。

### 1.2 Linux / WSL 本地完整 Compose

**推荐日常启停：**

~~~bash
python scripts/deploy/start_compose.py --env-file env.local
python scripts/deploy/stop_compose.py --env-file env.local
~~~

[`scripts/deploy/start_compose.py`](../scripts/deploy/start_compose.py) 会按 Docker Engine 实际 CPU / 内存生成 `compose.auto.yaml`，再启动当前已有镜像；[`scripts/deploy/stop_compose.py`](../scripts/deploy/stop_compose.py) 会停止服务但保留容器、网络和持久数据，方便下次继续启动。

这两个脚本**不负责首次 build / pull**。第一次没有镜像时先准备：

~~~bash
docker compose --env-file env.local build
docker compose --env-file env.local pull postgres
~~~

如果明确要删除本项目容器和 Compose 网络，再使用：

~~~bash
docker compose --env-file env.local down
~~~

详细说明：见本文第 10 节；首次环境、下载源和本地重置见 [docs/guides/04_Docker国内构建源与本地重置.md](guides/04_Docker国内构建源与本地重置.md)。

### 1.3 Windows Docker Desktop 完整 Compose

**推荐日常启停（CMD / PowerShell 均可）：**

~~~powershell
python .\scripts\deploy\start_compose.py --env-file .\env.local
python .\scripts\deploy\stop_compose.py --env-file .\env.local
~~~

脚本会自动叠加 [`compose.windows.yaml`](../compose.windows.yaml)；启动时按 Docker Engine 实际 CPU / 内存生成 `compose.auto.yaml`，停止时复用同一配置并保留容器、网络和持久数据。

第一次没有镜像时，先准备 Backend / Frontend / PostgreSQL：

~~~powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.local build
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.local pull postgres
~~~

如果明确要删除本项目容器和 Compose 网络，再使用：

~~~powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.local down
~~~

首次环境初始化、Windows storage override、镜像准备和重置边界统一见 [docs/guides/03_Windows_Docker_Desktop_Compose运行.md](guides/03_Windows_Docker_Desktop_Compose运行.md)。

### 1.4 公司 Linux 服务器 / 离线 Release

下面命令在**解压后的 Release 包根目录**执行。启动：

~~~bash
python3 start_compose.py --env-file /data/AIMA_UGC/env.production
~~~

停止服务但保留容器、网络和全部持久数据：

~~~bash
python3 stop_compose.py --env-file /data/AIMA_UGC/env.production
~~~

Release 包里的启动脚本会使用已导入镜像、自动计算 Docker Engine 资源配额并生成 `compose.auto.yaml`；服务器不是用源码仓库现场 build。

完整部署、升级、Backup/Restore、Rollback 和 Release 身份边界见 [docs/operations/01_生产部署与离线Release方案.md](operations/01_生产部署与离线Release方案.md)。尚未完成的 Production Gate 见 [docs/roadmap/01_生产上线实施路线.md](roadmap/01_生产上线实施路线.md)。

## 2. 日常源码开发：只记两个命令

仓库根目录打开两个终端。

### 2.1 后端

~~~bash
uv run python scripts/dev/backend.py
~~~

成功后主要入口：

~~~text
API       http://127.0.0.1:8090
Ready     http://127.0.0.1:8090/health/ready
~~~

后端 launcher 位于 [scripts/dev/backend.py](../scripts/dev/backend.py)。

### 2.2 前端

~~~bash
uv run python scripts/dev/frontend.py
~~~

浏览器：

~~~text
http://127.0.0.1:5173/
~~~

前端 launcher 位于 [scripts/dev/frontend.py](../scripts/dev/frontend.py)。

日常开发心智模型固定为：

~~~text
backend.py
+ frontend.py
+ 浏览器
~~~

不要求开发者手工拼接 PostgreSQL、Migration、Worker 和 Vite 的启动顺序。

## 3. backend.py 第一次启动会做什么

launcher 会按当前机器事实完成必要本地装配：

~~~text
检查 / 创建 env.local
→ 创建本地 runtime 目录
→ 准备内部 Secret
→ 检查 Docker Engine
→ 创建或启动本地 PostgreSQL
→ 等数据库 ready
→ alembic upgrade head
→ 装配历史导入批准根
→ 装配 TikHub / LLM 外部 Secret 与本地 Provider Config
→ 启动正式 Worker
→ 按配置决定是否启动 Scheduler
→ 启动 FastAPI
→ 等待 /health/ready
~~~

本地 PostgreSQL 数据使用 Docker named volume 保存。正常退出会停止本次运行进程和本地 PostgreSQL 容器，但不删除 volume，因此下次继续复用。

当前内部 PostgreSQL 密码文件是：

~~~text
.runtime/internal-secrets/postgres_password
~~~

旧路径 .runtime/secrets/postgres_password 已废弃，launcher 不读取、迁移或猜测旧密码。已有数据库 volume 但新内部密码丢失时会 fail closed；如果数据需要保留，应恢复与数据库 Role 匹配的真实密码，而不是生成一个新值碰运气。

## 4. env.local 的职责

模板：

- [env.local.example](../env.local.example)

真实 env.local 不入 Git。

同一 env.local 服务于：

~~~text
源码开发
→ scripts/dev/backend.py + scripts/dev/frontend.py

Linux / WSL 本地 Compose
→ compose.yaml

Windows Docker Desktop
→ compose.yaml + compose.windows.yaml
~~~

服务器不使用 env.local；服务器长期配置使用 env.production，说明见 [docs/operations/01_生产部署与离线Release方案.md](operations/01_生产部署与离线Release方案.md)。

### 4.1 历史导入目录有两个概念

- AIMA_HISTORICAL_IMPORT_HOST_ROOT：宿主机真实 source；
- AIMA_HISTORICAL_IMPORT_ROOT：Compose 内 API/Worker 看到的 runtime target。

源码 launcher 优先使用 HOST_ROOT。Compose 把 HOST_ROOT 作为 bind source，把 ROOT 作为容器 target。

不要把容器内 /data/... 路径直接当成本机源码进程路径。

### 4.2 Secret 分成两类

源码开发默认：

~~~text
AIMA 内部 Secret
→ .runtime/internal-secrets/

外部 TikHub / LLM Secret
→ .runtime/secrets/
~~~

内部 Secret 包含数据库密码和 Cursor signing key；外部 Secret 包含 Provider API Key。数据库 Provider Config 保存 Base URL、Model、启停、并发等非敏感配置，只保存 secret_ref，不保存 API Key 明文。

## 5. TikHub / LLM 为什么有时“未配置”

### 源码 launcher

API Key 为空时允许 Backend 启动，对应能力显示未配置。适合先开发不依赖外部付费 Provider 的功能。

需要 TikHub 时在 env.local 填真实 Key，再重启后端。launcher 会把 Key 写入外部 Secret 目录，并幂等维护本地 TikHub Provider Config。

LLM 同理：Base URL、Model、Key 满足当前装配条件后，正式 Worker 才能执行 Analysis Job。

### 新数据库的完整 Compose

模板可能已经声明 Provider Runtime 字段。数据库尚未拥有对应 Provider Config 时，首次 configure 会要求所需 Secret 可读；缺 Key 时 fail closed。

### 数据库已经有 Provider Config

数据库 Provider Config 是运行时事实源；env 不覆盖管理员配置，也不会因为当前默认 Provider 被禁用就偷偷退回旧 env 配置。

这条边界避免 env 和管理员配置形成两套运行事实。

## 6. Scheduler 为什么源码开发默认关闭

源码开发默认不自动启用周期 Scheduler，原因是本地数据库可能保留 enabled Collection Plan；自动启动可能立即产生真实 TikHub Run 和费用。

专门调试周期采集时，在 env.local 显式启用对应开发开关后重启 [scripts/dev/backend.py](../scripts/dev/backend.py)。

完整 Compose 的 Scheduler 是正式服务，不使用源码开发开关。

## 7. 本地文件、日志和持久状态

源码开发主要位置：

~~~text
PostgreSQL
→ Docker named volume

Artifact
→ .runtime/data/artifacts/

历史导入批准目录
→ .runtime/historical-input/

应用日志
→ .runtime/logs/

内部 Secret
→ .runtime/internal-secrets/

外部 Provider Secret
→ .runtime/secrets/
~~~

.runtime/ 与 env.local 都不入 Git。

正式 Excel/Data Import 的源文件、Raw、Export 等 Artifact 与 PostgreSQL 业务事实是两类 Owner：文件字节进入 ArtifactStore，业务状态进入 PostgreSQL。

Artifact 生命周期见 [docs/appendix/12_Artifact生命周期与保留策略.md](appendix/12_Artifact生命周期与保留策略.md)。

## 8. 全新数据库第一次使用前还缺什么

launcher 可以准备技术运行环境，不能替你猜业务配置。

正式 Excel/Data Import 与 TikHub Collection 都需要 Brand/Vehicle Filter。TikHub Discovery 还需要 Keyword Pack 作为 Search Terms。

全新数据库至少先通过管理员页面建立正确的 Brand/Vehicle 目录，再按真实业务需要创建关键词包和采集计划/Run。

不要把“爱玛”等业务样例硬编码进开发启动器；业务配置应该由正式产品入口维护。

## 9. 本地 Smoke、停止和重置

### 9.1 Smoke

后端和前端都启动后：

~~~bash
uv run python scripts/dev/check_local_stack.py
~~~

机器入口：[scripts/dev/check_local_stack.py](../scripts/dev/check_local_stack.py)。

页面能打开但 /health/ready 失败，不能算完整本地业务环境可用。

### 9.2 正常停止

Backend / Frontend 终端使用 Ctrl+C。Backend launcher 会停止它启动的 API、Worker、Scheduler 和本地 PostgreSQL 容器，但保留数据库 volume。

### 9.3 破坏性清空源码开发数据库

只在明确允许丢弃本地开发数据时：

~~~bash
docker rm -f aima-ugc-postgres-dev
docker volume rm aima-ugc-postgres-dev-data
~~~

随后删除当前本地内部 postgres_password；下次 backend.py 会重新建立空库并执行 Migration。

**不要把这组命令用于完整 Compose、公司服务器或真实业务数据。**

Windows Docker Desktop 的停止与项目级重置见 [docs/guides/03_Windows_Docker_Desktop_Compose运行.md](guides/03_Windows_Docker_Desktop_Compose运行.md) 和 [docs/guides/04_Docker国内构建源与本地重置.md](guides/04_Docker国内构建源与本地重置.md)。

## 12. 高级调试：直接启动正式进程

日常优先 launcher。只有需要隔离进程边界时才直接启动：

~~~bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090
uv run python -m aima_ugc.entrypoints.worker_main
uv run python -m aima_ugc.entrypoints.scheduler_main
uv run alembic upgrade head
~~~

直接运行正式进程时，调用者需要自己提供它要求的 AIMA_* 配置和 Secret File；这不是普通开发快速开始。

## 13. 常见故障从哪里查

### Docker 未启动

backend.py 会停止并报告基础依赖不可用。先恢复 Docker Engine，再重试。

### /health/live 正常但 /health/ready 失败

live 只证明 API 能响应；ready 才检查数据库、ArtifactStore 和日志等基础依赖。

源码开发先查 .runtime/logs/。Compose 环境按对应 Guide/Operations 的日志入口排查。

### AI / TikHub 显示未配置

先判断当前环境属于“源码 launcher / 新数据库 Compose / 已有数据库 Provider Config”哪一种，再检查相应 Secret 和数据库 Provider 状态。不要把管理员配置已经接管后的问题靠修改 env 强制覆盖。

### Excel 上传后一直 queued

正式导入需要 Worker。检查 Worker 是否运行、Job 状态和 worker 日志；不要用测试 harness 代替正式 Worker。

### 服务器目录看不到历史 Excel

先确认 HOST_ROOT / ROOT 是否按当前运行方式配置、目录存在、没有链接逃逸，并重新触发目录发现。完整迁移运行与安全边界见 [docs/operations/02_4000万历史迁移与Analysis Run运行手册.md](operations/02_4000万历史迁移与Analysis%20Run运行手册.md)。

### 旧 postgres_password 提示

不要用新随机密码覆盖已有数据库。可丢弃的本地数据按第 9 节重置；需要保留时恢复与数据库真实 Role 匹配的 Secret。
