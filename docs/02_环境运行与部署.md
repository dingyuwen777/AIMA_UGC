# 环境、运行与部署

本文是 AIMA_UGC 的日常运行入口。优先回答：**拿到源码以后，怎样用最少步骤在 Windows 或 Linux 上把真实后端、PostgreSQL、Worker 和 Vue 前端跑起来，以及怎样用同一套 Docker Runtime 在本地和服务器运行完整容器栈。**

架构、Schema、Contract 和生产部署边界仍分别以 `AGENTS.md`、`docs/blueprint/`、Migration、代码和 Roadmap 为准。本文明确区分源码开发、完整容器 Runtime 与正式不可变 Production Release，不把其中一种入口误写成另一种。

---

# 1. 本地开发快速开始

本地源码调试只需要记两个命令。Windows 和 Linux 使用**完全相同**的正式入口。

## 1.1 前提

开发机已经具备仓库锁定版本的：

```text
Python
uv
Node.js
npm
Docker CLI + Docker Engine
```

精确版本事实源：

```text
.python-version
.uv-version
.node-version
frontend/package.json
uv.lock
frontend/package-lock.json
```

Windows 第一次准备工具链可继续使用：

```powershell
scripts\setup_dev_environment.cmd
```

Linux 的工具链安装与应用启动是两件事。仓库现有 `scripts/setup_dev_environment.sh` 是 CentOS Stream 9 x86_64 的特定宿主初始化脚本；不应把它当成应用日常启动命令。只要目标 Linux 已准备正确版本的 Python/uv/Node/npm/Docker，下面两个 Python launcher 与 Windows 共用同一实现。

## 1.2 终端 1：启动完整本地后端

从仓库根执行：

```bash
uv run python scripts/dev/backend.py
```

这个命令不是“只启动 FastAPI”。它会把本地业务运行所需的基础组件准备好，再启动正式 API/Worker。

成功后主要地址：

```text
API          http://127.0.0.1:8090
Readiness    http://127.0.0.1:8090/health/ready
```

## 1.3 终端 2：启动前端

从仓库根执行：

```bash
uv run python scripts/dev/frontend.py
```

浏览器访问：

```text
http://127.0.0.1:5173/
```

Vite 会把 `/api` 和 `/health` 代理到本地 FastAPI。

因此日常源码开发的心智模型固定为：

```text
终端 1：backend.py
终端 2：frontend.py
浏览器：127.0.0.1:5173
```

不再要求开发者手工拼接 PostgreSQL、Migration、多个 Secret 和 Worker 启动命令。

# 2. 第一次运行 Backend 会自动做什么

第一次执行：

```bash
uv run python scripts/dev/backend.py
```

启动器按顺序处理：

```text
检查/创建 env.local
→ 创建 .runtime 本地目录
→ 在 .runtime/internal-secrets 自动生成仍缺失的数据库密码和三个 Cursor signing key
→ 检查 Docker Engine
→ 创建或启动 PostgreSQL 18.4 本地容器
→ 等 PostgreSQL ready
→ alembic upgrade head
→ 按 env.local 准备 TikHub / LLM 外部 Secret
→ 幂等维护本地 TikHub Provider Config
→ 启动正式 Worker
→ 按需启动 Scheduler
→ 启动 FastAPI
→ 等待 /health/ready = 200
→ 输出当前功能可用状态
```

本地 PostgreSQL 固定使用：

```text
image      postgres:18.4
container  aima-ugc-postgres-dev
volume     aima-ugc-postgres-dev-data
host       127.0.0.1
port       5432
database   aima_ugc
user       aima_ugc
```

数据库密码由启动器随机生成，不要求开发者填写，也不写入 Git。密码文件固定为：

```text
.runtime/internal-secrets/postgres_password
```

PostgreSQL 数据保存在 Docker named volume 中；关闭 `backend.py` 不删除容器数据。

## 2.1 后续启动

以后再次运行同一命令时：

```text
既有 PostgreSQL 容器在运行
→ 直接复用

容器已停止
→ 自动启动

Migration 已在 head
→ upgrade head 幂等返回

已有内部 Secret
→ 继续复用，不静默轮换
```

因此不需要每次重新配置数据库。

### 旧 `.runtime/secrets/postgres_password` 已废弃

旧版本曾把 PostgreSQL 密码放在：

```text
.runtime/secrets/postgres_password
```

当前 launcher **不再读取、迁移或兼容**这个旧路径。新的唯一运行时路径是：

```text
.runtime/internal-secrets/postgres_password
```

密码只是 PostgreSQL Role 的认证凭据，不代表一份独立数据。不同密码不会在同一个数据库容器里自动对应不同数据副本；如果应用使用的密码与数据库内 Role 实际密码不一致，只会认证失败。

因此，如果旧本地环境同时保留了 `aima-ugc-postgres-dev-data` volume，但新的 `.runtime/internal-secrets/postgres_password` 不存在，launcher 会 fail closed：不会读取旧路径密码，也不会生成一个新密码去猜既有数据库。对于可丢弃的本地开发数据，按第 12 节显式重置本地数据库即可。若确实要保留旧本地数据，只能由开发者自行确认数据库 Role 的真实密码，并把匹配值放到新的内部路径；这不是 launcher 自动兼容能力。

# 3. `env.local` 到底是什么

仓库提交的是：

```text
env.local.example
```

真实本地文件：

```text
env.local
```

已经加入 `.gitignore`。

第一次运行 Backend 或 Frontend 时，如果 `env.local` 不存在，launcher 会自动从 `env.local.example` 复制一份；开发者不需要先手工创建。

`env.local` **只属于源码开发 launcher 的输入界面，不是 Docker Compose/生产运行时 Contract**。

正式 API/Worker/Scheduler 在本地和生产都使用同一类双 Secret 根语义：

```text
非敏感运行配置
→ AIMA_* 子进程环境

AIMA 内部 Secret
→ AIMA_SECRET_DIR
→ 本地 .runtime/internal-secrets/

外部 Provider / LLM Secret
→ AIMA_EXTERNAL_SECRET_DIR
→ 本地 .runtime/secrets/

Provider Config
→ PostgreSQL 只保存 secret_ref
```

Dev launcher 读取 `env.local` 后会把 TikHub/LLM API Key 写到 `.runtime/secrets/`，并从正式子进程环境中移除本地明文 Key。PostgreSQL password 和三个 Cursor signing key 只位于 `.runtime/internal-secrets/`。Docker Compose 则读取 `env.production` 并通过持久挂载 / Compose Secret 实现同样的内部/外部分层，不读取 `env.local`。

---

# 4. `env.local` 现在只需要配置什么

默认文件非常短：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=

AIMA_LLM_BASE_URL=
AIMA_LLM_PROVIDER_NAME=
AIMA_LLM_MODEL=
AIMA_LLM_API_KEY=

AIMA_DEV_ENABLE_SCHEDULER=false
```

数据库 Host、Port、用户名、密码、数据目录、日志轮转、Cursor Key、Migration、Worker lease 等内部运行细节不属于日常本地配置，不再要求开发者填写。

## 4.1 什么都不填也能做什么

TikHub 和 LLM 都留空时，Backend 仍正常启动：

```text
Excel Import     AVAILABLE
Voice Plaza      AVAILABLE
Excel Export     AVAILABLE
TikHub           NOT CONFIGURED
AI Analysis      NOT CONFIGURED
Scheduler        DISABLED
```

`NOT CONFIGURED` 是 Warning，不是整个系统的启动错误。

真正会阻止 Backend 启动的是基础依赖失败，例如：

```text
Docker CLI / Docker Engine 不可用
PostgreSQL 容器创建或启动失败
PostgreSQL 无法 ready
Alembic Migration 失败
Worker/API 启动失败
/health/ready 无法通过
```

# 5. 要测试 TikHub 时怎么配置

只修改本机 `env.local`：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=<你的本地调试 Key>
```

然后重启：

```bash
uv run python scripts/dev/backend.py
```

启动器会：

```text
env.local 的 Key
→ .runtime/secrets/tikhub_api_key

PostgreSQL Provider Config
→ provider=tikhub
→ display_name=TikHub Local Dev
→ base_url=<env.local>
→ secret_ref=tikhub_api_key
→ enabled=true
```

数据库不保存真实 API Key。

如果把 `AIMA_TIKHUB_API_KEY` 再清空并重启，launcher 会删除对应本地 Secret，并禁用自己的 `TikHub Local Dev` Provider Config，避免前端继续把一个不可执行的本地 Provider 暴露成可用配置。

普通 CI 不读取你的真实 Key，也不会因为本地启动功能增加付费 TikHub 请求。

# 6. 要测试 AI 打标时怎么配置

只修改本机 `env.local`：

```dotenv
AIMA_LLM_BASE_URL=https://your-provider.example/v1
AIMA_LLM_PROVIDER_NAME=your-provider
AIMA_LLM_MODEL=your-model
AIMA_LLM_API_KEY=<你的本地调试 Key>
```

其中 `AIMA_LLM_PROVIDER_NAME` 可以在当前 Adapter 能从 Base URL 明确推导时留空；Base URL、Model、API Key 是实际启用 AI 所需的核心项。

重启 Backend 后：

```text
API Key
→ .runtime/secrets/llm_api_key

Base URL / Provider / Model
→ 正式 AIMA_LLM_* Runtime 配置

Worker
→ 正式 Content Analysis Job
→ LLM Adapter
```

如果只填了一部分 LLM 配置，Backend 会显示 Warning，并把 AI 视为未配置；不会让一组半完成配置污染正式 Worker Runtime。

声音广场同时通过正式能力接口读取安全布尔能力；浏览器不会收到 Secret 原值。Import 和普通 TikHub Collection 不会因为 LLM 配置存在就自动发起 AI 付费调用，只有显式创建 AI Analysis Job 才调用模型。

# 7. Scheduler 为什么默认关闭

本地默认：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=false
```

原因是本地数据库可能保留 enabled Collection Plan。若启动源码环境时自动开启 Scheduler，旧 Plan 可能立即创建真实 TikHub Run 并产生费用。

需要专门调试周期采集时才改为：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=true
```

然后重启同一个 `backend.py`。不需要记第三条 Scheduler 启动命令。

手工 TikHub Discovery / Batch Supplement 不依赖 Scheduler；它们依赖 API + Worker。

# 8. 前端第一次运行需要“编译”吗

本地开发不需要先执行 production build。

第一次执行：

```bash
uv run python scripts/dev/frontend.py
```

launcher 会：

```text
检查 Node/npm 精确版本
→ 检查 frontend/node_modules
→ 检查 package-lock.json 指纹
→ 首次或 lock 变化时自动 npm ci
→ npm run dev
→ Vite Development Server
```

Vite 在开发时实时处理 Vue / TypeScript / CSS，并提供热更新。修改 `.vue` / `.ts` 后保存，浏览器会自动更新。

只有正式构建才执行：

```bash
npm --prefix frontend run build
```

它会生成生产 `frontend/dist/`。CI 会直接验证这个构建；Internal V1-A 的根 `Dockerfile` 也在 Frontend build stage 执行同一构建，并只把 `dist` 复制到 Nginx Runtime。日常源码调试不需要先做 production build。

# 9. 本地数据、文件、日志和 Secret 在哪里

本地源码调试的主要持久状态：

```text
PostgreSQL
→ Docker volume: aima-ugc-postgres-dev-data

Excel 输入 / Raw / Export 等 Artifact
→ .runtime/data/artifacts/

应用日志
→ .runtime/logs/
   ├─ api.log
   ├─ worker.log
   └─ scheduler.log（启用时）

AIMA 内部 Secret
→ .runtime/internal-secrets/
   ├─ postgres_password
   ├─ import_batch_cursor_signing_key
   ├─ content_cursor_signing_key
   └─ collection_runtime_cursor_signing_key

外部 Provider / LLM Secret
→ .runtime/secrets/
   ├─ tikhub_api_key（配置时）
   └─ llm_api_key（配置时）

Frontend 依赖锁指纹
→ .runtime/dev/frontend-package-lock.sha256
```

`.runtime/` 和 `env.local` 都被 Git 忽略。

旧版本遗留在 `.runtime/secrets/` 下的 `postgres_password` 不属于当前运行时布局，launcher 不读取它；确认不再需要旧本地数据后可以人工删除。

上传的 Excel 原文件作为 Input Artifact 保存到 Local ArtifactStore，Import Batch、Job、Content 等业务事实保存到 PostgreSQL；因此完整 Excel Web 调试确实需要 PostgreSQL + Worker，而 `backend.py` 已自动把这两者包含在启动流程里。

# 10. 第一次导入 Excel 前还需要一个业务配置

本地运行配置可以自动准备，但**业务配置不能被 launcher 猜测**。

正式 Import/Collection 使用全局 Rule Relevance。一个全新数据库第一次使用时，请在前端：

```text
采集策略
→ 新建关键词包
→ 添加业务关键词（例如当前真正要监测的关键词）
→ 全局相关性
→ 选择该关键词包
```

然后再去：

```text
采集运行中心
→ 导入 Excel
```

不自动创建“爱玛”默认词包，是为了避免 dev launcher 变成业务配置的第二事实源。

# 11. 本地联调 Smoke

Backend 和 Frontend 都启动后，第三个终端可以执行：


# 12. 停止、重新启动和重置本地数据库

Backend 终端按 `Ctrl+C` 会停止 API、Worker 和本次启动的 Scheduler；PostgreSQL 容器与 named volume 默认保留。Frontend 终端按 `Ctrl+C` 停止 Vite。

如果明确要**破坏性清空本地源码开发数据库**，先停止 Backend，再手工执行：

```bash
docker rm -f aima-ugc-postgres-dev
docker volume rm aima-ugc-postgres-dev-data
```

随后删除与这个本地数据库绑定的当前内部密码：

```text
.runtime/internal-secrets/postgres_password
```

如果还存在旧文件：

```text
.runtime/secrets/postgres_password
```

它已经不被 launcher 使用，可以一并人工删除。下次 `backend.py` 会重新创建空数据库、生成新的内部随机密码并执行全部 Migration。这只允许用于本地源码开发数据，不要把这组命令用于完整 Compose 或包含真实业务数据的服务器。

Windows Docker Desktop 完整 Compose 的停止/重置方式见第 15.2 节；它使用独立 named volumes，不等于上面的源码 launcher 数据。

# 13. 高级开发：直接启动正式进程

日常优先使用两个 launcher。只有调试具体进程边界时才直接运行正式进程。

API：

```bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090 --reload --reload-dir backend/src
```

Worker：

```bash
uv run python -m aima_ugc.entrypoints.worker_main
```

Scheduler：

```bash
uv run python -m aima_ugc.entrypoints.scheduler_main
```

Migration：

```bash
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

直接启动这些正式进程时，调用者仍需自己提供它们要求的 `AIMA_*` 和 Secret File；这是高级调试路径，不是普通开发者快速开始。

# 15. 源码开发、完整 Docker Runtime 与 Internal V1-A 的边界

仓库按**运行方式**维护入口，不机械按“本地/生产”拆第二套业务配置：

```text
源码开发 / 热更新
→ env.local
→ scripts/dev/backend.py + scripts/dev/frontend.py

Linux / WSL 完整 Docker Runtime
→ env.production + compose.yaml
→ AIMA_HOST_ROOT bind mount

Windows Docker Desktop 原生 CMD / PowerShell
→ 同一个 env.production
→ compose.yaml + compose.windows.yaml
→ Docker-managed named volumes

公司 Linux 服务器 / 后续 Production Runtime
→ env.production + canonical compose.yaml
→ AIMA_HOST_ROOT=/data/AIMA_UGC
```

`compose.windows.yaml` **不是第二套业务 Compose**。它只覆盖 PostgreSQL、Artifact、日志和内部 Secret 的持久 storage source；API/Worker/Scheduler/Migration command、环境、Health、depends_on、网络、端口和外部 Secret 仍由根 `compose.yaml` 定义。

Internal V1-A 当前容器拓扑始终是：

```text
bootstrap
→ 只负责持久目录/volume 和内部随机 Secret

postgres
→ PostgreSQL 18.4

migrate
→ alembic upgrade head，一次性独立进程

configure
→ 幂等维护 Internal V1 Provider Config / 校验 LLM 配置，一次性独立进程

api / worker / scheduler
→ 正式后端进程

frontend
→ Vue build + 非 root Nginx，同源代理 /api 与 /health
```

## 15.1 Linux / WSL 本地完整 Docker：仓库相对 Host Root

如果本地文件系统具备 Linux POSIX owner/mode 语义，可以继续使用 canonical Compose：

```bash
cp env.production.example env.production
```

在本机 `env.production` 里设置：

```dotenv
AIMA_HOST_ROOT=./.runtime/compose
```

之后始终运行：

```bash
docker compose --env-file env.production up -d --build --wait
```

持久状态：

```text
.runtime/compose/
├─ postgres/
├─ runtime/
│  ├─ data/
│  └─ logs/
└─ shared/
   └─ secrets/
```

`.runtime/` 已被 Git 和 Docker build context 忽略。Linux 永久 CI 会真实验证仓库相对 Host Root 的 startup/readiness/persistence。

## 15.2 Windows Docker Desktop：CMD / PowerShell 标准 Compose CLI

Windows 原生模式不要求进入 WSL 终端，也不要求把 PostgreSQL/Secret bind mount 到 NTFS。它保留相同业务 Runtime，但把四类持久状态放到 Docker Desktop 管理的 Linux named volumes。

第一次从仓库根创建本机配置：

```cmd
copy env.production.example env.production
```

或 PowerShell：

```powershell
Copy-Item env.production.example env.production
```

编辑 `env.production` 后，CMD 与 PowerShell 使用完全相同的正式启动命令：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production up -d --build --wait
```

查看服务与日志：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production ps
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production logs -f api
```

日常停止并删除容器/网络，但保留 named volumes：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down
```

只有显式执行下面命令才会破坏性删除 Windows 本地 PostgreSQL、Artifact、日志、内部 Secret 和 AIMA service images：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down -v --remove-orphans --rmi all
```

Windows 原生持久状态由 Docker Desktop named volumes 管理：

```text
windows_runtime_data
windows_runtime_logs
windows_postgres
windows_internal_secrets
```

实际 volume 名会带 Compose project 前缀。可用 `docker volume ls` 查看。

在这个 Windows override 中，`AIMA_HOST_ROOT` 仍保留在同一个 `env.production` Schema 中，但**不决定 Windows 的持久数据物理位置**；所有对应 bind target 已由 `compose.windows.yaml` 按 target 替换成 named volume。

详细说明见 [`guides/03_Windows Docker Desktop Compose运行.md`](guides/03_Windows%20Docker%20Desktop%20Compose运行.md)。

永久 CI 的证据边界是：Windows Runner 直接验证标准 Compose CLI 在 CMD/PowerShell 下可解析同一 `compose.yaml + compose.windows.yaml + env.production`；Ubuntu Docker Engine 真实运行 merged named-volume Runtime 并验证严格 Secret mode、PostgreSQL/Migration/Readiness 和重启持久化。GitHub Hosted Windows Runner 本身不提供可依赖的 Docker Desktop Linux-container Runtime，因此首次在具体开发机使用时仍应执行一次本机 smoke。

## 15.3 公司服务器 Internal V1：canonical Compose + 数据盘 Host Root

服务器从同一个模板生成自己的 `env.production`：

```bash
cp env.production.example env.production
chmod 0600 env.production
```

服务器保持：

```dotenv
AIMA_HOST_ROOT=/data/AIMA_UGC
```

canonical `compose.yaml` 固定推导：

```text
PostgreSQL        → /data/AIMA_UGC/postgres
Artifact          → /data/AIMA_UGC/runtime/data
应用日志          → /data/AIMA_UGC/runtime/logs
AIMA 内部 Secret → /data/AIMA_UGC/shared/secrets
```

然后编辑公司内网 bind IP、TikHub/LLM 等机器配置并运行：

```bash
docker compose --env-file env.production up -d --build --wait
```

Internal V1-A/B 当前仍允许服务器现场 `--build`，因为这一阶段目标是验证仓库级最小部署栈和真实公司服务器。`/data/AIMA_UGC` 是持久 Data Root，不属于某个应用版本 Release；后续升级应用不能删除、移动或替换这个目录。

Windows storage override **不得**用于公司服务器，Production 也不依赖它。

## 15.4 Secret 为什么仍然分层

运行平台不同，Secret 分类不变：

```text
AIMA 内部随机 Secret
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
→ AIMA_SECRET_DIR=/run/internal-secrets

外部凭据
AIMA_TIKHUB_API_KEY
AIMA_LLM_API_KEY
→ Compose Secret
→ AIMA_EXTERNAL_SECRET_DIR=/run/secrets
```

Linux/服务器：内部 Secret 持久于 `${AIMA_HOST_ROOT}/shared/secrets`。

Windows Docker Desktop：内部 Secret 持久于 Docker named volume `windows_internal_secrets`，bootstrap 仍在 Linux 容器内施加相同的 `root:11001 / 0440` 文件权限；没有增加“Windows 弱权限模式”。

TikHub/LLM Key **不是**业务容器普通环境变量；Provider Config 继续只保存 `secret_ref`，不保存真实 Key。

PostgreSQL password 不要求管理员配置。无论 Linux bind 还是 Windows named volume，都遵守：

```text
空数据库 + 密码不存在
→ bootstrap 自动生成

已有 PostgreSQL 18 数据 + postgres_password 存在
→ 复用原密码，不轮换

已有 PostgreSQL 18 数据 + postgres_password 丢失
→ bootstrap fail closed
→ 禁止生成一个无法与既有数据库匹配的新密码
```

## 15.5 网络默认与 Internal V1-B

默认：

```dotenv
AIMA_HTTP_BIND_IP=127.0.0.1
AIMA_HTTP_PORT=8080
```

因此本地/仓库级 V1-A 默认只允许宿主机本地访问。进入 Internal V1-B 做真实公司服务器验收时，再把 `AIMA_HTTP_BIND_IP` 调整为管理员批准的公司内网地址，并验证真实网络可达性；PostgreSQL/API 仍不得发布到普通公司网络。

## 15.6 完整 Production Release：服务器仍加载不可变镜像

本地 Windows 支持不改变完整 Production Release 目标。正式服务器最终应获取已验证 Release，完成 `docker load` / 完整性校验后使用 canonical Production Runtime 启动，禁止在服务器现场构建与 CI 不同的镜像：

```bash
docker compose --env-file env.production up -d --no-build --pull never --wait
```

服务器仍使用：

```dotenv
AIMA_HOST_ROOT=/data/AIMA_UGC
```

应用镜像/Release 可以升级或回滚，而 PostgreSQL、Artifact、日志和内部 Secret 保持在 Release 外部的同一持久根。

当前仍不包含：

```text
Internal V1-B 的真实公司服务器 / 浏览器 / 容器重启与宿主机 reboot 验收
真实 TikHub / LLM 有界 Smoke
完整离线 Release Bundle、images.tar、Manifest、SBOM、签名与 Digest 固化
企业认证 / 授权 / HTTPS 正式入口
PostgreSQL + Artifact 同时点协调 Backup / Restore
```

# 16. 常见问题

## Docker 未启动

源码开发 Backend 会直接报错并停止。Compose 启动同样要求 Docker Engine / Docker Desktop 正常且当前用户有执行 Docker Compose 的权限。

## Windows 可以直接从 CMD / PowerShell 启动吗

可以。Docker Desktop 已启动后，从仓库根执行：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production up -d --build --wait
```

首次没有 `env.production` 时先从 `env.production.example` 复制一次并编辑。`compose.windows.yaml` 只负责 Windows named-volume 存储适配，不需要额外 wrapper。

## Windows 的 PostgreSQL 文件为什么不在 `.runtime/compose`

Windows 原生模式刻意使用 Docker-managed named volume，避免把 PostgreSQL 和内部 Secret 直接放在 NTFS bind mount 上。需要宿主可见 `.runtime/compose` 时，请在 Linux/WSL 文件系统使用 canonical `compose.yaml`。

## Windows `down` 后数据会丢吗

普通：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down
```

不删除 named volumes，数据会保留。只有显式加 `-v` 才会删除本项目 named volumes，是破坏性重置。

## 本地升级后提示旧 `.runtime/secrets/postgres_password` 不再受支持

这只针对源码开发 launcher：本机还保留已有 `aima-ugc-postgres-dev-data` volume，但新的 `.runtime/internal-secrets/postgres_password` 不存在。launcher 不再把旧路径密码迁移到新目录，也不会生成一个新密码去尝试连接既有数据。

如果旧源码开发数据可以丢弃，按第 12 节重置；若必须保留旧数据，需要先自行确认数据库 Role 的真实密码，并把匹配值放到 `.runtime/internal-secrets/postgres_password`。

## 正式 Compose 启动失败并提示已有 PostgreSQL 数据但缺少 `postgres_password`

不要删除数据库目录，也不要手工生成新密码。恢复与这份 PostgreSQL 数据匹配的原 `postgres_password`，再重新执行同一条 Compose 启动命令。自动生成新值不能修改既有数据库账户密码，只会造成应用与数据库不匹配，因此系统会主动拒绝这种恢复方式。

## `/health/live` 正常但 `/health/ready` 失败

`live` 只表示 API 能响应；`ready` 才检查 PostgreSQL、ArtifactStore 和日志目录。源码开发查看 `.runtime/logs/`；Linux Compose 查看 `${AIMA_HOST_ROOT}/runtime/logs`；Windows Docker Desktop 可直接执行：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production logs -f
```

或通过 Docker Desktop 查看 named-volume Runtime 的容器日志。

## AI/TikHub 显示未配置

源码开发按本文第 5/6 节填写 `env.local`；完整 Compose 填写 `env.production` 中相应 Base URL/Model/API Key 后重新启动。没有显式业务动作时不会因为 Key 存在就自动发起 AI 付费调用。

## Excel 上传后一直 queued

正常源码开发与完整 Compose 都会启动 Worker。持续 queued 时检查 Worker 进程/容器和对应 `worker.log`，不要用历史测试 harness 代替正式 Worker。
