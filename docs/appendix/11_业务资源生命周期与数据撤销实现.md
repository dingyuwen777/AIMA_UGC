# 业务资源生命周期与数据撤销实现

本文说明 AIMA_UGC 中“停用、归档、恢复、永久删除、数据导入撤销”的统一实现边界。它解释长期语义和调用链，不复制 OpenAPI、SQLAlchemy 列定义或 Alembic DDL；精确机器事实以代码、Contract 和 Migration 为准。

## 1. 解决什么问题

系统中的词包、采集计划、Provider、Analysis Scheme 和数据导入任务都可能在长期使用中被替换或不再使用，但它们的历史引用价值不同。

不能把所有“删除”都实现成数据库 `DELETE`：

- 已经参与过采集、导入或 AI 分析的配置需要继续解释历史运行；
- 当前生效或仍被其它资源引用的配置不能直接退出运行链；
- 数据导入撤销需要撤回该导入对当前业务视图的贡献，但不能破坏其它来源仍在支持的 Content；
- 只有从未进入业务历史、也没有引用关系的资源，才适合永久删除。

因此系统使用下面的分层语义：

```text
编辑
→ 改变当前配置，遵守版本/并发约束

停用
→ 暂停继续参与运行，但仍属于当前配置目录

归档
→ 退出普通业务目录和运行入口，历史事实继续保留

恢复
→ 重新进入当前配置目录；默认保持停用/非默认/非 active，避免恢复即执行

永久删除
→ 只允许从未进入业务历史、且没有引用关系的归档资源

数据导入撤销
→ 撤回指定 Campaign 的来源贡献；不是删除 Content 历史
```

## 2. 资源生命周期统一原则

### 2.1 归档与停用不是同一个状态

停用资源仍是当前可管理配置，例如临时暂停的词包、计划或 Provider。

归档资源不再出现在普通运行目录，不应继续被：

- Import / Historical Import 选中；
- Scheduler 扫描；
- Collection Plan 执行；
- Provider 当前配置选择；
- Analysis active 配置读取。

归档时间使用独立生命周期字段表达，不能用 `enabled=false` 或 `is_active=false` 代替。

### 2.2 恢复默认不重新执行

恢复只表示“重新进入当前配置目录”，不表示立即恢复业务运行：

- Keyword Pack：恢复后保持停用；
- Collection Plan：恢复后保持停用，并通过新 `schedule_version` 重新进入显式启用流程；
- Provider：恢复后保持停用、非默认；
- Analysis Scheme：恢复后保持非 active，需要显式发布或回滚某个 Version 才重新生效。

这避免“整理归档资源”产生意外采集、外部请求或 AI 运行。

### 2.3 永久删除是保守资格，不是普通操作

永久删除前先计算资格。只要发现历史引用，默认阻止删除并保留归档资源。

保守策略意味着：

> 宁可保留一条已经没有运行价值的历史配置，也不能为了目录整洁破坏历史解释、审计或重放能力。

## 3. Keyword Pack

当前词包支持：

```text
创建 / 编辑元数据
添加关键词
停用
停用后删除词包成员
复制
归档 / 恢复
条件永久删除
```

关键规则：

- 修改词包元数据或删除成员使用词包版本作为乐观并发前提；
- 删除已有关键词成员前必须先停用词包；
- 一个 Keyword 实体可被多个词包共享，删除成员不会无条件级联删除共享 Keyword；
- 复制词包会复制成员与车型关系，但副本默认停用；
- 全局相关性仍在引用、或未归档且启用的采集计划仍在引用时，不能归档；
- 已进入采集计划、数据导入、Job 或 Collection Run 历史的词包不能永久删除。

归档词包由正式目录读取和 `PostgresScheduledKeywordSnapshotReader` 共同排除，不能重新进入 Import/Scheduler 冻结输入。

## 4. Collection Plan

Collection Plan 使用现有 `schedule_version` 表达配置版本，不新增第二套 Plan Version 表。

编辑时：

1. 锁定当前未归档 Plan；
2. 校验客户端 `expected_version`；
3. 替换平台、词包、车型等当前配置；
4. `schedule_version + 1`；
5. 清空下一次调度游标；
6. 历史 Occurrence/Run 继续保留原版本号和冻结快照。

归档时自动停用并提升版本。Scheduler 的计划扫描、Plan 读取、启停和 cursor 更新都显式排除归档 Plan，因此归档不是前端标签，而是运行时门禁。

永久删除只允许没有历史 Occurrence、Collection Run 等引用的归档计划。

机器事实入口：

- [`backend/src/aima_ugc/adapters/persistence/postgres/collection_plan_lifecycle.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/collection_plan_lifecycle.py)
- [`backend/src/aima_ugc/adapters/persistence/postgres/collection_planning.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/collection_planning.py)

## 5. Provider Config

Provider 的稳定 UUID 与历史运行解释需要保留。

归档规则：

- 默认 AI Provider 不能直接归档，必须先切换默认配置；
- 未归档采集计划仍引用时不能归档；
- 归档后强制 `enabled=false`、`is_default=false`；
- 恢复后同样保持停用、非默认。

永久删除会检查：

- Collection Plan 历史引用；
- `provider_requests` 历史；
- Analysis Run 的冻结 `runtime_config_snapshot.provider_config_id`。

因此一个已经实际参与过采集或 AI 分析的 Provider 只允许归档，不允许抹掉配置身份。

### 5.1 数据库接管后的 LLM 配置不回退环境变量

一旦数据库中曾存在 LLM Provider，即使这些 Provider 后来全部停用或归档，运行时也不会悄悄重新启用旧环境变量里的 LLM 配置。

语义是：

```text
数据库已进入 LLM 配置控制面
+ 当前没有有效默认 Provider
→ LLM 当前未配置
```

而不是：

```text
→ 回退旧 env 配置
```

这避免归档动作意外恢复一个管理员已经退出使用的模型配置。

## 6. Provider“测试连接”

测试连接是独立的管理操作，只验证当前配置的鉴权和服务可达性，不创建采集任务、Content 或 LLM 推理。

当前边界：

- TikHub：请求受信任 TikHub Origin 的账户信息接口，不提交关键词、帖子或评论采集参数；
- OpenAI-compatible LLM：请求配置 Base URL 下的 `/models` 元数据接口，不发送 completion/chat 请求；
- 第三方响应正文、API Key、Secret 引用不进入公共响应或审计详情；
- 数据库读取在短事务中完成，外部 HTTP 不占用数据库事务；
- 连接测试结果只返回成功/失败、用户可读原因和延迟；
- 已归档 Provider 不允许测试连接。

机器事实入口：

- [`backend/src/aima_ugc/adapters/providers/connectivity.py`](../../backend/src/aima_ugc/adapters/providers/connectivity.py)

## 7. Analysis Scheme

Analysis Scheme 已有自己的版本状态机：

```text
draft
published
retired
```

发布或回滚某个 Version 时，旧的 published Version 会退役。资源生命周期不再增加第二套 Version 状态，只管理 Scheme 聚合本身：

- 复制：从来源 Scheme 最新 Version 的定义创建一个全新 Scheme 的 draft v1；
- 归档：当前 active Scheme 不能直接归档；
- 恢复：恢复后仍是非 active；
- 已归档 Scheme 不能追加草稿、更新草稿、发布或回滚；
- 曾经发布过，或曾被 Analysis Run 引用的 Scheme，只允许归档；
- 从未发布、从未进入运行历史的纯草稿 Scheme，归档后才可能永久删除。

机器事实入口：

- [`backend/src/aima_ugc/adapters/persistence/postgres/analysis_schemes.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/analysis_schemes.py)

## 8. Data Import Campaign 撤销

### 8.1 撤销的是来源贡献，不是直接删 Content

一个 Content 可能同时由多个导入/采集来源支持。撤销某个 Data Import Campaign 时：

- 该 Campaign 独占支持的 Content 退出当前业务可见视图；
- 仍有其它有效来源的共享 Content 保留；
- 该 Campaign 实际覆盖的 Current 字段，只在有精确可逆贡献证据时回退；
- Provider Raw、Content Version、审计和来源历史不因撤销被抹掉。

### 8.2 Contribution Delta

新写入会为 Content 来源保存精确 before/after Contribution。撤销时按逆序检查：

```text
当前值仍等于该来源写入后的值
+ 当前 freshness marker 仍等于该来源写入后的 marker
→ 才恢复 before
```

如果后来有新来源更新了同一字段，撤销不会覆盖更新后的事实。

`standard_observation` 和 `historical_fill_only` 都必须在业务写事务内捕获 Contribution；不能只给其中一条写入路径做可撤销支持。

### 8.3 老数据缺少可逆证据时 fail closed

历史数据可能是在 Contribution 机制上线前写入。对于已经实际创建、补空或更新 Current、但没有精确可逆 Delta 的 Campaign：

- 预览返回不可安全撤销；
- 明确给出缺少可逆证据的数量/原因；
- 执行接口返回冲突；
- 不用 Version 差值、字段猜测或“独占 Content 直接隐藏”冒充安全回滚。

### 8.4 撤销后的 Content Version

撤销重组 Current 后会追加新的 Content Version。这个 Version 不是伪装成外部 Provider 观测，而是使用内部、非计费、可审计的生命周期来源；撤销 Campaign、Content 和新 Version 的对应关系单独保存。

同一个 Campaign 重复撤销必须幂等，不重复追加撤销事实或生命周期 Version。

## 9. Schema 与 Migration

生命周期 Schema 仍遵守项目的单一 Migration 规则：

- Data Import Contribution / Revocation 由对应 Alembic migration 建立；
- 词包、采集计划、Provider、Analysis Scheme 的 `archived_at` 由同一产品生命周期 migration 建立；
- SQLAlchemy metadata 通过各 Owner 的幂等注册函数与 Migration 保持一致；
- 应使用现有 Migration compatibility + `alembic check` 验证 drift，不复制第二套 DDL 检查。

精确 revision、列名、约束名以 `migrations/versions/` 和 [`backend/src/aima_ugc/database_schema.py`](../../backend/src/aima_ugc/database_schema.py) 为准。

## 10. 前端与 Contract

前端不能手写平行生命周期 API。正式链路是：

```text
FastAPI 最终 entrypoint
→ scripts/contracts/generate.py
→ contracts/openapi/openapi.json
→ Orval
→ frontend/src/generated/api/client.ts
→ Feature API / Store / Page
```

因此新增或修改生命周期动作后，必须先生成并检查 OpenAPI，再生成前端客户端，最后接页面行为。

UI 应优先表达业务动作：

- 停用；
- 归档；
- 恢复；
- 永久删除；
- 测试连接；
- 撤销导入。

不要把 `archived_at`、Provider Request ID、Raw Artifact ID、Campaign UUID 等工程字段直接作为主要用户操作语言。确需技术排障时再进入详情或审计视图。

## 11. 验证边界

不同风险由不同证据证明：

| 风险 | 主要证据 |
| --- | --- |
| 归档资源仍进入普通目录/调度 | Repository PostgreSQL 集成测试 |
| 历史引用被永久删除 | 删除资格 PostgreSQL 集成测试 |
| Provider 测试连接触发业务副作用 | Mock HTTP 单测 + 有界真实 Probe（仅需要时） |
| OpenAPI 没包含扩展路由 | 最终 `create_app().openapi()` Contract 测试 |
| Migration 与 metadata 漂移 | Migration compatibility + `alembic check` |
| 导入撤销破坏共享 Content | 真实 PostgreSQL 撤销集成测试 |
| UI 动作没有接真实后端 | generated client + Browser/Full-stack 验收 |

Mock HTTP 可以证明请求方法、路径和无推理/无采集参数，但不能替代真实 PostgreSQL 或第三方服务可达性证据。

## 12. 当前限制

- 永久删除 Provider Config 当前只删除数据库配置；历史 Secret 文件的物理回收不与数据库事务混做，不能把数据库删除宣称成 Secret 已清理；
- 上线前必须完成 OpenAPI/Orval 生成、Migration/PostgreSQL 集成和前端验收；
- 真实 TikHub/LLM Probe 不进入普通 CI，只有需要确认第三方当前事实时才以显式、有限、Secret-safe 的方式执行。
