# 1. AI 为什么不属于 Canonical / Mapper

Canonical 表示外部来源真正观察到的事实，例如：

```text
标题
正文
作者展示信息
发布时间
互动指标
评论
来源
```

AI 的：

```text
相关/无关
发声类型
情感
舆情标签
```

都是**派生分析事实**，不是 Provider 原始事实。

所以链路固定分层：

```text
TikHub / Excel
→ Mapper
→ CanonicalContentV1
→ Content Owner / UnifiedContentRecordV1
→ Analysis
```

禁止：

- TikHub Mapper 直接判断情感；
- Excel Mapper 把源文件旧“情感列”当当前 AI 结果；
- 把 AI 标签塞进 `CanonicalContentV1.observed_fields`；
- 把完整 `UnifiedContentRecordV1` 当成 `contents` 的 JSONB。

正式 PostgreSQL 中：

```text
Content 事实
→ contents / content_versions ...

AI 事实
→ analysis_content_results / label_pairs ...
```

# 3. 当前表格格式一次模型调用做什么

当前一次模型调用仍完成一条 Content 的整体分析，不拆成固定的多阶段模型请求：

```text
relevance
→ source_type
→ content_intent
→ real_user_qualified
→ 按官号白名单、A-F 准入和组合表校验 voice_type
→ sentiment
→ labels[]
```

当前业务算法由唯一 Prompt 持有，程序不复制业务关键词分类器。模型返回主体、意图、A-F 准入结论及发声类型，Validator 按同一版本的组合表核对它们是否一致；未通过准入不能返回文档中定义的真实用户发声类型。证据不足的自然表达使用文档规定的非真实用户类别，交易、商业及机构内容按各自规则处理。

模型响应仍包含各维度原文证据和 `decision_status`。内部主体、意图、证据通过本地 Validator 后只投影为既有公共结果：

```text
ContentLabelAnalysisV3
→ relevance / voice_type / sentiment / labels[]
```

内部主体、意图、准入及证据不写入公共业务结果。对外 V3 结果仍直接保存该版本实际返回的发声类型、情感和标签值。正式与离线高并发继续保持：

```text
1 Content = 1 个独立逻辑 LLM Request
清晰内容 = 1 次 primary
结构/闭集错误 = 条件 repair
证据或未收敛结果 = 条件 judge
```

真正结果继续携带 Prompt/Taxonomy/Model/Input Hash/时间等可复现身份。

# 4. 当前固定结构与证据约束

`relevance=relevant` 必须有合法情感、至少一个标签及对应原文证据；`relevance=irrelevant` 固定为：

```text
sentiment = null
sentiment_evidence = []
labels = []
```

`relevance_evidence / voice_evidence / sentiment_evidence / labels[].evidence` 的普通值都必须是以下五个文本字段中的连续原文子串，不能改写、跨字段拼接或臆造：

```text
title
text
author.display_name
author.bio
author.verification_label
```

当前格式要求 evidence 来自实际可见文本；五个文本字段全部为空时，`relevance_evidence` 与 `voice_evidence` 只接受 `[EMPTY_INPUT]` 哨兵。最终 `decision_status` 必须收敛为 `clear`。

本地校验只确认固定结构、闭集、标签父子关系、证据来源和当前协议不变量，不实现第二套关键词/NLP 分类器。

---

# 5. `source_type / content_intent / voice_type` 怎样协作

当前格式输出 `source_type` 与 `content_intent` 作为内部辅助分类，用于解释当前可见主体和内容目的；它们都有 Prompt 定义的闭集，最终输出不能使用 `unknown`。

`RuntimeTaxonomyValidator` 校验主体、意图、准入布尔值、发声闭集和组合一致性，同时核验各维度证据。保存、筛选和展示直接使用该 Scheme Version 文档表格中的发声类型、情感和标签值，不生成第二套分类值，也不用当前文档改写旧结果。

# 6. 模型实际能看到哪些输入

`ContentLabelingModelItem` 只发送：

```json
{
  "item_no": 1,
  "platform": "xiaohongshu",
  "title": "...",
  "text": "...",
  "author": {
    "display_name": "...",
    "bio": "...",
    "verification_label": "..."
  }
}
```

`item_no` 只用于批次配对。`platform` 用于平台加作者名的官号白名单精确匹配，也参与内部 `input_hash`；模型不会收到 PostgreSQL Content UUID、URL、互动指标、Raw 地址、命中关键词或其他未批准字段。普通 evidence 只能来自五个文本字段，不能使用 `platform`。

发给模型的字段全部按不可信待分析数据处理。其中出现的提示、命令或 URL 不得改变系统 Prompt、分类闭集和输出协议。

# 7. Prompt、Taxonomy 与 Scheme 怎样保持同源

唯一 Git Prompt 与管理员编辑都消费同一 Markdown 文本；编译器从六张标记表生成完整机器快照并核对 JSON 输出示例。展示顺序显式保存，JSONB 键重排不会改变顺序。自然语言指南原样保留，不能自动删除以掩盖分类引用冲突。保存、发布、恢复以完整文本、编译快照及双 Hash 原子进行；历史版本按其已保存协议恢复，不经当前编译器重写。

未经支持的格式失败关闭。空库由镜像内唯一 [`backend/src/aima_ugc/modules/analysis/prompts/content_labeling.md`](../../backend/src/aima_ugc/modules/analysis/prompts/content_labeling.md) 创建首个 active Version。之后直接修改 Git Prompt 时，分析预览/创建 Run 的显式刷新入口会判断当前 lineage：仅当未删除 Scheme 仍只有默认 Scheme，且该 Scheme 全部 Version 都由系统 Git actor 创建时，才允许把当前 Git Prompt 追加为新的 published/active Version；历史 Analysis Run 不会被改写，仍引用创建时的旧 Version。只要存在另一套未删除 Scheme，或默认 Scheme 出现人工创建 Version，Git 自动刷新就停止，由管理员显式发布/回滚决定运行版本。

# 8. 为什么本文不复制完整 AI Taxonomy

Scheme 的情感、发声类型、标签体系和判断规则都是业务可变事实。运行时唯一完整事实是数据库 active Analysis Scheme Version；Git [`backend/src/aima_ugc/modules/analysis/prompts/content_labeling.md`](../../backend/src/aima_ugc/modules/analysis/prompts/content_labeling.md) 是当前唯一首次打标 bootstrap/灾备基线，生产目录不复制历史 Prompt 文件；已支持的历史协议由冻结版本恢复。

本文解释加载、校验、执行、持久化和修改入口，不复制容易漂移的完整标签表或官号白名单。

# 9. 模型返回后代码怎样校验

`RuntimeTaxonomyValidator.validate_response()` 依次检查：

```text
JSON 顶层 / items / item_no / 顺序 / 重复 / 缺失
→ 当前固定字段结构
→ relevance / voice_type / sentiment membership
→ 标签父子关系与重复标签对
→ relevant / irrelevant 形状
→ source_type / content_intent 辅助闭集、准入与组合规则
→ voice_evidence 所有发声类型均非空
→ evidence 是否来自对应 Content 五个文本字段
→ 全空输入 EMPTY_INPUT 唯一例外
→ decision_status 必须最终 clear
```

稳定错误码包括 `invalid_json / missing_item / unknown_voice_type / invalid_secondary_for_primary / fabricated_evidence / missing_evidence / irrelevant_has_sentiment_evidence / decision_needs_judge`。同批已合法 item 会立即晋级，不因另一条失败而重复调用。

# 10. Primary、Repair、Judge、Transport Retry 与 RPS

## 10.1 Primary / Repair / Judge

每条 Content 首次使用 `request_kind=primary`。固定结构、非法 JSON 或 Taxonomy membership 错误进入 `repair`；证据伪造/缺失或模型主动返回 `needs_judge` 才进入 `judge`。

Judge 只收到当前 unresolved item、稳定错误码和同一五字段输入，要求独立重新判断，不携带上一响应全文。历史 Run 和离线入口按冻结/显式 `max_retries` 限制轮数；新正式 v2 Run 没有 Validation 次数或持续时间上限，继续只复判 unresolved Item，采用下文持久退避。同一轮混合出现结构错误和语义歧义时按 item 拆成 repair/judge 请求；没有歧义的内容保持一次调用。

## 10.2 Transport Retry

```text
429 / 部分 5xx / 连接失败 / 超时
→ RetryingContentLabelingLLM
```

基础 `OpenAICompatibleContentLabelingLLM.complete()` 一次调用最多一次物理 HTTP 发送。Transport Retry 在外层明确重发，不与 Validation Retry/Judge 共用计数器。

## 10.3 max_rps

每个物理 HTTP Attempt（包括 Transport Retry）都必须重新经过 `RateLimitedContentLabelingLLM` 取得 RPS 时隙，避免 retry storm。

# 11. `ContentLabelingAttempt` 保存什么

每次 Validation Attempt 保存 item、`request_kind=primary/repair/judge`、错误、模型/Prompt/Taxonomy、开始/结束时间以及可获得的 token/cost 元数据。离线 `attempts.jsonl` 同步记录 `request_kind`。

当前正式 `analysis_content_results` 仍**没有** token/cost 或 V4 内部证据列；“运行时能计算 cost/校验证据”不等于 Analysis Result 表已经持久化这些字段。

# 12. 正式 PostgreSQL Analysis 怎样创建

当前 HTTP：

```text
POST /api/v1/analysis/content-runs/preview
POST /api/v1/analysis/content-runs
```

Preview/Create 共同读取当前默认 LLM Provider，冻结连接、模型和 Scheme 身份。新 Run 使用 `adaptive.v2`：同 Provider Config/Model 跨 Run 共享持久 Profile 的容量，Shard size 在 Create 时由学习的成功入库吞吐与目标时长派生：

```text
shard_size = clamp(成功入库 Content/s ÷ 所需 Shard 数 × 目标时长, 200, 50_000)
```

内部目标时长约 300 秒；没有历史时使用冷启动估计。精确常量与公式由 [`backend/src/aima_ugc/modules/analysis/adaptive_capacity.py`](../../backend/src/aima_ugc/modules/analysis/adaptive_capacity.py) 维护。历史固定 Snapshot 仍按原参数执行，不改写已冻结范围。

Shard size 与 HTTP timeout **不由管理员配置**。创建时冻结分片范围和初始等待，运行中不改 `shard_size` 或 `shard_no × shard_size`。v2 按真实模型等待证据有界延长后续 Read Timeout，历史 v1 保留冻结值；完整控制、资源和排障说明由 [`backend/src/aima_ugc/modules/analysis/README.md`](../../backend/src/aima_ugc/modules/analysis/README.md#14-共享自适应容量) 维护。固定 Job timeout、模型、思考模式、Prompt、Taxonomy 和生成配置保持；恢复协议也进入冻结业务身份。动态学习值不进入 Preview/Create/幂等确认 hash；真实连接/Secret Revision 或业务身份变化仍导致冲突。

环境配置同样遵守新协议，只提供连接和模型；原容量设置继续服务历史兼容入口。`AIMA_ANALYSIS_RUN_SHARD_SIZE` 和 `AIMA_ANALYSIS_BATCH_SIZE` 已移除。运行中的窗口可按 Provider 需求、CPU/内存、DB 余量和剩余工作扩展；已有分片不被取消。

机器预算继续复用 [`scripts/deploy/start_compose.py`](../../scripts/deploy/start_compose.py) 生成的 `compose.auto.yaml`：Docker Engine 可用资源决定各服务 CPU/内存硬上限，Worker 经 cgroup v1/v2 读取实际限制；API 经 `AIMA_AUTO_WORKER_CPU_CORES` / `AIMA_AUTO_WORKER_MEMORY_MIB` 使用同一 Worker 预算。运行时再读取可用内存压力，并结合 DB headroom 与 Provider 所需分片数限制投放。生成文件是部署资源分配结果，不能替代实时资源探测，也不为 AI 单独维护另一份机器参数文件。本机直接运行时使用当前进程可见 CPU 和宿主可用内存。文件生成到运行配额的链路由 [`tests/unit/test_compose_auto_scripts.py`](../../tests/unit/test_compose_auto_scripts.py) 验证，低 CPU、小内存、压力和恢复的正式投放由 [`tests/integration/content/test_analysis_adaptive_capacity.py`](../../tests/integration/content/test_analysis_adaptive_capacity.py) 验证。

Planner 对 `selected/query` 保留集合式短路径；公开 `all` 按稳定 Content UUID keyset 分批读取并连续追加 `content_id + current_version + target_ordinal`。高吞吐 Planner 用最后 `target_ordinal + 1` 恢复已冻结数量，不在每 1 万条批次后对越来越大的目标表重复 `COUNT(*)`。

`all` 完成后再次核对当前 Content 总数、已冻结 ordinal 和 Preview `expected_target_count`。只有一致才创建首批 Shard；数量变化以 `content_analysis_target_changed` fail closed。

下一批 Shard 由 Run 已知 `shard_count` 与已创建 Request 的连续 `shard_no` 推导，不再通过扫描全部 `analysis_content_run_targets` 计算 `floor(target_ordinal / shard_size)`。

# 14. 正式 Analysis Worker 怎样执行

正式代码：

- [`backend/src/aima_ugc/bootstrap/analysis_concurrent_worker.py`](../../backend/src/aima_ugc/bootstrap/analysis_concurrent_worker.py)
- [`backend/src/aima_ugc/bootstrap/analysis_high_throughput_planner.py`](../../backend/src/aima_ugc/bootstrap/analysis_high_throughput_planner.py)
- [`backend/src/aima_ugc/adapters/persistence/postgres/analysis_batch.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/analysis_batch.py)
- [`backend/src/aima_ugc/adapters/persistence/postgres/analysis_high_throughput.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/analysis_high_throughput.py)

正式 Shard 流程：

```text
读取 Run 冻结 Provider / Scheme / Prompt / Taxonomy
→ 验证配置身份
→ load_pending_page：按冻结 ordinal 持续取页，每页约 2 × max_concurrency，上限 10,000
→ 检查 cancel
→ 本地预检后首批即并发，不先发送串行探测请求
→ Shared Bounded Executor
→ 每秒刷新跨 Run 份额；本地物理上限与动态目标分离，份额允许为零
→ 动态 RPS 对每个物理 HTTP Attempt 生效，Retry 重新取时隙
→ Validation Retry / Transport Retry 分层
→ 完成结果在调度线程缓冲
→ 小任务或大任务尾部：已取完全部工作项且剩余未完成数不超过 max_concurrency，立即短事务提交
→ 其他阶段：满 200 条或首个结果等待约 1 秒即短事务提交
→ Heartbeat / Cancel
→ 空闲容量继续取下一条/下一页，不等待本页慢请求
```

LLM worker thread **不创建 PostgreSQL Session，也不持有数据库事务**。因此：

```text
1000 LLM in-flight
≠ 1000 PostgreSQL connections
```

批量短事务一次完成：

```text
1 次 Job Fence 校验
1 次 Request/Job 归属校验
1 次 Current Version 批量查询
多行 Result INSERT ... ON CONFLICT ... RETURNING
批量 Label Pair INSERT
executemany 更新 succeeded / failed / stale Request Item
```

幂等冲突时不会盲目覆盖已有 Result，而是批量读取既有业务值和标签并 fail closed 比较。

新正式 Run 的临时 Transport 耗尽仍 pending；历史固定 Run 继续终结对应 Content。401/402/403/404 和不可恢复的配置、Secret、Model、Prompt/协议错误停止整个父 Run，其他 Shard 和 Planner 不再补充。取消、失去 Lease 或达到 Attempt Deadline 会停止补充及后续 Transport/Validation Retry。接管重试只读取仍 pending 的内容，已提交成功项不会重发。

等待 HTTP 时，调度器每约 100 ms 醒来执行控制检查，正式取消/Lease 查询间隔约 250 ms。已取完全部工作项且剩余未完成数不超过一个并发窗口时，完成结果立即提交；其余阶段按数量或约 1 秒等待时间提交。这些是调度阈值，实际响应还包含数据库耗时。整页内容都已过期时继续沿扫描 ordinal 前进，只有扫描结束且 pending 清零才报告成功。

停止是协作式的：已经发出的同步 HTTP 不能靠取消 Future 撤回，也不能保证不计费；收到取消后等待当前 HTTP 返回或触发原网络超时，然后关闭 Client。HTTPX 的超时是连接/读/写/连接池等待限制，不是整个逻辑请求总时限。取消后不重试、不提交新结果；先前已经提交的成功结果保留。离线 Ctrl+C 同样收割可用结果并同步 checkpoint/审计，下一次运行按 identity/hash 恢复，全程无需数据库。

`analysis.execution_completed` 记录 Job/Run/Request、总耗时、装配耗时、数据库耗时、实际 HTTP 次数/峰值、逻辑调用次数、Transport Retry 和累计退避/限流等待。HTTP 累计耗时包含并发重叠，不能与总墙钟耗时直接相减来计算模型时间。`analysis.llm_request_completed` 增加 Content、逻辑/物理请求 ID 和请求耗时，正常请求仍为 DEBUG，错误为 WARNING，不记录 Prompt、正文或凭据。

声音广场和任务中心共用全局任务 Store 中的 Analysis Run 快照、在途查询和取消状态。活动 AI 任务（queued / running / cancelling）每秒轮询一次列表，同一浏览器页面内的两个入口共用一秒去重窗口；不为每个 Run 追加详情请求。任务终态退出快速轮询；任务中心其余来源和新任务发现保留 15 秒周期，广场活动导出保留 5 秒周期。后台标签页暂停，停止轮询会使尚未返回的状态查询失去继续加载内容的资格。

内容窗口只在 Run 状态或落库统计变化后重新读取，先确认新进度再读取内容。刷新期间又出现更新时保留下一次刷新，已完成任务也会补齐最后结果；查询失败则继续重试，避免状态完成后列表永远停在旧结果。初始内容、分类目录或导出查询不会阻塞独立的 AI 状态轮询。

活动任务不会被最近 50 条历史挤出列表。API 复用已成功 Shard 的持久结果，只对需要回退的 Shard 扫描 Item。取消后旧查询不能覆盖新状态；采集、打标、导出各自更新。

创建任务时主动读取创建后的快照，旧轮询不能覆盖或隐藏新任务。持续取页、及时提交、取消和失权的真实 HTTP/PostgreSQL 回归在 [`tests/integration/content/test_analysis_provider_concurrency.py`](../../tests/integration/content/test_analysis_provider_concurrency.py)；网页选择两条内容的验收在 [`frontend/e2e-fullstack/analysis-streaming.spec.ts`](../../frontend/e2e-fullstack/analysis-streaming.spec.ts)，复用既有 Full-stack Fixture 生成器和本地模型服务，模型服务等待两条请求都到达才回包。

为什么仍验证 `JobExecutionFence`：旧 Worker Lease 失效后不能继续把结果提交为当前合法事实。为什么还验证 Content Version/配置身份：执行期间 Content 或运行身份变化时不能把错误版本结果写成成功。

# 15. 什么叫 `stale`

Analysis 绑定 `content_id + content_version`。如果模型调用完成后 Current Version 已变化，批量 Repository 会把对应 Request Item 标记 `stale`，不会把旧版本结果当 current。

声音广场继续区分 `completed / stale / pending`。

# 16. Analysis Run 怎样定义“当前有效结果”

Current Analysis 先在明确目标版本内按 `analysis_content_runs.sequence_no DESC` 选择最新直接成功结果，没有直接结果时才采用正式输入等价引用。较早 Run 即使更晚完成，也不能覆盖更晚创建的 Run；最新 Run 失败/取消时旧成功结果继续作为 Current。等价证明、人工继承与直接重新分析的完整规则由 [backend/src/aima_ugc/modules/analysis/README.md](../../backend/src/aima_ugc/modules/analysis/README.md#6-analysis-为什么绑定-content-version) 维护。

Provider 连接、模型或 Scheme 的后续修改不会改写旧 Run 的冻结身份和 Runtime Snapshot。新协议容量从共享 Profile 动态读取，Shard size 和初始 Timeout 在创建时冻结；v2 可按真实延迟证据有界延长后续请求等待，历史 v1 的 Timeout 保持冻结。

# 20. 为什么一条内容一个模型请求

正式与离线均保持：

```text
任何情况下，一次逻辑 ContentLabeling 调用只包含一条 Content
```

原因：失败/Retry/费用/恢复粒度明确，一个坏 Content 不拖整个批次。高吞吐来自**并发多个单条请求**，而不是把几十条内容合成一个模型请求。

`ContentLabelingService` 仍保留 Sequence 能力用于通用 Service/历史兼容，但高吞吐执行器明确按单 Content 调用。

# 21. 离线 Checkpoint 怎样保证恢复

`checkpoints.jsonl` 是离线恢复事实源；`attempts.jsonl` 与 `failed.jsonl` 是调用/失败审计。恢复身份继续包含稳定 Content 身份、input hash、Prompt/Taxonomy/Model，命中后不重新付费调用。

---

# 22. 离线 preflight 为什么放在付费调用前

完整扫描并验证输入、稳定身份和 checkpoint 后才执行首批并发请求；输入后段格式坏时不会先把前面大量数据付费发送出去。

# 23. LLM 成本/Token 当前记录在哪里

`ContentLabelingLLMResponse` / `ContentLabelingAttempt` 可以携带 token、cache hit/miss、cost、pricing snapshot。正式 Worker 的 `analysis.llm_request_completed` 记录安全摘要；高吞吐成功请求使用 DEBUG，错误使用 WARNING，避免每秒数百/上千成功请求把 INFO 日志本身变成热路径。

当前仍没有 Analysis Result token/cost DB 列或金额/请求预算门禁。

# 27. 调试大批量数据

离线先看 summary 的 `rows_* / peak_in_flight / llm_attempts / HTTP requests / transport_retries / token/cost`。

正式 PostgreSQL 大 Run 重点看：

```text
Run target_count / shard_count / shard_size
共享 Profile C / RPS / state
Planner frozen ordinal
活动 Shard 数
单 Shard succeeded / failed / stale
LLM request audit
DB batch flush
```

4000 万目标下，正式 Planner 不再每 1 万条累计 `COUNT(*)`，也不在每次补 Shard 时扫描全部 Run Target。已成功 Shard 的 Run 统计优先读取持久 Job Result 计数，只对仍活动/异常的少量 Shard 扫描 Request Item。

并发参数仍不是越大越快。真实吞吐近似受：

```text
min(
  Provider/模型服务容量,
  共享 C / 平均模型延迟,
  共享 RPS,
  网络吞吐,
  本地 CPU/内存,
  PostgreSQL 批量写吞吐
)
```

限制。某个服务器能否稳定跑满 1000 必须在该部署环境压测，不能从 CI Runner 推断。

最后一个预留持有者退出时同时清除未闭尾窗和未完成候选，保留已学习的安全档与吞吐；同身份新任务不会借用上一批未完成的探测样本。仍有其他分片或未过期的未知 Fence 时保留共享证据和 C/RPS 承诺；本机受限窗口即使成功数少，也丢弃不适用候选。

429 分类优先采用当前响应的明确请求数或token配额，再使用已核验官方模型的并发声明；未知端点继续反馈学习。安全容量日志补充控制版本、候选累计时间/成功数/Validation失败数和已接受吞吐，便于判断是在收集证据、受机器/数据库限制，还是遭遇上游拥塞，不记录响应正文或密钥。

## 29.5 正式 Run 持久恢复

新 Run 冻结 `recovery.v2`。恢复复用现有 Run、Request Item 和 Job，不创建第二套任务队列。实现 Owner 为 [`backend/src/aima_ugc/adapters/persistence/postgres/analysis_recovery.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/analysis_recovery.py)，调度入口为 [`backend/src/aima_ugc/bootstrap/analysis_concurrent_worker.py`](../../backend/src/aima_ugc/bootstrap/analysis_concurrent_worker.py)。

新任务只有成功数等于目标数才能标为 `succeeded`；pending/未投放/failed/cancelled/stale 都不算成功。打标期间内容版本变化时保留 `stale`，任务显示 `partial_failed` 或 `failed`，不把旧版本标签覆盖到新内容。历史冻结协议不改写；系统错误、真实断网五分钟或手动取消仍是显式停止，不能用“全部成功”掩盖。

| 失败 | 持久行为 | 停止边界 |
| --- | --- | --- |
| 模型 JSON、字段、标签或证据未通过校验 | Item 保持 pending，保存错误码，下一轮复用 repair/judge；成功提交后清除恢复字段 | 不因次数或持续时间终结 Item；持续重试直到合法、取消或父 Run 因硬错误/真实断网停止 |
| network、真实发送 timeout（不含连接池等待） | 每次逻辑调用先执行原有四次显式 Transport Retry，耗尽后保存 pending/ready-at，退避并单探活 | 真实物理失败观测连续跨越五分钟，中途没有任何 HTTP 响应，以 `llm_transport_unavailable` 停止 |
| 408、429、5xx 或本地连接池等待 | 保持 pending，按原 Transport Retry/退避；限流和本地压力独立反馈容量 | 收到 HTTP 响应证明网络可达；连接池等待没有真实发送，两者均不能触发五分钟断网停止 |
| 401/402/403/404 或不可恢复配置/协议错误 | 立即写父 Run 停止事实，运行 Shard 不再补充，Planner 不再投放 | 立即失败；保留此前成功入库结果和可归属的已发合法结果 |

退避基线为 1/2/4/8/16/30 秒，带 0.5–1 倍 jitter、最长 30 秒；不以轮数终结可恢复 Item。等待项只存在数据库，ready-at 分页跳过未来项，并排除当前 in-flight 与尚未提交结果，不占 HTTP 线程。失败率和 429/延迟继续反馈同一容量 Profile，实际成功入库仍是唯一成功吞吐。

Run 的真实网络窗口与每个 Item 的 Validation 恢复独立。任意收到的 HTTP 响应，包括 429/503，都清除该 Run 在此之前的网络不可用故障；随后外层 JSON、choices、content 或模型输出不合法仍进入 Item Validation 修复。其他 Item 的成功不清除问题 Item 的错误断点，但 v2 不对该断点设置五分钟截止。一次失败后在本地等待五分钟不能证明持续断网，停止要求最后实际失败与连续首错之间至少五分钟。跨 Shard 按物理事件时间合并，迟到旧错误不能覆盖较新的响应，迟到响应也不能丢失其后的新失败。执行器与持久字段分别最多保留 4096 个失败时间段，极快故障时合并最旧半窗；响应落在压缩区间内时保守以响应时刻切分。调度线程每秒持久刷新，不等待整个逻辑 Retry 返回。

真实网络不健康时，同一 Run 只放行一个逻辑探活，沿用持有者 Job 的 Lease/Deadline 判断占用失效。其他 Shard 停止补充；收到任意 HTTP 响应后清除占用，已积压 Transport Item 恢复资格。429 的 C/RPS 保护仍生效，恢复资格不绕过共享许可。运行中的请求协作收尾，不能撤回已发送 HTTP。健康字段和 retry metadata 在 PostgreSQL 中保留，重启/接管不重置窗口；Job Fence 对观察、探活及业务写入同样生效。

逻辑恢复等待不消耗新的 Job attempt，也不延长原 1800 秒 Attempt Deadline。每个 Job 仍最多三次 Attempt；v2 当前 Request 在 Deadline 执行周期耗尽后仍有 pending，正式终态回调在同一事务创建同类型后继 Job 并切换原 Request 的 `job_id`。幂等身份包含 Request 与旧 Job，保留 Item、错误断点和成功状态；插入或绑定失败整个事务回滚，旧 Job 终态审计保留。迟到旧回调不终结后继，旧 Fence 不能写结果。取消、真实系统停止或 legacy v1 不续接；入口为 [`backend/src/aima_ugc/bootstrap/analysis_high_throughput_planner.py`](../../backend/src/aima_ugc/bootstrap/analysis_high_throughput_planner.py)。

用户取消优先停止等待和后续发送；取消与 Worker/Planner 先锁 Job 再锁 Run，并复核关联 Job 集合，覆盖后继创建竞争。正常 pending 和未投放内容仍计入未完成，不能因程序调度或周期到期标为成功。父 Run 失败是权威终态，各回调/Planner 不能复活；终态统计将未投放和未收尾 pending 投影到 failed，因此该汇总不等于每条都有模型输出错误。已发合法结果提交后仍按真实成功更新。列表通过当前 Planner/Shard 投影 execution_settling，在执行收尾前继续轮询。

历史 `recovery.v1` 保留“五分钟无合法输出停止父 Run、五分钟无 2xx 停止”的冻结语义；无 marker 的历史固定入口继续原行为。新代码不补写旧 Snapshot、不自动恢复旧失败 Item。本次 v2 复用既有恢复字段和索引，没有新增业务 Schema、Migration head 或 upgrade DDL；0077 downgrade guard 覆盖两种恢复版本。回滚前排空未完成的新协议 Run。回归在 [`tests/integration/content/test_analysis_retry_recovery.py`](../../tests/integration/content/test_analysis_retry_recovery.py) 使用专用 PostgreSQL 和本机 HTTP，普通 CI 不调用付费模型。

# 30. Analysis Run 的 selected / query / all 范围

声音广场批量 AI 打标有三个正式范围：

```text
selected
→ 显式 1—1000 个 Content ID

query
→ 当前已应用 ContentFilterSnapshot 命中的全部 Content Current
→ 不受 Cursor 分页、当前已加载条数或列表排序影响
→ 浏览器只提交筛选快照

all
→ 当前 PostgreSQL 中全部 Content Current
→ 与声音广场当前筛选条件无关
→ 不把全量 ID 放进浏览器或 HTTP Payload
```

`AnalysisRunTargetSelection(scope="query")` 必须且只能携带 `filters`；`selected` 必须且只能携带非空 `content_ids`；`all` 禁止携带二者。公开 `query` 直接复用列表、Count 和 query Export 的 `ContentFilterSnapshot` 语义，因此一级/二级标签 legacy compatibility 也沿用同一已应用查询事实，不建立 Analysis 专用筛选器。

Preview 使用同一查询语义返回服务端权威 `target_count`。用户确认 Create 时，服务端在单个 PostgreSQL Statement Snapshot 中重新读取 Query Target，并同时得到数量与由 `content_id + current_version` 构造的双 64-bit 聚合集合指纹；若 Preview 后数量变化则返回 409 `content_analysis_target_changed`，前端自动刷新 Preview，但不会自动提交扩大或缩小后的目标。确认请求成功后，这个集合指纹与原筛选快照一起写入 Run 的内部 `filter_snapshot`；公共 HTTP Contract 不暴露内部指纹字段。

数据库仍只保存 `scope = query | selected`。公开 `all` 用专用内部 marker 与普通 `query` 区分。Planner 对 `query` 与 `all` 都按稳定 Content UUID keyset 分批读取，并在独立短事务追加连续 `analysis_content_run_targets(content_id, content_version)`；全部冻结后才创建 Shard。对新 query Run，Planner 在结束时对已冻结 Target 重新计算同一集合指纹并与 Create 时指纹比较，因此即使总数相同但成员发生替换，也会以 `content_analysis_target_changed` fail closed，绝不在集合不一致时启动 LLM Shard。历史没有内部指纹的 query Run 仍保留旧数量核对路径。

分批冻结因此不需要跨全部批次持有一个长 MVCC 事务；它也不把 Preview 时刻冒充成执行快照。正式定义是：**成功 Create 的确认时 Query Target 集合**。Planner 要么冻结出与该集合相同的 `content_id + current_version` 多重集，要么失败；冻结完成后的后续内容或 Analysis 变化不会改写本 Run。指纹由两组 PostgreSQL `hashtextextended` 聚合值再经 SHA-256 编码形成，属于内部一致性护栏而不是安全签名。无需新增 Schema 或 Migration。
