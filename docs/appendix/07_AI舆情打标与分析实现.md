# 1. AI 为什么不属于 Canonical / Mapper

Canonical 表示外部来源真正观察到的事实，例如：

```text
标题
正文
作者展示信息
发布时间
互动指标
评论
来源
```

AI 的：

```text
相关/无关
发声类型
情感
舆情标签
```

都是**派生分析事实**，不是 Provider 原始事实。

所以链路固定分层：

```text
TikHub / Excel
→ Mapper
→ CanonicalContentV1
→ Content Owner / UnifiedContentRecordV1
→ Analysis
```

禁止：

- TikHub Mapper 直接判断情感；
- Excel Mapper 把源文件旧“情感列”当当前 AI 结果；
- 把 AI 标签塞进 `CanonicalContentV1.observed_fields`；
- 把完整 `UnifiedContentRecordV1` 当成 `contents` 的 JSONB。

正式 PostgreSQL 中：

```text
Content 事实
→ contents / content_versions ...

AI 事实
→ analysis_content_results / label_pairs ...
```

# 3. 当前 V3 一次模型调用做什么

当前一次模型调用为**一条 Content 的完整分析**：

```text
relevance
voice_type
sentiment
labels[]
```

不是四次模型请求，也不是把多条 Content 拼成一个请求。正式高并发与离线高并发都保持：

```text
1 Content = 1 个独立逻辑 LLM Request
```

核心结构：

```json
{
  "relevance": "relevant",
  "voice_type": "真实用户发声",
  "sentiment": "混合",
  "labels": [
    {
      "primary_label": "骑行性能",
      "secondary_label": "舒适性"
    }
  ]
}
```

真正结果还带 Prompt/Taxonomy/Model/Input Hash/时间等可复现身份。

---

# 4. relevant / irrelevant 的结构约束

当前 Contract 和 Validator 都 fail closed。

## relevant

必须：

```text
relevance = relevant
sentiment != null
labels 至少 1 个合法标签对
```

## irrelevant

必须：

```text
relevance = irrelevant
sentiment = null
labels = []
```

Pydantic 与 Raw Response 结构校验分别由 Analysis Contract 和 `RuntimeTaxonomyValidator.validate_response()` 负责。

---

# 5. `voice_type` 与情感/标签共享同一 Scheme Version

`voice_type` 的当前合法机器值不在本文复制。唯一运行事实是 Analysis Run 冻结 Scheme 的机器 Taxonomy `voice_types`；类型定义、主体/表达目的证据、边界、高混淆场景和学习示例与它处于同一 Scheme Version。

真实用户发声唯一业务判断：

```text
voice_type == "真实用户发声"
```

不要增加 `is_real_user_voice` / `is_user_voice` 平行字段。

---

# 6. 模型实际能看到哪些输入

`ContentLabelingModelItem` 当前只发送：

```json
{
  "item_no": 1,
  "title": "...",
  "text": "...",
  "author": {
    "display_name": "...",
    "bio": "...",
    "verification_label": "..."
  }
}
```

模型不会收到 PostgreSQL Content UUID、platform、URL、互动指标、Raw 地址、命中关键词或其他未批准字段。`item_no` 只用于当前单条请求的响应配对，不是业务身份。

---

# 7. Prompt 为什么同时有人类规则和机器 Taxonomy JSON

程序从 Prompt 中定位唯一 Taxonomy JSON 区块并校验 sentiments / voice_types / labels / 唯一性 / 父子关系，再计算 `taxonomy_sha256` 和完整 `prompt_sha256`。

机器 JSON 决定合法闭集，自然语言决定判断标准。二者语义冲突时必须修同一 Scheme，不能长期维护平行事实。

---

# 8. 为什么本文不复制完整 AI Taxonomy

当前 Scheme 的情感、发声类型和标签体系都是业务可变事实。运行时唯一完整分类事实是数据库 active Analysis Scheme Version；Git Prompt 只承担 bootstrap/灾备。

本文解释加载、校验、执行、持久化和修改入口，不复制一份容易漂移的完整标签表。

---

# 9. 模型返回后代码怎样校验

`RuntimeTaxonomyValidator.validate_response()` 会检查 JSON 顶层、items 列表、item_no、顺序/重复/缺失、relevance/voice_type/sentiment、标签父子关系、重复标签对和 relevant/irrelevant 形状。

错误使用稳定 code，例如 `invalid_json / missing_item / unknown_voice_type / invalid_secondary_for_primary`，供 Validation Retry 和审计使用。

# 10. Validation Retry、Transport Retry 与 RPS 为什么必须分开

## 10.1 Validation Retry

```text
HTTP 200
→ 模型返回了文本
→ 但 JSON/标签结构不合法
→ ContentLabelingService 只重新请求当前尚未成功的 Content
```

管理员 Provider 的 `max_retries` 当前表示 Validation Retry 上限。

## 10.2 Transport Retry

```text
429 / 部分 5xx / 连接失败 / 超时
→ RetryingContentLabelingLLM
```

基础 `OpenAICompatibleContentLabelingLLM.complete()` 一次调用最多一次物理 HTTP 发送；Transport Retry 在外层明确重发并记录。

## 10.3 max_rps

如果 Provider 配置 `max_rps`：

```text
RetryingContentLabelingLLM
→ 每次物理 Attempt 调用 RateLimitedContentLabelingLLM
→ 取得 RPS 时隙
→ Base Adapter 发送一次 HTTP
```

因此 Transport Retry 不能绕过限速。这样在高并发 429/5xx 场景下避免 retry storm。

# 11. `ContentLabelingAttempt` 保存什么

每次 Validation Attempt 保存 item、错误、模型/Prompt/Taxonomy、开始/结束时间以及可获得的 token/cost 元数据。

当前正式 `analysis_content_results` 仍**没有** token/cost 列；“运行时能计算 cost”不等于“Analysis Result 表已经持久化 cost”。

# 12. 正式 PostgreSQL Analysis 怎样创建

当前 HTTP：

```text
POST /api/v1/analysis/content-runs/preview
POST /api/v1/analysis/content-runs
```

Preview/Create 共同读取当前默认 LLM Provider 并把安全 Runtime Snapshot 纳入配置身份。对正式数据库 Provider：

```text
shard_size = clamp(max_concurrency × 20, 20, 50_000)
```

例如：

```text
250  并发 → 5,000 Content / Shard
1000 并发 → 20,000 Content / Shard
```

Shard Size **不由管理员配置**。Create 把计算结果冻结到 `analysis_content_runs.shard_size`；之后修改 Provider concurrency 只影响新 Run。

只有数据库 Provider 配置面启用前的 legacy env bootstrap LLM 继续读取旧 `AIMA_ANALYSIS_RUN_SHARD_SIZE`，用于旧部署兼容。

Planner 对 `selected/query` 保留集合式短路径；公开 `all` 按稳定 Content UUID keyset 分批读取并连续追加 `content_id + current_version + target_ordinal`。高吞吐 Planner 用最后 `target_ordinal + 1` 恢复已冻结数量，不在每 1 万条批次后对越来越大的目标表重复 `COUNT(*)`。

`all` 完成后再次核对当前 Content 总数、已冻结 ordinal 和 Preview `expected_target_count`。只有一致才创建首批 Shard；数量变化以 `content_analysis_target_changed` fail closed。

下一批 Shard 由 Run 已知 `shard_count` 与已创建 Request 的连续 `shard_no` 推导，不再通过扫描全部 `analysis_content_run_targets` 计算 `floor(target_ordinal / shard_size)`。

# 14. 正式 Analysis Worker 怎样执行

正式代码：

- [`backend/src/aima_ugc/bootstrap/analysis_concurrent_worker.py`](../../backend/src/aima_ugc/bootstrap/analysis_concurrent_worker.py)
- [`backend/src/aima_ugc/bootstrap/analysis_high_throughput_planner.py`](../../backend/src/aima_ugc/bootstrap/analysis_high_throughput_planner.py)
- [`backend/src/aima_ugc/adapters/persistence/postgres/analysis_batch.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/analysis_batch.py)
- [`backend/src/aima_ugc/adapters/persistence/postgres/analysis_high_throughput.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/analysis_high_throughput.py)

正式 Shard 流程：

```text
读取 Run 冻结 Provider / Scheme / Prompt / Taxonomy
→ 验证配置身份
→ load_pending：一次只取约 2 × max_concurrency 的工作窗口，上限 10,000
→ 检查 cancel
→ 第一条 Canary 单独请求
→ Canary Provider/认证/模型链成功后才放大
→ Shared Bounded Executor
→ 同时最多 max_concurrency 个单 Content 模型请求
→ max_rps 对每个物理 HTTP Attempt 生效
→ Validation Retry / Transport Retry 分层
→ 完成结果在调度线程缓冲
→ 约 200 条结果形成一个短 PostgreSQL 事务
→ Heartbeat / Cancel
→ 下一工作窗口
```

LLM worker thread **不创建 PostgreSQL Session，也不持有数据库事务**。因此：

```text
1000 LLM in-flight
≠ 1000 PostgreSQL connections
```

批量短事务一次完成：

```text
1 次 Job Fence 校验
1 次 Request/Job 归属校验
1 次 Current Version 批量查询
多行 Result INSERT ... ON CONFLICT ... RETURNING
批量 Label Pair INSERT
executemany 更新 succeeded / failed / stale Request Item
```

幂等冲突时不会盲目覆盖已有 Result，而是批量读取既有业务值和标签并 fail closed 比较。

单条并发 Transport 错误在 Canary 之后只终结对应 Content；不把一个 5,000/20,000 条的大 Shard 整体重新调用模型。Job Retry 保留给 Canary/配置/基础设施等 Job 级失败。

为什么仍验证 `JobExecutionFence`：旧 Worker Lease 失效后不能继续把结果提交为当前合法事实。为什么还验证 Content Version/配置身份：执行期间 Content 或运行身份变化时不能把错误版本结果写成成功。

# 15. 什么叫 `stale`

Analysis 绑定 `content_id + content_version`。如果模型调用完成后 Current Version 已变化，批量 Repository 会把对应 Request Item 标记 `stale`，不会把旧版本结果当 current。

声音广场继续区分 `completed / stale / pending`。

---

# 16. Analysis Run 怎样定义“当前有效结果”

Current Analysis 先匹配 Content Version，再按 `analysis_content_runs.sequence_no DESC` 选择最新成功用户意图。较早 Run 即使更晚完成，也不能覆盖更晚创建的 Run；最新 Run 失败/取消时旧成功结果继续作为 Current。

Provider concurrency、RPS 或 Scheme 的后续修改不会静默改写旧 Run，因为 Run 保存自己的冻结身份和 Runtime Snapshot。

---

# 17. irrelevant 在正式查询里怎样处理

正式 PostgreSQL 中 irrelevant 不物理删除 Content：

```text
Content Raw/Current/History 保留
→ Analysis 原始结果标记 irrelevant
→ 默认业务列表/查询型目标/导出排除
→ 用户可显式筛出并人工复核
```

人工复核仍通过追加账本改变业务有效相关性，不修改原始 AI Result。

---

# 18. 离线打标为什么可以物理移出最终 JSONL

离线 JSONL 是派生产物，不是正式 PostgreSQL Content 事实库。离线 irrelevant 可以从最终业务 JSONL rewrite 中移出，同时 checkpoint 保留恢复/审计事实；这与正式数据库保留 Content 的策略不冲突。

# 19. 离线高并发实现

公共入口：

- [`backend/src/aima_ugc/modules/analysis/offline_concurrent_labeling.py`](../../backend/src/aima_ugc/modules/analysis/offline_concurrent_labeling.py)
- [`backend/src/aima_ugc/modules/analysis/concurrent_labeling.py`](../../backend/src/aima_ugc/modules/analysis/concurrent_labeling.py)

DeepSeek 人工入口当前仍可配置：

```python
DEFAULT_OFFLINE_LLM_CONCURRENCY = 250
```

它是离线入口默认值，不是正式 Provider 的全局并发常量。

流程：

```text
完整 preflight

→ 共用 bounded executor
→ 最多 max_concurrency in-flight
→ 成功 checkpoint / attempts / failed
→ 全部结束后按原顺序 rewrite
```

正式 PostgreSQL 和离线 JSONL 现在共用同一个调度算法；差异只在输入和结果持久化方式。

# 20. 为什么一条内容一个模型请求

正式与离线均保持：

```text
任何情况下，一次逻辑 ContentLabeling 调用只包含一条 Content
```

原因：失败/Retry/费用/恢复粒度明确，一个坏 Content 不拖整个批次。高吞吐来自**并发多个单条请求**，而不是把几十条内容合成一个模型请求。

`ContentLabelingService` 仍保留 Sequence 能力用于通用 Service/历史兼容，但高吞吐执行器明确按单 Content 调用。

---

# 21. 离线 Checkpoint 怎样保证恢复

`checkpoints.jsonl` 是离线恢复事实源；`attempts.jsonl` 与 `failed.jsonl` 是调用/失败审计。恢复身份继续包含稳定 Content 身份、input hash、Prompt/Taxonomy/Model，命中后不重新付费调用。

---

# 22. 离线 preflight 为什么放在付费调用前

完整扫描并验证输入、稳定身份和 checkpoint 后才执行 Canary/并发请求；输入后段格式坏时不会先把前面大量数据付费发送出去。

# 27. 调试大批量数据

离线先看 summary 的 `rows_* / peak_in_flight / llm_attempts / HTTP requests / transport_retries / token/cost`。

正式 PostgreSQL 大 Run 重点看：

```text
Run target_count / shard_count / shard_size
Provider max_concurrency / max_rps
Planner frozen ordinal
活动 Shard 数
单 Shard succeeded / failed / stale
LLM request audit
DB batch flush
```

4000 万目标下，正式 Planner 不再每 1 万条累计 `COUNT(*)`，也不在每次补 Shard 时扫描全部 Run Target。已成功 Shard 的 Run 统计优先读取持久 Job Result 计数，只对仍活动/异常的少量 Shard 扫描 Request Item。

并发参数仍不是越大越快。真实吞吐近似受：

```text
min(
  Provider/模型服务容量,
  max_concurrency / 平均模型延迟,
  max_rps,
  网络吞吐,
  本地 CPU/内存,
  PostgreSQL 批量写吞吐
)
```

限制。某个服务器能否稳定跑满 1000 必须在该部署环境压测，不能从 CI Runner 推断。

# 30. Analysis Run 的 selected / all 范围

声音广场批量 AI 打标有两个正式范围：

```text
selected
→ 显式 1—1000 个 Content ID

all
→ 当前 PostgreSQL 中全部 Content Current
→ 与声音广场当前筛选条件无关
→ 不把全量 ID 放进浏览器或 HTTP Payload
```

`AnalysisRunTargetSelection(scope="all")` 禁止提交 `content_ids`。Preview 直接统计 PostgreSQL `contents` 的全部 Current 行，因此不会继承声音广场默认隐藏 irrelevant 的展示规则；Create 只建立 Run Header 与 `analysis.content-run-plan.v1` Planner Job。

Planner 对 `all` 按稳定 Content UUID keyset 分批读取并在独立短事务追加连续冻结目标；全部冻结、再次核对当前总数与 Preview 数量后，才按 Run 已冻结的自动 `shard_size` 和 `analysis_run_max_in_flight_jobs` 创建 Shard。禁止通过前端分页收集全部 ID，也禁止创建一个承载全部目标的超大 Job Payload。

分批冻结降低单事务规模，但在没有新增数据库快照边界字段的前提下，不宣称跨全部批次拥有单一 MVCC 时点；并发新增/修改仍由最终数量校验与每条冻结的 `current_version` 共同形成当前 fail-closed 边界。
