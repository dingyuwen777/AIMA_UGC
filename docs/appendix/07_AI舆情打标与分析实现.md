# 1. AI 为什么不属于 Canonical / Mapper

Canonical 表示外部来源真正观察到的事实，例如：

```text
标题
正文
作者展示信息
发布时间
互动指标
评论
来源
```

AI 的：

```text
相关/无关
发声类型
情感
舆情标签
```

都是**派生分析事实**，不是 Provider 原始事实。

所以链路固定分层：

```text
TikHub / Excel
→ Mapper
→ CanonicalContentV1
→ Content Owner / UnifiedContentRecordV1
→ Analysis
```

禁止：

- TikHub Mapper 直接判断情感；
- Excel Mapper 把源文件旧“情感列”当当前 AI 结果；
- 把 AI 标签塞进 `CanonicalContentV1.observed_fields`；
- 把完整 `UnifiedContentRecordV1` 当成 `contents` 的 JSONB。

正式 PostgreSQL 中：

```text
Content 事实
→ contents / content_versions ...

AI 事实
→ analysis_content_results / label_pairs ...
```

# 4. relevant / irrelevant 的结构约束

当前 Contract 和 Validator 都 fail closed。

## relevant

必须：

```text
relevance = relevant
sentiment != null
labels 至少 1 个合法标签对
```

## irrelevant

必须：

```text
relevance = irrelevant
sentiment = null
labels = []
```

不允许：

```text

+ 为了满足标签格式强行给“品牌评价”
```

```text

```

模型 Raw Response 的更严格批次结构校验：

```text
modules/analysis/content_labeling.py
→ RuntimeTaxonomyValidator.validate_response()
```

# 5. 当前 `voice_type` 只有这 7 类

机器值：

```text
user_voice
creator_marketing
brand_official
dealer_promotion
media_information
other_organization
unknown
```

精确业务判断规则看当前 Prompt。

最重要的业务边界：

```text
真实用户发声
= voice_type == user_voice
```

当前系统不再维护：

```text
is_real_user_voice
is_user_voice
```

之类平行布尔事实。

为什么：如果同时保存：

```text

is_user_voice = true
```

两个字段迟早冲突。

所以所有 API/Excel/前端/查询要判断“真实用户发声”，都应该从同一个 `voice_type` 推导。

# 6. 模型实际能看到哪些输入

`ContentLabelingModelItem` 当前只发送：

```json
{
  "item_no": 1,
  "title": "...",
  "text": "...",
  "author": {
    "display_name": "...",
    "bio": "...",
    "verification_label": "..."
  }
}
```

代码：

```text
modules/analysis/content_labeling.py
→ ContentLabelingModelItem.model_payload()
```

模型**不会收到**：

- PostgreSQL Content UUID；
- platform；
- Provider；
- URL；
- 点赞/评论数；
- 粉丝数；
- Raw 地址；
- 命中关键词；
- 源 Excel 情感；
- 其他未声明字段。

这样做的好处：

- 降低不必要的 token；
- 防止模型被无关元数据带偏；
- Prompt 规则和输入字段可以明确审计；
- 输入 Hash 更稳定。

`item_no` 只用于当前请求响应配对，不是业务身份。

如果两者语义冲突，必须修 Prompt；不能长期让“机器合法值”和“文字判断标准”各讲一套。

# 9. 模型返回后代码怎样校验

`RuntimeTaxonomyValidator.validate_response()` 不只验证“是不是 JSON”。

它会检查：

```text
顶层只能有 items
items 必须是 list
每个 item 必须有整数 item_no
不能返回未知 item_no
不能重复 item_no
返回顺序要匹配输入顺序
不能缺项
relevance / voice_type 结构合法
sentiment 属于当前 Taxonomy
primary_label 属于当前 Taxonomy
secondary_label 属于对应 primary
标签对不能重复
relevant/irrelevant 形状一致
```

结构性错误有稳定 error code，例如：

```text
invalid_json
invalid_response_structure
invalid_item_structure
invalid_item_no
unexpected_item_no
item_order_mismatch
missing_item
duplicate_item
relevant_missing_sentiment
relevant_missing_labels
irrelevant_has_sentiment
irrelevant_has_labels
unknown_sentiment
unknown_primary_label
invalid_secondary_for_primary
duplicate_label_pair
```

这些错误用于 Validation Retry 和审计，不是直接把模型原始异常字符串塞进业务结果。

# 10. Validation Retry 和 Transport Retry 为什么必须分开

这是当前 AI 实现最容易被改坏的地方。

## 10.1 Validation Retry

场景：

```text
HTTP 200
→ 模型确实返回文本
→ 但 JSON/标签结构不合法
```

由：

```text
ContentLabelingService.label_contents()
```

控制。

当前行为：

```text
第一次请求一批 items
→ 合法 item 立即锁定为成功
→ 只把仍不合法的 item 放进下一次 Validation Retry
```

不会因为一个 item 错误把同批已经合法的 item 重新请求一次。

下一次请求还会带：

```text
previous_validation_error_codes
```

帮助 Adapter/Prompt 层解释这是一次结构修复请求。

## 10.2 Transport Retry

场景：

```text
429
5xx
连接失败
超时
```

属于网络/Provider 调用层。

Adapter：

```text
adapters/llm/openai_compatible.py
```

Retry wrapper：

```text
adapters/llm/retrying.py
```

基础 `complete()` 的语义是一调用对应一次 HTTP 发送；如果需要 Transport Retry，由明确 wrapper/策略重新调用并记录。

不要在基础 Adapter 里用 `while True` 偷偷多发请求，否则：

- HTTP 请求数不可审计；
- 成本统计失真；
- Validation Retry 与网络 Retry 混在一起；
- 故障排查无法知道模型到底被调用多少次。

# 15. 什么叫 `stale`

Analysis 是针对：

```text
content_id + content_version
```

的。

如果请求冻结 V3，但 Worker 执行时发现业务事实已经无法按请求约束继续处理，Request Item 可以进入 `stale`。

声音广场当前也区分：

```text
completed
stale
pending
```

读取实现：

```text
adapters/persistence/postgres/content_queries.py
```

其中：

```text
当前 Content Version 有匹配当前 Analysis Identity 的结果
→ completed

当前版本没有匹配结果，但该 Content 历史有 Analysis
→ stale

从未有 Analysis
→ pending
```

这避免把旧版本/旧 Prompt 的结果伪装成当前分析。

# 17. irrelevant 在正式查询里怎样处理

当前 `PostgresContentQueryRepository` 默认：

```text
filters.relevance is None
→ 排除当前 Analysis 明确 relevance = irrelevant
→ 没有当前 Analysis 的 Content 仍允许显示
```

显式：

```text
relevance=irrelevant
```

可以查询无关内容用于审计。

单条：

```text
GET /api/v1/contents/{content_id}
```

也使用审计友好读取，不因为 irrelevant 就把真实业务记录物理删掉。

因此正式数据库语义是：

```text
Content Raw/Current/History 保留
→ Analysis 原始结果标记 irrelevant
→ 默认业务列表/查询型目标/导出排除
→ 用户可在声音广场显式筛出待复核 irrelevant
→ 人工把当前版本纳入 relevant 后进入默认业务集合
```

不是：

```text
DELETE FROM contents
```

人工复核不会修改 `analysis_content_results.relevance`。它向 `analysis_content_relevance_reviews(content_id, content_version, review_no, analysis_result_id, decision, request_id, reviewed_at)` 追加事件；`decision` 只允许 `relevant / irrelevant / inherit_ai`。最新 `relevant/irrelevant` 分别把当前版本人工纳入/排除业务相关集合，`inherit_ai` 撤销覆盖并回到当前 AI 基线；相反人工覆盖必须先撤销。重复提交当前已生效状态幂等，批量请求全量校验后同事务提交。查询层统一计算业务有效相关性，Content API 同时保留 `analysis.relevance` AI 原判并返回派生 `effective_relevance / relevance_source`，所以 Prompt/Model 变化导致 AI `stale` 时，已有人工覆盖仍能显示和撤销。Content 产生新版本后，旧人工事件继续留作历史审计，不自动影响新版本。

# 18. 离线打标为什么可以物理移出最终 JSONL

离线 `imports_test` 是文件处理链，最终业务 JSONL 只是本次离线派生产物。

当前 `offline_labeling.py` 在 Analysis 完成后：

```text
relevant
→ 把 Analysis 写回 UnifiedContentRecordV1

irrelevant
→ 从最终 source JSONL rewrite 结果中移除
```

同时保留最小 checkpoint 以便恢复/费用幂等。

这和正式 PostgreSQL“保留 Content、默认查询排除”并不冲突，因为两者的数据保留职责不同。

# 19. 离线高并发实现

入口：

```text
modules/analysis/offline_labeling.py
```

当前默认：

```python
DEFAULT_OFFLINE_LLM_CONCURRENCY = 250
```

但不是一上来就瞬间放大 250 个真实请求。

完整流程：

```text
1. 完整 preflight 输入 JSONL
2. 检查每行 Contract
3. 检查 stable identity 是否重复
4. 加载可恢复 checkpoint
5. 找到 pending
6. 先发送 1 条 canary
7. canary 成功后启动 bounded ThreadPoolExecutor
8. 最多 max_concurrency in-flight
9. 每条成功先写 checkpoint
10. attempts / failed 写审计
11. 全部结束后按原顺序重写源 JSONL
12. irrelevant 从最终业务 JSONL 删除
```

### 为什么先 Canary

如果：

- API Key 错；
- Base URL 错；
- 账户余额不足；
- 模型名错误；
- Provider 整体不可用；

直接并发 250 会把同一个配置错误放大成大量失败请求。

所以当前先用第一条 pending 做真实链验证。

# 20. 离线为什么一条内容一个模型请求

`label_unified_content_jsonl()` 当前说明：

```text
任何情况下每次模型请求都只有一条内容
```

旧 `batch_size` 参数只作为兼容别名解释成并发上限，不再表示“把几十条内容塞一个 LLM 请求”。

优点：

- 单条失败容易重试；
- checkpoint 粒度清楚；
- 一个坏 item 不拖整批；
- 请求/费用统计更准确；
- 恢复时只补缺失内容。

`ContentLabelingService` 本身仍支持 Sequence，因此正式数据库 Worker 可以按 `analysis_batch_size` 加载工作集合，但 Adapter/运行方式可以决定请求粒度。

# 21. 离线 Checkpoint 怎样保证恢复

目录：

```text

├─ checkpoints.jsonl
├─ attempts.jsonl
└─ failed.jsonl
```

## `checkpoints.jsonl`

恢复事实源。

一条内容成功后，先把可恢复 Analysis 决策写进去并 durable flush，然后才继续。

下次运行：

```text
同 stable content identity
+ 同 input_hash
+ 同 Prompt/Taxonomy/Model identity
```

命中时可以恢复，不重新付费调用。

## `attempts.jsonl`

调用/Validation Attempt 审计。

不是业务下游事实源。

## `failed.jsonl`

本次失败条目和 error codes。

也不是 Excel/Report 的数据源。

# 22. 离线 preflight 为什么放在付费调用前

`_preflight_source()` 会完整扫描输入，至少检查：

- 每行是合法 `UnifiedContentRecordV1`；
- stable identity 不重复；
- 已有 Analysis / 可恢复 Checkpoint / Pending 数量。

如果第 90000 行格式坏了：

```text
先失败
→ 不先把前 89999 行拿去付费打模型
```

这比边读边请求更适合大批量付费处理。

# 25. 修改 AI 业务规则应该改哪里

## 25.1 增删/改标签，调整标签判断规则

主要改：

```text
prompts/content_labeling_v3.md
```

如果只是 Taxonomy 内容变化：

- 不在 Python 复制一份 Enum；
- `PromptTaxonomyLoader` 自动解析新 Taxonomy；
- hash 会变化，旧 Analysis Identity 自动不再作为当前结果。

必须跑：

- Prompt parser/taxonomy tests；
- Validator tests；
- 代表性分类 fixture/fake tests；
- 正式/离线链相关回归。

## 25.2 改 `voice_type` 机器枚举

这不是只改 Prompt。

至少影响：

```text
contracts/analysis/content_label.py
Prompt
content_labeling.py Validator
modules/analysis/tables.py Check Constraint
新 Migration
Excel 中文映射
HTTP/OpenAPI/Generated Client（如果公开类型受影响）
前端筛选
Analysis tests
```

这是跨 Contract/Schema 的高风险修改。

## 25.3 改相关性删除/保留语义

要先区分：

```text
离线 JSONL
vs
正式 PostgreSQL
```

当前：

```text
离线 irrelevant
→ 最终业务 JSONL 删除

正式 DB irrelevant
→ Content 保留
→ Analysis 标记
→ 默认业务查询排除
```

修改任一侧都要同步对应测试/文档，不能把两种保留策略混成一句“无关就删除”。

## 25.4 改模型输入字段

代码：

```text
ContentLabelingModelItem
_to_model_item()
Prompt 输入字段说明
_input_hash()
```

增加平台/指标等输入会改变判断语义和 input_hash，需要明确业务理由。

## 25.5 换 LLM Provider / Model

通常先改配置和 Adapter：

```text
adapters/llm/
PlatformSettings
Secret
Pricing
```

Analysis Domain 不应该为某个 Provider 重写一套 Service。

# 26. 调试一条正式 Analysis

顺序查：

```text

2. analysis_content_request_items

4. 当前 Content Version

```

### 页面提示“当前环境尚未配置可用的 LLM Runtime”

声音广场只读取：

```text
GET /api/v1/content-analysis-capabilities
→ configured
```

源码开发 launcher 会把 `env.local` 中的 LLM Key 写到 `.runtime/secrets/llm_api_key`，并让 API/Worker 通过 `AIMA_EXTERNAL_SECRET_DIR` 读取。`.runtime/internal-secrets/` 只保存 PostgreSQL/Cursor 内部 Secret。排障时依次确认 Base URL、Model、外部 Secret 文件和 Backend 重启；不要让前端直接读 `env.local`，也不要把 Secret 原值加入能力响应或日志。

### Job succeeded，但声音广场显示 stale

检查：

```text
result.content_version
vs
contents.current_version
```

以及：

```text
prompt_version
prompt_sha256
taxonomy_sha256
model_provider
model
```

是否仍匹配当前 Analysis Identity。

### LLM 返回 200，但 item failed

看：

```text
validation_error_codes
```

重点区分：

```text
Transport 成功
≠ Analysis 结构合法
```

### 一直 retry

先看错误是：

```text
OpenAICompatibleLLMError.retryable
```

还是 Validation Retry。

不要把 Validation 错误当网络重试无限发送。

[`01_PostgreSQL查询与调试实战.md`](01_PostgreSQL查询与调试实战.md)

- 离线 preflight/canary/concurrency/checkpoint/recovery；
- irrelevant 离线 rewrite；
- 正式 Request 冻结 Content Version；
- Fencing 拒绝旧 Worker；
- stale/current Analysis Identity；
- 默认 Content Query 排除 current irrelevant；
- Excel `voice_type` 投影；
