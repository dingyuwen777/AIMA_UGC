# 数据入口与统一入库

这篇文档回答一个容易混淆的问题：**Excel 手工导入、TikHub 定时采集、TikHub 调试脚本看起来入口完全不同，为什么最后可以进入同一套内容数据库，而且不会各写一套去重逻辑？**

## 1. 先看结论

不同入口负责“怎么拿到数据”，统一入库负责“拿到业务数据以后怎么保存”。

```text
Excel 文件 ───────────────┐
TikHub 正式采集 ──────────┤
TikHub 手工调试写库 ───────┤
未来其他 Provider / 历史导入 ─┘
            ↓
各自 Raw / Reader / Mapper
            ↓
Canonical
            ↓
规则 Relevance
            ↓
Content Ingestion / Owner Repository
            ↓
PostgreSQL
```

所以最终内容身份、版本、指标历史和去重规则只维护一套。

AI Semantic Relevance 是 Content 进入 Analysis 之后的另一层派生判断，不属于“是否把这个 Candidate 正式写成 Content”的同一字段。

## 2. Canonical 是“统一入库”的分界线

Canonical 可以理解成：**系统内部约定好的平台无关内容格式。**

第三方字段变化发生在 Canonical 之前：

```text
TikHub 小红书 JSON
TikHub 抖音 JSON
Excel 一行数据
        ↓ 各自 Mapper
CanonicalContentV1 / CanonicalCommentV1
```

进入 Canonical 之后，Ingestion 不应该再判断“这个字段是 TikHub 的 note_id 还是 Excel 的某一列”。

这也是为什么：

- Provider 不能直接写 `contents`；
- Excel Reader 不能自己实现一套 `INSERT contents`；
- Mapper 不查数据库、不发 HTTP；
- 去重和版本逻辑不能散落在每个平台脚本里。

## 3. TikHub 正式采集的来源链

正式 Collection 使用：

```text
Plan（可选长期计划）
→ Occurrence（定时触发时）
→ Run
→ Scope
→ Provider Request
→ Provider Request Attempt
→ Raw Artifact
→ Candidate
→ Mapper
→ Canonical
→ 规则 Relevance
→ Ingestion
→ Content Owner
```

这里每层都有明确作用：

- Run：一次完整采集；
- Scope：某个平台/关键词等最小可恢复单元；
- Request：一个逻辑 Provider 请求；
- Attempt：一次真实发送；
- Raw：当时实际返回；
- Candidate：Raw 中某个来源项被发现的账本。

这条链的价值是以后能回答：

> 数据库里的这条帖子，到底来自哪次采集、哪次请求、哪个 Raw？

## 4. Excel 为什么不伪造 Run/Scope/Candidate

Excel 是一个已经存在的输入文件，它没有真实的“平台搜索 Run/Scope”。如果为了表结构统一硬造一套虚假的 Run，会让来源审计反而失真。

所以当前 File Import 使用：

```text
Input Artifact
→ Processing Import Batch
→ import-parent Provider Request
→ not_billable Attempt
→ Excel Reader / Mapper
→ Canonical
→ 规则 Relevance
→ Ingestion
→ Content Owner
```

`processing_import_batches` 是一次文件处理的父事实。

当前 `provider_requests` 在 Migration 后要求来源父级**恰好一个**：

```text
Collection 请求：scope_id 有值，import_batch_id 为空
File Import：   scope_id 为空，import_batch_id 有值
```

这样既复用了 Request/Attempt/Artifact 来源链，又没有伪造 Collection 事实。

## 5. TikHub 调试入口为什么可以选择写数据库

`tikhub_test` 首先是调试工具，所以默认行为仍应该允许：

```text
真实请求
→ 保存本地 Raw / JSONL / Excel
→ 不写业务数据库
```

显式打开数据库模式后，它复用正式 Collection/Provider/Ingestion 组件：

```text
run_xxx(..., write_to_database=True)
→ manual Collection Run / Scope
→ 正式 Provider Dispatch / Raw
→ Candidate-before-Mapper
→ Canonical
→ 规则 Relevance
→ Ingestion
```

关键点：**不能为了写数据库再发送第二次 TikHub 请求。**

同一个真实响应可以同时留下本地调试产物和正式 Raw Artifact，但数据来源仍是同一次外部请求。

## 6. imports_test 为什么也默认不写库

`imports_test` 是独立验证/离线处理入口。默认关闭数据库写入有两个好处：

- 可以在没有 PostgreSQL 的机器上测试 Excel 清洗、去重、打标、报告；
- 不会因为开发者只是想看结果文件就意外污染业务数据库。

只有显式数据库阶段才装配 PostgreSQL Runtime。

调试入口的原则始终是：

> **复用生产实现，但不要默认产生生产副作用。**

## 7. 去重发生在哪里

不同层的“重复”不是一回事。

### 7.1 同一外部内容是不是同一条业务数据

Content Owner 使用稳定业务身份收敛，例如内容按：

```text
(platform, external_content_id)
```

所以同一小红书帖子今天从 TikHub 来、明天又从 Excel 导入，不会因此生成两条 Current。

### 7.2 同一逻辑 Provider 请求是否重复

Provider Request 使用父级 + `request_fingerprint` 做幂等。

### 7.3 同一文件处理是否重复

Import Batch、Artifact、Job 和正式导入流程负责文件级执行事实，不能靠“Excel 文件名一样”猜测是否是同一数据。

### 7.4 内容没变但指标变了怎么办

当前内容使用：

```text
Current
+ Version
+ Metric Observation
```

正文业务字段变化才增加 Version；点赞/评论等指标变化写 Metric Observation，不需要复制整条内容。

## 8. 两层 Relevance 分别放在哪里

### 8.1 规则 Relevance：决定 Candidate 是否进入 Content Ingestion

相关性不能只在 Excel 清洗脚本里做，否则 TikHub 和 Excel 会得到不同业务口径。

当前统一位置：

```text
Mapper
→ Canonical
→ Global Relevance Service
→ relevant：Content Ingestion
→ filtered：记录来源过滤结果，不写成 Content
```

全局配置保存在 PostgreSQL。正式 Collection/Import 会冻结对应配置快照，避免任务运行一半配置变化导致前后口径不同。

这层的 `filtered` 是来源/Ingestion 账本事实。

### 8.2 AI Semantic Relevance：Analysis 对已经进入分析的 Content 做语义判断

Content Labeling V3 还会返回：

```text
relevance = relevant | irrelevant
```

数据库事实保存于：

```text
analysis_content_results.relevance
```

它不是 `contents.is_relevant`；当前 `contents` 没有这样的 AI 投影列。

HTTP 查询 Contract 支持显式 `relevance` 筛选，但默认是否带某个筛选条件要以具体 Query Service/调用方为准。

## 9. 一条 Excel 数据最终怎么进数据库：最小例子

假设 Excel 有一行：

```text
平台：小红书
帖子ID：abc123
正文：爱玛这款车骑起来……
点赞：120
```

简化流程：

```text
1. 上传 Excel → 保存 Input Artifact
2. 创建 Processing Import Batch + ingestion.import-excel.v1 Job
3. Worker 读取 Excel
4. Reader/Mapper 产出 Canonical(platform=xhs, external_content_id=abc123, ...)
5. 规则 Relevance 判断该 Candidate 是否继续入库
6. relevant → Ingestion 查 (xhs, abc123)
7. 不存在 → 新建 Current + Version + Metric Observation
   已存在 → 根据字段 freshness / business hash / 指标变化更新历史
8. filtered → 记录过滤结果，不写成 Content
9. 来源 Attempt/Artifact 继续保留
```

不会直接把 Excel 一整行 JSON 塞进 `contents`。

## 10. 一条 TikHub 数据最终怎么进数据库：最小例子

```text
1. Run 创建 xhs + keyword=爱玛 的 Scope
2. Provider Request/Attempt 发真实 TikHub 请求
3. Raw 先落 Artifact
4. 从 Raw item 建 Candidate
5. Mapper 产出 Canonical
6. 规则 Relevance
7. relevant → 同一个 Ingestion / Content Owner
8. PostgreSQL 按 (platform, external_content_id) 收敛
```

Excel 和 TikHub 真正共享的是 Canonical 后的规则 Relevance、Ingestion 和 Content Owner，不是强行共享前面的来源父级。

## 11. 当前正式 HTTP 能力

当前系统已经不是“只有 health smoke”。Stage 8 已实现业务 API/页面，包括：

- Import Batch 创建、列表、摘要、详情；
- Job 查询；
- Collection Capability / Run / Runtime 查询；
- Keyword Pack / Relevance Config / Collection Plan；
- 声音广场内容查询；
- Analysis 创建/查询；
- Excel Export 创建/查询。

精确 URL 和字段不要在这里复制第二套，见 [`../API接口说明.md`](../API接口说明.md) 和 `contracts/openapi/openapi.json`。

## 13. 不要做的事

- 为 Excel 再写一套 Content SQL；
- 为每个平台各维护一份去重实现；
- 从 JSONL/Excel 二次回灌来模拟正式 TikHub 来源；
- 调试脚本默认写生产库；
- Provider 直接写业务表；
- Mapper 里查询 PostgreSQL 判断“是否重复”；
- 把规则 `filtered` 和 AI `irrelevant` 混成一个数据库列；
- 假设不存在的 `contents.is_relevant`；
- 为了表结构看起来统一，伪造不存在的 Run/Scope/Candidate；
- 修改历史 Migration 去“整理”当前设计。
