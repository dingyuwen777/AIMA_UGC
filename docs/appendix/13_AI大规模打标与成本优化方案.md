> 当 AIMA_UGC 需要对数千万级历史帖子持续执行 `relevance / voice_type / sentiment / labels` 打标时，怎样在不破坏当前 Analysis 领域边界和标签语义的前提下，把成本、吞吐和质量控制到可长期运行的水平？

5. 训练、评估、灰度、回滚和验收方法；
6. 哪些内容只是建议，尚未成为当前代码事实。

# 2. 当前打标任务到底复杂到什么程度

当前一条帖子一次 Analysis 需要输出：

```text
relevance
voice_type
sentiment
labels[]
```

其中：

```text
relevance
→ relevant / irrelevant

voice_type
→ 7 类闭集

sentiment
→ 4 类闭集

labels
→ 9 个一级标签 / 39 个二级标签的层级多标签分类
```

模型输入只有：

```text
title
text
author.display_name
author.bio
author.verification_label
```

当前任务不要求模型：

- 自由生成长文；
- 使用工具；
- 联网搜索；
- 多轮 Agent 推理；
- 复杂数学推理；
- 从 Raw Provider JSON 自行发现字段；
- 创建新标签。

因此从机器学习问题类型看，它本质上属于：

> **有限输入、闭集输出、层级多标签、带少量语义边界判断的文本分类任务。**

这也是为什么在数千万条规模下，不应该默认让高成本生成式大模型永久承担 100% 推理流量。

# 4. 当前正式与离线批处理并不相同

## 4.1 正式 PostgreSQL Analysis

当前：

```text
analysis_batch_size 默认 = 20
允许范围 = 1..100
```

正式 Worker 每次：

```text
load_pending(limit=analysis_batch_size)
→ 一次 ContentLabelingService.label_contents(work)
→ 一个 LLM 请求可以包含这一批多个 item
```

因此，在**不考虑 Validation Retry、Transport Retry、重复结果复用和失败**时：

```text
4000 万条 / 每批 20 条
≈ 200 万个首轮 LLM 批次请求
```

这只是请求数量级，不代表实际费用；真实费用必须使用实际 token usage 计算。

## 4.2 离线 `imports_test` / JSONL

当前 [`offline_labeling.py`](../../backend/src/aima_ugc/modules/analysis/offline_labeling.py) 明确采用：

```text
一条内容
→ 一个 LLM 请求
```

默认最多 250 个并发请求在途。

因此如果直接把 4000 万条全部走现有离线模式，理论首轮请求数量约为：

```text
4000 万次
```

提高并发只能缩短墙钟时间，不能从根本上降低 token 成本。

# 5. 当前 DeepSeek 配置与价格

当前 AIMA 机器价格事实：

- [`backend/src/aima_ugc/adapters/llm/pricing.toml`](../../backend/src/aima_ugc/adapters/llm/pricing.toml)

当前正式配置模型：

```text
provider = api.deepseek.com
model = deepseek-v4-pro
currency = CNY
```

截至 `2026-08-24`，DeepSeek 中文官方价格页显示：

| 模型 | 输入缓存命中 / 百万 tokens | 输入缓存未命中 / 百万 tokens | 输出 / 百万 tokens | 官方并发限制 |
| --- | ---: | ---: | ---: | ---: |
| `deepseek-v4-flash` | 0.02 元 | 1 元 | 2 元 | 2500 |
| `deepseek-v4-pro` | 0.025 元 | 3 元 | 6 元 | 500 |

官方来源：

```text
https://api-docs.deepseek.com/zh-cn/quick_start/pricing/
https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit/
```

AIMA 当前 `pricing.toml` 只配置生产正在使用的 `deepseek-v4-pro`，没有因为本文推荐 Flash 就提前把生产模型切换掉。

当前 V4-Pro 一次物理请求的理论费用公式是：

```text
cost_CNY = (
    cache_hit_tokens * 0.025
    + cache_miss_tokens * 3
    + output_tokens * 6
) / 1_000_000
```

未来如果实际使用 V4-Flash，对应官方当前价格公式是：

```text
cost_CNY = (
    cache_hit_tokens * 0.02
    + cache_miss_tokens * 1
    + output_tokens * 2
) / 1_000_000
```

不要用“每条帖子固定多少钱”估算 4000 万条；应先从真实 `llm_requests` / Worker 审计中统计 token 分布，再按请求类型模拟。

# 6. 当前最值得先修的成本问题：思考模式

当前 [`openai_compatible.py`](../../backend/src/aima_ugc/adapters/llm/openai_compatible.py) 构造的请求体主要包含：

```text
model
messages
response_format=json_object
```

当前代码**没有显式发送**：

```json
{"thinking":{"type":"disabled"}}
```

而 DeepSeek V4 官方文档截至 `2026-08-24` 明确说明：

```text
thinking 默认 = enabled
```

官方来源：

```text
https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/
https://api-docs.deepseek.com/guides/thinking_mode
```

因此当前使用官方 `api.deepseek.com` + V4-Pro 时，除非 Provider 侧存在未记录的特殊配置，AIMA 请求会落入 V4 默认思考模式。

DeepSeek `usage.completion_tokens_details.reasoning_tokens` 还会单独暴露 reasoning token；总 `completion_tokens` 是当前费用审计使用的输出 token 口径。

对 AIMA 当前这类闭集分类任务，默认启用高成本思考并不是一个可以直接接受的长期假设。

## P0 推荐

先做真实 A/B：

```text
A: V4-Pro + thinking=enabled（当前基线）
B: V4-Pro + thinking=disabled
C: V4-Flash + thinking=disabled
```

在同一冻结测试集上比较：

```text
标签质量
Validation Retry
平均输入 token
平均输出 token
reasoning token
P50/P95 延迟
吞吐
每千条 / 每百万条成本
```

在没有 A/B 证据前，不直接把生产正式模型从 Pro 切到 Flash；但也不能继续默认“Pro + thinking”一定是最优分类器。

# 7. 为什么只优化 Prompt 和并发还不够

4000 万条规模下，以下优化都有价值，但只是第一层：

```text
关闭 thinking
Pro → Flash
减少输出 token
提高 Batch
使用 Context Cache
提高并发
```

它们仍然保留一个根本结构：

```text
每一条历史内容
→ 最终都要进入生成式 LLM
```

只要这一点不变，整体费用仍然近似随数据量线性增长。

所以长期优化目标不是单纯：

> “让同一个 LLM 请求再便宜 20%。”

而是：

> **让绝大多数简单样本根本不需要外部生成式 LLM，只把难样本交给 LLM。**

# 8. 推荐的最终架构：分层分析漏斗

推荐目标形态：

```text
Content Version
      │
      ▼
精确结果复用 / 确定性预处理
      │
      ▼
本地 AIMA 专用多任务分类器
      │
      ├── 高置信度
      │      │
      │      └── 直接生成标准 Analysis 结果
      │
      └── 低置信度 / OOD / 冲突样本
             │
             ▼
      DeepSeek V4-Flash
      thinking=disabled
             │
             └── 极少数仍不稳定样本
                    │
                    ▼
             DeepSeek V4-Pro
```

这里最重要的设计目标不是：

```text
本地模型 100% 替代 LLM
```

而是：

```text
在可验证质量边界内
尽量提高本地模型自动接受覆盖率
同时把高风险样本可靠送给更强模型
```

具体覆盖比例不能预先拍脑袋写死，例如 `95% / 4.5% / 0.5%` 只能作为容量模拟示例，不能作为当前承诺。

# 9. 第一层：精确复用与确定性预处理

当前 Analysis 已有稳定输入 Hash：

```text
input_hash
```

它由当前真正发送给模型的输入字段计算：

```text
title
text
author.display_name
author.bio
author.verification_label
```

在 4000 万历史数据正式重跑前，第一件应该做的不是立即训练模型，而是统计：

```text
COUNT(*)
COUNT(DISTINCT input_hash)
```

以及按：

```text
相同 input_hash
+ 相同 Taxonomy / 分析策略身份
```

计算可以安全复用的精确重复比例。

### 边界

当前不能简单按“标题相同”或“正文相似”就复用整个 Analysis：

- `voice_type` 依赖作者公开信息；
- 轻微文本差异可能改变 sentiment / label；
- 模糊近似复用很容易把营销账号和真实用户混掉。

因此第一版优先只做**精确输入身份复用**。

模糊去重如果未来要做，应作为独立高风险优化验证，不与精确 Hash 复用混在一起。

# 10. 第二层：本地多任务分类器

## 10.1 不推荐第一版训练“小型生成式 LLM”继续吐 JSON

如果只是把：

```text
DeepSeek V4-Pro
```

换成：

```text
本地 7B/14B 生成式模型
```

然后继续自回归生成完整 JSON，虽然避免 API 费用，但仍然保留：

- 生成式推理开销；
- JSON 解码；
- 输出 token；
- 批量吞吐较低；
- 格式 Validation Retry；
- 不必要的自由生成能力。

对于当前闭集任务，第一版更适合：

> **文本 Encoder / Embedding Backbone + 多任务分类 Head。**

## 10.2 推荐任务头

输入仍保持与当前 Analysis 一致，不静默增加平台、URL、互动量等新特征：

```text
title
text
author.display_name
author.bio
author.verification_label
```

推荐输出头：

```text
Head A: relevance
→ binary classification

Head B: voice_type
→ 7-way classification

Head C: sentiment
→ 4-way classification
→ 仅在 relevant 语义下使用

Head D: secondary_labels
→ 39-way multi-label sigmoid
```

一级标签不必让模型重复预测：

```text
secondary_label
→ 按当前 Taxonomy 父子关系确定 primary_label
```

这样可以减少自相矛盾的输出空间。

## 10.3 候选 Backbone

当前可作为实验候选之一：

```text
Qwen/Qwen3-Embedding-0.6B
```

截至 `2026-08-24`，Qwen 官方 Hugging Face 仓库提供该模型，许可证为 Apache-2.0：

```text
https://huggingface.co/Qwen/Qwen3-Embedding-0.6B
```

但本文**不锁死**这个模型。

真正选型必须在 AIMA 自己的数据上比较：

```text
模型大小
中文短文本效果
长文本截断行为
多标签效果
GPU/CPU 吞吐
显存
量化能力
训练成本
许可证
部署复杂度
```

如果一个更小的中文 Encoder 已经满足质量要求，不应该为了“模型更新”机械选择更大的 Backbone。

# 11. Teacher / Student 训练数据怎么建立

当前已经用 DeepSeek V4-Pro 产生的成功 Analysis 是非常有价值的 Teacher 数据，但不能直接把所有历史结果不加筛选地当 Gold Truth。

## 11.1 Teacher Dataset

从当前 PostgreSQL / 离线结果抽取：

```text
输入字段
+ relevance
+ voice_type
+ sentiment
+ labels
+ prompt/taxonomy identity
+ model identity
+ analysis status
```

只使用：

```text
结构校验成功
当前业务规则版本明确
输入与 Analysis Identity 可追溯
```

的样本。

## 11.2 必须分层抽样

不能随机抽一批多数类直接训练。

至少按这些维度分层：

```text
relevant / irrelevant
7 类 voice_type
4 类 sentiment
39 个二级标签
不同平台
长 / 中 / 短文本
高频 / 稀有标签
营销 / 门店 / 媒体 / 真实用户等高混淆边界
```

尤其要主动采集 hard negative：

```text
关键词碰撞
同名实体
竞品主体仅顺带爱玛
营销模板尾巴
作者名有“爱玛”但正文无关
```

## 11.3 Gold Test Set

必须保留独立人工复核 Gold Set。

如果测试集也完全使用 V4-Pro 自动标签，那么最终只能证明：

> “本地模型学得像不像 V4-Pro。”

不能证明：

> “业务标签是否真的正确。”

Gold Set 应重点人工检查：

```text
真实用户发声 vs 营销推广发声
门店经销商发声 vs 品牌官方发声
媒体机构发声 vs 真实用户发声
relevant vs 关键词碰撞
负面 vs 混合
稀有二级标签
多标签边界
```

# 12. 防止训练集泄漏

UGC 数据中转载、同稿、模板、近重复很多。

如果简单随机按“行”拆：

```text
train / validation / test
```

同一篇内容的近重复版本可能同时进入训练和测试，造成虚高指标。

因此正式训练前应先按可验证的内容族做去泄漏处理，例如：

```text
精确 input_hash
+ 必要时受控的近重复聚类
```

然后按 cluster / family 拆分，而不是只按数据库行随机拆分。

近重复聚类只用于**数据集拆分防泄漏**时，风险显著低于直接拿近重复结果做业务标签复用；两种用途不能混淆。

# 13. 置信度不是简单 `> 0.5`

本地模型能否直接接受，必须通过 Validation Set 做概率校准和阈值选择。

不同任务风险不同。

## 13.1 relevance

业务上通常：

```text
false negative
→ 真正舆情被排除
→ 代价高

false positive
→ 多保留一条无关数据
→ 代价相对低
```

因此 relevance 阈值应优先保证业务要求的 Recall，而不是机械追求总体 Accuracy。

## 13.2 voice_type

重点关注 Confusion Matrix：

```text
真实用户发声 ↔ 营销推广发声
真实用户发声 ↔ 门店经销商发声
品牌官方发声 ↔ 门店经销商发声
媒体机构发声 ↔ 真实用户发声
```

## 13.3 多标签

39 个标签不能共用一个固定阈值就结束。

稀有标签可能需要：

```text
per-label threshold
class weighting
focal loss / re-sampling 等实验
```

是否采用哪一种，必须根据验证数据决定。

---

# 14. Fallback 触发条件

第一版至少可以考虑以下触发来源：

```text
relevance 置信度低
voice_type top1/top2 间隔小
sentiment 置信度低
多标签整体不稳定
OOD / embedding distance 异常
本地输出违反 Taxonomy / 结构约束
模型版本与当前 Taxonomy 不匹配
```

最终触发规则必须从验证集校准，不在本文硬编码阈值。

Fallback 仍然复用当前：

```text
ContentLabelAnalysisV3
RuntimeTaxonomyValidator
Analysis Repository
```

而不是让本地模型建立第二套业务结果格式。

# 15. Analysis Identity 需要特别注意

当前“当前有效 Analysis”身份包含：

```text
content/version
prompt_version
prompt_sha256
taxonomy_sha256
model_provider
model
input_hash
```

如果未来加入本地分类器，可以先通过稳定身份表达：

```text
model_provider = local
model = aima-content-classifier-<version>
```

但存在一个必须在正式实现前解决的语义问题：

> 本地分类器推理时不会读取当前 Markdown Prompt，现有 `prompt_sha256` 语义是“模型实际使用的 Prompt 身份”。

不能为了少改 Schema 就长期把“训练标签策略来源”伪装成“推理时实际发送的 Prompt”。

因此正式实现本地 Engine 前必须单独设计并确认：

```text
Analysis policy identity
Engine identity
Taxonomy compatibility
Training data identity
Model artifact hash/version
```

如果需要修改公共 Contract / DB Schema / current Analysis identity，这将是 L3 Change，需要 Migration、兼容和回滚方案。

本文不提前替这个未来 Change 静默决定字段结构。

# 16. 质量评估不能只看 Accuracy

正式 Benchmark 至少要输出：

| 任务 | 推荐指标 |
| --- | --- |
| relevance | Precision / Recall / F1 / PR Curve |
| voice_type | Macro F1 / per-class F1 / Confusion Matrix |
| sentiment | Macro F1 / per-class F1 |
| 39 二级标签 | Micro F1 / Macro F1 / per-label Recall/Precision |
| 概率质量 | Calibration / ECE 或等价校准分析 |
| 自动路由 | Coverage vs Quality Curve |
| 运行性能 | rows/s、P50/P95 latency、GPU/CPU 利用率 |
| 成本 | 每千条 / 每百万条 / 全量估算 |
| fallback | fallback rate、fallback 后最终质量 |

最终验收核心不是：

```text
“模型 Accuracy 95%”
```

而应是：

```text
在业务要求的质量门槛下
本地模型能够自动接受多少比例
剩余多少比例需要 Flash / Pro
最终总成本和吞吐是多少
```

---

# 17. 4000 万条规模应该怎样估算成本

不要先用“平均每条 X token”的拍脑袋数字。

先从真实审计统计：

```text
P50/P90/P95 title+text 长度
P50/P90/P95 input tokens
cache hit / miss tokens
output tokens
reasoning tokens
Validation Retry rate
Transport Retry rate
当前 batch size 分布
```

然后至少模拟四条曲线：

```text
Scenario A
当前 V4-Pro + thinking

Scenario B
V4-Pro + non-thinking

Scenario C
V4-Flash + non-thinking

Scenario D
本地分类器 + Flash fallback + Pro fallback
```

对 Scenario D：

```text
LLM rows
= total_rows * fallback_rate
```

如果本地模型覆盖率从 0% 提升到 80%、90%、95%、98%，分别模拟总费用，而不是提前承诺最终一定可以覆盖多少。

# 18. 推荐实施顺序

## P0：先把当前 LLM 路线做对

目标：不改变业务标签语义，只去除明显不必要的生成式成本。

```text
1. 对当前真实样本统计 token / latency / cost 基线
2. 明确发送 thinking=disabled 的 Provider 参数能力
3. V4-Pro thinking vs non-thinking A/B
4. V4-Flash non-thinking A/B
5. 测试 batch_size 20 / 更高值，并转向按 token budget 组批的设计评估
6. 统计 Context Cache 命中率
7. 统计 Validation Retry / Transport Retry
```

注意：正式代码变更不能因为本文存在就跳过对应测试和 Change 门禁。

## P1：统计可复用数据

```text
1. 统计 4000 万条的 exact input_hash 去重率
2. 按当前 Analysis identity 检查已有可直接复用结果
3. 明确哪些历史 Analysis 因 Prompt/Taxonomy/Model 变化已经 stale
4. 形成“真正还需要分析多少条”的容量基线
```

## P2：建立 Teacher Dataset + Gold Set

```text
1. 从现有成功 V4-Pro 结果分层抽样
2. 补 hard negatives / rare labels
3. 人工复核独立 Gold Set
4. 建立 cluster-aware train/valid/test split
5. 固化 dataset manifest / taxonomy identity
```

## P3：本地分类器 PoC

```text
1. 先冻结 Backbone，只训练分类 Heads
2. 评估任务指标和吞吐
3. 不够时再考虑 LoRA / partial fine-tune
4. 比较 CPU / GPU / quantized inference
5. 输出 coverage-quality curve
```

## P4：混合路由 Shadow

```text
真实流量仍以当前 LLM 结果为业务事实
+ 本地分类器同时推理但不写 current
→ 对比差异
→ 统计置信度与错误类型
```

## P5：小范围 Canary

满足质量门槛后：

```text
高置信度本地结果
→ 小比例真实写入
低置信度
→ LLM fallback
```

必须能：

```text
按 engine/version 审计
快速把本地接受率降到 0
恢复全量 LLM 路由
```

## P6：扩大到历史全量

只有在：

```text
质量
成本
吞吐
稳定性
恢复能力
版本身份
```

都经过验证后，再对数千万历史数据扩大执行。

# 19. 为什么不建议直接一次跑完 4000 万条

在没有上述基线前直接全量执行，会把小问题放大成大成本：

- Prompt / 模型选择错误；
- Thinking 不必要；
- 标签边界漂移；
- Retry 比例异常；
- 重复数据没有复用；
- 价格配置错误；
- Provider 限流；
- checkpoint / Job 恢复问题；
- 大规模错误结果后续重算。

4000 万条不是“把 9 万条脚本的并发从 250 调更大”就可以安全解决的问题。

它需要先把：

```text
单位成本
单位吞吐
单位错误率
可恢复性
```

测清楚，再扩大规模。

# 20. 当前推荐结论

从当前业务任务、代码和规模出发，推荐路线按优先级是：

```text
第一步
修正当前 LLM 调用成本基线
→ explicit non-thinking A/B
→ Pro / Flash A/B
→ Token/Batch/Cache 实测

第二步
减少真正需要推理的数据
→ exact input_hash / 已有 Analysis 复用

第三步
把 DeepSeek V4-Pro 从“全量生产分类器”降级为 Teacher / 高难裁判

第四步
训练 AIMA 专用本地多任务分类器
→ 承担大多数高置信度样本

第五步
低置信度样本走 V4-Flash non-thinking
→ 极少数复杂边界再走 V4-Pro
```

这条路线的目标不是“为了省钱牺牲质量”，而是把不同复杂度样本送到**成本与能力匹配的推理层**。

当前标签任务复杂度有限，且输出严格闭集，因此它比开放式 Agent / 长文本生成更适合本地专用分类器。

# 22. 未来正式实现必须保持的边界

无论采用哪种优化路线，默认保持：

```text
Prompt / Taxonomy 仍是业务标签规则事实源
Analysis 不进入 Canonical / Mapper
正式 Analysis 仍绑定冻结 Content Version
历史 Analysis 不被覆盖
current / stale 语义可解释
输出继续通过严格 Taxonomy / Contract 校验
每种分析引擎都有可审计版本身份
失败和 fallback 可观测
外部请求费用可审计
Secret 不进入日志 / 数据集
```

如果本地分类器要求改变 Analysis Identity、Schema 或公共 API，应按仓库 L3 流程单独设计，不在普通性能优化中静默修改。
