## 2. 当前 Analysis 的问题类型

当前 Content Analysis 主要输出闭集/层级标签，例如：

~~~text
relevance
voice_type
sentiment
labels[]
~~~

模型还可能返回内部证据和决策字段，用于本地 Validator/Judge；持久公共结果继续由正式 Analysis Contract 决定。

从工程问题看，这不是开放式长文生成，而是：

> 有限输入 + 有限分类空间 + 多标签 + 部分语义边界判断。

这个性质说明“大模型 100% 长期承担所有历史数据推理”不是唯一可能路线，但**不能仅凭这个判断就直接切换模型或分类器**。质量、边界样本、可解释性、运行复杂度和回滚都必须重新证明。

## 4. Shard、Worker、LLM 并发是三个概念

大规模任务容易把三件事混在一起：

### Shard

是 Run 的目标分组和持久恢复粒度。

### Worker / Job

是后台执行单元，受当前容器资源、Job Lease、数据库和全局调度限制。

### LLM in-flight / RPS

是 Provider 请求容量，由创建 Run 时冻结的 Provider Runtime 能力约束。

提高 Shard 数不等于提高 LLM 并发；提高 Worker 数也不意味着 Provider、数据库或网络能够线性扩展。

当前精确算法以代码和 Run snapshot 为准，不在本文冻结经验数值。

## 6. 成本从第一性原理怎么算

对生成式模型，核心仍然是：

~~~text
总成本
≈ Σ(输入 tokens × 对应输入单价)
 + Σ(输出 tokens × 输出单价)
 + 重试 / Repair / Judge 的额外调用
~~~

影响成本的不是“并发高低”本身，而是：

- 每条输入 token；
- 每条输出 token；
- Cache 命中语义；
- 首轮失败率；
- Validation Repair；
- Judge 触发率；
- 重试；
- 重跑/重复任务是否被正确复用。

提高并发主要改变墙钟时间，不能自动降低 token 成本。

## 7. 吞吐的真实上界

大规模打标吞吐大致受最慢边界限制：

~~~text
Provider 请求容量
数据库读取/写入
Worker CPU/内存
网络
Validation / Retry
Job/Shard 调度
~~~

因此“机器有更多 CPU”不能直接推出“应该无限加 Worker”；“Provider 允许更多并发”也不能证明 PostgreSQL 写入和业务锁不会成为下一瓶颈。

容量优化必须用目标环境的阶段日志和持久计数定位瓶颈。

## 8. 当前优先优化顺序

在不改变模型能力前，通常先验证低风险浪费：

1. 是否重复分析已有相同 Analysis Identity 的 Content Version；
2. 输入是否携带不影响判断的冗余文本；
3. 输出是否包含业务不消费的自由文本；
4. Repair / Judge 是否被高失败率异常触发；
5. Provider Runtime 的 max_concurrency / max_rps 是否与真实账号能力一致；
6. Shard/Job 是否造成过量数据库/Artifact 往返；
7. 是否存在失败后从头重跑而不是从持久进度恢复。

这些检查属于当前实现优化审计；具体修改仍需正式 Requirement 和证据。

## 9. 候选 A：低成本模型 A/B

候选目的：在保持同一业务 Contract/Taxonomy 的前提下降低单位 token 成本或提高可用并发。

进入实施前至少需要：

- 当前模型作为 baseline；
- 固定 Gold / Review 样本；
- 各一级/二级标签和边界样本的分层覆盖；
- relevance / voice_type / sentiment / labels 分维度比较；
- JSON/Contract 成功率；
- Repair/Judge 触发率；
- 平均输入/输出 token；
- 端到端成本和吞吐；
- 可回滚。

单纯“更便宜”或“平均准确率差不多”不能完成准入。

状态：**未批准候选**，除非后续 Requirement/代码事实明确改变。

## 10. 候选 B：Prompt / 输出压缩

候选方向：

- 删除不会影响业务判断的重复说明；
- 保留稳定 system/context，改善可缓存部分；
- 减少模型不需要输出的解释文本；
- 让 Validator/Judge 只消费必要证据。

风险是过度压缩导致边界规则丢失、Repair 增多，最终成本反而上升。

所以评价指标不是 Prompt 字符数，而是：

~~~text
业务质量
+ 首轮合法率
+ Repair/Judge 比例
+ 平均总 token
+ 端到端成本
~~~

状态：**未批准候选**。

## 11. 候选 C：一请求多内容

如果 Provider 和 Prompt 能稳定支持多条内容批量输出，理论上可以摊薄重复 Prompt token 和 HTTP 开销。

但必须证明：

- 单条内容不会串标签；
- 输出能稳定映射回 content_id；
- 一条坏 JSON 不会让整批不可恢复；
- Token 上限、超时和重试成本可控；
- 单条失败可以安全补偿；
- 批量大小不会让 P99 延迟和 Repair 比例恶化。

当前“Shard”不等于“一个 LLM 请求包含多条内容”。两者必须区分。

状态：**未批准候选**。

## 12. 候选 D：本地分类器 + LLM fallback

这是中长期更结构化的候选。

可能的路线：

~~~text
高置信度闭集样本
→ 本地分类器

低置信度 / 边界样本
→ LLM

人工 Gold / Review
→ 持续评估
~~~

它有潜力把大量简单样本移出高成本生成式调用，但会新增：

- 模型训练与版本管理；
- Dataset/Label 质量治理；
- 置信度校准；
- 漂移监控；
- CPU/GPU Runtime；
- 灰度与回滚；
- 双模型结果一致性解释。

因此不能只比较 API 费用。

状态：**未批准候选**。

## 13. Teacher / Student 数据不能直接拿线上 LLM 输出当真值

如果未来做本地分类器，Teacher 数据至少应区分：

- 高一致性自动样本；
- 人工复核样本；
- 争议/边界样本；
- 低频标签；
- 新标签/规则变更后的样本。

Gold Test Set 不能与训练集混用，也不能只按整体随机抽样，否则大标签会掩盖小标签失败。

标签层级、Brand/Vehicle、内容来源、平台、文本长度等都可能需要分层，具体方案应由正式训练 Requirement 决定。

## 14. 质量准入不看一个总准确率

当前任务是多维度、多标签分类。

未来任何模型/路线切换至少要分别观察：

- relevance；
- voice_type；
- sentiment；
- 一级标签；
- 二级标签；
- 关键边界/否定样本；
- 结构合法率；
- Repair/Judge；
- 人工复核差异。

整体 Accuracy 很高，不代表稀有但重要标签已经可用。

## 15. 灰度与回滚原则

如果候选以后正式获批，推荐保持：

~~~text
旧方案
→ 仍可选 / 可回滚

新方案
→ 先影子或小流量
→ 对同一冻结样本比较
→ 满足准入
→ 再逐步放量
~~~

Analysis Identity 必须能区分模型、Prompt/Taxonomy、关键运行参数，避免不同方案结果被误当成同一分析事实。
