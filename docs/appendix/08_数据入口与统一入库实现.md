| 入口 | 输入证据 | 主要编排 | 最终写入 |
| --- | --- | --- | --- |
| Data Import Campaign：本地上传 | 浏览器显式选择的 XLSX | Campaign / Source Item / Snapshot / Chunk Job | Content Owner |
| Data Import Campaign：服务器目录 | 批准只读目录中的 XLSX | Discover / Snapshot / Chunk Job | Content Owner |

## 2. 共享链路只记一遍

本文只保留定位所需的最小链路：

~~~text
来源字节 / Provider 响应
→ Raw / Input Artifact
→ Reader / Mapper
→ Canonical
→ Brand/Vehicle Resolver / Filter（适用时）
→ Content Owner
→ Current / Version / Metric / Source Contribution
~~~

每一层为什么存在、负责什么，回到 Blueprint；下面只讲各入口的差异和恢复事实。

## 3. Data Import Campaign：来源和写入策略分开

当前页面只有一个“导入数据”业务入口，但来源和写入策略是两个独立维度。

来源：

~~~text
local_upload
server_path
~~~

写入策略：

~~~text
standard_observation
historical_fill_only
~~~

来源决定“文件怎样安全进入系统”；写入策略决定“Content Owner 怎样更新业务事实”。

不能从 server_path 自动推导 historical_fill_only，也不能从 local_upload 自动推导 standard_observation。

## 4. 本地上传和服务器目录为什么不能完全合并

### 本地上传

浏览器先提交冻结 Source Item 清单，再逐文件流式上传。一个 Item 的重试必须继续匹配被冻结的文件身份；不能把网络重试变成“换一份文件”。

全部文件完成后显式 finalize，再进入 Snapshot / Preflight / Chunk。

### 服务器目录

HTTP 只允许管理员批准根目录中的相对路径。目录发现拒绝：

- 绝对路径；
- 父目录逃逸；
- UNC / 设备路径；
- Symlink / Junction / Reparse Point 等链接组件。

Worker 在批准范围内把源文件快照成不可变 Artifact，再进入相同的预检/Chunk 链。

服务器目录是只读数据入口，不是上传、删除、移动、改名、下载任意服务器文件的通用文件管理器。

## 5. Snapshot / Chunk 的恢复边界

Data Import 在真正写 Content 前先把合法输入转成持久 Pure Canonical Chunk。

关键点：

- Source Item 身份先冻结；
- Snapshot Job 负责 Reader / Mapper；
- invalid 行保留最小可审计事实；
- 合法 Canonical 进入有界 Chunk Artifact；
- Chunk 大小在 Campaign 创建时冻结；
- 已创建 Campaign 不因为以后机器配置变化被重新切块；
- Chunk Worker 在业务事务前完整校验自己的有界 Artifact；
- Content、来源贡献、Evidence、逐行 Outcome 与 Job Fence 在正确事务边界内提交。
- 声音广场派生投影在每个 Chunk 的业务写入和调度收尾后、同一事务提交前刷新；已提交的 Chunk 可立即查询，不等整个 Campaign 结束。

实现：

- [backend/src/aima_ugc/modules/ingestion/historical_jobs.py](../../backend/src/aima_ugc/modules/ingestion/historical_jobs.py)
- [backend/src/aima_ugc/adapters/providers/imports/historical_chunk.py](../../backend/src/aima_ugc/adapters/providers/imports/historical_chunk.py)

Chunk 是事务和恢复粒度，不是“系统总共只能处理多少行”的容量限制。

## 6. Brand/Vehicle Filter Snapshot 必须冻结

Import 创建时使用当时的 Brand/Vehicle Catalog 形成 Filter Snapshot。

同一任务后续：

~~~text
预检
→ Filter
→ Content Brand/Vehicle Evidence
~~~

必须消费同一份冻结 Snapshot。不能在 Worker 中途重新读取实时 Catalog，然后让一批数据前后使用不同识别规则。

机器入口：

- [backend/src/aima_ugc/modules/ingestion/brand_vehicle_filter.py](../../backend/src/aima_ugc/modules/ingestion/brand_vehicle_filter.py)

如果用户后来补了 Brand、Vehicle 或 Alias，希望旧 Canonical 重新识别，应走 Persistent Canonical Replay，而不是偷偷让旧 Import 读取新目录。

## 7. standard_observation 与 historical_fill_only

### standard_observation

使用普通 Content 字段新鲜度、Version 和可信 Metric 语义。

### historical_fill_only

用于历史补空：

- 只补当前空值；
- 不用旧历史值覆盖已有非空 Current；
- 冲突进入账本；
- 没有可信观测时间时不把历史值当最新 Metric。

这两个策略共用 Campaign、Chunk、Lineage 和 Content Owner，但业务写入规则不同。

4000 万生产容量承诺的当前边界见：

- [docs/operations/02_4000万历史迁移与Analysis Run运行手册.md](../operations/02_4000万历史迁移与Analysis%20Run运行手册.md)
- [docs/roadmap/02_4000万历史数据迁移实施方案.md](../roadmap/02_4000万历史数据迁移实施方案.md)

不要从“Campaign 共用”推出任意来源/策略都已经获得同样的生产容量结论。

## 9. TikHub Collection 的差异在“来源证据”，不是 Content Writer

## 10. 两层身份不要混淆

### Content 稳定业务身份

正式去重首先依赖平台 + 稳定 external content identity。

如果两个入口最终证明是同一平台同一原生内容，应收敛到同一个 Content，而不是因为来源不同建立两条 Current。

### Provider lookup identity

能否对既有 Content 再请求 Detail / Comments，需要可被 Provider 精确定位的 typed identity。

Excel URL 可以产生：

- 已证明的原生 ID；
- 只够数据库稳定身份、但不够 Provider 补采的定位；
- 需要显式解析后才能获得精确 ID 的短链；
- 当前无法安全解析的分享/文章链接。

不能为了提高“可补采率”把 URL hash 或未证明的链接片段当原生 Provider ID。

补采资格和各平台限制由正式 Eligibility / Collection 能力判断，不在前端猜。

## 14. Persistent Canonical Replay 解决什么

Replay 解决：

> Canonical 已经存在，但创建它时的 Brand/Vehicle Catalog 还不足以命中；现在目录补齐后，希望用新目录重新做 Resolver/Filter，而不重新抓 Provider 或重新上传文件。

HTTP / Domain / Worker 入口：

- [backend/src/aima_ugc/bootstrap/canonical_replay_http.py](../../backend/src/aima_ugc/bootstrap/canonical_replay_http.py)
- [backend/src/aima_ugc/modules/ingestion/canonical_replay.py](../../backend/src/aima_ugc/modules/ingestion/canonical_replay.py)
- [backend/src/aima_ugc/bootstrap/canonical_replay_planner_worker.py](../../backend/src/aima_ugc/bootstrap/canonical_replay_planner_worker.py)
- [backend/src/aima_ugc/bootstrap/canonical_replay_worker.py](../../backend/src/aima_ugc/bootstrap/canonical_replay_worker.py)
- [backend/src/aima_ugc/adapters/persistence/postgres/canonical_replay.py](../../backend/src/aima_ugc/adapters/persistence/postgres/canonical_replay.py)

Replay 不重新发送 Provider 请求，也不改写 Raw。

管理员发起“全历史重筛”时，HTTP 不扫描全部历史 Canonical。受理事务只冻结当时的 Brand/Vehicle Catalog、数据库时间边界并创建 Planner Job；Planner 只选择该时间边界以前已经成立的合法 Canonical，再按现有每 Run 上限创建子 Run。这样排队期间新生成的 Artifact 不会静默进入既有请求，同时确认按钮的等待不再承担全历史规划成本。Planner 的 queued/running/planned/failed/cancelled 状态和 Job 关联由父 Replay Request 持久化，运行中心可以区分“正在规划”和“正在重筛”。

## 15. Replay 输入为什么必须先完整预检

一个 Replay 可以选择多个 Canonical Artifact。

在首个业务 Content 写入前，Worker 必须确认冻结输入集满足：

- Artifact 仍是合法 Replay 来源；
- 文件完整性成立；
- gzip / JSON / Contract 可解析；
- 行级 Source 与父来源关系一致；
- 当前已经进入撤销中的来源不会被继续写入。

这样第二个 Artifact 损坏时，不会出现“第一个已经写了一半，后来才发现整次输入其实无效”。

普通 Canonical Reader 与 Replay 的完整性证明/缓存可以减少重复验证成本，但不能降低输入正确性。

## 16. Replay 的去重和分片边界

Replay Run 内同一稳定 Content identity 必须保持一致顺序。

较大输入可以在原 Run 去重边界内按稳定内容身份生成持久工作单元；小输入、低命中输入或已有串行断点继续走单路，避免多个分片反复重读大量压缩输入反而变慢。

持久分片入口：

- [backend/src/aima_ugc/modules/ingestion/replay_shards.py](../../backend/src/aima_ugc/modules/ingestion/replay_shards.py)
- [backend/src/aima_ugc/adapters/persistence/postgres/replay_shards.py](../../backend/src/aima_ugc/adapters/persistence/postgres/replay_shards.py)

每个分片保存自己的断点和统计；父 Run 只有在：

~~~text
全部业务分片已提交
+ 关联子 Job 到终态
+ 父计数对账
~~~

后才能成功。

分片数不是 Worker 并发承诺。实际窗口还受有效 CPU、内存、数据库连接余量、剩余分片数、Artifact 重读成本和本轮实测吞吐限制。

历史 benchmark 和当时的实验数字属于对应 Change / Git 证据，不在当前实现说明长期复制。

## 17. Replay checkpoint / Job Fence 保证什么

恢复依赖三个事实：

- 输入 checkpoint；
- Run 内稳定 identity 去重事实；
- Job Fencing Token。

一个批次只有在 Content、Evidence、来源贡献、统计与 checkpoint 按正确事务提交后才算完成。

旧 Worker 失去 Lease 或进程崩溃时：

~~~text
已提交批次
→ 保留

未提交批次
→ 整体回滚

新 Worker
→ 从最后持久 checkpoint 继续
~~~

不能用内存进度冒充可恢复事实。Replay 单批事务从冻结上限的较小档位开始按实测吞吐逐级试探；事务墙钟过长会反馈降档，数据库锁等待有有界 timeout。后台批次遇到短期锁竞争应回滚当前批并重试，不允许用延长 Lease 把长事务继续压在在线管理写上。Worker 收到 LeaseLost 时只有数据库确认当前 Fence 已失效才放弃旧执行；当前 Fence 仍有效的异常继续上抛，避免把实现错误伪装成正常接管。

## 18. Replay 为什么必须记录可逆贡献

Replay 可能更新已有 Content，也可能让一个以前不可见的 Content 第一次进入业务视图。

因此每次 Replay 业务写入要同时保存足够的可逆事实，包括：

- 当前请求贡献了哪些字段/可见性；
- Content 是否由本请求新建；
- 自动 Brand/Vehicle Evidence 的 before/after；
- 后续写入是否已经接管当前事实。

撤回时不是简单 DELETE。

机器入口：

- [backend/src/aima_ugc/bootstrap/canonical_replay_reversal_worker.py](../../backend/src/aima_ugc/bootstrap/canonical_replay_reversal_worker.py)
- [backend/src/aima_ugc/modules/ingestion/reversal_shards.py](../../backend/src/aima_ugc/modules/ingestion/reversal_shards.py)
- [backend/src/aima_ugc/adapters/persistence/postgres/reversal_shards.py](../../backend/src/aima_ugc/adapters/persistence/postgres/reversal_shards.py)
- [backend/src/aima_ugc/adapters/persistence/postgres/content_lifecycle.py](../../backend/src/aima_ugc/adapters/persistence/postgres/content_lifecycle.py)

后续普通导入、另一轮 Replay 或人工锁已经接管的事实不能被旧 Replay 撤回覆盖。

## 19. Data Import Campaign 撤销也按贡献，不按“原始行数”

Campaign 撤销前先做 Preview，但真正要重组的 Content 必须来自当前完整贡献账本，而不是只看最初 Import 行。

这很重要：

~~~text
原导入行可能全部 filtered
→ 后来 Persistent Canonical Replay 用同一 Campaign 来源形成 Content Contribution
→ 撤销 Campaign 时仍然必须处理这些真实贡献
~~~

因此撤销 Preview 与 Worker 使用同源 Campaign Contribution 语义，终态还要记录实际重组数量。

实现：

- [backend/src/aima_ugc/bootstrap/import_revocation_worker.py](../../backend/src/aima_ugc/bootstrap/import_revocation_worker.py)
- [backend/src/aima_ugc/adapters/persistence/postgres/historical_revocation.py](../../backend/src/aima_ugc/adapters/persistence/postgres/historical_revocation.py)

## 20. 大撤销为什么按 Content 范围分片

普通 Campaign 撤销和 Replay 撤回都要求：

> 同一个 Content 的相关 Delta 必须在同一事务中按正确顺序处理。

所以大任务的并行粒度是互不重叠的 Content UUID 范围，不是任意切原始来源行。

持久分片：

- [backend/src/aima_ugc/modules/ingestion/reversal_shards.py](../../backend/src/aima_ugc/modules/ingestion/reversal_shards.py)
- [backend/src/aima_ugc/adapters/persistence/postgres/reversal_shards.py](../../backend/src/aima_ugc/adapters/persistence/postgres/reversal_shards.py)

父 Job 承担用户可见终态；子 Job 只承担业务工作单元。片断点、父计数与业务写入必须保持可恢复一致。

小任务沿原单 Job 路径，不为了“并行化”制造额外调度成本。

## 21. 自适应并行不是“机器核数越多越快”

当前持久 Job/Worker 可以根据：

- 有效 CPU；
- 可用内存；
- 数据库连接余量；
- 待处理分片；
- 已完成区间的实际吞吐；

逐级试探、回退和复探。

Linux 容器的 `memory.current` 包含文件页缓存。资源探测从 `memory.stat` 的
`inactive_file` 中扣除 `file_dirty` 和 `file_writeback` 后，才估算可回收缓存；
有效余量仍受宿主机 `MemAvailable` 限制。统计缺失时回退到保守余量。
`capacity.job_window_selected`、`capacity.worker_pool_resized` 等调整日志同时记录
`memory_accounted_mib`、`memory_reclaimable_mib` 和有效可用内存，便于区分
缓存增长与匿名内存压力。资源估算只是升档上界；已完成批次的吞吐和数据库余量
仍决定是否保持更高并发。

同一 Campaign 的不同来源 Chunk 可以共享取消门并行处理业务写入；一个来源内
按 Chunk 顺序处理。每个 Chunk 在业务写入完成后才申请 Campaign 父行锁，
用短暂的收口阶段串行调度后续 Job 和更新终态。取消请求取得独占门后，
不会与尚未提交的 Chunk 业务写入交错。

声音广场筛选目录按 Content 类型等维度维护精确计数。同值 Content 并行写入时，
目录计数行是共享热点；在 Content 写入初期刷新投影会把整个后续事务串行化。
批量导入 Chunk、兼容单文件导入 Job、重筛批次、普通导入撤销批次和重筛撤回批次先写业务事实，
再在**各自事务末尾**一次刷新受影响的 Content 投影及目录计数。投影仍与业务事实
原子提交，失败时一起回滚；普通单条写入继续由触发器同步刷新。重筛撤回的
已提交批次同时更新 Content 查询和声音广场的可见性，包含撤回尚未全部完成时
已经结清的内容。部署迁移会定向修复旧版本中已撤回重筛却仍显示可见的投影行。

比较导入性能时，Chunk 日志的 `projection_content_count`、`projection_refresh_ms`
与 `content_ingestion_ms`、`transaction_ms` 应一起看；投影锁在事务尾部仍可能让
少量并发事务等待，不能仅凭 Worker 数量判断是否达到目标机器的有效吞吐上限。

但数据库锁、WAL、压缩输入重读和单一父事实锁都可能让更多 Worker 变慢。

所以文档不再冻结“某机器应该开几个 Worker”的经验数字。当前调度行为以代码、日志和目标环境实测为准。
评估速度时分别比较 Discover、Snapshot 的 `reader_mapper_ms` / `chunk_publish_ms`、
Chunk 的 `content_ingestion_ms` / `evidence_ms` / `finalization_ms`、Replay 的
预检与入库、撤回的批量与分片事件，并同时观察容器 CPU、匿名内存、脏页、
数据库连接和 OOM 事件。运行中的任务进度不能代替同类完整输入的前后对比。

## 22. 强一致可见性

Content、来源贡献、Brand/Vehicle Evidence 与需要同步维护的业务读取投影在同一正确事务边界完成。

事务提交后，下一次业务查询应看到已提交结果；当前设计不依赖“另一个异步 Worker 以后再把声音广场补出来”。

精确投影/Trigger 事实以 Migration 与 PostgreSQL 集成测试为准，不在本页复制 DDL。

## 23. 常见故障排查

### Campaign 一直 queued

检查：

~~~text
Campaign 状态
→ Job 状态 / Lease
→ Worker 是否运行
→ worker 日志
~~~

不要用 imports_test 的成功替代正式 Worker 证据。

### Snapshot / Mapping 失败

检查：

~~~text
Source Item
→ Input Artifact 完整性
→ XLSX Profile / Header
→ Reader / Mapper
→ invalid row / Snapshot Job error
~~~

### Batch/Campaign 成功但 rows_ingested = 0

可能是：

- Filter 全部过滤；
- 都与既有 Content 收敛；
- 多来源重复；
- historical_fill_only 没有可补空字段。

0 新建不等于 0 处理。运行中心需要区分新增、处理已有、过滤、重复等各自单位。

### 同一帖子出现两条 Current

优先查：

~~~text
platform
→ external_content_id / alternate identity
→ Mapper
→ Content unique constraint
→ Content Owner
~~~

不要先在导入脚本里叠一层标题文本去重。

### tikhub_test 有 Raw，但 DB 模式失败

顺序查：

~~~text
Provider Config / Secret
→ Request / Attempt
→ Raw Artifact
→ Mapper
→ Canonical
→ Content Owner
~~~

### Replay 很慢

先分段确认：

~~~text
Artifact I/O / 解压
→ JSON / Contract 解析
→ Resolver / Filter
→ Content / Evidence 写入
→ Contribution / Checkpoint
→ PostgreSQL 锁 / WAL
~~~

不要只看最终新增 Content 数推断瓶颈，也不要直接增加分片数。先区分 Planner、预检、Artifact I/O、业务批事务和 PostgreSQL 锁等待；如果运行中心仍停在“规划重筛任务”，先查 Planner Job，而不是把它误判成 Replay Worker 入库慢。

### 撤销预览和实际处理量不一致

检查：

~~~text
原 Import 行
+ Content Source Contribution
+ Replay 贡献
→ 当前受影响 Content 集合
~~~

如果只看原始行账本，很容易漏掉后续 Replay 形成的真实贡献。

## 24. 修改数据入口时从哪里开始

### 新 Excel Profile

从 Reader / Mapper / Fixture / Canonical Contract 开始，最后仍复用正式 Content Owner。不要新增第二个 Content Writer。

### 新 Provider

从 Provider Adapter / Operation / Raw / Mapper / Capability / Fixture 开始，Canonical 后继续复用 Content Owner。

### 改跨来源业务身份

这是高风险边界，必须同时检查 Canonical identity、数据库唯一约束、Content Repository、Migration、现有数据兼容和所有入口测试。不能只改一个 Dedup helper。

### 改 Data Import Campaign

同时检查：

- 目录/上传安全；
- Source Artifact 完整性；
- Snapshot / Chunk；
- 行账本；
- Brand/Vehicle Snapshot；
- standard_observation / historical_fill_only；
- cancel / retry / revoke；
- Collection supplement eligibility；
- 运行中心 Read Model。

### 改 Replay / Reversal

同时检查：

- 输入资格；
- 全输入预检；
- Run identity / checkpoint；
- 持久分片；
- Job Fence；
- Source Contribution；
- Evidence before/after；
- 后续写入接管；
- 父子完成屏障；
- cancel / revoke / retry；
- 强一致读取投影。
