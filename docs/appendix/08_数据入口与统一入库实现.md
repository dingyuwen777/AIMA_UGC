# 数据入口与统一入库实现

本文解释当前 AIMA_UGC 最重要的数据问题：

> Excel、TikHub 正式采集、`imports_test`、`tikhub_test` 看起来是不同入口，为什么最终能进入同一套 PostgreSQL Content，而且跨来源去重、版本历史和来源追溯不会各做一套？

本文描述**当前实现**，不再按 Stage 8A/8B/8C 的施工过程组织。历史为什么分阶段实现，去 `changes/archive/` 查；开发者现在需要知道的是最终代码怎样工作。

- [`docs/blueprint/03_数据库与文件存储.md`](../blueprint/03_数据库与文件存储.md)

# 1. 当前有哪些数据入口

当前可以分成四类。

## 1.1 正式 Excel HTTP Import

```text
浏览器 / HTTP Client
→ POST /api/v1/import-batches
→ PostgreSQL Import Batch + Job
→ Worker
→ Content
```

这是产品化的文件导入入口。

## 1.2 正式 TikHub Collection

```text
Collection Plan / API Run
→ Collection Run / Scope
→ TikHub
→ Raw / Candidate / Mapper
→ Content
```

既可以由 Scheduler 创建 scheduled Run，也可以通过 API 创建 discovery / batch supplement Run。

## 1.3 `imports_test`

```text
本地 Excel
→ Canonical JSONL
→ Relevance
→ Dedup
→ 可选 PostgreSQL
→ 可选 AI
→ Excel
→ 可选 Word Report
```

它是人工调试/离线批处理入口，不是第二套产品数据库。

## 1.4 `tikhub_test`

```text
本地人工参数
→ 生产 TikHub Operation/Transport/Mapper
→ 本地 Raw/JSON/Excel
→ 可选 PostgreSQL 正式来源链
```

它用于人工验证五个平台，默认不要求写库。

# 2. 四个入口最终在哪里汇合

真正统一的地方不是“都用了 PostgreSQL”，而是：

```text
CanonicalContentV1 / CanonicalCommentV1
→ ContentIngestionService
→ Content Owner Repository
```

核心领域入口：

- [`backend/src/aima_ugc/modules/content/ingestion.py`](../../backend/src/aima_ugc/modules/content/ingestion.py)

核心类：

```python
ContentIngestionService
```

它接收系统统一的 Canonical，不接 TikHub Raw，也不接 Excel Worksheet。

正式 PostgreSQL Content Owner 实现在：

```text
backend/src/aima_ugc/adapters/persistence/postgres/
```

完整链可以理解为：

```text
TikHub
→ Operation / Mapper ───────────┐
                                │
Excel
→ Reader / Mapper ──────────────┼→ Canonical
                                │
未来其他 Provider
→ Adapter / Mapper ─────────────┘

Canonical
→ Relevance / Decision（入口按业务需要）
→ ContentIngestionService
→ PostgreSQL
```

因此当前没有：

```text
TikHubContentWriter
ExcelContentWriter
OfficialApiContentWriter
```

三套独立业务 Upsert。

# 3. Canonical 为什么是统一边界

第三方输入字段完全不同。

例如“正文”可能来自：

```text
xiaohongshu note.desc
Douyin aweme_info.desc
Weibo status.text
Excel “内文”列
```

如果数据库 Repository 直接理解这些字段，后面换 Provider 时数据库逻辑也会跟着变。

所以先映射成：

```text
CanonicalContentV1.text
```

同理：

```text
external_content_id
platform
author
published_at
metrics
source
observed_fields
```

都先变成统一 Contract。

精确定义：

- [`backend/src/aima_ugc/contracts/canonical/__init__.py`](../../backend/src/aima_ugc/contracts/canonical/__init__.py)：Canonical Python package 的公开导出边界；
- [`contracts/canonical/`](../../contracts/canonical/)：生成的 JSON Schema。

Canonical 不保存 AI 标签；AI 属于 Analysis Domain。

# 4. 正式 Excel Import 完整链路

当前 HTTP：

```text
POST /api/v1/import-batches
```

Route：

- [`backend/src/aima_ugc/bootstrap/api.py`](../../backend/src/aima_ugc/bootstrap/api.py)

Application Service：

- [`backend/src/aima_ugc/bootstrap/import_http.py`](../../backend/src/aima_ugc/bootstrap/import_http.py)

Job Executor：

- [`backend/src/aima_ugc/bootstrap/import_worker.py`](../../backend/src/aima_ugc/bootstrap/import_worker.py)

## 4.1 API 阶段

当前 multipart 必须包含一个 `file`，以及重复字段形式提交的 1—20 个不重复 `keyword_pack_ids`。HTTP/Application 层只做短事务前置工作和父事实创建：

```text
接收 multipart file + keyword_pack_ids
→ 校验 1—20 个不重复词包选择
→ 读取所选 Keyword Pack 当前版本与启用关键词
→ 合并并按现有 Relevance 匹配规则归一/去重 effective_keywords
→ 冻结 ImportKeywordSelectionSnapshot
→ 校验 XLSX 上传/ZIP 资源边界
→ 保存 Input Artifact
→ 同事务创建 processing_import_batches + ingestion.import-excel.v1 Job
→ Batch stats 与 Job Payload 保存同一 keyword_selection
→ commit
→ 返回 202
```

Excel Import 不读取 `global_relevance_config` 来决定本次筛选词包；全局 Relevance 配置继续服务 Collection 的当前入口语义。真正 Excel 处理不在 HTTP 请求里执行。

## 4.2 Worker 阶段

`PostgresImportJobExecutor` 当前顺序：

```text
读取 Batch + Job + Artifact
→ 校验 JobExecutionFence
→ 校验 Batch stats.keyword_selection == Job Payload keyword_selection
→ 读取冻结 effective_keywords
→ Artifact copy_to 临时 source.xlsx
→ 校验 SHA-256 / byte_size
→ validate_xlsx_archive()
→ stage = reading
→ stage = mapping
→ convert_excel_to_canonical_jsonl()
→ stage = filtering
→ filter_canonical_content_jsonl()
→ stage = deduplicating
→ deduplicate_content_jsonl()
→ stage = ingesting
→ ingest_unified_content_batch()
→ Batch / Job 成功收敛
```

当前进度 heartbeat 大致发生在：

```text
15%
40%
60%
80%
```

这些百分比是 Worker 实现细节，不是公共 Contract；精确值看 [`backend/src/aima_ugc/bootstrap/import_worker.py`](../../backend/src/aima_ugc/bootstrap/import_worker.py)。

## 4.3 为什么 Worker 每个 Attempt 从 Artifact 重新跑

当前 Import Job 的可恢复输入是：

```text
Input Artifact
+ Batch 冻结 Profile
+ ImportKeywordSelectionSnapshot
```

不是上一个 Worker 留在 `/tmp` 的中间 JSONL，也不是 Worker 启动时重新读取的实时 Keyword Pack。

Worker 重试时重新：

```text
Artifact
→ Reader
→ Filter
→ Dedup
→ Ingest
```

这样进程崩溃后不依赖不可持久临时目录，也不会因为管理员修改词包而改变已排队 Import 的业务输入。

# 5. XLSX 安全为什么在业务处理前

`.xlsx` 是 ZIP 容器。

攻击/异常文件可能：

- 文件本身过大；
- ZIP member 过多；
- 单 member 解压极大；
- 总解压量巨大；
- 压缩比异常；
- 不是合法 XLSX。

当前实现：

- [`backend/src/aima_ugc/modules/ingestion/xlsx_security.py`](../../backend/src/aima_ugc/modules/ingestion/xlsx_security.py)

正式 API 在保存 Input Artifact 前验证上传流的 XLSX 结构与资源边界；Worker 从 Artifact 恢复本地 `source.xlsx` 后再次执行 archive 校验并核对 Artifact SHA-256 / byte_size，再进入 Reader/Mapper。

如果要调整限制，必须同时看：

```text
xlsx_security.py
bootstrap/api.py multipart/body 上限
bootstrap/import_http.py
bootstrap/import_worker.py
API/Unit Tests
用户上传说明（如果可观察行为变化）
```

不能只把 `openpyxl` 异常当成安全门禁。

# 6. Excel 的来源链怎么建立

Excel 没有真实 TikHub HTTP，但仍需要能回答：

> 这条 Content 是从哪一个 Excel 文件、哪次导入进来的？

当前主链：

```text
Input Artifact
→ Processing Import Batch
→ import-parent Provider Request
→ non-billable Provider Attempt
→ Content Version
```

核心代码：

- [`backend/src/aima_ugc/bootstrap/manual_ingestion.py`](../../backend/src/aima_ugc/bootstrap/manual_ingestion.py)

关键函数：

```python
ingest_unified_content_batch(...)
```

它为每个平台建立稳定的 Import Request/Attempt lineage，然后把 Canonical 交给 `ContentIngestionService`。

虽然使用 Provider Request/Attempt 作为统一来源账本，但 Excel Attempt 是：

```text
non-billable
operation = excel_import
```

不会伪造真实外部网络收费。

# 7. 为什么 Excel 不伪造 Collection Run/Scope

Collection 的真实业务语义是：

```text
一个 Run
→ 多个平台/关键词 Scope
→ Provider 请求
```

Excel 没有这个过程。

如果为了“所有来源表结构看起来一样”而伪造：

```text
Fake Run
Fake Scope
```

后续排障会误以为发生过一次采集任务。

所以当前 Provider Request 来源父级设计为二选一：

```text
Collection Request
→ scope_id != null
→ import_batch_id = null

Import Request
→ scope_id = null
→ import_batch_id != null
```

数据库 Check Constraint 注册：

- [`backend/src/aima_ugc/modules/ingestion/tables.py`](../../backend/src/aima_ugc/modules/ingestion/tables.py)

这比“所有东西强行对称”更真实。

# 9. Import 的两层去重

“去重”不是只有一个位置。

## 9.1 批次内去重

正式 Import Worker：

```text
filter_canonical_content_jsonl()
→ deduplicate_content_jsonl()
```

主要作用：

- 同一个 Excel/批次不要重复处理相同稳定身份；
- 减少后续数据库工作；
- 离线场景避免重复 AI/导出。

## 9.2 PostgreSQL 跨批次、跨来源收敛

最终 Content 身份：

```text
(platform, external_content_id)
```

最终 Comment 身份：

```text
(content_id, external_comment_id)
```

场景：

```text
上午 Excel 导入 xiaohongshu + note_123
→ contents 里创建 Content A

下午 TikHub 又采到 xiaohongshu + note_123
→ 仍然是 Content A
→ 更新 Current / Version / Metric / 来源历史
```

即使 Excel 已在本批去重，也不能取消数据库 UNIQUE/Owner Upsert。

数据库层解决的是：

```text
跨批次
跨来源
跨时间
并发
```

的最终收敛。

---

## 9.3 稳定 Content 身份与 Provider lookup identity

Excel 和 TikHub 统一入库时必须区分两个用途：

```text
(platform, external_content_id)
→ PostgreSQL 稳定 Content 身份
→ 跨批次/跨来源去重、Current/Version/Metric、Comment 归属

CanonicalContentV1.alternate_ids
→ note_id / aweme_id / status_id / av_id / bv_id / photo_id
→ TikHub Detail / Comments / SubComments 的 Provider lookup locator
```

对当前 TikHub 正式支持的内容类型，Excel 与 TikHub 使用同一套平台身份规范化规则，使“Excel 先到”和“TikHub 先到”都能收敛到同一 Content：

- 小红书：`note_id`；
- 抖音：`aweme_id`；
- 微博状态：数字 `status_id/MID`；
- B站视频：Canonical 稳定身份统一为数字 AID；Excel 的 BV 链接确定性转换为 AID，同时保留 `bv_id/av_id` 供 Provider 调用；
- 快手作品：Canonical 稳定身份与补采 `photo_id` 使用公开分享作品 ID（`share_info.photoId`，通常为 `3x...`）；TikHub Raw 中另一套数字 `photo_id` 以 `provider_photo_id` 保留，不再作为跨来源主身份。

真实 Provider 验证已证明快手 Search 同一作品同时存在数字内部 `photo_id` 与公开分享 `photoId` 两套 ID；Excel `/short-video/{id}` 对应公开分享 ID。Detail/Comments 使用公开分享 ID 请求，Mapper 通过上下文继续挂回同一个稳定 Content。

当前 TikHub 正式 Capability 不采 B站动态/opus，也不把微博 `ttarticle` 作为独立 status 内容采集，因此这些尚不具备双边可验证身份的类型不会被伪装成“已可跨来源自动合并”；未来新增对应 Provider Capability 时必须单独完成真实 ID 对齐。

如果某条 Excel 只能用来源文章编号或 URL hash 作为稳定身份，但同时已经获得经过验证的 typed Provider ID，Batch Supplement 可以使用该 typed ID 补详情和评论，同时 Mapper 通过上下文继续把结果挂回原稳定 Content；不会为了发 Provider 请求改写 Content 主身份。

`content_external_ids` 按 `id_type` 合并保留不同来源观察到的可靠身份：较旧 Observation 可以补充此前缺失的 id_type，但不能覆盖同一 id_type 的较新值。

需要注意：typed locator 能让既有 Content 正确补采，并不等于把数据库中已经存在、稳定 `external_content_id` 不同的两条历史 Content 自动合并。历史实体合并需要独立的数据迁移/Identity Registry 设计，本链不会仅凭标题、正文或不确定别名猜测合并。

# 10. ContentIngestionService 当前怎样处理历史

领域入口：

- [`backend/src/aima_ugc/modules/content/ingestion.py`](../../backend/src/aima_ugc/modules/content/ingestion.py)

数据库事实：

```text
contents / comments
→ Current

content_versions / comment_versions
→ 业务字段历史

content_metric_observations / comment_metric_observations
→ 指标历史
```

重要规则：

- `observed_fields` 只声明本次真正观察到的字段；
- 未观察字段不等于 `0` / `null`；
- `field_observed_at` 做字段级 freshness；
- 旧 Observation 可以补一个从未观察过的字段；
- 旧 Observation 不能回滚已经由更新 Observation 明确观察过的字段；
- 正文业务变化才推进 Version；
- 指标变化走 Metric Observation。

详细见 Blueprint 03 和 Content README。

# 11. Rule Relevance 和 AI Relevance 是两层

正式 Excel Import 在进入 Content 前使用规则 Relevance。上传时必须选择一个或多个已启用 Keyword Pack；API 创建 Batch/Job 时冻结所选词包版本，并把各词包有效关键词合并、按现有 Relevance 匹配身份去重为 `effective_keywords`：

```text
Excel Upload
→ selected Keyword Packs (1..20)
→ frozen pack id/version
→ effective_keywords 并集去重
→ title/text 任一关键词 OR 匹配
→ filter_canonical_content_jsonl()
```

它的目的：

> 原始 Excel 里可能有明显和业务关键词无关的内容，先用确定性规则过滤。

Collection 同样使用 Rule Relevance，但它当前从 `global_relevance_config` 冻结 `RelevanceSnapshotV1` 到 Run；Excel Import 的本次选择不会改写该全局配置，两种入口也不会在 Worker 执行时重新解释实时词包。

AI Semantic Relevance 属于后续 Analysis：

```text
analysis_content_results.relevance
```

目的：

> 关键词匹配后仍可能语义无关，用模型进一步判断。

所以：

```text
Rule Relevance
≠ AI Semantic Relevance
```

正式 Import Job 当前不在同一个 Job 内顺便跑 LLM；AI 是独立：

```text
analysis.content-label.v1
```

# 12. Import Keyword Selection 为什么要冻结

假设用户提交 Import 时选择词包 A、B，当时实际有效关键词是：

```text
爱玛
电动车
```

Job 排队期间管理员修改了 A/B 的词条或停用状态。如果 Worker 启动时重新读当前词包，就无法回答：

> 这批数据到底是按提交时哪一组词包和关键词导入的？

所以当前 API 在创建 Batch/Job 前生成 `ImportKeywordSelectionSnapshot`，冻结：

```text
所选 Keyword Pack ID + Version
effective_keywords
```

Batch 保存到：

```text
stats.keyword_selection
```

Job Payload 保存同一份：

```text
keyword_selection
```

Worker `_load()` 会重新解析两边并要求完全相等；不一致直接失败，不自己猜一套，也不读取 `global_relevance_config` 替代本批输入。

精确结构以：

- [`backend/src/aima_ugc/modules/ingestion/import_job.py`](../../backend/src/aima_ugc/modules/ingestion/import_job.py)

为准。

# 14. 多 Excel 人工 run 的数据库来源

`ingest_excel_files_run_to_postgres()` 支持多个源 Excel。

当前规则：

```text
多个 Excel
→ 先形成全局统一/去重结果
→ 再按 Canonical source.source_value 分回原文件
→ 每个原 Excel 单独创建 Input Artifact + Import Batch
```

为什么不能把多个原文件伪装成一个 Artifact：

> 来源追溯必须知道某条 Content 实际来自哪个源 Excel。

当前同一个人工 run 不因此新增“万能父表”；每个源文件有自己真实 Batch。

## 15.1 为什么同一次 TikHub 请求既能保存本地 Raw 又写正式 Raw

`_MirroringTransport` 当前做：

```text
真实 Transport.send()
→ 只发送一次 HTTP
→ 响应镜像到本地调试文件
→ 同一 Response 进入正式 ProviderDispatchService
→ 正式 Raw Artifact
```

所以：

```text
write_to_database = true
```

不会为了写数据库再发第二次 TikHub 请求。

## 15.2 为什么 DB 模式要求正式 Provider Config

数据库来源链需要：

- Provider identity；
- Base URL；
- Secret ref；
- Pricing；
- Request/Attempt；
- Audit lineage。

所以不能只拿本地 `.env` API Key 直接伪造一条生产来源。

## 15.3 调试 Job

`tikhub_test` DB 模式会创建独立 debug Job/Run/Scope 事实，用于 Fencing 和正式来源链收敛；它不是 Scheduler 定时 Run。

当前 `_DEBUG_JOB_PREFIX` 等精确实现看 [`backend/src/aima_ugc/bootstrap/tikhub_test_database.py`](../../backend/src/aima_ugc/bootstrap/tikhub_test_database.py)。

| 真实 HTTP 次数 | 按正式计划 | 按调试配置 | 与本地调试共用同一次发送 |

核心原则：调试入口只改变“怎么触发”，不复制“怎么请求/映射/入库”。

# 20. 常见故障怎么定位

## Excel 上传成功，但 Batch 一直 queued

```text
processing_import_batches
→ jobs
→ Worker 是否运行/claim
```

## Batch running，在 mapping 失败

看：

```text
Batch stage/stats/error_summary
→ source XLSX
→ Excel profile / required headers
→ convert_excel_to_canonical_jsonl()
```

## filtering 后 0 行

检查：

```text
Batch stats.keyword_selection
→ keyword_packs 中提交时选择的 Pack/版本
→ effective_keywords
→ Canonical 标题/正文
→ filter_canonical_content_jsonl()
```

不要去改 `global_relevance_config` 试图改变已经创建的 Import；本批 Worker 使用的是提交时冻结的 `keyword_selection`。

## rows_ingested = 0，但 Batch succeeded

可能是：

- 规则相关性全过滤；
- Dedup 后没有保留记录；
- 多文件场景该源文件的记录在全局去重中都被前面文件保留。

不一定是数据库失败。

## TikHub 调试有本地 Raw，但数据库模式失败

查：

```text
Provider Config
Secret ref
Pricing
Debug Job / Run / Scope
Provider Request / Attempt
正式 Raw Artifact
```

## 同一帖子出现两条 Current

重点查：

```text
platform
external_content_id
Mapper 是否使用稳定 ID
数据库 Unique Constraint
Content Owner Repository
```

不要先在 Excel/TikHub 调试脚本里再加一层标题去重。

## 修改统一数据导入

当前页面只有一个“导入数据”入口。用户先选择来源，再独立选择写入策略：

```text
本地电脑
→ 多选 .xlsx，或用浏览器文件夹选择器递归取得其中全部 .xlsx
→ 先建立冻结上传清单，再逐文件流式上传为不可变 Source Artifact

服务器目录
→ 只枚举管理员批准、只读挂载的根目录
→ HTTP 只收发相对路径，Worker 再快照为不可变 Source Artifact

两种来源
→ 共用 Campaign / Source Item / Chunk / Job / 预检 / 进度 / 取消 / 重试 / 行账本
```

浏览器安全模型不会把本机绝对路径交给网页，也不允许网页在“选择一个文件”后自行扫描该文件所在目录。因此页面明确提供“选择文件（可多选）”和“选择文件夹（自动遍历）”两个本地动作；后端只接收浏览器返回的安全相对路径和文件字节。

本地 Campaign 创建后、全部字节上传完成前处于 `uploading`。网络或浏览器中断时，用户可从 Campaign 历史打开该任务并取消；后端会在同一事务把尚未预检的 Source Item 与 Campaign 收敛为 `cancelled`。已经形成并绑定的不可变 Artifact 仍保留审计关系，上传与取消并发时晚到的绑定会因 Campaign 已终止而失败，不能进入预检或产生业务写入。

来源与写入策略不是一回事：`standard_observation` 复用普通 Excel 的字段新鲜度、Version 和可信 Metric 语义；`historical_fill_only` 执行只补空、不覆盖非空、冲突留账本且无可信观测时间不更新 Metric 的 Stage 12 规则。页面切换来源时只给出安全初始建议，本次 Campaign 最终选择会被冻结，Worker 不读取全局开关。

```text
bootstrap/historical_import_http.py
→ modules/ingestion/historical_directory.py
→ adapters/persistence/postgres/historical_import.py
→ bootstrap/historical_import_worker.py
→ adapters/persistence/postgres/historical_content.py
```

修改这条链时必须同时检查：路径逃逸与 Link/Junction/Reparse Point 拒绝、Artifact/Chunk 哈希、Campaign/Item/Row Outcome 对账、低优先级有界调度、Content Owner 的 fill-only 语义，以及运行手册 [`docs/appendix/14_4000万历史迁移与Analysis Run运行手册.md`](14_4000万历史迁移与Analysis%20Run运行手册.md)。不得把服务器目录能力扩张成上传、删除、移动、改名或下载文件的通用文件管理器。

公开主 Contract 是 `/api/v1/data-import-*`：本地先创建 Campaign/清单、逐 Item 上传、finalize 后进入公共预检；服务器直接从批准相对路径创建 Campaign。既有 `/api/v1/import-batches` 与 `/api/v1/historical-import-*` 暂时保留兼容，但页面不再维护平行入口。数据库表、Job type 和 Python 文件里的 `historical_*` 是为避免高风险迁移改名而保留的物理标识，不代表第二条业务链。

Campaign 进入终态后仍是运行中心中的导入父记录，并可在“基于已有批次补采”中作为优先来源。补采创建先调用 Campaign 资格接口，随后把 `data_import_campaign_id` 冻结到 Collection Run；兼容旧批次则继续使用 `import_batch_id`。数据库约束和 Pydantic Contract 都要求二者至多/恰好按运行模式选择一个，不能让前端同时提交。

4000 万容量承诺只适用于 `server_path + historical_fill_only` 的集合式批量写入。`standard_observation` 在有界 Chunk 内复用现有 Content Owner 的逐记录业务调用，用于普通规模和兼容语义；它没有通过 4000 万吞吐验收，不得因共用 Campaign 就把任意来源/策略组合描述成已具备同等容量。

## 修改 Rule Relevance

先区分是在改共享匹配规则，还是某个入口怎样选择词包：

当前不要假设：

- 正式 Excel Import Job 会自动跑 LLM；
- Excel Import 会从 `global_relevance_config` 推导本批筛选词包；
- 当前 Import Job Payload 仍接受旧 `relevance` 单词包字段；

- `contents` 有 `is_relevant` AI 列；

- `tikhub_test` DB 模式会多发一次 Provider HTTP；
- 前端有独立 Import/Analysis/Export 页面路由；
- 每个数据来源都有独立业务表和 Writer。

本地上传与服务器目录已经共用同一个页面入口和 Campaign 编排；统一的是输入冻结、预检、Chunk、Job、进度和对账，不是把来源安全边界或写入语义混成一个开关。服务器仍只能读批准目录，本地仍必须由浏览器显式选择；`standard_observation` 与 `historical_fill_only` 仍由每个 Campaign 明确冻结。

当前系统的长期核心是：

```text
入口可以不同
证据链可以不同
Canonical 之后的业务事实收敛必须统一
```

## Excel URL 与 Provider Lookup Identity

Excel Import 先保留 Input Artifact，再由生产 Mapper 解析 URL。标准长链接可确定性得到的 Provider ID 会进入 `alternate_ids/content_external_ids`；文章编号或 URL hash 只能保证数据库稳定身份，不自动取得 TikHub 补采资格。

当前本地解析：小红书 `note_id`、抖音 `aweme_id`（含标准 `modal_id`）、微博数字 MID 或 Base62 BID→MID、B站 `av_id/bv_id`、快手 `photo_id`。短链/分享链会识别类型并保留 URL，但在 Detail 返回原生 ID 后尚不能保证原 Content 身份收敛时，普通 Batch Supplement fail closed。

Excel 不生成 Comment ID。一级评论只能在 Content Provider lookup identity 已确认后由 TikHub 获取；评论和二级回复身份继续来自 Provider 响应。


## 多词包入口一致性（2026-08）

当前主动按关键词处理内容的三个入口都以 Keyword Pack 作为关键词父事实，但用途不同：

```text
Excel Import
→ 用户选择一个或多个 Keyword Pack
→ 冻结词包版本与 effective_keywords
→ 对 title/text 执行关键词并集 OR 过滤

TikHub Manual Discovery / Collection Plan
→ 选择一个或多个搜索 Keyword Pack
→ 按目标平台与 platform_scope 展开搜索 Scope
```

Collection 的**搜索词包选择**不等于改变其全局 Rule Relevance；搜索 Candidate 进入 Canonical 后仍按创建 Run 时冻结的 `global_relevance_config → RelevanceSnapshotV1` 做确定性准入。`batch_supplement` 针对已有 Batch 内容补详情/评论，不接收 Keyword Pack，也不执行关键词搜索。
