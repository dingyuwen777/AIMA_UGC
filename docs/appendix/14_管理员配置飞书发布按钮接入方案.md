# 管理员配置页新增飞书发布按钮接入方案

> 状态：方案草案，仅供确认；本次不修改业务代码。
>
> 依据：当前仓库代码、现有测试和用户提供的页面截图。截图只作为页面布局参考，不作为额外开发指令。

## 1. 目标

在“管理员配置”页面增加两个相互独立的操作：

1. **生成并上传报告到飞书**

   页面选择本期报告输入 Excel、上一期报告输入 Excel和必填日期范围，然后执行现有报告入口的等价逻辑：

   ```powershell
   uv run python backend/src/aima_ugc/adapters/providers/imports_test/generate_report.py
   ```

2. **筛选代表性内容并上传飞书多维表格**

   管理员从浏览器选择一个已打标 XLSX 文件，执行现有代表性筛选入口的等价逻辑：

   ```powershell
   uv run python -m aima_ugc.entrypoints.representative_selection_main `
     --input-xlsx "C:\路径\抖音已打标.xlsx" `
     --write-feishu
   ```

两个操作都应具备：管理员权限校验、异步执行、明确的排队/成功/失败反馈、可安全展示的错误摘要和操作审计。

## 2. 当前代码事实

### 页面现状

- 页面入口：[`frontend/src/features/admin-configuration/pages/AdminConfigurationPage.vue`](../../frontend/src/features/admin-configuration/pages/AdminConfigurationPage.vue)
- 页面已经统一处理 `saving`、`error`、`notice` 和管理员身份守卫。
- 页面头部后面是标签页，当前标签页包括车型管理、词包关联、AI 模型、TikHub、AI 分析原则和操作记录。
- 页面已有可复用的 `AimaButton`、`AimaFeedbackBanner`、卡片和双栏布局样式。
- 页面 API 薄封装集中在 [`frontend/src/features/admin-configuration/api.ts`](../../frontend/src/features/admin-configuration/api.ts)。

### 后端现状

- 管理员 API 装配在 [`backend/src/aima_ugc/bootstrap/api.py`](../../backend/src/aima_ugc/bootstrap/api.py)。
- 管理员事务、权限和审计主要由 [`backend/src/aima_ugc/bootstrap/administration_http.py`](../../backend/src/aima_ugc/bootstrap/administration_http.py) 负责。
- 统一持久任务使用 `platform/jobs` 的 `jobs` 表、Lease/Fencing、Worker Registry 和 Job Handler。
- 当前任务中心只投影 AI 打标、采集/导入和 Excel 导出三类业务任务，并不是所有 `jobs` 表记录都会自动显示。
- 报告脚本 [`backend/src/aima_ugc/adapters/providers/imports_test/generate_report.py`](../../backend/src/aima_ugc/adapters/providers/imports_test/generate_report.py) 当前使用脚本内固定的输入 Excel、日期范围和输出目录；它读取飞书发布配置后生成 Markdown/Word 并发布飞书原生文档。因此要支持页面选择文件/日期，需要给现有报告函数增加参数化的薄包装，不能继续直接依赖脚本常量。
- 代表性筛选入口已经支持多个 `--input-xlsx`，默认读取 `imports_test/.env`，`--write-feishu` 会重新筛选并创建新的飞书多维表。
- 两个脚本目前都不是正式 HTTP API，也没有现成的管理员页面按钮。

### 重要限制

- 不建议让 HTTP 请求直接执行 `subprocess` 并等待命令结束；报告生成、LLM 筛选和飞书网络写入都可能超时。
- 不建议新增一个可以接收任意 shell 字符串的“执行命令”接口，否则会形成命令注入和越权执行面。
- 浏览器选择的本地文件不会把真实 `C:\...` 路径直接交给后端；如果前后端不在同一台 Windows 机器上，后端也无法读取浏览器本地路径，必须先上传到后端可访问的 Artifact/暂存区。
- 报告的日期范围必须填写开始日期和结束日期，并校验“开始日期不晚于结束日期”；页面选择的日期范围覆盖脚本当前固定的默认日期范围。

## 3. 页面放置建议

建议在 `AimaPageHeader` 下方、现有标签页上方新增一个独立的“飞书发布工具”卡片。不要把按钮塞进“车型管理”或其他配置标签页，避免用户误以为发布动作只作用于某个配置对象。

卡片采用两个并列操作区，移动端自动上下排列：

| 操作区 | 建议文案 | 输入 | 结果说明 |
| --- | --- | --- | --- |
| 报告发布 | `生成并上传报告到飞书` | 必选：本期报告输入 `.xlsx`、上一期报告输入 `.xlsx`、开始日期、结束日期 | 飞书在线文档链接、可编辑图表 Sheet 链接（如有） |
| 代表性内容发布 | `上传代表性内容到飞书多维表格` | 必选：浏览器选择一个已打标 `.xlsx` | 新建多维表格的结果摘要和表格信息 |

每个操作区独立维护 `loading/status/error/result`，一个按钮失败或运行时不会禁用另一个按钮。提交前使用一次确认提示，文案明确“会在飞书创建新文档/新表，不会修改旧表”。提交后显示任务编号仅用于技术详情，默认层显示业务状态。

### 浏览器本地文件上传方案

根据本次确认，两个操作都采用浏览器本地选择文件，不再让管理员填写服务器路径。报告操作需要选择两个文件：本期报告输入文件和上一期报告输入文件，并填写开始日期、结束日期；代表性筛选操作需要选择一个已打标文件。

1. 前端使用现有文件选择/上传交互模式校验 `.xlsx` 扩展名、文件大小和空文件。
2. 后端以 `multipart/form-data` 接收文件；先流式写入现有 ArtifactStore 或受控暂存区，再在文件完整落盘后计算并冻结文件名、大小和 SHA-256。
3. 文件成功暂存后才创建对应 Job。报告 Job Payload 保存本期和上一期两个 Artifact ID/稳定引用，以及页面必填的日期范围；代表性筛选 Job Payload 保存一个 Artifact ID。Payload 不保存浏览器路径，也不保存文件字节。
4. Worker 执行前从 ArtifactStore 取得只读输入，并再次校验扩展名、大小和 SHA-256；任务结束后按现有 Artifact 保留策略清理中间输入。
5. 报告和代表性筛选分别使用自己的上传与 Job Payload，两个操作不会共享或覆盖输入文件。

不建议把这两个文件硬塞进“数据导入 Campaign”，因为它们不是 Content 入库业务；应复用 Artifact 的存储/安全能力，但保持飞书发布自己的业务边界。若现有 Artifact 元数据接口暂时不支持该类输入，编码前再单独确认是否需要最小 Schema 扩展，不能默认新增第二套文件表。

## 4. 推荐技术方案

### 4.1 API 层

新增两个管理员专用的 multipart 启动接口，保持两个能力独立，不开放通用命令参数：

```text
POST /api/v1/admin/feishu-report-publications
POST /api/v1/admin/feishu-representative-selections
GET  /api/v1/admin/feishu-publication-jobs/{job_id}
```

建议：

- 报告 POST 接收本期报告输入 `.xlsx`、上一期报告输入 `.xlsx`、必填的 `start_date` 和 `end_date`；代表性筛选 POST 接收一个已打标 `.xlsx`。两个接口都限制文件大小、扩展名和 multipart 形状。
- POST 先完成管理员权限校验、上传文件安全校验和 Artifact 暂存，再完成审计和 Job 入队，返回 `202 Accepted + job_id`；上传失败不能创建孤儿 Job。
- GET 只允许管理员读取这两类 Job，返回现有 `JobStatusResponse` 语义，并扩展安全的报告/表格结果字段。
- 复用统一 `HttpErrorResponse`，业务失败不返回 200；错误中不暴露 Secret、完整内部路径、第三方响应正文或 traceback。
- 不把 `.env`、飞书 App Secret、LLM Key 或 `secret_ref` 返回给前端。

上传接口应复用当前项目已有的请求体大小限制、XLSX 文件校验和 Artifact 生命周期能力；不新建服务器目录浏览或文件管理 API。

### 4.2 Job 层

在现有 `jobs` 表和 Worker Runtime 上增加两个明确的 Job 类型，例如：

```text
feishu.report-publication.v1
feishu.representative-selection.v1
```

两个 Job 使用独立 Payload、独立超时/重试策略和独立失败码。Job Payload 只保存经校验的输入快照，不保存 Secret。

Worker 不拼接用户提供的 shell 字符串：

- 报告任务从 Artifact 读取本期和上一期两个输入文件，使用页面必填日期范围调用现有报告生成和飞书发布函数；如需返回链接，给脚本补一个薄的结构化运行包装函数，不改报告统计口径。
- 代表性筛选任务从 Artifact 读取上传的已打标 Excel，调用 `representative_selection_main.main([...])` 的参数入口，或提取一个薄包装函数传入 `--input-xlsx` 和 `--write-feishu` 语义；不复制筛选、飞书字段映射和重试逻辑。
- 如果最终必须保留子进程，命令必须由后端 allow-list 固定构造，参数通过参数数组传入，禁止 `shell=True`；但首选进程内调用，减少环境和输出解析问题。

任务结果只保存可展示的安全摘要，例如：

- 报告：报告产物目录、飞书在线文档 URL、可编辑图表 Sheet URL；
- 多维表：新表名称、记录创建/更新数量、验证数量和必要的表格 URL/ID；
- 失败：稳定错误码和缺少的配置名，不保存 Secret 或原始第三方响应。

报告脚本当前输出目录和配置偏固定，接入时应改为按 Job/运行 ID 生成独立输出目录；同一类报告任务在已有活动任务时返回冲突，或在 Worker 侧串行化，避免并发覆盖同一报告目录。

### 4.3 审计和结果

沿用管理员配置已有 `audit_events`：

- 启动时记录 `feishu_report_publication_requested` 或 `feishu_representative_selection_requested`；
- 任务终态记录成功、失败或取消事件；
- `safe_detail` 只记录任务类型、输入文件名/哈希、数量和安全错误码，不记录完整路径、Token 或 Secret。

第一版建议在管理员配置页内轮询上述 GET 接口并展示结果，不立即把这两类任务塞进全局任务中心。原因是当前任务中心按 AI/采集/导出业务模型组织，强行复用会增加全局列表 Contract、任务投影和前端状态机改动。若后续希望跨页面追踪，再单独把“飞书发布”作为第四类任务加入任务中心。

## 6. 验证计划

### 后端

- Contract/API 测试：普通用户 403、缺少本期/上一期文件、缺少开始/结束日期、multipart 形状错误、超大/空/非 `.xlsx` 文件被拒绝、开始日期晚于结束日期时返回 422、上传失败不创建 Job、成功返回 202 和 job_id。
- Job Unit 测试：Payload 校验、两个 Handler 注册、取消/失败/成功、重试边界和幂等行为。
- Worker 单元测试：用 fake runner 验证固定入口被调用，确保不会执行任意命令；验证安全结果不包含 Secret 和完整私密路径。
- 飞书适配测试：继续复用已有报告发布和多维表 Mock 测试，不在 API 测试中请求真实飞书。
- 审计测试：启动和终态都有安全事件，输入哈希和结果统计正确。

### 前端

- 页面渲染测试：两个操作区、报告本期/上一期文件选择器、代表性筛选文件选择器、必填报告日期范围、独立 loading、错误/成功状态和管理员页面既有标签全部保留。
- API Mock 测试：报告按钮在缺少本期或上一期文件、非 `.xlsx`、缺少开始/结束日期、日期顺序错误或重复提交时阻止请求；代表性按钮在未选择文件、非 `.xlsx` 或重复提交时阻止请求；上传进度和任务轮询状态正确衔接。
- 轮询测试：任务完成后停止轮询；失败只影响对应操作区；页面刷新后能根据 job_id 恢复状态。
- Browser/Full-stack：至少验证一次 `页面 → API → Job → Worker Mock → 状态回读 → 页面结果` 闭环。

### 验收重点

1. 选择本期、上一期报告 Excel 并填写合法日期范围后，点击报告按钮不会阻塞页面，最终能看到成功/失败和飞书结果。
2. 代表性内容按钮只接受浏览器选中的已打标 XLSX，能把文件暂存后传给既有入口并显示创建表结果。
3. 两个按钮互不影响，任一失败不会污染另一个操作状态。
4. 普通用户无法调用接口；前端隐藏按钮不是唯一权限控制。
5. 旧报告、旧多维表不会被删除或覆盖；每次发布的副作用符合现有脚本语义。

## 7. 仍需确认的问题

当前没有新的结构性问题；已按本次确认采用“报告上传本期和上一期两个 Excel，并强制填写日期范围；代表性筛选上传一个 Excel”的方案。

## 8. 结论

推荐采用“页面独立发布卡片 + 报告双 Excel/必填日期范围/代表性筛选单 Excel上传 + 两个专用管理员 API + 两个现有 Job Runtime 任务 + Worker 内调用既有 Python 入口 + 页面内轮询”的方案。

它能保持两个能力的独立性，复用当前权限、审计、Job、Artifact、飞书适配和前端反馈基础。方案确认后即可建立对应 Change/验证矩阵并开始编码。
