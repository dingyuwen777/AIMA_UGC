本文是当前近期开发的**执行计划**，目标不是一次完成完整 Production Go-Live，而是先把现有 Stage 8 前后端做成真正可用的业务闭环，再部署到公司服务器供公司内部网络使用。

完整生产安全、离线 Release、Backup/Restore、认证授权等长期路线仍见：

- [`../appendix/11_生产部署与离线Release方案.md`](../appendix/11_生产部署与离线Release方案.md)


# 9. Internal V1-A：最小可部署环境

## 当前状态：已完成

这一阶段复用长期 Stage 11 设计，但只实现公司内网 V1 真正需要的最小可部署基础，没有提前扩成完整 Production Release。

已实现：

```text
根 Dockerfile
根 compose.yaml
env.production.example
scripts/deploy/prepare_host.py
deploy/nginx.conf
bootstrap
frontend
api
worker
scheduler
migrate
configure
postgres
```

### 9.1 管理员启动入口

当前正式操作只需要：

```bash
cp env.production.example env.production
chmod 0600 env.production
# 编辑 env.production
docker compose --env-file env.production up -d --build --wait
```

`env.production` 可以包含 TikHub/LLM API Key，因此属于敏感文件并由 Git ignore。管理员不需要手工运行 `prepare_host.py`、创建数据库/Cursor 密钥文件、单独跑 Migration/configure 或逐个启动服务。

Compose 自动编排：

```text
bootstrap completed successfully
→ postgres healthy
→ migrate completed successfully
→ configure completed successfully
→ api / worker / scheduler
→ frontend healthy
```

`bootstrap` 是一次性 root 初始化服务，完成后退出，不常驻高权限容器。`migrate` 和 `configure` 也继续是一性独立进程；API 启动本身不修改 Schema。

### 9.2 Secret 分层

内部随机 Secret：

```text
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
```

首次由 bootstrap 自动生成到 `AIMA_HOST_SECRET_DIR`，不要求管理员填写，不静默轮换；Backend 通过 `/run/internal-secrets` 只读使用。

外部凭据：

```text
AIMA_TIKHUB_API_KEY
AIMA_LLM_API_KEY
```

管理员写入 `env.production` 后由 Compose 转成 `/run/secrets/*` Secret File，只授予需要的容器；不作为业务容器普通环境变量，也不保存进 Provider Config。Provider Config 仍只保存 `secret_ref`。

已有 PostgreSQL 18 数据但 `postgres_password` 丢失时，bootstrap fail closed，必须恢复原 Secret；禁止自动生成新密码造成数据库/应用密码漂移。

### 9.3 持久化与网络

```text
PostgreSQL
→ AIMA_HOST_POSTGRES_DIR（默认 /data/AIMA_UGC/postgres）
→ /var/lib/postgresql

Artifact
→ AIMA_HOST_DATA_DIR
→ /app/data

日志
→ AIMA_HOST_LOG_DIR
→ /app/logs
```

Frontend 是唯一宿主 HTTP published port；PostgreSQL/API 无宿主 PortBindings。正式 Backend/Frontend Runtime 仍非 root。

### 9.4 永久 Compose Golden Path

`.github/workflows/internal-v1a.yml` 从空隔离宿主状态使用与管理员相同的一条 Compose 命令，真实验证：

```text
Backend / Frontend image build
bootstrap one-shot
内部 Secret 首次生成与二次启动不轮换
PostgreSQL 18.4
空库 Migration 到 Alembic head
Provider Config configure one-shot
外部 API Key 只通过 Compose Secret File
业务容器 Config.Env 不含 API Key
PostgreSQL / Artifact / log 持久化
api / worker / scheduler / frontend 正式进程
Nginx /health/ready
非 root Runtime
内部 Secret read-only mount
PostgreSQL/API 无宿主 PortBindings
Frontend 唯一批准 PortBinding
已有 PostgreSQL 数据 + 丢 postgres_password 时 fail closed
恢复原 Secret 后同一启动命令可恢复系统
```

因此 Internal V1-A 的完成含义是：**仓库已经有一套经过隔离 Linux Runner 真实验证、管理员只需一个 `env.production` + 一条 Compose 命令即可启动的最小可部署环境。**

V1-A 本身不证明公司服务器、真实浏览器、真实 TikHub/LLM、目标容器重启和宿主机 reboot；这些属于 Internal V1-B，并已由业务 Owner 于 2026-08-26 确认完成。仓库没有相应外部执行明细时不得反向伪造证据。

# 10. Internal V1-B：公司服务器真实部署验收

## 当前状态：业务 Owner 于 2026-08-26 确认完成

目标环境：

```text
公司服务器
+ 公司内部网络
+ 不对公网开放
```

V1-B 直接使用 V1-A 已固化的一条启动命令，不重新拆分部署流程。最低验收：浏览器能访问前端、live/ready 正常、Migration 到 head、API/Worker/Scheduler 启动、宿主持久目录和真实 Secret 权限正确。

随后必须做真实业务 Smoke：

```text
1. 浏览器进入采集运行中心
2. 导入测试 Excel
3. Import Job queued → running → succeeded
4. Batch 统计正确
5. 查看入库内容 → 声音广场
6. 打开 Content 详情
7. 少量真实 AI Analysis
8. Excel Export + 下载 Artifact
9. 有界 TikHub Collection Run
10. 重启目标容器并确认数据仍在
11. 宿主机 reboot 后恢复运行
```

还要确认 `env.production` 和运行时 Secret 没有出现在 Git、镜像、页面、日志；公司浏览器只通过批准的内网地址访问；PostgreSQL 仍无普通客户端网络入口。TikHub/LLM 真实 Smoke 不进入普通 CI，执行时保持请求数和费用有界。

据业务 Owner 的完成确认，**AIMA_UGC 内网 V1 已上线。** 该外部验收确认不等于仓库持有每条服务器命令/日志，也仍不能定义成完整 Production Security / DR 已闭环。

# 11. 第一版明确延期的 Backlog

以下能力继续保留，不在 Internal V1-A / V1-B 中为了“顺便完善”扩大范围。

## 11.1 Authentication / Authorization

后续仍按 `External Identity Provider → Authentication Adapter → Principal/AuthContext → Authorization` 实现。暴露公司网络之外、需要用户权限/审计、敏感资源细粒度保护时重新成为前置门禁。

## 11.2 Legacy Migration（已转入 Stage 12）

内网 V1 上线时从新系统开始、未迁移旧历史数据。2026-08-26 业务 Owner 已解除延期，当前按 [`03_4000万历史数据迁移实施方案.md`](03_4000万历史数据迁移实施方案.md) 独立实现；这不代表 Legacy Exporter、历史 Version/Metric 或 4000 万实际对账已经完成。

## 11.3 RPO / RTO 与协调 Backup/Restore

完整设计仍有效，但不阻塞内网 V1。后续需要冻结 RPO、RTO、maintenance、写屏障、PostgreSQL + Artifact coordinated backup set 和 restore verification。

## 11.4 Retention / 容量 / Soak

上线后通过 PostgreSQL、Artifact、日志、Job、Content 的真实增长测量再决定正式 Retention、容量和性能目标。

## 11.5 Production Release 强化

后续继续实现不可变离线 Release Bundle、固定 image digest、SBOM、签名/provenance 与完整 rollback。

## 11.6 产品扩展

后续按真实业务价值决定 Monitoring/Alert、VOC/Ticket、Web Report Center、正式 Dashboard。
