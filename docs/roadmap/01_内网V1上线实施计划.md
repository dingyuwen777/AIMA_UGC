


# 9. Internal V1-A：最小可部署环境

## 当前状态：已完成

这一阶段复用长期 Stage 11 设计，但只实现公司内网 V1 真正需要的最小可部署基础，没有提前扩成完整 Production Release。

已实现：

```text
根 Dockerfile
根 compose.yaml
env.production.example
scripts/deploy/prepare_host.py
deploy/nginx.conf
bootstrap
frontend
api
worker
scheduler
migrate
configure
postgres
```

### 9.1 管理员启动入口

当前完整 Compose Runtime 操作使用：

```bash
cp env.production.example env.production
chmod 0600 env.production
# 编辑 env.production
docker compose --env-file env.production up -d --build --wait
```

正式离线 Release 部署则使用 Release Bundle 中已经验证的镜像，并以 `--no-build --pull never` 启动；两者不能混写成同一个交付级别。

`env.production` 可以包含 TikHub/LLM API Key，因此属于敏感文件并由 Git ignore。管理员不需要手工运行 `prepare_host.py`、创建数据库/Cursor 密钥文件、单独跑 Migration/configure 或逐个启动服务。

Compose 自动编排：

```text
bootstrap completed successfully
→ postgres healthy
→ migrate completed successfully
→ configure completed successfully
→ api / worker / scheduler
→ frontend healthy
```

`bootstrap` 是一次性 root 初始化服务，完成后退出，不常驻高权限容器。`migrate` 和 `configure` 也继续是一次性独立进程；API 启动本身不修改 Schema。

### 9.2 Secret 分层

内部随机 Secret：

```text
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
```

首次由 bootstrap 自动生成到宿主持久 Secret 目录，不要求管理员填写，不静默轮换；Backend 通过 `/run/internal-secrets` 只读使用。

外部凭据：

```text
AIMA_TIKHUB_API_KEY
AIMA_LLM_API_KEY
```

管理员写入 `env.production` 后由 Compose 转成 `/run/secrets/*` Secret File，只授予需要的容器；不作为业务容器普通环境变量，也不保存进 Provider Config。Provider Config 仍只保存 `secret_ref`。

已有 PostgreSQL 18 数据但 `postgres_password` 丢失时，bootstrap fail closed，必须恢复原 Secret；禁止自动生成新密码造成数据库/应用密码漂移。

### 9.3 持久化与网络

Linux/公司服务器 canonical 模型：

```text
AIMA_HOST_ROOT
→ PostgreSQL 持久目录
→ Artifact 持久目录
→ 应用日志目录
→ 内部 Secret 目录
```

公司服务器使用：

```text
AIMA_HOST_ROOT=/data/AIMA_UGC
```

Windows Docker Desktop 叠加 `compose.windows.yaml`，Artifact/日志继续 bind 到 `AIMA_HOST_ROOT`，PostgreSQL/内部 Secret 改用 Docker-managed named volume；该本地兼容模型不是 Production Host Root/Backup 模型。

Frontend 是唯一宿主 HTTP published port；PostgreSQL/API 无宿主 PortBindings。正式 Backend/Frontend Runtime 仍非 root。

### 9.4 永久 Compose Golden Path

当前长期 Runtime Workflow 以实际 `.github/workflows/runtime.yml`、`compose.yaml` 和相关测试为准。它持续验证 canonical Compose 的 bootstrap/Migration/configure/正式进程、Secret、持久化、Readiness 和 Linux/Windows 适用边界；不要继续从已删除/重构的历史 Workflow 名称推断当前 CI 文件。

因此 Internal V1-A 的完成含义是：**仓库已经有一套经过隔离 Runner 真实验证、管理员用 `env.production` + canonical Compose 可启动的最小可部署环境。**

V1-A 本身不证明公司服务器、真实浏览器、真实 TikHub/LLM、目标容器重启和宿主机 reboot；这些属于 Internal V1-B，并已由业务 Owner 于 2026-08-26 确认完成。仓库没有相应外部执行明细时不得反向伪造证据。

# 10. Internal V1-B：公司服务器真实部署验收

## 当前状态：业务 Owner 于 2026-08-26 确认完成

目标环境：

```text
公司服务器
+ 公司内部网络
+ 不对公网开放
```

V1-B 直接使用 V1-A 已固化的 Runtime，不重新拆分业务进程。最低验收：浏览器能访问前端、live/ready 正常、Migration 到 head、API/Worker/Scheduler 启动、宿主持久目录和真实 Secret 权限正确。

随后真实业务 Smoke 的批准范围包括：

```text
浏览器业务入口
→ Excel/Data Import
→ Worker/Job
→ PostgreSQL
→ 声音广场
→ 少量真实 AI
→ Excel Export/Artifact
→ 有界 TikHub Collection
→ 目标容器重启
→ 宿主机 reboot 恢复
```

还要确认 `env.production` 和运行时 Secret 没有出现在 Git、镜像、页面、日志；公司浏览器只通过批准的内网地址访问；PostgreSQL 仍无普通客户端网络入口。TikHub/LLM 真实 Smoke 不进入普通 CI，执行时保持请求数和费用有界。

据业务 Owner 的完成确认，**AIMA_UGC 内网 V1 已上线。** 该外部验收确认不等于仓库持有每条服务器命令/日志，也仍不能定义成完整 Production Security / DR 已闭环。

# 11. 内网 V1 后仍未闭环的 Backlog

以下能力没有因为 Internal V1 完成而消失；状态必须以当前机器事实和 Roadmap 02 为准。

## 11.1 Authentication / Authorization

当前仍未正式实现。后续按 `External Identity Provider → Authentication Adapter → Principal/AuthContext → Authorization` 实现。暴露公司网络之外、需要用户权限/审计、敏感资源细粒度保护时重新成为前置门禁。

## 11.2 Legacy Migration / Stage 12

内网 V1 上线时从新系统开始、未迁移旧历史数据。2026-08-26 业务 Owner 解除延期后，Stage 12 软件能力已经完成并归档，当前已经具备：

```text
统一“导入数据” Campaign
local_upload / server_path 两类 Source
standard_observation / historical_fill_only 两类独立写入策略
Artifact / SHA-256 / 预检 / 有界 Chunk
进度 / 取消 / 重试 / 逐行账本 / 冲突留痕
手动 Analysis Run / Planner / Shard / 历史结果
```

但 Stage 12 **生产执行尚未完成**：公司服务器 500 万或批准等效比例容量演练未完成，也未获得生产 4000 万写授权，因此不能把“软件完成”写成“4000 万迁移完成”。

正式边界见：

[`03_4000万历史数据迁移实施方案.md`](03_4000万历史数据迁移实施方案.md)

## 11.3 RPO / RTO 与协调 Backup/Restore

完整设计仍有效，但未闭环。后续需要冻结 RPO、RTO、maintenance、写屏障、PostgreSQL + Artifact coordinated backup set、restore/reconciliation verification。

## 11.4 Retention / 容量 / Soak

内网 V1 可根据 PostgreSQL、Artifact、日志、Job、Content 的真实增长继续积累数据；正式 Production Retention、通用容量/性能/Soak 目标仍需独立批准和验收。Stage 12 的服务器 500 万容量演练是历史迁移专项门禁，不等于整个系统通用 Production Soak 已完成。

## 11.5 Production Release 强化

GitHub Release Workflow 基础已经实现：Linux/AMD64 构建、`images.tar`、Release/Migration Manifest、`SHA256SUMS`、`DEPLOY.md`、no-build/no-pull 离线回放，以及正式发布的 GHCR digest / Git Tag / GitHub Release 基础。

仍待完整 Production 强化：

```text
SBOM
独立签名 / 完整 provenance
协调 PostgreSQL + Artifact Backup/Restore
生产服务器 preflight / backup / migrate / start / smoke / rollback 自动化
认证授权 / HTTPS 正式入口
完整生产安全 / 容量 / 恢复验收
```

## 11.6 产品扩展

当前没有正式 `monitoring/alerts/voc/tickets/dashboard` 业务域，也没有 Web Report Center。后续按真实业务价值决定 Stage 9B Monitoring/Alert/VOC/Ticket 与 Stage 10B Web Report Center，不因为 Roadmap 中存在名字就写成已实现。
