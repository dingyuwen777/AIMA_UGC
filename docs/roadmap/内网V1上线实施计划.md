# AIMA_UGC 内网 V1 上线实施计划

本文是当前近期开发的**执行计划**，目标不是一次完成完整 Production Go-Live，而是先把现有 Stage 8 前后端做成真正可用的业务闭环，再部署到公司服务器供公司内部网络使用。

完整生产安全、离线 Release、Backup/Restore、认证授权等长期路线仍见：

- [`生产上线实施路线.md`](生产上线实施路线.md)
- [`../appendix/生产部署与离线Release方案.md`](../appendix/生产部署与离线Release方案.md)

本文优先回答：

> **从当前代码出发，下一步具体先做什么，做到什么程度可以在公司内网给真实用户使用？**

---

# 1. 已确认的第一版目标

2026-08-22 已确认：

```text
首版目标
→ 先统一现有前端与后端能力
→ 修复真实功能缺口和不一致
→ Excel 可以从页面真实导入
→ Worker 真正处理并写入 PostgreSQL
→ 导入数据可以在声音广场正常显示
→ 部署到公司服务器
→ 仅公司内部网络访问
```

首版明确不做：

```text
登录 / Authentication
角色 / Permission / 权限隔离
旧历史数据迁移
```

因此，近期开发目标不是“补齐所有未来生产能力”，而是：

```text
业务闭环正确
+ 可稳定运行
+ 内网可访问
+ 数据可持久化
+ 出问题可排查
```

# 4. Stage 8F：前后端业务闭环与上线前验收

## 4.1 Stage 8F 的定位

Stage 8 已经形成大量真实实现，包括 Contract、Job、PostgreSQL、Vue Feature。

Stage 8F 做的是：

```text
保留正确实现
→ 系统检查业务链
→ 找到真实缺口
→ 只修缺口
→ 增加真实端到端验收
```

没有重新设计一套新前端或新 API，也没有改变当前 Pydantic Contract、OpenAPI、Schema 或 Migration。

---

## 4.2 前后端能力矩阵

每一个首版业务动作按以下层级核对：

| 层 | 要检查什么 |
| --- | --- |
| 业务动作 | 用户到底想完成什么 |
| 后端 Route | 是否真的有这个 API |
| Pydantic Contract | 请求、响应、枚举、错误是否正确 |
| OpenAPI / Generated Client | 是否和后端同步 |
| Feature `api.ts` | 是否调用正确 Generated Client |
| Store | 状态、筛选、分页、轮询是否正确 |
| Page / Button | 是否真的有入口 |
| Enabled / Disabled | 页面限制是否符合后端能力和状态机 |
| Loading / Error / Success | 用户是否能理解结果 |
| 跨页面 | 操作完成后是否能找到结果 |
| Tests | Mock UI、API、Integration、Full-stack 各自覆盖什么 |

当前完整矩阵不在 Roadmap 重复维护，统一见：

[`../appendix/Stage8F前后端能力矩阵与真实验收.md`](../appendix/Stage8F前后端能力矩阵与真实验收.md)

# 5. Stage 8F 已闭环的业务区域

## 5.1 采集运行中心

首版已保证：

```text
导入 Excel
→ 能选择文件
→ POST /api/v1/import-batches
→ 创建 Batch + Job
→ 页面显示 queued / running / succeeded / failed
→ 能打开 Batch 详情
→ 失败时能看到可理解错误和 request_id / Job 信息
```

同时继续验证：

- 列表筛选与后端查询一致；
- Cursor 翻页正确；
- 轮询不会覆盖用户当前状态；
- 运行完成后统计信息正确；
- TikHub Run 只能使用后端 Capability 支持的平台/Operation；
- 创建 Run 后可以查看 Run/Scope/Job 状态；
- 页面不能出现后端实际上不支持的动作。

### 关键跨页面闭环

Import Batch 详情中的“查看入库内容”现在固定为：

```text
Batch ID
→ /voice-plaza?source_identifier=<batch_id>
→ GET /api/v1/contents?source_identifier=<batch_id>
→ PostgreSQL 来源链过滤
→ 只显示该 Batch 导入的 Content
```

这条链已经进入不 Mock `/api/v1/**` 的永久 Full-stack Acceptance。

## 5.3 声音广场

首版继续以声音广场作为“数据是否真正进入系统”的主要业务结果页面。

已闭环：

```text
Content 列表

文本搜索
内容类型筛选
发布时间筛选
来源 Batch / Run 筛选

```

平台筛选与当前五平台能力一致：

```text
小红书
抖音
微博
B站
快手
+ Excel 文件导入
```

当前 Analysis 语义继续是：

```text
pending
stale
completed
```

Vue 不创建第二套与 PostgreSQL Query 不一致的过滤逻辑。

### AI 打标

首版已有 AI 功能继续保证：

```text
选择当前页 / 指定内容 / 当前查询目标
→ 创建 Analysis Request + Job
→ 页面显示 Job 状态
→ Worker 完成后刷新 Content
→ 显示 current Analysis
```

付费 LLM 不进入普通 CI；自动测试通过 Fake/Fixture 验证 Contract、状态和页面行为。

### Excel Export

继续验证：

```text
创建 Export
→ Job
→ 完成
→ Artifact
→ 下载
```

下载未就绪时不能表现成成功空文件。

# 10. Internal V1-B：公司服务器真实部署验收

目标环境：

```text
公司服务器
+ 公司内部网络
+ 不对公网开放
```

最低验收：

```text
浏览器能访问前端
/health/live 正常
/health/ready 正常
PostgreSQL Migration 到 head
API 启动
Worker 启动
Scheduler 启动
```

然后必须做真实业务 Smoke：

```text
1. 浏览器进入采集运行中心
2. 导入一份测试 Excel
3. Import Job 从 queued → running → succeeded
4. Batch 统计正确
5. 点击查看入库内容
6. 跳转声音广场
7. 能看到导入数据
8. 打开 Content 详情
9. 重启容器
10. 再次打开页面，数据仍存在
```

还要确认：

- 应用日志能从宿主机定位；
- Secret 没有出现在 Git、镜像、页面、日志；
- PostgreSQL/Artifact/日志目录不会随容器删除；
- 服务器 reboot 后服务可以按设计恢复；
- 浏览器访问地址只在批准的公司网络范围内可达。

完成后可以定义：

> **AIMA_UGC 内网 V1 已上线。**

不能定义成：

> **完整 Production Security / DR 已闭环。**

# 11. 第一版明确延期的 Backlog

以下能力继续保留，不在 Internal V1-A / V1-B 中为了“顺便完善”扩大范围。

## 11.1 Authentication / Authorization

后续仍按：

```text
External Identity Provider
→ Authentication Adapter
→ Principal / AuthContext
→ Authorization
```

实现。

触发条件至少包括：

- 系统要暴露到公司网络之外；
- 需要区分不同用户权限；
- 需要审计具体操作人；
- Provider 配置、Raw、Export 等需要细粒度保护。

## 11.2 Legacy Migration

首版从新系统开始，允许通过 Excel 导入需要展示的数据。

当前不实现：

```text
Legacy Exporter
历史 Version / Metric 迁移
大规模历史对账
```

如果以后确有历史迁移需求，再创建独立 Migration Change。

## 11.3 RPO / RTO 与协调 Backup/Restore

完整设计仍有效，但不阻塞内网 V1。

后续需要冻结：

```text
RPO
RTO
maintenance
写屏障
PostgreSQL + Artifact coordinated backup set
restore verification
```

## 11.4 Retention / 容量 / Soak

首版不要求现在先拍死长期数字。

上线后通过真实数据增长测量：

```text
PostgreSQL
Artifact
日志
Job
Content
```

再决定正式 Retention、容量和性能目标。

## 11.5 Production Release 强化

后续继续实现：

```text
不可变离线 Release Bundle
固定 image digest
SBOM
签名 / provenance
完整 rollback
```

## 11.6 产品扩展

后续按真实业务价值决定：

```text
Monitoring / Alert

正式 Dashboard
```

# 12. 后续每个新对话如何继续

每次新会话仍按仓库规则重新恢复事实。

当前执行顺序固定为：

```text
1. 检查 Stage 8F 是否已由 main + CI 证明闭环
2. 已闭环 → 进入 Internal V1-A，不重做 Stage 8F
3. V1-A 完成 → Internal V1-B 公司服务器验收
4. 内网 V1 上线后 → 按 Backlog 优先级继续生产强化
```

如果实际代码已经变化，不能只依据本文声明“完成”；必须由当前 Contract、代码、测试和 CI 重新证明。

# 13. 一句话路线

```text
先把现有功能真的做通
→ 再把做通的系统部署到公司内网
→ 用起来以后再补完整生产强化能力
```

这比“先把所有企业级能力做完再让人使用”，也比“页面还没闭环就先部署”，都更符合当前 AIMA_UGC 的实际阶段。
