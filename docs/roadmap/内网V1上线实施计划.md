# AIMA_UGC 内网 V1 上线实施计划

本文是公司内网 V1 的近期执行路线。它不替代长期 Production Roadmap，而是回答：**从当前已经完成的业务代码出发，下一步按什么顺序把系统做成开发者能稳定运行、服务器能部署、内部用户能使用的 V1。**

长期 Production 安全、Release、Backup/Restore 等见：

- [`生产上线实施路线.md`](生产上线实施路线.md)
- [`../appendix/生产部署与离线Release方案.md`](../appendix/生产部署与离线Release方案.md)

# 1. 已确认的内网 V1 边界

公司内网 V1 当前固定：

```text
访问范围
→ 公司服务器
→ 公司内部网络
→ 不对公网开放

Authentication / Authorization
→ 首版明确延期

Legacy Migration
→ 首版明确延期
→ 第一版以新系统数据为准
→ 需要展示的旧数据可通过 Excel 正式导入
```

首版最重要的是：

```text
业务功能正确
+ 开发环境能可靠启动
+ 部署环境可重复建立
+ 数据/Artifact/日志可持久化
+ 真实业务链可验收
```

# 2. 当前执行顺序

Stage 8F 已完成前后端业务闭环与真实 Excel Browser Full-stack Acceptance。后续顺序调整为：

```text
Stage 8F
前后端业务闭环与上线前验收
→ 已完成
↓
Local Dev Bootstrap
跨平台源码开发启动收口
→ 当前前置开发单元
↓
Internal V1-A
最小 Docker / Compose / Production Config
↓
Internal V1-B
公司服务器真实部署与业务 Smoke
↓
公司内网 V1 上线
↓
生产强化 Backlog
↓
完整 Production Go-Live
```

Local Dev Bootstrap 是在本轮运行审计中确认的必要前置，不重新打开 Stage 8 业务设计。它解决的是：业务已经存在，但开发者仍需手工拼 PostgreSQL、Secret、Migration、Worker 和环境变量，导致源码环境难以稳定复现。

Internal V1-A 不应通过 Compose 把这类未收口的启动复杂度藏起来；应先让正式进程入口和源码运行方式成立，再容器化同一套运行事实。

# 4. Local Dev Bootstrap：跨平台源码开发启动收口

## 当前状态：Internal V1-A 前置单元

目标不是生产部署，而是让 Windows/Linux 源码调试只有两个正式入口：

```bash
uv run python scripts/dev/backend.py
```

和：

```bash
uv run python scripts/dev/frontend.py
```

## 4.1 Backend 完成定义

Backend launcher 应自动完成：

```text
env.local 首次创建
.runtime/data / logs / secrets
随机 PostgreSQL 本地密码
三个独立 Cursor signing key
Docker Engine 检查
PostgreSQL 18.4 本地容器创建/启动
PostgreSQL ready
Alembic upgrade head
TikHub / LLM Secret materialize
本地 TikHub Provider Config 幂等维护
正式 Worker 启动
可选 Scheduler 启动
FastAPI 启动
/health/ready 验证
当前能力摘要
```

开发者不再需要手工设置数据库 Host/Port/User/Password、目录、Cursor Key、Migration 或 Worker 参数。

## 4.2 `env.local` 边界

`env.local.example` 只暴露开发者必须决定的可选项：

```text
TikHub Base URL / API Key
LLM Base URL / Provider / Model / API Key
是否在本地启用 Scheduler
```

`env.local`：

- 首次由 launcher 自动从模板创建；
- Git 忽略；
- 只作为 dev launcher 输入；
- 不成为生产 Runtime Contract。

正式进程继续使用：

```text
AIMA_* 非敏感运行配置
+ AIMA_SECRET_DIR 下 Secret File
+ PostgreSQL Provider Config 的 secret_ref
```

TikHub/LLM 未配置时只 Warning，不阻止 Excel Import、Voice Plaza、Excel Export。

## 4.3 Worker 完成定义

`backend/src/aima_ugc/entrypoints/worker_main.py` 必须是正式常驻进程入口，而不是只导出 factory。

本地、Full-stack CI 和未来 Internal V1-A Compose 复用：

```text
python -m aima_ugc.entrypoints.worker_main
```

不再让测试专用 Worker loop 成为事实上的运行方式。

## 4.4 Scheduler 默认关闭

源码调试默认：

```text
AIMA_DEV_ENABLE_SCHEDULER=false
```

因为本地数据库可能保留 enabled Plan，自动启动 Scheduler 可能产生未预期的真实 Provider 费用。

需要测试周期采集时显式打开后仍由同一个 `backend.py` 管理。

## 4.5 Frontend 完成定义

`frontend.py`：

```text
校验 Node/npm 锁定版本
→ node_modules 缺失或 package-lock 变化时自动 npm ci
→ npm run dev
→ Vite HMR
```

本地开发不要求先 `npm run build`；production build 留给 CI/Internal V1-A。

## 4.6 验收

至少要求：

```text
Windows launcher 静态/配置入口可执行
Linux launcher 静态/配置入口可执行
真实 PostgreSQL 18.4 bootstrap
真实 Alembic upgrade head
TikHub Provider Config 只保存 secret_ref
正式 Worker entrypoint
Stage 8F Real Full-stack 使用正式 Worker 后继续通过
主 CI / Contract / Frontend Build 不回归
```

该单元完成后才进入 Internal V1-A。

# 5. Internal V1-A：最小可部署环境

## 当前状态：Local Dev Bootstrap 完成后的下一正式单元

目标是把已经收口的正式运行进程装入公司内网 V1 的可部署拓扑，而不是重新设计业务代码。

最小服务：

```text
frontend
api
worker
scheduler
migrate
postgres
```

至少实现：

```text
仓库根 Dockerfile
Compose
Frontend production build + HTTP runtime
API / Worker / Scheduler 共用同版本后端镜像
Migration 一次性执行
PostgreSQL 18 持久化
Artifact 持久化
日志持久化
生产非敏感配置
只读 Secret mount
Health / Readiness
内部网络边界
```

长期目录规划继续采用：

```text
/data/docker
/data/AIMA_UGC/postgres
/data/AIMA_UGC/runtime/data
/data/AIMA_UGC/runtime/logs
/data/AIMA_UGC/releases
/data/AIMA_UGC/shared/env
/data/AIMA_UGC/shared/secrets
/data/AIMA_UGC/backups
```

即使内网首版暂不实现完整 Backup/Restore，也不能把 PostgreSQL、Artifact 或日志放在容器临时层。

## 5.1 Provider / LLM 配置

Internal V1-A 必须正式解决新环境初始化：

```text
TikHub Secret
→ 只读 Secret mount

TikHub Provider Config
→ PostgreSQL 保存非敏感配置 + secret_ref

LLM API Key
→ 只读 Secret mount

LLM Base URL / Provider / Model
→ Production 非敏感配置
```

不能依赖本地 `env.local` 或手工 SQL 作为服务器初始化方式。

> **AIMA_UGC 公司内网 V1 已上线。**

> **完整 Production Security / DR / Release Governance 已闭环。**

# 8. 内网 V1 明确延期事项

当前不让以下长期能力阻塞内网首版：

```text
Authentication / Authorization
旧历史数据 Migration
完整 RPO / RTO
协调 PostgreSQL + Artifact Backup/Restore
长期 Retention / 容量 / Soak 数字
不可变离线 Release Bundle / SBOM / 签名
完整生产 Rollback 演练
Monitoring / Alert
VOC / Ticket
Web Report Center
正式 Dashboard / 智能洞察
```

这些能力仍然有效；内网 V1 上线后按真实业务价值和风险进入 Production Backlog。
