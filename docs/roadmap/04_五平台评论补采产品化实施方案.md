# 五平台评论补采产品化实施方案

- 状态：Active
- 风险等级：L3（五平台 Provider 身份解析、评论采集语义、网页操作和持久恢复的跨层产品能力，涉及付费外部请求与公共 HTTP Contract）
- 目标：用户在网页端通过同一个“辅助补采”入口，对小红书、抖音、微博、B站、快手已有导入内容正确补采 Provider 可见的一级评论与回复；各平台先取得可证明的评论目标身份，完整分页、正确挂载、可恢复、可观测，且微博 `ttarticle` 等特殊 URL 不误请求、不抓错帖。
- 退出条件：五个平台分别通过本文成功标准、测试矩阵、真实 Probe、网页全栈验收、Completion Audit、Review 与 CI，并对当前失败样本完成受控重放或给出可审计的不可获取原因。
- 依赖：TikHub 当前可用接口、上游 Excel 能提供的五平台原生身份字段或可精确解析链接、各平台真实样本、Provider 费用与限流授权。

## 1. 背景与已确认现状

### 1.0 五平台当前正式能力

当前 [`backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py) 已声明五个平台都具有 `content_detail`、`comments` 和 `sub_comments` Capability；[`backend/src/aima_ugc/adapters/providers/tikhub/runtime.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/runtime.py) 也已分别构造评论、回复和分页请求。正式 lookup identity 为：

| 平台 | 评论目标 typed identity | 一级评论主 Operation | 回复主 Operation |
| --- | --- | --- | --- |
| 小红书 | `note_id` | `get_note_comments` | `get_note_sub_comments` |
| 抖音 | `aweme_id` | `fetch_video_comments` | `fetch_video_comment_replies` |
| 微博 | `status_id` | `fetch_status_comments` | `fetch_post_sub_comments` |
| B站 | `av_id` 或 `bv_id` | `fetch_video_comments` | `fetch_reply_detail` |
| 快手 | `photo_id` | `fetch_video_comment` | `fetch_video_sub_comments` |

这证明“每个平台都有代码”不等于“网页端对所有导入 URL 都能正确补采”。当前 Eligibility 只接受已经具备上述 typed identity 的内容；短链、分享链接、微博 `ttarticle` 或来源哈希如果尚未解析成原生 ID，会被排除。此次产品化必须同时验证五个平台的身份解析、一级评论分页、回复补齐、Coverage、持久恢复与网页闭环。

### 1.1 微博 `ttarticle` 当前数据事实

当前评论补采输入共 1597 条记录，其中只发现 1 个 `ttarticle` URL：

```text
https://weibo.com/ttarticle/p/show?id=<article_id>
```

该记录的 `external_content_id` 和 `alternate_ids.source_article_id` 都是来源系统哈希，没有微博数字 `status_id`，也没有作者 `uid`。因此它不是现有 TikHub 评论接口可直接消费的身份。

### 1.2 微博 `ttarticle` 当前代码事实

当前调用链为：

```text
Excel URL
→ imports/identity.py
→ CanonicalContentV1.external_content_id + alternate_ids
→ tikhub/runtime.py 选择 lookup identity
→ /api/v1/weibo/app/fetch_status_comments?status_id=...
```

已确认的缺口：

1. [`backend/src/aima_ugc/adapters/providers/imports/identity.py`](../../backend/src/aima_ugc/adapters/providers/imports/identity.py) 不识别 `/ttarticle/p/show?id=...`，没有保存 typed `ttarticle_id`；
2. [`backend/src/aima_ugc/adapters/providers/tikhub/runtime.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/runtime.py) 在缺少 `alternate_ids.status_id` 时会回退到 `external_content_id`；
3. [`backend/src/aima_ugc/adapters/providers/tikhub/operations/weibo.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/operations/weibo.py) 的正式一级评论 Operation 只接受 `status_id`；
4. 当前补采调试入口已增加请求前保护：非数字微博身份不再发请求，避免哈希误请求。这个保护是安全兜底，不是长文章能力的最终实现；
5. `content_external_ids.id_type` 是开放文本，Canonical `alternate_ids` 也是开放字典。增加 `ttarticle_id` 本身预计不需要数据库 Migration，但最终仍须以 Change 内的新鲜 Schema/Contract 检查为准。

### 1.3 微博 `ttarticle` 2026-09-12 本地真实 Probe 结论

使用项目现有本地 Secret、生产 TikHub Transport、单并发和单页请求完成了两组 A/B 及结构核对；本轮共发送 29 次无自动重试请求，未落盘 Raw，未输出 Secret、正文或账号信息。因候选 Web V2/App Search endpoint 尚未全部进入当前 Pricing Catalog，本轮不虚报精确费用；实施前必须先补价格核验和费用上限。

| 样本 | 请求方式 | 结果 |
| --- | --- | --- |
| 当前 Excel `ttarticle` | 去掉 `230940` 前缀后请求 App Detail/Comments | HTTP 400 |
| 当前 Excel `ttarticle` | 完整文章 ID 请求 Web V2 Detail/Comments | HTTP 200，但业务层 `data.ok=0` |
| 公开仍可访问的 `ttarticle` 对照样本 | 去掉 `230940` 前缀后请求 App Detail/Comments | HTTP 400 |
| 公开仍可访问的 `ttarticle` 对照样本 | 完整文章 ID 请求 Web V2 Detail/Comments | HTTP 200，但业务层 `data.ok=0` |
| “爱玛”文章搜索 | Web `fetch_search` + `search_type=21` | HTTP 404 |
| “爱玛”文章搜索 | App `fetch_search_all` + `search_type=21` | HTTP 200，但返回外部网页文章卡片，不提供可用于微博评论的父 `status_id` |

结论：

- `230940{数字}` 不是可以安全截断成 `status_id` 的已验证编码；
- TikHub 当前正式文档没有“按 `ttarticle_id` 获取长文章评论”或“按 `ttarticle_id` 解析父微博”的接口；
- 现有 App/Web V2 微博详情和评论接口消费的是帖子 ID，不消费长文章 ID；
- 只修改 `operations/weibo.py` 或把完整文章 ID 改发 Web V2，都会继续失败；
- 标题、正文、作者昵称的模糊搜索不能证明身份一致，禁止作为自动补采依据。

- [TikHub 当前 OpenAPI](https://api.tikhub.io/openapi.json)
- [TikHub Python SDK 接口参考](https://github.com/TikHub/TikHub-API-Python-SDK/blob/main/docs/reference.md)

### 1.4 当前网页端事实与缺口

当前已经存在基础产品入口，不需要再造一套调试页面：

```text
采集运行中心
→ 新建辅助补采
→ 基于已有批次补采
→ 选择数据导入来源与一个或多个平台
→ 勾选评论/二级回复
→ POST /api/v1/collection-runs
→ 后端返回 202 + run_id/job_id
→ 前端打开任务详情并每 5 秒轮询
```

现有实现位置：

- [`frontend/src/features/import-batches/pages/CollectionRuntimePage/components/TikHubSupplementDrawer.vue`](../../frontend/src/features/import-batches/pages/CollectionRuntimePage/components/TikHubSupplementDrawer.vue)：已有补采按钮、数据来源、平台、评论和二级回复选项；
- [`frontend/src/features/import-batches/api.ts`](../../frontend/src/features/import-batches/api.ts) 与 [`frontend/src/features/import-batches/store.ts`](../../frontend/src/features/import-batches/store.ts)：已通过生成 Client 创建 Run、读取 Eligibility、打开详情并轮询；
- [`backend/src/aima_ugc/bootstrap/api.py`](../../backend/src/aima_ugc/bootstrap/api.py)：已有 Eligibility、创建 Run、读取 Run 和统一运行列表 API；
- [`frontend/src/features/import-batches/pages/CollectionRuntimePage/components/CollectionRunDetailDrawer.vue`](../../frontend/src/features/import-batches/pages/CollectionRuntimePage/components/CollectionRunDetailDrawer.vue)：已有进度、评论总数和平台 Scope 展示。

当前仍缺：

1. Eligibility 只返回已有可用 lookup identity 的 `target_count`；只有短链、分享链接、来源哈希或 `ttarticle_id` 而尚未取得评论目标 ID 的内容，可能直接从可选平台消失，用户不知道原因；
2. Run Detail 只有通用成功/失败/评论数，无法区分“身份解析中、解析失败、一级评论完整、回复部分缺失”；
3. 前端虽然提示失败后可重试，但当前没有 Collection Run 重试 API 和按钮；
4. 没有逐平台覆盖“网页按钮 → API → 持久 Job → Provider → PostgreSQL → 内容详情评论”的五平台全栈验收。

## 2. 目标与非目标

### 2.1 目标

1. 小红书、抖音、微博、B站、快手的 URL/分享文本导入时，识别并保留已有原生 ID、短链或内容定位身份，不因无法立即补采而丢失原因；
2. 评论抓取前统一解析 `CommentTargetIdentity`，不再把 Canonical 主身份、来源哈希或分享定位符等同于 Provider lookup ID；
3. 已有可靠 `note_id`、`aweme_id`、`status_id`、`av_id/bv_id` 或 `photo_id` 时，直接复用对应平台现有评论主链；
4. 只有短链、分享链接或微博 `ttarticle_id` 时，自动进入该平台的精确解析流程；
5. 解析成功后持久化 typed comment target ID、来源 Attempt/Raw 和观察时间，再抓一级评论与回复；
6. 解析失败、歧义、内容不可见或 Provider 不支持时，输出平台无关且可审计的 Coverage/Failure，不请求错误 ID、不抓错内容；
7. 五个平台的一级评论分页、回复补齐、恢复、幂等、费用和 Raw 复用遵守同一门禁，并保留各平台真实分页/字段差异；
8. 正式 Collection 与 `imports_test` 调试入口复用同一套生产身份解析、Operation、Mapper 和评论实现；
9. 上线后用户只通过网页端即可选择任意一个或多个平台，创建、跟踪、重试补采任务并查看最终评论，不依赖命令行或 `imports_test`；
10. 用五平台逐项验收证明前端暴露的能力确实由后端、Worker、Provider 和数据库支持，而不是仅凭 Capability 声明或按钮存在判定完成。

### 2.2 非目标

- 不通过标题、正文、作者昵称或发布时间做模糊匹配；
- 不把所有引用该文章的转发/分享微博评论合并成“文章评论”；
- 不引入浏览器自动化、Cookie 爬虫或绕过任一平台访问控制；
- 不隐藏跨 TikHub App/Web/API family fallback；
- 不升级 Python、TikHub SDK 或其他依赖；
- 不做与评论补采无关的 Provider 重构；允许为五个平台修复必要的身份解析、Eligibility、分页、Mapper、Coverage 和恢复缺陷；
- 不承诺抓到已删除、私密、仅粉丝可见、关闭评论、地区/登录限制或 Provider 未暴露的数据。

## 3. 必须保持的评论语义

五个平台统一采用以下语义：评论必须挂载到被导入的同一个平台内容对象；只有当 Provider lookup ID 与该内容存在可证明的精确关联时才允许请求。标题、正文、作者昵称、发布时间或搜索排序只能帮助人工调查，不能自动建立评论归属。

微博 `ttarticle` 是文章对象，现有 TikHub 评论接口抓的是微博帖子评论。该特例还必须固定“对应评论”的定义：

```text
推荐定义：只抓 Provider 明确声明为该文章原始发布载体的唯一父微博评论线程。
```

不得选择：

- 搜到标题相同的任意微博；
- 任意包含文章链接的转发/分享微博；
- 多个分享帖评论的无差别聚合。

如果 Provider 返回多个候选父微博而没有“原始/主发布”标识，则状态必须是 `ambiguous`，由数据源补齐身份或人工确认，不能自动选择互动量最高、时间最早或搜索排序第一的记录。

## 4. 推荐架构

### 4.1 身份分层

保持三种身份分离：

| 身份 | 用途 | 五平台示例 |
| --- | --- | --- |
| Canonical 主身份 | AIMA 内稳定去重和关联 | `external_content_id`，可能来自原生 ID，也可能是来源系统稳定哈希 |
| 内容/链接定位身份 | 保存可用于精确解析原内容的事实 | `share_text`、`douyin_share_url`、`ttarticle_id`、`bilibili_share_url`、`kuaishou_share_url` |
| 评论目标身份 | 调 TikHub 对应平台评论接口 | `note_id`、`aweme_id`、`status_id`、`av_id/bv_id`、`photo_id` |

禁止让内容/链接定位身份覆盖 `external_content_id`，也禁止在未经精确解析时把它伪装成评论目标身份。

各平台身份与解析边界如下：

| 平台 | 可直接评论的 typed identity | 需要解析的典型输入 | 解析成功条件 |
| --- | --- | --- | --- |
| 小红书 | `note_id` | `xhslink.com` 短链、`share_text` | 跳转或正式 Provider 响应唯一给出同一笔记的 `note_id` |
| 抖音 | `aweme_id` | `v.douyin.com` 等 `douyin_share_url` | 唯一解析为同一视频的 `aweme_id` |
| 微博 | 数字 `status_id`，或可确定转换的 BID | `ttarticle_id`、视频/分享 URL、来源哈希 | 标准 URL 经 BID→MID，或正式数据唯一给出原始父微博 `status_id` |
| B站 | `av_id` 或 `bv_id` | `b23.tv` 等 `bilibili_share_url` | 唯一解析为同一视频的 AV/BV 身份 |
| 快手 | `photo_id` | 分享文本、短链或 `kuaishou_share_url` | 唯一解析为同一作品的 `photo_id` |

建议增加内部只读结果模型，不改变公共 Canonical V1 字段：

```text
CommentTargetResolution
├─ state: resolved | unavailable | ambiguous | failed
├─ canonical_external_content_id
├─ platform
├─ lookup_id_type: note_id | aweme_id | status_id | av_id | bv_id | photo_id | null
├─ lookup_id: string | null
├─ source: imported_typed_id | canonical_permalink | provider_exact_link | provider_exact_mapping | null
├─ provider_attempt_id/raw_artifact_id（Provider 解析时）
└─ stop_reason/failure_code
```

不使用模糊 `confidence` 分数；只有可证明的精确关联才能进入 `resolved`。

### 4.2 五平台统一自动路由

```text
导入内容
→ 是否已有该平台允许的 typed comment target ID？
  → 是：做格式和平台归属校验后直接抓评论
  → 否：是否有受支持的短链、分享链接或内容定位身份？
      → 否：identity_unavailable，不发 Provider 评论请求
      → 是：进入平台专属精确解析
          → 唯一解析：持久化 typed ID 后抓评论
          → 多个候选或归属冲突：identity_ambiguous
          → Provider/来源无映射：identity_unavailable
          → 网络结果未知：identity_resolution_unknown，可由新 Attempt 重试
```

Runtime 必须按 `platform + lookup_id_type` 白名单选择参数，删除“任意 `external_content_id` 回退为评论 ID”的通用路径。短链解析必须校验允许的 host、跳转次数、每次重定向目标和最终 URL，不能放宽现有 SSRF/Origin allowlist。

微博子路由为：

```text
微博内容
→ alternate_ids.status_id 存在且为数字？
  → 是：直接抓评论
  → 否：标准 /{uid}/{bid} 或 /status/{bid}？
      → 是：现有 Base62 → MID，抓评论
      → 否：alternate_ids.ttarticle_id 存在？
          → 否：identity_unavailable，不发评论请求
          → 是：进入 ttarticle 精确解析
              → 得到唯一父 status_id：持久化后抓评论
              → 多个无主次候选：identity_ambiguous
              → Provider/来源无映射：identity_unavailable
              → 网络未知：identity_resolution_unknown，可重试新 Attempt
```

### 4.3 微博 `ttarticle` 精确解析策略优先级

按可靠性从高到低：

1. **上游直接提供**：Excel 增加原始发布微博 URL、数字 `status_id` 或可转换 BID。成本最低、确定性最高，推荐作为正式保障方案；
2. **同一来源记录已有精确关联**：导入字段中文章 ID 与原始微博 ID 同时存在；
3. **TikHub Provider 精确映射**：仅当 TikHub 新增按 `ttarticle_id` 返回唯一父 `status_id` 的正式接口，或真实验证证明 `fetch_user_articles/fetch_user_posts` 在已知作者 `uid` 下能按完整 `ttarticle_id` 精确匹配并返回父 `status_id`；
4. **无法解析**：如当前样本既无 `status_id`、作者 `uid`，TikHub 也无解析接口，应返回 `identity_unavailable`。这是数据能力边界，不是可以用猜测修复的代码问题。

不推荐直接抓微博网页内部接口：它需要新增非 TikHub Provider、Cookie/登录态、反爬与合规边界，稳定性和运维成本显著高于让上游补齐 `status_id` 或让 TikHub提供正式接口。如业务必须采用，需单独 L3 决策和安全评审，不夹带进本 Change。

### 4.4 网页端到后台的正式闭环

复用现有页面和 `CollectionRunCreateRequest`，各平台身份解析由后端自动执行，不要求用户理解或手填原生 ID：

```text
用户选择导入来源
→ Eligibility 按平台返回直接可补采、需解析、不可解析数量
→ 页面展示五平台能力和阻塞说明
→ 用户勾选“评论/二级回复”并创建任务
→ POST /api/v1/collection-runs
→ collection.run.v1 持久 Job
→ identity_resolution
→ content_detail/comments/sub_comments
→ PostgreSQL Content/Comment + Coverage
→ Run Detail 轮询展示进度与分类结果
→ 完成后从声音广场内容详情查看评论
```

前端不直接调用 TikHub，也不携带 Provider Secret、文章 ID 或评论分页游标；这些都留在后端 Provider/Job 边界。

为保持已有请求兼容，默认不新增“短链/长文章”开关：用户勾选评论后，后端对已有原生 ID 的内容直接抓取，对受支持的分享/短链和 `ttarticle` 自动解析。需要补充的是响应侧可观测性：

- Eligibility 保留既有 `targets[].target_count` 语义，新增 Provider-neutral diagnostics，至少包含 `direct_target_count`、`resolution_candidate_count`、`blocked_count` 和稳定 `block_reasons`；
- Run/Scope 响应增加可选 Coverage 汇总，至少区分身份已解析、身份不可用/歧义、一级评论完整、评论部分完成和回复短缺；
- 前端将稳定错误码映射为可操作中文说明，不显示 Secret、Provider Raw 或内部文件路径；
- terminal partial/failed Run 提供“重试未完成项”按钮；重试必须创建新的 Attempt/Job 追溯，复用已校验 Raw，不重跑已经完成的内容；
- queued/running Run 是否同时提供取消按钮，以当前持久 Job 取消能力和 Change 事实为准，但不得用页面假取消替代后端状态转换。

推荐新增 `POST /api/v1/collection-runs/{run_id}/retry-incomplete`：仅允许对可重试终态调用，服务端根据原 Run 冻结的平台、Provider Config、来源范围和 Coverage 生成新 Run/Job，返回 202 与新的 `run_id/job_id`，并保存 `retry_of_run_id` 追溯。客户端不自行重组失败内容 ID，不直接重放 Provider 请求；并发重复提交须由请求幂等键或服务端唯一约束合并。最终端点名称和字段在 L3 Change 中以现有 Job/Run Contract 新鲜检查后固化。

## 7. 实现规则与安全边界

1. Secret 只从现有 Secret 文件/本地调试 `.env` 读取，禁止进入命令输出、日志、Fixture、Raw 元数据、Change 或文档；
2. TikHub 请求只发往批准的 HTTPS Origin；
3. 一次 Transport send 恰好一次网络请求，不隐藏重试；
4. 解析与评论是不同的 Provider action/Attempt，费用和失败分别记录；
5. 已校验完整 Raw 存在时禁止再次请求；
6. 解析结果必须来自精确字段关联，不以文本相似度、搜索排序或时间邻近推断；
7. Provider 返回 HTTP 200 但平台业务成功标志为失败时必须判失败，不能当作空评论成功；微博 `data.ok=0` 是已确认实例，不得把该字段机械套到其他平台；
8. 评论 Mapper 使用原 Canonical 内容身份挂载结果，同时保留实际平台 lookup identity 的来源证据；
9. 不把 `unavailable` 写成 `complete`，不把回复短缺写成完整覆盖；
10. 真实 Probe 默认关闭，显式运行时有请求数、费用和并发上限。

## 9. 成功标准与验收

### 9.1 可承诺的完成标准

- 五个平台 100% 的已支持合法 URL/分享格式被识别为原生 comment target identity 或明确的待解析定位身份；新增格式必须由测试和接口台账定义，不能用“看起来像链接”代替边界；
- 0 次把来源哈希、未解析短链、分享文本或 `ttarticle_id` 误发为平台评论 ID；
- 0 次基于模糊匹配、搜索排序或跨平台 ID 猜测抓取其他内容的评论；
- 五个平台解析成功的记录都从第一页抓到 Provider exhausted，并按各平台父子关系补齐 Provider 可见回复；
- 所有中断可从已持久 Raw/游标恢复，不重复已完成外部请求；
- complete / partial / unavailable / failed 与真实覆盖一致；
- 当前失败样本经过受控 replay，结果可追溯；
- 上线构建中，网页端能从 Batch/Campaign 选择小红书、抖音、微博、B站、快手任意组合并创建评论补采 Run；
- API 返回 202、任务可在统一运行列表恢复、进度和 Coverage 可见；
- 可重试失败能从页面只重试未完成项；
- 完成后用户能在声音广场内容详情看到数据库中的一级评论与回复；
- 前端不调用 TikHub、不暴露 Secret/Raw/分页游标，也不依赖本地脚本和 staging 文件。

### 9.2 不能承诺的范围

“所有评论”只能指 **TikHub/目标平台在请求时实际可见并返回的评论**。以下数据不能保证获得：

- 已删除、审核隐藏、私密或仅特定账号可见内容；
- 作者关闭评论、地区/登录/风控限制；
- TikHub 未提供的长文章评论接口或未返回的历史分页；
- 页面显示总数但平台接口或 TikHub 不再暴露的评论/回复；
- 只有 `ttarticle_id` 且不存在精确父 `status_id` 映射的数据。

这些情况必须有明确 `stop_reason` 和证据，不能用空数组冒充完整抓取。

## 10. 兼容、部署与回滚

- 五平台已有合法原生 ID 继续使用现有评论主链；
- 分享链接定位身份及 `ttarticle_id` 作为 alternate identity，不改变已有 Canonical 主键；
- 未证明某平台新解析 Operation 前不改变该平台正式 Capability；
- 预计无数据库 Migration、无依赖升级、无 Job type 变化；
- 回滚时可按平台关闭新增解析入口，保留已写入的 typed identity、来源和 Raw，不删除已采评论；
- 回滚后继续保留请求前身份保护，绝不恢复“任意 external ID 直接发评论接口”的旧行为。
