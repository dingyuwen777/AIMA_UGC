# 搜索与品牌车型过滤实施路线

- 状态：Active
- 目标：把“Provider 搜索条件”和“内容入库前监测对象过滤/分类”拆成两套清晰职责：Keyword Pack 只提供 Search Terms；品牌与车型目录负责统一过滤和分类；Excel 与 TikHub Discovery 复用同一个 Provider-neutral Brand/Vehicle Resolver，并最终让管理员配置、采集策略、数据导入、声音广场和导出使用同一套真实事实。
- 退出条件：Stage 1—7 全部完成；品牌与车型主数据、统一 Resolver、Excel/TikHub Filter、声音广场查询和导出形成完整闭环；旧 Keyword Pack↔车型、Collection Discovery 车型选择和 Global Keyword Relevance 旧职责完成安全退出；旧 Content 完成批准范围内的可恢复重分类；长期有效知识同步到 Product/Blueprint/Appendix/Operations/模块 README 后，本 Roadmap 从 live `docs/roadmap/` 退出。
- 依赖：当前模块化单体、PostgreSQL + Alembic、Canonical/Content Owner 主链、现有 Keyword Pack/Collection/Excel Import/Vehicle Catalog/Voice Plaza 能力；每个 Stage 开工时必须重新读取最新 `main`、当前 Migration head、Contract、相关 Figma 与适用项目规则，不能把本文中的未来设计写成当前已实现事实。

本文是已经批准但尚未完成的实施路线，不是当前实现说明。当前长期技术边界继续由 [`docs/blueprint/07_技术决策与实施门禁.md`](../blueprint/07_技术决策与实施门禁.md) 及相关 Blueprint 维护；精确 Schema、HTTP 字段、生成 Client、Migration head 和代码路径以各 Stage 开工时的机器事实为准。

## 1. 已确认的目标语义

### 1.1 Search 与 Filter 分离

系统以后明确区分：

```text
搜索条件
└─ Keyword Pack / Search Terms
   └─ 只负责告诉支持 Search 的数据来源“去搜什么”

内容过滤条件
└─ Brand + Vehicle Catalog
   └─ 只负责判断拿回来的内容是不是监测对象
   └─ 同一次匹配同时完成品牌/车型分类
```

固定语义：

- Keyword Pack 不再承担品牌归属、车型归属或入库前 Rule Relevance；
- 品牌识别词/品牌别名、车型识别词/车型别名不叫“搜索关键词”，避免重新和 Keyword Pack 混淆；
- TikHub **Discovery** 同时需要 Search + Filter；
- Excel/File Import 已经拿到本地文件，不执行远程 Search，因此只需要 Filter；前端最终把 Search 区域显示为“不适用于 Excel 文件导入”并置灰；
- TikHub Batch Supplement/Enrichment 处理已经接受的 Content，不重新做 Discovery Search，也不重新决定该 Content 是否允许入库。

### 1.2 Brand 与 Vehicle

目标关系固定为：

```text
Brand 1:N Vehicle
```

`vehicle_models.brand_id` 是车型品牌归属的唯一事实。不要再建立 Brand↔Vehicle N:N 关联。

内容本身仍然允许：

```text
Content N:N Brand
Content N:N Vehicle
```

通过 Evidence 表表达。一篇帖子可以同时提及爱玛和竞品，也可以同时命中多个车型；不得把 `brand_name`、`is_competitor`、单个 `vehicle_name` 之类标量塞进 Content 作为第二事实源。

### 1.3 首版 Filter Scope

首版只提供两种过滤范围：

```text
all_active
→ 当前任务创建时读取所有 active Brand
→ 自动包含这些 Brand 下全部 active Vehicle

selected
→ 用户选择一个或多个 Brand
→ 自动包含所选 Brand 下全部 active Vehicle
```

第一版不在 Collection Plan / Excel Import 中逐个选择车型。车型粒度只用于品牌目录管理以及声音广场结果查询，不重新成为数据来源层的第二套范围 Owner。

默认：

```text
filter_mode = all_active
```

### 1.4 Snapshot 与统一 Resolver

任务创建时冻结 Brand/Vehicle Catalog Snapshot；Worker 只使用冻结快照：

```text
09:00 创建 Run / Import → Catalog vN
11:00 管理员修改目录 → Catalog vN+1

09:00 已创建任务继续使用 vN
新任务使用 vN+1
```

Excel 和 TikHub Discovery 必须复用同一个 Canonical 之后的 `BrandVehicleResolver`。Resolver 首版只做确定性 Alias 匹配，不访问数据库、不发网络、不调用 AI；跨实体歧义 Alias 不自动猜测归属。

### 1.5 Global Keyword Relevance 与 AI Relevance 的边界

本 Roadmap 最终退出的是：

```text
Global Keyword Relevance
→ Keyword Pack
→ Canonical 后再做一次确定性关键词入库过滤
```

必须继续保留：

```text
Analysis Result.relevance
Content effective_relevance
AI relevance taxonomy
人工相关性复核
声音广场 AI/人工 relevance 展示和筛选
```

品牌/车型 Filter 回答“是不是监测对象”；AI/人工 Relevance 回答“已进入内容库的内容在分析语义上是否相关”。两者不能互相替代。

## 2. 跨 Stage 硬门禁

### 2.1 Expand first，Cleanup last

任何 Stage 都不得因为“新代码已经不用旧结构”而提前删除旧 Schema。固定顺序：

```text
DB Expand
→ 新 Backend 能力
→ 新 Runtime/Contract
→ Frontend 切换
→ 旧数据重分类
→ Cleanup Migration
```

Stage 1 只允许 Expand；删除 `keyword_pack_vehicle_models`、`collection_plan_vehicle_models`、`global_relevance_config` 等旧结构统一留到 Stage 7。

### 2.2 每个 Stage 合并到 main 时都必须保持可恢复

本文允许后端早于最终 Vue UI 开发，但阶段性 main 不能故意进入不可解释状态。公共 Contract 需要跨 Stage 迁移时，使用明确兼容窗口、版本化 Payload/API 或其他当前项目已有的等价机制；不得让新 Worker 错读旧 queued Job，也不得靠静默忽略旧字段维持“兼容”。

### 2.3 Mapper 边界不改变

正式主链继续遵守：

```text
Provider / File Reader
→ Raw / Source Artifact
→ Operation / Mapper
→ Canonical
→ Decision / Filter
→ Owner
→ PostgreSQL
```

Brand/Vehicle Resolver 位于 Canonical 之后；Mapper 不查数据库、不调 AI、不承担品牌业务判定。当前总原则见 [`docs/blueprint/02_采集系统与数据标准化.md`](../blueprint/02_采集系统与数据标准化.md)。

### 2.4 各 Stage 是独立施工单元

不要为整个 Roadmap 建一个长期占用数周/多 PR 的巨型 Change。每个 Stage 开工时：

1. 重新读取 Roadmap、本 Stage 上游和当前 `main`；
2. 重新确认当前 Migration/Contract/代码/Figma 是否漂移；
3. 创建或复用**本 Stage**所需的 Issue/Change/PR；L3 Stage 必须有持久施工契约、Migration/兼容/回滚和完成门禁；
4. 只实施当前 Stage 及其明确前置，不静默启动下一 Stage；
5. 用当前 revision 的直接 Evidence 验收；
6. 合并后再依据真实证据更新本 Roadmap 状态。

后续 PR 可以把本文件作为稳定 Requirement Source：

```text
Requirement-Source: docs/roadmap/04_搜索与品牌车型过滤实施路线.md
```

# Stage 1：数据模型基础

## 目标

先建立新的数据库结构和 SQLAlchemy Schema 能力，为后续 Backend 提供稳定数据基础；**不改变当前业务 Runtime 行为，不删除任何旧结构，不实现 Brand API/Resolver/前端。**

Stage 1 属于 Schema/Migration L3。

## 开工前必须重新读取

至少重新核对：

- 当前 Alembic head 和最新 Vehicle/Content Migration；
- [`backend/src/aima_ugc/modules/vehicles/tables.py`](../../backend/src/aima_ugc/modules/vehicles/tables.py)；
- [`backend/src/aima_ugc/adapters/persistence/postgres/vehicles.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/vehicles.py) 中当前目录/证据约束；
- [`backend/src/aima_ugc/database_schema.py`](../../backend/src/aima_ugc/database_schema.py)；
- 当前数据库集成测试、Table Owner 检查和 Migration CI；
- 与本 Stage 路径重叠的 Active Change/PR。

本文不固定“下一条 Migration 一定叫 0044”；正式 Revision 必须基于开工时最新 head。

## 目标 Expand Schema

### A. 复用 `vehicle_catalog_versions`

不再建立第二个 Brand Catalog Version。把现有 Vehicle Catalog Version 扩展为 Vehicles Domain 的统一品牌/车型目录版本，后续 Brand、Vehicle、Alias 和 Brand 归属变化都由同一版本序列冻结。

### B. 新增 `vehicle_brands`

至少承载：

```text
稳定 id / code
展示名称 display_name
角色 role = owned | competitor | other
生命周期 status
version
catalog_version
created_at / updated_at
```

`code` 是稳定机器身份；不得依赖显示名称作为外键。

### C. 新增 `vehicle_brand_aliases`

至少承载：

```text
id
brand_id
text
normalized_text
created_at
```

同 Brand 下 normalized alias 必须唯一；跨 Brand 不强制全局唯一，因为歧义应该由后续 Resolver 显式发现，而不是在 Schema 中伪造唯一性。

### D. `vehicle_models` 增加 `brand_id`

Expand 阶段：

```text
brand_id = nullable FK → vehicle_brands.id
```

并建立后续按 Brand 读取 active Vehicle 所需索引。

这里必须 nullable，因为现有车型归属尚未逐条确认。Migration 不得自动假设“旧车型全部属于爱玛”，也不得从旧 Keyword Pack↔Vehicle N:N 关系猜 Brand Ownership。

### E. 新增 `content_brand_evidence`

它与现有 `content_vehicle_evidence` 并行，用于后续持久化一篇 Content Version 为什么被识别为某 Brand。至少为以下未来来源留出清晰语义：

```text
alias_match
vehicle_match
manual_review
import（只在未来存在可信结构化 Import Brand 事实时使用）
```

需要支持：

- content_id + content_version；
- brand_id；
- matched_text / source_field；
- 由车型推导时的 `derived_vehicle_model_id`；
- catalog_version；
- confidence；
- active/manual-lock 语义；
- 按 Content 和按 Brand 的有效证据查询索引；
- 可幂等追加的身份约束。

具体 Unique/NULL 约束必须由 Stage 1 在真实 PostgreSQL 上验证，不能只根据本文示意写法猜数据库行为。

### F. 新增 `content_brand_review_locks`

与当前 Vehicle 人工复核锁保持一致的 Content Version 粒度，为 Stage 2/5 的 Brand Manual Review 留出正式持久边界。

## Stage 1 明确禁止

- 不删除 `keyword_pack_vehicle_models`；
- 不删除 `collection_plan_vehicle_models`；
- 不删除 `global_relevance_config`；
- 不改 Excel/TikHub Filter 行为；
- 不改 Collection Plan 公共 Contract；
- 不改 Frontend；
- 不新增 `contents.brand_name` / `contents.is_competitor` 等重复事实；
- 不做几千万 Content 回填；
- 不为通过 Migration 猜测现有 Vehicle 的 Brand。

## Stage 1 退出条件

至少取得当前 Stage revision 上的新鲜证据：

1. 新 Migration 在项目要求的真实 PostgreSQL 集成环境可 upgrade；
2. 项目要求时验证 downgrade/rollback 边界；
3. SQLAlchemy Table 定义与 Migration 一致；
4. FK、Check、Unique、Index、Owner 约束有直接集成/Schema 证据；
5. Expand 后现有 Runtime/测试不会因为新增 nullable Schema 立即失效；
6. 没有删除 Legacy 表或改变当前业务语义；
7. L3 Change Completion Audit、独立 Review、当前 PR HEAD CI 满足项目门禁；
8. 合并到 main 后只把 Stage 1 标为 `completed`，Stage 2 才从 `blocked` 变为 `planned`；不得自动进入 Stage 2。

# Stage 2：品牌车型管理与统一 Resolver

## 目标

在 Stage 1 Schema 上建立 Brand/Vehicle 主数据的唯一 Owner、管理 API、Catalog Snapshot 和纯确定性 Resolver，并完成当前 active Vehicle 的明确 Brand 归属准备。

## 必须完成

### Brand/Vehicle 主数据

- Brand CRUD、Alias 管理、生命周期、审计、Catalog Version；
- Vehicle Create/Update/Read 增加 `brand_id`；
- 新建 active Vehicle 必须绑定有效 active Brand；
- 修改 Vehicle Brand 归属是受审计的目录变化；
- Brand 停用必须 fail closed 处理旗下 active Vehicle，不能产生语义悬空。

### Filter Scope / Snapshot

实现第 1.3 节已经批准的：

```text
all_active
selected brand_ids
```

selected Brand 自动包含其全部 active Vehicle。Snapshot 冻结 Brand/Vehicle/Alias 版本，Worker 后续不读取实时目录。

### BrandVehicleResolver

Resolver 位于 Vehicles Domain，输入 `CanonicalContentV1 + frozen snapshot`，输出：

```text
matched
brand_matches
vehicle_matches
effective_brand_ids
effective_vehicle_model_ids
```

首版只做确定性文本归一和非歧义 Alias 匹配：

- Brand Alias 命中 → Brand Evidence candidate；
- Vehicle Alias 命中 → Vehicle + 所属 Brand；
- 多 Brand/Vehicle 可以同时返回；
- 一个 Alias 对应多个有效实体时不自动猜；
- 不调用 LLM/Embedding/外部网络。

### 旧 Vehicle 归属

通过管理员/受控迁移步骤明确设置现有 active Vehicle 的 Brand；不能把旧词包关联当 Brand Ownership。Stage 2 退出前，后续自动 Filter 所需的 active Vehicle 不应继续存在未解释 Brand。

## 非目标

- 暂不切换 Excel/TikHub Runtime；
- 暂不删除旧关系表；
- 暂不改声音广场 UI。

## 退出条件

- Brand/Vehicle 管理后端可独立使用；
- Snapshot/Resolver 有行为与 PostgreSQL 证据；
- active Vehicle Brand 归属达到本 Stage 验收目标；
- Stage 3 与 Stage 4 的共同前置稳定；
- 本 Stage 通过 L3 交付门禁后才标 `completed`。

# Stage 3：Excel 统一过滤

## 目标

让单文件 Excel Import 与 Historical/Data Import Campaign 不再把 Keyword Pack 当作入库过滤条件，而是统一使用 Stage 2 的 BrandVehicleFilter Snapshot + Resolver。

## 必须完成

- Excel Search 条件在后端语义上明确 `not applicable`；
- 新 Import 创建时冻结 Filter Snapshot；
- `mapping → filtering → dedup → ingestion` 主链继续保持；
- filtering 用统一 Resolver，匹配结果同时携带 Brand/Vehicle Evidence；
- 单文件 Import 和 Historical Campaign 同步迁移，不能只改一条入口；
- Job Payload/Chunk Schema 有版本化兼容策略，旧 queued/running Job 不被新 Worker 错读；
- Content 写入与 Brand/Vehicle Evidence 在当前 Owner/事务边界内正确协调；
- `imports_test` 等调试入口继续复用生产能力，不复制 Resolver。

## 兼容门禁

前端最终改造在 Stage 6，因此 Stage 3 如果改变公共 Import Contract，必须提供当前项目认可的明确兼容/部署窗口；不能通过“继续接受但静默忽略旧 Keyword Pack 参数”冒充兼容。

## 退出条件

- Excel/Historical 的 Search 与 Filter 职责在后端完成解耦；
- 有代表性 XLSX 的 Brand Alias、Vehicle Alias→Brand、多实体、unmatched filtered、retry 幂等和 Snapshot 不漂移证据；
- 不依赖真实 TikHub Probe；
- Roadmap 03 的生产容量/正式导入依赖按其文档执行。

# Stage 4：TikHub 搜索/过滤解耦

## 目标

让 TikHub Discovery 只遍历 Keyword Pack 的实际搜索词，不再把车型 Alias 与 Keyword 做组合；Provider 返回内容统一在 Canonical 后使用 Brand/Vehicle Snapshot Filter。

## 必须完成

### Discovery Search

目标复杂度：

```text
platform × keyword
```

而不是：

```text
platform × keyword × vehicle_alias
```

当前逐 Keyword Scope 的基础可从 [`backend/src/aima_ugc/modules/collection/scheduled_scopes.py`](../../backend/src/aima_ugc/modules/collection/scheduled_scopes.py) 继续演进；当前 Keyword×Vehicle 组合位置开工时重新核对 [`backend/src/aima_ugc/modules/collection/resource_selection.py`](../../backend/src/aima_ugc/modules/collection/resource_selection.py)。

### Post-Canonical Filter

```text
TikHub Search
→ Raw / Candidate / Mapper
→ Canonical
→ BrandVehicleResolver
→ matched: 继续 Decision/Ingestion
→ unmatched: 沿现有受控 Detail 链再判断
→ Detail 仍 unmatched: candidate filtered
```

不要通过增加 Search Query 组合解决召回问题。

### Collection Plan / Run

- Keyword Pack = Search Terms；
- Filter Scope = Brand Scope；
- Vehicle 不再作为 Discovery Search Resource；
- Scheduler/Run 冻结 Search Snapshot + Filter Snapshot；
- 旧 Global Keyword Relevance Runtime 在本 Stage 停止作为入库 Filter，但物理表/API 的最终删除留到 Stage 7；
- AI/人工 relevance 全部保留。

### Batch Supplement 例外

对已有 Content 的 TikHub Batch Supplement/Enrichment 不做 Keyword Search，也不重新决定该 Content 是否进入库。

## 退出条件

- Keyword Pack 每词独立 Search Scope 有确定性测试；
- 不再生成 Keyword×Vehicle Alias Discovery Scope；
- Search match、Search miss→Detail match、Detail miss→filtered 均有 Fixture/集成证据；
- Provider Request/Attempt 可追溯性和当前计费/重试边界保持不变；
- Stage 3 与 Stage 4 都完成后才能进入 Stage 5。

# Stage 5：查询、Contract 与导出

## 目标

把已经持久化的 Brand/Vehicle 事实变成正式产品 Read Model 和公共 Contract，使列表、Count、Analysis Target、Export 使用同一个过滤事实。

## 必须完成

### Voice Plaza Read Model

内容读取增加：

```text
brands[]
vehicles[].brand
competition_scope
```

`competition_scope` 至少能表达：

```text
owned_only
competitor_only
mixed
other_only
none_detected
```

它是 Brand Role 的派生投影，不在 `contents` 再存一个竞争标量事实。

### ContentFilterSnapshot

统一增加：

```text
brand_ids
competition_scopes
```

现有 `vehicle_model_ids` 可以继续作为**声音广场结果查询条件**；它与 Stage 4 删除“Collection Discovery 的 Vehicle Search Resource”是两个完全不同的边界。

以下消费者必须同步：

```text
List
Count
Analysis Run target
Export
```

Cursor/query hash 等防漂移语义也要包含新增过滤条件。

### Export

增加人类可读的 Brand/Role/Competition/Vehicle 列；不得静默把旧 `matched_keywords` 改成 Brand/Vehicle Alias 新含义。若 Search 来源词需要导出，应使用明确的新字段/列语义。

### OpenAPI / Generated Client

后端 Pydantic Contract 稳定后，按仓库正式链生成 OpenAPI/Orval Client；生成目录不手改。

## 退出条件

- API/PostgreSQL 查询对 Brand/Vehicle/Competition 有直接证据；
- Count/Analysis/Export 过滤结果与列表一致；
- OpenAPI/generated client 无漂移；
- Stage 6 不需要猜后端 API。

# Stage 6：前端产品化

## 目标

在 Stage 5 真实 Contract 上更新正式 Figma，再完成 Vue 前端，使用户看到的配置和结果与新领域语义一致。

## 顺序

```text
读取当前正式 Figma + 当前 Contract
→ Figma 更新/审查
→ Figma ↔ Backend Contract 再校准
→ OpenAPI generated client
→ Vue Feature API/Store/Page
→ Browser/Full-stack 验收
```

# Stage 7：旧数据回填与 Cleanup

## 目标

在新写入链和前端全部稳定后，完成旧 Content 的可恢复 Brand/Vehicle 重分类，并最终删除旧 Schema/Contract/代码职责。

## 旧 Content Reclassification

禁止在 Alembic Migration 中直接扫描几千万 Content。使用独立、可恢复、幂等的批处理/Job：

第一层优先利用已有 Vehicle Evidence：

```text
ContentVehicleEvidence
→ Vehicle.brand_id
→ materialize Brand Evidence(source=vehicle_match)
```

第二层按批准范围对 Current Content：

```text
title + text
→ frozen BrandVehicleCatalogSnapshot
→ Resolver
→ idempotent Brand/Vehicle Evidence
```

需要具备：

- keyset/shard/checkpoint；
- retry/cancel/progress；
- 幂等；
- 不调用 LLM；
- 不重写 Content Current；
- 统计与对账。

## Cleanup Migration

只有同时满足以下条件后才允许 Drop：

```text
新 Backend 不再读 Legacy
+ 旧 queued/running Job 已完成或有明确兼容结论
+ Frontend/generated client 已切换
+ Brand Ownership 已核对
+ 新 Filter/Query/Export 有直接证据
+ 旧配置已按回滚需要备份/导出
```

然后才删除：

```text
keyword_pack_vehicle_models
collection_plan_vehicle_models
global_relevance_config
对应旧 API / Contract / Repository / UI
```

`vehicle_models.brand_id` 只有在真实数据证明允许时才收紧为 NOT NULL；不得为了“Schema 漂亮”制造未知 Brand 或伪造归属。

## 5. 固定执行口令与 Agent 行为

后续可以直接使用：

```text
实施 docs/roadmap/04_搜索与品牌车型过滤实施路线 Stage 1，完成后合并主分支
```

或替换为 `Stage 2`—`Stage 7`。

该口令的固定含义：

1. 以本文件对应 Stage 作为上游 Requirement Source，而不是从聊天历史猜需求；
2. 开工前重新读取最新 `main`、项目规则、Stage 依赖和真实机器事实；
3. 只实施指定 Stage；依赖未完成时 fail closed，不跨 Stage 代做未来工作；
4. Schema/Migration/public Contract/数据等 L3 Stage 建立独立持久 Change 和相称 Validation Matrix；
5. 采用当前仓库允许的 PR/CI/Review 流程交付，`完成后合并主分支` 表示端到端交付，不表示绕过保护规则直接 push；
6. Merge 前重新确认当前 PR HEAD、目标分支漂移、Review/CI 和回滚边界；
7. Merge 后取得项目要求的 main fresh Evidence，再更新本 Roadmap Stage 状态；
8. 当前 Stage `completed` 后停止，不自动开始下一 Stage。

这样，Roadmap 负责“整个工程还要走到哪里”，每个 Stage 的 Change/Issue/PR 负责“这一次具体怎样施工和验证”。
