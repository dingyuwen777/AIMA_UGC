# 1. 背景与当前事实

Stage 12 开始时，系统已经具备一条小规模 Excel 导入链：

```text
网页上传单个 XLSX
→ Input Artifact
→ processing_import_batches + PostgreSQL Job（同一事务）
→ Worker
→ Excel Reader / Converter / Mapper
→ Canonical
→ Rule Relevance
→ ContentIngestionService
→ Content Owner Repository
→ PostgreSQL Current + Version + Metric
```

当前正式 AI 链也已经存在：兼容入口可以按选择内容或查询范围创建 `analysis_content_requests` 与持久 Job，Worker 针对冻结的 Content Version 调用模型并保存 `analysis_content_results`。Stage 12 新版 Analysis Run 页面只开放显式选择，单次最多 1000 条；查询范围 Run 在真实付费模型 Gold Set 与容量报告完成前不开放。

这些能力不能直接等同于 4000 万迁移。实施前已经确认的主要缺口是：

1. 当前 HTTP 入口一次上传一个文件，不能从网页浏览服务器目录、建立目录清单并批量调度；
2. 当前 Excel 转换使用执行时刻作为 `observed_at`，历史数据可能因此看起来比数据库现有 Current 更新，并覆盖已有非空字段；
3. 当前单文件处理和业务写入没有为超大历史批次建立完整的分片、断点和逐行对账账本；
4. 同值重复导入不会创建新的 Content Version，当前来源查询因此不能证明该批次确实处理过这条数据；
5. 当前 Analysis Request/Job 适合有界人工任务，不应把百万级选择一次性物化到 Python 内存，也不能把一轮大任务与历史结果混成同一身份；
6. “4000 万”是容量目标，不是现有验证结果。必须通过实际数据剖析、容量阶梯和故障恢复验收后，才可以授权全量执行。

当前实施已把本地选择与服务器批准目录收敛为同一个 Data Import Campaign 编排，旧单文件 Route 只保留兼容；该变化仍处于 Completion Audit 和门禁验证中。因此本阶段不是重写导入系统，而是在现有模块化单体、Artifact、Canonical、Content Owner、PostgreSQL Job 和 Analysis 边界上增加一套**统一输入编排、历史回填写策略、逐行账本和可重复 AI Run**。

# 2. 已确认决策

## 2.1 阶段与操作边界

- Internal V1-B 由业务 Owner 于 2026-08-26 明确确认为已完成；仓库本次只记录该外部决定，不伪造服务器命令、日志、CI 或 Smoke 明细。
- Stage 12 成为当前下一正式开发单元。
- 网页可以枚举服务器目录并启动迁移，但只能访问管理员配置的单一批准根目录。
- 开发和测试不自动执行生产 4000 万写入。全量生产迁移是软件验收后的独立、显式授权操作。

## 2.2 历史写入策略：方案 A

对相同业务身份（Content 继续使用当前平台与外部内容 ID 身份规则）：

| 当前数据库状态 | 历史值 | 结果 |
| --- | --- | --- |
| 不存在该实体 | 合法 | 创建实体和初始 Version |
| 当前字段为空 | 历史字段非空 | 只填充该空字段，并在业务事实变化时创建新 Version |
| 当前字段非空 | 历史字段相同 | Current、字段新鲜度、`last_seen_at` 均不变；账本记 `unchanged` |
| 当前字段非空 | 历史字段不同 | 保留当前值，不覆盖；冲突表记录字段、来源和双方哈希；账本记 `conflict` |
| 历史字段为空 | 任意 | 不清空当前值，不把空值记为已观测字段 |

该规则同时覆盖 Content Current、Author Current 和本次输入实际承载的稳定子实体/关联。不能只保护标题/正文，却通过作者或扩展字段路径覆盖现有事实。

历史来源没有可信观测时间的 Metric 不更新 Current，也不伪造“现在观测到”的 Metric Observation；若输入确实包含可验证的来源观测时间，则按真实时间追加历史 Observation，并由既有 Current 新鲜度规则决定当前值。

每个导入 Campaign 独立冻结 `ingestion_policy`：`standard_observation` 使用现有“字段级最新观测优先”语义，`historical_fill_only` 使用本节方案 A；两者都必须由版本化 Job Payload 显式传递，禁止根据本地/服务器来源静默推导，也禁止通过全局开关改变其他入口。Collection、补采和其他正常摄取继续使用既有标准语义。

## 2.3 迁移与 AI 解耦

- 历史导入成功不自动创建 AI Job，不产生隐式模型费用。
- AI 只由用户在网页中显式创建 Analysis Run。
- 同一 Content Version 允许被不同 Run 重复分析；每轮结果都保留。
- 当前展示结果按用户创建 Run 的顺序决定，不能按完成时间决定；较早 Run 晚完成时不能覆盖较新用户意图。
- 新 Run 某条失败时，保留上一条成功 Current，同时在新 Run 中展示失败状态。

## 2.4 统一入口与来源边界

- 采集运行中心只显示一个“导入数据”入口；用户可选本地电脑或服务器目录。
- 本地电脑可以显式多选 `.xlsx`，或通过浏览器文件夹选择器递归得到目录内全部 `.xlsx`；网页不接收或显示本机绝对路径，也不能在只选择单个文件后扫描其父目录。
- 服务器目录仍只允许管理员批准、只读挂载根目录内的相对路径，继续拒绝逃逸与 Link/Junction/Reparse Point。
- 两种来源形成不可变 Source Artifact 后，共用 Campaign、全量预检、有界 Chunk、低优先级 Job、进度、取消、重试和逐行账本。
- 旧 `/api/v1/import-batches` 与 `/api/v1/historical-import-*` 保留兼容，页面主入口只调用 `/api/v1/data-import-*`；内部 `historical_*` 物理命名暂不做高风险改名。
- 4000 万容量门禁只覆盖 `server_path + historical_fill_only`。标准观测路径用于普通规模和兼容语义，未获得同规模吞吐结论。

# 3. 目标、范围与非目标

## 3.1 目标

交付一套可以在现有公司内网环境中完成以下闭环的功能：

```text
网页选择本地文件/文件夹，或浏览批准的服务器历史目录
→ 建立不可变文件清单与 Artifact 快照
→ 预检并显示文件数、行数、错误和容量预测
→ 用户确认启动
→ 持久 Job 分片执行、可取消、可重试、可恢复
→ 只补空值并记录所有行的结果/冲突
→ PostgreSQL 可对账
→ 声音广场可按迁移 Campaign 查看内容
→ 用户按筛选条件手动创建 AI Run
→ 分片分析、保留每轮历史并展示进度/失败
```

## 3.2 范围

- 本地浏览器显式选择的多文件/文件夹清单，以及一个管理员配置、容器只读挂载的服务器历史根目录；
- `.xlsx` 目录枚举、游标分页、文件清单、快照、哈希和预检；
- Historical Import Campaign、File/Chunk Item、逐行结果账本、稀疏冲突账本；
- 复用当前 Excel Profile、Mapper、Canonical、Rule Relevance、ArtifactService、Content Owner 和 PostgreSQL Job Runtime；
- Content Owner 内的批量历史回填能力；
- 文件级/分片级断点、幂等、取消、失败重试和汇总对账；
- 网页 Campaign 列表、详情、启动、取消、重试失败项和冲突统计；
- Analysis Run + Shard、手工重分析、每轮历史和当前结果选择；
- OpenAPI/generated client、Migration、测试、容量基准、运行手册和正式文档同步。

## 3.3 非目标

- 不自动对 4000 万数据调用 AI；
- 不接入新的消息队列、Redis、Kafka、微服务、第二数据库或搜索引擎；
- 不允许网页输入任意本机/服务器绝对路径、UNC 路径、网络 URL 或下载服务器原文件；
- 不创建通用服务器文件管理器，不支持上传、删除、移动、改名或编辑服务器文件；
- 不绕过 Canonical、Content Owner 或正式 Job Runtime 用临时 SQL/脚本直接写业务表；
- 不改变 Content 业务身份，不为历史数据猜测或生成外部 ID；
- 不升级 Python、PostgreSQL、前后端框架或现有依赖；
- 不在本 Change 中实现认证、协调 Backup/Restore、预算账户或完整 Production Go-Live；
- 不承诺任意单个 500 MiB XLSX 都能在当前资源和 Attempt Deadline 内完成；上限必须由基准实测决定，超限文件在预检阶段拒绝并要求离线拆分。

# 4. 成功标准

软件功能完成必须同时满足：

1. 本地来源只接受浏览器显式选择的安全相对路径和 `.xlsx` 字节；服务器来源只能枚举批准根目录内的相对目录和 `.xlsx` 文件；路径穿越、符号链接/Junction/Reparse Point、根目录逃逸、超限目录和文件变化全部 fail closed；
2. Campaign 先完成不可变 Artifact 快照和全量预检，再允许启动业务导入；源文件在快照期间变化时该文件失败，不能导入混合版本；
3. 同一个创建幂等键、同一 Campaign Item、同一 Chunk 或同一 Job 重试不会重复产生业务副作用；
4. 已有非空 Content/Author/扩展事实在历史导入后逐字段保持不变，差异有可查询冲突记录；
5. 当前为空的字段被历史数据补齐；只有真实业务事实变化才创建新 Version；相同值和冲突不推进字段新鲜度或 `last_seen_at`；
6. 每个输入数据行都可落到一个终态：历史补空使用 `created / filled / unchanged / conflict / filtered / duplicate / invalid / failed`，标准观测还可使用 `updated`；批次、Campaign、文件、Chunk、Content 与来源 Artifact 可追溯；
7. 取消、Worker 崩溃、Lease 接管和人工重试后，从已提交断点继续，最终汇总与逐行账本一致；
8. 普通优先级 Job 不会被历史迁移长时间饿死；迁移并发和队列深度有界；
9. 用户可以在声音广场基于稳定筛选显式创建 AI Run，Run 被拆成有界 Shard；重复 Run 保留历史，当前结果选择符合第 2.3 节；
10. 本机软件交付以 10 万、100 万容量阶梯通过为门禁；500 万不再作为本机开发完成条件，延期到公司服务器生产前演练。只有服务器侧 500 万或经业务 Owner 批准的等效比例演练完成，才能形成 4000 万执行估算；全量执行前 PostgreSQL、Artifact、临时空间和 WAL 至少保留经批准的 30% 安全余量；
11. Browser Mock、Backend/API/PostgreSQL、Contract/generated client、Real Full-stack、故障恢复、容量和文档门禁取得本轮新鲜证据；
12. 历史预检和迁移展示由后端持久事实聚合的进度条；AI Run、Excel Export 和 Collection Scope 复用各自已有进度。目录发现等未知总量阶段只显示不确定进度，不伪造百分比。
13. “软件已具备迁移能力”和“4000 万实际迁移完成”分别验收，后者必须有全量清单、终态账本、数据库对账和异常处置记录。

不存在只靠一条测试就能绝对保证 4000 万效果的方案。这里的保证来自不可变输入、数据库约束、幂等身份、断点恢复、逐行账本、分层测试和逐级放量共同构成的可验证门禁。

# 6. 方案比较与选择

## 方案 A：现有系统内增量增加 Campaign、历史写策略和 Analysis Run（采用）

优点：复用现有 Artifact、Canonical、Owner、Job、页面和审计边界；最容易证明兼容和恢复；不产生第二套业务写入口。代价是需要新增 Schema/Migration、批量写入路径、页面和较完整的容量验证。

## 方案 B：外部 ETL 直接 `COPY`/SQL 写业务表（不采用）

吞吐可能更高，但会绕过 Mapper、Canonical、Content Owner、Current/Version/Metric、来源账本和业务触发规则；重复执行、冲突和回滚很难与当前系统一致。只有未来证明方案 A 在批准硬件上仍无法达到窗口，并另建 L3 决策时才可重新评估。

## 方案 C：新建微服务、队列或专用迁移数据库（不采用）

隔离性更强，但当前没有证据证明 PostgreSQL Job Runtime 和模块化单体无法承担该任务；会显著增加部署、数据一致性、故障恢复和运维成本。

结论：采用方案 A，并要求 Content Owner 提供**集合式批量历史回填**。禁止把 4000 万行逐行执行 `SELECT ... FOR UPDATE + UPDATE` 作为最终实现；小批次逐行实现只能用于单元/对照测试。

# 7. 目标架构与数据流

```text
浏览器显式选择本地多文件/文件夹
→ 冻结相对路径 + byte_size 清单并逐 Item 流式上传

或：管理员配置的只读历史根目录
→ Directory Browser（只返回相对路径和安全元数据）

两种来源
→ Data Import Campaign（冻结 source_kind + ingestion_policy）
→ 文件 Manifest + Artifact 快照 + SHA-256
→ 流式 XLSX 预检/转换
→ 不可变规范化 Chunk Artifact
→ 低优先级 Import Chunk Job
→ Import Staging / 集合式去重与比较
→ Content Owner Standard Observation 或批量 Historical Fill-Only
→ 每行结果账本 + 稀疏冲突账本
→ Campaign 汇总与对账
→ Voice Plaza 来源筛选

用户在 Voice Plaza 显式点击 AI 打标
→ Analysis Run
→ Planner Job 用 PostgreSQL INSERT ... SELECT 冻结 Content ID + Version
→ 有界 Shard Request + Job
→ 现有 Prompt/Adapter/Persistence
→ 每轮 Result 历史 + Current 投影
```

HTTP 请求只做参数校验、短事务和本地文件到 ArtifactStore 的有界流式传输；目录扫描、服务器文件复制、XLSX 解析、分片、数据库写入和 AI 调用都在持久 Job 中执行。

# 8. 服务器目录与快照安全设计

## 8.1 配置与挂载

- 新增一个明确的历史导入根配置，建议机器字段名为 `AIMA_HISTORICAL_IMPORT_ROOT`；实施前按当前 Settings 命名规则确认最终名称。
- canonical Linux Compose 把服务器批准目录以只读方式挂载到固定容器路径，例如 `/data/aima-historical-input:ro`；API 与 Worker 使用相同的容器内路径事实。
- HTTP Contract 永远只接受并返回根目录内相对路径，不返回宿主机绝对路径。
- 未配置、目录不存在、权限不正确或根目录不是目录时，能力端点明确返回 unavailable，不能退回任意路径访问。
- 当前系统尚未接入 Authentication/Authorization，因此能访问内网页面的客户端也能调用这些管理端点；Stage 12 不伪造角色权限。该限制必须在页面和部署文档中明确，创建、启动、取消、重试 Campaign 等高价值动作按当前 `audit_events` 边界记录。若访问范围扩大，认证授权先成为独立 L3 前置门禁。

## 8.2 枚举规则

- 仅列出直接子目录与 `.xlsx` 文件；是否递归由用户在创建 Campaign 时显式选择，默认不递归；
- 使用游标分页和稳定排序；单页、最大扫描文件数、最大目录深度均有限制；
- 拒绝 `..`、绝对路径、UNC、设备路径、空字节、路径分隔混淆、符号链接、Junction/Reparse Point；
- 对每一级解析后的真实路径再次验证仍在批准根目录内；
- 不读取或返回文件正文，不提供原文件下载；日志只记录相对路径摘要、Campaign/Item ID 和错误码。

## 8.3 不可变快照

创建 Campaign 后先进入预检，不立即写业务表：

1. 服务器来源枚举得到文件相对路径、大小、修改时间和稳定顺序；本地来源先冻结浏览器选择的相对路径和大小清单，再逐 Item 上传；
2. 服务器 Snapshot Job 读取前后分别核对大小/mtime，本地上传逐 Item 核对文件名、大小及重复 PUT 的 SHA-256；两者都通过 `ArtifactService` 保存 Input Artifact 和 SHA-256；
3. 文件变化、读取中断、Zip/XLSX 安全检查失败时，Item 失败；
4. Artifact 快照成功后，后续导入只读 Artifact，不再读取原目录；
5. 流式解析为有界规范化 Chunk Artifact；每个 Chunk 有行号范围、记录数、SHA-256、Profile/Mapper/词包快照和版本化格式；
6. 所有文件预检完成且容量检查通过后，Campaign 才进入 `ready`，页面才启用“开始迁移”。

规范化 Chunk 优先使用 UTF-8 JSON Lines + gzip 等标准库可生成/读取的版本化内部格式；不得为此默认新增 Parquet 等依赖。若实测证明标准格式不满足性能，新增依赖必须另行说明许可证、维护、体积和替代方案。

# 9. Campaign、Item、账本与状态机

## 9.1 表与 Owner

由 Ingestion 模块拥有：

- `historical_import_campaigns`：来源、写入策略、目录/上传清单、创建幂等键、Profile、词包快照、状态、总数和时间；表名为兼容保留的物理名称；
- `historical_import_campaign_items`：一个源文件/规范化 Chunk 的 Manifest、Artifact、哈希、状态、尝试和统计；
- `processing_import_batch_items`：已进入 Chunk 业务事务的输入行紧凑终态账本；
- `processing_import_batch_item_conflicts`：仅冲突字段写入的稀疏账本；
- `processing_import_batches` 增加可空的 Campaign Item/历史模式关联和冻结配置，不破坏现有上传批次。

由 Content 模块继续独占写入 `contents`、`content_versions`、Author、扩展表与 Metric 表。Ingestion 只能调用 Content Owner 暴露的历史批量写入口。

已进入 Chunk 业务事务的逐行账本至少包含 `batch_id + source_row_ordinal` 唯一身份、Campaign Item、平台、外部 ID 或其安全哈希、Content ID、outcome、错误码、filled/conflict 数量和提交 Chunk；不复制完整正文。Chunk 的业务变化、逐行账本和 `succeeded` 状态在同一事务提交，因此结构失败或取消的整段未处理行不会存在“部分业务写入、没有账本”的中间状态。此类行由不可变 Chunk Item 的 `row_start/row_end/row_count + failed/cancelled` 作为紧凑区间终态，并统一计入汇总 `failed`；不为一个尚未解析或已经取消的 40M 输入批量伪造逐行记录。失败 Chunk 重试时创建新 Batch，并用集合式 `INSERT ... SELECT` 继承前一 Batch 已提交的身份集合，避免跨 Chunk 重复行改变语义；重试成功后，该区间重新获得真实逐行 outcome。冲突表保存字段名、当前 Content Version、来源行、当前值哈希和历史值哈希，默认不复制敏感全文。

## 9.2 状态

Campaign：

```text
uploading → snapshotting → ready → queued → running
         ↘ cancelled
discovering → snapshotting → ready → queued → running
                                      ↘ cancelling → cancelled
running → succeeded | partial_failed | failed
```

Item/Chunk：

```text
discovered → snapshotting → ready → queued → running
running → succeeded | failed | cancelled
```

状态转换必须使用数据库约束和 CAS。父级汇总从子项事实计算或由同事务安全推进，不能只相信前端计数。

## 9.3 Job 与事务

建议的版本化 Job：

```text
ingestion.historical-discover.v1
ingestion.historical-snapshot.v1
ingestion.historical-import-chunk.v1
analysis.plan-content-run.v1
```

服务器 Campaign 与 Discover Job 同一事务创建；本地 Campaign 与冻结 Source Item 清单同一事务创建，全部 Artifact 上传完成后的 finalize 短事务才创建 Snapshot Job；本地上传中断时允许用户取消，尚未进入预检的 Source Item 和 Campaign 在同一事务直接收敛为 `cancelled`，不等待不存在的 Worker 回调。Item 与其 Snapshot Job、Import Batch 与 Import Job、Analysis Run 与 Planner Job、Shard Request 与对应 Job 都保持同事务创建。

所有进度、续租、终态和业务可见 Chunk 提交继续验证现有 Fencing Token。历史 Job 使用低于普通交互 Job 的优先级；并发上限由当前 Worker 数量与数据库中的 Campaign in-flight 门禁共同限制，避免一次把所有文件转成可运行 Job。

Campaign 页面进度必须从持久事实重建：目录发现尚无总文件数时显示不确定进度；预检进度按每个 Source Item 的终态和对应 Snapshot Job 进度聚合；迁移进度按终态 Chunk 的冻结 `row_count` 汇总，并以 Campaign `total_rows` 为分母。`failed/cancelled` Chunk 也属于已取得对账终态，但不能在状态或统计中显示成成功。Campaign 列表必须集合式查询这些聚合，不得对每个 Campaign 或每行明细逐项往返数据库。Analysis Run 前端只对活动 Run 补读现有详情中的 Shard，并以冻结的 Run `target_count` 为分母汇总 `Shard target_count × progress`；尚未调度的目标按 0% 计入，防止有界窗口扩展时百分比倒退。Excel Export 与 Collection Scope 直接使用已有 Job/Scope 进度。

# 10. 大规模导入实现规则

## 10.1 流式与有界资源

- XLSX 必须使用只读/流式 Reader；禁止把整个工作簿、所有 Canonical 或 4000 万身份集合放入 Python 内存；
- 规范化 Chunk 行数和字节数由基准选择，并固化到版本化 Payload/Manifest；
- 跨 Chunk 的同文件去重使用磁盘有界外排/归并或 PostgreSQL staging 的唯一约束实现“稳定首行胜出”，不得退回进程内大字典；
- 逐行账本与 staging 使用批量插入/COPY；Content Owner 使用集合式比较、空值填充、Version 生成和冲突输出；
- staging 必须按 Batch/Chunk 隔离，成功后可清理；崩溃时允许从不可变 Chunk 重建，不能依赖不可恢复的内存状态。

## 10.2 幂等与断点

- Campaign 创建：客户端幂等键唯一；
- 文件快照：`campaign_id + relative_path + manifest_identity` 唯一；
- Chunk：`campaign_item_id + ordinal + sha256` 唯一；
- 批次行：`batch_id + source_row_ordinal` 唯一；
- 历史业务写：内容身份继续由数据库唯一约束保障；
- 每个已提交 Chunk 记录终态计数和 checkpoint；Job 接管只处理未完成 Chunk；
- 同一技术 Attempt 重试复用相同 Artifact/Chunk/Batch；用户“重试失败项”创建新的 Batch/Job Attempt，但引用同一不可变输入并可与原失败项关联。

## 10.3 历史回填算法

Content Owner 的批量实现必须在 PostgreSQL 中锁定/比较实际 Current，并返回逐行结果：

```text
新身份
→ INSERT Current + 初始 Version

已有身份
→ 逐字段比较
→ current IS NULL 且 historical IS NOT NULL：填充
→ current IS NOT NULL 且相等：不写 Current/新鲜度/last_seen_at
→ current IS NOT NULL 且不同：不写 Current，输出 conflict
→ 至少一个业务字段被填充：current_version + 1，并保存 Version
→ 无业务变化：不创建 Version
```

并发时不得用先读后写的无锁 Python 判断。集合式 SQL 必须在数据库约束、行锁或等价原子条件下保证标准摄取与历史回填竞态时仍不覆盖非空值。

## 10.4 Rule Relevance 与输入错误

- Campaign 创建时冻结用户选择的 1—20 个 Keyword Pack 版本和有效关键词，Worker 不读取实时词包；
- `filtered`、`duplicate`、`invalid` 都是可对账终态，不等于系统错误；
- 缺少稳定平台/外部 ID 的行不能发明身份，记为 `invalid`；
- 单行错误不回滚已提交 Chunk；结构级错误、Artifact 损坏或策略快照不一致使该 Item/Chunk 失败；
- Campaign 终态允许 `partial_failed`，但页面必须显示失败文件/Chunk 和是否可重试，不能把部分成功显示成全量成功。

# 11. 手动 AI Run 与重复打标

## 11.1 数据模型

Analysis 模块新增 `analysis_content_runs` 作为一次用户操作的父事实；现有 `analysis_content_requests` 作为 Shard 子请求，增加 `run_id` 与 `shard_no`。已有 Request 通过 Alembic 数据迁移回填为“一 Request 对应一历史 Run”，保持原结果可读。

Run 冻结：

- 显式 selected IDs，单次 1—1000 条；数据库与读取模型仍兼容历史 query scope，但新版 Preview/Create Contract 不接受 query；
- `run_intent`，至少区分普通待分析与 `manual_reanalysis`；
- Prompt Version/SHA、Taxonomy SHA、Provider、Model；
- 实际发送的生成参数及 `generation_config_hash`；
- 创建顺序、状态和汇总。

Planner 在 PostgreSQL 内使用 `INSERT ... SELECT` 冻结 `content_id + content_version`，不能把全部目标先装入 Python list/tuple。每个 Shard 仍使用现有版本化 Analysis Job Runtime 和 Decision R。

## 11.2 重复结果与 Current

- `analysis_content_results` 增加 `analysis_run_id` 和 `generation_config_hash`；
- 幂等唯一身份包含 Run，使同一 Run 重试不重复、不同 Run 可保留新结果；
- 当前成功结果按 Run 创建序号选择，不按 `analyzed_at` 或完成时间选择；
- 较新 Run 的失败/取消不删除旧成功结果；查询同时返回当前成功结果和最新 Run 状态；
- Content 新版本仍使旧结果 stale；人工相关性复核继续按当前 Content Version 和既有追加账本语义工作。

## 11.3 分片和质量门禁

Shard 大小不能拍脑袋固定为 20。用真实脱敏样本比较 1/4/8/16/20 等批量，选择满足以下门禁的最大安全值：

- 核心分类相对 batch=1 的指标下降不超过 1 个百分点；
- 设计的跨条污染用例为 0；
- 允许的结构重试后 JSON 结构有效率为 100%；
- P95 单 Shard 运行时间不超过对应 Attempt Deadline 的 70%；
- token、成本、吞吐和失败率有完整报告。

如果没有多条批量满足门禁，正式值就是 batch=1。模型不支持的 temperature/top_p/seed 等参数不得伪造为已冻结；只记录实际发送配置和适配器/运行版本。

当前批准边界是：Shard 大小保持 1；新版 Analysis Run 只允许用户显式选择 1—1000 个 Content ID。查询范围 Run 属于待真实付费 Gold Set、费用和容量报告完成后重新决策的最大规模能力，不得从前端或直接 HTTP 绕过。

# 16. 容量、质量与全量执行门禁

## 16.1 迁移容量报告必须包含

- 运行硬件、PostgreSQL 配置、Worker 数、Chunk 大小、队列上限；
- 输入文件数、大小、总行数、有效/重复/过滤/错误/冲突比例；
- 端到端和分阶段吞吐、P50/P95 Chunk 时间、峰值 RSS/CPU；
- PostgreSQL 主表/索引/账本增长、WAL、临时文件、锁等待、查询延迟；
- Artifact 原文件与 Chunk 增长、临时盘峰值；
- Worker 崩溃、重启、取消、失败重试后的恢复时间和对账结果；
- 基于实测分布而不是线性拍脑袋的 4000 万时间/容量预测。

本轮本机容量验证上限由业务 Owner 确认为 100 万。10 万和 100 万报告用于证明流式、有界、集合式链路在开发机上的资源增长和对账行为，不足以单独预测或授权生产 4000 万。500 万本机尝试因磁盘空间耗尽及频繁 Checkpoint 暴露环境容量风险，后续重跑由业务 Owner 主动中止；两次都属于未完成证据，不能写成通过。500 万或经业务 Owner 批准的等效比例演练移到公司服务器生产前门禁，必须使用目标部署配置和真实数据分布重新形成报告。

## 16.2 AI Gold Set 报告必须包含

- 从真实数据分层抽样，覆盖五平台、文本长短、相关/不相关、发声类型、情感、标签、硬负例和长文本；
- 双人标注和分歧仲裁；
- 固定 Prompt/Taxonomy/Model/生成配置；
- batch 1 与候选批量的 macro/micro 指标、跨条污染、JSON 有效率、重试、延迟、token 和成本；
- 最终 Shard 大小、最大 Run 目标数及选择依据。

## 16.3 停止条件

任一条件出现就暂停放量并调查根因：

- 已有非空字段发生覆盖；
- 账本总数无法与输入行数对平；
- 相同 Chunk 重试产生重复业务副作用；
- Worker 接管绕过 Fencing；
- 普通 Job 出现不可接受的持续饥饿；
- 预计全量后任一关键存储安全余量低于批准值；
- 数据库错误率、锁等待、查询延迟或恢复时间超过已批准门槛；
- AI 出现跨条污染或质量门禁不达标。

# 17. 部署、迁移与回滚

- Schema 只做向前 Alembic Migration；新增表/列先保持可空或有安全默认，再回填旧 Analysis Request；禁止在同次部署中先删旧字段/约束。

- 历史目录使用只读挂载；回滚应用版本不能删除 PostgreSQL、Artifact 或迁移账本。
- 代码回滚只停止新 Campaign/Run，不反向删除已经创建或补齐的业务数据。
- 如果要撤销某次实际数据迁移，必须基于该 Campaign 的逐行账本制定独立、显式批准的补偿 Change；由于方案 A 会填充原空字段并可能与后续正常采集交织，禁止自动“整批删除/清空”。
- 当前完整协调 Backup/Restore 尚未闭环。全量生产执行前必须明确可用备份事实、恢复验证和维护窗口；没有证据时不得把“可回滚”写成已具备。
