# 1. 背景、Stage 12 前缺口与当前结果

Stage 12 开始前，系统已有一条小规模兼容 Excel 导入链：

```text
网页上传单个 XLSX
→ Input Artifact
→ processing_import_batches + PostgreSQL Job（同一事务）
→ Worker
→ Excel Reader / Converter / Mapper
→ Canonical
→ Rule Relevance
→ ContentIngestionService
→ Content Owner Repository
→ PostgreSQL Current + Version + Metric
```

当时正式 AI 链也已有 `analysis_content_requests`、持久 Job 和 `analysis_content_results`，但还没有面向一轮用户意图的 Run/Target/Planner 模型。

Stage 12 开始前确认的主要缺口是：

1. 单文件 HTTP 入口不能从网页浏览批准服务器目录、建立多文件清单并有界调度；
2. 普通观测语义不适合“旧历史只补空”的导入，可能把历史数据错误视为当前新观测；
3. 大批次缺少完整 Campaign、不可变快照、Chunk、断点和逐行对账账本；
4. 同值/冲突不产生新 Content Version，单靠 Version 无法证明某个历史 Campaign 处理过该输入行；
5. Analysis Request 不足以表达“一次用户 Run + 多个有界 Shard + 多轮结果历史”；
6. “4000 万”是容量目标，不是可以由功能单测直接证明的结果。

这些**软件缺口已经完成实现**。当前页面把本地选择与服务器批准目录收敛为同一个 Data Import Campaign；旧 `/api/v1/import-batches` 和 `/api/v1/historical-import-*` 只保留兼容。当前还没有完成的是公司服务器容量演练和生产 4000 万实际执行/对账。

因此 Stage 12 当前边界是：

```text
软件设计 / Schema / Contract / API / Worker / 页面 / 测试
→ 已完成

公司服务器 500 万或批准等效比例容量演练
→ 待执行

生产 4000 万实际 Campaign + 全量对账
→ 待独立生产写授权
```

# 2. 已确认且已实现的业务决策

## 2.1 阶段与操作边界

- Internal V1-B 由业务 Owner 于 2026-08-26 明确确认为已完成；仓库只记录该外部决定，不伪造服务器命令、日志、CI 或 Smoke 明细。
- Stage 12 曾作为 Internal V1-B 后的下一正式开发单元；当前软件 Change 已完成并归档，不再是“待开发阶段”。
- 网页可以枚举服务器目录并创建导入 Campaign，但只能访问管理员配置的单一批准根目录。
- 开发、CI、本机容量测试都不自动授权生产 4000 万写入。全量生产迁移是软件验收后的独立、显式生产操作。

## 2.2 历史写入策略：方案 A

对相同业务身份（Content 继续使用当前平台与外部内容 ID 身份规则）：

| 当前数据库状态 | 历史值 | 结果 |
| --- | --- | --- |
| 不存在该实体 | 合法 | 创建实体和初始 Version |
| 当前字段为空 | 历史字段非空 | 只填充该空字段，并在业务事实变化时创建新 Version |
| 当前字段非空 | 历史字段相同 | Current、字段新鲜度、`last_seen_at` 均不变；账本记 `unchanged` |
| 当前字段非空 | 历史字段不同 | 保留当前值，不覆盖；冲突表记录字段、来源和双方哈希；账本记 `conflict` |
| 历史字段为空 | 任意 | 不清空当前值，不把空值记为已观测字段 |

该规则覆盖 Content Current、Author Current 和历史输入实际承载的稳定扩展事实。不能只保护标题/正文，却通过作者或扩展字段路径覆盖现有事实。

历史来源没有可信观测时间的 Metric 不更新 Current，也不伪造“现在观测到”的 Metric Observation；若输入确实包含可验证的来源观测时间，则按真实时间追加历史 Observation，并由既有 Current 新鲜度规则决定当前值。

每个 Data Import Campaign 独立冻结 `ingestion_policy`：

```text
standard_observation
→ 现有字段级观测/新鲜度语义

historical_fill_only
→ 本节方案 A
```

两者都通过版本化 Job Payload 显式传递，禁止根据本地/服务器来源静默推导，也禁止通过全局开关改变其他入口。Collection、补采和其他正常摄取继续使用既有标准语义。

## 2.3 迁移与 AI 解耦

- 导入成功不自动创建 AI Job，不产生隐式模型调用；
- AI 只由用户在声音广场显式创建 Analysis Run；
- 同一 Content Version 允许被不同 Run 重复分析，每轮结果都保留；
- Current 结果按 Run 创建顺序选择，不能按完成时间让更早用户意图覆盖更晚意图；
- 新 Run 失败/取消不删除上一轮成功结果，同时保留最新 Run 状态。

## 2.4 统一入口与来源边界

当前采集运行中心只显示一个“导入数据”入口：

```text
source_kind
→ local_upload
→ server_path

ingestion_policy
→ standard_observation
→ historical_fill_only
```

两维正交：来源只决定文件如何形成 Artifact，策略只决定进入 Content Owner 后的写入语义。

- 本地电脑可以显式多选 `.xlsx`，或使用浏览器文件夹选择器递归取得用户选择目录内的 `.xlsx`；页面不取得本机绝对路径，也不会在用户只选择单个文件后扫描父目录；
- 服务器目录只能访问管理员批准、容器只读挂载根目录内的相对路径，并拒绝路径逃逸、Symlink/Junction/Reparse Point；
- 两种来源形成不可变 Source Artifact 后，共用 Campaign、全量预检、有界 Chunk、低优先级 Job、进度、取消、重试和逐行账本；
- 旧 `/api/v1/import-batches` 与 `/api/v1/historical-import-*` 保留兼容，当前页面主入口使用 `/api/v1/data-import-*`；内部 `historical_*` 物理命名为兼容保留，不表示第二套业务入口；
- 4000 万容量门禁只覆盖 `server_path + historical_fill_only`。`standard_observation` 未取得同规模吞吐结论。

## 3.1 已实现目标

当前软件已经形成以下闭环：

```text
网页选择本地文件/文件夹，或浏览批准的服务器历史目录

→ Planner 冻结 Content Version
```

## 3.2 当前实现范围

- 本地浏览器显式选择的多文件/文件夹，以及一个管理员配置、容器只读挂载的服务器历史根目录；
- `.xlsx` 目录枚举、文件清单、快照、SHA-256 和预检；
- Data Import Campaign、Source File/Chunk Item、逐行结果账本、稀疏冲突账本；
- 复用现有 Excel Profile、Mapper、Canonical、Rule Relevance、ArtifactService、Content Owner 和 PostgreSQL Job Runtime；
- Content Owner 的历史 Fill-Only 集合式写入能力；
- 文件级/Chunk 级断点、幂等、取消、失败重试和汇总对账；
- Campaign 列表/详情/启动/取消/重试/冲突/真实进度页面闭环；
- Analysis Run + Target + Planner + Shard、手工重分析、每轮历史和 Current 选择；
- Pydantic/OpenAPI/generated client、Alembic Migration、分层测试、容量基准、运行手册和正式文档。

## 3.3 仍然是非目标

- 不自动对导入数据调用 AI；
- 不接入新的消息队列、Redis、Kafka、微服务、第二数据库或搜索引擎；

- 不绕过 Canonical、Content Owner 或正式 Job Runtime 用临时 SQL/外部 ETL 直接写业务表；
- 不改变 Content 业务身份，不为历史数据猜测或生成外部 ID；
- 不自动升级 Python、PostgreSQL、前后端框架或依赖；
- Stage 12 不实现认证、协调 Backup/Restore、预算账户或完整 Production Go-Live；
- 不承诺任意超大单个 XLSX 在任意资源下都能成功，超限文件必须按预检/运行门禁处理。

# 6. 方案比较与最终选择

## 方案 A：现有系统内增量增加 Campaign、历史写策略和 Analysis Run（已采用并实现）

复用现有 Artifact、Canonical、Owner、Job、页面和审计边界；不产生第二套业务写入口。Stage 12 已按该方案落地 Schema/Migration、批量写入路径、页面和容量验证工具。

## 方案 B：外部 ETL 直接 `COPY`/SQL 写业务表（未采用）

吞吐可能更高，但会绕过 Mapper、Canonical、Content Owner、Current/Version/Metric、来源账本和业务触发规则；重复执行、冲突和回滚难与当前系统一致。只有未来证明方案 A 在批准硬件上仍无法满足明确窗口，并另建 L3 决策时才能重新评估。

## 方案 C：新建微服务、队列或专用迁移数据库（未采用）

隔离性更强，但当前没有证据证明 PostgreSQL Job Runtime 和模块化单体无法承担任务；会增加部署、数据一致性、故障恢复和运维成本。

当前固定结论仍是方案 A：Content Owner 提供集合式批量 Historical Fill-Only；禁止把 4000 万行逐行 `SELECT ... FOR UPDATE + UPDATE` 作为最终实现。

# 8. 服务器目录与快照安全设计（已实现边界）

## 8.1 配置与挂载

当前使用历史导入根配置：

```text
AIMA_HISTORICAL_IMPORT_ROOT
```

canonical Compose 把管理员批准目录以只读方式暴露给 API/Worker；HTTP Contract 只接受/返回批准根内相对路径，不把宿主机绝对路径作为业务 Contract。

未配置、目录不存在、权限不正确或根目录不可用时，目录能力 fail closed；当前系统尚未接入 Authentication/Authorization，因此所有能访问受控内网页面的客户端都处于同一当前权限边界。访问范围扩大时，认证授权成为独立 L3 前置门禁。

## 8.2 枚举规则

- 只允许批准根目录内目录与 `.xlsx`；递归由用户显式选择；
- 使用稳定排序和有界分页/扫描；
- 拒绝 `..`、绝对路径、UNC、设备路径、空字节、路径分隔混淆、Symlink、Junction/Reparse Point；
- 每一级解析后都验证仍位于批准根内；
- 不提供通用文件删除/移动/改名/下载能力；日志只记录允许的安全摘要/业务 ID。

## 8.3 不可变快照

Campaign 不直接写业务表：

1. 服务器来源枚举相对路径/大小/mtime；本地来源冻结浏览器选择的相对路径/大小清单；
2. 服务器 Snapshot 在读取前后核对文件状态；本地上传按 Item 核对文件名、大小和重复 PUT 的 SHA-256；
3. 两者都通过 ArtifactService 保存不可变 Input Artifact + SHA-256；
4. 快照成功后后续导入只读 Artifact，不再依赖原目录/浏览器文件；
5. 流式解析为有界规范化 Chunk Artifact；
6. 全部预检成功且满足门禁后 Campaign 才进入 `ready`，页面才允许 start。

规范化 Chunk 使用当前已实现的版本化内部格式；未来若要更换格式/新增依赖，必须由真实性能证据和独立 Change 决定。

## 9.1 当前表与 Owner

逐行账本使用 `batch_id + source_row_ordinal` 等数据库唯一身份；冲突表只保存必要字段/哈希，不复制完整敏感正文。业务变化、逐行账本和 Chunk 成功状态在对应事务边界保持一致，失败/取消 Chunk 使用冻结的 row range/row_count 形成可对账区间事实。

## 9.2 当前状态机

Campaign：

```text

→ snapshotting
→ ready
→ queued / running / cancelling
→ cancelled / succeeded / partial_failed / failed
```

Item/Chunk：

```text
discovered
→ snapshotting
→ ready
→ queued
→ running
→ succeeded / failed / cancelled
```

精确允许值和约束以当前 `historical_tables.py` / Migration 为准；本文不复制第二套完整 DDL。

## 9.3 当前版本化 Job 与事务

当前真实 Worker Job type：

```text

ingestion.historical-snapshot.v1
ingestion.historical-import-chunk.v1
analysis.content-run-plan.v1
analysis.content-label.v1
```

注意：Stage 12 早期方案中的 `analysis.plan-content-run.v1` 已不是当前机器事实，现行名称是 **`analysis.content-run-plan.v1`**。

Campaign/Item/Batch/Run/Shard 在各自状态转换中保持“业务父事实 + 本阶段必须触发 Job”的事务原子性；所有进度、续租、终态和业务可见 Chunk 提交继续使用现有 Job Runtime 的 Lease/Fencing/Deadline/Cancel/Retry 语义。

历史 Job 使用低优先级并限制 in-flight 数量，防止长迁移饿死普通 Job。

Campaign 进度从数据库持久事实集合式聚合：发现阶段未知总量时显示不确定进度；预检按 Source Item/Snapshot Job；迁移按冻结 Chunk `row_count` 的终态聚合。`failed/cancelled` 表示已经取得对账终态但不是成功。Analysis Run 以冻结 `target_count` 和 Shard 持久进度汇总，尚未进入有界调度窗口的目标按 0% 计入。

# 10. 大规模导入实现规则

## 10.1 流式与有界资源

当前设计必须继续保持：

- XLSX 只读/流式处理，不把整个工作簿、所有 Canonical 或 4000 万身份集合放进 Python 内存；
- 规范化 Chunk 行数/字节数有界；
- 跨 Chunk 去重不能退回进程内 4000 万大字典；
- 逐行账本/中间集合采用批量数据库操作；
- Content Owner 的 Historical Fill-Only 使用集合式比较/补空/Version/冲突输出；
- 任何可清理中间状态都必须能从不可变 Artifact/Chunk 重建。

## 10.2 幂等与断点

当前身份/约束维持：

```text
Campaign 创建
→ client idempotency key

Source Manifest
→ campaign_id + relative_path + manifest_identity

Chunk
→ Campaign Item + ordinal/hash 的稳定身份

Batch 行
→ batch_id + source_row_ordinal

业务 Content
→ (platform, external_content_id)
```

Job/Worker 接管只能继续未完成事实，不重复已提交业务副作用。

## 10.3 Historical Fill-Only 算法

Content Owner 的批量实现必须继续保证：

```text
新身份
→ INSERT Current + 初始 Version

已有身份
→ current IS NULL 且 historical IS NOT NULL：填充
→ current IS NOT NULL 且相等：不写 Current/新鲜度/last_seen_at
→ current IS NOT NULL 且不同：不写 Current，输出 conflict
→ 至少一个业务字段被填充：按当前 Version 规则形成业务变化
→ 无业务变化：不制造新 Version
```

并发时不得退回无锁“先读再写”的 Python 判定。

## 10.4 Rule Relevance 与输入错误

- Campaign 冻结所选 Keyword Pack/关键词快照，Worker 不读取实时词包改变已创建 Campaign；
- `filtered / duplicate / invalid` 是可对账业务终态，不等于系统故障；
- 缺少稳定平台/外部 ID 的行不得发明身份；
- 单行错误不应回滚已经安全提交的其他 Chunk；
- `partial_failed` 必须能明确显示失败 Item/Chunk 和重试边界，不能伪装成全成功。

- PostgreSQL/Artifact/WAL/临时空间容量与性能；
- Voice Plaza 来源查询抽样；
- AI Run 若执行，必须单独报告，不能混入导入成功率。
