# 4000 万历史数据生产迁移实施路线

- 状态：Active
- 目标：在不改变已完成历史迁移软件语义的前提下，完成公司服务器容量验证、独立生产写授权、4000 万正式导入和全量对账。
- 退出条件：容量门禁达到批准阈值并留存资源/吞吐证据；取得生产写授权；正式 4000 万 Campaign 完成；逐行结果、冲突、数据库和资源账本完成全量对账；异常与剩余项有明确处置结论。
- 依赖：已完成的 Data Import Campaign/Historical Fill-Only、当前 Brand/Vehicle Filter 软件与运行手册、目标公司服务器、正式历史数据、业务 Owner 授权及必要的生产备份/恢复边界；真实数据处理容量演练和正式 Campaign 还必须遵守 [`docs/roadmap/05_可重放数据底座与监测重分类实施路线.md`](05_可重放数据底座与监测重分类实施路线.md) 的 Persistent Canonical JSONL.gz / Replay 数据底座依赖。

本文不再重复 Stage 12 已完成的软件建设过程。当前软件语义和运行方法分别由长期技术决策及 [`docs/operations/02_4000万历史迁移与Analysis Run运行手册.md`](../operations/02_4000万历史迁移与Analysis%20Run运行手册.md) 维护。

## 1. 已经完成的软件基线

当前系统已经实现：

- 单一“导入数据”入口；
- `local_upload / server_path` 两种 Source；
- `standard_observation / historical_fill_only` 两种独立写入策略；
- 不可变 Source Artifact、SHA-256、全量预检、有界 Chunk；
- 持久 Job、进度、取消、重试、断点恢复；
- 逐行结果账本和冲突留痕；
- Historical Fill-Only：只补空值，不覆盖已有非空 Current；
- Data Import Campaign 与 AI Analysis Run 解耦；
- 手工 Analysis Run、目标冻结、Planner/Shard 和多轮结果历史；
- 本机 10 万、100 万阶梯的软件/容量验证基线。

这些内容是当前实现，不再作为“待开发功能”。长期写入语义见 [`docs/blueprint/07_技术决策与实施门禁.md`](../blueprint/07_技术决策与实施门禁.md) 的历史迁移与统一导入决策。

## 2. 本 Roadmap 只覆盖的容量组合

4000 万吞吐门禁仅覆盖：

```text
source_kind = server_path
+
ingestion_policy = historical_fill_only
```

`standard_observation` 虽然共用 Campaign、Chunk 和账本，但当前仍使用普通观测语义，**不能因为底层组件相同就继承 4000 万吞吐结论**。

## 3. 与 Brand/Vehicle Filter、Persistent Canonical Roadmap 的执行依赖

当前实现已经把 Excel 的入库前过滤从 Keyword Pack/车型混合选择迁移为冻结的 Brand/Vehicle Filter；[`docs/roadmap/05_可重放数据底座与监测重分类实施路线.md`](05_可重放数据底座与监测重分类实施路线.md) 只增加最小的 Persistent Canonical JSONL.gz Artifact 与 Replay，使成功归一化数据在 Filter 前被长期保留，并能在 Brand/Vehicle/Alias 变化后直接重筛。

为了避免完整 4000 万正式数据先走“无 Persistent Canonical”路径、随后再进行一次同规模 Canonical Backfill：

- 环境准备、生产授权、Backup/Restore 准备可以与 Roadmap 05 独立或并行推进；
- 业务急需的**过去一年数据**可以先按当前正式 Brand/Vehicle Filter 链导入、用于车型组共现、新 UI、报表和专题分析；Roadmap 05 Stage 4 再从现有 Source/Raw/历史 Chunk 补齐 Persistent Canonical，这不等价于提前执行完整 4000 万正式 Campaign；
- Gate A 的最终容量结论必须覆盖 Roadmap 05 完成后的实际生产数据路径，包括 Canonical JSONL.gz Artifact 的压缩、Artifact I/O、磁盘增长，以及 Replay 的有界读取/过滤资源边界；如果 Roadmap 05 的容量证据与本 Gate A 使用同一目标服务器、同一 `server_path + historical_fill_only` 组合且范围充分，可以复用，不机械重复；
- Gate C 的正式 4000 万生产 Campaign 默认在 Roadmap 05 Stage 1—4 全部完成、Persistent Canonical/Replay 和容量/恢复证据成立后执行；如果业务 Owner 未来明确批准更早执行，必须先证明该时点已经具备等价的 Canonical 持久化、Replay、容量和恢复事实，不能只因为当前 Brand/Vehicle Filter 已可用就跳过数据底座门禁；
- Roadmap 05 不建立 Monitoring Membership，也不会因后续 Filter 缩小自动删除/隐藏既有 Content；本 Roadmap 的生产逐行迁移账本继续保持自己的职责，最终全量对账使用同一 Brand/Vehicle 和 Content 身份事实。

## 4. Gate A：公司服务器容量演练

### 目标

在真实目标服务器执行 500 万条，或由业务 Owner 明确批准的等效比例容量演练，验证软件在真实 CPU、内存、磁盘、PostgreSQL、Artifact 和 I/O 条件下是否可接受。

### 必须记录

至少记录：

- 输入文件数、行数、有效/无效数据比例；
- 总耗时和稳定吞吐；
- CPU、内存峰值和持续区间；
- PostgreSQL 数据量、索引、WAL/磁盘增长；
- Artifact 临时/持久空间增长；
- Canonical JSONL.gz Artifact 的压缩比、总大小和写入/读取 I/O；
- Chunk/Job 并发与积压；
- created / filled / unchanged / conflict / filtered / duplicate / invalid / failed 等适用结果计数；
- Replay 读取 Canonical → Brand/Vehicle Filter 的吞吐与资源使用（如果在本次 Gate 范围内）；
- 失败重试、取消或接管是否造成重复副作用；
- 演练后数据库、Artifact 与逐行账本能否对账。

### 通过条件

吞吐和资源使用满足业务批准的 4000 万完成窗口与安全余量；不存在无法解释的数据差异、持续资源失控或恢复失败。如果不满足，先形成有证据的瓶颈 Change，不直接把并发参数无限调大。

## 5. Gate B：生产写授权与不可逆边界

容量通过不等于自动获得生产数据写权限。正式 4000 万执行前必须显式确认：

- 目标数据库/Artifact 根确实是生产环境；
- 数据来源目录和文件清单已冻结；
- `server_path + historical_fill_only` 配置正确；
- 当前应用/Schema/Release 版本已记录；
- 生产 Backup/Restore 或等效安全恢复边界已满足本次操作要求；
- 可接受的执行窗口、磁盘余量和停止阈值已确认；
- 业务 Owner 明确授权本次生产写入。

未经这些确认，不从开发/CI/容量测试自动跳到正式执行。

## 6. Gate C：正式 Campaign 执行

正式执行沿当前软件链路，不新增临时 SQL/ETL。Roadmap 05 完成后，实际生产链必须包含已经正式切换的 Persistent Canonical Artifact，不退回旧链绕过该能力：

```text
批准服务器目录
→ 创建 Data Import Campaign
→ Source Artifact / SHA-256
→ 全量预检
→ 用户显式开始
→ 有界 Chunk + 持久 Job
→ Mapper
→ Persistent Canonical JSONL.gz Artifact
→ Brand/Vehicle Monitoring Filter
→ Historical Fill-Only / Content Owner
→ PostgreSQL
→ 逐行结果 / 冲突账本
```

运行期间持续观察：

- Campaign/Job 状态和进度；
- 失败率、重试率和冲突变化；
- PostgreSQL/Artifact 磁盘余量；
- CPU/内存/WAL；
- Worker 积压和处理速率；
- Persistent Canonical Artifact 增长；
- 日志中的重复异常或数据完整性错误。

达到预设停止条件时应先停止/取消并保留可恢复事实，不为了“跑完 4000 万”继续扩大故障。

## 7. Gate D：全量对账

“Campaign succeeded”不是唯一完成证明。正式迁移完成至少需要：

```text
输入总行数
↔ 预检/Source 覆盖行数
↔ Mapper 成功 / invalid
↔ Persistent Canonical 行数
↔ Brand/Vehicle Filter matched / filtered
↔ 逐行终态账本
↔ created / filled / unchanged / conflict / duplicate / invalid / failed 汇总
↔ Content/Author/扩展事实增量
↔ 冲突账本
```

并确认：

- 每个已进入业务处理的输入行都有一个可解释终态；
- 所有成功生成合法 Canonical 的 observation 均在 Filter 前进入 Persistent Canonical Artifact；
- Historical Fill-Only 没有覆盖已有非空 Current；
- 冲突可定位回来源；
- 不可信历史 Metric 没有伪造当前观测；
- 同一业务身份的重复输入没有形成重复 Content；
- 失败/无效/过滤数据有明确数量和后续处置；
- Campaign、数据库、Raw/Source/Persistent Canonical Artifact、日志的最终资源状态可解释。

必要时抽样回查源 Excel 与数据库 Current/冲突记录，但抽样不能替代全量账本计数闭合。

## 8. AI 分析边界

生产历史导入不自动触发 LLM。数据迁移与 AI 成本/吞吐是两个独立问题：

```text
历史迁移完成
≠
自动分析 4000 万条
```

AI 继续由用户在声音广场显式创建 Analysis Run。大规模 AI 成本和本地分类器/LLM fallback 方案见 [`docs/appendix/13_AI大规模打标与成本优化方案.md`](../appendix/13_AI大规模打标与成本优化方案.md)，除非另有批准，不属于本生产迁移 Roadmap 的退出条件。

## 9. 非目标

本 Roadmap 不用于：

- 重写已完成的 Data Import Campaign；
- 改变 Content 业务身份；
- 用临时 SQL/ETL 绕过 Mapper/Canonical/Content Owner；
- 自动触发 AI；
- 引入新数据库、Kafka/Redis/第二套任务队列；
- 宣称 `standard_observation` 已获得相同 4000 万吞吐结论；
- 用开发机或 GitHub Runner 代替公司服务器容量证据。

## 10. 完成后的文档生命周期

Gate A—D 全部通过并形成可追溯生产证据后，本 Roadmap 完成。Historical Fill-Only、Campaign、Persistent Canonical/Replay（届时适用）、Analysis Run 等长期语义继续留在 Blueprint/Operations；生产执行证据进入对应 Change/运行记录与 Git，本文件从 live `docs/roadmap/` 退出。
