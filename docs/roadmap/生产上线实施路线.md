# AIMA_UGC 从当前代码到生产上线的实施路线

这篇文档是 AIMA_UGC **后续继续开发的正式 Roadmap**。

它不保存某个 Stage 当时怎样施工，也不替代代码、Contract、Migration 或测试。它只持续回答：

> **当前已经做到哪里，哪些目标仍未完成，下一步应该按什么顺序继续开发，直到生产服务器正式上线。**

文档分工：

```text
Blueprint 01—08
→ 长期架构和技术边界

Roadmap
→ 阶段状态、剩余目标、生产上线顺序

Appendix / Module README / Guide
→ 当前具体实现和调试方法

changes/archive
→ 已完成 Stage/Change 当时为什么这样设计、怎样验收

代码 / Contract / Migration / tests
→ 精确机器事实
```

因此，已完成 Stage 形成的旧 Blueprint 09—17 可以在当前有效知识完成迁移后删除；**未完成的后续目标必须继续保留在本 Roadmap，直到真正闭环。**

# 2. Roadmap 状态定义

只使用四种状态：

```text
已完成
→ 当前代码、Contract/Migration、测试和已合并交付可以证明主要目标闭环

部分完成
→ 已有正式实现，但原阶段仍有当前产品需要的剩余能力

待实现
→ 目标仍有效，但当前机器事实尚未落地

已被后续决策替代
→ 历史方案不再是待办，不能从旧 Stage 文档直接恢复实现
```

**Stage 名称不是完成证据。** 每次开始新任务仍要重新读取当前 `main` 的机器事实。

## 14.5 Stage 11C：协调 Backup / Restore

业务事实同时存在：

```text
PostgreSQL
+ ArtifactStore bytes
```

因此正确恢复单位是：

```text
Coordinated Backup Set
= PostgreSQL + ArtifactStore
```

只 `pg_dump` 或只复制文件都不够。

进入实现时需要通过独立高风险 Change 冻结：

```text
maintenance state / epoch
共享业务写屏障
Backup 独占屏障
Job/Scheduler 暂停语义
pg_dump / restore
Artifact snapshot / manifest
Backup Set metadata
restore verification
orphan Artifact reconciliation
RPO / RTO exercise
```

目标流程：

```text
业务写
→ 取得共享 write lock
→ 复核 maintenance epoch
→ PostgreSQL / Artifact 关联提交
→ 释放

Backup
→ maintenance
→ 停止新 Scheduler / Job 写入
→ 取得独占 lock
→ 等待已有 writer 退出
→ pg_dump + Artifact capture
→ 验证 Backup Set
→ 释放
```

精确 advisory lock key、表和状态机在 Stage 11C Change 中设计，不从 Roadmap 猜实现。

```text
认证/授权阻止未授权访问
容量/资源满足已批准目标
```

如果首次上线要求旧历史数据，Stage 11E 还必须包含 Stage 12 迁移的生产等价演练、对账和回滚边界；不能先验收“空系统上线”，再把必要历史迁移留成上线后的未知风险。

这些未通过前，系统仍是 Production No-Go。

# 15. 生产认证 / 授权：Stage 11 前置安全工作

当前后端没有正式企业认证/授权闭环。

上线前必须完成：

```text
External Identity Provider
→ Authentication Adapter
→ Principal / AuthContext
→ Backend Permission / Object Authorization
→ Frontend Login / Session Interaction
→ Security Tests
```

业务模块不能把飞书 `open_id/union_id` 等 Provider 私有身份当长期业务主键。

不能把：

```text
部署在内网
前端没有按钮
```

当成后端授权。

真正实现前需要业务确认身份 Provider、角色和 Permission 模型，属于 L3 安全 Change。

# 16. Stage 12：旧数据迁移

## 当前状态：部分基础已具备，是否需要完整执行取决于上线数据范围

当前已有：

```text
Excel → Canonical → Content Ingestion
processing_import_batches
ingestion.import-excel.v1
```

这提供了迁移基础，但当前没有完整的：

```text
Legacy Read-only Exporter
→ Canonical Importer
→ Historical reconciliation
```

如果生产上线需要迁入旧历史数据，必须明确：

- 旧数据源；
- 如何映射当前 Canonical；
- 稳定外部 ID 是否可信；
- 发布时间/来源如何保真；
- 只迁 Current 还是迁 Version/Metric 历史；
- 去重规则；
- 数量/Checksum/抽样对账；
- 失败重跑；
- 回滚。

迁移原则：

```text
旧系统 Read-only Exporter
→ 当前 Canonical / Import Service
→ 当前 Owner Repository
```

不让旧系统表结构污染当前业务模块。

**Stage 编号不是执行依赖顺序。** 如果首次上线必须带入旧历史数据，Stage 12 应在最终 Stage 11E 验收/切换之前完成方案、迁移演练和对账，并成为该次 Release 的条件门禁；如果首次上线不需要旧数据迁移，可以明确延期到生产上线以后。延期必须写入 Release 决策，而不是默认忽略。

# 17. 后续阶段设计合理性评估与实际开发顺序

## 17.1 总体结论

当前 Stage 0—12 的**能力拆分总体合理**，不需要重新编号或把已经完成的 Stage 1—8 再做一遍。真正需要修正的是执行模型：

```text
Stage 编号
≠ 必须严格串行的工程依赖
```

后续应明确分成两条线：

```text
生产硬门禁线
→ 不完成就不能 Production Go-Live

条件产品线
→ 只有产品/SLO 明确要求时才阻塞首发
```

生产硬门禁包括：认证授权、Stage 11A—11E，以及“首发必须带历史数据”时的 Stage 12。

条件产品线包括：Stage 9B Monitoring/Alert/VOC/Ticket 和 Stage 10B Web Report Center。它们可以继续开发，但不能仅因为 Stage 编号靠前就自动抢在生产安全能力之前。

## 17.2 推荐依赖图

先完成 P0 生产决策，然后按真实依赖推进：

```text
P0 生产关键业务决策
│  身份 Provider / Permission
│  RPO / RTO
│  数据保留
│  网络暴露
│  容量目标
│  首发是否必须迁旧数据
│
├─ P1 企业认证 / Backend Authorization
│
├─ P2 Stage 11A Docker / Compose / Production Config
│     └─ P3 Stage 11B Offline Release Bundle
│
├─ P4 Stage 11C Coordinated Backup / Restore
│
└─ P5 Stage 12 Legacy Migration（仅首发需要旧数据时）
      → 迁移方案 / 演练 / 对账 / 回滚边界

P1 + P3 + P4 +（P5，如果需要）
→ P6 Stage 11D Deploy / Rollback Automation
→ P7 Stage 11E Real Production Server Acceptance
→ Production Go-Live
```

这里有几个关键点：

1. **P0 必须先决策。** 认证、RPO/RTO、持久化、容量和旧数据要求都会改变后续设计，不能由 Agent 猜。
2. **P1、P2、P4 和条件 P5 不必机械串行。** P0 冻结后，它们可以作为独立 Change 并行设计/实现，但共享 `PlatformSettings`、Secret、生产目录、Release 配置时必须做并行冲突检查。
3. **Stage 11B 依赖 11A 的真实镜像/Compose 产物。** 不能先设计一个与最终镜像无关的 Release Bundle。
4. **Stage 11D 依赖可部署 Release 和可恢复 Backup。** 否则所谓 rollback 只能回应用文件，不能保证业务数据恢复边界。
5. **Stage 11E 是最终综合验收，不是“另一个独立功能”。** 它必须消费前面已经完成的认证、Release、Backup/Restore、Deploy/Rollback，以及首发所需的旧数据迁移。

## 17.3 条件产品能力怎么排

Stage 9B / 10B：

```text
Monitoring / Alert / VOC / Ticket
Web Report Center / durable Report Job
```

可以在 P0 后按产品优先级并行开发，但默认**不进入生产硬门禁链**。

只有当 P0 明确：

```text
没有告警就不能值守
或
没有网页报告中心就不能完成首发业务流程
```

它们才升级为该次 Go-Live 的阻塞条件，并进入 Stage 11E 验收矩阵。

这比“因为 Stage 9/10 编号在 Stage 11 前，所以必须先做完”更符合真实产品依赖。

## 17.4 Stage 12 为什么不能固定排在生产验收之后

旧数据迁移有两种完全不同的产品语义：

```text
首发不需要旧历史
→ Stage 12 可以上线后独立执行

首发必须展示/分析旧历史
→ Stage 12 是 Go-Live 前置
→ 必须在 Stage 11E 前完成生产等价演练与对账
```

因此原来“P7 可选产品功能 → P8 Legacy Migration”的固定顺序不合理，现改为条件依赖。

## 17.5 当前下一最小正式单元

从当前仓库机器事实看，下一步**不是继续扩 Monitoring 或 Report Center**，也不是直接开始写 Dockerfile。

先要完成 P0 中仍未冻结、会影响生产架构的业务决定：

```text
企业身份 Provider
角色 / Permission
生产网络暴露边界
RPO / RTO
数据/Artifact/Log 保留周期
容量/性能验收目标
首次上线是否必须迁旧历史数据
```

这些决定一旦明确，就可以把“企业认证/授权”和“Stage 11A Docker/Compose/Production Config”拆成独立 L3 Change 开始实施；Backup/Restore 也可在 RPO/RTO 与生产目录冻结后并行进入设计。

# 20. 与已完成 Stage 文档的关系

已完成 Stage 的详细施工文档不需要永久保留在核心 Blueprint。

本轮文档治理的最终原则：

```text
已完成 Stage 的当前有效技术事实
→ Core Blueprint / Appendix / Module README / Guide

未完成的后续技术目标
→ Roadmap

某个 Stage/Change 当时的施工过程和验收证据
→ changes/archive
```

因此，原 Blueprint 09—17 在完成知识迁移、测试依赖迁移和链接更新后可以删除。

以后如果要删除其他阶段型技术文档，也必须先证明：

```text
当前有效事实已有明确新承载
+ 当前代码事实已校正
+ 测试和链接已迁移
+ 未完成目标仍在 Roadmap
+ 历史原因仍可从 Change Archive 追溯
```

目标不是保留最多文件，而是**既不丢开发知识，也不让已完成阶段污染长期架构导航。**
