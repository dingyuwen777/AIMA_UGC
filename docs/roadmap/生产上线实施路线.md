# AIMA_UGC 从当前代码到生产上线的实施路线

这篇文档不是历史总结，而是**后续继续开发的正式路线图**。

目标只有一个：

> 在不破坏已经完成的架构和数据边界前提下，继续完成剩余业务能力、生产 Release、认证、安全、备份恢复和上线验收，最终让 AIMA_UGC 可以在生产服务器长期运行。

原 `docs/blueprint/06-开发约束与分阶段实施.md` 中 Stage 0—12 的设计仍然有效的部分在这里继续保留；已经由后续正式决策改变的部分会明确标记“已被替代”，不会静默删除，也不会让开发者按过期方案继续实现。

精确当前实现仍以代码、Contract、Migration、测试为准。

---

# 1. 先说结论：当前离“生产上线”还差什么

当前仓库已经不是原型。代码已经具备：

```text
PostgreSQL 18 业务事实库
+ Alembic Migration
+ 持久化 Job Runtime
+ API / Worker / Scheduler / Migration 分进程入口
+ TikHub 五平台 Operation / Mapper / Capability
+ Raw Artifact / Candidate / 来源追溯
+ Content Current / Version / Metric / Comment Coverage
+ Excel Import
+ Analysis / AI 打标
+ 正式 Excel Export
+ 离线 Markdown / Word 舆情报告
+ Vue 采集运行中心 / 采集策略 / 声音广场
```

对应事实入口：

```text
backend/src/aima_ugc/modules/
backend/src/aima_ugc/bootstrap/
backend/src/aima_ugc/entrypoints/
backend/src/aima_ugc/adapters/providers/tikhub/
frontend/src/app/routes.ts
frontend/src/features/
migrations/versions/
```

但当前仓库还**不能直接作为生产公网系统上线**，主要缺口是：

```text
企业认证 / 后端授权
生产 Dockerfile / Compose
正式生产 env / Secret 装配
离线 Release Bundle
固定镜像 digest / SBOM / 制品校验
生产 Migration 发布流程
PostgreSQL + Artifact 协调 Backup/Restore
正式恢复与回滚演练
生产服务器安装/初始化/升级 Runbook
生产 Smoke / Soak / 容量与恢复验收
Monitoring 告警/VOC/工单等后续业务域（如果产品仍需要）
```

当前分支根目录没有 `Dockerfile`、`compose.yaml` 或 `env.production.example`；因此任何写成“现在执行 docker compose 即可生产部署”的文档都属于错误事实。

# 2. 状态规则

每个阶段使用：

```text
已完成
部分完成
待实现
已被后续决策替代
```

“已完成”必须能找到当前机器事实，不因为 README 写了 done 就算完成。

“待实现”不是历史废话。只要该设计仍是达到生产目标所需要的，就必须继续保留并指导后续开发。

# 14. Stage 11：生产 Release —— 当前最关键的未完成阶段

## 原设计目标

```text

Compose
Migration
离线 Bundle
备份

```

预期结果：

> 全新 Ubuntu 服务器可以在不 `git pull`、不现场编译依赖的情况下部署一个可验证、可回滚的正式 Release。

## 当前状态：待实现 / 生产 Go-Live 阻塞项

当前仓库根没有：

```text
Dockerfile
compose.yaml
compose.production.yaml
env.production.example
```

所以 Stage 11 不能标记完成。

## 14.1 生产服务拓扑的已批准方向

原设计保留：

```text
frontend
api
worker
scheduler
migrate
postgres
```

其中：

```text
migrate
→ 一次性发布步骤，不是常驻业务进程
```

API/Worker/Scheduler/Migration 复用同一 Python 应用代码，不拆微服务仓库。

## 14.2 生产宿主目录设计

原批准目录仍保留为目标：

```text
/data/docker
/data/AIMA_UGC/runtime/data
/data/AIMA_UGC/runtime/logs
/data/AIMA_UGC/postgres
/data/AIMA_UGC/backups
/data/AIMA_UGC/releases
/data/AIMA_UGC/shared/env
/data/AIMA_UGC/shared/secrets
```

职责：

```text
/data/docker
→ Docker 自身 data-root

/data/AIMA_UGC/postgres
→ PostgreSQL 数据

/data/AIMA_UGC/runtime/data
→ Local Artifact 等运行时业务文件

/data/AIMA_UGC/runtime/logs
→ api/worker/scheduler 日志

/data/AIMA_UGC/releases
→ 每个不可变 Release

shared/env / shared/secrets
→ 跨 Release 的配置/Secret

backups
→ 协调 Backup Set
```

不要把数据库和业务文件塞进 Docker data-root。

PostgreSQL 18 生产镜像的实际持久卷挂载点、UID/GID 等在 Stage 11 实现时必须用当时选定镜像真实验证，不从历史文字猜。

## 14.3 生产镜像与 Compose 要实现什么

后续 Stage 11 Change 至少需要新增：

```text
Dockerfile
compose.yaml
compose.production.yaml
env.production.example
release build/package scripts
release/deploy verification scripts
```

要求：

- 根目录是唯一 Docker build context；
- Backend/Frontend 多阶段构建；
- 生产不运行 `pip install` / `npm install`；
- 基础镜像固定版本并在 Release Manifest 固定 digest；
- 应用以非 root 运行；
- Secret 以只读文件进入 `/run/secrets` 或等价受控目录；
- Postgres 不对公网开放；
- Nginx/Frontend 同源代理 API；
- Healthcheck 使用镜像真实存在的工具；
- Compose 生产 bind mount 不依赖 Docker 默默创建目录；
- 日志和 Artifact 落到宿主持久目录。

## 14.4 Release Bundle 设计不能丢

原设计的离线包结构继续作为目标：

```text
AIMA_UGC-v<version>-deploy.tar.gz
├─ images.tar
├─ compose.yaml
├─ compose.production.yaml
├─ env.production.example
├─ release-manifest.json
├─ migration-manifest.json
├─ SHA256SUMS
├─ SBOM/
├─ SIGNATURES/
└─ DEPLOY.md
```

生产服务器原则：

```text
禁止 git pull 部署
禁止现场 npm/pip 安装
禁止现场 build 代替已验证 Release
```

发布应从固定 Git SHA 构建，并能证明镜像、Migration、Contract 和制品来源。

## 14.5 生产发布顺序

原设计保留为 Stage 11 实现目标：

```text
确认目标 Git SHA 和 CI
→ 获取 Release Bundle
→ 验证来源/签名和 SHA-256
→ 检查磁盘/配置/Secret
→ 暂停 Scheduler 和新高风险写入
→ 等待/取消运行中 Job
→ 建立协调 Backup Set
→ 导入镜像
→ 执行 Migration
→ 校验 Compose
→ 启动 PostgreSQL/API/Worker/Scheduler/Frontend
→ health/readiness
→ 关键业务 smoke
→ 恢复 Worker/Scheduler
→ 观察日志和数据库状态
```

这套顺序目前是**已批准设计，尚未代码化的发布流程**。

## 14.6 Backup/Restore 是 Stage 11 必做，不是文档装饰

业务数据同时存在：

```text
PostgreSQL metadata/business facts
+ ArtifactStore bytes
```

只备份一个都不能完整恢复。

目标恢复单位：

```text
PostgreSQL + ArtifactStore 的协调 Backup Set
```

原设计中的共享写屏障、独占 backup lock、maintenance epoch、Artifact rename/delete 协调等机制目前尚未实现。

因此 Stage 11 必须通过独立 Change 设计并实现：

- 写入屏障；
- 备份状态；
- pg_dump/恢复；
- Artifact 清单/快照；
- Backup Set 一致性；
- restore verification；
- 回滚；
- 孤儿 Artifact 对账；
- RPO/RTO 演练。

## 14.7 认证是正式上线前置条件

当前后端没有正式企业认证/授权闭环。

生产上线前必须：

```text
选择真实身份 Provider
→ Authentication Adapter
→ Principal/AuthContext
→ 后端 Permission/Object authorization
→ 前端登录/Session 交互
→ 安全测试
```

不能把“部署在内网”“前端没有按钮”当成授权机制。

## 14.8 Stage 11 验收

至少需要实际证明：

```text
linux/amd64 Release 能构建
离线服务器无 git/no build 部署成功
全新 PostgreSQL 可 migrate 到 head
旧正式 revision 可升级
API/Worker/Scheduler/Frontend 全部启动
health ready 成功
一次 Import / 一次 Collection / 一次 Analysis / 一次 Export 可跑通
日志/Artifact/PostgreSQL 均落持久目录
重启容器数据不丢
服务器重启后恢复正常
备份可在隔离环境完整恢复
应用回滚路径真实演练
镜像/Release 校验可验证
生产 Secret 不泄露
认证/授权阻止未授权访问
```

Stage 11 未通过这些验收前，仍是生产 No-Go。

这为旧数据迁移提供了基础，但当前没有单独的“旧系统 Exporter + 完整历史迁移 + 对账”正式模块/流程。

如果生产上线需要把旧系统历史数据迁入，应在上线前确认：

```text
旧数据来源
→ 能否转成当前 Canonical
→ 稳定 ID 是否可信
→ 时间/来源如何保真
→ 是否导入历史 Version/Metric，还是只导入当前快照
→ 去重规则
→ 对账方式
→ 回滚方式
```

然后通过独立 Migration/Import Change 实施。

如果生产首次上线不需要迁移旧系统历史数据，Stage 12 可以明确延期，但必须在 Release 决策中写清楚，而不是默认忽略。

# 16. 当前建议的实际下一阶段顺序

为了尽快达到“可以生产上线”，当前不应该重新开发已经完成的 Stage 1—8。

推荐顺序：

```text
P0：补齐 Stage 0 的生产决定
    → 身份/权限
    → RPO/RTO
    → 数据保留
    → 网络暴露

P1：生产认证/授权

P2：Stage 11A Docker/Compose/生产配置基础
    → Dockerfile
    → Compose
    → production env/secrets
    → 持久目录
    → 本地/CI build + smoke

P3：Stage 11B 离线 Release Bundle
    → images.tar
    → manifest/checksum/signature/SBOM
    → no-build/no-pull deploy

P4：Stage 11C Backup/Restore/回滚
    → PostgreSQL + Artifact 协调一致性
    → 恢复演练

P5：生产服务器真实部署与验收
    → migrate
    → startup
    → smoke
    → restart/reboot
    → backup/restore
    → rollback
    → monitoring/logging

P6：按产品优先级继续 Stage 9 Monitoring / Stage 10 报告产品化

P7：需要时执行 Stage 12 旧数据迁移
```

其中 Stage 9 Monitoring 是否必须挡住首次上线，要由产品目标决定；**Stage 11 Release、安全和恢复不能跳过。**

# 17. 下一次让 GPT/Codex 继续开发时怎么判断阶段

每次新会话不要只说“继续 Stage 11”。正确做法：

```text
1. 读取 AGENTS.md
2. 读取本 Roadmap
3. 读取 07 技术决策与实施门禁
4. 重新检查当前 main 的代码/文件/PR/CI
5. 判断上一个最小单元是否真正闭环
6. 未闭环先完成，不跳阶段
7. 一次只做一个可独立验收的正式单元
8. 完成后更新本 Roadmap 的当前状态和下一步
```

Stage 是导航，不是事实源；代码/Migration/Contract/测试仍是事实源。

# 18. 生产 Go-Live 最终清单

只有下面全部满足，才能把系统从“开发可运行”改成“生产可上线”：

- [ ] 生产身份认证和后端授权已实现并验证；
- [ ] 生产 Dockerfile/Compose/环境配置已进入仓库；
- [ ] API/Worker/Scheduler/Migration/PostgreSQL/Frontend 服务拓扑已验证；
- [ ] 镜像固定 digest，不在服务器现场 build；
- [ ] Release Bundle 可离线部署；
- [ ] Secret 不进 Git/镜像/日志/业务表明文；
- [ ] PostgreSQL 和 Artifact 均使用持久目录；
- [ ] Migration 从空库和上一正式 Revision 验证；
- [ ] API/Worker/Scheduler 重启恢复验证；
- [ ] 关键业务流程生产 Smoke 通过；
- [ ] PostgreSQL + Artifact 协调备份可以恢复；
- [ ] 应用回滚和数据库兼容/恢复策略演练；
- [ ] 日志轮转、磁盘和健康检查验证；
- [ ] 生产容量/资源使用达到已批准目标；
- [ ] 安全/Secret/出站/下载边界通过检查；
- [ ] 当前 Release 对应 CI 全绿；
- [ ] DEPLOY / BACKUP / RESTORE / ROLLBACK 文档与实际脚本一致；
- [ ] 如果需要旧数据迁移，Stage 12 对账完成；
- [ ] 未完成但允许延期的业务功能有明确批准，不影响生产安全和数据完整性。
