# AIMA_UGC 从当前代码到内网 V1 与完整生产上线的实施路线

这篇文档是 AIMA_UGC **长期开发与上线 Roadmap**。

它持续回答两类不同问题：

> **当前下一步做什么，怎样先把现有系统做成公司内网可用的 V1？**
>
> **内网 V1 之后，还差哪些生产强化能力才能达到完整 Production Go-Live？**

当前近期执行细节见：

[`内网V1上线实施计划.md`](内网V1上线实施计划.md)

文档分工：

```text
Blueprint 01—08
→ 长期架构和技术边界

本 Roadmap
→ 阶段状态、剩余目标、内网 V1 与完整 Production 顺序

内网 V1 实施计划
→ 当前最近几个开发单元的具体执行路线和验收

Appendix / Module README / Guide
→ 当前具体实现和调试方法

changes/archive
→ 已完成 Stage/Change 当时为什么这样设计、怎样验收

代码 / Contract / Migration / tests
→ 精确机器事实
```

**重要：现在必须区分“公司内网 V1 上线”和“完整 Production Go-Live”。**

公司内网 V1 是一个经业务 Owner 明确缩小范围的近期交付里程碑；它不是把长期 Production 安全、灾备和治理要求删除掉。

# 2. Roadmap 状态定义

只使用四种状态：

```text
已完成
→ 当前代码、Contract/Migration、测试和已合并交付可以证明主要目标闭环

部分完成
→ 已有正式实现，但原阶段仍有当前产品需要的剩余能力

待实现
→ 目标仍有效，但当前机器事实尚未落地

已被后续决策替代
→ 历史方案不再是待办，不能从旧 Stage 文档直接恢复实现
```

**Stage 名称不是完成证据。** 每次开始新任务仍要重新读取当前 `main` 的机器事实。

# 3. 当前已经冻结的近期产品与部署边界

## 3.1 公司内网 V1 已确认

```text
访问范围
→ 公司服务器
→ 公司内部网络可访问
→ 不对公网开放

Authentication / Authorization
→ 首版延期
→ 后续可扩展

Legacy Migration
→ 首版延期
→ 第一版以新系统数据为准
→ 需要展示的数据可以通过 Excel 导入

第一版最关键业务链
→ Excel 页面上传
→ Worker 处理
→ PostgreSQL 入库
→ 采集运行中心显示状态
→ 声音广场显示导入数据
```

这些是已确认的产品决定，后续 Agent 不得把认证、权限和历史迁移重新静默恢复成公司内网 V1 的前置阻塞项。

## 3.2 暂不需要为内网 V1 先冻结的长期数字

以下项目继续保留，但可以在内网 V1 上线后根据真实使用情况再正式冻结：

```text
正式 RPO / RTO
Raw / Content / Artifact / Log 长期 Retention
正式容量 / 性能 / Soak 目标
正式告警和值班 SLO
完整 Coordinated Backup / Restore
完整 Release provenance / SBOM / 签名
```

这不是说这些能力不重要，而是：

> 它们不应继续阻塞当前“先把现有功能做通并在公司内网用起来”的近期目标。

## 3.3 内网 V1 仍然不能省略的基础门禁

即使首版范围缩小，也不能省略：

```text
真实前后端业务闭环
PostgreSQL 持久化
Artifact 持久化
日志持久化
Secret 不进 Git / 镜像 / 页面 / 日志
Health / Readiness
Migration 能从空库到 head
API / Worker / Scheduler 进程都真正运行
容器重启后数据不丢
宿主机 reboot 后数据仍可恢复运行
公司网络访问边界明确
PostgreSQL 不向普通客户端网络暴露
真实 Excel Full-stack Smoke
```

当前分工已经明确：

```text
Stage 8F
→ 证明真实前后端业务闭环与 Excel Full-stack

Internal V1-A
→ 证明容器化 Migration、正式进程、持久目录、只读 Secret、Readiness、PostgreSQL/API 不发布宿主端口

Internal V1-B
→ 在真实公司服务器验证公司网络、真实浏览器/业务、真实 Secret、容器重启与宿主机 reboot
```

因此剩余的内网 V1 风险已经从“仓库有没有可部署栈”收敛为“真实公司服务器能否按批准边界稳定运行并通过业务验收”。

# 15. Internal V1-A：最小可部署 Docker / Compose / Config

## 当前状态：已完成

这是公司内网 V1 的部署基础。它复用 Stage 11A 的长期方向，但只完成当前内网 V1 所需的最小范围。

已实现：

```text
Dockerfile
.dockerignore
compose.yaml
env.production.example
deploy/nginx.conf
scripts/deploy/prepare_host.py
backend Internal V1 configure one-shot
.github/workflows/internal-v1a.yml
```

服务拓扑：

```text
frontend
api
worker
scheduler
migrate
configure
postgres
```

其中 `migrate`、`configure` 是一次性 tools profile 动作，不是常驻服务。

当前实现与验证证明：

- 仓库根是唯一 build context；
- Backend / Frontend 采用多阶段构建；
- API/Worker/Scheduler/Migration/Configure 使用同一 Backend image 不同正式 command；
- Frontend 使用生产 Vue build 输出和非 root Nginx Runtime；
- `/api`、`/health` 通过 Nginx 同源代理 API；
- PostgreSQL 18.4 使用宿主持久目录 `/data/AIMA_UGC/postgres`，容器挂载点按 PostgreSQL 18 使用 `/var/lib/postgresql`；
- Local ArtifactStore 使用宿主 `/data/AIMA_UGC/runtime/data`；
- `.log` 使用宿主 `/data/AIMA_UGC/runtime/logs`；
- Secret 使用宿主 `/data/AIMA_UGC/shared/secrets` → `/run/secrets` 只读装配；
- 宿主准备工具固定目录 UID/GID/权限，不使用 `chmod 777`，不静默轮换已有 Secret；
- TikHub/LLM 外部 Key 不由脚本生成，不进入 `env.production`、数据库、镜像或 Git；
- 生产运行不读取本地 `env.local`；
- Provider Config one-shot 只保存非敏感配置和 `secret_ref`；
- 空 PostgreSQL 能显式 `alembic upgrade head`；
- PostgreSQL/API 无宿主 PortBindings；
- Frontend 是唯一宿主 HTTP PortBinding，默认只绑定 `127.0.0.1:8080`；
- `/health/ready` 通过正式 Nginx→API 链检查 PostgreSQL、ArtifactStore、日志目录；
- API/Worker/Scheduler 共用同一 PlatformSettings/Database/Artifact/Secret 运行时事实。

长期目录继续使用：

```text
/data/docker
/data/AIMA_UGC/runtime/data
/data/AIMA_UGC/runtime/logs
/data/AIMA_UGC/postgres
/data/AIMA_UGC/backups
/data/AIMA_UGC/releases
/data/AIMA_UGC/shared/env
/data/AIMA_UGC/shared/secrets
```

独立永久门禁：

```text
.github/workflows/internal-v1a.yml
→ 隔离 Ubuntu Runner
→ 宿主目录/Secret 准备与 check-only
→ Compose topology
→ Backend / Frontend 实际 build
→ 空库 Migration
→ Provider Config
→ PostgreSQL 容器重建持久化
→ api / worker / scheduler / frontend 正式启动
→ Nginx readiness
→ 非 root / RW data+log / RO Secret
→ Docker PortBindings
→ Artifact marker 与宿主日志/PG 数据目录
```

# 17. 认证 / Authorization

## 当前状态：完整 Production 待实现；公司内网 V1 明确延期

长期身份边界不变：

```text
External Identity Provider
→ Authentication Adapter
→ Principal / AuthContext
→ Backend Permission / Object Authorization
→ 业务 Service
```

业务模块不能把飞书 `open_id/union_id` 等 Provider 私有身份当长期业务主键。

2026-08-22 的当前产品决定是：

```text
公司内网 V1
→ 不实现登录
→ 不实现角色 / Permission
→ 不做权限隔离
```

该决定仅适用于：

```text
公司受控服务器
+ 公司内部网络访问
+ 不对公网开放
```

它不意味着“内网等于认证”。

以下任一条件出现时，认证/授权重新升级为前置门禁：

- 暴露到公司网络之外；
- 需要区分不同用户可见/可操作能力；
- 需要审计具体操作人；
- Provider 配置、Raw、Export 或其他敏感资源需要细粒度保护；
- 进入完整 Production Go-Live。

# 18. Stage 11：完整 Production Release

## 当前状态：长期待实现；直接复用 Internal V1-A 部署基础

Stage 11 不再阻塞“先完成内网 V1”，但仍是完整 Production Go-Live 的核心阶段。

完整设计：

[`../appendix/生产部署与离线Release方案.md`](../appendix/生产部署与离线Release方案.md)

## 18.1 Stage 11A：Production Docker / Compose Hardening

Internal V1-A 已提前实现并验证：

- 根多阶段 Dockerfile；
- 单一根 Compose 服务拓扑；
- 非 root Backend/Frontend Runtime；
- 持久 PostgreSQL/Artifact/log bind mount；
- 只读 Secret mount；
- 空库 Migration；
- Health/Readiness；
- 隔离 Linux Compose smoke；
- PostgreSQL/API 不发布宿主端口。

Stage 11A 不得重复造第二套基础，而应基于这些事实增量完成完整 Production 要求：

- 不可变 image/digest 绑定；
- 必要时增加有独立语义的 `compose.production.yaml`；
- 正式 HTTPS/Host/浏览器安全与认证入口；
- 生产资源/安全覆盖；
- CI linux/amd64 Release build；
- no-build/no-pull Compose smoke；
- 不在目标服务器临时联网安装依赖；
- 不通过现场修改容器文件修复正式版本。

## 18.2 Stage 11B：离线 Release Bundle

长期目标包结构：

```text
AIMA_UGC-v<version>-deploy.tar.gz
├─ images.tar
├─ compose.yaml
├─ compose.production.yaml
├─ env.production.example
├─ release-manifest.json
├─ migration-manifest.json
├─ SHA256SUMS
├─ SBOM/
├─ SIGNATURES/
└─ DEPLOY.md
```

`release-manifest.json` 至少记录：

- Release version；
- Git SHA；
- build time；
- target platform；
- image digest；
- Alembic head；
- Contract/OpenAPI hash/版本；
- 最低 Docker/Compose 版本；
- Migration 兼容性；
- rollback 边界；
- SBOM/签名信息。

完整 Production 原则：

```text
禁止 git pull 部署
禁止现场 pip/npm install
禁止现场 build 代替已验证 Release
```

Internal V1-A 当前允许在受控仓库验收环境构建镜像，只用于证明最小部署栈；它不改变上面的正式 Release 原则。

## 18.3 Stage 11C：协调 Backup / Restore

完整 Production 的恢复单位仍是：

```text
Coordinated Backup Set
= PostgreSQL + ArtifactStore
```

只 `pg_dump` 或只复制文件都不足以证明完整恢复。

长期目标机制：

```text
业务写
→ 取得共享 write lock
→ 复核 maintenance epoch
→ PostgreSQL / Artifact 关联提交
→ 释放

Backup
→ maintenance
→ 停止新 Scheduler / Job 写入
→ 取得独占 lock
→ 等待已有 writer 退出
→ pg_dump + Artifact capture
→ 验证 Backup Set
→ 释放
```

精确 advisory lock key、表和状态机仍在 Stage 11C Change 中设计。

公司内网 V1 当前允许延期这套完整机制，但 Internal V1-A 已先保证 PostgreSQL/Artifact 使用持久目录，避免“没有协调备份”退化成“容器删除即数据消失”。

## 18.4 Stage 11D：正式发布和回滚自动化

长期目标：

```text
preflight
verify release
backup
migrate
start
health/smoke
rollback
logs/diagnosis
```

正式发布顺序：

```text
确认目标 Git SHA + CI
→ 获取 Release Bundle
→ 验证来源 + 完整性
→ 检查磁盘/目录/UID/GID/Secret
→ 暂停 Scheduler / 新高风险写入
→ 等待或受控取消运行中 Job
→ 建立协调 Backup Set
→ docker load
→ Migration
→ compose config
→ 启动 API / Worker / Scheduler / Frontend
→ live / ready
→ 关键业务 smoke
→ 恢复 Scheduler / Worker
→ 观察日志 / Job / DB / 磁盘
```

## 18.5 Stage 11E：完整真实生产验收

完整 Production 最终必须证明：

```text
全新服务器可从正式 Release 部署
空 PostgreSQL 可 migrate 到 head
上一正式 revision 可升级
API / Worker / Scheduler / Frontend 可启动
live / ready 正确
Import 可执行
Collection 可执行
Analysis 可执行
Excel Export 可执行
日志 / Artifact / PostgreSQL 落持久目录
容器重启后数据不丢
宿主机 reboot 后系统可恢复
协调 Backup 可在隔离环境恢复
应用 Rollback 真实演练
Secret 不泄露
认证/授权阻止未授权访问
容量/资源满足批准目标
```

这些完整条件未满足前，仍不能把内网 V1 叫做“完整 Production Go-Live”。
