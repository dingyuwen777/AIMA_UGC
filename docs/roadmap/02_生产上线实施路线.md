# 完整 Production Go-Live 实施路线

- 状态：Active
- 目标：完成 AIMA_UGC 从已上线公司内网 V1 到完整 Production Go-Live 的生产强化。
- 退出条件：企业认证与正式授权、HTTPS/浏览器安全、协调 Backup/Restore、Release 供应链强化、生产发布/回滚流程和真实生产安全/容量/恢复验收全部形成正式证据并满足 Go-Live。
- 依赖：当前 Internal V1/离线 Release 基线，以及业务 Owner 对正式生产范围、RPO/RTO、Retention、容量/SLO 等数值的批准。

本文只维护**仍未完成的 Production 门禁**。已经完成的 Stage、内网 V1 施工过程和历史 CI/PR 不在这里重复维护；历史见 [`changes/archive/`](../../changes/archive/) 与 Git。

## 1. 当前已经具备的基线

以下能力已经存在，后续 Production 工作必须复用，不重新造第二套运行时：

- 公司内网 V1 已完成并由业务 Owner 确认；
- API / Worker / Scheduler / Migration 分进程；
- PostgreSQL 18 + Alembic + PostgreSQL Durable Job Runtime；
- 根 [`Dockerfile`](../../Dockerfile)、canonical [`compose.yaml`](../../compose.yaml)、[`env.production.example`](../../env.production.example)；
- bootstrap → PostgreSQL → migrate → configure → API/Worker/Scheduler → frontend 的 Compose 启动链；
- Linux/公司服务器 `AIMA_HOST_ROOT` 持久化边界和 Windows storage-only override；
- 内部随机 Secret 与外部 Provider/LLM Secret 的文件化边界；
- Health/Readiness、Migration、持久数据和重启恢复的 Internal V1 基线；
- Provider-neutral `Principal`、`administrator/user` 角色语义和管理员后端授权守卫；
- GitHub 离线 Release 基础：Linux/AMD64 镜像、`images.tar`、release/migration manifest、`SHA256SUMS`、`DEPLOY.md`、`--no-build --pull never` 回放、GHCR digest、Tag/Release 基础。

部署与 Release 当前实现见 [`docs/operations/01_生产部署与离线Release方案.md`](../operations/01_生产部署与离线Release方案.md)。

## 2. P0：企业认证与正式 Authorization 验收

### 当前已有

后端业务已经使用 Provider-neutral Principal，并由后端对管理员写操作执行角色校验。前端管理员路由守卫只改善交互，不承担安全边界。

### 仍需完成

- 飞书或后续正式企业身份提供方的真实登录/回调；
- Token/Session/Claims 的验证与生命周期管理；
- 已验证 Claims → Principal 的正式 Identity Adapter；
- Principal 过期、撤销、登出和失效语义；
- 普通用户与管理员的对象级/操作级生产授权验收；
- 认证失败、权限不足、会话过期等浏览器端真实流程；
- 审计事件能够追溯真实 Principal，而不是 Development Principal。

### 退出条件

在隔离生产候选环境中完成真实身份提供方登录、普通用户/管理员正反向授权、过期/撤销和审计验收；Development Identity 不再作为正式 Production 身份来源。

## 3. P0：HTTPS 与浏览器安全边界

### 当前已有

应用侧 Frontend Nginx 已建立浏览器安全响应头基线：HSTS（不启用 `includeSubDomains`/`preload`）、enforced CSP、Permissions-Policy、`X-Content-Type-Options` 与 `Referrer-Policy`；旧版 `clientaccesspolicy.xml` / `crossdomain.xml` 显式返回 404。该基线保持 `server_name _;`、8080 监听、`/api/`、`/health/` 和 SPA fallback 不变，也不在应用层强制 HTTP→HTTPS，因此服务器绑定与防火墙允许时仍可保留 IP+端口的内网诊断入口。

### 仍需完成

完整 Production 不能只依赖“公司网络”。需要结合最终入口方式明确并验证：

- TLS/HTTPS 终止位置与证书更新；
- 最终公网/企业反向代理与应用 Nginx 的响应头所有权，避免重复或冲突注入 HSTS；
- 安全 Cookie/Session 策略（若正式认证使用 Session）；
- CORS/同源策略；
- CSRF/重放边界（按最终认证方式）；
- 浏览器缓存策略，以及生产候选环境中 CSP 对真实页面、图片、图表、接口请求的兼容验收；
- 管理员配置、下载 Artifact、历史目录等敏感对象的对象级授权；
- 反向代理、客户端 IP、请求 ID 与审计链的一致性；
- 对最终 HTTPS 入口执行响应头检查和安全扫描复验。

不在 Roadmap 里提前写死具体网关产品；由目标生产基础设施和正式认证方案决定实现。应用侧响应头完成不等于本 P0 已完成，GitHub Runner 也不能替代真实生产候选 HTTPS 入口证据。

## 4. P0：协调 PostgreSQL + Artifact Backup/Restore

当前持久业务事实不只在 PostgreSQL：ArtifactStore 也保存 Raw、输入、导出等需要协同恢复的文件。因此 Production 不能只做数据库 dump。

仍需形成：

```text
协调 Backup Set
→ PostgreSQL 一致性点
→ Artifact 一致性边界
→ 内部 Secret/必要配置保护
→ Manifest / 校验和
→ 可恢复版本身份
```

并完成：

- 业务 Owner 批准 RPO/RTO；
- 备份频率、Retention、加密和访问控制；
- 备份成功/失败可观察性；
- 空环境 Restore；
- 恢复后数据库 ↔ Artifact reconciliation；
- Secret 丢失/损坏的 fail-closed 与恢复流程；
- 至少一次真实 Restore Drill，并记录恢复时长和未满足项。

长期边界见 [`docs/blueprint/05_日志安全部署与运维.md`](../blueprint/05_日志安全部署与运维.md)。

## 5. P1：Release 供应链强化

当前离线 Bundle 基础已经成立，剩余重点不是重新做 `images.tar`，而是把候选版本的来源和兼容性证明补完整：

- 为正式 Release 生成 SBOM；
- 形成独立来源的签名/验证方案；
- 补足 provenance/构建身份链；
- 固化应用版本、数据库 Migration、PostgreSQL 镜像与 Bundle 的兼容矩阵；
- 在服务器导入前验证 manifest、digest、签名和目标平台；
- Release 证据不包含真实 Secret。

不要把“GitHub Tag 存在”当成完整供应链证明。

## 6. P1：生产发布、升级与回滚闭环

正式 Production 发布至少需要把以下步骤形成可重复、可审计的操作链：

```text
preflight
→ 校验目标主机/磁盘/网络/版本/Secret
→ 协调备份
→ 导入并验证 Release
→ migrate
→ start / readiness
→ 关键业务 smoke
→ 观察窗口
→ 成功收口
```

失败时必须区分：

- 应用版本可直接回滚；
- 数据库 Migration 是否允许 downgrade；
- 不可安全 downgrade 时怎样 restore Backup Set；
- Artifact/数据库如何保持同一恢复点；
- 回滚后如何 reconciliation。

目标不是堆一组 shell 命令，而是保证每个不可逆边界都有前置检查、证据、失败策略和恢复路径。

## 7. P1：真实生产验收

最终 Go-Live 需要在目标生产基础设施取得新鲜证据，至少覆盖：

- 认证与授权安全；
- HTTPS/浏览器安全；
- 正式 Secret 装配；
- 容量、吞吐、磁盘增长、WAL、Artifact 增长；
- 长时间运行/Soak；
- 容器、进程、宿主机重启恢复；
- Backup/Restore Drill；
- Release/rollback 演练；
- 关键业务 Browser → Vue → API → PostgreSQL/Worker → Vue Smoke；
- 失败路径、诊断信息和审计可追溯。

CI、开发机 Docker 和 GitHub Runner 都不能替代真实生产候选环境证据。

## 8. 不属于本 Roadmap 的候选产品能力

以下能力不是完整 Production Go-Live 的自动组成部分，也没有因旧 Stage 文档提到就成为当前施工项：

- Monitoring / Alert / VOC / Ticket 产品模块；
- Web Report Center；
- 通用 Dashboard；
- Gold Set / 自动模型评测；
- 双人审批；
- 个人导出列配置；
- Provider 自动 Availability 观测；
- 大范围 Count 估算基础设施/SLO。

若未来确认业务需要，单独建立需求来源、Issue/Change 和验收标准。

## 9. 实施原则

1. 每个高风险主题拆独立 L3 Change，不做一个“生产化大重构”。
2. 先恢复当前机器事实，再决定该 Change 的最小可交付闭环。
3. 不重写已经工作的 Docker/Compose/Job/Owner 体系。
4. 不在没有业务数据前随意拍 RPO/RTO、Retention、容量数字。
5. 所有完成声明以当前实现 + 当前环境 + 新鲜验证证据为准。
6. 当本页所有退出条件满足并由业务 Owner 批准 Go-Live 后，本 Roadmap 完成并退出 live `docs/roadmap/`。
