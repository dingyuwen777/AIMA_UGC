# AIMA_UGC 从当前代码到内网 V1 与完整生产上线的实施路线

这篇文档是 AIMA_UGC **长期开发与上线 Roadmap**，持续回答两类问题：

> **当前下一步做什么，怎样先把现有系统做成公司内网可用的 V1？**
>
> **内网 V1 之后，还差哪些生产强化能力才能达到完整 Production Go-Live？**

近期执行细节见 [`01_内网V1上线实施计划.md`](01_内网V1上线实施计划.md)。长期架构看 Blueprint；具体实现看 Appendix/模块 README；精确机器事实看代码、Contract、Migration、tests、locks；历史施工证据看 `changes/archive/`。

**公司内网 V1 与完整 Production Go-Live 必须继续区分。** 内网 V1 是经业务 Owner 明确缩小范围的近期里程碑，不等于删除长期安全、灾备和治理要求。

# 1. 当前总状态

当前仓库主要业务基础已经形成：

```text
PostgreSQL 18 + Alembic
PostgreSQL Durable Job Runtime
API / Worker / Scheduler / Migration 分进程
TikHub 五平台 Operation / Mapper / Capability
Raw Artifact / Candidate / 来源追溯
Content Current / Version / Metric / Coverage
Excel Import
Analysis / AI 打标
正式 Excel Export
离线 Markdown / Word 舆情报告
Vue 采集运行中心 / 采集策略 / 声音广场
Stage 8F 真实 Excel Browser Full-stack Acceptance
Local Dev Bootstrap
Internal V1-A Docker / Compose / Production Config / 持久化 / Secret / Readiness
Windows Docker Desktop mixed-storage Compose compatibility
```

完整容器 Runtime 继续只维护一个业务基线：

```text
Dockerfile
compose.yaml
+ env.production
```

Linux / WSL / 公司服务器使用 canonical `compose.yaml`。宿主持久目录只配置：

```text
AIMA_HOST_ROOT
→ Linux / WSL 本地：./.runtime/compose
→ 公司服务器 / Production：/data/AIMA_UGC
```

Windows Docker Desktop 原生 CMD / PowerShell 不把 PostgreSQL/内部 Secret bind mount 到 NTFS，而是在 canonical `compose.yaml` 之上叠加 storage-only `compose.windows.yaml`：

```text
同一个 env.production
compose.yaml + compose.windows.yaml
→ Artifact / 应用日志：AIMA_HOST_ROOT bind mount
→ PostgreSQL / 内部 Secret：Docker-managed named volumes
```

Windows override 只改变持久 storage source，并为 data/log bind 增加最小 bootstrap 权限兼容；不复制 API/Worker/Scheduler/Migration command、Health、网络、端口或 Secret 分类，因此不形成第二套业务 Runtime。Windows CMD / PowerShell 直接执行标准 Docker Compose CLI，不再维护额外 wrapper。

Compose 自动编排一次性 bootstrap → PostgreSQL → Migration → configure → API/Worker/Scheduler → Frontend。PostgreSQL password/Cursor key 由系统自动生成并持久保存；TikHub/LLM API Key 可由敏感 `env.production` 输入，但通过 Compose Secret File 进入需要的服务，不作为业务容器普通环境变量。

源码开发仍独立使用 `env.local` + `scripts/dev/backend.py` / `frontend.py`；这与完整 Compose Runtime 是两种运行入口，不是两套业务实现。

主要机器事实入口：

```text
backend/src/aima_ugc/modules/
backend/src/aima_ugc/bootstrap/
backend/src/aima_ugc/entrypoints/
backend/src/aima_ugc/adapters/
frontend/src/app/routes.ts
frontend/src/features/
migrations/versions/
tests/
frontend/e2e/
frontend/e2e-fullstack/
Dockerfile
compose.yaml
compose.windows.yaml
env.production.example
scripts/deploy/prepare_host.py
.github/workflows/internal-v1a.yml
.github/workflows/compose-windows-desktop.yml
.github/workflows/stage8f-fullstack.yml
```

当前完整 Production 仍是 **No-Go**：完整不可变 Release、认证授权、协调 Backup/Restore、正式生产验收等尚未闭环。

2026-08-22 已确认公司内网 V1：不对公网开放；首版不做登录/权限隔离；首版不迁旧历史数据；先保证 Excel → Worker → PostgreSQL → Voice Plaza 的真实业务闭环，再部署到公司服务器供内部网络使用。

当前执行顺序：

```text

```

```text

→ 公司服务器 / 公司内部网络 / 不对公网开放
```

正式 RPO/RTO、长期 Retention、容量/性能/Soak、正式告警和值班 SLO、完整 Coordinated Backup/Restore、完整 Release provenance/SBOM/签名继续保留，但可在内网 V1 使用后根据真实情况冻结。

## 3.3 内网 V1 仍不能省略的基础门禁

```text
真实前后端业务闭环
PostgreSQL / Artifact / 日志持久化
Secret 不进 Git / 镜像 / 页面 / 日志
Health / Readiness
Migration 能从空库到 head
API / Worker / Scheduler 真正运行
容器重启后数据不丢
宿主机 reboot 后可恢复运行
公司网络边界明确
PostgreSQL 不向普通客户端网络暴露
真实 Excel Full-stack Smoke
```

分工：

```text
Stage 8F
→ 证明真实前后端业务闭环与 Excel Full-stack

Internal V1-A
→ 证明 canonical Compose 可以完成 bootstrap/Migration/configure/正式进程启动
→ 证明 Linux bind-mount 持久目录、内部/外部 Secret File、Readiness、端口边界、内部 Secret 幂等
→ 证明服务器绝对 AIMA_HOST_ROOT 与 Linux/WSL 仓库相对 AIMA_HOST_ROOT
→ 证明已有 PostgreSQL 数据丢 password Secret 时 fail closed

Windows Docker Desktop compatibility
→ 证明 Windows CMD / PowerShell 可直接使用标准 Compose CLI 调用同一业务 Runtime
→ Artifact/应用日志由 AIMA_HOST_ROOT bind mount，便于开发机直接查看
→ PostgreSQL/内部 Secret 继续使用 Docker-managed named volumes
→ bind-compatible 例外只作用于 data/log，不降低 PostgreSQL/Secret 与 Linux/服务器门禁
→ 不替代真实公司服务器验收

Internal V1-B
→ 在真实公司 Linux 服务器以 AIMA_HOST_ROOT=/data/AIMA_UGC 验证公司网络、真实浏览器/业务、真实 Secret、目标容器重启和宿主机 reboot
```

因此剩余内网 V1 风险仍是“真实公司服务器能否按批准边界稳定运行并通过业务验收”。Windows 本地便利能力不能被当成 V1-B 服务器验收证据。

# 15. Internal V1-A：最小可部署 Docker / Compose / Config

## 当前状态：已完成；持续作为所有容器 Runtime 的 canonical 基线

这是公司内网 V1 的部署基础，复用 Stage 11A 长期方向但只实现内网 V1 所需最小范围。

当前机器事实：

```text
Dockerfile
.dockerignore
compose.yaml
compose.windows.yaml
env.production.example
deploy/nginx.conf
scripts/deploy/prepare_host.py
backend Internal V1 configure
.github/workflows/internal-v1a.yml
.github/workflows/compose-windows-desktop.yml
```

服务/启动拓扑：

```text
bootstrap（一次性 root 初始化，成功后退出）
→ postgres healthy
→ migrate（一次性）
→ configure（一次性）
→ api / worker / scheduler
→ frontend healthy
```

### Linux / WSL / 公司服务器

canonical 入口：

```bash
cp env.production.example env.production
chmod 0600 env.production
# 编辑 env.production
docker compose --env-file env.production up -d --build --wait
```

Linux/WSL 使用 `AIMA_HOST_ROOT` bind mount：

```text
${AIMA_HOST_ROOT}/postgres
${AIMA_HOST_ROOT}/runtime/data
${AIMA_HOST_ROOT}/runtime/logs
${AIMA_HOST_ROOT}/shared/secrets
```

### Windows Docker Desktop 原生

Windows 不改变业务 Runtime，只叠加 storage-only override：

```text
compose.yaml + compose.windows.yaml
```

第一次从仓库根创建本机配置：

```cmd
copy env.production.example env.production
```

或 PowerShell：

```powershell
Copy-Item env.production.example env.production
```

Windows 本地推荐：

```dotenv
AIMA_HOST_ROOT=./.runtime
```

CMD / PowerShell 统一入口：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production up -d --build --wait
```

日常停止并保留 Host Root 文件与 named volumes：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down
```

持久状态采用混合存储：

```text
${AIMA_HOST_ROOT}/runtime/data
→ Artifact

${AIMA_HOST_ROOT}/runtime/logs
→ 应用 .log

windows_postgres
→ PostgreSQL

windows_internal_secrets
→ PostgreSQL password + Cursor signing keys
```

这样 Windows 本地可以直接查看 Artifact 与应用日志，而 PostgreSQL/内部 Secret 仍不依赖 NTFS 的 Linux UID/GID/mode 语义。`prepare_host.py` 只对 `runtime/data` / `runtime/logs` 放宽精确 POSIX owner/mode 校验；PostgreSQL 与 Secret 继续执行严格权限边界。

`down -v` 只删除 Windows PostgreSQL/内部 Secret named volumes，不能删除 bind-mounted Artifact/日志；完全重置必须额外显式删除 `${AIMA_HOST_ROOT}/runtime/data` 与 `${AIMA_HOST_ROOT}/runtime/logs`。旧 `windows_runtime_data` / `windows_runtime_logs` volume 不自动迁移或删除。

### Secret / 持久化不变量

无论 storage source 是 Linux bind 还是 Windows mixed storage：

- PostgreSQL 18.4 容器路径仍 `/var/lib/postgresql`；
- Backend 内部 Secret 路径仍 `/run/internal-secrets`；
- 外部 TikHub/LLM Secret 仍由 Compose Secret 进入 `/run/secrets`；
- PostgreSQL password/Cursor key 首次随机生成，后续不静默轮换；
- 已有 PostgreSQL 数据丢 password Secret 时 fail closed；
- Backend/Frontend 正式 Runtime 非 root；
- Frontend 是唯一宿主 HTTP PortBinding；
- PostgreSQL/API 无宿主 PortBindings；
- Migration 保持独立一次性进程；
- bootstrap 完成后退出，不保留长期高权限初始化容器。

永久验证分层：

```text
Internal V1-A Linux Golden Path
→ 真实绝对 / repo-relative bind mount 生命周期

Windows Runner
→ 真实 CMD / PowerShell 标准 Compose CLI config

Windows storage model Golden Path
→ 真实 Docker Engine merged Compose hybrid Runtime
→ Artifact/log bind + host-visible files
→ PostgreSQL / Secret named volumes
→ bootstrap / Migration / Readiness / Secret mode / restart persistence / down -v 生命周期
```

GitHub Hosted Windows Runner 不能被描述成真实个人 Docker Desktop Linux-container Runtime；具体 Windows 开发机首次使用仍需本机 smoke。

V1-A 不包含真实公司服务器/浏览器/真实 TikHub/LLM/reboot、完整离线 Release、认证或协调 Backup/Restore。

# 18. Stage 11：完整 Production Release

## 当前状态：长期待实现；直接复用 Internal V1-A canonical Linux 部署基础

完整设计见 [`../appendix/11_生产部署与离线Release方案.md`](../appendix/11_生产部署与离线Release方案.md)。

## 18.1 Stage 11A：Production Docker / Compose Hardening

Internal V1-A 已提前实现并验证：根多阶段 Dockerfile、canonical 根 Compose、单一 `AIMA_HOST_ROOT` Linux 持久根、一次性 bootstrap/migrate/configure、非 root Backend/Frontend、持久 PostgreSQL/Artifact/log、内部/外部 Secret File、空库 Migration、Health/Readiness、Linux Compose smoke、PostgreSQL/API 不发布宿主端口。

Windows `compose.windows.yaml` 是本地开发 storage adapter，**不是 Production Compose 路线**，也不是 Stage 11A 服务器设计基础。

Stage 11A 应增量完成：不可变 image/digest、必要且有独立生产语义的 `compose.production.yaml`、正式 HTTPS/Host/浏览器安全与认证入口、生产资源/安全覆盖、CI linux/amd64 Release build、no-build/no-pull Compose smoke、目标服务器不现场联网安装/构建。

完整 Production 的 `/data/AIMA_UGC` 持久根与 `/data/AIMA_UGC/releases/<version>` 版本目录继续分离。服务器加载已验证镜像后最终使用 no-build/no-pull 语义，而不是把 Internal V1 的现场 build 继续当正式发布。

## 18.2 Stage 11B：离线 Release Bundle

长期目标：`images.tar`、canonical/production Compose、env example、release/migration manifest、SHA256、SBOM、SIGNATURES、DEPLOY.md；Manifest 记录 Release/Git SHA/build time/platform/image digest/Alembic head/Contract hash/最低 Docker/Compose/Migration 兼容/rollback/SBOM/签名信息。

Windows 本地 override 可以作为开发辅助材料单独保留，但不能参与服务器持久化、Backup/Restore 或 Production 验收口径。

## 18.3 Stage 11C：协调 Backup / Restore

完整 Production 的恢复单位仍是 `PostgreSQL + ArtifactStore` 的 Coordinated Backup Set。共享写屏障、maintenance、独占 backup lock、PG dump + Artifact capture、验证与 restore/reconciliation 仍待正式 Change 设计。

Windows Docker Desktop 的 Host Root + named-volume 混合持久状态不是 Production Backup Set。

## 18.4 Stage 11D：正式发布和回滚自动化

目标包括 preflight、verify release、backup、migrate、start、health/smoke、rollback、logs/diagnosis。

## 18.5 Stage 11E：完整真实生产验收

必须证明全新 Linux 服务器正式 Release 部署、空库/升级 Migration、四类正式进程、live/ready、Import/Collection/Analysis/Export、持久化、容器重启/reboot、协调恢复、应用 rollback、Secret 不泄露、认证授权、容量/资源达到批准目标。
