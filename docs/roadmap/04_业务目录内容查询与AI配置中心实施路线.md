# AIMA_UGC 声音广场与业务配置实施路线

本文维护声音广场 VP0–VP5 与业务配置 U1–U5 的当前实施边界。VP1–VP4 已完成代码范围，旧 VP5 的 PostgreSQL/Real Full-stack 新鲜验证由用户明确延期；U1–U5 已进入实现收口，是否可标为完整交付仍以各 Change、Migration、Contract、测试和本轮验证证据为准。

当前主链已经从“仅文件配置”升级为：

```text
Vehicle Catalog + Keyword Pack
→ Collection / Import 冻结资源版本与消歧结果
→ Content 车型证据与查询

active Analysis Scheme Version
→ Prompt / relevance / sentiment / voice_type / labels 原子配置
→ Run 冻结 Scheme Version 与 Prompt 快照
→ 人工覆盖按 Content Version 锁定

Provider-neutral Principal
→ administrator / user 后端授权
→ 管理员配置页与审计
→ 后续 Feishu Identity Adapter
```

[`backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md`](../../backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md) 现在只负责空库 bootstrap/灾备基线；数据库中唯一 active Analysis Scheme Version 是运行时配置事实。前端继续只消费 Pydantic → OpenAPI → generated Client，不复制车型或 AI 枚举。

# 1. 要解决的根问题

当前问题不是缺少几个下拉框，而是同一业务概念在不同入口中没有统一的事实链：

```text
车型 / 关键词 / AI 分类定义
→ 用户在 Collection、Import、声音广场中怎样选择
→ 提交后怎样冻结版本
→ 内容为什么命中、被分到什么车型或标签
→ 查询、导出和消息怎样展示同一结果
→ 配置变更后历史任务怎样保持可审计
```

如果只在页面补选项，会产生四类漂移：

- 前端维护一套车型、`voice_type`、情感或标签枚举，后端与 Prompt 又各有一套；
- 已排队任务读取实时配置，导致同一任务前后语义变化；
- 查询能筛选但没有证据说明内容为什么命中；
- Figma 展示总数、页码、消息或下架状态，但真实 Contract/Schema 并不存在。

声音广场既有交付链仍为：

```text
active Analysis Scheme / Taxonomy
→ Scheme 编译与 Hash 校验
→ 只读 Taxonomy Contract
→ generated Client
→ 声音广场筛选 / 列表 / 详情
→ 人工复核 / AI Run / Export
→ Browser、API、PostgreSQL 与 Figma 一致性验收
```

U1–U5 实现链为：

```text
Vehicle Catalog / Analysis Scheme
→ Provider-neutral Principal / Authorization
→ 管理员配置中心
→ 版本发布与运行冻结
→ 车型证据 / Facet / Count / Availability
→ 自定义 Export / Notification
→ 后续 Feishu Identity Adapter
```

# 3. 长期 Owner 边界

| Owner | 负责 | 不负责 |
| --- | --- | --- |
| Vehicle Catalog | 标准车型、车型别名、启停/废弃/合并、目录版本、Pack 与车型引用关系、车型匹配器和内容车型证据 | 不拥有 Keyword Pack 本体，不保存 AI 标签，不直接写 Content 主表 |
| Collection | Keyword Pack 本体、Pack 版本、Collection 选择、Plan↔车型关系与 Run 快照 | 不复制车型别名，不直接写 Pack↔车型关系，不维护 Analysis Scheme |
| Ingestion | 冻结 Import 选择、调用统一 Matcher、保留导入匹配证据并把 Canonical 交给 Content Owner | 不根据页面实时状态重新解释已创建 Campaign |
| Analysis | active Analysis Scheme、Git bootstrap、Loader/Compiler、Validator、Analysis Identity、Run 冻结、结果与人工覆盖 | 不把完整车型目录写进 Prompt，不拥有关键词包；不允许前端维护平行枚举 |
| Content | Content Current/Version/Metric 与统一查询读模型 | 不新增长期平行 AI 列，不拥有车型目录或 Prompt |
| Reporting | 导出范围、列 Profile、Artifact、导出快照 | 不自行重算标签、车型或匹配规则 |
| Notification | 业务事件投影、收件箱、按 Principal 的已读/未读 | 不替代 Job、Export、Analysis Run 的真实状态机 |
| Identity | Provider-neutral Principal、两种角色和 Identity Adapter 边界 | 不把飞书私有 ID 扩散成业务主键，不把前端守卫当后端授权 |
| Frontend Admin | 管理员配置中心的车型、关键词关系、Analysis Scheme 草稿/发布/回滚和审计交互 | 不直接写数据库，不允许分别激活 Prompt 与分类定义，不在本地保存第二份合法枚举 |
| Frontend Shared/Domain | 公共选择器、平台显示、北京时间格式、日期区间语义 | 不维护后端枚举、Analysis Scheme 或 Provider Capability 的第二份事实 |

Vehicle Catalog 可以作为模块化单体中的新业务模块，但不能演化成接收所有枚举的“万能 Catalog”。平台 Capability 继续由 Provider/Collection Owner 管理，完整 Analysis Scheme 继续由 Analysis Owner 管理。

# 4. 车型与关键词包怎样统一

## 4.1 车型不能继续只放在 Prompt

把完整车型列表直接放进打标签 Prompt 不作为正式方案，原因是：

- Collection 和 Import 在调用 AI 前就需要车型筛选；
- 车型别名会频繁维护，放进每次 Prompt 会增加 token 和运行成本；
- Prompt 的职责是判断语义，不适合作为车型主数据、启停和别名管理数据库；
- 历史任务需要冻结当时目录版本，不能随当前 Prompt 静默变化；
- Content 可能同时提到多个车型，不能只增加一个自由文本 `car_model` 字段。

推荐建立独立 Vehicle Catalog：

```text
标准车型
→ 多个别名 / 俗称 / 历史名称
→ active / deprecated
→ 目录版本
→ 可追溯的创建、修改和启停时间
```

内容与车型采用多对多关系，不强制“主车型”。每个匹配至少保留：标准车型身份、命中方法、命中文本、来源字段、目录版本和证据来源。

## 4.2 车型与词包关联，但不合并成一个概念

关键词包表达品牌词、主题词、活动词或其他确定性匹配资源；车型表达稳定业务主数据。两者可以关联，不能共用同一张自由文本表。

推荐模型：

```text
Keyword Pack
├─ 当前关键词项
└─ 车型引用（新增关联）
      ↓
    执行快照时展开为该车型版本下的有效别名
```

这样可以：

- 在“车型相关词包”中复用车型别名，不手工复制；
- 车型改名/新增别名后只影响未来快照；
- 已创建 Run/Import 继续使用冻结别名，不被实时目录改写；
- Pack 仍可包含非车型关键词，不被错误降级成车型集合。

## 4.3 公共选择模型

Collection Plan、手工 Discovery、Excel/Data Import 可以复用同一个前端“匹配资源选择器”，但各入口仍保留自己的业务状态机和 API Owner。

推荐的内部选择快照 V2 至少包含：

```text
selected keyword packs + pack versions + resolved keywords
selected vehicle models + catalog version + resolved aliases
pack-to-vehicle references
match mode
normalized effective terms
snapshot hash
```

兼容原则：

- 现有只选择 Keyword Pack 的合法行为保持不变；
- 已排队 V1 Job/Snapshot 继续按旧 Payload 执行，不运行时补读新目录；
- V2 只对新建 Run/Campaign 生效；
- 公共 API 先 additive 增字段/资源，再经过兼容期收敛，不能直接删除 `keyword_pack_ids`。

推荐默认匹配语义是：

```text
同一维度内 OR：命中任一所选 Pack / 车型即可
不同维度间 AND：同时选择 Pack 和车型时，必须既满足 Pack 条件又命中所选车型
```

该语义可以让“车型筛选”真正缩小 Import 范围，同时保持单独选择 Pack 时的现有行为。它仍属于业务语义门禁，开始 Contract/Schema 实现前必须由业务 Owner 明确确认。

## 4.4 车型识别执行顺序

```text
车型别名确定性匹配
→ 形成 0..N 个候选与证据
→ 无歧义：直接形成车型匹配事实
→ 有歧义且任务要求 AI 复核：只把候选编号与必要文本交给 Analysis
→ Validator 只接受候选集合中的标准车型身份
```

不把完整车型目录塞给每次 LLM，也不允许模型创造目录外车型 ID。没有候选时首版保持“未识别”，不做不可审计的自由文本车型落库。

# 5. 当前阶段：版本化业务配置驱动声音广场

## 5.1 当前配置边界

运行时读取数据库中唯一 active Analysis Scheme Version。它把 Prompt 模板、`relevance` 判断、情感、`voice_type`、标签树和 Validator Taxonomy 作为一个原子快照；Git Prompt 只在空库时 bootstrap 首个发布版。

当前配置维护流程是：

```text
管理员创建或保存完整草稿（每次保存追加 Version）
→ 编译受控 Taxonomy 占位符并校验结构/显式 unknown
→ 原子发布完整 Version并写审计
→ 新 Analysis Run 冻结 Version ID、Prompt 快照和 Hash
→ 历史 Run/Result 保持原身份
```

第一版不强制双人审批，但所有发布、回滚和配置修改都必须由后端鉴权并写 `audit_events`。页面不读取仓库文件、数据库或 Secret，也不复制 Taxonomy。

## 5.2 安全只读 Taxonomy 投影

声音广场通过 `GET /api/v1/content-analysis-taxonomy` 读取 active Scheme 的安全分类投影：

- `prompt_version`；
- `prompt_sha256`；
- `schema_version`；
- `taxonomy_sha256`；
- `sentiments`；
- `voice_types`；
- `labels` 一级/二级父子树。

该接口不返回 Prompt 正文、判断规则、LLM Base URL、Model 配置、Secret 路径或 API Key。它与 `GET /api/v1/content-analysis-capabilities` 分开：Capability 只回答当前环境能否运行 AI，Taxonomy 只回答页面有哪些合法筛选值。

读取或解析失败时必须 fail closed：接口返回统一错误，声音广场显示“分类配置暂不可用”并禁用依赖 Taxonomy 的筛选，但内容列表和其他独立操作仍可继续使用；不能回退到前端旧枚举。新增 Contract 必须通过 Pydantic → OpenAPI → generated Client 生成链交付，不能手写第二套 TypeScript 类型。

## 5.3 声音广场当前交付范围

声音广场现有页面继续作为唯一 Feature Owner，不重做平行页面。近期交付包含：

### 筛选

- 搜索、平台、内容类型、AI 状态、有效相关性；
- 把后端已经支持的 `voice_type` 接入 Store、请求快照和筛选控件；
- 情感从只读 Taxonomy 投影加载，不保留前端硬编码；
- 一级/二级标签改为级联选择，二级选项受一级约束；
- 发布起止时间继续按 `Asia/Shanghai` 的整日起止边界提交；
- 当前 `source_identifier` 继续作为兼容输入；车型使用稳定 ID 多选，同维度 OR。

### 列表与详情

- 保留真实 Content Read Model 的标题/正文摘要、平台、作者、互动、发布时间；
- 展示 AI 当前性、有效相关性及来源、`voice_type`、情感和全部有序标签对；
- 详情继续展示媒体、评论覆盖、来源记录和补采状态等当前 Contract 已有事实；
- 分页继续使用 `next_cursor / has_more` 的“加载更多”；Count 仅按 `none/exact/estimated` 的后端语义展示，不伪造编号页码；
- 覆盖 Loading、Empty、Error、Partial Data、Stale 和无 AI 配置状态。

### 业务动作

- 单条和批量人工相关性复核，并明确 AI 原判与人工覆盖来源；
- 选中内容后执行 AI Run 预检、确认创建、进度、失败、取消和历史查看；
- 保持当前单次最多 1000 条的真实选择边界；
- 保留 selected/page/query 三种 Excel 导出范围、后端列白名单、导出记录和 Artifact 下载；
- 展示第三方可用状态的当前投影，并保留“技术失败不等于已删除”的表达；
- 按当前 Principal 读取和更新消息收件箱；
- 所有错误继续使用统一 HTTP Error Contract，并显示可排障的 `request_id`。

仍不进入当前正式能力的部分包括：编号页码、无界精确总数、类型化来源目录、保存个人导出列 Profile，以及把一次 Provider 技术失败解释为“已删除”。Figma 中的示例值不构成生产数据。

## 5.4 Scheme 与运行冻结

现有 Analysis Run 预检已经返回 Prompt/Taxonomy/Generation Configuration Hash，并在创建时校验 `expected_configuration_hash`。近期继续复用这条身份链：

```text
当前 active Scheme Version
→ 预检冻结 Scheme/Prompt/Taxonomy/模型身份和目标数
→ 创建 Run 时校验 expected_configuration_hash
→ Worker 按 Run 冻结 Version 和 Prompt 快照执行
→ 后续发布只影响新 Run
```

Taxonomy 只读接口用于页面选项，不替代 Run 冻结身份。页面加载目录后若 active Version 改变，后端按配置 Hash/Version 冲突失败关闭，前端重新预检，不能自行猜测兼容值。

## 5.5 管理员配置中心

管理员配置中心是独立路由和 Figma 页面，不塞入声音广场。当前遵守以下边界：

- Vehicle Catalog 与 Analysis Scheme 是不同 Domain Owner，不合并为万能表；
- `relevance` 规则、情感、`voice_type`、标签、Prompt 模板和 Validator 组成一个 Analysis Scheme Version；
- Scheme 必须整体校验、原子发布和整体回滚，不能分别激活；
- 已发布 Scheme Version 保留历史，只能通过新版本或回滚改变 active；
- 车型无引用时允许物理删除，已有任何引用后只能废弃、改显示名或合并；
- 管理员 API 依赖后端 `administrator` 授权和审计；普通用户只消费授权的业务读接口；
- Git Prompt 与数据库不同时成为可写主事实源。

飞书企业身份只预留 Identity Adapter；当前 development Adapter 用于本地开发，不是生产认证。Gold Set、自动评测和双人审批未实现，其中双人审批在第一版明确不强制。

# 6. 当前查询边界与后续 Facet

## 6.1 查询只使用当前 Contract

声音广场只使用当前 `ContentFilterSnapshot` 和产品 Contract 已支持的查询语义：

- 平台继续来自正式 Platform Contract，中文显示由 Shared Domain 统一；
- 内容类型保持当前文本输入，不在没有目录 Contract 时伪造下拉枚举；
- 情感、`voice_type`、标签树来自 active Scheme 的只读投影；
- `source_identifier` 保持当前 UUID 兼容语义；
- 车型使用稳定 ID 多选；可用状态消费追加观察的当前投影；Count 使用独立模式语义。

后续新增更多 Facet 数量时仍必须明确 `as_of`、过滤范围和精确/估算语义，不能把异步变化的大表数字当事务级承诺。

## 6.2 来源筛选类型化

后续可用类型化来源引用替代 UI 中的“Batch / Run UUID 猜测”：

```text
source_kind + source_id + display_name/status
```

兼容期保留现有 `source_identifier`，但新前端使用来源目录选择器；Cursor 查询 Hash 必须包含新筛选语义。

## 6.3 Cursor、总数和页码

Cursor 继续是大列表唯一规范分页方式，不改成 Offset/页码：

- 数据持续新增时，Offset 容易跳项和重复；
- 4000 万规模下每次精确 `COUNT(*)` 可能成为主要查询成本；
- Figma 的编号页码仍只能标记 `DESIGN_EXAMPLE / FUTURE`。

当前独立 Query Summary/Count 能力使用：

```text
count_mode = none（默认） / exact / estimated
count
count_kind
as_of
```

首版只在有界或已冻结范围提供 exact；大范围实时查询默认 `none`，必要时提供 estimated。编号分页不是这项能力的必然结果，前端继续使用“加载更多”或虚拟列表。

# 7. 第三方下架/删除状态

“第三方内容现在不可访问”与“删除本地 Content”是两件事。推荐建立追加式可用状态观察：

```text
available
unavailable_confirmed
unavailable_suspected
unknown
```

每次观察至少保留：

- Content 与当前 Version；
- Provider/Operation/Request Attempt；
- `observed_at`；
- 规范化原因与有限安全摘要；
- 原始证据定位；
- 是否为明确 Provider 业务响应或仅技术失败。

规则：

- timeout、429、5xx、Secret 不可用或一次 404 不能直接标记“已删除”；
- 只有 Provider 明确语义或经批准的多次确认策略才能进入 `unavailable_confirmed`；
- 本地 Content、Version、Raw、Analysis 和来源账本继续保留；
- 当前状态是观察历史的只读投影，不覆盖历史；
- UI 文案优先显示“第三方不可用/疑似不可用”，只在证据能区分时显示“作者删除/平台下架”；
- 查询、导出和补采资格都消费同一投影，不各自猜测。

第一版不设置“失败 N 次自动确认”阈值：只有明确 Provider 业务证据可以写 `unavailable_confirmed`，技术失败保持 `unknown/suspected`。逐 Provider 自动观察、重试周期和生产保留策略以后按真实 Operation 独立接线。

# 8. 导出、自定义列与消息中心

## 8.1 自定义导出列

Reporting 已提供版本化列目录和安全白名单，不允许前端提交任意数据库字段名。当前支持：

```text
系统默认 Profile
用户选择的 columns
```

Data Export Request Snapshot 必须冻结：目标 Content/Version、查询条件、列集合/列目录版本、相关 Analysis Scheme/车型目录身份和生成时间。

列目录中只有后端能够真实投影的字段可用；Worker 按请求冻结的列顺序生成，未知列在进入 Job 前失败关闭。保存个人 `column_profile` 不在第一版范围。

## 8.2 消息中心保持独立投影

Export/Analysis/Import/Collection Job 是业务事实；消息中心只是这些事实产生的通知投影。推荐链路：

```text
业务终态事件
→ Notification Event
→ 按 Principal 的 Inbox / Read State
→ 前端消息中心
```

消息中心不能：

- 成为 Job 成功/失败的新事实源；
- 把 Artifact 下载权限交给前端隐藏按钮；
- 在没有 Principal 时伪造按用户已读/未读；
- 与 Export Center 合并成一张万能任务表。

当前 Inbox/Read State 按 Provider-neutral `principal_id` 隔离；development Principal 只用于本地环境。飞书接入后由 Identity Adapter 提供稳定 Principal，不改变 Notification Domain，也不能借此绕过 Artifact 对象级授权。

# 11. 已确认决定与明确延期

## 11.1 已确认的产品原则

以下内容来自用户确认或其“其他按推荐方案”的授权，后续 Change 应直接追溯：

- 一条内容允许 0..N 个车型，不设主车型；车型同维度 OR，和 Keyword Pack 维度间 AND；
- 歧义别名不得自动任选，必须人工消歧；任务冻结车型/词包版本及已解析别名；
- 无引用车型可以物理删除；已引用车型只能废弃、改显示名或合并；连续合并指向最终标准车型，查询/导出按最终车型聚合，历史证据仍保留原车型；
- 人工车型、`voice_type`、情感和标签按 Content Version/维度锁定，只有显式人工解锁才能被后续自动结果替代；
- 未知/无法分类必须显式表达，不能静默映射为中性/其他；
- Prompt、`relevance`、情感、`voice_type`、标签和 Validator Taxonomy 作为一个 Scheme Version 原子发布/回滚；
- 第一版不强制双人审批，但所有发布、回滚和配置修改必须审计；
- 企业身份预留飞书 Adapter，角色仅 `administrator/user`；飞书真实接入后续实施；
- Cursor 保持规范分页；有界 exact，大范围 estimated/none，不提供编号页码；
- `unavailable_confirmed` 只来自明确 Provider 证据且必须关联 Attempt/Raw Artifact；技术失败只记 unknown/suspected，并保留历史；
- 导出列由后端白名单治理；消息中心按 Principal 建独立 Inbox。

## 11.2 明确延期

- 旧 VP5 的 PostgreSQL/Real Full-stack 验证；
- 飞书真实登录、回调、Session/OIDC/企业目录接线；
- 双人审批、Gold Set 与自动评测；
- 类型化来源目录、个人导出列 Profile、逐 Provider 自动 Availability 观察；
- 大范围 Count 的正式估算基础设施和容量 SLO。

这些延期不允许通过静态假数据或前端开关伪装成已实现；以后启动时按新的 L3 Change 恢复当时机器事实。

# 13. 兼容、部署与回滚

- U1–U5 使用 0031–0036 additive Migration；部署顺序是先迁移再启动新代码，不回写或删除既有 Content/Analysis 事实；
- 旧请求未选择车型/列/Count 模式时保持旧默认行为；Cursor 查询 Hash 包含新增筛选语义；

- 已创建 Run、历史 Result、旧 Cursor、Export Artifact、车型证据和人工复核保持可读；
- 如果新增筛选改变查询语义，必须进入 Cursor query hash；不兼容旧 Cursor 时返回明确错误；
- 应用回滚前必须确认旧版本是否能容忍 additive 表/列；不能 downgrade Migration 后继续运行已写入新事实的代码或物理删除审计/历史；
