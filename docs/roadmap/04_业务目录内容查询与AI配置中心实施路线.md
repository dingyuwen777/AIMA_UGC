# AIMA_UGC 声音广场近期交付与业务配置升级路线

本文把开发主线分成两层：近期先依靠当前 Git Prompt 文件配置完成声音广场；后期再建设车型目录、管理员配置中心、Analysis Scheme、查询增强、消息和第三方可用状态。近期目标是让现有后端能力、文件内 Taxonomy、生成 Client、Vue 页面和 Figma 达成一致，不让尚未实现的管理能力阻塞声音广场交付。

本文同时包含**近期交付路线**和**后期升级路线**。当前已经实现什么仍以 Contract、Migration、代码和测试为准；新增公共 Contract、Schema 或业务语义必须在对应 Change 完成后才能成为生产事实。

当前优先级已经确认：

```text
先完成声音广场
→ 当前 content_labeling_v3.md 继续作为分类与 Prompt 唯一事实源
→ 后端只读投影情感 / voice_type / 标签给前端
→ 前端完成真实筛选、列表、详情、人工复核、AI Run 和导出体验
→ 管理员配置中心、车型目录和 Analysis Scheme 后期升级
```

近期不建立可写配置数据库，也不开发管理员配置页面。Prompt/Taxonomy 调整继续通过 Git 修改、测试、Review 和部署生效；前端不直接读取文件，也不复制其中的枚举。

# 1. 要解决的根问题

当前问题不是缺少几个下拉框，而是同一业务概念在不同入口中没有统一的事实链：

```text
车型 / 关键词 / AI 分类定义
→ 用户在 Collection、Import、声音广场中怎样选择
→ 提交后怎样冻结版本
→ 内容为什么命中、被分到什么车型或标签
→ 查询、导出和消息怎样展示同一结果
→ 配置变更后历史任务怎样保持可审计
```

如果只在页面补选项，会产生四类漂移：

- 前端维护一套车型、`voice_type`、情感或标签枚举，后端与 Prompt 又各有一套；
- 已排队任务读取实时配置，导致同一任务前后语义变化；
- 查询能筛选但没有证据说明内容为什么命中；
- Figma 展示总数、页码、消息或下架状态，但真实 Contract/Schema 并不存在。

近期交付链固定为：

```text
Git Prompt / Taxonomy
→ PromptTaxonomyLoader 严格解析与 Hash
→ 只读 Taxonomy Contract
→ generated Client
→ 声音广场筛选 / 列表 / 详情
→ 人工复核 / AI Run / Export
→ Browser、API、PostgreSQL 与 Figma 一致性验收
```

后期升级链保留为：

```text
Vehicle Catalog / Analysis Scheme
→ Authentication / Authorization
→ 管理员配置中心
→ 版本发布与运行冻结
→ 车型证据 / Facet / Count / Availability
→ 自定义 Export / Notification
```

| Owner | 负责 | 不负责 |

| Analysis | 当前拥有 Git Prompt/Taxonomy、Loader、Validator、Analysis Identity 与结果；后期拥有结构化 Analysis Scheme 和可选车型歧义复核 | 不把完整车型目录写进 Prompt，不拥有关键词包；不允许前端维护平行枚举 |

| Reporting | 导出范围、列 Profile、Artifact、导出快照 | 不自行重算标签、车型或匹配规则 |
| Notification（认证后新增） | 业务事件投影、收件箱、按 Principal 的已读/未读 | 不替代 Job、Export、Analysis Run 的真实状态机 |

# 4. 车型与关键词包怎样统一

## 4.1 车型不能继续只放在 Prompt

把完整车型列表直接放进打标签 Prompt 不作为正式方案，原因是：

- Collection 和 Import 在调用 AI 前就需要车型筛选；
- 车型别名会频繁维护，放进每次 Prompt 会增加 token 和运行成本；
- Prompt 的职责是判断语义，不适合作为车型主数据、启停和别名管理数据库；
- 历史任务需要冻结当时目录版本，不能随当前 Prompt 静默变化；
- Content 可能同时提到多个车型，不能只增加一个自由文本 `car_model` 字段。

推荐建立独立 Vehicle Catalog：

```text
标准车型
→ 多个别名 / 俗称 / 历史名称
→ active / deprecated
→ 目录版本
→ 可追溯的创建、修改和启停时间
```

内容与车型采用多对多关系，不强制“主车型”。每个匹配至少保留：标准车型身份、命中方法、命中文本、来源字段、目录版本和证据来源。

## 4.2 车型与词包关联，但不合并成一个概念

关键词包表达品牌词、主题词、活动词或其他确定性匹配资源；车型表达稳定业务主数据。两者可以关联，不能共用同一张自由文本表。

推荐模型：

```text
Keyword Pack
├─ 当前关键词项
└─ 车型引用（新增关联）
      ↓
    执行快照时展开为该车型版本下的有效别名
```

这样可以：

- 在“车型相关词包”中复用车型别名，不手工复制；
- 车型改名/新增别名后只影响未来快照；
- 已创建 Run/Import 继续使用冻结别名，不被实时目录改写；
- Pack 仍可包含非车型关键词，不被错误降级成车型集合。

## 4.3 公共选择模型

Collection Plan、手工 Discovery、Excel/Data Import 可以复用同一个前端“匹配资源选择器”，但各入口仍保留自己的业务状态机和 API Owner。

推荐的内部选择快照 V2 至少包含：

```text
selected keyword packs + pack versions + resolved keywords
selected vehicle models + catalog version + resolved aliases
pack-to-vehicle references
match mode
normalized effective terms
snapshot hash
```

兼容原则：

- 现有只选择 Keyword Pack 的合法行为保持不变；
- 已排队 V1 Job/Snapshot 继续按旧 Payload 执行，不运行时补读新目录；
- V2 只对新建 Run/Campaign 生效；
- 公共 API 先 additive 增字段/资源，再经过兼容期收敛，不能直接删除 `keyword_pack_ids`。

推荐默认匹配语义是：

```text
同一维度内 OR：命中任一所选 Pack / 车型即可
不同维度间 AND：同时选择 Pack 和车型时，必须既满足 Pack 条件又命中所选车型
```

该语义可以让“车型筛选”真正缩小 Import 范围，同时保持单独选择 Pack 时的现有行为。它仍属于业务语义门禁，开始 Contract/Schema 实现前必须由业务 Owner 明确确认。

## 4.4 车型识别执行顺序

```text
车型别名确定性匹配
→ 形成 0..N 个候选与证据
→ 无歧义：直接形成车型匹配事实
→ 有歧义且任务要求 AI 复核：只把候选编号与必要文本交给 Analysis
→ Validator 只接受候选集合中的标准车型身份
```

不把完整车型目录塞给每次 LLM，也不允许模型创造目录外车型 ID。没有候选时首版保持“未识别”，不做不可审计的自由文本车型落库。

# 5. 当前阶段：文件配置驱动声音广场

## 5.1 当前配置边界

近期继续以 [`backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md`](../../backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md) 作为 `relevance` 规则、情感、`voice_type`、一级/二级标签和 Prompt 正文的唯一业务事实源。现有 [`backend/src/aima_ugc/modules/analysis/prompt_taxonomy.py`](../../backend/src/aima_ugc/modules/analysis/prompt_taxonomy.py) 负责严格解析、校验和计算 `prompt_sha256 / taxonomy_sha256`。

当前配置维护流程是：

```text
修改同一 Prompt Markdown 中的机器 Taxonomy 与自然语言规则
→ Loader / Validator / Prompt 测试
→ Code Review
→ 随应用版本部署
→ 仅影响之后新建的 Analysis Run
```

这是一条有审查、可回滚的文件配置路线，不是前端硬编码。近期明确不做：

- PostgreSQL 可写配置表；
- 管理员配置页面；
- Prompt 在线编辑、在线发布或在线回滚；
- 为了做下拉框在前端复制 Taxonomy；
- 让页面直接读取仓库文件或暴露服务器文件路径。

## 5.2 增加安全只读 Taxonomy 投影

声音广场需要动态下拉项，但不需要先建设配置中心。后端应复用当前 `PromptTaxonomyLoader`，增加 `GET /api/v1/content-analysis-taxonomy` 只读 HTTP Contract，投影：

- `prompt_version`；
- `prompt_sha256`；
- `schema_version`；
- `taxonomy_sha256`；
- `sentiments`；
- `voice_types`；
- `labels` 一级/二级父子树。

该接口只投影当前文件已经拥有的安全分类事实，不返回 Prompt 正文、判断规则、LLM Base URL、Model 配置、Secret 路径或 API Key。它与现有 `GET /api/v1/content-analysis-capabilities` 分开：Capability 只回答当前环境能否运行 AI，Taxonomy 只回答页面有哪些合法筛选值。

读取或解析失败时必须 fail closed：接口返回统一错误，声音广场显示“分类配置暂不可用”并禁用依赖 Taxonomy 的筛选，但内容列表和其他独立操作仍可继续使用；不能回退到前端旧枚举。新增 Contract 必须通过 Pydantic → OpenAPI → generated Client 生成链交付，不能手写第二套 TypeScript 类型。

## 5.3 声音广场近期交付范围

声音广场现有页面继续作为唯一 Feature Owner，不重做平行页面。近期交付包含：

### 筛选

- 搜索、平台、内容类型、AI 状态、有效相关性；
- 把后端已经支持的 `voice_type` 接入 Store、请求快照和筛选控件；
- 情感从只读 Taxonomy 投影加载，不保留前端硬编码；
- 一级/二级标签改为级联选择，二级选项受一级约束；
- 发布起止时间继续按 `Asia/Shanghai` 的整日起止边界提交；
- 当前 `source_identifier` 继续作为兼容输入，不在近期伪造来源目录。

### 列表与详情

- 保留真实 Content Read Model 的标题/正文摘要、平台、作者、互动、发布时间；
- 展示 AI 当前性、有效相关性及来源、`voice_type`、情感和全部有序标签对；
- 详情继续展示媒体、评论覆盖、来源记录和补采状态等当前 Contract 已有事实；
- 分页继续使用 `next_cursor / has_more` 的“加载更多”，不显示虚构页码或总数；
- 覆盖 Loading、Empty、Error、Partial Data、Stale 和无 AI 配置状态。

### 业务动作

- 单条和批量人工相关性复核，并明确 AI 原判与人工覆盖来源；
- 选中内容后执行 AI Run 预检、确认创建、进度、失败、取消和历史查看；
- 保持当前单次最多 1000 条的真实选择边界；
- 保留 selected/page/query 三种 Excel 导出范围、导出记录和 Artifact 下载；
- 所有错误继续使用统一 HTTP Error Contract，并显示可排障的 `request_id`。

近期不进入声音广场正式交付的控件包括：车型、动态内容类型 Facet、类型化来源目录、精确总数/编号页码、第三方下架状态、自定义导出列和消息中心。Figma 可以保留这些后期设计，但必须标记 `Future / Implementation Required`，生产页面不能用静态假数据假装已经支持。

## 5.4 当前配置与运行冻结

现有 Analysis Run 预检已经返回 Prompt/Taxonomy/Generation Configuration Hash，并在创建时校验 `expected_configuration_hash`。近期继续复用这条身份链：

```text
当前 Prompt 文件
→ 预检冻结配置身份和目标数
→ 创建 Run 时校验 expected_configuration_hash
→ Worker 按 Run 冻结身份执行
→ 文件后续变更只影响新 Run
```

Taxonomy 只读接口用于页面选项，不成为 Run 的新配置事实源，也不改变当前 Analysis Identity。页面加载的目录版本与提交查询之间如果发生部署切换，查询仍按后端 Contract 校验；前端不得自行猜测兼容值。

## 5.5 后期管理员配置升级

管理员配置中心保留在后期路线，不再是声音广场的前置依赖。升级时仍遵守以下长期边界：

- Vehicle Catalog 与 Analysis Scheme 是不同 Domain Owner，不合并为万能表；
- `relevance` 规则、情感、`voice_type`、标签、Prompt 模板和 Validator 组成一个 Analysis Scheme Version；
- Scheme 必须整体校验、原子发布和整体回滚，不能分别激活；
- 已发布分类项使用稳定身份和版本化显示名，只能退役，不能物理删除；
- 管理员页面依赖正式 Authentication/Authorization、后端权限判断和审计；
- 完成运行切换前，Git Prompt 与数据库配置不能同时成为可写主事实源。

后期迁移顺序是：结构化 Scheme 建模与当前 Prompt 播种 → 管理员草稿/校验/Gold Set → Run/Worker 冻结 Scheme Version → 切换唯一事实源 → Git Prompt 降级为 bootstrap/灾备基线。该切换会改变 [`docs/blueprint/07_技术决策与实施门禁.md`](../blueprint/07_技术决策与实施门禁.md) 的现行 Prompt 决定，必须通过独立 L3 Change 完成。

# 6. 近期查询边界与后期 Facet

## 6.1 近期查询只使用当前 Contract

近期声音广场只使用当前 `ContentFilterSnapshot` 已支持的查询语义，并增加 Prompt Taxonomy 的只读目录投影：

- 平台继续来自正式 Platform Contract，中文显示由 Shared Domain 统一；
- 内容类型保持当前文本输入，不在没有目录 Contract 时伪造下拉枚举；
- 情感、`voice_type`、标签树来自当前 Git Prompt 的只读投影；
- `source_identifier` 保持当前 UUID 兼容语义；
- 车型、来源目录和第三方可用状态不进入近期请求。

后期新增 Facet 数量时必须明确 `as_of`、过滤范围和精确/估算语义，不能把异步变化的大表数字当事务级承诺。

## 6.2 来源筛选类型化

后期用类型化来源引用替代 UI 中的“Batch / Run UUID 猜测”：

```text
source_kind + source_id + display_name/status
```

兼容期保留现有 `source_identifier`，但新前端使用来源目录选择器；Cursor 查询 Hash 必须包含新筛选语义。

## 6.3 Cursor、总数和页码

Cursor 继续是大列表唯一规范分页方式，不改成 Offset/页码：

- 数据持续新增时，Offset 容易跳项和重复；
- 4000 万规模下每次精确 `COUNT(*)` 可能成为主要查询成本；
- Figma 的页码/总数在没有 Contract 前只能标记 `DESIGN_EXAMPLE / FUTURE`。

如果产品确实需要总数，推荐增加独立 Query Summary/Count 能力：

```text
count_mode = none（默认） / exact / estimated
count
count_kind
as_of
```

首版只在有界或已冻结范围提供 exact；大范围实时查询默认 `none`，必要时提供 estimated/cached。编号分页不是这项能力的必然结果，前端仍可使用“加载更多”或虚拟列表。

# 7. 第三方下架/删除状态

“第三方内容现在不可访问”与“删除本地 Content”是两件事。推荐建立追加式可用状态观察：

```text
available
unavailable_confirmed
unavailable_suspected
unknown
```

每次观察至少保留：

- Content 与当前 Version；
- Provider/Operation/Request Attempt；
- `observed_at`；
- 规范化原因与有限安全摘要；
- 原始证据定位；
- 是否为明确 Provider 业务响应或仅技术失败。

规则：

- timeout、429、5xx、Secret 不可用或一次 404 不能直接标记“已删除”；
- 只有 Provider 明确语义或经批准的多次确认策略才能进入 `unavailable_confirmed`；
- 本地 Content、Version、Raw、Analysis 和来源账本继续保留；
- 当前状态是观察历史的只读投影，不覆盖历史；
- UI 文案优先显示“第三方不可用/疑似不可用”，只在证据能区分时显示“作者删除/平台下架”；
- 查询、导出和补采资格都消费同一投影，不各自猜测。

具体确认阈值、重试周期和保留策略会影响 Provider 费用与业务语义，实施前需要业务 Owner 决定。

# 8. 导出、自定义列与消息中心

## 8.1 自定义导出列

Reporting 提供版本化列目录和安全白名单，不允许前端提交任意数据库字段名。建议支持：

```text
系统默认 Profile
用户选择的 columns
可选保存的 column_profile（认证后）
```

Data Export Request Snapshot 必须冻结：目标 Content/Version、查询条件、列集合/列目录版本、相关 Analysis Scheme/车型目录身份和生成时间。

在开放自定义列前先补齐匹配证据：当前 [`backend/src/aima_ugc/contracts/export/models.py`](../../backend/src/aima_ugc/contracts/export/models.py) 已声明 `matched_keywords`，但 [`backend/src/aima_ugc/adapters/persistence/postgres/reporting.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/reporting.py) 的当前 Content 投影未填充。不能在 UI 勾选“命中关键词”后导出空列。

## 8.2 消息中心必须独立设计

Export/Analysis/Import/Collection Job 是业务事实；消息中心只是这些事实产生的通知投影。推荐链路：

```text
业务终态事件
→ Notification Event
→ 按 Principal 的 Inbox / Read State
→ 前端消息中心
```

消息中心不能：

- 成为 Job 成功/失败的新事实源；
- 把 Artifact 下载权限交给前端隐藏按钮；
- 在没有 Principal 时伪造按用户已读/未读；
- 与 Export Center 合并成一张万能任务表。

因此消息中心依赖正式认证授权。认证前继续使用各业务页面的运行/导出历史，不建立假的单用户已读状态。

# 13. 兼容、部署与回滚

- 近期只读 Taxonomy Contract 不需要业务 Schema/Migration，也不改变 Prompt 的唯一事实源；
- `voice_type` 是当前已有 additive 查询字段，前端接入不能改变旧请求和默认查询行为；
- 情感/标签选项改为动态读取后，Taxonomy 不可用时显示错误，不静默回退到旧硬编码；
- 当前 Prompt 文件、Loader、Validator、Run Preview/Create 的配置 Hash 身份链保持不变；
- 已创建 Run、历史 Result、旧 Cursor、Export Artifact 和人工复核结果保持可读；
- 如果新增筛选改变查询语义，必须进入 Cursor query hash；不兼容旧 Cursor 时返回明确错误；
- 回滚近期页面时可以关闭新筛选入口或回退应用版本，不能删除历史 Analysis/Export/Review 事实；
- 后期 Schema 仍使用 expand → backfill/dual-read（必要时）→ switch → contract，并在对应升级 Change 单独设计。
