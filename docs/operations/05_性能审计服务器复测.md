# 性能审计服务器复测

本页用于本轮性能修复部署后的只读观察与功能复核。部署、Migration 和业务操作仍按正式流程执行；本页中的 SQL 只读取状态，不修改生产数据。记录实测时先注明应用 Commit、Alembic revision、数据库版本、测试时段、数据规模和 Worker 并发档位，否则不同运行无法比较。

## 1. 先确认环境

通过已批准的数据库入口运行：

```sql
SELECT current_setting('server_version') AS postgres_version,
       current_database() AS database_name,
       pg_postmaster_start_time() AS database_started_at;

SELECT version_num FROM alembic_version;
```

本轮历史导入计数依赖 `20260926_0070`；应用和数据库 revision 必须匹配。声音广场读模型需先按 [04_声音广场读模型回填与性能验证](04_声音广场读模型回填与性能验证.md) 确认 `ready`。数据库检查结果与日志一起提供，但不要提供连接串、Secret、原始正文或完整 SQL 参数。

## 2. 对照场景与应保留证据

| 场景 | 功能复核 | 耗时与日志 |
| --- | --- | --- |
| 品牌/车型目录 | 已关联内容较多的实体，分别做不影响投影的别名/显示名修改与真正影响投影的角色/合并目标修改；核对筛选结果 | 请求耗时、`api.request_slow`（若有）、锁等待；只用已批准的受控操作，不为压测批量改生产目录 |
| 历史导入 | 观察一项真实 Campaign 的运行、取消/失败重试及详情与采集运行中心进度一致性；同 Source 顺序、不同 Source 并发保持 | `historical_import.chunk_completed` 的 `scheduling_ms`、`status_refresh_ms`、`finalization_ms`、`projection_refresh_ms`、`transaction_ms`，关联 `campaign_id`/`batch_id`/`chunk_item_id` |
| Excel 数据明细导出 | 用实际常见的筛选条件受理导出，核对目标数、文件行数、顺序及冻结时版本 | 浏览器 Network 中 `POST /api/v1/data-exports` 的耗时/状态；慢请求的 `api.request_slow`，Job 终态与导出文件校验 |
| 页面首次进入 | 清缓存后进入首页，再进入声音广场、采集运行中心、采集策略及后台配置；从页面内导航重复一次 | 浏览器 Network 的首屏 JS/CSS 传输量、页面请求耗时和可交互时间；检查直达地址、刷新、权限与页面功能 |

比较时使用相近数据量、缓存状态和并发。记录 P50/P95、总完成时间及成功/失败数；单次最快值不能证明生产吞吐提升。若历史导入总耗时仍高，应分开看内容写入、投影刷新、调度、状态收口和数据库锁等待，先定位主导段再决定是否修改。

## 3. 数据库只读排查

只在相关时段短时采样活动与等待，不输出 SQL 正文：

```sql
SELECT clock_timestamp() AS sampled_at,
       pid, application_name, state,
       wait_event_type, wait_event,
       clock_timestamp() - xact_start AS transaction_age,
       pg_blocking_pids(pid) AS blocking_pids,
       query_id
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
  AND state <> 'idle'
ORDER BY transaction_age DESC NULLS LAST
LIMIT 30;
```

`pg_stat_statements` 只有已启用时才可用；先检查，不为了本次测试临时变更数据库扩展或全局配置：

```sql
SELECT extname
FROM pg_extension
WHERE extname = 'pg_stat_statements';
```

如果已启用，可在复测前后分别记录相关查询的 `queryid`、`calls`、`total_exec_time`、`mean_exec_time`、`shared_blks_hit`、`shared_blks_read`，用差量判断；不要直接分享可能含敏感值的完整查询文本，也不要清空全局统计。对于指定 Campaign，可用下列只读核对一次 Source 派生计数与 Chunk 事实；大 Campaign 上该核对本身会扫描 Chunk，不应放进周期监控：

```sql
WITH source_totals AS (
    SELECT COALESCE(SUM(completed_row_count), 0) AS completed_rows,
           COALESCE(SUM(failed_chunk_count), 0) AS failed_chunks
    FROM historical_import_campaign_items
    WHERE campaign_id = :campaign_id AND item_kind = 'source_file'
), chunk_totals AS (
    SELECT COALESCE(SUM(row_count) FILTER (
               WHERE status IN ('succeeded', 'failed', 'cancelled')), 0) AS completed_rows,
           COUNT(*) FILTER (WHERE status = 'failed') AS failed_chunks
    FROM historical_import_campaign_items
    WHERE campaign_id = :campaign_id AND item_kind = 'chunk'
)
SELECT source_totals.completed_rows AS source_completed_rows,
       chunk_totals.completed_rows AS chunk_completed_rows,
       source_totals.failed_chunks AS source_failed_chunks,
       chunk_totals.failed_chunks AS chunk_failed_chunks
FROM source_totals CROSS JOIN chunk_totals;
```

这里的 `:campaign_id` 由批准的查询客户端绑定实际 ID；不要复制带密钥的连接命令。两组值应相等。若不一致，保留 revision、Campaign ID、时间窗口和脱敏日志，先排查状态变更路径，暂不要手工改计数。

## 4. 回传内容

提供：部署 Commit 与 Migration revision、场景/数据量/并发、同一时段的脱敏日志、浏览器 Network 统计、数据库等待采样，以及异常时的 Job/Campaign ID。对比修复前后时注明环境是否相同。若只有修复后日志，只能判断当前瓶颈和功能状态，不能据此量化生产提升。
