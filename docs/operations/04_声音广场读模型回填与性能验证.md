# 声音广场读模型回填与性能验证

本文只描述已经由当前代码实现的运行边界。Migration、Worker 重启和服务器查询必须按正式部署流程执行；本文不授权生产写入、部署或手工修改投影。

## 1. 部署后会发生什么

Migration `20260920_0054` 只创建声音广场投影、筛选目录、状态、函数、触发器和索引，不在 Migration 事务里扫描历史 Content。后续 Migration `20260921_0055` 为 `processing_import_batch_items.content_id` 和 `collection_candidate_ingestions.content_id` 建立非空部分索引，避免投影判断来源可见性时对历史账本重复做全表扫描；部署时必须先完成 Migration，再启动新 Worker。新写入或变更的 Content、Analysis、人工复核、Brand/Vehicle Evidence、来源贡献和撤销会在原业务事务里增量刷新对应 Content。

Worker 启动时检查 `voice_plaza_projection_state`。状态不是 `ready` 时，幂等创建低优先级 `content.voice-plaza-projection-backfill.v1` Job。每个 Job 切片最多执行 5 个批次，每批按 UUID keyset 处理至多 500 条；批内使用集合式 SQL，投影和检查点在同一短事务提交。单条 PostgreSQL 语句最多执行 180 秒，整个批次事务最多执行 240 秒，因此五个批次即使连续触发事务超时，也会在 30 分钟 Job Deadline 前回到统一 Job Retry，而不是一直占用 Worker。切片成功后在同一 Job 终态事务创建下一切片，让普通采集、分析和导出任务可以优先执行；进程重启、Lease 接管或普通重试仍从最后已提交 UUID 继续。

若外部严格重置误删派生状态单例行，Worker 会通过唯一键幂等恢复 `pending` 状态，并沿原 Job 流程重新扫描 Content；多 Worker 同时启动只形成一个有效状态行和当前代次的回填 Job。恢复不会重建被脚本删除的 Content 或 Artifact，也不覆盖现有检查点。正式需要清空业务数据并保留车型目录时，应使用 [`reset_keep_vehicle_catalog.sh`](../../scripts/deploy/reset_keep_vehicle_catalog.sh) 的 dry-run 与执行入口；它在清库事务中恢复系统种子。

回填完成前：

- 列表和详情基础记录继续走旧查询，保证 1,823,565 条既有数据不会因为部分投影而消失；
- 筛选目录只读已经完成的聚合小表，并返回 `catalog_status=building`；平台、相关性、分析状态和 active Taxonomy 值仍可使用；
- 页面不展示后台同步提示；动态目录会自动刷新，平台、相关性和分析状态继续可用，只有目录请求真实失败时才显示告警。

状态变为 `ready` 后，列表、平台筛选、加载更多、详情基础记录和复用同一查询入口的目标冻结切换到投影路径。

页面首次进入、查询和重置时先发起列表请求，随后立即并行发起同一已应用筛选快照的总数请求；总数不再等待列表完成。快速切换筛选时，浏览器会取消上一条尚未完成的总数请求，旧响应也不能覆盖当前筛选结果。列表或总数任一失败只影响自己的显示区域。

## 2. 只读检查

以下 SQL 都是只读检查；应通过批准的 PostgreSQL 运维入口执行，不在日志或命令历史中写 Secret。

```sql
SELECT status,
       generation,
       last_content_id,
       projected_count,
       total_content_count,
       started_at,
       finished_at,
       last_error_code,
       updated_at
FROM voice_plaza_projection_state;
```

预期终态是 `status='ready'`。没有并发新增时，`projected_count` 应与本代次首次批处理时记录的 `total_content_count` 相等；生产持续写入时，UUID keyset 可能继续扫描部分新记录，另一些新记录由增量触发器直接维护，因此两者可以不同。`total_content_count` 是回填启动时的进度基准，不是此刻全库总数或终态完整性的唯一判断。

```sql
SELECT id,
       status,
       attempt,
       max_attempts,
       progress,
       error_code,
       created_at,
       started_at,
       finished_at
FROM jobs
WHERE job_type = 'content.voice-plaza-projection-backfill.v1'
ORDER BY created_at DESC
LIMIT 5;
```

确认来源反查索引已经随 Migration 建立：

```sql
SELECT tablename,
       indexname,
       indexdef
FROM pg_indexes
WHERE schemaname = current_schema()
  AND indexname IN (
      'ix_processing_import_batch_items_content_id',
      'ix_collection_candidate_ingestions_content_id'
  )
ORDER BY indexname;
```

预期返回两行，且 `indexdef` 都包含 `WHERE (content_id IS NOT NULL)`。缺少任一索引时不要启动回填 Worker，应先检查 Alembic 当前 revision 和 Migration 日志。

不要手工把状态改成 `ready`，也不要直接删除 Job 或投影行来“加速”。这些操作会绕过完整性切换条件。

## 3. 日志怎么看

API 对声音广场五类读取记录统一事件：

```text
voice_plaza.read_completed  DEBUG
voice_plaza.read_slow       WARNING（总耗时 >= 500ms）
```

安全字段包含 `operation=list/filter_options/count/detail/comments`、总耗时、配置读取耗时、数据库查询耗时和投影是否 ready；各操作再记录与排障直接相关的结果形状。`count` 记录请求模式、结果类型、是否得到可靠数字、是否截断以及使用了哪些筛选字段名，不记录搜索词、筛选值、正文、评论、Payload 或 Secret。API 全局中间件仍会对总耗时达到 1000ms 的请求记录 `api.request_slow`。

生产默认 INFO 时不会记录正常 DEBUG 明细，只会保留慢读取 WARNING。需要短时采样正常请求时，先按正式变更流程把 `AIMA_LOG_LEVEL=DEBUG` 应用于 API；验证后恢复原级别，避免长期放大日志量。Worker 启动日志 `worker.started` 会包含本次确保的投影 Job ID；Job 生命周期继续使用统一 `job.started/job.succeeded/job.retry_scheduled/job.failed` 事件。

投影 Worker 额外记录三个批次事件：

```text
voice_plaza_projection.batch_started    INFO
voice_plaza_projection.batch_completed  INFO
voice_plaza_projection.batch_failed     WARNING
```

开始事件包含代次、批次序号和批大小；完成事件还包含本批处理条数、累计投影条数、总量基准、状态和耗时；失败事件只记录异常类型和耗时，不记录 SQL、Content ID、正文或 Secret。发生 `batch_failed` 时先确认两条来源索引存在，再结合 `duration_ms`、Job Retry 和数据库负载分析，不应直接放大语句超时。

## 4. 服务器效果验收

真实 1,823,565 条及后续增长数据的性能结论只能以服务器部署 revision、数据库状态和新鲜日志为准。至少在 `voice_plaza_projection_state=ready` 后分别采样：

1. 无筛选首次进入：`published_at DESC` 的第一页；
2. 五个平台各选择一次后读取第一页；
3. 连续点击两次“加载更多”；
4. 打开包含评论和不包含评论的帖子详情；
5. 一级评论第一页以及一个回复线程。

对前两项同时观察列表和总数请求：两者应使用同一已应用筛选条件，列表请求先发起但总数不能等列表返回后才开始。快速连续切换两个筛选条件时，旧总数请求应被取消或丢弃；当前列表不应被总数失败清空。读模型未就绪时，有筛选的总数显示为“总数数据准备中”；请求真实失败时显示“总数统计失败”；可靠结果为零时显示“共 0 条”。

验收时分别记录列表和总数的 HTTP P50/P95、是否出现 `voice_plaza.read_slow`、`projection_ready` 和数据库 CPU/IO，并确认增加并行总数请求后列表 P50/P95 没有明显回退。浏览器体感还应确认：列表与总数各自完成后立即显示、第一页先于筛选目录出现、切换页面后筛选条件保留、详情摘要即时打开、评论和完整详情独立补齐、加载更多优先命中预取。

如果状态已经 `ready` 但列表日志仍显示 `projection_ready=false`，或相同路径仍持续超过 500ms，应保留对应 `request_id`、时间范围、部署 Commit、状态查询结果和脱敏日志再分析；不要先增加超时或盲目追加索引。

## 5. 回滚边界

应用回滚到不认识新表的旧 revision 时，新表不会改变旧查询事实；但是否执行 Alembic downgrade 仍必须服从正式 Release/数据回滚门禁。`20260921_0055` 的 downgrade 只删除两条来源反查索引；`20260920_0054` 的 downgrade 只删除派生投影、目录、触发器、函数和状态，不删除 Content、Analysis、Evidence、Job 历史以外的业务事实。生产 downgrade 前仍需备份和批准，不能把“派生可重建”当成跳过回滚门禁的理由。
