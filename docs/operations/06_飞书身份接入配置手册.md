# 飞书身份接入配置手册

本手册说明**怎样把一个或多个飞书企业接入 AIMA_UGC，并自证配置正确**。

它只讲"已经存在的飞书登录能力怎样安全配置"。飞书身份能力的架构与安全边界见
[`docs/blueprint/05_日志安全部署与运维.md`](../blueprint/05_日志安全部署与运维.md)；
企业认证的正式验收状态见 [`docs/roadmap/01_生产上线实施路线.md`](../roadmap/01_生产上线实施路线.md)。

## 1. 适用场景与前置条件

适用：源码开发、本地 Compose、公司服务器或生产候选环境首次接入飞书登录，或新增应用。

前置：

```text
□ 已经有可用的 AIMA_UGC 部署（Compose 能正常起来）
□ 有飞书开放平台的应用管理权限（建应用、配权限、发版）
□ 有飞书管理后台的组织架构权限（建/查用户组 ID）
□ 能确定该站点的对外访问地址（协议、域名或 IP、端口）
```

**必须先确定的两个值**（后面所有地址都依赖它们）：

| 值 | 说明 |
| --- | --- |
| **站点地址** | 用户浏览器实际访问的地址，如 `https://ugc.example.com` 或 `http://192.0.2.10:8080` |
| **企业标识（`code`）** | 每个应用入口一个短标识，会进 URL。只允许小写字母、数字、连字符，且以字母或数字开头 |

> **站点地址的三个硬要求**：飞书后台登记的重定向 URL、网页应用主页、配置里的 `redirect_uri`
> 必须**协议、域名/IP、端口完全一致**。生产环境必须 HTTPS。

## 2. 飞书开放平台要配什么

**每家企业各自一个自建应用，各自配置，互不共用。** 两家企业共用一个应用是不行的：
`app_id` 是身份空间的一部分，共用会让两家用户身份互相覆盖。

### 2.1 添加「网页应用」能力

开发者后台 → 应用 → 左侧「添加应用能力」→ 找到「网页应用」→ 添加。

### 2.2 开通权限

按本手册的登录与角色判定链路，需要 5 个权限：

| 权限 | 身份类型 | 用途 |
| --- | --- | --- |
| `contact:group:readonly` | **应用身份** | 查用户所属用户组（判角色的依据） |
| `contact:user.base:readonly` | **用户身份** | 取登录用户的姓名等基础信息 |
| `contact:contact.base:readonly` | 应用身份 | 展示部门信息 |
| `contact:user.department:readonly` | 应用身份 | 取用户所属部门 |
| `contact:department.base:readonly` | 应用身份 | 取部门名称 |

> 前 2 个不配，登录或判角色会直接失败；后 3 个只影响部门信息能否展示。
> 部分权限需要额外设置「数据范围」（可访问的部门/成员），按最小必要范围配置。

### 2.3 配置「重定向 URL」

开发者后台 → 应用 → 左侧「安全设置」→「重定向 URL」→ 添加：

```text
<站点地址>/api/v1/auth/feishu/<该企业 code>/callback
```

**必须与 `AIMA_FEISHU_CONNECTORS` 里该家的 `redirect_uri` 逐字一致。**

### 2.4 配置「网页应用主页」

开发者后台 → 应用 → 左侧「网页应用」→ 网页配置：

| 字段 | 填 |
| --- | --- |
| 桌面端主页 | `<站点地址>/login?c=<该企业 code>` |
| 移动端主页 | 同上 |

**为什么带 `?c=`**：它让用户从本企业工作台进入时，登录页直接显示"你正在从【本企业】登录"，
不需要在企业列表里自己选。不带 `?c=` 时登录页会列出全部已配置企业，用户**可能选错企业**，
选错后飞书会以"你没有该应用的使用权限"拒绝（因为账号不属于那家企业）。

**注意**：`?c=` 只影响"选哪家"，用户仍需点一次登录按钮。若希望完全跳过登录页，
主页可直接填 `<站点地址>/api/v1/auth/feishu/<code>/login`，但这会跳过前端页面。

### 2.5 发布

- **正式应用**：改完配置要「创建版本 → 发布」才生效；
- **测试版应用**（使用"测试企业与人员"时）：改完即时生效，无需发版。

## 3. AIMA 侧配置

本地使用 `env.local`，服务器使用 `env.production`。启用登录时设 `AIMA_IDENTITY_MODE=feishu`；正式模式配置不完整时启动失败，`development` 只适用于明确的本地开发或隔离测试。

### 3.1 推荐格式：每个应用一个对象

一个应用填一项，多个企业或同企业多个应用填多项。App ID 与 App Secret 均来自该应用「凭证与基础信息」，用户组 ID 按对应应用授权范围填写。

```dotenv
AIMA_IDENTITY_MODE=feishu
AIMA_FEISHU_CONNECTORS='[
  {
    "code": "aaa",
    "display_name": "A 公司正式应用",
    "app_id": "cli_aaa",
    "app_secret": "<该应用 App Secret>",
    "admin_group_id": "<管理员组ID>",
    "user_group_id": "<普通用户组ID>",
    "redirect_uri": "https://ugc.example.com/api/v1/auth/feishu/aaa/callback"
  },
  {
    "code": "aaa-test",
    "display_name": "A 公司测试应用",
    "app_id": "cli_aaa_test",
    "app_secret": "<测试应用 App Secret>",
    "admin_group_id": "<管理员组ID>",
    "user_group_id": "<普通用户组ID>",
    "redirect_uri": "https://ugc.example.com/api/v1/auth/feishu/aaa-test/callback"
  }
]'
```

外层单引号必须配对；内部是标准 JSON，使用双引号，无注释或尾随逗号。源码 launcher 和 Compose 均支持这种多行写法。JSON 字符串内如需单引号，按 env 语法写成 `\'`；不要使用 shell 命令替换。

`code` 是应用入口标识，影响登录 URL；`display_name` 是登录页显示名称。每项的 `code`、`app_id` 与 `app_secret_ref` 必须唯一，管理员组与普通组不能相同。同企业的不同应用仍有独立身份空间，用户布局、导出和个人配置不会因为姓名或企业相同而自动合并。

`app_secret_ref` 可省略，默认生成 `feishu_<code>_secret`。已有文件引用可继续显式填写；引用必须是安全的相对路径，不能占用内部运行配置或 TikHub/LLM 文件，不能让一个文件同时成为另一引用的父目录。

### 3.2 回调地址按启动方式填写

| 启动方式 | 站点地址示例 |
| --- | --- |
| 源码 [scripts/dev/backend.py](../../scripts/dev/backend.py) + [scripts/dev/frontend.py](../../scripts/dev/frontend.py) | `http://127.0.0.1:5173`（前端代理 API 8090） |
| 本地 Compose | `http://127.0.0.1:8080`（端口取实际 `AIMA_HTTP_PORT`） |
| 生产反向代理 | 实际 HTTPS 站点，如 `https://ugc.example.com` |

每项回调都是 `<站点地址>/api/v1/auth/feishu/<code>/callback`，必须与该应用后台登记的重定向 URL 逐字一致。源码启动不会监听 8080；本地默认也没有 HTTPS 监听。配置里的斜线直接写 `/`，无需写 `http\://`。

### 3.3 单应用与独立发布应用

登录只使用 `AIMA_FEISHU_CONNECTORS`，单应用保留数组中的一项即可。旧扁平登录变量已移除；仍填写旧用户组或回调变量时启动明确报错，请把对应值移到数组项中。正式 `feishu` 模式没有有效 Connector 时拒绝启动。

`AIMA_FEISHU_APP_ID` / `AIMA_FEISHU_APP_SECRET_REF` 仅服务独立的多维表同步和 Word 报告发布，不会启用网页登录或自动选取某个登录应用。不使用发布能力时 App ID 留空；需要共用登录应用时，显式填写同一 App ID 及生成的 Secret 引用。报告未配置引用时的默认 `feishu/report_app_secret` 与模板显式的 `feishu_app_secret` 是不同文件。

## 4. App Secret 自动落盘与兼容文件

填写非空 `app_secret` 后，源码 launcher 或 Compose 的 bootstrap 初始化容器会先校验整组配置，再将各应用凭据写入对应文件。错误只报告配置位置和规则，不回显凭据。原始输入只供启动流程使用；API、Worker、Scheduler 的 Connector 配置中不包含 `app_secret`。

| 运行方式 | Secret 实际位置 |
| --- | --- |
| 源码 | `.runtime/secrets/<app_secret_ref>` |
| Linux Compose | `${AIMA_HOST_ROOT}/shared/provider-secrets/<app_secret_ref>` |
| Windows Compose 覆盖 | Docker named volume `windows_provider_secrets` 内相同引用 |

Compose bootstrap 同时生成不含凭据的 `feishu-connectors.json`，业务容器通过内部 `AIMA_FEISHU_CONNECTORS_FILE` 只读加载；不需要用户填写该内部路径。Windows named volume 由同一初始化流程写入，填写 app_secret 后无需手工复制到卷。Linux 自动文件使用业务 UID/GID 10001:10001、0600；子目录也允许该用户遍历。

显式填写的凭据在每次启动时更新，可用于轮换；因此轮换应修改原始 env 并重新启动全部受影响进程/服务，不能只改生成文件。`app_secret` 留空或省略时不覆盖、不删除已有手工文件，也不会自动迁移旧引用；仍需确保对应文件可读。移除 Connector 不会自动删除历史 Secret，停用后按部署方的凭据清理流程处理。

真实 env 文件现在也包含飞书 App Secret，必须限制访问（Linux 建议 0600），不得提交 Git、打进镜像或 Release、粘贴到工单/日志。Compose bootstrap 是唯一接收原始 CONNECTORS 启动输入的容器，Docker 管理权限可查看其环境；应与 env 文件及其他 Provider 凭据采用相同的主机访问控制。

仍需手工提供凭据时，只放 App Secret 本身，UTF-8，无首尾空格；读取器允许末尾换行。Linux 文件需业务用户可读，目录不能是链接。Windows Compose 手工模式应将文件放入对应 provider-secrets named volume，不能只写宿主同名目录；推荐改用上述自动落盘方式。

此配置调整不需要数据库迁移。应用回退保留生成的 Secret 文件；回退到尚不支持自动落盘的旧代码时，必须同时恢复匹配的 Compose，并将 CONNECTORS 改为只含显式 `app_secret_ref` 的旧格式，移除 `app_secret`。旧业务进程不能直接接收带明文凭据的数组；回退涉及旧认证缺陷时仍需先建立访问隔离。

## 5. 生效

源码方式修改 `env.local` 后重启 [scripts/dev/backend.py](../../scripts/dev/backend.py)。Compose 修改 env 后必须先重新运行 bootstrap 更新文件，再重建业务服务；不能只 restart API。

```bash
docker compose --env-file env.local -f compose.yaml -f compose.windows.yaml \
  run --rm --no-deps bootstrap
docker compose --env-file env.local -f compose.yaml -f compose.windows.yaml \
  up -d --force-recreate api worker scheduler
docker compose --env-file env.local -f compose.yaml -f compose.windows.yaml \
  restart frontend
```

- `--force-recreate` 必须：只 `up -d` 不会重新读取变更后的 env；
- `restart frontend` 必须：nginx 启动时解析一次 `api` 主机名并缓存，
  重建 api 后容器 IP 变化，不重启 frontend 会得到 `502`。

Linux 上不叠加 [`compose.windows.yaml`](../../compose.windows.yaml) 时去掉该 `-f` 参数。

## 6. 验证

按顺序做，任一步失败就不要继续。

### V1 配置是否进入容器

```bash
docker exec aima-ugc-api-1 printenv AIMA_IDENTITY_MODE
docker exec aima-ugc-api-1 printenv AIMA_FEISHU_CONNECTORS_FILE
```

身份模式应为 `feishu`，内部配置路径应为 `/run/provider-secrets/feishu-connectors.json`。业务容器不接收原始 CONNECTORS；不要通过打印 bootstrap 环境检查凭据。数组内容以接下来的公开 Connector 发现接口核对；单应用同样应返回数组中配置的那一项。

### V2 Secret 文件是否就位

```bash
docker exec aima-ugc-api-1 ls -la /run/provider-secrets/
```

每个 `app_secret_ref` 应各有一个文件。缺文件时检查对应 app_secret 是否填写、bootstrap 是否成功，以及运行模式是否匹配；手工模式检查文件所在 bind/volume。不要打印文件内容。

### V3 企业列表是否正确

```bash
curl -s http://127.0.0.1:8080/api/v1/auth/connectors
```

预期返回每家一条，只含 `code` 与 `display_name`，**不含密钥、组 ID 或回调地址**：

```json
{"items":[{"code":"aaa","display_name":"A 公司"},{"code":"bbb","display_name":"B 公司"}]}
```

### V4 每家的登录入口是否指向自己的应用（**最关键**）

```bash
for c in aaa bbb; do
  echo "--- $c ---"
  curl -s -D - -o /dev/null "http://127.0.0.1:8080/api/v1/auth/feishu/$c/login" \
    | tr -d '\r' | grep -i '^location'
done
```

**⚠️ 必须用 `curl -s -D - -o /dev/null`（GET 取头），不要用 `curl -sI`** ——
`-I` 发 HEAD 请求，登录路由只接受 GET，会返回 `405`；看到 405 是用错了命令，不是配置错。

预期每家的 `location` 里 `client_id` **等于该企业自己的 App ID**，
`redirect_uri` **含该企业自己的 code**。两家的 `client_id` 相同即为配置串号。

### V5 真实登录

用该企业的飞书账号走完整流程，确认能进入系统并显示正确身份。
若要验证"同一人在两家企业得到两个独立身份"，用同一账号依次从两家入口登录，
数据库 `identity_external_identities` 中应出现两条不同 `connector_id` 的映射。

## 7. 常见报错对照

### 7.1 启动时报配置错误

| 报错片段 | 原因 | 处理 |
| --- | --- | --- |
| `不是合法 JSON` | JSON 语法错（多逗号、少引号、被换行拆断） | 用 JSON 校验器过一遍，确认整行未被折行 |
| `必须是 JSON 数组` | 写成了对象 `{...}` | 外层套方括号 |
| `code='X' 不合法` | `code` 含大写或特殊字符 | 改为小写字母/数字/连字符 |
| `redirect_uri 必须包含 '/feishu/X/callback'` | 回调地址少了企业标识段，或带了别家的 | 改成 `/feishu/<本条 code>/callback` |
| `code 重复` | 两家 `code` 相同 | 改掉其中一个（约束 1） |
| `使用了同一个 app_id` | 两家用同一应用 | 两家各建独立应用（约束 2） |
| `使用了同一个 app_secret_ref` | 两家 Secret 文件名相同 | 改成两个不同文件名（约束 3） |
| `admin_group_id 与 user_group_id 相同` | 同家里两个组 ID 一样 | 建两个独立用户组（约束 5） |
| `缺少非空字符串字段` | 少写字段 | 补齐 7 个字段 |
| `多企业配置不能是空列表` | 写了 `[]` | 要么不写这行，要么至少写一家 |

### 7.2 运行时报错

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `app secret invalid` | Secret 值不对（常见：多/少字符，或文件末尾有换行） | 用飞书「复制」重取，确认文件无换行 |
| `SecretFileError` | 文件不存在、权限不对，或 Windows 没同步进卷 | 见 4.2–4.4 |
| 飞书返回 `20071` / `20029` | 飞书后台登记的回调地址与配置不一致 | 逐字符核对 |
| `unknown_connector`（404） | 访问了没配置的 `code` | 检查 `AIMA_FEISHU_CONNECTORS` |
| 登录后进了别家企业 | `redirect_uri` 的 code 与本条不一致 | 见约束 4 |
| `502 Bad Gateway` | 重建 api 后没重启 frontend | 见第 5 节 |
| 改了配置没生效 | 没 `--force-recreate` | 见第 5 节 |
| 用户看到企业列表而非"正在从 X 登录" | 飞书后台「网页应用主页」没配 `?c=` | 见 2.4 |
