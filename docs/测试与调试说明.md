# AIMA_UGC 测试与调试说明

本文是面向开发、调试、联调和维护人员的 **AIMA_UGC 人类可读测试入口**。它回答“这个能力怎么单独验证、测试代码在哪、需要什么依赖、什么结果算成功”。

测试代码、Contract、Fixture、Migration、实际运行结果和 CI 才是机器事实；本文只负责导航和解释，不复制第二套断言或 Schema。

## 1. 核心原则

对具有明确输入输出、独立业务价值、独立失败边界，或无需启动完整系统即可验证的能力，优先建立独立验证闭环：

```text
生产实现
→ 明确输入
→ 可控依赖
→ 可观察输出
→ 自动化测试
→ 明确运行命令
→ 预期结果
```

调试、Probe、测试和示例必须复用生产实现，不得重新复制分页、映射、状态转换、数据库写入、错误分类或业务规则。

不机械要求“一模块一个测试文件”或“一功能一个测试文档”。测试粒度由行为边界、风险、依赖和失败模式决定。

## 2. 测试目录与层级

仓库根目录的测试分层为：

```text
tests/
├─ unit/
├─ contracts/
├─ integration/
└─ api/
```

前端测试由 `frontend/` 内的 Vitest / Vue Test Utils / Playwright 入口维护。

各层职责：

| 层级 | 主要证明什么 | 典型对象 |
| --- | --- | --- |
| Unit | 纯逻辑、转换、状态机和错误分类 | Mapper、分页状态机、业务规则、Formatter、费用计算 |
| Contract | 生产者/消费者共享结构不漂移 | Canonical、Job Payload、OpenAPI、Provider Fixture、生成 Client |
| Integration | 与真实隔离基础设施协作正确 | Repository、Migration、Artifact、Job、Ingestion、Query、事务与并发 |
| API | HTTP Contract 和 Router/Service 行为正确 | 状态码、错误、ID、时间、Cursor、异步 Job API |
| Frontend Unit | Store、Feature API 和组件状态正确 | loading/error/empty、交互、生成 Client Mock |
| E2E | 用户可见完整纵切正确 | 页面 → API → Service → PostgreSQL / Fake Provider |
| Release Smoke | 构建和部署产物能在目标环境运行 | Compose、镜像、Migration、离线 Release |

一个能力可能同时需要多层测试。不要因为已经有 Unit Test 就省略真正需要 PostgreSQL、HTTP 或 E2E 才能证明的行为。

## 3. 一个独立验证闭环必须说明什么

开发或实质修改一个独立能力时，在模块 README、测试说明或现有等价事实源中明确：

1. **生产入口**：正式代码从哪里进入；
2. **输入**：参数、Contract、Fixture、文件或数据库前置状态；
3. **输出**：返回值、数据库状态、Artifact、事件、错误等；
4. **测试位置**：哪些测试文件/目录覆盖它；
5. **Fixture / Fake**：使用什么固定样本或可控依赖；
6. **外部依赖**：是否需要 PostgreSQL、文件目录、浏览器或真实外部服务；
7. **运行命令**：最小可重复执行入口；
8. **预期结果**：什么算通过；
9. **已知限制**：哪些场景尚未验证。

若能力没有独立验证价值，不为形式创建空测试目录或文档。

## 4. AIMA 关键能力如何验证

以下是长期测试边界。只有进入对应开发阶段、生产实现真实存在后，才建立相应测试；不要提前为未来能力补造空测试。

### 4.1 Provider Adapter / Operation

目标：确认外部输入边界、请求构造、分页、错误分类和来源元数据正确，同时不让测试逻辑复制 Provider 实现。

推荐组合：

```text
Fake Transport / Stub
→ 正式 Client / Adapter / Operation
→ 固定 Raw Page / Error
```

- Unit：请求参数、分页状态机、停止条件、错误分类、费用逻辑；
- Contract：脱敏 Provider Fixture 的结构和关键语义；
- 真实 Probe：只用于确认真实 Provider 行为，默认关闭，不进入普通 CI；
- 有费用的 Probe 必须显式提醒费用，不写生产库，不打印 Secret。

Stage 5A Provider-neutral 生产入口和测试为：

```text
ProviderRequestV1 + ProviderTransportRequest
→ ProviderClient
→ FakeProviderTransport
→ ProviderAttemptV1 + 脱敏 Raw Request/Response
```

```bash
uv run pytest tests/unit/collection tests/contracts/test_provider_v1.py -q
```

覆盖一次发送、成功、429、5xx、发送前失败、发送后结果未知、费用状态和测试 Token 排除序列化。Stage 7 已在该边界之上接通小红书、抖音、微博、B站、快手 TikHub Operation/Mapper；普通测试仍使用 Fake + 脱敏 Fixture，不访问真实付费 Provider。

Stage 6 小红书请求和分页的生产入口是
`aima_ugc.adapters.providers.tikhub.operations.xiaohongshu`：

```bash
uv run pytest tests/unit/collection/test_xhs_tikhub_operation.py -q
```

测试覆盖搜索、图文/视频详情、一级/二级评论 endpoint 和参数，以及搜索/评论分页推进、空页、重复页和
状态不推进停止。2026-08-14 经用户明确授权执行过最小只读真实搜索 Probe；两次 HTTP 200 都是空结果页，
只确认当次响应包装、分页会话字段和空页兼容，不替代非空 Fixture，也不进入普通 CI。

#### Stage 7 统一人工 Real Provider Probe

Stage 7 已建立受控 Real Provider Probe 脚本；它们复用生产 Operation/Transport/Mapper，不是第二套采集器。当前主要入口包括：

```text
scripts/dev/probe_tikhub_api_families.py
scripts/dev/probe_tikhub_endpoint_ledger.py
scripts/dev/probe_tikhub_stage7_search.py
scripts/dev/probe_tikhub_stage7_detail_comments.py
scripts/dev/probe_tikhub_stage7_replies.py
```

统一原则仍是：

```text
显式 Probe 配置
→ 正式 Provider Config / Secret 边界
→ 正式 Provider Client
→ 正式 Platform Operation / 分页
→ 逐请求 Raw
→ 正式 Mapper
→ Canonical Contract 校验
→ 原始数据 Excel 导出
```

Probe 配置应允许开发者按当前已经批准并实现的 Operation 选择/填写：

- Provider Base URL；
- 平台；
- Operation；
- 关键词；
- 内容 ID、评论 ID；
- 排序、发布时间范围等该 Operation 明确支持的搜索选项；
- 初始分页参数或状态；
- `max_pages`、`max_requests` 等显式请求上限；
- 独立输出目录。

五个平台不要求拥有相同的 Provider 私有参数；脚本只调用当前代码已经批准的 Operation/分页状态机。新增或替换 endpoint 时，先以官方资料、现有 Fixture/台账确认；仍有结构不确定时才在用户明确授权下用 GitHub Runner 做有请求上限的最小真实 Probe，并把合法脱敏结果固化为 Fixture/台账。

真实 API Key/Credential 从正式 Secret 边界读取，不写进 Probe 配置样例或脚本。真实 URL 可以显式配置，但仍受正式 Provider 出站域名和安全校验约束。Probe 不得自行拼 endpoint、复制分页状态机、重新实现 Mapper，也不得因为“只是调试”绕过 Secret、脱敏、请求上限或安全检查。

一次人工 Probe 至少产生三类可观察结果：

```text
Raw
→ 每个真实请求的完整脱敏 JSON/GZIP，保留 Provider 原始证据

Canonical
→ 正式 Mapper 的转换结果，并通过当前 Canonical Contract 校验

原始数据 Excel
→ 基于 Canonical 生成的帖子/指标/评论明细视图；完整 Provider Raw 仍单独保存
```

Real Probe 默认关闭、不进入普通 CI、不写生产业务数据库。普通 CI 仍使用 Fake + 脱敏 Fixture。真实结果只证明当次接口兼容性；发现字段变化后应把合法脱敏样本固化为 Fixture，再由可重复自动测试维护。

#### 原始数据 XLSX 布局

XLSX 的目标是让人快速阅读帖子/笔记/视频及其评论，不是把数据库表或嵌套 JSON 原样铺成大量 Sheet。Workbook 应控制在少量 Sheet，核心必须提供 `内容与评论` 视图；可以使用 `概览`、`异常与原始定位` 等辅助 Sheet，但完整 Raw 不复制成大量工作表。

`内容与评论` 的长期显示规则：

- 一条帖子/笔记/视频形成一个连续的纵向内容区块；
- 帖子公共字段跨该内容对应的评论行纵向合并；
- 每条一级或二级评论独占一行；
- 一级/二级回复可用层级列、缩进或轻量标识帮助阅读，但真实关系仍必须显示或可追溯到 `external_comment_id`、`root_comment_id`、`parent_comment_id`，不得靠 Excel 行位置猜关系；
- 如果内容没有评论，仍至少保留一行内容，并明确显示 `complete`、`partial`、`not_requested`、`unavailable` 等评论覆盖状态，不能把空白解释成“确定没有评论”；
- 内容/评论的外部 ID 按文本格式写入，避免 Excel 长整数精度丢失或科学计数法；
- 长正文自动换行，原文 URL/可公开链接可作为超链接；
- 不使用粗黑边框包围每个帖子区块；以留白、轻量分隔和清晰层级为主，避免把原始数据 Excel做成密集数据库网格；
- Provider/用户可控文本写入 XLSX 时必须防公式注入，不能让以 `=`, `+`, `-`, `@` 等起始的外部文本被 Excel 当成公式执行。

辅助定位信息应让人工发现异常后能够回到原始证据，例如来源页/请求、Raw 文件和稳定 item locator。XLSX 不是机器回灌格式，不承担无损保存全部 Provider JSON 的职责；完整结构始终回到 Raw，业务映射始终回到 Canonical。

#### 长期五平台 `tikhub_test` 调试入口

`backend/src/aima_ugc/adapters/providers/tikhub_test/` 是五个平台长期人工调试入口。平台函数只准备业务参数，实际 endpoint、分页、Mapper、Capability、Decision 和增量历史边界都复用生产实现。

默认模式：

```text
run_xiaohongshu / run_douyin / run_weibo / run_bilibili / run_kuaishou
→ write_to_database=False
→ 生产 TikHub Runtime / Transport → 本地 Raw → 生产 Mapper → Canonical
→ 生产 Collection Decision / known_comment_reached
→ run_summary.json + state.json + 共享原始数据 Excel
```

显式 Stage 8A 数据库模式：

```text
write_to_database=True + provider_config_id=<正式 UUID>
→ PostgreSQL 18 / Schema / Provider Config / Secret 一致性校验
→ manual Collection Run / Scope / Job Fencing
→ 正式 Provider Request / Attempt / Dispatch
→ 同一次网络响应同时保留本地调试 Raw + 正式 Raw Artifact
→ Candidate-before-Mapper
→ 正式 Mapper / Canonical
→ fenced Content Ingestion
→ PostgreSQL
```

真实 `.env` 只保存在调试目录本地且不提交；关键词是函数参数。支持单关键词和多关键词，多关键词共享内容 identity 去重。XHS/B站在已验证最新排序下可用已知评论历史边界停止下一页；其余平台保持受控刷新。数据库模式要求显式 `provider_config_id`，且正式 Provider Config 的 Base URL/Secret 必须与本次 `.env` 实际配置一致；脚本不管理 Docker，也不自动运行 Migration。

当前原始数据 Excel 已复用 `UnifiedDataExcelV1 + aima_ugc.platform.export.excel` 共享 Exporter；`tikhub_test` 不再维护平行 Workbook 实现。数据库模式不会从该 Excel 或 Canonical JSONL 二次回灌，也不会为了写库额外再发送一次 TikHub 请求。

#### 文件 Excel `imports_test` 调试入口

`backend/src/aima_ugc/adapters/providers/imports_test/test.py` 复用正式 Excel Reader/Mapper、
Provider-neutral 关键词过滤、稳定身份去重、Analysis Service、LLM Adapter 和共享 Excel
Exporter。普通自动回归不调用真实 LLM；人工执行该入口到 AI 打标阶段时默认启用真实付费
调用，可在仅做导入、去重或导出时把 `ENABLE_REAL_LLM` 改为 `False`。

去重身份固定为 `(platform, external_content_id)`。同一身份无论业务字段是否完全相同，都只保留
源 JSONL 中首次出现的记录；非等价后续记录写入 `deduplication_conflicts.jsonl` 作为差异审计，
但不阻止发布 `deduplicated/contents.jsonl`。测试必须覆盖五个平台、首次记录顺序、差异字段审计
以及输出稳定身份唯一性，不能通过拼接字段制造一条源输入中不存在的代表记录。

Stage 8A 保持 `WRITE_TO_DATABASE=False` 默认值；显式 `run_all(write_to_database=True)` 或单独调用 `ingest_database(run_dir=...)` 时，在去重后建立 Input Artifact → Processing Import Batch → import-parent Provider Request / non-billable Attempt → Canonical Source → 正式 Content Ingestion。该路径不伪造 Collection Run/Scope/Candidate，不直接写 Content SQL，也不管理 PostgreSQL 容器或 Alembic Migration。

### 4.2 Mapper

目标：证明固定 Raw/Fixture 能通过正式 Mapper 产生合法 Canonical。

```text
脱敏 Fixture
→ 正式 Mapper
→ CanonicalContentV1 / CanonicalCommentV1
→ Contract 校验
```

Mapper 测试不得访问数据库或发真实 HTTP。

Stage 7 五个平台 Mapper/Extractor 都从生产实现进入，并使用 `tests/fixtures/providers/tikhub/{xhs,douyin,weibo,bilibili,kuaishou}/` 下的合法脱敏真实/固定 Fixture 维护已观察结构。平台 Operation/Mapper/Capability 的单元测试、Stage 6/7 正式 CI，以及保留的 `Stage 7 TikHub Real Shape` 手动入口共同防止字段映射漂移。

```bash
uv run pytest tests/unit/collection/test_xhs_tikhub_mapper.py -q
uv run pytest tests/unit/collection -q
```

Fixture 证明的是已捕获并脱敏的响应形态，不承诺 Provider 永久不变；真实接口变化必须先保留 Raw 证据，再更新 Mapper/Fixture/测试，不能凭一次在线请求静默改字段。

### 4.3 Raw / Artifact

目标：证明不可变 Raw/Artifact 的写入、完整性和来源关联正确。

Integration 至少按实际能力覆盖：原子写、不可覆盖、路径安全、SHA-256、gzip/文件可读取性、状态推进和失败对账。

Stage 5A 使用正式 `ProviderClient → RawArtifactService → ArtifactService → LocalArtifactStore`，Metadata 使用可控 Fake 隔离尚未建立的 Provider Attempt Repository：

```bash
uv run pytest tests/integration/collection/test_raw_artifact.py -q
```

测试验证递归 Secret 脱敏、稳定层级路径、no-overwrite、SHA-256、大小、gzip、Pydantic 回放和篡改拒绝。独立 Raw 测试只推进 Artifact 到 `stored`；Stage 5D 的 PostgreSQL 集成测试再验证 terminal Attempt 引用 Raw 并把 Artifact 推进到 `linked`。

Run/Scope 创建；Repository 不提交事务，提交或回滚由调用方持有：

```bash

uv run alembic upgrade head
uv run pytest tests/integration/collection/test_collection_repository.py -q
uv run alembic check
```

Integration 要求隔离 PostgreSQL 18、对应 `AIMA_*` 配置和

JSONB/default、读取与 caller rollback；独立 `.github/workflows/stage5b-collection-execution.yml`
同时验证 `base → head`、`20260814_0002 → head` 及两种 downgrade/re-upgrade。SQLite、Mock Row

本阶段只创建 `manual/api/backfill` queued 父事实；不验证 Worker、Run/Scope 状态转换、
Plan/Occurrence/Scheduler、Provider 持久化、预算或真实外部调用。Provider 持久化由下一节独立验证。

### 4.5 Provider Request / Attempt 持久化基础

Stage 5C 从正式 `ProviderPersistenceService → PostgresProviderRepository → PostgreSQL` 入口验证
Provider Request/Attempt 的创建和查询；Repository 不提交事务、不执行外部 I/O：

```bash
uv run pytest tests/unit/collection/test_provider_persistence.py -q
uv run alembic upgrade head
uv run pytest tests/integration/collection/test_provider_repository.py -q
uv run alembic check
```

Integration 要求隔离 PostgreSQL 18、对应 `AIMA_*` 配置和
`<AIMA_SECRET_DIR>/postgres_password`。测试覆盖 Collection Scope/Request/Artifact 外键、Request/Attempt
幂等和冲突、父链不匹配、来源身份冻结、并发 Attempt 编号、数据库 Check/Unique 和 caller rollback；
独立 `.github/workflows/stage5c-provider-persistence.yml` 同时验证 `base → head`、
`20260814_0003 → head` 及两种 downgrade/re-upgrade。SQLite、Mock Row 或内存集合不能代替这些证据。

Stage 8A 在不改写 Stage 5C 历史 Revision 的前提下，把 Provider Request 父级向前一般化为 `collection_scope XOR import_batch`：现有 Collection Request 仍走 Scope；File Import 走 Processing Import Batch。新增 Contract/Schema 集成测试必须同时证明无父级和双父级都关闭失败，且 import-parent Request 不绑定外部 `provider_config_id`。

Stage 5C 基线只验证 `pending` Request 和 `dispatch_status=reserved`、尚未发送、
`billing_status=not_billable` 的 Attempt；HTTP Provider dispatch/recovery 仍由下一节独立验证。Stage 8A File Import 的 non-billable Attempt 与 Input Artifact 绑定由 Stage 8A PostgreSQL 集成测试验证。

### 4.6 Provider Dispatch 与恢复

Stage 5D 从正式 `ProviderDispatchService → ProviderClient/Fake Transport → RawArtifactService` 和
`PostgresProviderDispatchPersistence → PostgreSQL` 入口验证不计费 Provider-neutral 纵切：

```bash
uv run pytest tests/unit/collection/test_provider_dispatch.py tests/unit/collection/test_provider_recovery.py -q
uv run alembic upgrade head
uv run pytest tests/integration/collection/test_provider_dispatch.py -q
uv run alembic check
```

Integration 要求隔离 PostgreSQL 18、对应 `AIMA_*` 配置和
`<AIMA_SECRET_DIR>/postgres_password`。测试必须证明：有效 Job Fencing 才能取得
`reserved → dispatching` CAS；旧 Token 在 Transport 之前关闭失败；每个 Attempt 最多调用一次；
terminal 结果与 Raw 引用、Artifact `linked` 在短事务中提交；接管者发现完整 Raw 时只做回放恢复，
没有完整 Raw 时记为 `unknown` 且不复发同一 Attempt。独立
`.github/workflows/stage5d-provider-dispatch.yml` 还验证第五条 Migration、上一 Revision 升级和
downgrade/re-upgrade。

本阶段使用 Fake Transport，不访问网络、不产生费用；不验证真实 Provider/Operation、预算账户与 Reservation、
费用结算、Candidate/Ingestion、Collection Job Handler 或生产 Probe。普通 CI 禁止调用付费 Provider。

## 5. Fixture、Fake、Stub、Probe 的区别

### Fixture

固定、可复现输入。适合 Provider 响应、Canonical、数据库种子和报告上下文。

- 必须脱敏；
- 不提交 Secret、Cookie、Token 或未授权个人信息；
- 能稳定复现测试行为。

### Fake / Stub

用于控制不属于当前验证目标的外部依赖。测试仍从生产入口进入，不只验证 Fake 自己。

### 真实 Probe

用于确认真实外部系统、版本、网络或 Provider 行为。它不是普通自动化测试的替代品。

真实 Probe 如果涉及费用、写操作、速率限制或敏感信息：

- 默认关闭；
- 明确运行前提、真实参数和费用上限；
- 真实 Credential 只从正式 Secret 边界取得；
- 不进入普通 CI；
- 不写生产数据；
- 不打印或持久化 Secret；
- 完整脱敏 Raw 必须保留，人工 XLSX 只作为派生原始数据 Excel；
- 结果只证明当次真实边界，不替代可重复 Fixture/Fake 测试。


不为每个小函数创建 README/TESTING 文档；如果模块 README 已经能完整说明，就不另建平行文档。

## 8. 如何判断测试闭环完成

至少确认：

- 目标行为有自动化测试或明确、合理的替代验证；
- 测试从生产入口进入，没有第二套业务实现；
- 与风险匹配的层级已经覆盖，必要的真实基础设施测试没有被 Mock 代替；
- Fixture/Fake/Probe 边界清楚；
- 运行命令和预期结果能被后续维护者理解；
- 失败模式、边界条件和关键错误语义被验证；
- 受影响的模块 README / 本文已经同步；
- 本轮目标测试、相关回归和 CI 有新鲜证据。

测试文件存在本身不代表闭环，README 写了“测试通过”也不代表闭环；以实际行为和执行证据为准。

## 高风险 Collection / Content 长期回归门禁

Stage 1—7 当前机器实现的高风险回归不能只靠普通 happy-path Unit Test。至少长期覆盖：

- Search Current 已提交后 Detail/Comments 失败，再次执行恢复 durable action，不因 previous/current 已变化而跳过；
- old Raw replay 使用 Raw 自身完成时间，不回滚较新的 Current；
- invalid Plan 与 valid Plan 同时存在时 Scheduler 隔离失败，0 execution-surface/0 Scope 关闭失败；
- Run Snapshot 的 Provider/Decision/关键词/Deadline 语义在 Plan/Provider Config 后续变化后不漂移；
- Candidate 在 Mapper 前形成，Mapper/内容/线程身份失败仍有 invalid/failed ledger；
- 内容级与 thread Coverage 区分 Provider 末页、显式空页、soft target、known ID、技术分页异常，不能把 partial 伪装为 complete；
- Canonical 子实体和字段 freshness 在乱序/A→B→A/显式 null 下保持 Current/Version 一致；
- Attempt↔Raw 来源、Job Fencing、Secret root/symlink、递归日志脱敏由 PostgreSQL/边界测试共同保护；
- Alembic 数据型 Migration 要从旧 Revision 写入代表性历史数据后升级验证，而不仅是空库 `upgrade/downgrade`。

当前核心入口为 `tests/unit/collection/test_stage1_stage7_comprehensive_corrective.py`、`tests/unit/collection/test_comprehensive_corrective_invariants.py`、`tests/integration/collection/test_comprehensive_corrective_runtime.py`、`tests/integration/collection/test_collection_scope_replies_runtime.py`、`tests/integration/database/test_migration_data_lifecycle.py`。普通 CI 使用 PostgreSQL 18 + Fake/脱敏 Fixture，不调用真实付费 TikHub。
