# AIMA_UGC 测试与调试说明

本文是面向开发、调试、联调和维护人员的 **AIMA_UGC 人类可读测试入口**。它回答“这个能力怎么单独验证、测试代码在哪、需要什么依赖、什么结果算成功”。

测试代码、Contract、Fixture、Migration、实际运行结果和 CI 才是机器事实；本文只负责导航和解释，不复制第二套断言或 Schema。

## 1. 核心原则

对具有明确输入输出、独立业务价值、独立失败边界，或无需启动完整系统即可验证的能力，优先建立独立验证闭环：

```text
生产实现
→ 明确输入
→ 可控依赖
→ 可观察输出
→ 自动化测试
→ 明确运行命令
→ 预期结果
```

调试、Probe、测试和示例必须复用生产实现，不得重新复制分页、映射、状态转换、数据库写入、错误分类或业务规则。

不机械要求“一模块一个测试文件”或“一功能一个测试文档”。测试粒度由行为边界、风险、依赖和失败模式决定。

## 2. 测试目录与层级

仓库根目录的测试分层为：

```text
tests/
├─ unit/
├─ contracts/
├─ integration/
└─ api/
```

前端测试由 `frontend/` 内的 Vitest / Vue Test Utils / Playwright 入口维护。

各层职责：

| 层级 | 主要证明什么 | 典型对象 |
| --- | --- | --- |
| Unit | 纯逻辑、转换、状态机和错误分类 | Mapper、分页状态机、业务规则、Formatter、费用计算 |
| Contract | 生产者/消费者共享结构不漂移 | Canonical、Job Payload、OpenAPI、Provider Fixture、生成 Client |
| Integration | 与真实隔离基础设施协作正确 | Repository、Migration、Artifact、Job、Ingestion、Query、事务与并发 |
| API | HTTP Contract 和 Router/Service 行为正确 | 状态码、错误、ID、时间、Cursor、异步 Job API |
| Frontend Unit | Store、Feature API 和组件状态正确 | loading/error/empty、交互、生成 Client Mock |
| E2E | 用户可见完整纵切正确 | 页面 → API → Service → PostgreSQL / Fake Provider |
| Release Smoke | 构建和部署产物能在目标环境运行 | Compose、镜像、Migration、离线 Release |

一个能力可能同时需要多层测试。不要因为已经有 Unit Test 就省略真正需要 PostgreSQL、HTTP 或 E2E 才能证明的行为。

## 3. 一个独立验证闭环必须说明什么

开发或实质修改一个独立能力时，在模块 README、测试说明或现有等价事实源中明确：

1. **生产入口**：正式代码从哪里进入；
2. **输入**：参数、Contract、Fixture、文件或数据库前置状态；
3. **输出**：返回值、数据库状态、Artifact、事件、错误等；
4. **测试位置**：哪些测试文件/目录覆盖它；
5. **Fixture / Fake**：使用什么固定样本或可控依赖；
6. **外部依赖**：是否需要 PostgreSQL、文件目录、浏览器或真实外部服务；
7. **运行命令**：最小可重复执行入口；
8. **预期结果**：什么算通过；
9. **已知限制**：哪些场景尚未验证。

若能力没有独立验证价值，不为形式创建空测试目录或文档。

## 4. AIMA 关键能力如何验证

以下是长期测试边界。只有进入对应开发阶段、生产实现真实存在后，才建立相应测试；不要提前为未来能力补造空测试。

### 4.1 Provider Adapter / Operation

目标：确认外部输入边界、请求构造、分页、错误分类和来源元数据正确，同时不让测试逻辑复制 Provider 实现。

推荐组合：

```text
Fake Transport / Stub
→ 正式 Client / Adapter / Operation
→ 固定 Raw Page / Error
```

- Unit：请求参数、分页状态机、停止条件、错误分类、费用逻辑；
- Contract：脱敏 Provider Fixture 的结构和关键语义；
- 真实 Probe：只用于确认真实 Provider 行为，默认关闭，不进入普通 CI；
- 有费用的 Probe 必须显式提醒费用，不写生产库，不打印 Secret。

当前 Stage 5A 可独立验证的生产入口和测试为：

```text
ProviderRequestV1 + ProviderTransportRequest
→ ProviderClient
→ FakeProviderTransport
→ ProviderAttemptV1 + 脱敏 Raw Request/Response
```

```bash
uv run pytest tests/unit/collection tests/contracts/test_provider_v1.py -q
```

覆盖一次发送、成功、429、5xx、发送前失败、发送后结果未知、费用状态和测试 Token 排除序列化。当前没有真实 Provider Operation、分页、真实 Fixture 或 Probe，不能据此宣称外部平台兼容。

### 4.2 Mapper

目标：证明固定 Raw/Fixture 能通过正式 Mapper 产生合法 Canonical。

```text
脱敏 Fixture
→ 正式 Mapper
→ CanonicalContentV1 / CanonicalCommentV1
→ Contract 校验
```

Mapper 测试不得访问数据库或发真实 HTTP。

### 4.3 Raw / Artifact

目标：证明不可变 Raw/Artifact 的写入、完整性和来源关联正确。

Integration 至少按实际能力覆盖：原子写、不可覆盖、路径安全、SHA-256、gzip/文件可读取性、状态推进和失败对账。

Stage 5A 使用正式 `ProviderClient → RawArtifactService → ArtifactService → LocalArtifactStore`，Metadata 使用可控 Fake 隔离尚未建立的 Provider Attempt Repository：

```bash
uv run pytest tests/integration/collection/test_raw_artifact.py -q
```

测试验证递归 Secret 脱敏、稳定层级路径、no-overwrite、SHA-256、大小、gzip、Pydantic 回放和篡改拒绝。Artifact 只推进到 `stored`；数据库引用和 `linked` 状态属于后续 Provider 持久化集成测试。

### 4.4 Collection Run / Scope 父事实

Stage 5B 从正式 `CollectionExecutionService → PostgresCollectionRepository → PostgreSQL` 入口验证
Run/Scope 创建；Repository 不提交事务，提交或回滚由调用方持有：

```bash
uv run pytest tests/unit/collection/test_collection_execution.py -q
uv run alembic upgrade head
uv run pytest tests/integration/collection/test_collection_repository.py -q
uv run alembic check
```

Integration 要求隔离 PostgreSQL 18、对应 `AIMA_*` 配置和
`<AIMA_SECRET_DIR>/postgres_password`。测试覆盖真实 Job FK、每 Job 唯一 Run、Scope 复合唯一、
JSONB/default、读取与 caller rollback；独立 `.github/workflows/stage5b-collection-execution.yml`
同时验证 `base → head`、`20260814_0002 → head` 及两种 downgrade/re-upgrade。SQLite、Mock Row
或内存集合不能代替这些数据库证据。

本阶段只创建 `manual/api/backfill` queued 父事实；不验证 Worker、Run/Scope 状态转换、
Plan/Occurrence/Scheduler、Provider 持久化、预算或真实外部调用。

### 4.5 Ingestion

目标：证明 Canonical 写入 PostgreSQL 后 Current、Version、Metric Observation、来源账本和幂等行为正确。

```text
Canonical Fixture
→ 正式 Ingestion Service
→ Owner Repository
→ 隔离 PostgreSQL
→ 查询并断言业务结果
```

不得为了测试单独写一套“测试入库逻辑”。

### 4.6 Repository / Query / Read Model

目标：证明数据库写入 Owner、查询、排序、分页和聚合语义正确。

- Repository 使用隔离 PostgreSQL；
- Query Repository / Read Model 用固定数据库状态验证读取；
- 不通过 Mock SQLAlchemy Row 冒充真实 SQL、约束或事务已验证；
- 涉及 Migration 的能力同时验证空库和上一正式 Revision 升级门禁。

### 4.7 Job Runtime

目标：证明持久化 Job 的认领、恢复、Lease、Fencing、Deadline、重试、取消和超时状态语义正确。Provider 多级预算属于后续 Provider/Collection 阶段，不由 Stage 4 Job Runtime 测试冒充已验证。

```text
正式 Job Runtime
+ Fake Handler
+ 隔离 PostgreSQL 18
```

当前生产入口和验证边界：

- Registry：`aima_ugc.platform.jobs.JobRegistry`；
- Worker/Reaper：`aima_ugc.platform.jobs.JobWorker` / `JobReaper`，由 `aima_ugc.bootstrap.worker` 组装；
- Repository：`aima_ugc.adapters.persistence.postgres.jobs.PostgresJobRepository`；
- Unit：`tests/unit/jobs/`；
- PostgreSQL Integration：`tests/integration/jobs/`；
- CI：`.github/workflows/stage4-job-runtime.yml`。

最小本地验证需要已经按仓库方式准备的 PostgreSQL 18 和 `<AIMA_SECRET_DIR>/postgres_password`：

```bash
uv run pytest tests/unit/jobs -q
uv run alembic upgrade head
uv run pytest tests/integration/jobs -q
uv run alembic check
```

第二条及后续 Revision 不能只验证空库。Stage 4 专项 CI 同时证明：

```text
base → head
20260813_0001 → head
head → base → head
head → 20260813_0001 → head
```

Fake Handler 只替代具体业务处理，仍通过正式 Registry、Worker、Heartbeat/Fencing 和 PostgreSQL Repository 执行，不复制 Job 状态机。普通 CI 不调用真实付费 Provider。

### 4.8 HTTP API

目标：证明公开 HTTP Contract 与真实 Router/Service 一致。

- 使用真实 Router 和 Service；
- 外部 Provider 等非目标边界使用 Fake；
- 验证状态码、统一错误、ID、时间、Cursor、权限/幂等（进入对应阶段后）；
- 修改公开 API 时同时检查固定 OpenAPI、生成 TypeScript Client 和 [`API接口说明.md`](API接口说明.md)。

### 4.9 Frontend

目标：前端通过生成 Client 的稳定边界验证，不复制后端 Request/Response Contract。

```text
Vue Component / Page
→ Feature Store / Feature API
→ Generated Client Mock
```

Unit 验证组件与状态；关键用户流程用 E2E 验证。前端隐藏按钮不能替代后端权限校验。

### 4.10 Renderer / Report

目标：固定 Report Context 通过正式 Renderer 得到可打开、可校验的产物。测试不复制渲染业务规则。

## 5. Fixture、Fake、Stub、Probe 的区别

### Fixture

固定、可复现输入。适合 Provider 响应、Canonical、数据库种子和报告上下文。

- 必须脱敏；
- 不提交 Secret、Cookie、Token 或未授权个人信息；
- 能稳定复现测试行为。

### Fake / Stub

用于控制不属于当前验证目标的外部依赖。测试仍从生产入口进入，不只验证 Fake 自己。

### 真实 Probe

用于确认真实外部系统、版本、网络或 Provider 行为。它不是普通自动化测试的替代品。

真实 Probe 如果涉及费用、写操作、速率限制或敏感信息：

- 默认关闭；
- 明确运行前提和费用；
- 不进入普通 CI；
- 不写生产数据；
- 不打印 Secret；
- 结果只证明当次真实边界，不替代可重复 Fixture/Fake 测试。

## 6. 模块 README 的测试部分

有持续维护价值的业务模块 README 应至少提供：

```markdown
## 独立调试
说明正式入口、输入和输出。

## 测试入口
列出对应测试目录/文件和最小运行命令。

## 测试数据与可控依赖
说明 Fixture、Fake、Stub 或隔离基础设施。

## 外部依赖
说明 PostgreSQL、文件系统、浏览器或真实 Provider 等要求。

## 预期结果
说明什么算成功，以及需要观察的关键状态。

## 已知限制
说明尚未自动验证或只通过 Probe 验证的内容。
```

不为每个小函数创建 README/TESTING 文档；如果模块 README 已经能完整说明，就不另建平行文档。

## 7. 常用仓库验证命令

后端基础检查：

```bash
uv lock --check
uv run ruff format --check backend tests scripts
uv run ruff check backend tests scripts
uv run mypy backend/src
uv run pytest tests/unit -q
uv run pytest tests/contracts -q
uv run pytest tests/integration -q
uv run pytest tests/api -q
```

Contract：

```bash
uv run python scripts/contracts/generate.py --check
uv run python scripts/contracts/check_compatibility.py
```

架构、安全和文档：

```bash
uv run python scripts/quality/check_architecture.py
uv run python scripts/quality/check_table_ownership.py
uv run python scripts/quality/scan_secrets.py
uv run python scripts/quality/check_docs.py
```

前端：

```bash
npm --prefix frontend run lint
npm --prefix frontend run typecheck
npm --prefix frontend run test -- --run
npm --prefix frontend run build
npm --prefix frontend run test:e2e
```

只执行与当前能力和阶段实际适用的门禁；但不能因为某个检查较慢或失败就删除、跳过或降低既有质量标准。完成结论使用本轮新鲜执行结果和最终 CI。

## 8. 如何判断测试闭环完成

至少确认：

- 目标行为有自动化测试或明确、合理的替代验证；
- 测试从生产入口进入，没有第二套业务实现；
- 与风险匹配的层级已经覆盖，必要的真实基础设施测试没有被 Mock 代替；
- Fixture/Fake/Probe 边界清楚；
- 运行命令和预期结果能被后续维护者理解；
- 失败模式、边界条件和关键错误语义被验证；
- 受影响的模块 README / 本文已经同步；
- 本轮目标测试、相关回归和 CI 有新鲜证据。

测试文件存在本身不代表闭环，README 写了“测试通过”也不代表闭环；以实际行为和执行证据为准。
