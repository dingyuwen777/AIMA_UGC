# 工程基线与研发治理接线

本文只回答一个项目级问题：

> **AIMA_UGC 怎样把通用 Agent_Skills 治理落到本仓库的 Requirement、Change、测试、CI、文档和交付机器接线上？**

通用的分析、TDD、根因调试、Review、测试设计、Git 交付和完成判定方法不在本文复制。进入 AIMA 的统一入口是 [AGENTS.md](../../AGENTS.md)；Agent_Skills 的当前通用规则由该入口指定的治理方式取得。

## 1. 三层职责

~~~text
Agent_Skills
→ 通用“怎么做”：Analysis / Coding / Testing / Review / Docs / Figma / Git / Delivery

AIMA_UGC/AGENTS.md
→ 项目“必须遵守什么”：项目 Overlay、长期规则、授权边界、事实导航

本文件
→ “怎么接到仓库”：Requirement / Change carrier / CI / 文档 / 归档 / Release 的 AIMA 接线
~~~

如果同一条规则已经由 Agent_Skills 负责，本文不再翻写一版 AIMA 规则。只有 AIMA 独有的目录、脚本、Workflow、事实 Owner 和机器接线留在这里。

## 2. 当前事实从哪里恢复

研发前先从目标问题反推最少充分事实。

| 问题 | AIMA 事实 Owner |
| --- | --- |
| 产品当前行为 | [docs/product/](../product/) + 当前前后端实现 |
| 长期架构 | [docs/blueprint/](README.md) |
| 公共 HTTP | [contracts/openapi/openapi.json](../../contracts/openapi/openapi.json) + Pydantic/FastAPI |
| 数据结构 | SQLAlchemy + [migrations/versions/](../../migrations/versions/) |
| Worker 注册 | [backend/src/aima_ugc/bootstrap/worker.py](../../backend/src/aima_ugc/bootstrap/worker.py) |
| 前端 Route / Feature | [frontend/README.md](../../frontend/README.md) + [frontend/src/app/routes.ts](../../frontend/src/app/routes.ts) |
| 测试与调试入口 | [docs/04_测试与调试说明.md](../04_测试与调试说明.md) + 当前测试/Workflow |
| 未完成目标 | [docs/roadmap/](../roadmap/) |
| 历史原因 | [changes/archive/](../../changes/archive/) + Git |

不要从旧 Stage、聊天或某一篇 Markdown 单独推断当前实现。

## 3. Requirement Source 与 Change carrier

AIMA 的 Requirement 可以来自用户明确决定、GitHub Issue、批准的 Roadmap/Spec 或其他正式上游来源。通用的“何时需要持久 Change”判断由当前治理规则负责；一旦需要持久 Change，AIMA 的项目 carrier 固定为：

~~~text
changes/active/<CHANGE_ID>/CHANGE.md
~~~

合并后历史固定进入：

~~~text
changes/archive/YYYY-MM/<CHANGE_ID>/CHANGE.md
~~~

项目校验入口：

- [scripts/quality/check_change_completion.py](../../scripts/quality/check_change_completion.py)

这个脚本只拥有 AIMA carrier、legacy 边界和项目接线；Change schema / Ready 语义不在项目文档复制第二份。

## 4. AIMA 的分支、PR 与 Requirement 关联

需要 PR 交付的实现或文档治理任务，AIMA 使用稳定关联：

~~~text
Requirement Source
→ Change（需要时）
→ task branch
→ Implementation PR
→ current-head CI / Review
→ merge main
→ repository-native Change Archive（存在 Change 时）
→ main-fresh / Closure
~~~

PR 描述用 Requirement-Source 关联正式 Requirement。分支命名、问询边界、Review 方法、修复收敛等通用行为遵守当前 Agent_Skills；本文件不维护另一套规则。

多人实际操作见 [docs/guides/05_多人协作与Change自动归档.md](../guides/05_多人协作与Change自动归档.md)。

## 5. Change Archive 是 AIMA 的项目机器接线

Implementation PR 合并后，如果 PR 携带一个合法 Active Change，AIMA 由仓库原生 Workflow 自动冻结施工记录：

- [.github/workflows/change-archive.yml](../../.github/workflows/change-archive.yml)
- [scripts/quality/archive_change_after_merge.py](../../scripts/quality/archive_change_after_merge.py)

它只允许：

~~~text
changes/active/<ID>/CHANGE.md
→ changes/archive/YYYY-MM/<ID>/CHANGE.md

status: ready_for_review
→ status: done
~~~

归档程序不修改产品、Migration、文档或其他 Change。Change Archive 成功只证明“该施工单元已经进入 main 并被冻结”，不替代 Requirement Acceptance。

## 6. CI：由 changed scope 决定证明责任

AIMA 的 CI 入口：

- [.github/workflows/ci.yml](../../.github/workflows/ci.yml)
- [scripts/quality/classify_ci_scope.py](../../scripts/quality/classify_ci_scope.py)

分类器根据真实 changed paths 选择需要的证据层。文档/治理、后端、前端、Contract、Persistence、Full-stack 等是否需要运行，不由开发者在 Markdown 里手工声明“可以跳过”。

文档-only 变化仍会经过：

- 项目治理接线检查；
- Change readiness（存在 Change 时）；
- Secret/docs gates；
- 文档事实与链接检查。

如果改到文档质量脚本或其测试，CI 会升级到 repository-quality 证明责任。

## 7. 项目文档门禁

AIMA 文档的机器检查：

- [scripts/quality/check_docs.py](../../scripts/quality/check_docs.py)：入口、链接、项目治理边界、仓库文件导航；
- [scripts/quality/check_docs_facts.py](../../scripts/quality/check_docs_facts.py)：少量适合机器同步的权威事实、版本和生命周期；
- [tests/unit/test_docs_navigation.py](../../tests/unit/test_docs_navigation.py)
- [tests/unit/test_docs_facts.py](../../tests/unit/test_docs_facts.py)

设计原则：

~~~text
适合机器直接拥有的精确事实
→ 不要求 Markdown 手抄全集

适合人类理解的稳定语义
→ 文档解释

确实需要小型 exact-set 的项目事实
→ 受控 docs-facts 块 + 机器校验
~~~

例如 OpenAPI 自己拥有完整 Route 集合，API Guide 只需要指向机器入口并解释跨接口语义；永久 Workflow 这种小型、稳定、具备导航价值的集合可以保留 exact-set。

文档 Owner 和生命周期见 [docs/README.md](../README.md) 与 [docs/AGENTS.md](../AGENTS.md)。

## 8. AIMA 的验证入口，而不是第二套测试方法

测试方法由当前 Agent_Skills Testing/Coding 治理。AIMA 只维护“有哪些真实入口、它们证明哪一层”。

统一说明见 [docs/04_测试与调试说明.md](../04_测试与调试说明.md)。当前资产包括：

- 后端 Unit / Contract / API / PostgreSQL Integration；
- 前端 Vitest / Typecheck / Build；
- Browser Mock Acceptance；
- Real Full-stack Golden Path；
- 显式 Real Provider Probe。

具体测试命令、Fixture、数据库准备和排障入口由 [docs/04_测试与调试说明.md](../04_测试与调试说明.md) 与当前 package/workflow 文件维护，不在本文件重复。

## 9. Contract / Schema / Generated Client 的项目接线

AIMA 的公共 HTTP 类型链固定为：

~~~text
Pydantic / FastAPI
→ OpenAPI
→ Orval
→ Frontend Generated Client
~~~

机器事实：

- [contracts/openapi/openapi.json](../../contracts/openapi/openapi.json)
- [frontend/src/generated/api/](../../frontend/src/generated/api/)

前端不得因为设计稿或临时 Mock 手写第二套公共 Request/Response 类型。Contract 变化时按当前 Agent_Skills Coding/Testing/Review 规则执行；AIMA 侧只要求机器生成链和相关 CI 保持一致。

数据库演进同理：当前 Schema 由 SQLAlchemy 与 [migrations/versions/](../../migrations/versions/) 共同证明，文档解释语义，不手抄完整 DDL。

## 10. Figma / Design-to-Code 的项目接线

AIMA 的通用 Figma 工作方法由 Agent_Skills 提供；项目只维护：

- 当前 Figma 文件/页面/Owner 节点；
- Vue Feature / Shared Component 对应关系；
- Generated Client 和真实后端 Contract 边界；
- AIMA 设计验证入口。

项目操作见 [docs/guides/01_Figma与前端设计开发工作流.md](../guides/01_Figma与前端设计开发工作流.md)，页面专项基线见 [docs/guides/02_管理员配置Figma开发基线.md](../guides/02_管理员配置Figma开发基线.md) 与 [docs/guides/07_采集运行中心Figma开发基线.md](../guides/07_采集运行中心Figma开发基线.md)。

## 11. Release / Deploy 不由研发流程自动获得授权

AIMA 的 Release 和 Production 机器事实由：

- [.github/workflows/release.yml](../../.github/workflows/release.yml)
- [Dockerfile](../../Dockerfile)
- [compose.yaml](../../compose.yaml)
- [docs/operations/01_生产部署与离线Release方案.md](../operations/01_生产部署与离线Release方案.md)

共同承担。

完整 Production 尚未完成的 Gate 只看 [docs/roadmap/01_生产上线实施路线.md](../roadmap/01_生产上线实施路线.md)。

开发、PR、merge 授权不自动扩展为 Release、Deploy、生产 Migration 或生产数据操作授权。

## 12. 本文件明确不再维护什么

以下内容若需要，回到 Agent_Skills 或对应 Owner：

- 通用第一性原理分析步骤；
- L1/L2/L3 的通用判定方法；
- 通用 TDD / Debug / Review 流程；
- 通用 Ask/No-Ask 决策；
- 通用 Git / PR / merge 方法；
- 通用测试策略；
