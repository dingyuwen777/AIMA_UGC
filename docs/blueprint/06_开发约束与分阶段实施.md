# 工程基线与研发治理接线

本文只回答一个项目级问题：

> **AIMA_UGC 怎样把通用 Agent_Skills 治理落到本仓库的 Requirement、Change、测试、CI、文档和交付机器接线上？**

通用的分析、TDD、根因调试、Review、测试设计、Git 交付和完成判定方法不在本文复制。进入 AIMA 的统一入口是 [AGENTS.md](../../AGENTS.md)；Agent_Skills 的当前通用规则由该入口指定的治理方式取得。

## 1. 三层职责

~~~text
Agent_Skills
→ 通用“怎么做”：Analysis / Coding / Testing / Review / Docs / Figma / Git / Delivery

AIMA_UGC/AGENTS.md
→ 项目“必须遵守什么”：项目 Overlay、长期规则、授权边界、事实导航

本文件
→ “怎么接到仓库”：Requirement / Change carrier / CI / 文档 / 归档 / Release 的 AIMA 接线
~~~

如果同一条规则已经由 Agent_Skills 负责，本文不再翻写一版 AIMA 规则。只有 AIMA 独有的目录、脚本、Workflow、事实 Owner 和机器接线留在这里。

## 3. Requirement Source 与 Change carrier

AIMA 的 Requirement 可以来自用户明确决定、GitHub Issue、批准的 Roadmap/Spec 或其他正式上游来源。通用的“何时需要持久 Change”判断由当前治理规则负责；一旦需要持久 Change，AIMA 的项目 carrier 固定为：

~~~text
changes/active/<CHANGE_ID>/CHANGE.md
~~~

合并后历史固定进入：

~~~text
changes/archive/YYYY-MM/<CHANGE_ID>/CHANGE.md
~~~

项目校验入口：

- [scripts/quality/check_change_completion.py](../../scripts/quality/check_change_completion.py)

这个脚本只拥有 AIMA carrier、legacy 边界和项目接线；Change schema / Ready 语义不在项目文档复制第二份。

## 4. AIMA 的分支、PR 与 Requirement 关联

需要 PR 交付的实现或文档治理任务，AIMA 使用稳定关联：

~~~text
Requirement Source
→ Change（需要时）
→ task branch
→ 本地实现、必要技术验证与 Review
→ 用户本地验收（适用时）
→ Implementation PR
→ current-head CI / Review
→ merge main
→ repository-native Change Archive（存在 Change 时）
→ main-fresh / Closure
~~~

PR 描述用 Requirement-Source 关联正式 Requirement。分支命名、问询边界、Review 方法、修复收敛等通用行为遵守当前 Agent_Skills；本文件不维护另一套规则。

多人实际操作见 [docs/guides/05_多人协作与Change自动归档.md](../guides/05_多人协作与Change自动归档.md)。

## 5. Change Archive 是 AIMA 的项目机器接线

Implementation PR 合并后，如果 PR 携带一个合法 Active Change，AIMA 由仓库原生 Workflow 自动冻结施工记录：

- [.github/workflows/change-archive.yml](../../.github/workflows/change-archive.yml)
- [scripts/quality/archive_change_after_merge.py](../../scripts/quality/archive_change_after_merge.py)

它只允许：

~~~text
changes/active/<ID>/CHANGE.md
→ changes/archive/YYYY-MM/<ID>/CHANGE.md

status: ready_for_review
→ status: done
~~~

归档程序不修改产品、Migration、文档或其他 Change。Change Archive 成功只证明“该施工单元已经进入 main 并被冻结”，不替代 Requirement Acceptance。

## 6. CI：由 changed scope 与新鲜 Evidence 决定证明责任

AIMA 的 CI 入口：

- [.github/workflows/ci.yml](../../.github/workflows/ci.yml)
- [scripts/quality/classify_ci_scope.py](../../scripts/quality/classify_ci_scope.py)
- [scripts/quality/resolve_main_evidence.py](../../scripts/quality/resolve_main_evidence.py)

PR 是产品 Evidence 的主要生成点。分类器根据真实 changed paths 选择需要的证据层，不由开发者在 Markdown 里手工声明“可以跳过”。PostgreSQL 优先使用能直接证明叶子风险的精确 test target；共享领域变化再运行 domain suite；只有共享数据库基础设施、Migration/CI harness 或无法安全分类的真实横切边界才退回 `all`。Real Full-stack 同样按已知用户 Journey 选择 spec，不因为普通“前端 + 后端”组合本身就机械升级为全部真实浏览器链路。

Final CI 使用单一 [`scripts/quality/classify_ci_scope.py`](../../scripts/quality/classify_ci_scope.py) 计算证明责任。PR 以唯一 merge-base 到 HEAD 的变更选择测试，checkout 继续使用 GitHub 的合并结果验证最终组合；缺失对象、无共同基线或多个 merge-base 均明确失败。push 使用 before 到当前 SHA 的直接比较，定时安全网显式使用 full。

轻量 `CI Plan` 负责 changed-scope、main Evidence reuse 与 selector 输出；随后 `CI Preflight` 检查 Requirement Source、Change Ready、文档、Secret 和适用的配置模板。只有 Preflight 成功后，`Requirement Traceability and Completion Audit`、`PostgreSQL Integration`、`Real Full-stack Golden Path` 才并行执行昂贵测试，最后由稳定的 `CI Gate` 聚合。Plan 或 Preflight 失败时 Core 与总 Gate 都必须明确失败，不能让 required context 因 dependency skip 被误判为通过。

Backend/Frontend 与 PostgreSQL/Full-stack 使用同一原则：明确 Owner/Feature 的局部变化优先选择直接 unit / Browser Mock target；共享入口、Contract、CI selector 自身或无法安全映射的未知路径回退 `all`。每日全量 CI 继续作为 selector 漏判的低频安全网。

分类完成后，CI 与本地入口在实际 checkout/worktree 中统一检查目标可用性；删除和改名仍保留 changed paths 与原证明责任。不存在的精确测试升级到现存 Owner suite，无法确定时保守使用对应层的 all；不允许过滤后清空测试。根 [USAGE.md](../../USAGE.md) 是明确受控的文档入口，与 README 一起进入文档检查及 docs-only 分类，未知根 Markdown 不自动豁免。

开发期使用 `python scripts/dev/validate_changed.py --base origin/main` 读取同一 classifier；`--fix` 只收敛 changed Python formatter 与 Contract/generated owner，`--execute` 运行当前可在本地稳定证明的 targeted layers。真实 PostgreSQL 与 Real Full-stack 默认明确留给正式 CI，不用 Fake 冒充。

Draft 期间普通 commit/push 不触发重 CI，也不因无关 main/Change Archive 前进机械追 base；真实依赖冲突可提前同步，最终 Ready 前统一同步最新 main 并重跑受影响 preflight/Review。临时 Workflow/debug/formatter/generated/取 Red 过程态默认留在 working tree 或受控临时环境，不形成正式 commit；commit 应对应可独立理解的 checkpoint。正常 merge 重新核当前 head/base/required checks，不使用 bypass 替代门禁。

PR metadata `edited` 与 Final full CI 使用独立 concurrency lane；metadata 校验必须等待同 HEAD、同 base 的 full `CI Gate` 与 `Compose Golden Path` 真正绿色后才能通过，因此编辑 PR 描述不会取消正在执行的 Final CI，也不能用 metadata-only 结果冒充完整 Evidence。base retarget 的 `edited` 走正常验证，不能复用旧 base 的结果。

PR 的 `opened`、`reopened`、`synchronize`、`ready_for_review` 都提供当前 HEAD 的自动验证入口。实现与 Repair 阶段优先保持 Draft；Draft 不运行完整产品、数据库、Runtime 或发布验证，但 **required contexts 不能用 job-level skipped 作为门禁结果**：`Requirement Traceability and Completion Audit`、`CI Gate`、`Compose Golden Path` 只执行最前置的轻量 fail-closed guard 并明确失败，Tooling/Release 等非 required 重任务仍可直接跳过。普通非 Draft PR 修复后 push 自动重新选择并验证当前 HEAD；同 PR 的旧 full 运行由 cancel-in-progress 取消。base 分支前进本身不等于 PR 新提交，strict required-status 继续要求最新组合；最终交付前同步 base 并验证，不能借旧 HEAD/base 或 merge 后 main CI 通过预合并门禁。

配置模板由 [`scripts/quality/check_env_templates.py`](../../scripts/quality/check_env_templates.py) 检查；它只读取受控的两份模板，不读取用户 Secret。注释变化检查语法、重复键、Compose 插值与文档/Secret；值或结构变化增加真实 PlatformSettings、飞书身份配置、Release 模板保留和 Compose config。部署/镜像/路径等配置变化继续承担 Runtime / Release / Windows Compose 的独立证明责任。未知或不能解析的风险保守升级，不能按 `.example` 后缀豁免。历史模板重复键按原来最后生效值恢复比较，目标模板必须消除重复。

风险比较保留值声明中的引号、转义和插值结构。单引号会改变 Compose 插值语义，即使去掉外引号后的字符串相同，也不能归为注释变化；无法证明消费者等价时升级为配置验证。真正只修改注释且声明未变时继续走静态路径。

### Workflow 责任与保留映射

各 Workflow 直接消费同一 classifier，不能各自维护路径风险清单；修改 classifier、Workflow、Migration 或共享基础设施仍触发 full。缩减仅针对已经由轻量配置证据充分覆盖的输入，不删正式场景。

| 原有证明责任 / 消费者 | 当前承载位置 | 保留的独立证据与成本边界 |
| --- | --- | --- |
| Requirement、Change、文档与 Secret | CI Preflight | 提前失败，阻止后续数据库、产品和浏览器环境初始化；三个 required check identity 保持不变 |
| 模板语法、配置解析、飞书多企业边界 | 模板 validator + 配置定向 unit | 重复键、未知键、生产解析失败必须失败；不需要启动 PostgreSQL 或 Browser |
| production 模板打包与非目标配置保留 | validator 调用正式 Release 重写函数 + Release bundle unit | 模板值变化证明原值保留；镜像、Manifest、离线回放风险仍进入 Release dry-run |
| Compose 启动、安全、持久化和恢复 | Compose Golden Path | Docker/Compose、运行入口、部署路径变化保留真实启动与恢复；[frontend/nginx.conf](../../frontend/nginx.conf) 由 Dockerfile COPY 进入镜像，保留真实容器启动和 Release 离线镜像验证；普通身份模板变化用生产解析和 config 渲染 |
| Linux 开发脚本与最小环境 | Linux Local Development Tooling | 工具链、脚本和运行相关变化保留真实安装/运行；Provider system Repository 变化仍运行源码 Launcher bootstrap，验证 TikHub Local Dev 与 Secret 引用；该 Job 的最小 env 不消费身份模板值，Windows 不承担这项数据库 bootstrap 证明 |
| Windows 本地 env 和 Compose overlay | Windows Development and Compose Tooling | env.local 的非注释变化继续运行真实 Windows Job，覆盖本地 Launcher、PowerShell bootstrap、模板读取与 Compose config；不升级为 PostgreSQL suite 或全部 Browser |
| Backend、Frontend、PostgreSQL、真实用户链路 | CI Core / PostgreSQL Integration / Real Full-stack Golden Path | Preflight 后并行，沿用精确 target / domain suite / all；保留每日 CI、每周 Runtime/Tooling 安全网，不改数据库隔离体系 |
| merge 后相同 tree 的已有验证 | resolve_main_evidence.py | 仍要求唯一 merged PR、相同 tree、来源成功 check；查询失败回真实验证 |

Tooling 的纯 metadata 编辑使用独立 metadata check identity，避免跳过的 Job 置换同 HEAD 的正式成功结果。正式 identity 的最新 skipped/失败仍禁止 main evidence reuse，不允许无条件忽略 skipped 或寻找任意旧绿色。

所有重任务的准备、安装和构建只在它确实承担独立风险时执行。本次不引入跨 Workflow 可变环境共享，也不并行复用数据库；正式发布仍执行锁定镜像构建、离线 Bundle 与 no-build/no-pull 回放。

Runtime、Tooling、Release 在各自昂贵阶段前也检查 PR Requirement Source / Change Ready，正式 Release 不执行 PR 门禁。各 Workflow 为保持独立失败隔离，目前仍可能重复一次锁定 Python setup / uv sync 和模板配置验证；这些成本没有被宣称去重。当前收益来自正确范围、Preflight 失败停止重任务，以及模板风险与真实运行风险分离。控制面变更自身必须 full，不能拿它和模板 PR 的耗时直接比较；可比的 Runner 数据应在同一新 main 上用受控模板/文档 PR 采样，完成后清理，不能改变正式 HEAD 的 required 责任。

merge 到 `main` 后，commit SHA 变化本身不等于代码内容变化。main push 会先用 [scripts/quality/resolve_main_evidence.py](../../scripts/quality/resolve_main_evidence.py) 核对：

~~~text
当前 main commit
→ 唯一关联的 merged PR
→ 当前 tree SHA == PR 最终 HEAD tree SHA
→ 来源 PR 对应 required check 的最新结果为 success
~~~

只有全部事实都能确认时才复用来源 PR Evidence；PR 无法唯一解析、tree 不同、check 缺失/失败或 GitHub API 暂时不可确认时，复用结果为 false，workflow 自动回到原 changed-scope / Runtime / Tooling 验证。CI Evidence 优化因此不能把外部查询失败转换成“跳过测试”。

文档-only 变化仍会经过与其责任相称的治理/文档检查；修改文档质量脚本或其测试会升级到 repository-quality 证明责任。前端依赖审计只在依赖清单/锁或等价工具链输入变化时执行；Wheel 安装验证只在 Python package/build 输入变化时执行。Reporting 字体仍是完整 Backend Unit suite 的真实先决条件，在没有更细 Backend test-impact 证据前不为了省时移除。

为了发现 impact mapping 的潜在遗漏，交互式 PR 使用精准 Evidence，同时保留低频全量安全网：CI 每日运行 full profile，Runtime 与 Developer Tooling 每周运行完整验证。精确 cron、Job/check 名称与当前映射仍以实际 workflow/classifier 为机器事实。

## 7. 项目文档门禁

AIMA 文档的机器检查：

- [scripts/quality/check_docs.py](../../scripts/quality/check_docs.py)：入口、链接、项目治理边界、仓库文件导航；
- [scripts/quality/check_docs_facts.py](../../scripts/quality/check_docs_facts.py)：少量适合机器同步的权威事实、版本和生命周期；
- [tests/unit/test_docs_navigation.py](../../tests/unit/test_docs_navigation.py)
- [tests/unit/test_docs_facts.py](../../tests/unit/test_docs_facts.py)

设计原则：

~~~text
适合机器直接拥有的精确事实
→ 不要求 Markdown 手抄全集

适合人类理解的稳定语义
→ 文档解释

确实需要小型 exact-set 的项目事实
→ 受控 docs-facts 块 + 机器校验
~~~

例如 OpenAPI 自己拥有完整 Route 集合，API Guide 只需要指向机器入口并解释跨接口语义；永久 Workflow 这种小型、稳定、具备导航价值的集合可以保留 exact-set。

文档 Owner 和生命周期见 [docs/README.md](../README.md) 与 [docs/AGENTS.md](../AGENTS.md)。

## 9. Contract / Schema / Generated Client 的项目接线

AIMA 的公共 HTTP 类型链固定为：

~~~text
Pydantic / FastAPI
→ OpenAPI
→ Orval
→ Frontend Generated Client
~~~

机器事实：

- [contracts/openapi/openapi.json](../../contracts/openapi/openapi.json)

前端不得因为设计稿或临时 Mock 手写第二套公共 Request/Response 类型。Contract 变化时按当前 Agent_Skills Coding/Testing/Review 规则执行；AIMA 侧只要求机器生成链和相关 CI 保持一致。

数据库演进同理：当前 Schema 由 SQLAlchemy 与 [migrations/versions/](../../migrations/versions/) 共同证明，文档解释语义，不手抄完整 DDL。
