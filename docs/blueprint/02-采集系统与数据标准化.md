# 采集系统与数据标准化

## 1. 目标

采集系统必须回答：

```text
为什么发起这次采集？
用了哪些平台和关键词？
每个平台实际请求了哪些接口和分页参数？
TikHub 原始返回是什么？
哪些内容被识别、去重和更新？
哪条业务数据来自哪个原始请求？
失败后从哪里恢复？
本次调用花费多少？
```

如果这些问题只能靠猜日志或查看一大段业务代码，设计就是不合格的。

## 2. 采集策略

业务日、默认调度和日志显示时区固定为 `Asia/Shanghai`。第一版 `collection_plans.timezone` 也只能取该值；字段保留 IANA 时区名称，是为以后通过独立决策、迁移和 DST 测试开放其他调度时区，不表示当前可以任意配置。

### 2.1 主调度

```text
00:00 关键词滚动发现
06:00 关键词滚动发现
12:00 关键词滚动发现
18:00 关键词滚动发现
每天一次 最近 7 天回补
每周一次 可选深度回补
```

滚动发现使用各平台支持的“最新发布”和最小时间范围。时间范围重叠是有意设计，用来补偿平台排序波动、延迟出现和某次请求失败。

### 2.2 发现来源

| 来源 | 作用 | 默认频率 |
| --- | --- | --- |
| 关键词搜索 | 主发现通道 | 每 6 小时 |
| 已知话题 | 补充固定话题内容 | 每 6 小时或每日 |
| 已跟踪账号 | 品牌、竞品、KOL | 每 6 小时 |
| 热榜 | 发现突发事件和新词 | 每 6 小时，全局一次 |
| 搜索建议 | 扩展别名和相关词 | 每日 |
| 文件导入 | 补录历史或其他来源 | 人工 |

不同来源都只能产生 Candidate，不能绕过统一摄取直接写内容表。

## 3. 采集的六层记录

### 3.1 Plan：长期计划

保存：

- 名称；
- 是否启用；
- 调度；
- 目标平台；
- 选择的词包；
- 详情和评论策略；
- 预算；
- 创建人和更新时间。

Plan 不保存某次执行时的最终关键词列表。

### 3.2 Run：一次执行

Run 是某次人工或定时触发的完整执行记录。创建 Run 时必须冻结配置：

```json
{
  "schema_version": "collection-run-config.v1",
  "plan_id": "plan_01",
  "trigger": "scheduler",
  "timezone": "Asia/Shanghai",
  "platform_keywords": {
    "xhs": ["爱玛", "爱玛电动车"],
    "dy": ["爱玛", "爱玛电动车"]
  },
  "date_from": "2026-08-11T18:00:00+08:00",
  "date_to": "2026-08-12T18:00:00+08:00",
  "comment_policy": "high_priority_only",
  "request_budget": 300
}
```

词包后续修改不能改变已经创建的 Run。

### 3.3 Scope：最小独立执行单元

Scope 示例：

```text
xhs + keyword_search + 爱玛
dy  + keyword_search + 爱玛电动车
xhs + tracked_account + user_123
xhs + comments + note_456
```

每个 Scope 有独立状态、分页进度、统计和错误。一个 Scope 失败不能让其他平台和关键词全部丢失。

### 3.4 Provider Request：一个可幂等的逻辑请求

Provider Request 表示“这个 Scope 的这一页或这一组明确参数需要完成一次外部操作”。它由 Operation、脱敏后的稳定参数和分页状态计算 `request_fingerprint`，同一逻辑请求在任务重试后仍使用同一条记录。

保存：

- `request_id`；
- `run_id`；
- `scope_id`；
- Provider；
- 平台；
- Operation；
- 脱敏请求参数；
- 分页输入；
- 逻辑状态；
- 尝试次数；
- 累计费用；
- 创建和完成时间。

Provider Request 不是一条真实网络调用记录，因此不会因为重试而覆盖 HTTP 状态、TikHub request ID 或 Raw。

### 3.5 Provider Request Attempt：一次真实 HTTP 调用

每一次真实 TikHub HTTP 调用都生成独立 Attempt：

- `attempt_id`；
- 所属 `request_id`；
- 尝试序号；
- 开始/结束时间；
- HTTP 状态；
- TikHub request ID；
- 计费币种、计费单位、单价快照、预计/实际费用；
- `billing_status` 和是否可能重复计费；
- 本次 Raw Artifact ID；
- 错误分类和安全摘要。

同一逻辑请求可能有多个 Attempt。所有 Attempt 都保留，逻辑请求汇总最终状态和累计费用。这样可以准确回答重试了几次、每次返回什么、实际付费多少，也不会为了幂等而抹掉失败证据。

### 3.6 Candidate：一次发现

Candidate 表示某条来源项在某次 Attempt 的某个 Raw 中被看到。它不是最终内容副本，也不能只用 `content_discoveries` 的首末 Run 聚合替代。

```text
Candidate
→ 提取平台身份
→ 去重
→ 必要时详情补全
→ Mapper
→ Canonical
→ Ingestion
```

每个 Candidate 只直接保存实际 Provider Request Attempt、`item_kind`（content/comment）、`external_item_id`、稳定 `item_locator` 和发现时间；Run、Scope、Raw Artifact、平台及来源类型/值必须通过唯一受约束链 `Candidate → Attempt → Provider Request → Scope → Run` 和 `Attempt.raw_artifact_id` 推导，禁止复制这些列后仅靠应用保证一致。创建 Candidate 前，Deferred Constraint Trigger 验证 Attempt 已完成且有完整性已校验的 Raw。每次 Mapper/Ingestion 结果追加独立记录，保存 Canonical 版本/身份、`target_type`，以及互斥的 `content_id` 或 `comment_id` 外键、结果或安全错误；Trigger 还验证非空 `target_type` 与 Candidate 的 `item_kind` 相同，并验证目标 Content（或 Comment 所属 Content）平台与 Scope 平台一致。由此才能回答“哪个 Raw 中哪一项在何次执行产生或再次发现了这条内容/评论”，且数据库不能拼接互相矛盾的来源链。

## 4. 关键词和词包

关键词必须以单个词为最小单位保存在数据库，不使用运行时文件驱动采集。

```text
keyword_packs
keywords
keyword_pack_items
collection_plan_keyword_packs
```

规则：

1. 同一个规范化关键词只保存一份；
2. 词包和关键词使用关联表，不保存逗号分隔字符串；
3. 关键词可以设置平台、启用状态、优先级和备注；
4. 保存 Plan 时校验所有目标平台至少有一个可用关键词；
5. 创建 Run 时把最终关键词按平台展开并冻结；
6. Worker 只消费 Run Snapshot，不读取词包猜测默认词；
7. 文件只用于批量导入、导出或初始化 Seed。

## 5. TikHub Adapter

目标目录：

```text
adapters/providers/tikhub/
├─ client.py
├─ config.py
├─ errors.py
├─ models.py
├─ pricing.py
├─ operations/
│  ├─ xiaohongshu.py
│  ├─ douyin.py
│  ├─ kuaishou.py
│  ├─ weibo.py
│  └─ bilibili.py
└─ mappers/
   ├─ xiaohongshu.py
   ├─ douyin.py
   ├─ kuaishou.py
   ├─ weibo.py
   └─ bilibili.py
```

### 5.1 Client 只负责通用 HTTP

`client.py` 负责：

- URL 和认证；
- 超时；
- 连接池；
- 限流；
- 可重试错误；
- TikHub 公共响应包；
- request ID；
- 计费元数据；
- 日志上下文；
- Raw Request/Response Envelope。

Client 不知道小红书的 `cursor`，也不解析内容字段。

### 5.2 Operation 负责平台调用规则

Operation 负责：

- endpoint；
- 请求参数；
- 分页状态；
- 详情和评论调用组合；
- 平台停止条件；
- 返回 Raw Page。

例如小红书关键词搜索使用 `search_notes`，分页需要页码和搜索会话字段；评论需要保存 `cursor/index/pageArea`。抖音视频搜索使用 `cursor/search_id`，部分接口还需要 `backtrace`。B站当前分类搜索使用返回的下一页 cursor。

业务 Service 不能直接拼 endpoint 或解析 cursor。

### 5.3 Mapper 只负责翻译事实

Mapper 输入：

```text
Raw Page / Raw Item
+ SourceObservation
+ 明确的采集上下文
```

Mapper 输出：

```text
CanonicalContentV1
CanonicalCommentV1
MetricObservationV1
```

Mapper 禁止：

- 读数据库；
- 发 HTTP；
- 写文件；
- 计算告警；
- 调用模型；
- 猜测无法确认的发布时间、作者、父评论或业务分类。

## 6. Raw 原始证据

### 6.1 保存原则

每个成功返回并完成校验的 Provider Request Attempt 必须保存一个不可变 gzip JSON 文件。失败响应如果包含可安全保存的响应体，也保存错误 Envelope。

文件路径：

```text
/data/AIMA_UGC/runtime/data/raw/
  tikhub/
    xhs/
      2026/08/12/
        <run_id>/
          <scope_id>/
            <attempt_id>.json.gz
```

不使用固定 `latest.json.gz` 覆盖历史。需要“最新”时由数据库查询 Provider Request 或生成可重建索引。

### 6.2 Raw Envelope

```json
{
  "schema_version": "provider-response.v1",
  "provider": "tikhub",
  "platform": "xhs",
  "operation": "search_notes",
  "request_id": "req_01",
  "attempt_id": "attempt_01",
  "run_id": "run_01",
  "scope_id": "scope_01",
  "requested_at": "2026-08-12T10:00:01Z",
  "completed_at": "2026-08-12T10:00:02Z",
  "request": {
    "method": "GET",
    "path": "/api/v1/xiaohongshu/app_v2/search_notes",
    "params": {
      "keyword": "爱玛",
      "page": 1,
      "sort_type": "time_descending",
      "time_filter": "一天内"
    }
  },
  "response": {
    "status_code": 200,
    "external_request_id": "tikhub_request_id",
    "body": {}
  }
}
```

写入步骤：

```text
递归脱敏
→ JSON 序列化校验
→ ArtifactService 创建 pending 元数据并分配 storage_key
→ 写临时文件
→ flush + fsync
→ gzip 可读取校验
→ 计算 SHA-256
→ 原子 rename
→ ArtifactService/Repository 把元数据更新为 stored
→ Attempt 与业务短事务关联 Artifact，并更新为 linked
```

`ArtifactStore` 只完成按 `storage_key` 的字节写入和原子 rename，不写数据库状态；`ArtifactService` 和 Repository 才能推进 `pending/stored/linked`。任一步失败都保留可对账状态，由维护任务识别长期 pending、元数据缺文件和磁盘孤儿文件，不以删除证据作为失败恢复手段。

禁止在 Raw 中保存 Authorization、Cookie、API Key、数据库密码、模型密钥和内部会话 Token。

## 7. 分页状态机

每个平台 Operation 必须把分页写成可测试状态机：

```text
初始状态
→ 构造请求
→ 保存 Raw
→ 提取结果和下一页状态
→ 去重
→ 判断停止
→ 下一页
```

统一停止条件：

- Provider 明确无下一页；
- 当前页为空；
- 下一 cursor/page 没有推进；
- 页面内容完全重复；
- 已连续越过时间边界；
- 达到本次显式预算；
- 任务被取消；
- 技术安全页数上限。

“安全页数上限”只防止异常无限循环，不能当业务数据上限。触发时 Run 必须标记为 `partial_success`，并记录 `page_limit`，不能假装完整。

## 8. Canonical 数据契约

Canonical 只表达跨平台、下游真正需要的稳定业务含义。

### 8.1 Content

```json
{
  "schema_version": "content.v1",
  "platform": "xhs",
  "external_content_id": "note_123",
  "content_type": "image_note",
  "canonical_url": "https://www.xiaohongshu.com/explore/note_123",
  "author": {
    "external_author_id": "user_1",
    "name": "示例用户"
  },
  "title": "示例标题",
  "text": "示例正文",
  "published_at": "2026-08-12T08:30:00+08:00",
  "observed_at": "2026-08-12T10:00:02Z",
  "metrics": {
    "like_count": 100,
    "comment_count": 20,
    "share_count": 3,
    "collect_count": 15,
    "play_count": null
  },
  "source": {
    "provider": "tikhub",

    "raw_artifact_id": "artifact_01",
    "source_type": "keyword_search",
    "source_value": "爱玛"
  }
}
```

### 8.2 Comment

```json
{
  "schema_version": "comment.v1",
  "platform": "xhs",
  "external_content_id": "note_123",
  "external_comment_id": "comment_100",
  "root_comment_id": "comment_100",
  "parent_comment_id": null,
  "author": {
    "external_author_id": "user_2",
    "name_hash": "sha256-prefix"
  },
  "text": "示例评论",
  "published_at": "2026-08-12T09:20:00+08:00",
  "observed_at": "2026-08-12T10:05:00Z",
  "like_count": 8,
  "source": {
    "provider": "tikhub",
    "provider_request_id": "req_02",
    "provider_attempt_id": "attempt_02",
    "raw_artifact_id": "artifact_02"
  }
}
```

### 8.3 身份规则

```text
内容：(platform, external_content_id)
评论：(platform, external_content_id, external_comment_id)
```

评论身份包含内容 ID，更稳妥地避免不同帖子下评论 ID 空间重叠。

评论关系：

- `root_comment_id`：所属一级评论线程；
- `parent_comment_id`：直接回复对象；
- 无法确认时为 `null`；
- 不根据数组位置或展示层级猜测父评论；
- 子评论接口明确带根评论 ID 时可以用调用上下文补充 root。

### 8.4 时间规则

- API/Canonical 使用 ISO-8601；
- 数据库存 `timestamptz`；
- 无时区时间只有在 Provider 语义明确且已绑定平台时区时才能转换；
- 无法可靠解析时保存 `null` 和原始时间到 Raw；
- 禁止把采集时间冒充发布时间；
- 小红书 ID 推算时间只能作为低置信度候选，不覆盖明确字段，并必须标记推算来源。

## 9. 摄取算法

```text
1. Raw 已成功落盘
2. Mapper 输出 Canonical
3. Pydantic + JSON Schema 校验
4. 开启数据库事务
5. 按平台身份锁定或 Upsert 当前内容
6. 业务字段变化时新增 content_version
7. 指标变化或到达每日检查点时新增 metric_observation
8. 更新 current 表的最新值、first_seen_at、last_seen_at
9. 写入 Candidate Ingestion 结果并更新发现来源聚合
10. 评论按同样规则 Upsert
11. 如需后续分析/监控，在同一事务插入内部幂等 Job
12. 更新 Scope/Run 统计并提交事务
```

数据库写失败时 Raw 已存在，Job 可以重试 Mapper 和 Ingestion，且在 Raw 完整性校验通过时不得再次调用 Provider。若此前网络结果未知且没有可用 Raw，是否重试必须按费用策略决定，系统要记录潜在重复计费，不能承诺外部 Provider 一定未收费。

## 10. 当前值和历史

不把全部历史塞进一个 JSON。

```text
contents
→ 当前稳定字段

content_versions
→ 标题、正文、作者、URL、状态等变化

content_metric_observations
→ 点赞、评论、分享、收藏、播放等时间序列

comments
→ 当前评论

comment_versions
→ 评论文本、关系或状态变化

comment_metric_observations
→ 评论点赞等变化
```

指标历史默认规则：

- 首次发现一定记录；
- 数值变化时记录；
- 即使无变化，每个 `Asia/Shanghai` 业务日最多记录一个检查点，并由数据库部分唯一约束兜底；
- 同一 Request 重试不得产生重复 Observation；
- 使用唯一键保证幂等。

## 11. 详情和评论刷新

### 11.1 内容详情

搜索卡片只负责发现。以下情况获取详情：

- 首次发现；
- 搜索卡片缺少关键字段；
- 互动指标变化；
- 高风险或高热内容；
- 到达计划刷新节点。

### 11.2 默认刷新层级

| 层级 | 刷新 |
| --- | --- |
| 高热/高风险 | 首次、6h、12h、24h，之后每日到第 7 天 |
| 普通 | 首次、24h、72h、第 7 天 |
| 低优先级 | 首次详情；后续由指标变化触发 |
| 超过 30 天 | 默认不主动刷新，除非进入事件或人工关注 |

评论只对高价值内容增量抓取。单内容评论预算和单 Run 评论预算分别控制，某个热门内容不能耗尽全部平台预算。

## 12. 成本控制

每次 Provider Request Attempt 必须记录本次调用事实，逻辑 Provider Request 汇总全部 Attempt：

- Operation；
- 请求次数；
- 单价快照；
- 预计费用；
- 实际费用；
- 缓存命中；
- 是否重试；
- 是否由补回任务触发。

Run、单内容评论和全局费用/请求预算必须由数据库原子预留并在 Attempt 完成后结算；禁止多个 Worker 使用“先读剩余额度、后各自调用”的竞态流程。每次准备发起真实 HTTP 调用都先创建新的 Attempt，并为该 Attempt 取得 global + run 预留；只有评论 Operation 再强制取得目标 content_comments 预留。任何应有账户缺失或调用时刻没有覆盖周期都必须关闭失败，不能当作没有预算限制。网络重试是新的真实调用，因此必须创建新的 Attempt 和预留。只有同一 Attempt 的预留事务重放使用唯一键复用原预留；Dispatcher 验证所属 Job Fencing 后 CAS 进入 `dispatching`，Transport 必须关闭单次调用内隐藏的自动网络重试，该 Attempt 最多执行一次 Provider Client 调用，崩溃后不能用同一 Attempt 再次发送。`dispatching` 未得到已校验 Raw/确定响应时按计费未知处理并保留额度；新的网络发送使用新 Attempt。只有能证明请求从未进入发送边界的 `reserved` Attempt 才能标记 `not_sent` 并释放。网络结果未知时预留额度保持占用，待人工/对账策略确认后再释放或记为实际费用。

优化顺序：

1. 同一 Run 内跨词去重；
2. 热榜全局请求一次；
3. 搜索卡片先判断，避免所有内容都抓详情；
4. 只对高价值内容抓评论；
5. 通过完整性校验的 Raw 存在时只做回放；
6. 分页以数据和时间边界停止，不用固定页数制造大量无效请求。

## 13. 独立调试和测试

### 13.1 Provider Operation

输入：

```text
TikHubConfig + platform + operation + explicit parameters
```

输出：

```text
Raw Page + Pagination State + Request Metadata
```

验证方式：

- Fake HTTP Fixture；
- 脱敏真实响应 Fixture；

## 15. 验收标准

采集模块完成必须证明：

- 五平台每个平台至少一个脱敏 Fixture；
- 每个平台分页第一页、下一页、末页、重复页、cursor 不推进测试；
- Raw 文件不可覆盖、可解压、SHA-256 正确；
- Secret 脱敏测试；
- Canonical Schema 测试；
- 同一内容跨词去重；
- 内容字段变化和指标变化历史正确；
- 评论 root/parent 关系不被猜测；
- 同一逻辑 Provider Request 的多个 Attempt 都保留各自状态、Raw 和费用；
- 已校验 Raw 的取消/重试只做回放；网络结果未知时按策略重试并记录潜在重复计费；
- 每个 Candidate 可追溯到 Run、Scope、Attempt、Raw 和来源项；
- Run、评论和全局预算的并发预留/结算有真实 PostgreSQL 集成测试；
- Provider Probe 复用生产实现；
- 费用和 Run 统计可查询。
