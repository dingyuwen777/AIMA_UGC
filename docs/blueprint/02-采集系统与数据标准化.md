# 采集系统与数据标准化

## 1. 目标

采集系统必须回答：

```text
为什么发起这次采集？
用了哪些平台和关键词？
每个平台实际请求了哪些接口和分页参数？
实际 Provider 原始返回/输入是什么？
哪些内容被识别、去重和更新？
哪条业务数据来自哪个原始请求？
失败后从哪里恢复？
本次调用花费多少？
```

如果这些问题只能靠猜日志或查看一大段业务代码，设计就是不合格的。

## 2. 采集策略

业务日、默认调度和日志显示时区固定为 `Asia/Shanghai`。第一版 `collection_plans.timezone` 也只能取该值；字段保留 IANA 时区名称，是为以后通过独立决策、迁移和 DST 测试开放其他调度时区，不表示当前可以任意配置。

### 2.1 主调度

```text
00:00 关键词滚动发现
06:00 关键词滚动发现
12:00 关键词滚动发现
18:00 关键词滚动发现
每天一次 最近 7 天回补
每周一次 可选深度回补
```

滚动发现使用各平台支持的“最新发布”和最小时间范围。时间范围重叠是有意设计，用来补偿平台排序波动、延迟出现和某次请求失败。

### 2.2 发现来源

| 来源 | 作用 | 默认频率 |
| --- | --- | --- |
| 关键词搜索 | 主发现通道 | 每 6 小时 |
| 已知话题 | 补充固定话题内容 | 每 6 小时或每日 |
| 已跟踪账号 | 品牌、竞品、KOL | 每 6 小时 |
| 热榜 | 发现突发事件和新词 | 每 6 小时，全局一次 |
| 搜索建议 | 扩展别名和相关词 | 每日 |
| 文件导入 | 补录历史或其他来源 | 人工 |

不同来源都只能产生 Candidate，不能绕过统一摄取直接写内容表。

## 3. 采集的六层记录

### 3.1 Plan：长期计划

保存：

- 名称；
- 是否启用；
- 调度；
- 目标平台；
- 选择的词包；
- 详情和评论策略；
- 预算；
- 创建人和更新时间。

Plan 不保存某次执行时的最终关键词列表。

### 3.2 Run：一次执行

Run 是某次人工或定时触发的完整执行记录。创建 Run 时必须冻结配置：

```json
{
  "schema_version": "collection-run-config.v1",
  "plan_id": "plan_01",
  "trigger": "scheduler",
  "timezone": "Asia/Shanghai",
  "platform_keywords": {
    "xhs": ["爱玛", "爱玛电动车"],
    "dy": ["爱玛", "爱玛电动车"]
  },
  "date_from": "2026-08-11T18:00:00+08:00",
  "date_to": "2026-08-12T18:00:00+08:00",
  "comment_policy": "high_priority_only",
  "request_budget": 300
}
```

词包后续修改不能改变已经创建的 Run。

### 3.3 Scope：最小独立执行单元

Scope 示例：

```text
xhs + keyword_search + 爱玛
dy  + keyword_search + 爱玛电动车
xhs + tracked_account + user_123
xhs + comments + note_456
```

每个 Scope 有独立状态、分页进度、统计和错误。一个 Scope 失败不能让其他平台和关键词全部丢失。

### 3.4 Provider Request：一个可幂等的逻辑请求

Provider Request 表示“这个 Scope 的这一页或这一组明确参数需要完成一次外部操作”。它由 Operation、脱敏后的稳定参数和分页状态计算 `request_fingerprint`，同一逻辑请求在任务重试后仍使用同一条记录。

保存：

- `request_id`；
- `run_id`；
- `scope_id`；
- Provider；
- 平台；
- Operation；
- 脱敏请求参数；
- 分页输入；
- 逻辑状态；
- 尝试次数；
- 累计费用；
- 创建和完成时间。

Provider Request 不是一条真实网络调用记录，因此不会因为重试而覆盖 HTTP 状态、TikHub request ID 或 Raw。

### 3.5 Provider Request Attempt：一次真实 Provider 执行

每一次真实 Provider 执行都生成独立 Attempt。HTTP/SDK Provider 的一次外部发送是一条 Attempt；文件/历史导入的一次受控读取同样以 Attempt 留下可追溯执行事实。HTTP 状态、外部 request ID 和计费字段只在该传输/Provider 明确提供时填写：

- `attempt_id`；
- 所属 `request_id`；
- 尝试序号；
- 开始/结束时间；
- HTTP 状态；
- TikHub request ID；
- 计费币种、计费单位、单价快照、预计/实际费用；
- `billing_status` 和是否可能重复计费；
- 本次 Raw Artifact ID；
- 错误分类和安全摘要。

同一逻辑请求可能有多个 Attempt。所有 Attempt 都保留，逻辑请求汇总最终状态和累计费用。这样可以准确回答重试了几次、每次返回什么、实际付费多少，也不会为了幂等而抹掉失败证据。

### 3.6 Candidate：一次发现

Candidate 表示某条来源项在某次 Attempt 的某个 Raw 中被看到。它不是最终内容副本，也不能只用 `content_discoveries` 的首末 Run 聚合替代。

```text
Candidate
→ 提取平台身份
→ 去重
→ 必要时详情补全
→ Mapper
→ Canonical
→ Ingestion
```

每个 Candidate 只直接保存实际 Provider Request Attempt、`item_kind`（content/comment）、`external_item_id`、稳定 `item_locator` 和发现时间；Run、Scope、Raw Artifact、平台及来源类型/值必须通过唯一受约束链 `Candidate → Attempt → Provider Request → Scope → Run` 和 `Attempt.raw_artifact_id` 推导，禁止复制这些列后仅靠应用保证一致。创建 Candidate 前，Deferred Constraint Trigger 验证 Attempt 已完成且有完整性已校验的 Raw。每次 Mapper/Ingestion 结果追加独立记录，保存 Canonical 版本/身份、`target_type`，以及互斥的 `content_id` 或 `comment_id` 外键、结果或安全错误；Trigger 还验证非空 `target_type` 与 Candidate 的 `item_kind` 相同，并验证目标 Content（或 Comment 所属 Content）平台与 Scope 平台一致。由此才能回答“哪个 Raw 中哪一项在何次执行产生或再次发现了这条内容/评论”，且数据库不能拼接互相矛盾的来源链。

## 4. 关键词和词包

关键词必须以单个词为最小单位保存在数据库，不使用运行时文件驱动采集。

```text
keyword_packs
keywords
keyword_pack_items
collection_plan_keyword_packs
```

规则：

1. 同一个规范化关键词只保存一份；
2. 词包和关键词使用关联表，不保存逗号分隔字符串；
3. 关键词可以设置平台、启用状态、优先级和备注；
4. 保存 Plan 时校验所有目标平台至少有一个可用关键词；
5. 创建 Run 时把最终关键词按平台展开并冻结；
6. Worker 只消费 Run Snapshot，不读取词包猜测默认词；
7. 文件只用于批量导入、导出或初始化 Seed。

## 5. Provider Adapter 与 TikHub 参考实现

系统允许 TikHub、平台官方 API、Apify、自建采集器、文件/历史导入等同级 Provider Adapter。Provider 可以使用 HTTP、SDK 或文件读取，但都必须先形成可追溯 Raw Evidence/Candidate，再由 Mapper 产出同一 Canonical；任何 Provider 都不能直接写内容表。TikHub 只是当前规划中的第一个具体参考实现。

TikHub 目标目录：

```text
adapters/providers/tikhub/
├─ client.py
├─ config.py
├─ errors.py
├─ models.py
├─ pricing.py
├─ operations/
│  ├─ xiaohongshu.py
│  ├─ douyin.py
│  ├─ kuaishou.py
│  ├─ weibo.py
│  └─ bilibili.py
└─ mappers/
   ├─ xiaohongshu.py
   ├─ douyin.py
   ├─ kuaishou.py
   ├─ weibo.py
   └─ bilibili.py
```

### 5.1 Client 只负责通用 HTTP

`client.py` 负责：

- URL 和认证；
- 超时；
- 连接池；
- 限流；
- 可重试错误；
- TikHub 公共响应包；
- request ID；
- 计费元数据；
- 日志上下文；
- Raw Request/Response Envelope。

Client 不知道小红书的 `cursor`，也不解析内容字段。

### 5.2 Operation 负责平台调用规则

Operation 负责：

- endpoint；
- 请求参数；
- 分页状态；
- 详情和评论调用组合；
- 平台停止条件；
- 返回 Raw Page。

例如小红书关键词搜索使用 `search_notes`，分页需要页码和搜索会话字段；评论需要保存 `cursor/index/pageArea`。抖音视频搜索使用 `cursor/search_id`，部分接口还需要 `backtrace`。B站当前分类搜索使用返回的下一页 cursor。

业务 Service 不能直接拼 endpoint 或解析 cursor。

### 5.3 Mapper 只负责翻译事实

Mapper 输入：

```text
Raw Page / Raw Item
+ SourceObservation
+ 明确的采集上下文
```

Mapper 输出：

```text
CanonicalContentV1
CanonicalCommentV1
MetricObservationV1
```

Mapper 禁止：

- 读数据库；
- 发 HTTP；
- 写文件；
- 计算告警；
- 调用模型；
- 猜测无法确认的发布时间、作者、父评论或业务分类。

## 6. Raw 原始证据

### 6.1 保存原则

每个成功返回并完成校验的 Provider Request Attempt 必须保存一个不可变 gzip JSON 文件。失败响应如果包含可安全保存的响应体，也保存错误 Envelope。

文件路径：

```text
/data/AIMA_UGC/runtime/data/raw/
  <provider>/
    <platform>/
      2026/08/12/
        <run_id>/
          <scope_id>/
            <attempt_id>.json.gz
```

不使用固定 `latest.json.gz` 覆盖历史。需要“最新”时由数据库查询 Provider Request 或生成可重建索引。

### 6.2 Raw Envelope

Raw Envelope 顶层语义 Provider 无关；下面只用 TikHub + 小红书展示一个具体实例，其他 Provider 不需要伪装成 TikHub 字段。

```json
{
  "schema_version": "provider-response.v1",
  "provider": "tikhub",
  "platform": "xhs",
  "operation": "search_notes",
  "request_id": "req_01",
  "attempt_id": "attempt_01",
  "run_id": "run_01",
  "scope_id": "scope_01",
  "requested_at": "2026-08-12T10:00:01Z",
  "completed_at": "2026-08-12T10:00:02Z",
  "request": {
    "method": "GET",
    "path": "/api/v1/xiaohongshu/app_v2/search_notes",
    "params": {
      "keyword": "爱玛",
      "page": 1,
      "sort_type": "time_descending",
      "time_filter": "一天内"
    }
  },
  "response": {
    "status_code": 200,
    "external_request_id": "tikhub_request_id",
    "body": {}
  }
}
```

写入步骤：

```text
递归脱敏
→ JSON 序列化校验
→ ArtifactService 创建 pending 元数据并分配 storage_key
→ 写临时文件
→ flush + fsync
→ gzip 可读取校验
→ 计算 SHA-256
→ 原子 rename
→ ArtifactService/Repository 把元数据更新为 stored
→ Attempt 与业务短事务关联 Artifact，并更新为 linked
```

`ArtifactStore` 只完成按 `storage_key` 的字节写入和原子 rename，不写数据库状态；`ArtifactService` 和 Repository 才能推进 `pending/stored/linked`。任一步失败都保留可对账状态，由维护任务识别长期 pending、元数据缺文件和磁盘孤儿文件，不以删除证据作为失败恢复手段。

禁止在 Raw 中保存 Authorization、Cookie、API Key、数据库密码、模型密钥和内部会话 Token。

## 7. 分页状态机

每个平台 Operation 必须把分页写成可测试状态机：

```text
初始状态
→ 构造请求
→ 保存 Raw
→ 提取结果和下一页状态
→ 去重
→ 判断停止
→ 下一页
```

统一停止条件：

- Provider 明确无下一页；
- 当前页为空；
- 下一 cursor/page 没有推进；
- 页面内容完全重复；
- 已连续越过时间边界；
- 达到本次显式预算；
- 任务被取消；
- 技术安全页数上限。

“安全页数上限”只防止异常无限循环，不能当业务数据上限。触发时 Run 必须标记为 `partial_success`，并记录 `page_limit`，不能假装完整。

## 8. Canonical 数据契约

Canonical 是 AIMA 自己定义的理想业务语言，不由 TikHub 或任一平台当前响应反向决定。机器事实源固定在：

```text
backend/src/aima_ugc/contracts/canonical/
→ Pydantic 唯一手写事实源

contracts/canonical/*.schema.json
→ 由 Pydantic 确定性生成的 JSON Schema

contracts/canonical/examples/
→ 固定合法脱敏示例
```

写入使用原子 Observation：`CanonicalContentV1` 与 `CanonicalCommentV1`；读取、导出、AI 和页面使用以一条内容为根的 `CanonicalContentAggregateV1`。Mapper 只生成原子 Contract，不为凑出整帖树查询数据库。

### 8.1 内容与账号

内容身份固定为 `(platform, external_content_id)`，备用稳定 ID 放入 `alternate_ids`。内容可表达内容类型、标题、正文、稳定原文 URL、分享 URL、发布时间/来源更新时间、公开作者资料、媒体、话题、@提及、公开地点/IP 属地、状态和来源追溯。

帖子作者和评论者复用 `CanonicalAuthorV1`。已批准方案 B：在 Provider 明确公开提供时尽量保存主账号 ID、备用 ID、handle/账号名、显示昵称、主页 URL、头像 URL、简介、认证、公开地区及粉丝/关注/作品/累计获赞等统计；缺失或不可靠时为 `null`，禁止猜测。手机号、Cookie、Token、API Key、签名和其他认证 Secret 不进入 Canonical；生日、性别、学校、职业不属于 V1 核心字段。

### 8.2 互动指标

`CanonicalMetricsV1` 可表达：

```text
like_count
comment_count
share_count
repost_count
favorite_count
view_count
play_count
danmaku_count
coin_count
download_count
reply_count
```

平台没有该概念或本次响应未提供时为 `null`；明确观察到零才写 `0`。多次采集允许指标上升或下降，不能使用 `max()` 覆盖真实平台校正、取消点赞或评论删除。

### 8.3 评论关系

评论身份固定为 `(platform, external_content_id, external_comment_id)`：

- `external_comment_id`：评论自身 ID；
- `root_comment_id`：所属一级评论线程根；
- `parent_comment_id`：直接回复对象；
- 无法确认关系时保留 `null` 或进入聚合视图的 `unthreaded_comments`，禁止按数组位置猜父子关系。

评论还可表达评论者公开资料、正文、发布时间/来源更新时间、点赞/回复数、媒体、@提及、地点/IP 属地、是否内容作者本人、状态和来源。

### 8.4 稀疏 Observation

每个 `CanonicalContentV1` / `CanonicalCommentV1` 都必须带 `observed_fields`，只声明本次 Provider/Operation 真正观察到的可更新字段：

```text
字段出现在 observed_fields
→ Ingestion 可以按本次值更新

字段未出现
→ 保留数据库已有更完整值

字段明确观察为 null
→ 只有该字段/Operation 语义允许清空时才清空
```

因此搜索卡片、详情、评论接口和不同 Provider 可以共同刷新同一内容，而不会因为稀疏响应把历史详情、媒体或作者资料误删。

### 8.5 内容聚合与评论覆盖

`CanonicalContentAggregateV1` 是 Read Model/交换结构，不是数据库单行大 JSON。它以一条帖子/笔记/视频/微博为根，包含：

```text
content
comment_coverage
comment_threads[]
  ├─ root_comment
  ├─ replies[]
  └─ coverage
unthreaded_comments[]
system(first_seen_at / last_seen_at / latest_observed_at)
lineage[]
```

评论覆盖状态固定区分 `complete`、`partial`、`not_requested`、`unavailable`，并可记录平台报告总数、已采集数和观察时间。空评论数组不能被静默解释成“平台确实没有评论”。`lineage` 从 Candidate/Attempt/Raw 等来源事实组装，不创建第二套来源真相。

### 8.6 时间规则

- API/Canonical 使用 ISO-8601 且需要时刻的字段必须带时区；
- 数据库存 `timestamptz`；
- 无时区时间只有在 Provider 语义明确且已绑定平台时区时才能转换；
- 无法可靠解析时保存 `null` 和原始值到 Raw；
- 禁止把采集时间冒充发布时间；
- 从平台 ID 推算时间只能作为明确标记的低置信度候选，不覆盖来源明确的发布时间。

## 9. 摄取算法

```text
1. Raw 已成功落盘并形成 Candidate
2. 对应 Provider/平台 Mapper 输出原子 Canonical
3. Pydantic + JSON Schema 校验，并保留 `observed_fields`/Source
4. ContentIngestionService 开启数据库短事务
5. 按平台身份锁定或 Upsert 当前内容；只更新 `observed_fields` 明确观察到的字段，未观察字段保持原值
6. 业务字段变化时新增 content_version
7. 指标变化或到达每日检查点时新增 metric_observation；指标允许真实下降，禁止只取历史最大值
8. 更新 current 表的最新值、first_seen_at、last_seen_at
9. 写入 Candidate Ingestion 结果并更新发现来源聚合
10. 评论按同样规则 Upsert
11. 如需后续分析/监控，在同一事务插入内部幂等 Job
12. 更新 Scope/Run 统计并提交事务
```

数据库写失败时 Raw 已存在，Job 可以重试 Mapper 和 Ingestion，且在 Raw 完整性校验通过时不得再次调用 Provider。若此前网络结果未知且没有可用 Raw，是否重试必须按费用策略决定，系统要记录潜在重复计费，不能承诺外部 Provider 一定未收费。

## 10. 当前值和历史

不把全部历史塞进一个 JSON。

```text
contents
→ 当前稳定字段

content_versions
→ 标题、正文、作者、URL、状态等变化

content_metric_observations
→ 点赞、评论、分享、转发、收藏、浏览/播放、弹幕、投币、下载等时间序列

comments
→ 当前评论

comment_versions
→ 评论文本、关系或状态变化

comment_metric_observations
→ 评论点赞、回复数等变化

comment_coverage_observations
→ 评论完整/部分/未请求/不可用及抓取数量历史
```

指标历史默认规则：

- 首次发现一定记录；
- 数值变化时记录；
- 即使无变化，每个 `Asia/Shanghai` 业务日最多记录一个检查点，并由数据库部分唯一约束兜底；
- 同一 Request 重试不得产生重复 Observation；
- 使用唯一键保证幂等。

## 11. 详情和评论刷新

### 11.1 内容详情

搜索卡片只负责发现。以下情况获取详情：

- 首次发现；
- 搜索卡片缺少关键字段；
- 互动指标变化；
- 高风险或高热内容；
- 到达计划刷新节点。

### 11.2 默认刷新层级

| 层级 | 刷新 |
| --- | --- |
| 高热/高风险 | 首次、6h、12h、24h，之后每日到第 7 天 |
| 普通 | 首次、24h、72h、第 7 天 |
| 低优先级 | 首次详情；后续由指标变化触发 |
| 超过 30 天 | 默认不主动刷新，除非进入事件或人工关注 |

评论只对高价值内容增量抓取。单内容评论预算和单 Run 评论预算分别控制，某个热门内容不能耗尽全部平台预算。

## 12. 成本控制

每次 Provider Request Attempt 必须记录本次调用事实，逻辑 Provider Request 汇总全部 Attempt：

- Operation；
- 请求次数；
- 单价快照；
- 预计费用；
- 实际费用；
- 缓存命中；
- 是否重试；
- 是否由补回任务触发。

Run、单内容评论和全局费用/请求预算必须由数据库原子预留并在 Attempt 完成后结算；禁止多个 Worker 使用“先读剩余额度、后各自调用”的竞态流程。每次准备发起真实 HTTP 调用都先创建新的 Attempt，并为该 Attempt 取得 global + run 预留；只有评论 Operation 再强制取得目标 content_comments 预留。任何应有账户缺失或调用时刻没有覆盖周期都必须关闭失败，不能当作没有预算限制。网络重试是新的真实调用，因此必须创建新的 Attempt 和预留。只有同一 Attempt 的预留事务重放使用唯一键复用原预留；Dispatcher 验证所属 Job Fencing 后 CAS 进入 `dispatching`，Transport 必须关闭单次调用内隐藏的自动网络重试，该 Attempt 最多执行一次 Provider Client 调用，崩溃后不能用同一 Attempt 再次发送。恢复时先校验确定性路径上的 Raw：存在就只做回放和关联，缺失或损坏才把 `dispatching` 按计费未知处理并保留额度。新的网络发送使用新 Attempt。只有活跃 Transport 明确证明请求从未进入发送边界时，Attempt 才能终结为 `not_sent` 并释放；进程崩溃后不能倒推为未发送。网络结果未知时预留额度保持占用，待人工/对账策略确认后再释放或记为实际费用。

优化顺序：

1. 同一 Run 内跨词去重；
2. 热榜全局请求一次；
3. 搜索卡片先判断，避免所有内容都抓详情；
4. 只对高价值内容抓评论；
5. 通过完整性校验的 Raw 存在时只做回放；
6. 分页以数据和时间边界停止，不用固定页数制造大量无效请求。

## 13. 独立调试和测试

### 13.1 Provider Operation

输入：

```text
ProviderConfig + platform + operation + explicit parameters
```

输出：

```text
Raw Page + Pagination State + Request Metadata
```

验证方式：

- Fake HTTP Fixture；
- 脱敏真实响应 Fixture；
- 受控 Probe。

Probe 必须调用对应 Provider Adapter 的生产 Client/Operation，不能复制 endpoint、参数、分页或文件解析逻辑。

### 13.2 Mapper

```text
Fixture JSON
→ 生产 Mapper
→ Canonical JSON
→ Schema 校验
```

不需要启动前端、Scheduler 或数据库。

### 13.3 Ingestion

```text
Canonical Fixture
→ ContentIngestionService
→ 隔离 PostgreSQL
→ 查询 current/history/来源关联
```

### 13.4 真实 Provider Probe

五个平台进入正式实现后，都必须保留一个由人工显式运行、复用生产实现的 Real Probe。Probe 的职责是验证真实 Provider 当前兼容性，不是建立第二套采集器，也不是生产调度入口。

统一调用链固定为：

```text
显式 Probe 配置
→ 正式 Provider Config / Secret 边界
→ 正式 Provider Client
→ 正式 Platform Operation / 分页
→ 逐请求 Raw
→ 正式 Mapper
→ Canonical Contract 校验
→ 人工审阅派生物
```

Probe 配置必须能够按已实现 Operation 显式选择或填写：

- Provider Base URL；
- `platform`；
- `operation`；
- 关键词；
- 内容 ID、评论 ID 等目标身份；
- 排序、时间范围及其他该 Operation 明确支持的业务选项；
- 初始分页状态；
- `max_pages`、`max_requests` 等显式技术/费用上限；
- 独立测试输出目录。

不同平台的私有参数由对应正式 Operation 定义和校验，不为了配置表面统一而制造一个猜测所有平台语义的万能参数模型。Probe 脚本/入口不得自行拼 endpoint、复制 cursor/page 推进、重新解释 Provider JSON 或重写 Mapper。

真实 Credential/API Key 必须从正式 Secret 边界取得；允许 Probe 使用真实 Provider URL 和真实凭据，但 Secret 不得硬编码在脚本或配置样例中，不得进入 Git、日志、Raw、Canonical、XLSX、Job Payload 或数据库明文。Provider URL 仍受正式出站域名/安全边界约束，不能用“调试”绕过既有校验。

每个实际请求必须保留独立、完整、可追溯的脱敏 Raw JSON/GZIP；Probe 同时使用正式 Mapper 产出 Canonical 并执行 Contract 校验。Raw 是外部 Provider 原始证据，Canonical 是机器可验证的业务转换结果。Probe 可以基于 Raw/Canonical 生成 XLSX 等人工审阅文件，但这些文件只用于人工检查，是可重新生成的派生物，不作为 Provider 原始证据、Canonical Contract、数据库导入事实源或业务持久化格式。

真实 Probe 还必须满足：

- 默认关闭，只能由人工显式启动；
- 明确提示真实调用可能产生费用并要求显式请求/分页预算；
- 不进入普通 CI；普通 CI 继续使用 Fake + 脱敏 Fixture；
- 不写生产业务数据库；
- 不把真实响应或个人信息未经脱敏直接提交 Git；
- 不打印 Secret；
- 结果只证明当次真实 Provider 边界，不替代可重复 Fixture/Fake 测试。

人工审阅 XLSX 的详细布局和使用方式由 [`../测试与调试说明.md`](../测试与调试说明.md) 维护，避免 Blueprint 复制视觉规格；这里仅冻结“逐请求 Raw + Canonical + 可重新生成的人工审阅视图”这一边界。

## 14. 平台能力门禁与 TikHub Provider 入口参考

TikHub 只是一个 Provider Adapter。官方 API、Apify、自建采集器和文件/历史导入可以并列增加，只要遵守相同 Raw → Mapper → Canonical 边界。以下仅是截至 2026-08-13 对 TikHub 设计时核验过且保留为候选的入口：

- 小红书搜索笔记：`/api/v1/xiaohongshu/app_v2/search_notes`
- 小红书图文/视频详情：`get_image_note_detail`、`get_video_note_detail`
- 小红书评论：`get_note_comments`
- 小红书用户笔记：`get_user_posted_notes`
- 抖音视频搜索 V2：`/api/v1/douyin/search/fetch_video_search_v2`
- 抖音视频搜索 V1：可作为经过验证的回退
- B站分类搜索：`/api/v1/bilibili/app/fetch_search_by_type`

以上清单不是五平台能力矩阵，也不授权凭端点名称直接实现。编码前必须在阶段 0 为小红书、抖音、微博、B站、快手逐一确认所选 Operation、请求字段、分页/停止语义、详情和评论能力、费用单位、速率限制、数据保留限制、真实脱敏 Fixture 和验收字段。微博与快手在本蓝图修订时尚未选定唯一 Operation，因此是明确门禁，不得由 Coding Agent 猜测或静默套用其他平台规则。

Operation 目录中的 endpoint 必须来自实施时再次核验的 TikHub 官方文档和 Fixture，不从聊天记录抄写。TikHub 文档变化时先更新能力矩阵和 Operation Contract Test，评估兼容与费用后再改实现；普通功能开发不顺手切换新版端点。

## 15. 验收标准

采集模块完成必须证明：

- 五平台每个平台至少一个脱敏 Fixture；
- 每个平台分页第一页、下一页、末页、重复页、cursor 不推进测试；
- Raw 文件不可覆盖、可解压、SHA-256 正确；
- Secret 脱敏测试；
- Canonical Schema 测试；
- 同一内容跨词去重；
- 内容字段变化和指标变化历史正确；
- 评论 root/parent 关系不被猜测；
- 同一逻辑 Provider Request 的多个 Attempt 都保留各自状态、Raw 和费用；
- 已校验 Raw 的取消/重试只做回放；网络结果未知时按策略重试并记录潜在重复计费；
- 每个 Candidate 可追溯到 Run、Scope、Attempt、Raw 和来源项；
- Run、评论和全局预算的并发预留/结算有真实 PostgreSQL 集成测试；
- Provider Probe 复用生产实现；
- 五个平台正式 Operation 都有可由人工显式运行的 Real Probe，可配置真实 Provider URL、Secret 和已批准 Operation 参数，并受显式请求/分页预算约束；
- Real Probe 逐请求保存完整脱敏 Raw、运行正式 Mapper/Canonical 校验，并可生成不替代机器事实的 XLSX 人工审阅派生物；
- 费用和 Run 统计可查询。
