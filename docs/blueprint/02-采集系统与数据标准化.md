# 采集系统与数据标准化

## 1. 目标

采集系统必须回答：

```text
为什么发起这次采集？
用了哪些平台和关键词？
每个平台实际请求了哪些接口和分页参数？
实际 Provider 原始返回/输入是什么？
哪些内容被识别、去重和更新？
为什么某条内容继续/没有继续抓详情或评论？
哪条业务数据来自哪个原始请求？
失败后从哪里恢复？
本次调用花费多少？
```

如果这些问题只能靠猜日志或查看一大段业务代码，设计就是不合格的。

Stage 7 的五平台业务 Decision Pipeline、Provider Capability、首版 TikHub Operation Matrix、自适应评论、Deep Collection、Provider Billing/成本审计以及未来 Budget/Cost Guard 扩展方向统一见 [08-采集策略与平台能力.md](08-采集策略与平台能力.md)；面向开发/调试的具体平台抓取逻辑见 [`../collection/README.md`](../collection/README.md)。本文保留 Provider/Raw/Mapper/Canonical/来源链等采集基础，不维护第二份平台 endpoint 表。

## 2. 采集策略

业务日、默认调度和日志显示时区固定为 `Asia/Shanghai`。第一版 `collection_plans.timezone` 也只能取该值；字段保留 IANA 时区名称，是为以后通过独立决策、迁移和 DST 测试开放其他调度时区，不表示当前可以任意配置。

### 2.1 主调度

```text
00:00 关键词滚动发现
06:00 关键词滚动发现
12:00 关键词滚动发现
18:00 关键词滚动发现
每天一次 最近 7 天回补
每周一次 可选深度回补
```

上述是默认业务节奏，不表示所有 Provider 都有精确 6 小时时间过滤。每个平台按 Capability 使用真实支持的排序/时间过滤；Provider 最小时间窗大于调度周期时允许重叠，通过内容身份去重和 08 的 Decision Pipeline 避免重复详情/评论费用。用户配置的搜索时间范围小于调度周期时只 Warning，不阻止保存；Provider 不支持或参数非法才 Error。

### 2.2 发现来源

| 来源 | 作用 | 默认频率 |
| --- | --- | --- |
| 关键词搜索 | 主发现通道 | 每 6 小时 |
| 已知话题 | 补充固定话题内容 | 每 6 小时或每日 |
| 已跟踪账号 | 品牌、竞品、KOL | 每 6 小时 |
| 热榜 | 发现突发事件和新词 | 每 6 小时，全局一次 |
| 搜索建议 | 扩展别名和相关词 | 每日 |
| 文件导入 | 补录历史或其他来源 | 人工 |

不同来源都只能产生 Candidate，不能绕过统一摄取直接写内容表。

## 3. 采集的六层记录

### 3.1 Plan：长期计划

保存：

- 名称；
- 是否启用；
- 调度；
- 目标平台；
- 选择的词包；
- 每个平台选择的具体 `provider_config_id`，以及该 `Provider + Platform` Capability 允许的业务搜索参数；
- 详情策略；
- 评论触发/深度/排序/二级回复策略；
- 创建人和更新时间。

Provider 配置实例与平台选择分离：同一种 Provider 可以存在多个配置实例/账号，一个配置实例也可以被多个平台引用；Plan 选择稳定 `provider_config_id`，而不是只保存一个无法区分账号的 `provider='tikhub'` 字符串。Provider Config 本身不绑定平台。

Plan 不保存某次执行时的最终关键词列表，也不保存 cursor/search_id/pageArea/API Key 等 Provider 技术状态或 Secret。Stage 7 的结构化平台策略由版本化 Pydantic Contract 定义，数据库落点按 03 的 Plan/关联表和后续 Stage 7 Migration 建立。

### 3.2 Run：一次执行

Run 是某次人工或定时触发的完整执行记录。创建 Run 时必须冻结已经解析的 Provider Config 身份、Provider 类型、平台业务策略和最终关键词，后续修改 Provider Config 或 Plan 不能改变已经创建的 Run。当前版本不把请求/金额预算写入 Run Snapshot。

概念示例：

```json
{
  "schema_version": "collection-run-config.v1",
  "plan_id": "plan_01",
  "trigger": "scheduler",
  "timezone": "Asia/Shanghai",
  "platform_keywords": {
    "xhs": ["爱玛", "爱玛电动车"],
    "dy": ["爱玛", "爱玛电动车"]
  },
  "platform_policies": {
    "xhs": {
      "provider_config_id": "provider_config_01",
      "provider": "tikhub",
      "search": {
        "sort": "latest",
        "published_within": "1d"
      },
      "comments": {
        "trigger": "new_or_comment_changed",
        "mode": "adaptive",
        "full_fetch_threshold": 50,
        "sample_target": 50,
        "reply_target_per_root": 5
      }
    }
  },
  "date_from": "2026-08-11T18:00:00+08:00",
  "date_to": "2026-08-12T18:00:00+08:00"
}
```

示例只说明 Snapshot 语义，不是 Pydantic/数据库字段事实；实际 Contract 建立后以机器 Contract 为准。Snapshot 不保存原始 API Key/Token；需要执行 Provider 时由稳定 `provider_config_id`/`secret_ref` 经服务端 Secret 边界解析。

### 3.3 Scope：最小独立执行单元

Scope 示例：

```text
xhs + keyword_search + 爱玛
dy  + keyword_search + 爱玛电动车
xhs + tracked_account + user_123
xhs + comments + note_456
```

每个 Scope 有独立状态、分页进度、统计和错误。一个 Scope 失败不能让其他平台和关键词全部丢失。

### 3.4 Provider Request：一个可幂等的逻辑请求

Provider Request 表示“这个 Scope 的这一页或这一组明确参数需要完成一次外部操作”。它由 Operation、脱敏后的稳定参数和分页状态计算 `request_fingerprint`，同一逻辑请求在任务重试后仍使用同一条记录。

保存：

- `request_id`；
- `run_id`（由 Scope 父链推导，数据库不重复列）；
- `scope_id`；
- Provider；
- 平台（由 Scope 父链推导）；
- Operation；
- 脱敏请求参数；
- 分页输入；
- 逻辑状态；
- 尝试次数；
- 累计费用；
- 创建和完成时间。

Provider Request 不是一条真实网络调用记录，因此不会因为重试而覆盖 HTTP 状态、TikHub request ID 或 Raw。Stage 5C 已发布的 Request Schema 暂保留 `provider` 字段兼容；稳定 `provider_config_id` 已由 Stage 7 Migration 加入 Provider Request 来源链，历史 Revision 不改写。该身份用于 Provider 路由和审计，不代表当前存在预算账户。

### 3.5 Provider Request Attempt：一次真实 Provider 执行

每一次真实 Provider 执行都生成独立 Attempt。HTTP/SDK Provider 的一次外部发送是一条 Attempt；文件/历史导入的一次受控读取同样以 Attempt 留下可追溯执行事实。HTTP 状态、外部 request ID 和计费字段只在该传输/Provider 明确提供时填写：

- `attempt_id`；
- 所属 `request_id`；
- 尝试序号；
- 开始/结束时间；
- HTTP 状态；
- Provider external request ID；
- 计费币种、计费单位、单价快照、预计/实际费用；
- `billing_status` 和是否可能重复计费；
- 本次 Raw Artifact ID；
- 错误分类和安全摘要。

同一逻辑请求可能有多个 Attempt。所有 Attempt 都保留，逻辑请求汇总最终状态和累计费用。这样可以准确回答重试了几次、每次返回什么、实际付费多少，也不会为了幂等而抹掉失败证据。

### 3.6 Candidate：一次发现

Candidate 表示某条来源项在某次 Attempt 的某个 Raw 中被看到。它不是最终内容副本，也不能只用 `content_discoveries` 的首末 Run 聚合替代。

```text
Candidate
→ 提取平台身份
→ 形成/读取当前 Observation
→ 去重和 previous/current 比较
→ 08 Decision Pipeline 决定后续动作
→ Mapper / Canonical / Ingestion
```

每个 Candidate 只直接保存实际 Provider Request Attempt、`item_kind`（content/comment）、`external_item_id`、稳定 `item_locator` 和发现时间；Run、Scope、Raw Artifact、平台及来源类型/值必须通过唯一受约束链 `Candidate → Attempt → Provider Request → Scope → Run` 和 `Attempt.raw_artifact_id` 推导，禁止复制这些列后仅靠应用保证一致。创建 Candidate 前，Deferred Constraint Trigger 验证 Attempt 已完成且有完整性已校验的 Raw。每次 Mapper/Ingestion 结果追加独立记录，保存 Canonical 版本/身份、`target_type`，以及互斥的 `content_id` 或 `comment_id` 外键、结果或安全错误；Trigger 还验证非空 `target_type` 与 Candidate 的 `item_kind` 相同，并验证目标 Content（或 Comment 所属 Content）平台与 Scope 平台一致。

“重复内容”不删除 Candidate 证据；它只影响是否继续花钱请求详情/评论。

## 4. 关键词和词包

关键词必须以单个词为最小单位保存在数据库，不使用运行时文件驱动采集。

```text
keyword_packs
keywords
keyword_pack_items
collection_plan_keyword_packs
```

规则：

1. 同一个规范化关键词只保存一份；
2. 词包和关键词使用关联表，不保存逗号分隔字符串；
3. 关键词可以设置平台、启用状态、优先级和备注；
4. 保存 Plan 时校验所有目标平台至少有一个可用关键词；
5. 创建 Run 时把最终关键词按平台展开并冻结；
6. Worker 只消费 Run Snapshot，不读取词包猜测默认词；
7. 文件只用于批量导入、导出或初始化 Seed。

## 5. Provider Adapter 与 TikHub 参考实现

系统允许 TikHub、平台官方 API、Apify、自建采集器、文件/历史导入等同级 Provider Adapter。Provider 可以使用 HTTP、SDK 或文件读取，但都必须先形成可追溯 Raw Evidence/Candidate，再由 Mapper 产出同一 Canonical；任何 Provider 都不能直接写内容表。

当前五个平台默认 Provider 均为 TikHub，但 Provider 与 Platform 解耦：以后可以单独替换某个平台 Provider，而不改写 Canonical/Ingestion/数据库。

### 5.1 Provider Config 与平台路由

Stage 7 的 Provider 配置模型固定为两层：

```text
Provider Config 实例
  ├─ provider_config_id（稳定 UUID）
  ├─ provider（例如 tikhub）
  ├─ display_name
  ├─ base_url
  ├─ secret_ref
  └─ enabled
        ↓
平台 / Plan 选择具体 provider_config_id
        ↓
Provider Registry 校验 provider + base_url
        ↓
Provider + Platform Capability
        ↓
Operation
```

规则：

1. 同一种 Provider 可以存在多个配置实例/账号，例如主 TikHub、备用 TikHub；配置实例用稳定 UUID 区分，显示名称可修改但不能靠名称作为业务外键；
2. Provider Config 不绑定平台；同一个配置实例可被多个平台引用，不同平台也可选择不同 Provider Config；
3. `base_url` 是非 Secret 配置，但必须使用 HTTPS，并在运行时经过已注册 Provider Adapter 的出站 allowlist；“前端可配置 URL”不等于允许任意 SSRF 目标；
4. `secret_ref` 只保存服务端 Secret 的安全相对引用，数据库、Contract、日志、Raw、Job Payload 和读取 API 都不保存/回显原始 API Key、Token、Cookie；
5. 当前机器 Registry 只接线已经有实现事实的 `tikhub + xhs`，TikHub 允许的 Base URL 为 `https://api.tikhub.io`；抖音、微博、B站、快手必须在各自 Operation/Fixture/Capability 单元完成后再加入 Registry；
6. Provider 类型是配置实例稳定身份的一部分。需要从 TikHub 改为另一个 Provider 时创建新的 Provider Config，并让 Plan/平台显式改引用，不能原地把旧 UUID 改成另一 Provider 后污染历史来源/审计；
7. 后续 Stage 8 可以提供 Provider 管理页面和 Secret 写入接口，但 Secret 写入必须进入正式 SecretStore/SecretService；读取 Provider Config 只返回非敏感配置和“已配置”状态，绝不回显原始 Secret。

当前机器 Contract 为 `ProviderConfigV1` 与 `ProviderPlatformRouteV1`；`provider_configs` 为 `system` Owner。后续 Plan/Run Snapshot 和最终预算 Ledger 以 `provider_config_id` 作为稳定 Provider 配置身份。

TikHub 目标目录：

```text
adapters/providers/tikhub/
├─ client.py
├─ config.py
├─ errors.py
├─ models.py
├─ pricing.py
├─ operations/
│  ├─ xiaohongshu.py
│  ├─ douyin.py
│  ├─ kuaishou.py
│  ├─ weibo.py
│  └─ bilibili.py
└─ mappers/
   ├─ xiaohongshu.py
   ├─ douyin.py
   ├─ kuaishou.py
   ├─ weibo.py
   └─ bilibili.py
```

当前 main 实际只有小红书 Operation/Mapper；其余四平台是 Stage 7 目标路径，只有真实实现存在后才成为机器事实。

### 5.2 Client 只负责通用 HTTP

`client.py` 负责：

- URL 和认证；
- 超时；
- 连接池；
- Provider 级限流；
- 一次传输；
- TikHub 公共响应包；
- request ID；
- 计费元数据；
- 日志上下文；
- Raw Request/Response Envelope。

Client 不知道小红书的 `cursor`，也不解析内容字段。单个 Attempt 内禁止隐藏网络自动重试。

### 5.3 Operation 负责平台调用规则

Operation 负责：

- endpoint；
- 规范化业务参数 → Provider 参数；
- 分页状态；
- 详情和评论调用组合；
- 平台停止条件；
- 返回 Raw Page。

业务 Service 不能直接拼 endpoint 或解析 cursor。TikHub App/Web/V2/V3 是 Provider 内部 API family，不是独立 Provider；每个业务 Operation 使用 08 批准的主 endpoint，不做通用静默 fallback。

### 5.4 Capability 负责“可配置什么”

每个 `Provider + Platform + Business Operation` 声明真实能力，至少覆盖排序、时间过滤、内容类型、comment_count/评论许可观察、评论排序、二级评论和增量评论能力。前端只展示 Capability 支持的**业务语义**，不暴露 cursor/search_id/pageArea/API Key 等第三方技术状态。

完整 Capability 语义见 08。

### 5.5 Mapper 只负责翻译事实

Mapper 输入：

```text
Raw Page / Raw Item
+ SourceObservation
+ 明确的采集上下文
```

Mapper 输出：

```text
CanonicalContentV1
CanonicalCommentV1
MetricObservationV1
```

Mapper 禁止：

- 读数据库；
- 发 HTTP；
- 写文件；
- 计算告警；
- 调用模型；
- 猜测无法确认的发布时间、作者、父评论或业务分类。

新平台 Mapper 只有在合法脱敏真实 Fixture/明确上下文证明字段后才能建立对应映射；官方 endpoint 文档不能替代真实响应 Fixture。

## 6. Raw 原始证据

### 6.1 保存原则

每个成功返回并完成校验的 Provider Request Attempt 必须保存一个不可变 gzip JSON 文件。失败响应如果包含可安全保存的响应体，也保存错误 Envelope。

文件路径：

```text
/data/AIMA_UGC/runtime/data/raw/
  <provider>/
    <platform>/
      2026/08/12/
        <run_id>/
          <scope_id>/
            <attempt_id>.json.gz
```

不使用固定 `latest.json.gz` 覆盖历史。需要“最新”时由数据库查询 Provider Request 或生成可重建索引。

### 6.2 Raw Envelope

Raw Envelope 顶层语义 Provider 无关；下面只用 TikHub + 小红书展示一个具体实例，其他 Provider 不需要伪装成 TikHub 字段。

```json
{
  "schema_version": "provider-response.v1",
  "provider": "tikhub",
  "platform": "xhs",
  "operation": "search_notes",
  "request_id": "req_01",
  "attempt_id": "attempt_01",
  "run_id": "run_01",
  "scope_id": "scope_01",
  "requested_at": "2026-08-12T10:00:01Z",
  "completed_at": "2026-08-12T10:00:02Z",
  "request": {
    "method": "GET",
    "path": "/api/v1/xiaohongshu/app_v2/search_notes",
    "params": {
      "keyword": "爱玛",
      "page": 1,
      "sort_type": "time_descending",
      "time_filter": "一天内"
    }
  },
  "response": {
    "status_code": 200,
    "external_request_id": "tikhub_request_id",
    "body": {}
  }
}
```

写入步骤：

```text
递归脱敏
→ JSON 序列化校验
→ ArtifactService 创建 pending 元数据并分配 storage_key
→ 写临时文件
→ flush + fsync
→ gzip 可读取校验
→ 计算 SHA-256
→ 原子 rename
→ ArtifactService/Repository 把元数据更新为 stored
→ Attempt 与业务短事务关联 Artifact，并更新为 linked
```

`ArtifactStore` 只完成按 `storage_key` 的字节写入和原子 rename，不写数据库状态；`ArtifactService` 和 Repository 才能推进 `pending/stored/linked`。任一步失败都保留可对账状态，由维护任务识别长期 pending、元数据缺文件和磁盘孤儿文件，不以删除证据作为失败恢复手段。

禁止在 Raw 中保存 Authorization、Cookie、API Key、数据库密码、模型密钥和内部会话 Token。

## 7. 分页状态机

每个平台 Operation 必须把分页写成可测试状态机：

```text
初始状态
→ 构造请求
→ 保存 Raw
→ 提取结果和下一页状态
→ 去重
→ 判断停止
→ 下一页
```

统一停止条件：

- Provider 明确无下一页；
- 当前页为空；
- 下一 cursor/page 没有推进；
- 页面内容完全重复；
- 已连续越过**可靠的**时间边界；
- 任务被取消；
- 技术安全页数上限。

Provider 没有原生时间筛选时，不能凭想象加时间停止。只有排序/发布时间字段经 Fixture/Probe 证明稳定时，才能用本地时间边界，并在 Capability/UI 中标明不是 Provider 原生筛选。

“安全页数上限”只防止异常无限循环，不能当业务数据上限。触发时 Run 必须标记为 `partial_success`，并记录 `page_limit`，不能假装完整。

## 8. Canonical 数据契约

Canonical 是 AIMA 自己定义的理想业务语言，不由 TikHub 或任一平台当前响应反向决定。机器事实源固定在：

```text
backend/src/aima_ugc/contracts/canonical/
→ Pydantic 唯一手写事实源

contracts/canonical/*.schema.json
→ 由 Pydantic 确定性生成的 JSON Schema

contracts/canonical/examples/
→ 固定合法脱敏示例
```

写入使用原子 Observation：`CanonicalContentV1` 与 `CanonicalCommentV1`；读取、导出、AI 和页面使用以一条内容为根的 `CanonicalContentAggregateV1`。Mapper 只生成原子 Contract，不为凑出整帖树查询数据库。

### 8.1 内容与账号

内容身份固定为 `(platform, external_content_id)`，备用稳定 ID 放入 `alternate_ids`。内容可表达内容类型、标题、正文、稳定原文 URL、分享 URL、发布时间/来源更新时间、公开作者资料、媒体、话题、@提及、公开地点/IP 属地、状态和来源追溯。

帖子作者和评论者复用 `CanonicalAuthorV1`。已批准方案 B：在 Provider 明确公开提供时尽量保存主账号 ID、备用 ID、handle/账号名、显示昵称、主页 URL、头像 URL、简介、认证、公开地区及粉丝/关注/作品/累计获赞等统计；缺失或不可靠时为 `null`，禁止猜测。手机号、Cookie、Token、API Key、签名和其他认证 Secret 不进入 Canonical；生日、性别、学校、职业不属于 V1 核心字段。

### 8.2 互动指标

`CanonicalMetricsV1` 可表达：

```text
like_count
comment_count
share_count
repost_count
favorite_count
view_count
play_count
danmaku_count
coin_count
download_count
reply_count
```

平台没有该概念或本次响应未提供时为 `null`；明确观察到零才写 `0`。多次采集允许指标上升或下降，不能使用 `max()` 覆盖真实平台校正、取消点赞或评论删除。

`comment_count=0` 和 `comment_count=null` 在采集决策中含义不同：前者只有当前 Operation 可靠观察到零时才触发“无需请求评论”，后者表示未知/未观察，必须按 Capability 处理。

### 8.3 评论关系

评论身份固定为 `(platform, external_content_id, external_comment_id)`：

- `external_comment_id`：评论自身 ID；
- `root_comment_id`：所属一级评论线程根；
- `parent_comment_id`：直接回复对象；
- 无法确认关系时保留 `null` 或进入聚合视图的 `unthreaded_comments`，禁止按数组位置猜父子关系。

评论还可表达评论者公开资料、正文、发布时间/来源更新时间、点赞/回复数、媒体、@提及、地点/IP 属地、是否内容作者本人、状态和来源。

### 8.4 稀疏 Observation

每个 `CanonicalContentV1` / `CanonicalCommentV1` 都必须带 `observed_fields`，只声明本次 Provider/Operation 真正观察到的可更新字段：

```text
字段出现在 observed_fields
→ Ingestion 可以按本次值更新

字段未出现
→ 保留数据库已有更完整值

字段明确观察为 null
→ 只有该字段/Operation 语义允许清空时才清空
```

因此搜索卡片、详情、评论接口和不同 Provider 可以共同刷新同一内容，而不会因为稀疏响应把历史详情、媒体或作者资料误删。

### 8.5 内容聚合与评论覆盖

`CanonicalContentAggregateV1` 是 Read Model/交换结构，不是数据库单行大 JSON。它以一条帖子/笔记/视频/微博为根，包含：

```text
content
comment_coverage
comment_threads[]
  ├─ root_comment
  ├─ replies[]
  └─ coverage
unthreaded_comments[]
system(first_seen_at / last_seen_at / latest_observed_at)
lineage[]
```

评论覆盖状态固定区分 `complete`、`partial`、`not_requested`、`unavailable`，并可记录平台报告总数、已采集数和观察时间。空评论数组不能被静默解释成“平台确实没有评论”。Stage 7 还要求读取/API/报告能解释抽样排序、目标、实际数量和停止原因，具体见 08。`lineage` 从 Candidate/Attempt/Raw 等来源事实组装，不创建第二套来源真相。

### 8.6 时间规则

- API/Canonical 使用 ISO-8601 且需要时刻的字段必须带时区；
- 数据库存 `timestamptz`；
- 无时区时间只有在 Provider 语义明确且已绑定平台时区时才能转换；
- 无法可靠解析时保存 `null` 和原始值到 Raw；
- 禁止把采集时间冒充发布时间；
- 从平台 ID 推算时间只能作为明确标记的低置信度候选，不覆盖来源明确的发布时间。

## 9. 摄取算法

```text
1. Raw 已成功落盘并形成 Candidate
2. 对应 Provider/平台 Mapper 输出原子 Canonical
3. Pydantic + JSON Schema 校验，并保留 observed_fields/Source
4. ContentIngestionService 开启数据库短事务
5. 按平台身份锁定或 Upsert 当前内容；只更新 observed_fields 明确观察到的字段
6. 业务字段变化时新增 content_version
7. 指标变化或到达每日检查点时新增 metric_observation；指标允许真实下降
8. 更新 current 表的最新值、first_seen_at、last_seen_at
9. 写入 Candidate Ingestion 结果并更新发现来源聚合
10. 评论按同样规则 Upsert
11. 如需后续分析/监控，在同一事务插入内部幂等 Job
12. 更新 Scope/Run 统计并提交事务
```

数据库写失败时 Raw 已存在，Job 可以重试 Mapper 和 Ingestion，且在 Raw 完整性校验通过时不得再次调用 Provider。若此前网络结果未知且没有可用 Raw，是否重试必须按已批准的错误/重试策略决定，系统要记录潜在重复计费，不能承诺外部 Provider 一定未收费。

## 10. 当前值和历史

不把全部历史塞进一个 JSON。

```text
contents
→ 当前稳定字段

content_versions
→ 标题、正文、作者、URL、状态等变化

content_metric_observations
→ 点赞、评论、分享、转发、收藏、浏览/播放、弹幕、投币、下载等时间序列

comments
→ 当前评论

comment_versions
→ 评论文本、关系或状态变化

comment_metric_observations
→ 评论点赞、回复数等变化

comment_coverage_observations
→ 评论完整/部分/未请求/不可用及抓取数量历史
```

指标历史默认规则：

- 首次发现一定记录；
- 数值变化时记录；
- 即使无变化，每个 `Asia/Shanghai` 业务日最多记录一个检查点，并由数据库部分唯一约束兜底；
- 同一 Request 重试不得产生重复 Observation；
- 使用唯一键保证幂等。

## 11. 详情和评论刷新

Stage 7 的完整 Decision Pipeline 见 08。本文只保留基础原则：搜索先发现和观察，后续详情/评论是**条件动作**，不是每条内容都无脑调用。

### 11.1 内容详情

默认只在以下情况之一获取：

- 新内容且搜索字段不足；
- 搜索卡片缺少业务要求字段；
- Plan 明确配置的业务变化触发；
- 人工 Deep Collection；
- 到达明确的计划刷新检查点。

重复内容搜索字段足够、且需要监控的业务字段/指标没有变化时，不为了“刷新一下”重复请求详情。

### 11.2 评论默认触发

评论不再使用模糊“只对高价值内容抓取”作为基本资格。第一版默认：

```text
comment_trigger = new_or_comment_changed
```

- 新内容、可靠观察到评论数 > 0：按自适应策略抓；
- 可靠 `comment_count=0` 或评论关闭：直接跳过；
- 重复内容 `comment_count` 未变化：默认不抓；
- 点赞/分享/收藏/播放等变化但评论数未变化：默认不因此抓评论；
- 评论数增加：优先增量；没有稳定最新排序时受控部分刷新；
- 评论数减少：记录下降并受控刷新，非完整 coverage 不猜具体删除；
- 自动 Deep Collection 在 Stage 7 默认关闭。

默认 `full_fetch_threshold=50`、`sample_target=50`、`reply_target_per_root=5`；均由 08/Capability/Plan Contract 维护。

## 12. Provider Billing 与成本审计

每次 Provider Request Attempt 必须记录本次调用事实，逻辑 Provider Request 汇总全部 Attempt：

- Operation；
- 请求次数；
- 单价快照（Provider 已核验时）；
- 预计费用；
- Provider 权威返回的实际费用（若存在）；
- 是否重试；
- 是否可能重复计费；
- 是否由回补/Deep 触发。

这些字段用于执行审计和后续对账，不是当前预算额度。当前版本没有 Plan 请求次数上限、金额上限、评论预算、Budget Account、Reservation Ledger 或超预算发送门禁；历史预算结构由 `20260817_0015` 向前删除。Provider Billing/Pricing 仍必须保持事实完整：本地估算不能冒充 Provider `actual_cost`，网络结果未知时要记录潜在重复计费。

优化优先级：

1. 关键词发现优先于下游 enrichment；
2. 同一 Run 内跨词/重叠窗口按内容身份去重；
3. 搜索 Observation 先判断，避免所有内容都抓详情；
4. 可靠零评论直接跳过评论；
5. 重复且 comment_count 未变化不重抓评论；
6. 评论目标使用自适应 50/50/5，已返回整页全部保留；
7. 一级评论明确无回复时不请求二级；
8. 有已校验 Raw 时只回放，不再次调用 Provider；
9. 分页以 Provider 末页、可靠时间/已知 ID、技术安全页数、取消和错误等真实边界停止；
10. Deep/额外统计优先级最低，由明确业务触发。

未来如果业务需要 Budget/Cost Guard，只按 08 的扩展方向通过新的 L3 Change 重新设计，不在当前生产代码中保留 dormant Budget 接口。

## 13. 独立调试和测试

### 13.1 Provider Operation

输入：

```text
ProviderConfig + platform + operation + explicit parameters
```

输出：

```text
Raw Page + Pagination State + Request Metadata
```

验证方式：Fake HTTP Fixture、脱敏真实响应 Fixture、受控 Operation Probe。Probe 必须调用对应 Provider Adapter 的生产 Client/Operation，不能复制 endpoint、参数、分页或文件解析逻辑。

### 13.2 Mapper

```text
Fixture JSON
→ 生产 Mapper
→ Canonical JSON
→ Schema 校验
```

不需要启动前端、Scheduler 或数据库。

### 13.3 Ingestion

```text
Canonical Fixture
→ ContentIngestionService
→ 隔离 PostgreSQL
→ 查询 current/history/来源关联
```

### 13.4 Real Provider Probe

五个平台进入正式实现后，都必须保留由人工显式运行、复用生产实现的 Real Probe：

```text
显式 Probe 配置
→ 正式 Provider Config / Secret
→ 正式 Client / Operation / 分页
→ 逐请求 Raw
→ 正式 Mapper
→ Canonical Contract
→ XLSX 人工审阅派生物
```

真实 Credential/API Key 只从 Secret 边界取得，不硬编码、不进入 Git/日志/Raw/Canonical/XLSX/Job Payload/数据库明文。真实 Probe 默认关闭，不进入普通 CI，不写生产业务库；必须设置显式请求/分页上限，并在运行前核对预计费用。

### 13.5 Business Pipeline Probe

Stage 7 还必须提供完整业务 Probe：

```text
Search
→ previous state
→ 同一生产 Decision Service
→ Detail / Comment / Reply Actions
→ Raw / Canonical
→ decisions.jsonl
→ XLSX
```

生产 previous state 来自 PostgreSQL；Probe 可以读取上一轮 Probe Snapshot。连续两次运行必须能够证明“重复且 comment_count 未变化没有再次调用评论”“零评论短路”“评论增加进入增量/受控刷新”等业务省钱逻辑。

人工审阅 XLSX 的详细布局和使用方式由 [`../测试与调试说明.md`](../测试与调试说明.md) 维护。

## 15. 验收标准

采集模块完成必须证明：

- Provider Config 与平台路由使用稳定 `provider_config_id`；同一 Provider 可有多个配置实例、同一实例可被多个平台复用，禁用/未知/不支持组合关闭失败；
- `provider_configs` 不存在 API Key/Token/Cookie 等明文 Secret 列，`secret_ref` 路径校验和 Provider Base URL allowlist 有自动化测试；
- 五平台每个平台至少一组合法脱敏非空真实 Fixture；
- 每个平台分页第一页、下一页、末页、重复页、状态不推进测试；
- 五平台 Operation 与 08/平台文档批准的主链路一致，无静默 fallback；
- Provider Capability 只暴露真实支持的业务参数；
- Raw 文件不可覆盖、可解压、SHA-256 正确；
- Secret 脱敏测试；
- Canonical Schema 测试；
- 同一内容跨词/重叠窗口去重，但 Candidate 来源证据不丢失；
- 重复内容 comment_count 未变化不会再次请求评论；
- 可靠 comment_count=0/评论关闭不会请求评论；
- 自适应 50/50/5、整页保留、coverage/stop reason 语义正确；
- 内容字段变化和指标变化历史正确；
- 评论 root/parent 关系不被猜测；
- 同一逻辑 Provider Request 的多个 Attempt 都保留各自状态、Raw 和费用；
- 已校验 Raw 的取消/重试只做回放；网络结果未知时按策略重试并记录潜在重复计费；
- 每个 Candidate 可追溯到 Run、Scope、Attempt、Raw 和来源项；
- Operation Probe 和 Business Pipeline Probe 都复用生产实现；
- 五个平台正式 Operation 都有可由人工显式运行的 Real Probe，可配置真实 Provider URL、Secret 和已批准业务参数，并设置显式请求/分页上限；
- Real Probe 逐请求保存完整脱敏 Raw、运行正式 Mapper/Canonical 校验，并可生成不替代机器事实的 XLSX 人工审阅派生物；
- Provider Billing/预计费用与 Provider 权威实际费用在语义中明确区分；当前 API/前端不得暴露不存在的预算额度配置；
- 费用和 Run 统计可查询。
