# 采集系统与数据标准化

## 1. 目标

采集系统必须回答：

```text
为什么发起这次采集或导入？
用了哪些平台和关键词？
每个平台实际请求了哪些接口和分页参数？
实际 Provider 原始返回/文件输入是什么？
哪些内容被识别、去重和更新？
为什么某条内容继续/没有继续抓详情或评论？
哪条业务数据来自哪个原始请求或输入 Artifact？
失败后从哪里恢复？
本次调用花费多少？
```

如果这些问题只能靠猜日志或查看一大段业务代码，设计就是不合格的。

Stage 7 的五平台业务 Decision Pipeline、Provider Capability、首版 TikHub Operation Matrix、自适应评论、Deep Collection、Provider Billing/成本审计以及未来 Budget/Cost Guard 扩展方向统一见 [08-采集策略与平台能力.md](08-采集策略与平台能力.md)；面向开发/调试的具体平台抓取逻辑见 [`../collection/README.md`](../collection/README.md)。Stage 8 的 Excel 主入口、Processing / Import Batch 与调试入口可选写库见 [17-Stage8数据入口统一入库与业务前端实施.md](17-Stage8数据入口统一入库与业务前端实施.md)。本文保留 Provider/Raw/Mapper/Canonical/来源链等通用基础，不维护第二份平台 endpoint 表。

## 2. 采集策略

业务日、默认调度和日志显示时区固定为 `Asia/Shanghai`。第一版 `collection_plans.timezone` 也只能取该值；字段保留 IANA 时区名称，是为以后通过独立决策、迁移和 DST 测试开放其他调度时区，不表示当前可以任意配置。

### 2.1 主调度

```text
00:00 关键词滚动发现
06:00 关键词滚动发现
12:00 关键词滚动发现
18:00 关键词滚动发现
每天一次 最近 7 天回补
每周一次 可选深度回补
```

上述是 Collection 子系统的默认业务节奏，不表示第一版产品整体的数据入口优先级高于 Excel，也不表示所有 Provider 都有精确 6 小时时间过滤。每个平台按 Capability 使用真实支持的排序/时间过滤；Provider 最小时间窗大于调度周期时允许重叠，通过内容身份去重和 08 的 Decision Pipeline 避免重复详情/评论费用。用户配置的搜索时间范围小于调度周期时只 Warning，不阻止保存；Provider 不支持或参数非法才 Error。

### 2.2 发现与导入来源

| 来源 | 作用 | 默认频率 |
| --- | --- | --- |
| Excel 文件导入 | 第一版主要业务数据入口、历史/人工数据 | 人工 |
| 关键词搜索 | TikHub/其他 Collection 主发现通道 | 每 6 小时 |
| 已知话题 | 补充固定话题内容 | 每 6 小时或每日 |
| 已跟踪账号 | 品牌、竞品、KOL | 每 6 小时 |
| 热榜 | 发现突发事件和新词 | 每 6 小时，全局一次 |
| 搜索建议 | 扩展别名和相关词 | 每日 |

不同来源**不能绕过统一摄取直接写内容表**，但来源账本不强制伪装成同一种业务父级：

- Collection/HTTP/SDK 等外部发现链继续使用 `Run → Scope → Provider Request/Attempt → Raw → Candidate → Mapper → Canonical`；
- Stage 8A File Import 使用 `Input Artifact → ProcessingImportBatch → import-parent Provider Request/Attempt` 建立正式来源事实，然后把既有 Excel Reader/Mapper/关键词清洗/稳定身份去重产生的 Canonical 绑定到真实 Attempt/Artifact 后进入统一 Ingestion；
- Excel 不为满足 Collection 结构而制造虚假的 Run/Scope/Candidate。

## 3. Collection 与 Provider 执行记录

### 3.1 Plan：长期计划

保存：

- 名称；
- 是否启用；
- 调度；
- 目标平台；
- 选择的词包；
- 每个平台选择的具体 `provider_config_id`，以及该 `Provider + Platform` Capability 允许的业务搜索参数；
- 详情策略；
- 评论触发/深度/排序/二级回复策略；
- 创建人和更新时间。

Provider 配置实例与平台选择分离：同一种 Provider 可以存在多个配置实例/账号，一个配置实例也可以被多个平台引用；Plan 选择稳定 `provider_config_id`，而不是只保存一个无法区分账号的 `provider='tikhub'` 字符串。Provider Config 本身不绑定平台。

Plan 不保存某次执行时的最终关键词列表，也不保存 cursor/search_id/pageArea/API Key 等 Provider 技术状态或 Secret。Stage 7 的结构化平台策略由版本化 Pydantic Contract 定义。

### 3.2 Run：一次 Collection 执行

Run 是某次人工或定时触发的完整 Collection 执行记录。创建 scheduled Run 时冻结 `provider_config_id/provider/base_url/secret_ref` 身份、平台业务配置、`CollectionDecisionPolicyV1`、最终关键词以及 Job Deadline 的技术执行上限事实；后续修改/禁用 Provider Config 或 Plan 不改变已创建 Run 的非 Secret 执行语义。同一 `secret_ref` 指向的 Secret 文件内容允许合规轮换，Snapshot 从不保存 Secret 值。当前版本不把请求/金额预算写入 Run Snapshot。

Stage 8A `tikhub_test` 显式数据库模式也建立 `trigger_type=manual` 的正式 Collection Run/Scope；它不创建第二套 TikHub Batch。Excel File Import 则由 Processing / Import Batch 作为父事实，不制造 Collection Run。

概念示例：

```json
{
  "schema_version": "collection-run-config.v1",
  "plan_id": "plan_01",
  "trigger": "scheduler",
  "timezone": "Asia/Shanghai",
  "platform_keywords": {
    "xhs": ["爱玛", "爱玛电动车"],
    "dy": ["爱玛", "爱玛电动车"]
  },
  "platform_policies": {
    "xhs": {
      "provider_config_id": "provider_config_01",
      "provider": "tikhub",
      "search": {
        "sort": "latest",
        "published_within": "1d"
      },
      "comments": {
        "trigger": "new_or_comment_changed",
        "mode": "adaptive",
        "full_fetch_threshold": 50,
        "sample_target": 50,
        "reply_target_per_root": 5
      }
    }
  },
  "date_from": "2026-08-11T18:00:00+08:00",
  "date_to": "2026-08-12T18:00:00+08:00"
}
```

示例只说明 Snapshot 语义，不是 Pydantic/数据库字段事实；实际 Contract 建立后以机器 Contract 为准。Snapshot 不保存原始 API Key/Token；需要执行 Provider 时由稳定 `provider_config_id`/`secret_ref` 经服务端 Secret 边界解析。

### 3.3 Scope：Collection 最小独立执行单元

Scope 示例：

```text
xhs + keyword_search + 爱玛
dy  + keyword_search + 爱玛电动车
xhs + tracked_account + user_123
xhs + comments + note_456
```

每个 Scope 有独立状态、分页进度、统计和错误。一个 Scope 失败不能让其他平台和关键词全部丢失。File Import 不使用 Scope；其业务父级见 Blueprint 17 的 Processing / Import Batch。

### 3.4 Provider Request：一个可幂等的逻辑请求

Stage 8A 后，`ProviderRequestV1` 已从 Collection-only 最小一般化为**恰好一个来源父级**：

```text
Collection Request
→ run_id + scope_id
→ import_batch_id = null

File Import Request
→ import_batch_id
→ run_id = null
→ scope_id = null
```

数据库 `provider_requests` 同样通过外键、唯一约束与 exactly-one CHECK 保证 `scope_id` / `import_batch_id` 二选一；现有 Collection 历史仍保持 `scope_id != null`，没有重写历史 Revision。

Provider Request 由 Operation、脱敏后的稳定参数和分页状态计算 `request_fingerprint`；同一父级内的同一逻辑请求使用对应唯一约束实现幂等。保存的公共执行事实包括：

- `request_id`；
- `scope_id` 或 `import_batch_id`；
- `provider_config_id`（外部 Provider Collection 使用；File Import 不绑定外部 Provider Config）；
- Provider；
- Operation；
- 脱敏请求参数；
- 分页输入；
- 逻辑状态；
- 尝试次数；
- 累计费用；
- 创建和完成时间。

Provider Request 不是一条真实网络调用记录，因此不会因为重试而覆盖 HTTP 状态、TikHub request ID 或 Raw。Stage 5C 已发布的 Request Schema 暂保留 `provider` 字段兼容；Stage 8A 新增 `import_batch_id` 但保持原 Collection 构造方式兼容。稳定 `provider_config_id` 用于 Provider 路由和审计，不代表当前存在预算账户。

### 3.5 Provider Request Attempt：一次真实 Provider 执行

每一次真实 Provider 执行都生成独立 Attempt。HTTP/SDK Provider 的一次外部发送是一条 Attempt；文件/历史导入的一次受控读取同样以非计费 Attempt 留下可追溯执行事实。HTTP 状态、外部 request ID 和计费字段只在该传输/Provider 明确提供时填写：

- `attempt_id`；
- 所属 `request_id`；
- 尝试序号；
- 开始/结束时间；
- HTTP 状态；
- Provider external request ID；
- 计费币种、计费单位、单价快照、预计/实际费用；
- `billing_status` 和是否可能重复计费；
- 本次 Raw Artifact ID；
- 错误分类和安全摘要。

同一逻辑请求可能有多个 Attempt。所有 Attempt 都保留，逻辑请求汇总最终状态和累计费用。File Import Attempt 的 `raw_artifact_id` 真实指向输入 Excel Artifact，不伪造 HTTP Raw，也不降低 Content Owner 的 Attempt↔Artifact 来源校验。

### 3.6 Candidate：Collection 外部发现项

Candidate 表示外部 Collection Provider 的某条来源项在某次 Attempt 的某个 Raw 中被看到。它不是最终内容副本，也不能只用首末 Run 聚合替代。

```text
Provider Raw item
→ 先建立 Candidate（Attempt + 稳定 item_locator）
→ Mapper / Canonical 校验
→ 形成/读取当前 Observation
→ previous/current 比较与 Decision
→ Ingestion / 后续 durable action
```

Collection Candidate 只直接保存实际 Provider Request Attempt、`item_kind`（content/comment）、`external_item_id`、稳定 `item_locator` 和发现时间；其 Run、Scope、Raw Artifact、平台及来源类型/值通过受约束链 `Candidate → Attempt → Provider Request → Scope → Run` 与 `Attempt.raw_artifact_id` 推导。Candidate 在 Mapper 前建立，因此缺 ID、Contract invalid、内容/root 身份不一致等失败也能追加 `invalid/failed` Ingestion ledger。

**File Import 不创建虚假的 Collection Candidate。** Excel 的逐行定位保留在 Canonical `source.item_locator`，来源父事实通过 `Input Artifact → ProcessingImportBatch → Provider Request/Attempt` 审计；进入 Content Owner 前仍必须具备合法 Attempt/Artifact 引用。

“重复内容”不删除来源证据；它只影响是否创建第二条业务 Current（不允许）以及是否继续花钱请求详情/评论。

## 4. 关键词和词包

关键词必须以单个词为最小单位保存在数据库，不使用运行时文件驱动正式 Collection 采集。

```text
keyword_packs
keywords
keyword_pack_items
collection_plan_keyword_packs
```

规则：

1. 同一个规范化关键词只保存一份；
2. 词包和关键词使用关联表，不保存逗号分隔字符串；
3. 关键词可以设置平台、启用状态、优先级和备注；
4. 保存 Plan 时校验所有目标平台至少有一个可用关键词；
5. 创建 Run 时把最终关键词按平台展开并冻结；
6. Worker 只消费 Run Snapshot，不读取词包猜测默认词；
7. 文件只用于批量导入、导出或初始化 Seed；`imports_test` 的人工关键词包属于离线调试/处理输入，不替代正式数据库词包。

## 5. Provider Adapter 与 TikHub 参考实现

系统允许 TikHub、平台官方 API、Apify、自建采集器、文件/历史导入等来源在 Canonical 之前各自适配。HTTP/SDK 外部 Provider 使用正式 Raw/Candidate 链；文件导入使用输入 Artifact + ProcessingImportBatch + import-parent Provider Request/Attempt。无论来源为何，最终都只能经 Mapper/Canonical 与统一 Ingestion 进入 Content Owner，任何 Provider/调试入口都不能直接写内容表。

当前五个平台默认 Provider 均为 TikHub，但 Provider 与 Platform 解耦：以后可以单独替换某个平台 Provider，而不改写 Canonical/Ingestion/数据库。

### 5.1 Provider Config 与平台路由

Stage 7 的 Provider 配置模型固定为两层：

```text
Provider Config 实例
  ├─ provider_config_id（稳定 UUID）
  ├─ provider（例如 tikhub）
  ├─ display_name
  ├─ base_url
  ├─ secret_ref
  └─ enabled
        ↓
平台 / Plan 选择具体 provider_config_id
        ↓
Provider Registry 校验 provider + base_url
        ↓
Provider + Platform Capability
        ↓
Operation
```

规则：

1. 同一种 Provider 可以存在多个配置实例/账号，例如主 TikHub、备用 TikHub；配置实例用稳定 UUID 区分，显示名称可修改但不能靠名称作为业务外键；
2. Provider Config 不绑定平台；同一个配置实例可被多个平台引用，不同平台也可选择不同 Provider Config；
3. `base_url` 是非 Secret 配置，但必须使用 HTTPS，并在运行时经过已注册 Provider Adapter 的出站 allowlist；“前端可配置 URL”不等于允许任意 SSRF 目标；
4. `secret_ref` 只保存服务端 Secret 的安全相对引用，数据库、Contract、日志、Raw、Job Payload 和读取 API 都不保存/回显原始 API Key、Token、Cookie；
5. 当前机器 Registry 已接线 `tikhub + xhs/douyin/weibo/bilibili/kuaishou` 五个平台，且只允许受批准的 TikHub HTTPS Origin；新增 Provider/Platform 组合仍必须先具备 Operation/Fixture/Mapper/Capability 与纵切测试；
6. Provider 类型是配置实例稳定身份的一部分。需要从 TikHub 改为另一个 Provider 时创建新的 Provider Config，并让 Plan/平台显式改引用，不能原地把旧 UUID 改成另一 Provider 后污染历史来源/审计；
7. 后续 Stage 8 可以提供 Provider 管理页面和 Secret 写入接口，但 Secret 写入必须进入正式 SecretStore/SecretService；读取 Provider Config 只返回非敏感配置和“已配置”状态，绝不回显原始 Secret。

当前机器 Contract 为 `ProviderConfigV1` 与 `ProviderPlatformRouteV1`；`provider_configs` 为 `system` Owner。Plan/Run Snapshot 与 Provider Request 来源链以 `provider_config_id` 作为稳定配置身份；当前不存在预算 Ledger。

TikHub 目标目录：

```text
adapters/providers/tikhub/
├─ client.py
├─ config.py
├─ errors.py
├─ models.py
├─ pricing.py
├─ operations/
│  ├─ xiaohongshu.py
│  ├─ douyin.py
│  ├─ kuaishou.py
│  ├─ weibo.py
│  └─ bilibili.py
└─ mappers/
   ├─ xiaohongshu.py
   ├─ douyin.py
   ├─ kuaishou.py
   ├─ weibo.py
   └─ bilibili.py
```

当前机器已具备小红书、抖音、微博、B站、快手五个平台的 TikHub Operation/Mapper/Capability/Registry；各平台主链和增量评论能力差异以 08 与当前 Contract/Fixture/Test 为准。

### 5.2 Client 只负责通用 HTTP

`client.py` 负责 URL/认证、超时、连接池、Provider 级限流、一次传输、公共响应包、request ID、计费元数据、日志上下文和 Raw Request/Response Envelope。Client 不知道小红书的 cursor，也不解析内容字段。单个 Attempt 内禁止隐藏网络自动重试。

### 5.3 Operation 负责平台调用规则

Operation 负责 endpoint、规范化业务参数 → Provider 参数、分页状态、详情/评论调用组合、平台停止条件与 Raw Page。业务 Service 不能直接拼 endpoint 或解析 cursor。TikHub App/Web/V2/V3 是 Provider 内部 API family，不是独立 Provider；每个业务 Operation 使用 08 批准的主 endpoint，不做通用静默 fallback。

### 5.4 Capability 负责“可配置什么”

每个 `Provider + Platform + Business Operation` 声明真实能力，至少覆盖排序、时间过滤、内容类型、comment_count/评论许可观察、评论排序、二级评论和增量评论能力。前端只展示 Capability 支持的业务语义，不暴露 cursor/search_id/pageArea/API Key 等第三方技术状态。完整 Capability 语义见 08。

### 5.5 Mapper 只负责翻译事实

Mapper 输入：

```text
Raw Page / Raw Item 或受控文件行
+ SourceObservation
+ 明确的来源上下文
```

Mapper 输出：

```text
CanonicalContentV1
CanonicalCommentV1
MetricObservationV1
```

Mapper 禁止读数据库、发 HTTP、写业务数据库、计算告警、调用模型或猜测无法确认的发布时间/作者/父评论/业务分类。新平台 Mapper 只有在合法脱敏真实 Fixture/明确上下文证明字段后才能建立对应映射；官方 endpoint 文档不能替代真实响应 Fixture。

## 6. Raw 与输入 Artifact 原始证据

### 6.1 Collection Provider Raw

每个成功返回并完成校验的 HTTP/SDK Provider Request Attempt 必须保存一个不可变 gzip JSON 文件。失败响应如果包含可安全保存的响应体，也保存错误 Envelope。

文件路径：

```text
/data/AIMA_UGC/runtime/data/raw/
  <provider>/
    <platform>/
      2026/08/12/
        <run_id>/
          <scope_id>/
            <attempt_id>.json.gz
```

不使用固定 `latest.json.gz` 覆盖历史。需要“最新”时由数据库查询 Provider Request 或生成可重建索引。

Raw Envelope 的 `run_id/scope_id` 仍是 Collection-only 语义。Stage 8A 不把 Excel 伪装成 HTTP RawEnvelope；File Import 的原始证据是由 `ArtifactService` 保存的输入 Excel Artifact，并由 ProcessingImportBatch 与非计费 Import Attempt 真实引用。

### 6.2 Raw Envelope 示例

```json
{
  "schema_version": "provider-response.v1",
  "provider": "tikhub",
  "platform": "xhs",
  "operation": "search_notes",
  "request_id": "req_01",
  "attempt_id": "attempt_01",
  "run_id": "run_01",
  "scope_id": "scope_01",
  "requested_at": "2026-08-12T10:00:01Z",
  "completed_at": "2026-08-12T10:00:02Z",
  "request": {
    "method": "GET",
    "path": "/api/v1/xiaohongshu/app_v2/search_notes",
    "params": {"keyword": "爱玛", "page": 1}
  },
  "response": {"status_code": 200, "body": {}}
}
```

Collection Raw 写入步骤：

```text
递归脱敏
→ JSON 序列化校验
→ ArtifactService 创建 pending 元数据并分配 storage_key
→ 写临时文件
→ flush + fsync
→ gzip 可读取校验
→ 计算 SHA-256
→ 原子 rename
→ ArtifactService/Repository 把元数据更新为 stored
→ Attempt 与业务短事务关联 Artifact，并更新为 linked
```

`ArtifactStore` 只完成按 `storage_key` 的字节写入和原子 rename，不写数据库状态；`ArtifactService` 和 Repository 才能推进 `pending/stored/linked`。任一步失败都保留可对账状态，不以删除证据作为失败恢复手段。禁止在 Raw/Input Artifact 元数据中保存 Authorization、Cookie、API Key、数据库密码、模型密钥和内部会话 Token。

## 7. 分页状态机

每个平台 Operation 必须把分页写成可测试状态机：

```text
初始状态
→ 构造请求
→ 保存 Raw
→ 提取结果和下一页状态
→ 去重
→ 判断停止
→ 下一页
```

统一停止条件：Provider 明确无下一页、当前页为空、下一 cursor/page 没有推进、页面内容完全重复、已连续越过可靠时间边界、任务被取消或达到技术安全页数上限。Provider 没有原生时间筛选时，不能凭想象加时间停止；触发安全页数上限时 Run 必须标记 `partial_success`，不能假装完整。

## 8. Canonical 数据契约

Canonical 是 AIMA 自己定义的理想业务语言，不由 TikHub 或任一平台当前响应反向决定。机器事实源固定在：

```text
backend/src/aima_ugc/contracts/canonical/
→ Pydantic 唯一手写事实源

contracts/canonical/*.schema.json
→ 确定性生成的 JSON Schema

contracts/canonical/examples/
→ 固定合法脱敏示例
```

写入使用原子 Observation：`CanonicalContentV1` 与 `CanonicalCommentV1`；读取、导出、AI 和页面使用以一条内容为根的 `CanonicalContentAggregateV1`。Mapper 只生成原子 Contract，不为凑出整帖树查询数据库。

### 8.1 内容与账号

内容身份固定为 `(platform, external_content_id)`，备用稳定 ID 放入 `alternate_ids`。内容可表达内容类型、标题、正文、稳定原文 URL、分享 URL、发布时间/来源更新时间、公开作者资料、媒体、话题、@提及、公开地点/IP 属地、状态和来源追溯。

帖子作者和评论者复用 `CanonicalAuthorV1`。Provider 明确公开提供时尽量保存主账号 ID、备用 ID、handle/账号名、显示昵称、主页 URL、头像 URL、简介、认证、公开地区及公开统计；缺失或不可靠时为 `null`，禁止猜测。认证 Secret 和敏感认证信息不进入 Canonical。

### 8.2 互动指标

`CanonicalMetricsV1` 可表达 like/comment/share/repost/favorite/view/play/danmaku/coin/download/reply 等公开指标。平台没有该概念或本次响应未提供时为 `null`；明确观察到零才写 `0`。多次采集允许指标上升或下降，不能使用 `max()` 覆盖真实平台校正。

### 8.3 评论关系

评论身份固定为 `(platform, external_content_id, external_comment_id)`；`root_comment_id` 表示线程根，`parent_comment_id` 表示直接回复对象。无法确认关系时保留 `null` 或进入聚合视图的 `unthreaded_comments`，禁止按数组位置猜父子关系。

### 8.4 稀疏 Observation

每个 Canonical Observation 都必须带 `observed_fields`，只声明本次来源真正观察到的可更新字段。字段未观察到时保留数据库已有更完整值；明确观察为 null 也必须符合该字段/Operation 可清空语义。

### 8.5 内容聚合与评论覆盖

`CanonicalContentAggregateV1` 是 Read Model/交换结构，不是数据库单行大 JSON。评论覆盖状态区分 `complete`、`partial`、`not_requested`、`unavailable`，并保留来源、数量、目标、观察时间和停止原因。`lineage` 从正式来源事实组装，不创建第二套来源真相。

### 8.6 时间规则

- API/Canonical 的时刻字段必须带时区；
- 数据库存 `timestamptz`；
- 无法可靠解析的发布时间不猜测；
- 禁止把采集/导入时间冒充发布时间。

## 9. 摄取算法

### 9.1 Collection / TikHub

```text
1. Provider Request/Attempt 建立
2. Raw 成功落盘
3. Raw item 建立 Candidate
4. Provider/平台 Mapper 输出 Canonical
5. Pydantic/Contract 校验并保留 observed_fields/Source
6. ContentIngestionService → Content Owner Repository
7. 按稳定身份 Upsert Current
8. 业务变化新增 Version；指标变化/检查点新增 Metric Observation
9. 写 Candidate Ingestion 结果
10. 评论按同样规则处理
11. Scope/Run/Job 在 Fencing 下推进
```

### 9.2 Stage 8A File Import

```text
1. 既有 Excel Reader/Mapper → Canonical
2. 关键词相关性清洗 → 稳定身份批次去重 → UnifiedContentRecordV1
3. 显式 DB 阶段把原始 XLSX 保存为 Input Artifact
4. 创建 ProcessingImportBatch
5. 每个平台创建 import-parent Provider Request + non-billable Attempt
6. Attempt.raw_artifact_id 真实引用 Input Artifact
7. 将已有 Canonical Source 绑定到真实 Request/Attempt/Artifact，保留稳定 item_locator
8. ContentIngestionService → PostgresCompleteContentRepository → PostgresContentRepository
9. Batch 标记 succeeded/failed 并保存最小统计/安全错误摘要
```

File Import 不复制 Mapper、不创建 ExcelDatabaseWriter、不直接 SQL，也不创建虚假的 Collection Candidate。

数据库写失败时文件证据仍存在；业务写事务回滚后可重试。最终业务幂等依赖 Content Owner 的稳定身份/唯一约束，不以批次内去重替代数据库去重。

## 10. 当前值和历史

不把全部历史塞进一个 JSON。Content/Comment 保持 Current + Version + Metric Observation + Coverage 结构。指标首次发现、数值变化和每日无变化 Checkpoint 按现有 Content Owner 规则记录；同一内容从 Excel 与 TikHub 多次观察时收敛到同一个 Current，但不同合法 Attempt/Artifact 来源与 Version/Metric 历史不会因此丢失。

## 11. 详情和评论刷新

Stage 7 的完整 Decision Pipeline 见 08。本文只保留基础原则：搜索先发现和观察，后续详情/评论是条件动作，不是每条内容都无脑调用。

### 11.1 内容详情

默认只在新内容且搜索字段不足、搜索卡片缺少业务要求字段、Plan 明确变化触发、人工 Deep Collection 或到达计划刷新检查点时获取。重复内容字段足够且业务字段/指标没有变化时，不为“刷新一下”重复请求详情。

### 11.2 评论默认触发

第一版默认 `comment_trigger = new_or_comment_changed`：可靠零评论短路；重复且 comment_count 未变化默认不抓；评论变化按 Capability 做增量/受控刷新。默认 `full_fetch_threshold=50`、`sample_target=50`、`reply_target_per_root=5`；完整语义由 08/Capability/Plan Contract 维护。

## 12. Provider Billing 与成本审计

每次外部 Provider Request Attempt 必须记录 Operation、请求次数、单价/预计/实际费用事实、重试与潜在重复计费。File Import Attempt 为 `not_billable`。这些字段用于执行审计和后续对账，不是当前预算额度。当前没有 Plan 请求/金额预算、Budget Account、Reservation Ledger 或超预算发送门禁；未来需要预算能力必须通过新的 L3 Change。

## 15. 验收标准

采集/导入基础必须证明：

- Provider Config 与平台路由使用稳定 `provider_config_id`；
- Secret 不进入数据库明文、日志、Raw、Canonical 或生成物；
- 五平台正式 Collection 保持合法真实 Fixture、分页、Capability、Operation 与 Mapper 测试；
- Collection Raw 不可覆盖、可校验，Candidate-before-Mapper 来源链完整；
- File Import 使用真实 Input Artifact + ProcessingImportBatch + import-parent Request/Attempt，不伪造 Collection Run/Scope/Candidate；
- Canonical 后只有一套 ContentIngestionService/Content Owner 写入；
- 同一内容跨词、跨批次、跨 Excel/TikHub 收敛为一个 Current，同时来源/Version/Metric 历史不丢；
- `imports_test` / `tikhub_test` 默认 file-only，数据库模式必须显式 opt-in；
- DB 不可用/Schema 不满足时明确失败，不自动 Docker/Migration，不把 file-only 冒充 DB 成功；
- tikhub_test DB 模式一次外部请求只发送一次，不从导出 JSONL 建平行 Writer；
- DB 阶段失败后可幂等重试，不制造第二条业务 Current；
- 所有 PostgreSQL 集成使用真实 PostgreSQL 18；
- Provider Billing/实际费用和本地估算语义明确区分；当前 API/前端不得暴露不存在的预算额度配置。
