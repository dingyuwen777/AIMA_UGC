# 采集系统与数据标准化

这篇文档只讲长期不容易变化的主链：**不同来源的数据，怎样变成同一套业务数据，同时保留来源证据。**

具体 TikHub 响应、接口选型、Scheduler 恢复、Excel 导入步骤见 [`../appendix/README.md`](../appendix/README.md)。

## 1. 为什么不能让每个平台直接写数据库

假设五个平台各写一套：

```text
小红书 JSON → 小红书 SQL
抖音 JSON   → 抖音 SQL
微博 JSON   → 微博 SQL
……
```

短期看很快，长期会出现：

- 同一个业务字段有五种解释；
- 去重逻辑复制五份；
- 第三方字段一改，数据库/API/前端一起受影响；
- Excel 导入又要写第六套；
- 无法稳定回放历史 Raw。

所以系统把“外部数据怎么来”和“业务数据怎么存”分开。

## 2. 当前稳定主链

### 2.1 正式 Provider 采集

```text
Plan / Run / Scope
→ Provider Request / Attempt
→ Raw Artifact
→ Candidate
→ Mapper
→ Canonical
→ Relevance
→ Ingestion Service
→ Content Owner Repository
→ PostgreSQL
```

### 2.2 Excel File Import

```text
Input Artifact
→ Processing Import Batch
→ import-parent Provider Request / Attempt
→ Reader / Mapper
→ Canonical
→ Relevance
→ 同一个 Ingestion / Content Owner
→ PostgreSQL
```

两条链在 Canonical 之前允许不同，在 Canonical 之后共享业务语义。

Excel 不伪造 Collection Run/Scope/Candidate；TikHub 也不通过 Excel/JSONL 二次回灌来假装正式来源。

## 3. 每一层为什么存在

### 3.1 Provider Adapter / Operation

负责把业务动作翻译成第三方调用，例如：

```text
关键词搜索
内容详情
一级评论
二级回复
```

它知道 TikHub endpoint、分页和 Provider 私有参数，但不知道 `contents` 表怎么写。

### 3.2 Raw Artifact

保存外部 Provider 当时实际返回的原始证据。

关键规则：

- 先保存 Raw，再 Mapper；
- Raw 不可被后续业务逻辑改写；
- 已有完整 Raw 时优先 replay，不重复调用 Provider；
- Raw 不等于业务 Current。

### 3.3 Candidate

Candidate 记录“某个 Raw 中的一项内容/评论被发现过”。

它在 Mapper 前建立，因此即使 Mapper 失败，也能回答：

> 哪次请求的哪一项数据没能进入业务系统？

File Import 没有真实 Collection Candidate，不为结构对称而伪造。

### 3.4 Mapper

Mapper 只做：

```text
Provider/File 私有结构
→ Canonical
```

Mapper 禁止：

- 查数据库；
- 发 HTTP；
- 判断业务去重；
- 做 AI 分类；
- 直接写内容表。

### 3.5 Canonical

Canonical 是平台无关业务语言。

当前写入原子契约：

```text
CanonicalContentV1
CanonicalCommentV1
```

完整查询/导出视图可使用 Aggregate/Read Model，但 Aggregate 不作为一个大 JSON 整体持久化。

Canonical 只保存外部可观察事实，不保存：

- AI 情感；
- AI 一级/二级标签；
- voice_type；
- 模型结果版本。

这些属于 Analysis。

### 3.6 Relevance

所有来源都在 Mapper 后、正式 Content Ingestion 前经过同一 Relevance 边界：

```text
Canonical
→ Relevance Service
→ Ingestion
```

这样 Excel 和 TikHub 不会各自维护一套关键词过滤。

AI V3 还有语义 relevance；最新业务相关性投影保存在 Content Current 上，默认业务查询过滤无关内容。

### 3.7 Ingestion / Content Owner

负责把 Canonical 变成数据库业务事实：

- 稳定身份去重；
- Current；
- Version；
- Metric Observation；
- 账号/评论关系；
- 来源账本；
- 字段 freshness。

一张业务表只有一个写 Owner。

## 4. 数据身份怎么理解

### 内容

核心稳定身份：

```text
(platform, external_content_id)
```

同一个帖子从 TikHub、Excel 或后续其他 Provider 再次出现，最终仍收敛到同一个 Content Current。

### 评论

评论在所属 Content 内使用稳定 external comment identity 收敛，并保留 root/parent 关系。

### Provider Request

Request 表示一个逻辑操作；Attempt 表示一次真实执行。

```text
同一个 Request
→ Attempt 1 失败/未知
→ Attempt 2 重试
```

失败 Attempt 不会被覆盖掉。

## 5. 为什么 Current、Version、Metric 要拆开

只保存最新值会丢历史；每次都复制整行又会产生大量无意义版本。

当前结构：

```text
Current
→ 页面/查询看到的最新状态

Version
→ 正文、标题、作者等业务版本变化

Metric Observation
→ 点赞、评论、播放等指标观察
```

例如：

```text
帖子正文没变，点赞从 100 变 120
→ Current 指标更新
→ 新 Metric Observation
→ 不需要复制一个正文 Version
```

如果正文 A → B → A，第三次仍是新版本，因为比较的是“当前业务 Hash”，不是“历史上是否出现过”。

## 6. 字段缺失不等于字段变成空

Provider 某次没返回一个字段，不代表这个字段真实变成 `null` 或 0。

因此 Current 保存字段观察时间（field freshness），只有当前来源明确观察到某字段时，才允许用更近的观察覆盖旧值。

这个机制对多 Provider、列表/详情不同字段完整度尤其重要。

## 7. 评论 Coverage 为什么单独保存

“抓了评论”不能等同于“评论抓全了”。

当前会保存内容级和 thread 级 Coverage，表达：

- 已抓多少；
- Provider 报告多少；
- 是否完整；
- 为什么停止；
- 某 root thread 的二级回复是否完整。

评论 target 是“还要不要继续请求下一页”的软目标；已经付费返回的一页数据应先完成 Mapper/Ingestion，再决定停止。

## 8. 关键词与 Relevance 的关系

关键词有两种不同用途，不应混为一个字段：

### Collection Keyword Pack

回答：

> 用什么词去发现外部内容？

### Global Relevance Keyword Pack

回答：

> 已经拿到的数据，哪些明显属于当前监测主题？

两者都存 PostgreSQL，并通过正式关系表管理；正式运行不依赖一个本地 txt 文件作为唯一业务事实。

## 9. 运行快照为什么重要

Plan/全局配置在任务执行期间可能被修改。

因此创建 Run/Import Job 时会冻结执行所需快照，例如：

- Provider Config 身份；
- 平台业务配置；
- 最终关键词；
- Relevance 配置版本；
- Decision Policy；
- 必要的 Deadline 技术上限。

快照不保存 Secret 值。

这样能回答：

> 这次任务到底按哪一版配置执行？

## 10. Provider 错误和重试

外部网络调用必须区分：

```text
确定没发出去 not_sent
发送结果未知 unknown
明确得到失败响应
成功并有 Raw
```

当前一个 Attempt 内不隐藏自动重发。真正重试会建立新 Attempt。

如果已经有完整且校验通过的 Raw：

```text
replay Raw
→ 禁止再次调用 Provider
```

详细恢复规则见 [`../appendix/Scheduler运行与恢复.md`](../appendix/Scheduler运行与恢复.md)。

## 11. Provider Billing 不是 Budget

Request/Attempt 会记录成本、价格快照、billing status、潜在重复计费等执行事实。

当前没有：

- Budget Account；
- Reservation Ledger；
- 请求次数硬预算；
- 金额硬预算；
- 发送前 Cost Guard。

如果以后需要预算控制，必须作为新的 L3 Change 设计，不能把成本审计字段误当预算系统。

## 13. 一个最小例子

TikHub 返回一条小红书帖子：

```text
Raw item
→ Candidate 记录“这次请求看到了它”
→ XHS Mapper 产出 Canonical(platform=xhs, external_content_id=abc123)
→ Relevance
→ Ingestion 查 (xhs, abc123)
→ 不存在：新建 Content/Version/Metric
→ 已存在：按 freshness/business hash/指标变化更新
```

如果明天同一条帖子从 Excel 又导入：

```text
Excel Row
→ Canonical(platform=xhs, external_content_id=abc123)
→ 同一个 Ingestion
→ 仍然是同一 Content Current
```

## 15. 不要做的事

- Provider 直接写业务表；
- Mapper 查数据库；
- 前端理解 TikHub 私有 JSON；
- Excel 导入再造一套内容去重 SQL；
- 把 AI 标签放进 Canonical；
- 为文件导入伪造不存在的 Run/Scope/Candidate；
- 有 Raw 可回放时再次付费请求 Provider；
- 用逗号字符串代替真实关联关系。
