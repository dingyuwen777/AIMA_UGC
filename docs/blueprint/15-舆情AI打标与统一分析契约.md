# 舆情 AI 打标与统一分析契约

## 1. 定位

本设计负责全平台通用的**内容 AI 打标**能力，不属于临时 P1 私有逻辑，也不属于某个 Provider/平台 Mapper。

长期调用方向：

```text
TikHub / 官方 API / Apify / 文件导入 / 未来其他 Provider
→ 各自 Mapper
→ CanonicalContentV1
→ Provider-neutral 内容记录 / Query Read Model
→ Analysis Service
→ SentimentClassifier Port
→ LLM Adapter
→ ContentLabelAnalysisV1
→ Analysis Repository / 统一 JSONL / Excel / 页面 / 报告
```

任何平台都复用同一套标签 Contract、Prompt、校验和 Analysis Service；只有 Provider → Canonical 的转换不同。

P1 的无数据库实现只是这套长期能力的第一个独立验证入口。以后正式系统从 PostgreSQL 读取内容后，仍调用同一 Analysis Service，不能为 TikHub、文件导入或不同平台各写一套提示词/标签逻辑。

## 2. Canonical 不增加 AI 标签

`CanonicalContentV1` 表示平台/Provider 实际观察到的内容事实，例如标题、正文、作者、发布时间和互动指标。AI 情感和主题标签是**派生分析事实**，不能混入 Canonical 的 `observed_fields`，也不能让 Mapper 伪装成 Provider 原始字段。

因此跨平台统一结构分两层：

```text
CanonicalContentV1
= 外部可观察事实

UnifiedContentRecordV1
= CanonicalContentV1 + 处理元数据 + 可空 Analysis
```

P1 目标 JSONL 记录概念结构：

```json
{
  "schema_version": "content-record.v1",
  "content": {
    "schema_version": "content.v1"
  },
  "matched_keywords": ["爱玛"],
  "analysis": null
}
```

打标成功后仍是同一条记录，只填充 `analysis`：

```json
{
  "schema_version": "content-record.v1",
  "content": {
    "schema_version": "content.v1"
  },
  "matched_keywords": ["爱玛"],
  "analysis": {
    "schema_version": "content-labeling.v1",
    "sentiment": "positive",
    "primary_label": "产品反馈",
    "secondary_label": "使用体验",
    "taxonomy_version": "aima-content-taxonomy.v1",
    "prompt_version": "content-labeling.v1",
    "prompt_sha256": "...",
    "model_provider": "...",
    "model": "...",
    "input_hash": "...",
    "analyzed_at": "2026-08-18T10:00:00Z"
  }
}
```

`UnifiedContentRecordV1` 是 Provider-neutral 的处理/交换记录，不要求数据库把整条记录作为一个巨大 JSON 持久化。

## 3. 模型只接收三个业务字段

每条内容发送给 LLM 的**业务输入只能包含**：

```text
title
text
author.display_name
```

不得把以下内容发送给模型，除非未来通过独立业务决定修改 Contract：

- 平台内容 ID；
- 原文 URL；
- 点赞/评论/转发/粉丝等指标；
- Provider 名称；
- 命中关键词；
- 源 Excel 的“全文情感”；
- Raw 定位；
- 其他 Provider 私有字段。

字段缺失时必须显式填充空字符串，而不是省略或发送 Python/JSON `null`：

```text
title = content.title or ""
text = content.text or ""
author_display_name = content.author.display_name if available else ""
```

批量请求为了把返回值与原记录对应，可以增加**临时顺序号** `item_no`；它只用于协议配对，不是业务输入字段，也不得使用平台 ID/作者 ID 代替。

## 4. 模型输出必须是闭集标签

模型不得自由发明标签、同义词、英文别名或额外类别。

每条成功结果必须且只能选择：

```text
1 个情感标签
1 个一级标签
1 个二级标签
```

一级标签与二级标签必须满足本文固定父子映射。任何不在闭集中的值、父子不匹配、缺失、多值输出都视为结构化结果失败，代码不能“猜一个最接近的值”替模型修正。

首版不要求模型输出自由文本“理由”，避免把不可约束的长文本混入核心标签 Contract。调优和人工评估需要解释时，应使用独立受控 Probe 输出，不改变正式标签字段。

## 5. 情感标签

闭集：

```text
正面
中性
负面
混合
```

机器 Contract 推荐使用稳定代码值：

```text
positive
neutral
negative
mixed
```

Excel/页面显示中文。

### 5.1 正面

对爱玛品牌、产品、服务、价格政策、渠道、活动或营销内容存在明确认可、满意、推荐、支持、表扬或积极体验。

典型证据：

- 明确称赞质量、续航、设计、骑行体验；
- 表扬门店/售后服务；
- 认可价格、补贴或活动；
- 明确推荐爱玛或表达购买满意。

### 5.2 中性

仅陈述事实、新闻、活动、配置、价格、政策或客观信息，没有对爱玛表达可识别的正负态度；信息不足无法判断时也使用中性，而不是凭语气词猜测。

### 5.3 负面

对爱玛存在明确投诉、批评、质疑、不满、失望、风险指控或负面使用/服务体验。

典型证据：

- 产品故障、续航/耐用性差；
- 售后不处理、门店服务差；
- 价格过高、政策不合理；
- 虚假宣传、失信等品牌质疑。

### 5.4 混合

同一条内容中，对**爱玛本身**同时存在有实质信息量的正面和负面评价，且任何一方都不能视为无关或轻微修饰。

例如：

```text
“车骑起来挺舒服，但售后处理问题太慢。”
```

如果负面描述针对竞品、正面描述针对爱玛，则仍按爱玛态度判断，不因为全文同时有正负词就标“混合”。

## 6. 一级/二级标签闭集

首版 taxonomy 版本：

```text
aima-content-taxonomy.v1
```

### 6.1 品牌形象

| 二级标签 | 判断标准 |
| --- | --- |
| 正面形象 | 主体是对爱玛整体品牌印象、信誉、可靠性、信任度、行业地位等的积极评价，而不是某个具体产品/服务问题。 |
| 负面形象 | 主体是对爱玛整体品牌信誉、诚信、可信度、虚假宣传、失信等的消极评价，而不是某个具体业务问题。 |
| 中性形象 | 主体是对爱玛品牌整体的客观介绍、品牌信息或无明显倾向描述，且没有更具体的产品/服务/价格/渠道/活动主题可归类。 |

### 6.2 产品反馈

| 二级标签 | 判断标准 |
| --- | --- |
| 性能/质量问题 | 涉及故障、续航、耐用性、电池/电机/刹车等性能与质量异常、损坏、可靠性问题。只要核心是“产品哪里坏/不达预期”，优先此类。 |
| 功能/设计建议 | 对功能、配置、外观、结构、交互、储物、智能化等提出改进建议、需求或设计评价，核心是“应该怎么改/设计如何”。 |
| 使用体验 | 对购买后实际骑行、舒适度、操控、便利性、空间、日常使用等体验的评价，但没有明确聚焦故障/质量问题或具体改进建议。 |

### 6.3 服务反馈

| 二级标签 | 判断标准 |
| --- | --- |
| 售后问题 | 涉及维修、保修、客服响应、退换货、投诉处理、配件等待等购买后的售后服务问题。 |
| 门店服务 | 核心评价线下人员态度、接待、解释、办理、服务规范等“服务质量”，不以购买渠道流程本身为核心。 |
| 服务表扬 | 对客服、售后、维修人员、门店人员等服务行为表达明确感谢、认可或表扬。 |

### 6.4 价格与政策

| 二级标签 | 判断标准 |
| --- | --- |
| 价格评价 | 对价格高低、贵/便宜、性价比、定价合理性、价格差异等直接评价。 |
| 促销/补贴政策 | 涉及优惠券、折扣、补贴、国补、以旧换新、赠品、促销规则或领取/核销政策的评价。出现具体促销/补贴机制时优先于“价格评价”。 |

### 6.5 渠道与销售

| 二级标签 | 判断标准 |
| --- | --- |
| 线上购买体验 | 对电商平台、品牌线上商城、直播带货、线上下单/支付/配送等购买渠道与流程的反馈。 |
| 线下门店体验 | 对到店看车、试驾、报价、库存、下单、提车等线下购买流程的反馈。若重点是人员服务态度而非购买流程，归“服务反馈/门店服务”。 |

### 6.6 品牌活动

| 二级标签 | 判断标准 |
| --- | --- |
| 活动反馈 | 对品牌举办/参与的发布会、赛事、线下活动、联名活动、用户活动等本身的反馈。 |
| 营销内容评价 | 对广告、代言人、宣传片、直播内容、社媒传播、营销文案、传播策略等内容营销的评价。 |

### 6.7 其他

| 二级标签 | 判断标准 |
| --- | --- |
| 竞品对比 | 内容核心是把爱玛与雅迪、九号、小牛等其他品牌进行明确比较，并以品牌/产品对比作为主要表达目的。若只是顺带提及竞品而核心是具体质量/服务问题，优先具体业务标签。 |
| 无明确分类 | 内容与爱玛相关，但按现有 taxonomy 无法稳定归入以上类别，或信息过少不能确定主题。它是最后兜底，不得因为模型犹豫就优先使用。 |

## 7. 一级/二级严格父子映射

唯一合法映射：

```text
品牌形象
├─ 正面形象
├─ 负面形象
└─ 中性形象

产品反馈
├─ 性能/质量问题
├─ 功能/设计建议
└─ 使用体验

服务反馈
├─ 售后问题
├─ 门店服务
└─ 服务表扬

价格与政策
├─ 价格评价
└─ 促销/补贴政策

渠道与销售
├─ 线上购买体验
└─ 线下门店体验

品牌活动
├─ 活动反馈
└─ 营销内容评价

其他
├─ 竞品对比
└─ 无明确分类
```

代码必须先校验二级标签属于所选一级标签，不能只验证两个字符串分别合法。

## 8. 主题选择优先级

一条帖子首版只选择**一个主一级标签 + 一个主二级标签**。

当内容同时包含多个主题时：

1. **具体业务主题优先于泛品牌形象**：明确产品、服务、价格、渠道、活动时，不因为出现“爱玛不错/爱玛不行”就归品牌形象；
2. **核心诉求优先**：投诉/建议/购买体验的主要篇幅与核心诉求优先于顺带提及；
3. 性能故障/质量异常优先于一般使用体验；
4. 明确促销、补贴、以旧换新规则优先于一般价格评价；
5. 售后维修/退换优先“售后问题”；线下人员服务态度优先“门店服务”；看车/报价/下单/提车流程优先“线下门店体验”；
6. 竞品对比只有在“比较”本身是主要表达目的时使用；
7. “品牌形象”仅用于整体信誉/品牌印象为核心、且没有更具体业务主题的内容；
8. `其他/无明确分类` 只能最后兜底。

如果多个具体主题信息量接近，选择最能代表作者核心结论或问题诉求的一项，不输出多个标签。

## 9. Prompt 必须是可编辑 Markdown 文件

正式实现时必须建立一个人类可直接修改和调优的运行时 Prompt 文件：

```text
backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v1.md
```

不把完整 Prompt 硬编码在 Python 字符串中。

Prompt 文件至少包括：

```text
角色与任务
输入字段说明
情感标签及判断标准
一级/二级标签闭集
严格父子映射
主题选择优先级
缺失字段规则
输出 JSON Schema/示例
禁止事项
```

建议文件开头使用简单、可解析的元信息：

```markdown
<!-- prompt_version: content-labeling.v1 -->
<!-- taxonomy_version: aima-content-taxonomy.v1 -->
```

运行时加载 Markdown 原文并计算：

```text
prompt_sha256
```

分析幂等键必须绑定 Prompt 实际内容 Hash，而不是只相信文件名/手工版本号。这样用户直接修改 Markdown 调优后，即使忘记改版本字符串，旧分析缓存也不会被错误复用。

Prompt 的标签定义必须与机器 Contract 的闭集一致。Prompt 修改不能新增 Contract 未声明标签；真正新增/删除/改名标签属于 taxonomy/Contract 变化，必须走独立设计与兼容门禁。

## 10. 模型请求格式

单条业务输入概念：

```json
{
  "title": "...",
  "text": "...",
  "author_display_name": "..."
}
```

批量时允许：

```json
{
  "items": [
    {
      "item_no": 1,
      "title": "...",
      "text": "...",
      "author_display_name": "..."
    }
  ]
}
```

`item_no` 只是本次请求内顺序号。

模型成功输出只允许：

```json
{
  "items": [
    {
      "item_no": 1,
      "sentiment": "positive",
      "primary_label": "产品反馈",
      "secondary_label": "使用体验"
    }
  ]
}
```

模型不负责返回 `model`、`prompt_version`、`prompt_sha256`、`input_hash`、`analyzed_at`；这些由程序根据真实运行事实补充，防止模型伪造元数据。

## 11. 输入 Hash 与重新打标

`input_hash` 只根据**实际发送给模型的三个业务字段**计算，建议使用确定性 JSON 后 SHA-256：

```text
title
author_display_name
text
```

分析身份至少绑定：

```text
content stable identity
+ input_hash
+ taxonomy_version
+ prompt_sha256
+ model provider/model
```

以下任一变化都必须形成新的分析结果而不是复用旧标签：

- title/text/author.display_name 变化；
- Prompt Markdown 内容变化；
- taxonomy 版本变化；
- 模型配置变化。

## 12. P1 写回同一 JSONL 的规则

P1 中 `deduplicated/contents.jsonl` 每行使用 `UnifiedContentRecordV1`，`analysis` 初始为 `null`。

`label_sentiment()`：

1. 顺序读取 `deduplicated/contents.jsonl`；
2. 只构造三个业务输入字段；
3. 已存在且分析 identity 完全匹配的 `analysis` 直接跳过；
4. 新成功结果先追加到：

```text
analysis/checkpoints.jsonl
```

并 flush；
5. 按受控批次把成功结果合并到 `deduplicated/contents.jsonl.tmp`；
6. 完整写出、flush/fsync 后原子 replace：

```text
deduplicated/contents.jsonl.tmp
→ deduplicated/contents.jsonl
```

7. 崩溃恢复时先读取 checkpoint，避免重复已成功付费调用，再重建/补写源 JSONL。

因此**打标完成后分析结果回写到原 `deduplicated/contents.jsonl` 本身**；`analysis/checkpoints.jsonl` 只是恢复/审计辅助，不是下游业务事实源。

## 13. Excel 导出闭环

共享 Exporter 的默认最终输入只需要：

```text
deduplicated/contents.jsonl
```

其中 `analysis` 已被填充。

```text
deduplicated/contents.jsonl
→ UnifiedDataExcelV1
→ shared Excel exporter
→ labeled_data.xlsx
```

可选 raw Excel 也读同一文件，但在导出模式中忽略/留空 `analysis` 列：

```text
deduplicated/contents.jsonl
→ shared Excel exporter(include_analysis=False)
→ raw_data.xlsx
```

这样 raw/labeled 不需要两份业务 JSONL，也不需要在 Excel 与 JSONL 之间反复转换。

## 14. 数据库长期落点

未来正式进入 PostgreSQL 时，**不把 `UnifiedContentRecordV1` 整体塞进一列 JSONB**。

写入拆分为两个 Owner：

```text
record.content
→ ContentIngestionService
→ Content Owner Repository
→ contents / content_versions / metrics / ...

record.analysis
→ AnalysisIngestionService
→ Analysis Owner Repository
→ analysis_runs / content_analysis_results
```

`content_analysis_results` 至少需要能够稳定表达：

```text
content_id
content_version / input_hash 绑定
sentiment
primary_label
secondary_label
taxonomy_version
prompt_version
prompt_sha256
model_provider
model
analyzed_at
analysis_run_id
```

具体 DDL、唯一约束和 Migration 在正式 Analysis 数据库阶段通过独立 L3 Change 冻结；P1 无数据库阶段不提前添加 Migration。

数据库中 AI 标签仍由 Analysis 模块拥有，不能为了页面查询方便直接增加到 `contents` 表并由 Content Owner 写入。

## 15. 平台通用性

未来不论数据来自：

```text
小红书
抖音
微博
B站
快手
Excel 文件导入
其他 Provider
```

只要已经形成同一 Canonical/Read Model，都调用同一：

```text
build_content_label_input()
→ ContentLabelingService
→ SentimentClassifier
```

模型业务输入仍只有 title/text/author.display_name；平台差异、URL、指标、Raw 等不进入 Prompt。

## 16. 测试门禁

自动测试至少覆盖：

- 4 个情感标签闭集；
- 7 个一级标签闭集；
- 17 个二级标签闭集；
- 每个二级 → 一级唯一映射；
- 不合法标签 fail closed；
- 合法字符串但父子错配 fail closed；
- 缺 title/text/author 时填空字符串；
- LLM payload 不包含 URL/ID/指标/源全文情感等禁止字段；
- Prompt Markdown 加载与 `prompt_sha256`；
- Prompt 内容变化导致 analysis identity 变化；
- 相同 input/prompt/taxonomy/model 可安全恢复跳过；
- JSONL checkpoint + 原子回写；
- 最终 Excel 只从回写后的统一 JSONL 读取标签。

真实模型 Probe 还要用人工确认样本分别覆盖各主类别、4 种情感和容易混淆的边界案例，不能只测“请求返回 200”。
