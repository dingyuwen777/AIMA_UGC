# 舆情 AI 打标与统一分析契约

## 1. 定位

本设计负责全平台通用的**内容 AI 打标**能力，不属于临时 P1 私有逻辑，也不属于某个 Provider/平台 Mapper。

长期调用方向：

```text
TikHub / 官方 API / Apify / 文件导入 / 未来其他 Provider
→ 各自 Mapper
→ CanonicalContentV1
→ Provider-neutral 内容记录 / Query Read Model
→ Analysis Service
→ LLM Port
→ LLM Adapter
→ ContentLabelAnalysisV1
→ Analysis Repository / 统一 JSONL / Excel / 页面 / 报告
```

P1 的无数据库实现只是这套长期能力的第一个独立验证入口。以后正式系统从 PostgreSQL 读取内容后，仍调用同一 Analysis Service，不得按 TikHub、文件导入或平台分别维护标签逻辑。

当前 P1 只对帖子/内容打标；未来若启用评论打标，应复用本文同一 Prompt Taxonomy 与 Validator，只新增评论到模型输入的适配，不复制第二套标签体系。

## 2. Canonical 不增加 AI 标签

`CanonicalContentV1` 只表示平台/Provider 实际观察到的事实。情感、一级标签和二级标签是**派生分析事实**，不能混入 Canonical `observed_fields`，也不能让 Mapper 伪装成 Provider 原始字段。

跨平台统一结构分两层：

```text
CanonicalContentV1
= 外部可观察事实

UnifiedContentRecordV1
= CanonicalContentV1 + 处理元数据 + 可空 Analysis
```

概念结构：

```json
{
  "schema_version": "content-record.v1",
  "content": {
    "schema_version": "content.v1"
  },
  "matched_keywords": ["爱玛"],
  "analysis": null
}
```

AI 成功后仍是同一条记录，只填充：

```text
analysis: ContentLabelAnalysisV1
```

未来正式入数据库时：

```text
record.content
→ Content Owner

record.analysis
→ Analysis Owner
```

不得为了方便把整个 `UnifiedContentRecordV1` 当成 `contents` 表的一坨 JSONB 持久化。

## 3. 最重要的维护规则：Prompt Markdown 是标签体系唯一事实源

### 3.1 不在 Python 硬编码具体标签

具体的：

- 情感标签有哪些；
- 一级标签有哪些；
- 二级标签有哪些；
- 一级与二级的父子关系；
- 每个标签的覆盖内容；
- 典型表达；
- 冲突选择规则；
- 正反例；

**全部只维护在一个 Markdown Prompt 文件：**

```text
backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v1.md
```

Python/Pydantic 不再维护 `Literal[...]`、`Enum` 或第二份 `PRIMARY_TO_SECONDARY` 常量来复制这些具体标签。

这样以后业务 Owner 修改、增加、删除、重命名标签或调整判断标准时，只修改这个 Markdown 文件，不需要同步改 Python 枚举。

### 3.2 代码硬约束的是“规则”，不是“标签内容”

代码仍必须严格验证：

```text
每条结果只有 1 个 sentiment
每条结果只有 1 个 primary_label
每条结果只有 1 个 secondary_label
三个字段都是非空字符串
sentiment 必须存在于当前 Prompt Taxonomy
primary_label 必须存在于当前 Prompt Taxonomy
secondary_label 必须属于当前 primary_label
批量 item 必须一一对应
不得缺项、重复、多余项
不得返回数组、多标签或额外未声明字段
```

这意味着“标签不硬编码”**不等于**“模型可以自由输出”。模型最终仍只能从当前 Markdown 中定义的闭集取值。

## 4. Prompt Markdown 的机器可读结构

为了既让用户直接编辑 Markdown，又让程序可靠获得闭集，不允许通过模糊解析自然语言表格推测标签。

正式 Prompt 必须在同一个 Markdown 中包含一个明确的机器可读 JSON 区块，例如：

````markdown
<!-- AIMA_TAXONOMY_START -->
```json
{
  "schema_version": "aima-content-taxonomy.v1",
  "sentiments": ["正面", "中性", "负面", "混合"],
  "labels": {
    "品牌评价": [
      "口碑与信任",
      "形象与定位",
      "性价比与溢价",
      "推荐与购买意愿",
      "偏好与转换",
      "营销与传播"
    ]
  }
}
```
<!-- AIMA_TAXONOMY_END -->

# 判断标准
...
````

运行时流程固定为：

```text
读取完整 Markdown
→ 精确提取 AIMA_TAXONOMY_START / END 中的 JSON
→ 标准库 json 解析
→ 校验 Taxonomy 自身结构
→ 规范化 JSON 后计算 taxonomy_sha256
→ 对完整 Markdown 计算 prompt_sha256
→ 用同一 Taxonomy 构造模型约束和本地 Validator
→ 发送完整 Markdown + 本批最小业务输入给 LLM
```

不新增 YAML 解析依赖；首版使用 JSON 是为了只依赖 Python 标准库并避免 Markdown 自然语言解析歧义。

### 4.1 Taxonomy 文件自身也必须 fail closed

启动真实 AI 调用前，Prompt Taxonomy 至少校验：

- `sentiments` 是非空、去重后的字符串数组；
- `labels` 是非空对象；
- 一级标签名称非空且唯一；
- 每个一级标签至少有一个非空二级标签；
- 同一一级下二级标签不能重复；
- 首版要求二级标签在整个 Taxonomy 中也唯一，避免只返回二级名称时产生歧义；
- JSON 区块缺失、多于一个、无法解析或结构非法时，禁止调用真实模型；
- Prompt 中的标签判断说明如果与机器 JSON 闭集冲突，机器 JSON 决定“什么值合法”，人工 Review 负责修正文档语义不一致。

## 6. 多主题内容的主标签选择

首版每条内容只输出**一个主一级标签 + 一个主二级标签**。

当内容同时涉及多个主题时：

1. 以作者主要诉求、主要评价对象、主要篇幅为先；
2. 具体产品/服务事实优先于泛品牌印象；
3. 明确故障优先“耐用性与质量 / 故障问题与稳定性”，除非内容明确只在讨论某一性能维度的正常表现；
4. 电池续航、衰减、充电、安全问题优先放入“电池、续航与充电”，不要因为属于质量问题就全部归“耐用性与质量”；
5. 智能 App/NFC/仪表/电子功能优先放入“智能化与电子功能”；
6. 售后维修、保修、配件、投诉优先放入“售后服务”；购买前/下单/提车过程优先“销售与购买体验”；
7. 具体车型价格/配置、优惠、养护成本优先“价格与价值”；品牌层面的“这个牌子有没有溢价”才用“品牌评价 / 性价比与溢价”；
8. 广告、代言、直播、达人、联名等传播内容使用“品牌评价 / 营销与传播”；
9. 如果一条内容确实有多个主题，仍只选最核心主题，不输出数组；未来多标签是独立 Contract 变更。

## 7. 情感标签也由 Prompt 管理

当前 Prompt 基线情感闭集：

```text
正面
中性
负面
混合
```

情感同样不写死在 Python `Enum/Literal` 中，而是从 Prompt Taxonomy 的 `sentiments` 读取。

判断标准：

- **正面**：对爱玛品牌、产品、服务、价格/政策、渠道或使用体验有明确认可、满意、推荐、支持或表扬；
- **中性**：以客观信息、事实描述、新闻、配置、价格或政策说明为主，没有明确正负态度；信息不足无法可靠判断时也用中性；
- **负面**：存在明确投诉、批评、质疑、不满、失望、风险指控或负面体验；
- **混合**：对爱玛本身同时存在具有实质信息量的正面和负面评价，且任何一方都不能忽略。对竞品的负面 + 对爱玛的正面不等于混合。

## 8. 模型只接收三个业务字段

每条内容发送给 LLM 的业务输入只能包含：

```text
title
text
author.display_name
```

字段缺失必须填空字符串：

```text
title = content.title or ""
text = content.text or ""
author_display_name = content.author.display_name if available else ""
```

不得发送：平台内容 ID、URL、互动指标、粉丝数、Provider、命中关键词、源 Excel “全文情感”、Raw 定位或其他 Provider 私有字段。

批量请求为返回配对可增加临时 `item_no`；它不是业务字段，也不能使用平台 ID 代替。

## 9. 模型输出 Contract：结构固定，标签动态

`ContentLabelAnalysisV1` 的标签字段使用普通字符串，不使用包含具体业务标签的 `Literal/Enum`：

```text
sentiment: str
primary_label: str
secondary_label: str
```

程序固定保存的运行事实仍包括：

```text
schema_version
sentiment
primary_label
secondary_label
prompt_version
prompt_sha256
taxonomy_sha256
model_provider
model
input_hash
analyzed_at
analysis_status
```

模型本身只需要返回本批 item 对应的：

```json
{
  "items": [
    {
      "item_no": 1,
      "sentiment": "正面",
      "primary_label": "骑行性能",
      "secondary_label": "舒适性"
    }
  ]
}
```

模型不负责伪造 `model`、Hash 或时间，这些由程序根据真实运行事实填充。

## 10. 大模型不能替代本地校验

无论模型 Provider 是否提供 JSON mode / structured output，系统都必须本地校验。原因包括：

- 网络/流式输出可能截断；
- 批量结果可能缺 item、重复 item 或多 item；
- 模型可能返回 Prompt 中不存在的同义词；
- 模型可能返回合法一级和合法二级，但父子组合错误；
- Prompt Taxonomy 可能被用户编辑成非法 JSON/重复标签；
- structured output 只能提高结构遵循度，不能证明业务分类语义正确。

正式验证链：

```text
PromptTaxonomyLoader
→ Taxonomy 自身校验
→ 如果 LLM Provider 支持，动态生成 response JSON Schema/枚举约束
→ LLM
→ JSON 解析
→ 固定结构/Pydantic 校验
→ item_no 一一对应校验
→ Runtime Taxonomy membership 校验
→ 一级/二级父子校验
→ 通过后才允许写入 analysis
```

**本地 Validator 是强制门禁，不是可选兜底。**

非法结果必须 fail closed：不做模糊匹配、不自动改成“最接近标签”、不静默写入。第一版不隐藏额外付费自动修复请求；失败项记录后可由显式补跑处理。

## 11. Prompt/Taxonomy Hash 与历史可追溯

运行时计算：

```text
prompt_sha256
= 完整 Markdown 原文 SHA-256

taxonomy_sha256
= Taxonomy JSON 规范化（稳定 key 顺序/UTF-8）后的 SHA-256
```

分析缓存/恢复 identity 至少绑定：

```text
内容 input_hash
prompt_sha256
taxonomy_sha256
model_provider
model
```

因此：

- 只改判断标准 → `prompt_sha256` 变化，旧结果不复用；
- 增删/重命名标签 → 两个 Hash 通常都变化；
- 只改父子关系 → `taxonomy_sha256` 变化；
- 用户忘记手工改 `prompt_version` / `taxonomy_version` 也不会误复用旧结果。

版本字符串用于人工阅读，Hash 才是精确运行事实。

## 12. JSONL 回写与恢复

P1 `label_sentiment()`/长期 `label_content()` 输入固定为：

```text
deduplicated/contents.jsonl
```

每条只提取三个批准字段构造模型输入。

成功结果先 append + flush：

```text
analysis/checkpoints.jsonl
```

再按受控批次：

```text
deduplicated/contents.jsonl
+ checkpoint
→ deduplicated/contents.jsonl.tmp
→ flush / fsync
→ atomic replace
→ deduplicated/contents.jsonl
```

最终业务 JSONL 自身 `analysis` 已填。checkpoint 只负责恢复、费用安全和审计，不是 Excel/数据库/页面的业务事实源。

## 13. Excel 只读回写后的统一 JSONL

最终：

```text
deduplicated/contents.jsonl（analysis 已填）
→ 唯一共享 Excel Exporter
→ labeled_data.xlsx
```

不额外 join 第二份业务 Analysis JSONL，也不从 Excel 回读进入 AI。

可选 raw Excel 读取同一 JSONL，但 `include_analysis=False`，因此无需维护两份业务 JSONL。

## 14. 未来数据库设计

未来数据库不建议把当前标签做 PostgreSQL `ENUM`，否则只改 Markdown 无法生效。

推荐 Analysis Owner 保存：

```text
content_id
content/input_hash
sentiment              text/varchar
primary_label          text/varchar
secondary_label        text/varchar
prompt_version
prompt_sha256
taxonomy_sha256
model_provider
model
analyzed_at
analysis_run_id
```

运行时写入前已经按对应 `taxonomy_sha256` 的 Prompt Taxonomy 验证合法性。历史结果保留 Hash，因此后来修改标签体系不会抹掉旧结果当时使用的分类规则。

正式表、唯一约束、历史策略和 Migration 在未来 Analysis 数据库阶段单独冻结；P1 不建立表。

## 15. P1E 必须落地的生产能力

P1E 至少建立：

```text
modules/analysis/prompts/content_labeling_v1.md
PromptTaxonomyLoader
ContentLabelAnalysisV1（结构字段，不硬编码业务枚举）
ContentLabelingService
LLM Port
Fake Classifier
Runtime Taxonomy Validator
```

测试至少证明：

1. Prompt 当前基线能解析出 **9 个一级、39 个二级**且名称逐项与本文一致；
2. Python 源码中没有第二份完整业务标签枚举/父子映射；
3. 修改 Prompt JSON 增加一个临时标签后，不修改生产 Python 即可被 Loader/Validator 接受；
4. 删除/重命名 Prompt 标签后，旧标签立即被 Validator 拒绝；
5. 合法一级 + 非所属二级被拒绝；
6. 重复标签、空标签、非法 Taxonomy JSON 在调用模型前失败；
7. 模型输出未知同义词不会被程序自动修正；
8. title/text/author 缺失时输入填 `""`；
9. 模型 payload 不包含 ID、URL、指标、Provider、matched_keywords、源情感；
10. Prompt 文本变化会改变 `prompt_sha256`；Taxonomy 变化会改变 `taxonomy_sha256`。

## 16. P1F 真实模型验证

真实模型 Probe 默认关闭且不进入普通 CI。

建议人工确认样本覆盖：

- 4 种当前情感；
- 9 个当前一级标签；
- 39 个二级至少都有离线/Fake 合法性 Fixture；
- 人工真实模型样本重点覆盖易混淆边界，例如：品牌溢价 vs 车型价格、长期寿命 vs 单次故障、电池安全 vs 一般故障、销售咨询 vs 售后客服、门店渠道便利 vs 售后网点便利、操控稳定 vs 系统稳定等。

真实 Probe 记录结构化成功率、人工标签差异、延迟、token/费用和失败原因，但一次 Probe 不能承诺长期模型稳定性。

## 17. 长期维护规则

### 改判断标准/示例

只改：

```text
content_labeling_v1.md
```

代码不变，`prompt_sha256` 自动变化。

### 增删/重命名标签或改父子关系

仍然只改：

```text
content_labeling_v1.md
```

同时修改该文件中的机器 JSON 区块和对应人类判断说明。代码不改，`taxonomy_sha256` 自动变化。

### 什么时候才需要改代码

只有以下情况才需要新的 Contract/代码 Change：

- 从单一级+二级改为多标签数组；
- 增加三级标签；
- 增加必须返回的置信度、理由、实体等新字段；
- 改模型业务输入字段；
- 改 JSONL/数据库 Analysis 结构；
- 改失败/重试/历史语义。

“只是标签列表和判断规则变化”不再触发 Python 枚举修改。
