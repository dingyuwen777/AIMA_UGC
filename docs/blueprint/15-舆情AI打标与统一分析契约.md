## 1. Analysis 为什么单独成为一个业务域

Canonical 只表示 Provider/File **观察到的事实**：

```text
标题
正文
作者
发布时间
互动指标
来源
...
```

下面这些不是 Provider 原始事实，而是模型派生结论：

```text
relevance
voice_type
sentiment
primary / secondary labels
```

所以系统固定分开：

```text
Canonical / Content
→ 外部观察事实

Analysis
→ 对某个 Content Version 按某个 Prompt/Taxonomy/Model 得到的派生事实
```

不能把 AI 标签写进 `CanonicalContentV1.observed_fields`，也不能让 Mapper 负责模型分类。

## 2. 当前真实调用链

正式数据库模式：

```text

→ analysis.content-label.v1 Job

→ ContentLabelingService
→ Prompt/Taxonomy Loader
→ LLM Port
→ OpenAI-compatible Adapter

```

```text

```

旧设计中“以后正式系统从 PostgreSQL 读取内容后再持久化 Analysis”的描述已经完成，不再是未来目标。

## 3. 当前 V3 一次模型调用输出什么

当前成功结果使用：

```text
ContentLabelAnalysisV3
```

一次逻辑模型调用同时判断：

```text
relevance
+ voice_type
+ sentiment
+ labels
```

语义：

```text
relevance = irrelevant
→ 不要求 sentiment/labels 形成正常业务标签集合

relevance = relevant
→ 继续要求合法 sentiment + label pairs
```

精确 Pydantic 结构以 `modules/analysis` 当前 Contract 为准，不在 Blueprint 再维护第二套字段定义。

## 4. `voice_type` 是唯一“谁在发声”业务事实

当前机器值：

```text
user_voice
creator_marketing
brand_official
dealer_promotion
media_information
other_organization
unknown
```

真实用户发声的业务判断固定为：

```text
voice_type == user_voice
```

当前公共 Contract/Excel/前端不再同时维护一个重复的 `is_user_voice` 二值字段。

`voice_type` 描述的是**这条内容当前的发声属性**，不是法律意义上的账号身份认证。Prompt 会综合：

- 标题；
- 正文；
- 作者展示名；
- 公开简介；
- 认证文案。

证据不足使用 `unknown`，不能仅凭昵称或单个营销词机械判断。

## 5. Prompt Markdown 为什么是 taxonomy 唯一事实源

当前文件：

```text
backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md
```

它同时保存：

- 模型任务说明；
- relevance 规则；
- voice_type 规则；
- sentiment；
- 一级/二级标签；
- 父子关系；
- 边界/优先级/示例；
- 机器可读 taxonomy JSON 区块。

Python 负责：

```text
提取 taxonomy
→ 校验结构
→ 计算 prompt_sha256 / taxonomy_sha256
→ 校验模型返回只能使用当前闭集
```

Python 不再维护一份业务标签 `Enum` 或 `PRIMARY_TO_SECONDARY` 平行列表。

因此如果只是业务 Owner 调整标签体系：

```text
标签新增/删除/改名
父子关系
判断说明/示例
```

先改 Prompt，再跑 Prompt/Validator/Analysis 测试；不要同时在 Python、Vue、Excel 文档复制一套新 taxonomy。

## 6. 为什么 Analysis 必须绑定 Content Version 和模型身份

如果正文从：

```text
Version A
→ Version B
```

旧 Version A 的 Analysis 不能自动冒充 Version B 的当前结论。

当前 Analysis Identity 会考虑：

```text
content_id / content_version
+ analysis schema/version
+ prompt identity
+ taxonomy identity
+ provider/model identity
```

声音广场因此能区分：

```text
completed
→ 当前 Content Version 已有当前 Analysis Identity 的成功结果

stale
→ 历史有 Analysis，但当前版本/当前配置没有

pending
→ 还没有可用 Analysis
```

精确 Identity 计算和 Query 以当前 Analysis/Content Repository 代码为准。

## 8. 规则 Relevance 与 AI Relevance 是两层

不要把两者合并。

### 规则层 Relevance

发生在正式 Ingestion/Collection 前后规定的确定性关键词相关性边界，用于：

```text
先做低成本粗筛
→ 避免明显无关内容进入后续业务处理
```

它的配置/快照属于 System/Collection/Import 执行事实。

### AI Semantic Relevance

发生在 Analysis：

```text
已经进入 Content 的内容
→ LLM 结合标题/正文/作者上下文判断语义是否真正相关
```

结果进入 Analysis Result。

因此：

```text
规则层筛过
≠ AI 一定 relevant
```

数据库默认业务列表/查询型 Analysis target/查询型 Export 会按当前 Analysis relevance 规则排除已判定 irrelevant 的内容；显式审计查询仍可读取 irrelevant 事实。

## 9. 离线 `imports_test` 和正式数据库模式有什么差别

### 正式模式

```text
Content
→ durable Analysis Request/Job
→ PostgreSQL Analysis Result
```

### 离线模式

`imports_test` 仍可在 file-only 场景运行：

```text
Canonical/Unified record JSONL
→ Offline Labeling
→ checkpoint / attempt / llm request audit
→ 最终 JSONL / Excel / Word Report
```

AI 判定 `irrelevant` 时，离线最终业务输出会移除完整内容记录；checkpoint 可以保留不含正文的最小成功决策，用于崩溃恢复和避免重复付费。

不要把离线 checkpoint 当正式数据库 Analysis 表，也不要因为数据库 Analysis 已经存在就删除 file-only 调试模式。

## 10. Transport Retry 与 Validation Retry 必须分开

### Transport Retry

```text
网络连接/读取超时
408 / 429 / 可恢复 5xx
```

由共享 LLM Adapter 显式处理；每次物理 HTTP 请求都能单独审计。

### Validation Retry

```text
HTTP 已成功
但模型 JSON/字段/taxonomy 不合法
```

由 Analysis 业务层重新发起一个新的 Validation Attempt。

这两者都可能产生真实模型请求和费用，不能共用一个“retry_count”掩盖物理请求数量。

详细：

```text
backend/src/aima_ugc/adapters/llm/README.md
```

## 11. 离线高并发为什么还有 Canary 和 Checkpoint

离线大批量打标当前支持高并发，但不是一上来就同时发满全部数据。

设计：

```text
少量 canary
→ 确认 Prompt/模型/解析/费用链正常
→ bounded in-flight concurrency
→ shared HTTP client
→ durable checkpoint
→ single writer 收敛文件输出
```

这样可以降低：

- 配置错误导致成百上千次付费失败；
- 进程崩溃后重复调用；
- 多协程同时覆盖 JSONL/Excel；
- 内存一次性加载全部结果。

精确并发默认值和文件名以 `imports_test`/offline labeling 当前代码为准。

## 13. 排障顺序

### API 提交 Analysis 后一直 pending

```text
analysis_content_requests
→ jobs
→ worker.log
→ analysis_content_request_items
→ content version / current identity
```

### Job failed

```text
Job error summary
→ worker.log request/job/content IDs
→ LLM Transport/Protocol
→ Validation Attempt
→ Analysis Repository commit
```

### 页面显示 stale

```text
当前 Content Version
→ 当前 Prompt/Taxonomy/Model Identity
→ 是否存在匹配 Analysis Result
→ Query current-analysis join
```

不要通过前端把历史 Analysis 强制显示成 completed。

### Excel/Word 没有某条内容

依次判断：

```text
规则 Relevance 是否过滤
→ 去重是否移除
→ AI relevance 是否 irrelevant
→ Export/Report 输入是否默认 relevant-only
```
