# 技术决策与实施门禁

这篇文档只保存两类内容：

1. **已经确认、会影响多个模块的长期决定**；
2. **开始重大开发前必须满足的门禁**。

具体 SQL、TikHub endpoint、Prompt taxonomy、包 patch 版本、Stage 施工记录和某次 CI 结果，不在这里复制第二份。

## 1. 事实冲突怎么处理

优先级：

```text
本轮用户明确决定 / 已批准 OpenSpec Change（存在时）
→ 当前代码、Contract、Migration、生成物、锁文件和测试
→ 本文跨模块已确认决定
→ 01—08 对应 Blueprint
→ 模块 README / collection / appendix / guide
→ 根 README
→ 历史 Change / 旧聊天
```

但不能机械地“代码优先于设计”。发现冲突时先判断：

```text
代码是否偏离已批准设计？
文档是否只是过期？
是否有新决定尚未同步？
```

确定正确事实后，在同一任务修正受影响的正式事实源。

## 2. 总体架构

### 模块化单体

当前使用一个仓库、一个 PostgreSQL 业务事实库，通过模块 Owner 和依赖方向隔离变化。

没有真实问题证据时，不引入：

- 微服务；
- Redis；
- Kafka/RabbitMQ；
- MongoDB；
- OpenSearch；
- Kubernetes；
- 多数据库兼容层。

### 运行进程

```text
API       → 短请求、查询、创建 Job
Worker    → 执行长任务
Scheduler → 创建到期 Occurrence / Run / Job
Migration → 独立升级数据库
```

### 单一根 Python 工程

仓库根是唯一 Python/uv 工程根：

```text
pyproject.toml
uv.lock
.python-version
backend/src/aima_ugc/
tests/
scripts/
migrations/
```

禁止再建立 `backend/pyproject.toml`、`backend/uv.lock`、`backend/tests/` 或 `uv --project backend` 第二套工程方式。

精确版本由版本文件和锁文件维护，Blueprint 不复制 patch 版本表。

## 3. 外部数据进入系统的稳定主链

```text
Provider Adapter / File Reader
→ Raw / Input Artifact
→ Mapper
→ Canonical
→ 规则 Relevance
→ Ingestion Service
→ Owner Repository
→ PostgreSQL
```

长期不变量：

- Provider 不直接写业务表；
- Mapper 不查数据库、不发 HTTP、不做 AI 分类；
- Canonical 不包含 AI 派生结果；
- 一个业务表只有一个写 Owner；
- 已有完整 Raw 时优先 replay，不为恢复再次调用 Provider；
- File Import 使用 Processing Import Batch，不伪造 Collection Run/Scope/Candidate。

## 4. PostgreSQL 与 Artifact

PostgreSQL 是唯一业务事实库。

稳定规则：

- 外部 ID 用字符串；
- 业务时间用 `timestamptz`；
- 关系用 FK/关联表；
- 稳定字段用列；
- 只有确实灵活的扩展元数据才用 JSONB；
- Content/Comment 使用 Current + Version + Metric Observation；
- 外部 HTTP 不放数据库事务中；
- 正式 Schema 变化只通过新的 Alembic Migration 向前演进；
- 已发布历史 Revision 不改写。

文件边界：

```text
ArtifactService
→ Artifact ID、元数据、业务关系、生命周期/权限

ArtifactStore
→ storage_key 对应的字节存取
```

默认 Local ArtifactStore，真实需要时再替换 S3。

## 5. Job Runtime

耗时任务必须走 PostgreSQL 持久 Job，例如：

- Collection；
- Excel Import；
- AI Analysis；
- Excel Export；
- 后续真正的报告/清理长任务。

Job 必须具备：

```text
版本化 Payload
幂等
Lease
Fencing Token
Heartbeat
不可被 Heartbeat 无限延长的 Attempt Deadline
取消
分类重试
进度
结果/错误
```

Worker 可以认领 `queued`，也可以接管 Lease 已过期的 `running`。旧 Worker 失去 Fencing 后不能继续写可见业务结果。

业务事实和必须触发的下游 Job，应在同一个 PostgreSQL Unit of Work 提交。

## 6. Scheduler

调度唯一身份：

```text
(plan_id, schedule_version, scheduled_for)
```

当前固定：

```text
timezone = Asia/Shanghai
misfire_policy = latest_only
max_catch_up_runs = 0
```

停机跨过多个周期后：

```text
更早到期时刻 → skipped / misfire_superseded
最新到期时刻 → enqueued
下一未来时刻 → next_run_at
```

Occurrence、Run、Job 和 Plan cursor 推进必须同事务提交。

详见 [`../appendix/Scheduler运行与恢复.md`](../appendix/Scheduler运行与恢复.md)。

## 7. Provider Request / Attempt 与费用

一个 Request 表示一个逻辑外部操作；Attempt 表示一次真实执行。

必须保持：

- 同一 Attempt 最多一次外部发送；
- 真正重发建立新 Attempt；
- `not_sent` 和 `unknown` 分开；
- `unknown` 保留潜在重复计费事实；
- 完整 Raw 已存在时 replay，不再次 Provider 调用；
- Transport 不隐藏自动网络重试；
- 当前不自动跨 TikHub App/Web/V1/V2/V3 API family fallback。

当前保留 Billing/成本审计事实，但明确**不实现**：

```text
Budget Account
Reservation Ledger
请求次数预算
金额预算
发送前 Budget / Cost Guard
```

历史 `0012/0013/0014` 的预算结构由 `20260817_0015` 向前删除；历史 Revision 保留，不回写。

## 8. Relevance 与 Analysis

这里有两层不同能力。

### 规则 Relevance

```text
Canonical
→ Global Relevance Service
→ relevant：继续 Content Ingestion
→ filtered：记录来源过滤结果，不把该 Candidate 写成 Content
```

它属于来源/Ingestion 业务链。

### AI Semantic Relevance

Content Labeling V3 一次模型调用完成：

```text
relevance
voice_type
sentiment
labels
```

AI relevance 保存在：

```text
analysis_content_results.relevance
```

当前值：

```text
relevant
irrelevant
```

当前 `contents` 表没有 `is_relevant` 这种 AI 投影列。

### voice_type

`voice_type` 是发声类型唯一业务事实。当前合法机器值必须与 Prompt、Migration 和表约束一致：

```text
user_voice
creator_marketing
brand_official
dealer_promotion
media_information
other_organization
unknown
```

白话含义：

```text
user_voice           → 真实用户发声
creator_marketing    → 创作者/KOL/KOC 营销表达
brand_official       → 品牌官方
 dealer_promotion    → 经销商/门店推广
media_information    → 媒体/资讯表达
other_organization   → 其他机构
unknown              → 证据不足，无法可靠判断
```

需要统计“真实用户发声”时，唯一业务依据是：

```text
voice_type = user_voice
```

不再保存一个平行布尔字段。

完整 Prompt/taxonomy 唯一事实源：

```text
backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md
```

文档和 Python 不维护第二份完整 taxonomy。

## 9. Analysis 数据库事实

当前正式表：

```text
analysis_content_results
analysis_content_requests
analysis_content_request_items
analysis_content_label_pairs
```

正式 Job：

```text
analysis.content-label.v1
```

`analysis_content_results` 当前保存 Content 版本、relevance、voice_type、sentiment、Prompt/Taxonomy hash、模型和分析时间等可复现分析事实。

当前表**没有** token/cost 列。离线 LLM 成本能力不能被文档写成数据库已持久化成本事实。

## 10. Excel、正式 Export 与 Word 报告

### 统一 Excel

系统级数据 Excel 只消费 Canonical/Aggregate/批准的 Provider-neutral Read Model，不直接消费平台私有 JSON。

`tikhub_test`、`imports_test` 和正式 Export 不能长期维护三套同名不同义的 Excel 字段。

### 正式 Excel Export

当前 Job：

```text
reporting.content-export-excel.v1
```

当前表：

```text
reporting_data_exports
reporting_data_export_items
```

`reporting_data_export_items` 冻结本次导出的 `content_id + content_version + ordinal`。

### Word 报告

离线报告：

```text
统一 Excel
→ 同一统计事实
→ Markdown 模板
→ report.md
→ DOCX Renderer
→ report.docx
```

Markdown 是正文结构事实源；Office Chart 保持可编辑；词云允许 PNG。离线 Renderer 不直接查 PostgreSQL、不发 HTTP、不调用 LLM。

## 11. HTTP Contract 与前端

HTTP 唯一手写事实源：Pydantic Request/Response。

```text
Pydantic
→ FastAPI OpenAPI
→ contracts/openapi/openapi.json
→ Orval
→ frontend/src/generated/api/
```

生成目录禁止手改。

前端依赖方向：

```text
Page
→ Feature Store / Feature API
→ Generated Client
→ HTTP API
```

Figma 负责设计和交互事实，不替代 HTTP Contract。工作流见 [`../guides/前端与Figma工作流.md`](../guides/前端与Figma工作流.md)。

## 12. 认证授权

当前正式业务 API/页面已经存在，但企业登录/正式认证仍明确延期。

长期方向：

```text
Feishu / OIDC / 其他企业身份源
→ Identity Adapter
→ Principal / AuthContext
→ Authorization
→ 业务 Service
```

当前不能宣称业务 API 已具备公网生产认证能力，也不提前创建虚假的本地用户/Session/actor 语义。

## 13. 日志

应用 `.log` 是主要人工排障日志，Docker stdout/stderr 是辅助。

当前人工格式：

```text
[YYYY-MM-DD HH:mm:ss.SSS filename Lline] [LEVEL] event=... fields...
```

基本原则：

- 北京时间；
- 重要生命周期 INFO；
- Retry/异常 WARNING/ERROR；
- 正常高频轮询/成功细节 DEBUG；
- Secret、完整 Raw、用户完整正文不进入普通诊断日志。

## 14. Release / Backup

长期目标是 Docker Compose 离线 Release，并让 PostgreSQL + Artifact 形成同一 Backup Set。

真正一致恢复需要共享/独占写屏障覆盖数据库业务写和 Artifact rename/delete。

**当前完整离线 Release、统一写屏障和协调 Backup/Restore 尚未闭环。**

任何“可生产恢复”结论都必须有真实 restore 验证证据。

## 16. 文档写作门禁

正式文档优先回答：

```text
为什么需要
→ 输入/输出
→ 数据/调用怎么走
→ 当前代码在哪里
→ 最小例子
→ 限制/未实现
→ 精确事实源
```

要求：

- 面向基础一般的读者；
- 必要术语第一次出现用白话解释；
- 能不用术语就不为了显得专业而用；
- 代码、表名、命令只在帮助理解/调试时出现；
- 不复制第二套完整 Schema、OpenAPI、Prompt taxonomy 或 Migration SQL；
- 不用“企业级、先进、高可用”等空话替代真实机制；
- “已实现/未实现/默认行为”必须能从当前仓库验证。

## 17. 当前阶段与下一阶段

当前机器事实已包含：

- Stage 1—7：基础平台、Job、Provider、Content、Scheduler、多平台 Collection；
- 临时 P1：Excel 离线清洗、AI、报告；
- Stage 8A—8F：统一导入、规则 Relevance、业务 API/页面、声音广场、Analysis/Export、关键词/Plan 产品化。

下一正式方向：**Stage 9 Analysis and Monitoring**。

Stage 名称不是实现事实。开始 Stage 9 子单元前仍必须重新确认 main、Active Change、当前 Contract/Schema 和真实最小业务目标。

不能因为名称里有 Monitoring 就提前假设告警、VOC、工单或 dashboard 表已经存在。

## 18. 用户决策门禁

如果仓库没有已批准事实，而且决定会实质影响：

- 业务语义；
- 页面/验收；
- 公共 Contract；
- Schema；
- 安全/权限；
- 隐私/删除；
- Provider Operation；
- 费用/预算；
- 调度；
- SLO/RPO/RTO；
- 不可逆兼容行为；

Agent 必须先调查能自行确认的事实，再给出推荐方案和必要备选，由用户/业务 Owner 决定。

用户决定后，同一任务同步到长期事实源，聊天不能成为唯一设计记录。

## 19. 版本升级门禁

发现上游有新版本，不等于应该升级。

任何运行时、数据库、框架或关键依赖升级都作为独立任务：

```text
确认官方发布/兼容性
→ 评估安全与行为影响
→ 修改版本/锁文件
→ 完整验证
→ 迁移/回滚说明
```

普通功能开发不顺手升级依赖。
