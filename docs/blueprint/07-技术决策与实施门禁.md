# 技术决策与实施门禁

这篇文档只保存两类东西：

1. **已经确认、会影响多个模块的长期决定**；
2. **开始重大开发前必须满足的门禁**。

它不再保存具体包版本、Windows 安装步骤、TikHub endpoint、完整 Schema、Stage 施工流水或某次 CI 记录。那些内容分别由锁文件、运行文档、附录、Migration、模块 README、Change 和 CI 维护。

## 1. 发生冲突时先相信什么

仓库事实优先级：

```text
本轮用户明确决定 / 已批准 OpenSpec Change（存在时）
→ 当前代码、Contract、Migration、生成物、锁文件和测试
→ 本文已确认的跨模块决定
→ 01—08 对应领域 Blueprint
→ 模块 README / docs/collection / Appendix / Guide
→ 根 README 和导航摘要
→ 历史 Change / 旧聊天
```

但“机器事实优先”不等于看到代码和文档冲突就机械改文档。

正确处理：

```text
先确认代码是不是偏离了已批准设计
→ 如果代码错，修代码
→ 如果已批准实现已经改变系统事实，修文档
→ 同一任务把相关事实源收口
```

## 2. 当前总体架构决定

### 2.1 模块化单体

当前使用一个代码仓库和一个 PostgreSQL 业务事实库，通过模块 Owner 和依赖方向隔离变化。

不因为“以后可能扩展”提前引入：

- 微服务；
- Redis；
- Kafka/RabbitMQ；
- MongoDB；
- OpenSearch；
- Kubernetes；
- 多数据库兼容层。

只有真实测量/业务证据证明现有边界不够时，才独立评估。

### 2.2 API / Worker / Scheduler / Migration 分进程

```text
API       → 短请求、查询、创建 Job
Worker    → 执行长任务
Scheduler → 创建到期的 Occurrence/Run/Job
Migration → 独立升级数据库
```

它们共用后端代码和数据库，但职责不同。

### 2.3 单一根 Python 工程

仓库根是唯一 Python/uv 工程根：

```text
pyproject.toml
uv.lock
.python-version
backend/src/aima_ugc/
tests/
scripts/
migrations/
```

禁止再建立：

```text
backend/pyproject.toml
backend/uv.lock
backend/tests/
uv --project backend
```

这条决定避免同一仓库出现两套安装/测试命令。

精确 Python/uv/包版本由 `.python-version`、`.uv-version`、`pyproject.toml`、`uv.lock` 维护，不在本文复制。

## 3. 外部数据进入系统的唯一长期主链

```text
Provider Adapter / File Reader
→ Raw/Input Artifact
→ Mapper
→ Canonical
→ Relevance
→ Ingestion Service
→ Owner Repository
→ PostgreSQL
```

Collection 外部来源在 Raw 和 Mapper 之间还有 Candidate 来源账本；File Import 使用 Processing Import Batch，不伪造 Collection Run/Scope/Candidate。

必须保持：

- Provider 不直接写业务表；
- Mapper 不查数据库、不发 HTTP、不做 AI 业务分类；
- Canonical 不包含 AI 派生标签；
- 一个业务表只有一个写 Owner；
- 已有完整 Raw 时优先 replay，不为恢复再次付费请求 Provider。

## 4. PostgreSQL 是唯一业务事实库

当前只支持 PostgreSQL 18。

稳定数据原则：

- 外部 ID 用字符串；
- 时间用 `timestamptz`；
- 关系用 FK/关联表；
- 稳定字段用列；
- 灵活扩展元数据才用 JSONB；
- Content/Comment 使用 Current + Version + Metric Observation；
- 外部 HTTP 不放数据库事务中；
- 可重试业务写入必须有数据库可约束的幂等身份。

正式 Schema 变化只通过新的 Alembic Migration 向前演进；已发布 Revision 不改写。

## 5. Job Runtime 决定

长任务必须使用 PostgreSQL 持久化 Job，包括采集、导入、AI、导出、报告/清理等耗时工作。

Job 必须具备：

```text
版本化 Payload
幂等
Lease
Fencing Token
Heartbeat
不可被 Heartbeat 无限延长的 Attempt Deadline
取消
分类重试
进度
结果/错误
```

Worker 可以认领 `queued`，也可以接管 Lease 已过期的 `running`。旧 Worker 失去 Fencing 后不能继续写可见业务结果。

业务事实和必须触发的下游 Job，应在同一 PostgreSQL Unit of Work 提交。

## 6. Scheduler 决定

调度身份固定：

```text
(plan_id, schedule_version, scheduled_for)
```

当前第一版：

```text
timezone = Asia/Shanghai
misfire_policy = latest_only
max_catch_up_runs = 0
```

停机跨过多个周期后：

```text
更早到期时刻 → skipped / misfire_superseded
最新到期时刻 → enqueued
下一未来时刻 → next_run_at
```

Occurrence、Run、Job 和 Plan cursor 推进必须在同一短事务完成。

更详细运行/恢复解释见 [`../appendix/Scheduler运行与恢复.md`](../appendix/Scheduler运行与恢复.md)。

## 7. Provider Request / Attempt 决定

一个 Request 表示一个逻辑 Provider 操作；Attempt 表示一次真实执行。

必须保持：

- 同一 Attempt 最多一次外部发送；
- 真正重发建立新 Attempt；
- `not_sent` 和 `unknown` 必须区分；
- `unknown` 保留潜在重复计费事实；
- 完整 Raw 已存在时 replay，不再次 Provider 调用；
- 不在 Transport 内隐藏自动网络重试；
- 不自动跨 App/Web/V1/V2/V3 API family fallback。

备用 Provider/API family 只有经过显式验证和独立决策才切换。

## 8. Provider Billing 与 Budget 的决定

当前保留：

- Provider Request/Attempt 计费状态；
- 单价快照；
- estimated/actual cost；
- currency/unit；
- potential duplicate charge。

当前明确**不实现**：

```text
Budget Account
Reservation Ledger
请求次数预算
金额预算
发送前 Budget/Cost Guard
```

历史 Revision `0012/0013/0014` 中出现过预算相关结构，`20260817_0015` 已通过向前 Migration 删除。历史 Revision 保留，不回写。

未来如果需要预算控制，必须新建 L3 Change，重新确认 Contract、Schema、Migration、发送前边界和回滚。

## 9. Canonical / Analysis 决定

### Canonical

只表达平台可观察业务事实，不包含 AI 派生结论。

### Analysis

Analysis 是独立业务域。当前 Content Labeling V3 一次模型调用完成：

```text
relevance
voice_type
sentiment
labels
```

`voice_type` 是发声类型唯一事实：

```text
professional_media
influencer_self_media
ordinary_user
```

不再保存平行的“是否真实用户发声”布尔字段。

完整 AI taxonomy 和 Prompt 业务规则唯一事实源：

```text
backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md
```

Blueprint、README、Excel 和前端不得手工维护第二套 taxonomy。

无关内容：

- 离线最终业务 JSONL/Excel/report 可以不输出；
- Raw/输入/checkpoint 不因过滤被销毁；
- 正式 PostgreSQL 保留必要审计，并通过 `contents.is_relevant` 让默认业务查询过滤。

## 10. Excel / Export / Report 决定

### 统一 Excel

系统级数据 Excel 只消费 Canonical/Aggregate/批准的 Provider-neutral Read Model，不直接消费平台私有 JSON。

`tikhub_test`、`imports_test` 和正式 Export 不能长期各维护一套列语义。

### 正式 Excel Export

当前 Reporting Domain 使用持久化 Job，并冻结本次要导出的 Content 集合；最终文件由 Artifact 管理。

### Word 报告

离线 Word 报告消费统一 Excel：

```text
UnifiedDataExcelV1
→ 同一统计事实
→ Markdown 模板
→ report.md
→ DOCX Renderer
→ report.docx
```

Markdown 是正文结构事实源；Office 图表保持可编辑，词云允许 PNG。Report Renderer 不直接查 PostgreSQL、不发 HTTP、不调用 LLM。

## 11. HTTP Contract / 前端决定

HTTP 唯一手写事实源：Pydantic Request/Response。

```text
Pydantic
→ FastAPI OpenAPI
→ contracts/openapi/openapi.json
→ Orval
→ frontend/src/generated/api/
```

生成目录禁止手改。

前端依赖方向：

```text
Page
→ Feature Store / Feature API
→ Generated Client
→ HTTP API
```

禁止页面直接访问数据库、复制另一套业务 Client 或修改生成文件。

Figma 只负责设计/交互事实，不替代 API Contract；工作流见 [`../guides/前端与Figma工作流.md`](../guides/前端与Figma工作流.md)。

## 12. 认证授权决定

当前正式业务 API/页面已经存在，但第一版企业登录/身份认证仍明确延期。

长期边界：

```text
Feishu / OIDC / 其他身份源
→ Identity Adapter
→ Principal / AuthContext
→ Authorization
→ 业务 Service
```

业务模块不能把 Provider 私有 `open_id` 等字段当权限事实。

在真实认证落地前，不宣称系统具备公网生产认证能力，也不提前创建虚假的本地用户/Session/API Idempotency actor 语义。

## 13. Artifact 决定

```text
ArtifactService
→ ID、元数据、业务关系、生命周期/权限

ArtifactStore
→ storage_key 对应的字节存取
```

默认 Local ArtifactStore，可在真实需要时替换 S3。

业务模块不直接把宿主机路径当公共 Contract。

## 14. 日志决定

应用 `.log` 是主要人工排障日志，Docker stdout/stderr 是辅助。

当前人工格式：

```text
[YYYY-MM-DD HH:mm:ss.SSS filename Lline] [LEVEL] event=... fields...
```

- `Asia/Shanghai`；
- 不重复 `service=`；
- 正常高频轮询/成功细节用 DEBUG；
- 重要生命周期 INFO；
- Retry/异常 WARNING/ERROR；
- Secret/完整 Raw/用户正文不进入普通诊断日志。

## 15. Release / Backup 当前门禁

长期目标：Docker Compose 离线 Release，并让 PostgreSQL + Artifact 形成统一 Backup Set。

要真正做到一致恢复，需要共享/独占数据库 advisory 写屏障覆盖业务写事务和 Artifact rename/delete，再在独占窗口捕获数据库+文件。

**当前完整离线 Release、统一写屏障和协调 Backup/Restore 尚未闭环。**

因此：

- 不把设计目标写成当前可发布事实；
- 进入 Release 阶段前必须重新核对当前代码和部署脚本；
- 任何声称“可生产恢复”都必须有真实 restore 验证证据。

## 16. 文档体系决定

正式文档按职责分层：

```text
docs/blueprint/
→ 长期架构、为什么这样设计、稳定门禁
\模块 README
→ 当前代码怎么实现、入口/Owner/测试

docs/appendix/
→ PostgreSQL、Scheduler、TikHub、Excel、AI、报告等专题细节和调试

docs/guides/
→ Figma 等开发过程指南

代码 / Contract / Migration / generated / tests / locks
→ 精确机器事实

changes/archive/
→ 历史为什么改过
```

核心 Blueprint 固定为 `01`—`08`。不要再因为一个新专题继续新增 `09、10、11...`；只有真正新增长期架构领域且无法合理放入 01—08 时，才通过文档治理 Change 调整核心结构。

## 17. 文档写作门禁

正式文档必须优先回答：

```text
为什么需要
→ 输入/输出
→ 数据/调用怎么走
→ 当前实现位置
→ 最小例子
→ 限制/未实现
→ 精确事实源
```

要求：

- 面向基础一般的读者；
- 必要术语第一次出现时用白话解释；
- 能不用术语就不为了显得专业而用；
- 是否引用类名/表名/代码，以是否帮助理解为准；
- 不复制完整 Schema、OpenAPI、Prompt taxonomy 或 Migration SQL；
- “已实现/未实现/默认行为”必须能从当前仓库验证；
- 不写空泛的“企业级、先进、高可用”形容词替代真实机制。

## 18. 当前阶段状态与下一阶段门禁

当前机器事实已经包含：

- Stage 1—7 基础平台、Job、Provider、Content、Scheduler、多平台 Collection；
- 临时 P1 Excel 离线清洗/AI/报告；
- Stage 8A—8F 统一导入、相关性、业务 API/页面、声音广场、Analysis/Export、关键词/Plan 产品化。

下一正式方向：**Stage 9 Analysis and Monitoring**。

Stage 名称不是实现事实。开始 Stage 9 子单元前必须重新确认：

- 当前 main；
- Active Change 冲突；
- 是否已经存在对应模块/Contract/Schema；
- 该子单元的最小可观察业务价值；
- 需要的用户上游决定。

不能因为名字里有 Monitoring 就提前假设告警、VOC、工单或 dashboard 表已经存在。

## 19. 用户决策门禁

如果仓库没有已批准事实，且决定会实质影响：

- 业务语义；
- 页面/验收；
- 公共 Contract；
- Schema；
- 安全/权限；
- 隐私/删除；
- Provider Operation；
- 费用/预算；
- 调度；
- SLO/RPO/RTO；
- 不可逆兼容行为；

Agent 必须先完成可自行确认的事实调查，再在对话中给出推荐方案和必要备选，由用户/业务 Owner 决定。

用户决定后，同一任务同步到长期事实源；聊天不能成为唯一设计记录。

## 20. 版本升级门禁

精确版本以锁文件/版本文件为事实。

发现上游有新版本，不等于应该升级。任何运行时/框架/数据库/关键依赖升级都作为独立任务：

```text
确认官方发布/兼容性
→ 评估安全与行为影响
→ 修改版本/锁文件
→ 完整验证
→ 迁移/回滚说明
```

不允许在普通功能开发里顺手升级依赖。
