## 1. 本文的地位

本文只保存跨文档的已确认决策、版本冻结快照和开始编码前的硬门禁。各领域的完整设计仍由 `01`—`06` 负责；发生冲突时按以下优先级处理：

```text
已批准的 OpenSpec change（仓库建立后）
→ 当前代码、Migration、Contract、锁文件和测试事实
→ 本文的已确认跨文档决策
→ 01—06 对应领域设计
→ README 导航和摘要
```

若机器事实与已批准设计不一致，不能静默以机器事实覆盖设计：先确认是实现缺陷、文档过期还是新决策，再在同一任务中修正。聊天记录、模型记忆和旧系统实现不属于事实源。

## 2. 已确认决策

### 2.1 方案 A：单一根 Python 工程

```text
仓库根目录/
├─ pyproject.toml
├─ uv.lock
├─ .python-version
├─ .node-version
├─ .uv-version
├─ backend/src/aima_ugc/
├─ migrations/
├─ tests/
├─ scripts/
└─ frontend/package.json + package-lock.json
```

- 根目录是唯一 uv 项目和质量命令执行目录；
- Python 可导入源码固定在 `backend/src/aima_ugc/`；
- `backend/` 不再拥有 `pyproject.toml`、`uv.lock`、`tests/` 或 `scripts/`；
- 不使用 `cd backend` 或 `uv --project backend` 形成第二种开发方式；
- `frontend/` 是独立 npm 项目，不加入另一个 JavaScript 包管理器。

阶段 1 已实际选择 `uv_build 0.12.3` 作为根 Python build backend，并显式配置 `module-root = "backend/src"`、`module-name = "aima_ugc"`。锁定环境已验证直接 `import aima_ugc`，并验证 Wheel 构建、隔离环境安装和再次直接导入；因此不再允许用 `PYTHONPATH`、改变工作目录或修改 `sys.path` 掩盖打包问题。

### 2.2 保持既定技术路线

- 模块化单体；API、Worker、Scheduler、Migration 分进程，共用一个后端运行镜像；
- PostgreSQL 同时承担业务事实、事务和当前规模的持久化 Job；
- Provider → 不可变 Raw → Mapper → Canonical → Ingestion；
- Vue 3 + TypeScript 前端，通过 OpenAPI 生成 Client；
- Local ArtifactStore 为默认字节存储，可替换 S3，但不预建多存储兼容复杂度；
- Docker Compose 离线 Release；
- 没有测量证据时不引入微服务、消息中间件、Redis、OpenSearch 或 Kubernetes。

### 2.3 已消除的跨文档冲突

| 主题 | 唯一决定 |
| --- | --- |
| HTTP 幂等 | 独立 `api_idempotency_records`，作用域为 actor + operation + key；绑定请求 Hash 和有效期；同 key 异 Payload 返回 409 |
| Job 幂等 | 只表达内部 `job_type + internal_idempotency_key`，不模拟用户/有效期语义 |
| Worker 恢复 | 原子认领 queued 或 Lease 已过期的 running；每次 Attempt 有不可续期 Deadline；Reaper 处理超时/取消/次数耗尽；所有可见写入受 Fencing 约束 |
| Scheduler | 唯一 `(plan_id, schedule_version, scheduled_for)` Occurrence；Occurrence/Run/Job/推进 Plan 同事务；停机补跑受 misfire 策略和上限约束 |
| 认证授权 | Session、登录限流、Role/Permission、撤销/过期和审计均有数据库事实；在业务写 API 前实施 |
| 来源追溯 | 内容和评论 Candidate/Ingestion 都是逐项不可变账本，可追溯 Run/Scope/Attempt/Raw/item；Discovery 只是聚合 |
| 内容版本 | 新 Hash 只和当前版本比较；允许 `A → B → A` 产生第三个版本 |
| 每日指标 | `Asia/Shanghai` 业务日，数据库部分唯一约束保证每日最多一个无变化 Checkpoint |
| Artifact | `ArtifactService` 负责 ID/元数据/权限/生命周期，`ArtifactStore` 只按 `storage_key` 存取 |
| 下游任务 | 业务事实与下游 PostgreSQL Job 在同一 Unit of Work 提交，Job 表兼任事务型 Outbox |
| Provider 费用 | 有已校验 Raw 时不再调用；网络结果未知时可能重复计费；每个真实 HTTP Attempt 强制取得 global+run，评论再取得 content_comments；dispatching 同一 Attempt 不复发，预留事务重放才幂等复用 |
| 中文检索 | 阶段 0 用真实中文语料做质量/性能基准后选 PostgreSQL 方案，不预先承诺 `tsvector` 效果 |
| 常规/发布备份 | 维护 epoch + 统一共享/独占 PostgreSQL advisory 写屏障排空在途写入，再创建统一截止点的数据库+Artifact Backup Set；独立文件增量不算恢复点 |

### 2.4 Stage 1 前端工具链

阶段 1 已通过真实 `linux/amd64` CI 固化以下规则：

- HTTP 契约仍以 Pydantic Request/Response 为唯一手写事实源，FastAPI 生成固定 `contracts/openapi/openapi.json`；所有公开 Route 使用稳定 `operation_id`；
- TypeScript Fetch Client 使用 `Orval 8.24.0` 从固定 OpenAPI 生成到 `frontend/src/generated/api/`，生成目录禁止手工修改；
- Fetch Client 使用 `includeHttpResponseReturnType: false` 返回业务响应数据；不启用 `forceSuccessResponse`，错误语义后续仍由统一 HTTP Contract 和 Feature API 处理；
- 项目普通 `.ts` 代码使用 TypeScript 7.0.2 native compiler；由于 TypeScript 7.0 暂无供 Vue/Volar 等工具使用的 programmatic JS API，Vue SFC 类型检查采用 TypeScript 官方与 Vue Language Tools 当前兼容模型：`@typescript/native` 指向 `typescript@7.0.2`，包名 `typescript` 指向 `@typescript/typescript6@6.0.2`，仅供 `vue-tsc 3.3.9` 等需要 JS compiler API 的工具消费；这不表示应用语言降级为 TypeScript 6；
- `npm run typecheck` 必须同时执行 TS7 native `.ts` 检查和 `vue-tsc` Vue SFC 检查，缺一不可；
- Stage 1 Lint 使用 ESLint 10.8.0 + `eslint-plugin-vue` 10.10.0 + `vue-eslint-parser` 10.4.1 + Babel TypeScript syntax parser。当前 `typescript-eslint` 尚未正式支持 TypeScript 7，因此不强行引入；Stage 1 不宣称具备 type-aware ESLint，类型正确性由双类型门禁负责；
- 前端直接依赖和开发依赖全部精确锁定，并由 `package-lock.json` 固定传递依赖；初始化 CI 已验证生产依赖和完整依赖树 `npm audit` 均无已报告漏洞。

### 2.5 本地开发启动闭环

本地开发启动已经通过真实 `linux/amd64` CI 的双服务 smoke 固化：

- Uvicorn `0.52.2` 是根 Python 项目的锁定运行依赖，不允许要求开发者额外全局 `pip install uvicorn`；
- 本地 FastAPI 使用正式 `aima_ugc.entrypoints.api_main:app`，固定监听 `127.0.0.1:8090`；开发时允许 `--reload --reload-dir backend/src`，但 `--reload` 不是生产运行参数；
- Vite 本地开发固定监听 `127.0.0.1:5173` 且 `strictPort=true`；端口被占用时明确失败，不静默切换端口；
- Vite 仅把 `/health` 与 `/api` 代理到 `http://127.0.0.1:8090`，前端生成 Client 继续使用相对 URL；本地联调不以放宽 CORS 作为解决方案；
- `scripts/dev/check_local_stack.py` 只通过 HTTP 观察正式服务，验证后端直连健康检查、Vite 首页和 Vite → FastAPI 代理，不复制应用逻辑；
- 以上本地开发方式不改变 Blueprint 05 的生产部署设计。生产仍要求 Nginx、Docker Compose、离线 Release 和正式运行进程，不允许把 `vite dev` 或 Uvicorn `--reload` 当作生产方案。

### 2.6 Windows x64 开发环境引导与国内源

Windows 开发机的目标不是“把所有旧开发工具都替换掉”，而是保证 AIMA_UGC 能取得并使用仓库锁定的工具版本，同时尽量不破坏其他项目环境。当前固定方案：

- 双击入口为 `scripts/setup_dev_environment.cmd`，实际逻辑在 `scripts/setup_dev_environment.ps1`；入口不依赖 Python/Node 预先存在；
- Python、Node、uv 的目标版本分别来自 `.python-version`、`.node-version`、`.uv-version`；npm 目标来自 `frontend/package.json`，安装脚本不得再维护平行版本常量；
- 中国大陆一键引导固定使用国内源：Python Windows 安装包使用清华 TUNA Python 镜像；PyPI、uv 自身与 Python 项目依赖使用清华 TUNA PyPI；Node Windows MSI 与 `SHASUMS256.txt` 使用 npmmirror Node 二进制镜像；npm 自身和前端依赖使用 `registry.npmmirror.com`；
- 国内源仅在脚本当前进程或具体安装命令中生效，脚本结束后恢复原来的 `UV_DEFAULT_INDEX`、`npm_config_registry` 和 `npm_config_replace_registry_host`，不得永久修改其他项目的全局 pip/uv/npm Registry；
- 国内镜像失败时明确报错并显示镜像 URL，**不自动回退境外运行时下载源**；否则会形成难以审计的混合供应链；
- 版本不符时先展示已发现的旧安装，再由用户决定是否主动卸载；Python/Node 默认不卸载；npm 因标准全局安装不提供并行版本，会明确询问是否替换，拒绝则停止并说明仓库环境未就绪；
- Python 使用 TUNA 镜像中的 Windows x64 官方安装包并保留 GUI；下载后要求 Authenticode 状态有效。Python 支持多版本并存，用户保留旧版本时通过直接路径或 Windows Python Launcher 确认目标运行时存在，AIMA_UGC 再由 `.python-version + uv` 选择项目 Python，不强制改写全局 Python PATH 优先级；
- Node 使用 npmmirror 中的精确版本 x64 MSI，并用同镜像 `SHASUMS256.txt` 校验 SHA-256，同时要求 Authenticode 状态有效。标准 Node MSI 可能在固定安装位置执行产品升级，因此“脚本不主动卸载旧 Node”不等于承诺多版本长期并存；
- uv 不再调用 Astral 境外安装器；目标 Python 就绪后通过 `python -m pip install uv==<target> --index-url <TUNA PyPI>` 安装精确版本。安装完成后最多把目标 Python 的 `Scripts` 目录加入**当前用户 PATH**，不删除其他 PATH 项，不改 Machine PATH；
- 用户要求删除旧 uv 时，仅对 `%USERPROFILE%\.local\bin` 中的独立 `uv/uvx/uvw` 自动删除；其他目录视为可能由第三方包管理器所有，不自动删除；
- 禁止使用 `Win32_Product` 查询已安装软件，避免触发 MSI repair；禁止永久调用 `Set-ExecutionPolicy`；脚本不会修改系统代理、证书或安全软件；
- 工具满足后必须继续执行 `uv lock --check`、`uv sync --locked`、`npm ci --prefix frontend` 和包导入验证，不能只安装系统运行时就宣称项目环境完成；
- 自动引导当前只支持 Windows x64。Linux/macOS 继续按操作文档手工准备相同锁定版本，不伪装已支持跨平台自动安装。

GitHub Actions 的 `Windows bootstrap` 使用 Windows PowerShell 5.1 验证脚本可解析、版本事实读取、目标 Python 与 Scripts 路径发现、国内源精确 URL、`.cmd` 入口、无境外运行时源残留，以及 `Win32_Product` / 永久 ExecutionPolicy 禁用门禁。CI **不真实卸载或安装 Runner 上的系统软件，也不自动操作 GUI**；因此不能把该门禁描述为“完整安装过程已经无人值守实机验证”。实际 GUI 安装和卸载仍由开发者本机交互完成。CI 自身使用的 GitHub Actions 下载属于测试基础设施，不属于开发机一键脚本的供应链路径。

### 2.7 Stage 2 Platform 基础

Stage 2 已用独立 Platform 单元测试、隔离 PostgreSQL 18.4 集成测试和真实 HTTP readiness smoke 固化以下边界：

- Config 继续复用 Pydantic，只读取代码显式声明的 `AIMA_*` 环境变量；当前不自动加载 `.env` 或 `env.local.example`，避免引入第二套隐式配置优先级；
- PostgreSQL 密码不进入普通环境变量，固定从 `<AIMA_SECRET_DIR>/postgres_password` 只读文件读取；Secret Reader 限制文件类型/大小/UTF-8/NUL/空值，并且异常不回显 Secret 内容；
- 数据库采用已批准的同步 SQLAlchemy 2 + psycopg 3 路线，提供惰性 Engine、`SELECT 1` readiness、同步 Session Factory 与 `dispose()`；Stage 2 不自动建表、不自动运行 Alembic；
- `GET /health/live` 保持原 Contract，只表示进程存活；新增稳定 `operation_id=healthReady` 的 `GET /health/ready`，检查 PostgreSQL、Artifact 根目录和日志目录，全部就绪返回 200，任一失败返回 503；响应只包含组件 `ok/error`，禁止回传连接串、Secret 或原始异常；
- 应用日志使用 Python 标准库 `logging + RotatingFileHandler`，按 Blueprint 05 输出北京时间毫秒、一行稳定事件、最终层脱敏和 `20 MiB × 10` gzip 轮转；API/Worker/Scheduler 分文件，Docker/stdout 继续只是辅助；
- `ArtifactStore` 只按 `storage_key` 存取字节；Local 实现禁止绝对路径、`..`、反斜杠与符号链接逃逸，同 key 不静默覆盖，并采用同目录临时文件 + fsync + hard-link 原子 no-overwrite 发布；
- `ArtifactService` 负责 Artifact ID、元数据 Port 和 `pending → stored → linked` 编排；Stage 2 只用 Fake Metadata Port 证明边界，PostgreSQL `artifacts` Table/Repository 与 Alembic Revision 留到 Stage 3；
- Artifact 删除/保留动作继续不实现，直到阶段 0 的访问、保留与删除规则得到批准；
- API、Worker、Scheduler、Migration 已建立共用 Platform bootstrap/entrypoint，但本阶段不伪造 Worker Job 循环、Scheduler 计划逻辑或 Migration Revision；这些仍分别受后续阶段门禁约束；
- Stage 2 CI 使用 `postgres:18.4` 做隔离集成验证。CI 拉取到的具体镜像 digest 只是该次测试证据，不是生产 Release digest；生产基础镜像 variant/digest 仍由阶段 0/11 决定。

### 2.8 身份认证延期、第三方扩展边界与用户决策规则

用户已确认：当前第一版不设计或实现登录入口、本地用户名/密码、MFA、Session、CSRF 或登录限流。未来预计与飞书等第三方企业应用/身份源结合后实现身份认证与权限控制；具体认证协议、回调、Token/Session 生命周期在真实接入需求明确后作为独立 L3 Change 冻结。

当前只冻结以下长期边界：

```text
Feishu / OIDC / 其他企业身份源
→ Identity / Authentication Adapter
→ Principal / AuthContext
→ Authorization
→ stable Permission / object policy
→ business service
```

- 业务模块不得直接依赖飞书 SDK、`open_id`、`union_id`、租户字段或其他 Provider 私有身份；
- Authentication 与 Authorization 解耦，替换身份 Provider 不应要求改写业务 Service；
- 角色名称/操作边界仍由阶段 0 业务决定，`admin/operator/analyst/viewer` 目前只是候选示例；
- 未完成真实认证接入前，敏感/写 API 不得宣称具备公网生产认证能力；
- 用户明确延期的能力不得由后续 Agent 因旧模板或“最佳实践”偷偷恢复实现。

需要用户/业务 Owner 决定的事项采用固定门禁：Agent 先调查可自行确认的事实，**在对话中给出推荐方案**，必要时附 2–3 个实质不同备选和影响，再由用户作最终决定。决定前暂停依赖该语义的 Contract/Schema/安全或不可逆实现；用户决定或明确延期后，同一任务必须写入对应领域 Blueprint/需求、OpenSpec（存在时）和当前 Change，形成机器 Contract/Schema 时再同步机器事实。聊天记录不能成为后续实现唯一依据。

## 3. 版本选择与冻结政策

### 3.1 “最新稳定”的可执行定义

“最新稳定”只在**初始化或显式升级任务的核验时刻**使用：

1. 运行时和基础设施选择官方标记的 Stable/LTS 且仍受支持版本；
2. 语言包选择官方 Registry `latest` 指向的非 prerelease、非 yanked/deprecated 版本；
3. 排除 Alpha、Beta、RC、Nightly 和未发布主版本；如果项目自身的成熟度 classifier 仍是 Beta，但其版本号是 Registry 最新非预发布版，必须如实标注，不能改称 Production/Stable；
4. 选择必须满足本蓝图已批准的大版本兼容范围，并核验关键 engine/peer/Requires-Python 约束；
5. 初始化完成后立即写入版本声明和锁文件，Release 镜像再固定 digest。

“发现了更新”不等于“应升级”。日常启动、构建、功能开发和 CI 都禁止解析 `latest` 或自动改 Lock。升级只能通过独立提案/PR，说明发布说明、安全与兼容影响、Migration、回滚和完整验证结果。

## 6. 变更控制

- 本文的已确认决定发生变化时，先提交设计变更，列出新旧差异、影响、迁移、回滚和验证；
- 精确版本升级先更新本文唯一权威版本快照，再同步运行时声明与 Lock，并执行规定的文档和构建验证；
- 普通功能任务不得顺手升级运行时、框架、数据库、镜像、OpenAPI 生成器或 Provider Operation；
- Windows 环境引导不得把“方便”作为静默卸载旧运行时、修改系统代理/证书/安全策略、永久改全局包源或永久放宽执行策略的理由；
- 国内镜像的使用不得取消官方制品签名/哈希校验；镜像不可用时不得静默切换未知来源；
- TypeScript 7 programmatic API、Vue Language Tools 或生成器未来出现新版本，不等于当前双安装/Orval 方案应自动变化；升级或移除 compatibility alias 都是独立任务；

- 每次修订运行结构/链接/JSON/冲突/版本一致性并执行仓库已有文档和构建验证；文档校验不等于实现验证。
