## 2. 已确认决策

### 2.1 方案 A：单一根 Python 工程

```text
仓库根目录/
├─ pyproject.toml
├─ uv.lock
├─ .python-version
├─ .node-version
├─ .uv-version
├─ backend/src/aima_ugc/
├─ migrations/
├─ tests/
├─ scripts/
└─ frontend/package.json + package-lock.json
```

- 根目录是唯一 uv 项目和质量命令执行目录；
- Python 可导入源码固定在 `backend/src/aima_ugc/`；
- `backend/` 不再拥有 `pyproject.toml`、`uv.lock`、`tests/` 或 `scripts/`；
- 不使用 `cd backend` 或 `uv --project backend` 形成第二种开发方式；
- `frontend/` 是独立 npm 项目，不加入另一个 JavaScript 包管理器。

阶段 1 已实际选择 `uv_build 0.12.3` 作为根 Python build backend，并显式配置 `module-root = "backend/src"`、`module-name = "aima_ugc"`。锁定环境已验证直接 `import aima_ugc`，并验证 Wheel 构建、隔离环境安装和再次直接导入；因此不再允许用 `PYTHONPATH`、改变工作目录或修改 `sys.path` 掩盖打包问题。

### 2.2 保持既定技术路线

- 模块化单体；API、Worker、Scheduler、Migration 分进程，共用一个后端运行镜像；
- PostgreSQL 同时承担业务事实、事务和当前规模的持久化 Job；
- Provider → 不可变 Raw → Mapper → Canonical → Ingestion；
- Vue 3 + TypeScript 前端，通过 OpenAPI 生成 Client；
- Local ArtifactStore 为默认字节存储，可替换 S3，但不预建多存储兼容复杂度；
- Docker Compose 离线 Release；
- 没有测量证据时不引入微服务、消息中间件、Redis、OpenSearch 或 Kubernetes。

### 2.4 Stage 1 前端工具链

- 前端直接依赖和开发依赖全部精确锁定，并由 `package-lock.json` 固定传递依赖；初始化 CI 已验证生产依赖和完整依赖树 `npm audit` 均无已报告漏洞。

### 2.6 Windows x64 开发环境引导与国内源

Windows 开发机的目标不是“把所有旧开发工具都替换掉”，而是保证 AIMA_UGC 能取得并使用仓库锁定的工具版本，同时尽量不破坏其他项目环境。当前固定方案：

- 双击入口为 `scripts/setup_dev_environment.cmd`，实际逻辑在 `scripts/setup_dev_environment.ps1`；入口不依赖 Python/Node 预先存在；
- Python、Node、uv 的目标版本分别来自 `.python-version`、`.node-version`、`.uv-version`；npm 目标来自 `frontend/package.json`，安装脚本不得再维护平行版本常量；
- 中国大陆一键引导固定使用国内源：Python Windows 安装包使用清华 TUNA Python 镜像；PyPI、uv 自身与 Python 项目依赖使用清华 TUNA PyPI；Node Windows MSI 与 `SHASUMS256.txt` 使用 npmmirror Node 二进制镜像；npm 自身和前端依赖使用 `registry.npmmirror.com`；
- 国内源仅在脚本当前进程或具体安装命令中生效，脚本结束后恢复原来的 `UV_DEFAULT_INDEX`、`npm_config_registry` 和 `npm_config_replace_registry_host`，不得永久修改其他项目的全局 pip/uv/npm Registry；
- 国内镜像失败时明确报错并显示镜像 URL，**不自动回退境外运行时下载源**；否则会形成难以审计的混合供应链；
- 版本不符时先展示已发现的旧安装，再由用户决定是否主动卸载；Python/Node 默认不卸载；npm 因标准全局安装不提供并行版本，会明确询问是否替换，拒绝则停止并说明仓库环境未就绪；
- Python 使用 TUNA 镜像中的 Windows x64 官方安装包并保留 GUI；下载后要求 Authenticode 状态有效。Python 支持多版本并存，用户保留旧版本时通过直接路径或 Windows Python Launcher 确认目标运行时存在，AIMA_UGC 再由 `.python-version + uv` 选择项目 Python，不强制改写全局 Python PATH 优先级；
- Node 使用 npmmirror 中的精确版本 x64 MSI，并用同镜像 `SHASUMS256.txt` 校验 SHA-256，同时要求 Authenticode 状态有效。标准 Node MSI 可能在固定安装位置执行产品升级，因此“脚本不主动卸载旧 Node”不等于承诺多版本长期并存；
- uv 不再调用 Astral 境外安装器；目标 Python 就绪后通过 `python -m pip install uv==<target> --index-url <TUNA PyPI>` 安装精确版本。安装完成后最多把目标 Python 的 `Scripts` 目录加入**当前用户 PATH**，不删除其他 PATH 项，不改 Machine PATH；
- 用户要求删除旧 uv 时，仅对 `%USERPROFILE%\.local\bin` 中的独立 `uv/uvx/uvw` 自动删除；其他目录视为可能由第三方包管理器所有，不自动删除；
- 禁止使用 `Win32_Product` 查询已安装软件，避免触发 MSI repair；禁止永久调用 `Set-ExecutionPolicy`；脚本不会修改系统代理、证书或安全软件；
- 工具满足后必须继续执行 `uv lock --check`、`uv sync --locked`、`npm ci --prefix frontend` 和包导入验证，不能只安装系统运行时就宣称项目环境完成；
- 自动引导当前只支持 Windows x64。Linux/macOS 继续按操作文档手工准备相同锁定版本，不伪装已支持跨平台自动安装。

GitHub Actions 的 `Windows bootstrap` 使用 Windows PowerShell 5.1 验证脚本可解析、版本事实读取、目标 Python 与 Scripts 路径发现、国内源精确 URL、`.cmd` 入口、无境外运行时源残留，以及 `Win32_Product` / 永久 ExecutionPolicy 禁用门禁。CI **不真实卸载或安装 Runner 上的系统软件，也不自动操作 GUI**；因此不能把该门禁描述为“完整安装过程已经无人值守实机验证”。实际 GUI 安装和卸载仍由开发者本机交互完成。CI 自身使用的 GitHub Actions 下载属于测试基础设施，不属于开发机一键脚本的供应链路径。

### 2.7 Stage 2 Platform 基础

Stage 2 已用独立 Platform 单元测试、隔离 PostgreSQL 18.4 集成测试和真实 HTTP readiness smoke 固化以下边界：

- Config 继续复用 Pydantic，只读取代码显式声明的 `AIMA_*` 环境变量；当前不自动加载 `.env` 或 `env.local.example`，避免引入第二套隐式配置优先级；
- PostgreSQL 密码不进入普通环境变量，固定从 `<AIMA_SECRET_DIR>/postgres_password` 只读文件读取；Secret Reader 限制文件类型/大小/UTF-8/NUL/空值，并且异常不回显 Secret 内容；
- 数据库采用已批准的同步 SQLAlchemy 2 + psycopg 3 路线，提供惰性 Engine、`SELECT 1` readiness、同步 Session Factory 与 `dispose()`；Stage 2 不自动建表、不自动运行 Alembic；
- `GET /health/live` 保持原 Contract，只表示进程存活；新增稳定 `operation_id=healthReady` 的 `GET /health/ready`，检查 PostgreSQL、Artifact 根目录和日志目录，全部就绪返回 200，任一失败返回 503；响应只包含组件 `ok/error`，禁止回传连接串、Secret 或原始异常；
- 应用日志使用 Python 标准库 `logging + RotatingFileHandler`，按 Blueprint 05 输出北京时间毫秒、一行稳定事件、最终层脱敏和 `20 MiB × 10` gzip 轮转；API/Worker/Scheduler 分文件，Docker/stdout 继续只是辅助；
- `ArtifactStore` 只按 `storage_key` 存取字节；Local 实现禁止绝对路径、`..`、反斜杠与符号链接逃逸，同 key 不静默覆盖，并采用同目录临时文件 + fsync + hard-link 原子 no-overwrite 发布；
- `ArtifactService` 负责 Artifact ID、元数据 Port 和 `pending → stored → linked` 编排；Stage 2 只用 Fake Metadata Port 证明边界，PostgreSQL `artifacts` Table/Repository 与 Alembic Revision 留到 Stage 3；
- Artifact 删除/保留动作继续不实现，直到阶段 0 的访问、保留与删除规则得到批准；
- API、Worker、Scheduler、Migration 已建立共用 Platform bootstrap/entrypoint，但本阶段不伪造 Worker Job 循环、Scheduler 计划逻辑或 Migration Revision；这些仍分别受后续阶段门禁约束；
- Stage 2 CI 使用 `postgres:18.4` 做隔离集成验证。CI 拉取到的具体镜像 digest 只是该次测试证据，不是生产 Release digest；生产基础镜像 variant/digest 仍由阶段 0/11 决定。

### 2.8 身份认证延期、第三方扩展边界与用户决策规则

用户已确认：当前第一版不设计或实现登录入口、本地用户名/密码、MFA、Session、CSRF 或登录限流。未来预计与飞书等第三方企业应用/身份源结合后实现身份认证与权限控制；具体认证协议、回调、Token/Session 生命周期在真实接入需求明确后作为独立 L3 Change 冻结。

当前只冻结以下长期边界：

```text
Feishu / OIDC / 其他企业身份源
→ Identity / Authentication Adapter
→ Principal / AuthContext
→ Authorization
→ stable Permission / object policy
→ business service
```

- 业务模块不得直接依赖飞书 SDK、`open_id`、`union_id`、租户字段或其他 Provider 私有身份；
- Authentication 与 Authorization 解耦，替换身份 Provider 不应要求改写业务 Service；
- 角色名称/操作边界仍由阶段 0 业务决定，`admin/operator/analyst/viewer` 目前只是候选示例；
- 未完成真实认证接入前，敏感/写 API 不得宣称具备公网生产认证能力；
- 用户明确延期的能力不得由后续 Agent 因旧模板或“最佳实践”偷偷恢复实现。

需要用户/业务 Owner 决定的事项采用固定门禁：Agent 先调查可自行确认的事实，**在对话中给出推荐方案**，必要时附 2–3 个实质不同备选和影响，再由用户作最终决定。决定前暂停依赖该语义的 Contract/Schema/安全或不可逆实现；用户决定或明确延期后，同一任务必须写入对应领域 Blueprint/需求、OpenSpec（存在时）和当前 Change，形成机器 Contract/Schema 时再同步机器事实。聊天记录不能成为后续实现唯一依据。

### 2.10 Stage 4 PostgreSQL Job Runtime

Stage 4 建立第二条 `20260814_0002` Revision，新增 `jobs` 与 `job_attempt_events`，两表 Owner 均为 `platform`。当前冻结：

- `job_type + internal_idempotency_key` 只表达系统内部幂等；同键异 Payload 关闭失败；
- Registry 只允许 Worker Claim 已注册类型，并按版本化 Pydantic Payload 校验；
- queued Claim 递增 Attempt 并建立不可续期 Deadline；Lease 过期且 Deadline 未到时只能同 Attempt takeover；
- Heartbeat 以数据库时间续租且不超过 Deadline；取消、过期 Lease、Deadline 到达或旧 Token 均不能续租；
- 成功、失败、重试、取消和 Reaper 转换受当前 Token Fencing；`jobs` 只保留快照，Attempt 事件同事务写 `job_attempt_events`；
- 事件仅保存 Lease Token SHA-256 指纹，不保存原 Token；终态事件保留对应 Worker 身份；
- Worker Handler 在数据库事务外执行，自动 Heartbeat 周期为 Lease 的三分之一；Fake Handler 通过同一正式 Worker 实现独立验证；
- Stage 4 不实现 Scheduler、Provider Request/Raw、Collection/Content 业务表或预算能力。

Stage 4 之后曾在 Stage 7 设计中引入过预算结构，但该功能已经通过新的向前 Migration `20260817_0015` 撤回。历史 Migration 保持不可变；当前 Schema、Contract 和运行时不得保留 Budget Account、Reservation Ledger、`request_budget` 或 dormant Budget 接口。未来如重新需要预算/限额，必须创建新的 L3 Change。

### 2.11 Stage 5A Provider-neutral 与 Raw Artifact

用户已批准把 Stage 5 首个正式单元拆为不含 Provider 数据库表的 Stage 5A。当前冻结：

- `ProviderRequestV1` 在 Scope 内以 Operation、脱敏稳定参数和分页输入形成确定性 fingerprint；逻辑 Request 拒绝 Secret；
- `ProviderAttemptV1` 版本化表达 `reserved/dispatching/completed/not_sent/unknown`、安全错误、费用快照和潜在重复计费；
- `ProviderClient` 每个 Attempt 最多调用一次注入的 `ProviderTransport`，不隐藏自动重试；Fake Transport 不访问网络、不保存 credential；
- 确定 HTTP 响应与发送前失败分开记录；发送后结果未知必须是 `unknown` 费用和 `potential_duplicate_charge=true`，不能承诺未计费；
- `RawEnvelopeV1` 固定为 `provider-response.v1`；Raw 递归脱敏后以确定性 JSON + gzip 保存，经 Artifact SHA-256、大小、gzip 和 Pydantic Contract 校验回放；
- Raw 使用 `raw/<provider>/<platform>/<YYYY>/<MM>/<DD>/<run>/<scope>/<attempt>.json.gz`，日期按 `Asia/Shanghai` 计算；Local Store 继续原子 no-overwrite；
- Raw 独立捕获后先保持 Artifact=`stored`；Stage 5D terminal 短事务建立 Provider Attempt 引用后标记 `linked`；
- Stage 5A 不包含真实 Provider/Operation、Provider/Collection 表、预算、Mapper、Candidate、Worker 注册、Probe 或生产部署。

Provider Request/Attempt 最终表采用 `03` 的 Schema，其中 `provider_requests.scope_id` 外键到 `collection_scopes`。Stage 5C 已补齐该持久化基础，Stage 5D 已补齐受 Job Fencing 约束的 dispatch、计费未知、Raw 关联和崩溃恢复。

### 2.12 Stage 5B Collection Run/Scope 父事实

用户已批准 Stage 5B 采用只建立 Collection 父事实的方案 A。当前冻结：

- 第三条 Revision 建立 `collection_runs/collection_scopes`，两表唯一写 Owner 为 `collection`；
- `collection_runs.job_id` 是 `jobs.id` 的非空唯一外键；Handler 未来通过反向关系取 Run，不把不可约束的 Run ID 作为 Job Payload 事实源；
- 本阶段 Run 只接受 `manual/api/backfill`，数据库拒绝 `scheduled`；`manual_plan_id/occurrence_id` 等待真实 Plan/Occurrence 父表后用附加 Migration 建立，禁止无外键占位列；
- Run 保留 `queued/running/partial_success/succeeded/failed/cancelled` 已批准白名单和非负计数；
- Blueprint 尚未冻结 Scope 完整状态枚举，本阶段不静默新增白名单；创建 Service 只写 `queued`，后续执行状态机 L3 再固化转换和约束；

- Stage 5B 不包含 Provider 表、Plan/Occurrence/Scheduler、预算、分页状态机、真实网络、HTTP API、前端或生产部署。

Stage 5B 完成只表示 Provider 来源链父事实就绪，不表示采集可运行。Stage 5C 已按最终外键建立 Provider Request/Attempt 持久化基础；未来 Plan/Occurrence 到位后再以附加 Migration 扩展 Run，不能重写第三条 Revision。

### 2.13 Stage 5C Provider 持久化基础

用户已批准 Stage 5C 采用方案 A。当前冻结：

- 第四条 Revision 按 `03` 最终字段建立 `provider_requests/provider_request_attempts`，两表唯一写 Owner 为 `collection`；
- `provider_requests.scope_id → collection_scopes.id`、`provider_request_attempts.provider_request_id → provider_requests.id` 和可空 `provider_request_attempts.raw_artifact_id → artifacts.id` 都是真实外键，禁止改用无约束 UUID；
- Request 以 `(scope_id, request_fingerprint)` 作为逻辑幂等键；创建前必须校验 `ProviderRequestV1.run_id/platform` 与真实 Scope 父链一致；

- `PostgresProviderRepository` 不提交事务、不执行外部 I/O，使未来 Worker 可在同一短事务内编排状态与业务事实；
- Stage 5C 不包含 dispatch、网络调用、费用 Reservation/Settlement、Raw 写入或关联、Artifact `linked`、Job Fencing/CAS、Reconciler、Candidate/Ingestion、HTTP API、前端或生产部署。

Stage 5C 完成只表示 Provider 持久化父链和未发送 Attempt 基础就绪，不表示采集可运行。该阶段遗留的 dispatch、计费未知、Raw 关联和崩溃恢复已由下一节 Stage 5D 在不改写第四条 Revision 的前提下补齐。

### 2.14 Stage 5D Provider Dispatch 与恢复

用户已批准 Stage 5D 采用方案 A：先建立不计费 Provider-neutral 纵切，不接真实付费 Provider。当前冻结：

- `JobExecutionFence(job_id, lease_token)` 是内部执行凭证，Token 不进入 Job Payload、日志或 `repr`；所有 Dispatch 开始和 terminal 可见写都验证 Job 仍为当前 `running`、Token 匹配且 Lease/Deadline 未过期；
- Dispatcher 先在短事务中锁住 Job 和 Attempt，以 CAS 把 `reserved → dispatching`；提交后才允许在事务外调用一次正式 `ProviderClient`，Transport 不得隐藏网络重试；
- Transport 明确证明没有进入外部发送边界时，活跃执行可把已进入数据库 `dispatching` 的 Attempt 终结为 `not_sent` 并清除发送开始时间；否则崩溃或结果不明不能声明未发送；
- `completed/unknown` 先通过正式 `RawArtifactService` 按数据库发送时间写入确定性路径并校验完整性，再在 terminal 短事务中由 Collection Owner 关联 Attempt、由 Artifact Owner 推进 `stored → linked`；Raw 引用只允许从空值设置一次，之后不可改写或清除；
- 接管新 Job Fence 或 Reaper 处理遗留 `dispatching` 时，先按确定性路径查找并校验 Raw；存在有效 Raw 就恢复其 terminal Attempt 并关联，不再调用 Provider；Raw 缺失或损坏则保守终结为 `unknown`、`billing_status=unknown`、`potential_duplicate_charge=true`，保留证据且不复发同一 Attempt；
- `provider_requests.status` 固定为最新 Attempt 快照 `pending/dispatching/completed/not_sent/unknown`；新 Attempt 创建时重置为 `pending`，已知费用按所有 Attempt 聚合；
- 第五条 Revision 只追加 Request 状态约束并修订现有来源 Trigger，不改写第四条 Revision，不创建预算、Content/Candidate 或 Scheduler 临时表；
- Stage 5D 的生产调用链只使用 Fake Transport 做自动化验证，不接真实 HTTP/SDK/文件 Provider，不产生费用，不注册 Collection Job Handler，也不实现预算 Reservation/Settlement、Candidate/Ingestion、API、前端或生产 Probe。

Stage 5 的 Provider-neutral 工程范围至此完成。真实付费 Provider 在后续 Stage 6/7 只能通过独立批准的 Operation/Probe/运行链接入，并继续保留 Provider Request/Attempt Billing、Raw 与审计；当前不存在预算前置门禁，也不得借付费调用恢复已撤回的 Budget Runtime。

### 2.16 Stage 7 真实 Provider Probe 与人工审阅边界

用户已确认：五个平台进入正式实现后，都必须保留可由开发者人工显式运行的统一 Real Provider Probe，用于真实 Provider 兼容性调试和人工数据核验；该 Probe 是开发/验收入口，不是第二套生产采集器。

固定边界：

```text
显式 Probe 配置
→ 正式 Provider Config / Secret 边界
→ 正式 Provider Client
→ 正式 Platform Operation / 分页
→ 逐请求完整脱敏 Raw
→ 正式 Mapper
→ Canonical Contract 校验
→ XLSX 等人工审阅派生物
```

- Probe 必须复用生产 Client、Operation、分页和 Mapper，不允许测试脚本自己拼 URL、复制 cursor/page 状态机、重新解释 Provider JSON 或维护第二套字段映射；
- Probe 必须允许按已经批准并实现的 Operation 显式配置真实 Provider Base URL、平台、Operation、关键词、内容/评论 ID、排序、时间范围、分页输入等该 Operation 支持的参数，并提供 `max_requests`、`max_pages` 等显式调用上限；不同平台的私有参数由各自 Operation 定义，不制造万能平台参数模型；
- 真实 Credential/API Key 必须从正式 Secret 边界取得；不得硬编码或进入源码、Git、日志、Raw、Canonical、XLSX、Job Payload 或数据库明文；调试不得绕过正式出站域名和安全校验；
- 每次真实请求的原始响应独立保存为完整脱敏 Raw JSON/GZIP，并继续运行正式 Mapper/Canonical 校验；Raw 是 Provider 原始证据，Canonical 是机器业务结构；
- XLSX 只用于人工阅读，是可从 Raw/Canonical 重新生成的派生物，不是 Provider 原始证据、Canonical Contract、数据库导入事实源或业务持久化格式；
- 真实 Probe 默认关闭，只能人工显式启动；明确提示可能产生费用，不进入普通 CI，不写生产业务数据库，不把未经脱敏的真实响应提交 Git；普通 CI 继续使用 Fake + 脱敏 Fixture；
- 人工审阅 XLSX 的具体布局由 `docs/测试与调试说明.md` 维护；Blueprint 只冻结 Raw/Canonical/人工审阅物的角色边界。

本节冻结 Probe 的安全/事实边界；五平台首版 Operation 与通用采集业务语义现由下一节和 [`08-采集策略与平台能力.md`](08-采集策略与平台能力.md) 批准。Scheduler 恢复策略已经单独批准并实现为 `latest_only + max_catch_up_runs=0`，完整语义以 [`09-Scheduler运行与恢复策略.md`](09-Scheduler运行与恢复策略.md) 为准。

### 2.17 Stage 7 五平台采集策略与平台能力

用户已批准 [`08-采集策略与平台能力.md`](08-采集策略与平台能力.md) 作为 Stage 7 采集业务设计，当前冻结：

- 五个平台默认 Provider 都是 TikHub；Platform 与 Provider 解耦，以后每个平台可单独显式更换 Provider；
- App/Web/V2/V3 只是 TikHub 内部 API family；每个 `Provider + Platform + Business Operation` 选择一个主 endpoint，不建立通用静默 fallback；
- 首版主链路固定为：小红书 App V2；抖音 Search V2 + App V3 详情/评论；微博 Web 搜索 + App 详情/一级评论 + Web V2 二级评论；B站 App 搜索/详情/评论；快手 App Search V2/详情/一级评论/二级评论；快手 Web 评论只保留显式 `verified_backup`，不自动 fallback；
- 当前仓库已建立五平台 Operation/Mapper/Capability/Registry 和合法脱敏真实 Fixture，并通过生产 Extractor/Mapper/Canonical/PostgreSQL 纵切验证；Real Probe 只证明特定时间点和输入的真实可调用性，不等于长期稳定 SLA；
- 前端配置规范化业务语义，由 Provider Capability 决定真实可选项；cursor/search_id/pageArea/max_id/API Key 等技术状态和 Secret 不进入普通业务 UI；
- 统一 Decision Pipeline 为 Search Raw → 先建 Candidate → Mapper/Observation → previous/current 比较 → 持久化 durable content action → Detail/Comment/Reply → Provider Request → Raw → Candidate → Mapper/Canonical/Ingestion；Search 已更新 Current 后的 Job retry/takeover 恢复未完成 action，不重新计算并丢失本次动作；
- 普通评论不由模糊“高价值”决定。默认 `comment_trigger=new_or_comment_changed`：可靠零评论或评论关闭直接短路，重复内容 `comment_count` 未变化不重抓评论，其他指标变化但评论数不变也不因此抓评论；评论数增加优先增量，减少只记录下降并受控刷新；
- 自适应评论默认 `full_fetch_threshold=50`、`sample_target=50`、`reply_target_per_root=5`、`comment_sort=latest_if_supported`；目标是软目标，整页已经返回的数据全部保留，Provider 仍有下一页时 target 命中只记 `partial` 并停止下一次付费请求；Provider 末页/显式空页、取消、错误和技术安全页数保持独立停止语义，技术截断不得伪造 `complete`；当前没有预算停止条件；
- 评论覆盖必须继续区分 `complete/partial/not_requested/unavailable`，并向页面/报告解释排序、目标、实际、平台报告总量和停止原因，不能把样本冒充全量；
- 时间窗口小于调度周期只 Warning，不阻止保存；Provider 不支持或参数非法才 Error；无原生时间筛选的平台必须在 Capability 中如实表达；
- Stage 7 自动 Deep Collection 默认关闭。人工从内容页触发 Deep 时只提交内部 `content_id`，后端解析平台/外部 ID/Provider；系统未发现的内容才使用高级外部 ID/分享链接入口；
- Provider Billing、endpoint Pricing、成本快照和 `potential_duplicate_charge` 继续作为执行/审计事实；当前系统不实现请求次数/金额预算、Budget Account、Reservation Ledger、Run/评论 Budget 或发送预算门禁，不保留 dormant Budget 接口；
- 保留 Operation Probe 和 Business Pipeline Probe。生产 previous state 来自 PostgreSQL，Business Probe previous state 可来自上一 Probe Snapshot，但两者复用同一生产 Decision Service，并输出可解释 decision 证据；
- Scheduler 固定 `latest_only + max_catch_up_runs=0`；正式 `collection.run.v1` Worker 已通过生产 Registry/JobWorker → `CollectionRunExecutor` → `TikHubCollectionScopeExecutor` 的 PostgreSQL/Fake Transport 纵切。

平台详细开发说明维护在 [`../collection/README.md`](../collection/README.md) 和五个平台文档；任何 endpoint、分页、Capability、Mapper/Fixture 状态变化都必须同步目标平台文档。

## 3. 版本选择与冻结政策

### 3.1 “最新稳定”的可执行定义

“最新稳定”只在**初始化或显式升级任务的核验时刻**使用：

1. 运行时和基础设施选择官方标记的 Stable/LTS 且仍受支持版本；
2. 语言包选择官方 Registry `latest` 指向的非 prerelease、非 yanked/deprecated 版本；
3. 排除 Alpha、Beta、RC、Nightly 和未发布主版本；如果项目自身的成熟度 classifier 仍是 Beta，但其版本号是 Registry 最新非预发布版，必须如实标注，不能改称 Production/Stable；
4. 选择必须满足本蓝图已批准的大版本兼容范围，并核验关键 engine/peer/Requires-Python 约束；
5. 初始化完成后立即写入版本声明和锁文件，Release 镜像再固定 digest。

“发现了更新”不等于“应升级”。日常启动、构建、功能开发和 CI 都禁止解析 `latest` 或自动改 Lock。升级只能通过独立提案/PR，说明发布说明、安全与兼容影响、Migration、回滚和完整验证结果。
