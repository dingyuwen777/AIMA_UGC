# 开发约束与分阶段实施

## 1. 这篇文档怎么用

这篇文档不是一般性建议，而是从空仓库开始开发时的执行规则。每个功能必须经历：

```text
确认事实和范围
→ 确定边界和契约
→ 写失败测试
→ 最小实现
→ 相关验证
→ 文档影响检查
→ Review
→ CI
→ 合并
```

不允许以“Vibe Coding 速度快”为理由跳过契约、测试、Migration、日志、安全和交付验证。

## 2. 项目目标

### 2.1 目标

- 建立可长期维护的多平台舆情监控系统；
- 支持 TikHub 五平台采集和后续 Provider 替换；
- 前端、后端、Worker、Scheduler、数据库独立开发和验证；
- Raw、Canonical、数据库、API 和日志边界清晰；
- 代码、Contract、Migration、测试和文档同步；
- 任何完成结论都有本轮新鲜验证证据；
- 新人根据文档可以定位常见修改入口。

### 2.2 范围

第一阶段包含：

- 用户和基础权限；
- 关键词和词包；
- 采集计划和 Run；
- TikHub 小红书、抖音、微博、B站、快手；
- Raw Artifact；
- 内容、评论、版本和指标历史；
- AI 标签和摘要；
- 告警、VOC、工单；
- 看板、查询、报告和导出；
- Docker Compose 本地和生产部署；
- 离线 Release、备份和回滚。

### 2.3 非目标

- 电商商品采集；
- 微服务；
- Kubernetes；
- 多数据库运行时兼容；
- 通用插件市场；
- 实时流式大数据平台；
- 自动替代人工运营判断；
- 未验证的全平台字段统一；
- 为未来假设预建大量抽象。

## 3. 成功标准

系统达到可发布状态必须同时满足：

1. 关键业务流程可从页面完成；
2. 五平台至少有一组脱敏真实 Fixture；
3. Provider、Mapper、ArtifactService/ArtifactStore、Ingestion 可独立验证；
4. API 契约和前端 Client 自动生成；
5. PostgreSQL Migration 可从空库和旧 Revision 升级；
6. Job 可重启恢复、幂等、重试、取消和超时；
7. 内容和评论当前值、版本、指标历史正确；
8. `.log` 文件、轮转、脱敏和关联 ID 正确；
9. Docker 离线 Release 可启动、备份和回滚；
10. 完整 CI 全绿；
11. 文档与最终代码一致；
12. 未验证内容被明确报告。

## 8. 设计规则

### 8.1 最小边界

只有以下情况创建 Port/Protocol：

- 连接第三方；
- 连接文件存储；
- 连接数据库且 Service 需要 Fake；
- 跨业务模块；
- 有两个真实实现；
- 独立测试明显受益。

禁止：

- 每个函数一套 Interface；
- 空 Facade；
- 无业务语义的 Manager；
- 万能 Repository；
- 为目录对称创建空文件；
- 运行时依赖注入框架；
- 用抽象掩盖不清楚的业务规则。

### 8.2 一份生产逻辑

Probe、测试、脚本、API 和 Worker 复用同一正式函数。

错误例子：

```text
生产 TikHub 分页实现一份
调试脚本再复制一份
测试又手写一份
```

正确：

```text
Operation 是唯一实现
Probe 提供真实输入
测试提供 Fixture/Fake
Worker 提供业务编排
```

### 8.3 依赖方向

业务模块不依赖具体前端、Docker 或服务器路径。`platform/` 不依赖业务模块。Provider 不写业务表。一个表只有一个写 Owner。

### 8.4 时间和 ID

- 外部 ID 一律字符串；
- 数据库时间 `timestamptz`；
- API UTC ISO-8601；
- 日志北京时间文本；
- 没有可靠来源不猜时间；
- 不可混用秒和毫秒。

## 9. Red-Green-Refactor

### 9.1 Red

先写最小测试并实际运行，确认因缺少目标行为失败。

缺陷修复必须有回归测试证明：

```text
修复前失败
修复后通过
```

### 9.2 Green

只写使测试通过的最少代码。禁止同时重构无关模块、升级依赖或扩大范围。

### 9.3 Refactor

测试通过后才能重构。重构后重新运行目标和相关测试。

### 9.4 例外

纯文档、生成文件、一次性 Migration 脚本或外部付费 Probe 无法完整 TDD 时，必须写明原因和替代验证，不能伪造 Red 过程。

文档例外仍要求确定性验证：Markdown/链接/JSON 示例、术语和冲突扫描、合订本重建、Manifest 与 SHA-256 重算；这些结果只证明文档一致性，不能冒充代码、性能、安全或生产验证。


### 10.1 Unit

- 错误分类；

### 10.2 Contract

- Canonical；
- Job Payload；

- Provider Fixture；

### 10.3 Integration

使用隔离 PostgreSQL：

- Repository；
- Migration；
- Job；
- Ingestion；
- 事务和并发；
- 查询索引；
- 备份恢复脚本的非破坏检查。

Job/调度专项至少覆盖：claim 后、外部 HTTP 前后、Raw 落盘后、业务事务提交前后和终态更新前杀死 Worker；旧/新 Lease 并发；Attempt Deadline 到期但 Heartbeat 仍存活；Reaper 的超时/取消/次数耗尽 CAS；次数耗尽的 transient 不会留下 queued；多 Scheduler 同一 Occurrence；Plan 在预扫后被禁用/改版本；Scheduler 在每个提交边界崩溃和停机多周期后的有界 misfire/catch-up。API 幂等覆盖同 key 同/异 Payload、跨用户和过期复用。预算覆盖 global/run/content_comments 多级账户的并发预留、结算、释放和计费未知，并分别证明 global+run 必需、评论额外 content 必需、缺账户关闭失败、新 HTTP Attempt 必须新预留、同一 Attempt 的预留事务重放不会重复预留。Provider Dispatch 覆盖旧/伪 Job Token、`reserved` 提交后、CAS 前、CAS 后/socket 前后崩溃，并检查 Transport 不在一个 Attempt 内自动重发，证明 `dispatching` 不复发且按 unknown 保守处理。Artifact 覆盖 pending 的空 SHA/大小、孤儿文件、缺失文件和各生命周期状态对账。协调备份分别把 API 事务、Artifact rename、关联事务和删除暂停在屏障前后，证明独占 advisory lock 会等待全部共享写者退出，并在数据库/文件捕获完成前阻止新写入。

### 10.4 API

使用真实 Router 和 Service，外部 Provider 用 Fake。验证状态码、统一错误、Session/CSRF/RBAC/对象级授权、API 幂等、ID、时间以及签名并绑定查询条件的 Cursor。SSRF 测试覆盖 DNS 解析和重定向，上传/下载覆盖路径、Zip、大小和日志注入边界。

### 10.5 Frontend

- Store；
- Feature API；

- loading/error/empty；
- 64 位 ID；
- 时间显示；
- 权限按钮只是展示，后端仍验证。

关键流程：

```text

→ 配词包

→ 查看 Run
→ 查看内容/评论
```

阶段 0 另建立真实中文查询集，在隔离 PostgreSQL 中记录召回质量、延迟和 `EXPLAIN`；生产 Release 前执行容量/长时间 Soak、协调数据库+Artifact 恢复和回滚演练。

## 11. 目标验证命令

新仓库完成相应阶段后，命令必须可执行。

## 13. 依赖

### 13.1 Python

- 初始化时按 `07-技术决策与实施门禁.md` 中编制日已核验的最新稳定版本声明直接依赖，并生成锁文件；
- 只在 `pyproject.toml` 声明；
- 精确解析写入 `uv.lock`；
- `uv.lock` 提交 Git；
- CI 使用 `--locked`；
- 普通功能不升级依赖；
- 新增依赖前说明必要性、许可证、维护状态、体积和替代方案。
- 未来存在更新不等于应升级；升级是独立任务，先核验一手发布说明、兼容性和安全影响，再更新声明与 Lock 并跑完整门禁。

### 13.2 Frontend

- Node 使用仓库声明固定精确 24 LTS patch，npm 依赖由 `package-lock.json` 固定；
- `package-lock.json` 提交 Git；
- CI 使用 `npm ci`；
- 禁止使用不锁定的安装结果发布；
- 不同时引入 npm、pnpm、yarn；
- UI 和工具库按实际功能选，不堆重复组件库。

### 13.3 基础镜像

Release 固定 digest，禁止 `latest`。版本标签只帮助阅读，digest 才是发布事实。小版本升级单独 PR，执行完整构建、Migration、集成、安全和离线冒烟；不得在普通功能或镜像重建时自动漂移。

## 17. 分阶段实施

### 阶段 0：产品和字段基线

→ 修改范围：产品范围/非目标、页面和角色、五平台能力矩阵、Canonical 示例、数据隐私、中文检索样本、容量/SLO/RPO/RTO  
→ 预期结果：明确每个平台所选 Operation、字段、分页/评论/费用能力与真实脱敏 Fixture；批准刷新/保留、日请求和数据量、Worker 并发、最大 Run、API 延迟、磁盘预算、RPO/RTO  
→ 验证：业务与技术共同 Review；所有 Canonical 示例可解析；能力矩阵每个平台均有官方依据和 Fixture；中文检索基准、容量预算和恢复目标有可验收数值  
→ 门禁：任何一项未批准时，不得批量实现五平台、承诺中文检索效果或宣称生产容量/恢复方案成立

### 阶段 1：仓库骨架和工具链

→ 修改范围：方案 A 目录、运行时声明、根 Python build backend 与 `backend/src` package discovery、`pyproject.toml`、`uv.lock`、前端直接依赖与 Lock、Ruff、mypy、pytest、CI、OpenAPI SDK 与前端 Lint PoC  
→ 预期结果：应用作为可安装 package 运行，空 API、前端、测试和构建可运行；选定支持 TypeScript 7 且生成可调用 Client 的 OpenAPI 工具；选定完整可运行的 ESLint/Vue/TypeScript 组合  
→ 验证：Python/Node 精确版本、Lock、`uv run python -c "import aima_ugc"`、Wheel 安装/内容、生成 Client 编译、Lint、Type、Unit、Build 和 `linux/amd64` CI 全部通过；不允许用临时 `PYTHONPATH`/`sys.path` 补丁，不采用与 TypeScript 7 peer 约束冲突的生成器
