# 开发约束与分阶段实施

这篇文档回答：**在这个仓库里改一个功能，怎样避免“代码能跑，但 Contract、数据库、测试、文档和 Git 状态已经互相矛盾”。**

统一入口仍是仓库根 [`../../AGENTS.md`](../../AGENTS.md) 和 `.agents/skills/reliable-vibe-coding/SKILL.md`。本文不复制 Skill 的全部细节，只保留项目长期开发约束。

## 1. 一次正常开发的最短闭环

```text
确认当前仓库事实
→ 明确目标/范围/非目标
→ 判断 L1/L2/L3
→ 必要时建立/认领 Change
→ 找真实 Owner / Contract / Schema
→ 写失败测试或说明测试例外
→ 最小实现
→ 同步受影响文档
→ 目标测试 + 回归 + 静态/构建检查
→ Review
→ CI
→ Git 交付
```

“Vibe Coding”只改变写代码的速度，不改变验证责任。

## 2. 为什么每次都先读当前代码

AIMA_UGC 已经快速演进过多个 Stage。聊天、旧 PR、旧 Blueprint 段落都可能比 main 落后。

因此事实优先：

```text
用户本轮明确决定 / 已批准 Change
+ 当前代码
+ Contract
+ Migration
+ 锁文件
+ 生成物
+ 测试
```

如果文档和机器事实冲突，不能机械选一边：

1. 先判断是实现偏离设计，还是文档过期；
2. 如果代码错，修代码；
3. 如果已批准实现改变了事实，修正式文档；
4. 同一任务收口。

## 3. L1 / L2 / L3 怎么理解

### L1

机械、低风险、行为不变，例如：

- 明确错别字；
- 小范围文档链接修复；
- 不改变行为的极小修正。

### L2

多文件或重要行为变化，例如：

- 新功能；
- 重要 Bug；
- 模块内重构；
- 多文档治理；
- 需要多人/多 Agent 跟踪的任务。

需要 Change。

### L3

会改变系统长期边界：

- 公共 HTTP Contract；
- Schema / Migration；
- 跨模块 Contract；
- 认证授权；
- 安全；
- 部署；
- 重大依赖；
- 破坏性兼容变化。

需要比较方案、明确迁移/回滚并通过上游决策门禁。

行数少不代表风险小。

## 4. 什么事情不能由 Agent 自己拍板

如果仓库里没有已批准事实，而某个决定会实质影响：

- 业务语义；
- 公共 Contract；
- Schema；
- 安全/权限；
- 隐私/删除；
- Provider Operation；
- 费用/预算；
- 调度策略；
- SLO/RPO/RTO；
- 不可逆兼容行为；

就先调查事实，给出推荐方案和必要备选，再由业务 Owner 决定。

已经固化过的决定直接读事实源执行，不重复问。

## 5. 模块边界是为了减少修改面

后端允许调用链：

```text
Router
→ Service
→ Model / Port
→ Repository / Adapter
```

外部数据：

```text
Provider
→ Raw
→ Mapper
→ Canonical
→ Ingestion
→ Owner Repository
→ PostgreSQL
```

读取：

```text
PostgreSQL
→ Query Repository / Read Model
→ Query Service
→ Router / API
```

禁止：

- Router 直接 SQL；
- Provider 直接写业务表；
- Mapper 查数据库/发 HTTP/做 AI 分类；
- 前端直接访问数据库；
- Feature 复制另一个 Feature 的 Store/API；
- 为同一能力造平行 Mapper/Repository/Client/Job；
- 为了目录对称创建空抽象。

## 6. Contract 和生成物怎么改

### HTTP

```text
Pydantic Request/Response
→ OpenAPI
→ TypeScript Client
```

### Canonical

```text
Pydantic Canonical Model
→ JSON Schema
→ Mapper/Ingestion/Contract Test
```

### Job

```text
版本化 Pydantic Payload
→ Job Registry / Handler / Contract Test
```

生成目录禁止手改。改事实源后重新生成并验证差异。

## 7. 数据库怎么改

正式 Schema 改动必须：

```text
当前模型/需求
→ 新 Alembic Revision
→ old revision → head 验证
→ base → head 验证（适用时）
→ downgrade/upgrade 安全性
→ alembic check
```

不改已经发布的历史 Migration。

一个表只有一个写 Owner；外部 HTTP 不放数据库事务里；业务事实和需要的下游 Job 同事务提交。

## 8. Red-Green-Refactor 什么时候用

### 新功能/缺陷/重构

```text
Red
→ 先观察目标行为确实失败

Green
→ 最少代码让目标通过

Refactor
→ 保持测试绿的前提下整理
```

### 文档/生成文件/环境任务

无法合理 TDD 时，不伪造 Red。

改用：

- 链接/结构检查；
- 解析/生成差异；
- 构建；
- 实际运行；
- Repo-wide 冲突扫描。

必须明确验证证明了什么、没证明什么。

## 9. 调试入口必须复用生产实现

正确：

```text
生产 Operation 是唯一逻辑
Probe 给真实输入
Fixture/Fake 给可控输入
Worker/API 做正式编排
```

错误：

```text
生产一套 Provider 分页
测试脚本复制一套
调试脚本再复制一套
```

当前 `tikhub_test`、`imports_test` 的价值就是提供独立验证入口，但正式写库模式仍复用生产 Collection/Ingestion/Reporting/Analysis 能力。

## 10. 文档怎么分层

当前正式文档分四层：

```text
Blueprint
→ 长期架构、为什么这样设计、稳定边界
\模块 README
→ 当前代码怎么实现、常见修改入口

Appendix
→ Scheduler/TikHub/Excel/AI/SQL/报告等专题细节和调试

Guide
→ Figma 等开发工作流
```

另外：

```text
机器精确事实
→ Contract / Migration / tables.py / generated / tests / locks

历史为什么改变
→ changes/archive/
```

不要把阶段流水塞回 Blueprint，也不要让 Appendix 成为第二套 Schema。

## 11. 文档写作要求

所有长期文档从实际问题出发：

```text
为什么需要
→ 输入是什么
→ 数据/调用怎么走
→ 当前代码在哪
→ 最小例子
→ 限制/未实现
→ 精确事实源
```

要求：

- 假设读者基础一般；
- 第一次出现的必要术语用白话解释；
- 不为了显得专业堆“高可用、企业级、先进架构”等空话；
- 是否贴代码/表名取决于是否帮助理解；
- 示例要短、真实、可验证；
- “已实现/未实现/默认行为”必须有当前仓库事实依据。

## 13. 文档同步不是收尾可选项

改代码以后至少语义检查：

- Blueprint；
- 模块 README；
- API 说明；
- Contract/Schema；
- Migration；
- 配置示例；
- 测试/调试说明；
- 环境/部署说明。

行为不影响文档时可以明确记录“不受影响”，不要为了留下修改痕迹乱改文档。

## 14. Git 规则

基本流程：

```text
从当前 main 建任务分支
→ 保留用户已有修改
→ 只提交任务范围文件
→ 中文、可读 commit
→ PR
→ 新鲜 CI
→ Review
→ 按授权合并
→ Change 归档
```

禁止：

- force push 覆盖别人的工作；
- `reset --hard` 清理未知修改；
- 绕过 CI/Branch Protection；
- 未验证就宣称完成；
- 一个任务顺手大规模升级依赖。

## 16. Stage 9 的边界

Stage 9 可以继续建设 Analysis/Monitoring，但开始具体子阶段前仍要重新读取当前 main 和正式 Blueprint，自行判断下一个最小单元。

不能因为 Stage 名称叫“Monitoring”就提前假设：

- 告警表已经存在；
- 风险规则已经定义；
- VOC/工单 Contract 已冻结；
- Dashboard 聚合模块已经存在。

这些都要由对应 Change/实现/Migration 形成新事实。

## 17. 开始一个任务应该读什么

固定：

1. `AGENTS.md`；
2. `.agents/skills/reliable-vibe-coding/SKILL.md`；
3. `docs/blueprint/README.md`；
4. `07-技术决策与实施门禁.md`；
5. 当前任务对应的 Blueprint/Appendix/Guide；
6. 相关模块 README；
7. Contract、Migration、实现、测试、配置。

只读和当前任务直接相关的东西，不用“读完整仓库”代替真正理解调用链。
