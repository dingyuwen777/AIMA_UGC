# 1. 每个任务的固定闭环

```text
恢复当前事实
→ 明确目标/范围/非目标
→ 找到 Owner / Contract / Schema / 调用链
→ 检查 Active Change 冲突
→ 按 L1/L2/L3 建立任务契约
→ 行为变化先建立失败证据/测试
→ 最小实现
→ 目标测试
→ 相关回归
→ 文档事实同步
→ Review
→ PR 最新 HEAD CI
→ 合并
→ Change 归档
```

不能因为使用 AI/Vibe Coding 就跳过：

- 事实恢复；
- 数据 Owner；
- Migration；
- Contract；
- 测试；
- 文档；
- CI；
- Git 交付状态。

# 3. 当前事实优先级

发生冲突时不要机械“代码优先”或“文档优先”。

工作顺序：

```text
用户本轮明确决定 / 已批准 Change
→ 当前代码、Contract、Migration、generated、tests、locks
→ Blueprint 07 已确认跨模块决定
→ 对应领域 Blueprint
→ 模块 README / Appendix / Guide
→ 历史 Change / 聊天
```

要判断：

```text
代码偏离已批准设计？
→ 修代码

代码已经形成新批准事实，文档落后？
→ 修文档

两边都不能确认？
→ 调查/提请上游决策
```

禁止为了“文档一致”把实现 Bug 写成正式设计。

# 4. 任务等级

以 `.agents/skills/reliable-vibe-coding/SKILL.md` 当前规则为准。

## L1

适合：

- 纯机械文案/路径修正；
- 行为不变的极小修改；
- 影响面非常隔离的简单修复。

不要求 Change，但仍需要验证。

## L2

适合：

- 新功能；
- 行为变化；
- 多文件重要修复；
- 需要追踪的文档/架构治理；
- 并行协作影响。

需要一个 Active Change。

## L3

适合：

- 公共 API；
- Schema/Migration；
- Canonical/跨模块 Contract；
- 认证授权；
- 安全；
- 部署/恢复；
- 重大依赖；
- 破坏性兼容变化。

必须先比较方案并确定上游业务/技术决策。

“只改几行”不代表 L1。删除一个 API 字段可能比新增 500 行内部代码风险更高。

---

# 5. L2/L3 Change 负责什么

路径：

```text
changes/active/<CHANGE_ID>/CHANGE.md
```

它记录：

```text
为什么做
目标
成功标准
范围
非目标
必须保持不变
受影响路径/领域
验证计划
当前交付状态
```

Change 不是系统当前说明书。

完成后：

```text
正式当前事实
→ Blueprint / README / Contract / Migration / Test

历史为什么这样改
→ changes/archive/<year-month>/
```

不要因为已经有 Change，就不更新长期文档。

---

# 6. Active Change 并行冲突

任务开始前读取：

```text
changes/active/*/CHANGE.md
```

关注真正共享的事实：

- 同一个表/Owner；
- 同一个 Contract；
- 同一个 Migration head；
- 同一个 Prompt；
- 同一个 API Route；
- 同一个前端 Feature；
- 同一个文档事实源；
- 同一共享测试/配置。

只有实际交集才叫冲突，不因为“两个任务都涉及后端”就阻塞。

已合并 PR 对应的 Change 不能长期残留 `active`，否则后续 Agent 会误判并行状态。

# 7. 开码前的任务契约

复杂任务至少写清：

```text
背景与当前代码事实

可观察成功标准
范围
非目标
输入/输出
Owner

数据/Migration
必须保持不变
预计修改文件
测试
部署
回滚
文档同步

```

每一步用：

```text
[步骤]
→ 修改范围
→ 预期行为
→ 验证方式
```

```text
1. 优化架构
2. 完善代码
3. 测试一下
```

# 8. 哪些决定必须由业务 Owner 确认

仓库无法确认、且会改变以下语义时，不得静默选择：

- 数据保留/删除；
- 公共 API；
- Canonical；
- Schema；
- 权限/认证；
- Provider Operation；
- 费用/预算；
- 调度；
- SLO/RPO/RTO；
- 破坏性兼容；
- 不可逆 Migration。

Agent 应先调查仓库/真实资料，给出推荐和真实备选，再由业务 Owner 决策。

已经明确并固化过的决定不重复问。

# 9. Red → Green → Refactor

新行为、Bug 修复、重构默认使用：

```text
Red
→ 先观察目标测试因缺少/错误行为失败

Green
→ 最小代码让测试通过

Refactor
→ 行为绿后再整理
```

Bug 修复必须能证明：

```text
修复前失败
修复后通过
```

不能先把代码改好，再写一个永远不会失败的“装饰测试”。

---

# 10. 哪些任务不强行 TDD

以下可以采用替代验证：

- 纯文档；
- 生成物同步；
- 纯配置；
- 受控真实付费 Probe；
- 无合理失败测试的一次性操作。

例如文档治理：

```text
旧路径扫描
Markdown 链接检查
事实源对照
架构/Owner 检查
CI
```

不要为了形式编造一个假 Red。

# 11. 测试分层

```text
Unit
→ Contract
→ Integration(PostgreSQL)
→ API
→ Frontend Unit
→ E2E
→ Release / Runtime 验证
```

## 11.1 Unit

适合：

- Mapper；
- Pagination；
- Scheduler Cron；
- Decision；
- AI Validator；
- Cursor；
- 日志 Formatter；
- Excel Renderer；
- Word Report 统计/OOXML。

## 11.2 Contract

保护：

- Canonical；
- HTTP Pydantic；
- Job Payload；
- Prompt/Taxonomy；
- Sanitized Provider Fixture；
- OpenAPI / generated Client。

## 11.3 Integration

必须使用真实 PostgreSQL 行为验证：

- UNIQUE/FK/CHECK；
- Transaction；
- Row Lock；
- `SKIP LOCKED`；
- Fencing；
- Migration；
- Ingestion Current/Version/Metric；
- Scheduler 并发；
- Analysis/Export 持久化。

不能用 SQLite 通过后声称 PostgreSQL 已验证。

## 11.4 API

至少覆盖：

- HTTP status；
- Request/Response Contract；
- 错误结构；
- 404/409/422 等边界；
- Job 创建事务；
- Cursor；
- 下载未就绪；
- multipart/resource limits。

## 11.5 Frontend

当前 Feature：

```text
voice-plaza
import-batches
collection-strategy
```

使用 generated Client Mock，不手写第二套后端类型。

# 12. 数据库变化的固定流程

→ old revision → head

→ alembic check

- 手工生产 ALTER 后不补 Revision；
- 多模块各自写同一表；
- 为测试方便取消真实约束。

# 16. 文档是交付门禁

代码改变系统事实时，同一任务必须检查：

```text
Blueprint
模块 README
Appendix / Guide
API 说明
测试/调试说明
部署说明
AGENTS 导航
根 README
```

但不是“每次改代码都全部重写文档”。

判断原则：

```text
长期架构变化
→ Blueprint

当前模块实现变化
→ Module README

专题深度/调试变化
→ Appendix

开发操作流程变化
→ Guide

精确字段变化
→ Contract/Migration/tables/generated；文档只更新必要说明/导航
```

# 17. 正式文档写作标准

文档必须能让读者回答：

```text
为什么需要？
输入/输出是什么？
完整调用链怎么走？
当前代码在哪？
核心类/函数/表/Contract 是什么？
要改这个行为应该先改哪里？
怎么验证？
怎么调试？
当前限制是什么？
精确机器事实在哪？
```

禁止把文档写成：

```text
系统采用先进架构
模块高度解耦
具备企业级能力
后续可扩展
```

却不给实际机制和代码入口。

文档结构调整**不能等于信息压缩**：旧文档有效的真实 Endpoint、字段路径、状态机、SQL、恢复边界、测试方法必须保留或用更准确的当前实现替代。

# 19. 质量门禁

仓库已有的检查必须按影响面执行。

常用：

```bash
uv run ruff format --check backend tests scripts
uv run ruff check backend tests scripts
uv run mypy backend/src
uv run pytest tests/unit -q
uv run pytest tests/contracts -q
uv run pytest tests/api -q
python scripts/quality/check_architecture.py
python scripts/quality/check_table_ownership.py
python scripts/quality/scan_secrets.py
python scripts/quality/check_docs.py
```

数据库/Migration/Frontend/Stage 专项以当前 CI Workflow 和受影响路径为准。

门禁失败：

```text
修根因
```

禁止：

- skip 测试；
- 删除断言；
- 降低质量阈值；
- 针对测试硬编码；
- 用旧 CI 冒充最新 HEAD。

# 21. Git 交付

从最新 `main` 建任务分支。

分支前缀：

```text
feature/
fix/
refactor/
docs/
test/
build/
chore/
migration/
```

禁止：

- `reset --hard`；
- `clean -fd`；
- force push；
- 覆盖用户修改；
- 绕过 CI；
- 未授权直接推 main。

提交信息使用中文。

复杂变更默认通过 PR；最终依据 PR **最新 head** 的 CI，而不是中间某个旧 commit 的绿灯。

# 22. 完成报告必须提供什么

不能只说：

```text
完成了，测试通过
```

至少报告：

```text
变更摘要
关键文件/目的
Contract/Schema/Migration 是否变化
文档同步
实际验证命令/CI
未验证风险
兼容性
部署/回滚
分支/commit/PR/merge 状态
```

只有当前 HEAD 的实际证据才能支持“可合并/完成”。

- TikHub 五平台 Collection；
