# 2. 当前日志实现在哪里

```text
backend/src/aima_ugc/platform/logging/
├─ formatter.py
└─ setup.py
```

当前正式进程日志：

```text
api       → api.log
worker    → worker.log
scheduler → scheduler.log
```

Migration 当前没有独立长期应用日志文件映射，执行输出以调用环境/CLI 为准。

`configure_service_logging()` 同时创建：

```text

```

文件日志是人工排障主入口；stdout 适合未来容器/平台辅助收集。

# 3. 当前日志一行是什么样

Formatter：

```text
backend/src/aima_ugc/platform/logging/formatter.py
```

格式概念：

```text
[YYYY-MM-DD HH:mm:ss.SSS file.py L123]
[INFO]
event=stable.event
job_id="..."
run_id="..."
message="..."
```

人工日志时间显示：

```text
Asia/Shanghai
```

数据库机器时间仍用 `timestamptz`，不要混淆。

真实调用文件和源码行号放在前缀，是为了让人工排障可以直接跳回代码。

---

# 4. 日志脱敏是代码能力，不只是规范

`formatter.py` 当前会：

- 对敏感 key 递归替换为 `***`；
- 清理 `Bearer ...`；
- 清理 password/token/api key/cookie 等 inline 值；
- 清理 PostgreSQL URL 密码；
- 对常见邮箱/手机号/身份证形态做基础脱敏；
- 对 dict/list/tuple 递归脱敏；
- 截断过长字段/异常/整行；
- 把换行转义成单行；
- 安全 traceback 不复制可能带 Secret 的 source line/message。

精确限制常量直接看：

```text
_FIELD_LIMIT
_EXCEPTION_LIMIT
_LINE_LIMIT
_MAX_TRACEBACK_FRAMES
```

不要把具体数字在文档里维护成第二份 Contract。

# 5. 日志级别怎么用

```text
DEBUG
→ 正常轮询、空 Scheduler tick、高频成功细节

INFO
→ 低频重要生命周期、真正业务结果

WARNING
→ Retry、部分失败、需要关注但系统还能继续

ERROR
→ 永久失败、非法配置、需要人工介入或未预期异常
```

例如：

```text
Scheduler 空 tick
→ DEBUG

初始化 cursor / enqueue / misfire skip
→ INFO

某个 Plan 失败
→ ERROR plan event
+ tick summary WARNING
```

不要用 INFO 日志证明进程存活；健康由 Health 和实际 Job/Run 事实判断。

## 5.1 功能开发时怎样选择日志观测点

仓库已经具备正式应用日志体系，因此实现重要功能时不能只考虑返回值和数据库结果，也要判断后期排障是否需要补充**最小充分**的运行过程日志。

优先记录：低频重要生命周期、Job/Run/Batch 等关键状态变化、外部 I/O 的安全结果摘要、Retry/部分失败/跳过/取消/永久失败，以及能显著帮助定位“执行到哪一步”的关键分支。优先复用已有 `request_id/job_id/run_id/batch_id/content_id` 等真实关联 ID 和稳定 event，不为日志新造业务身份。

同时控制日志噪声：逐条记录、正常轮询、循环内部高频成功细节使用 DEBUG 或不记录；INFO 保留给真正重要且低频的生命周期/业务结果。同一异常原则上在拥有处理或终止责任的边界记录一次，避免多层重复 traceback。

新增日志必须继续经过现有 Formatter/脱敏/轮转边界，禁止主动记录 Secret、Token、密码、Authorization、敏感 Raw/Payload 或未脱敏 PII。日志只辅助解释“为什么/在哪一步”，不能替代 PostgreSQL 业务事实、Artifact、Health 或正式审计表。

# 6. 日志轮转

精确默认值看：

```text

```

# 8. Secret 当前怎么进入系统

当前原则：

```text
非敏感配置
→ 环境变量 / 当前 env example

Secret 值
→ AIMA_SECRET_DIR 下只读文件

数据库/业务配置
→ 只保存 secret_ref
```

常见 Secret 包括：

```text
postgres_password
LLM API Key
Content Cursor signing key
Import Batch Cursor signing key
Collection Runtime Cursor signing key
```

精确文件名和路径以：

```text
backend/src/aima_ugc/platform/config/settings.py
```

为准。

Worker Provider Secret 解析主要看：

```text
backend/src/aima_ugc/bootstrap/worker.py
backend/src/aima_ugc/platform/security/
```

Secret 禁止进入：

- Git；
- Job Payload；
- Plan config；
- Raw；
- Fixture；
- 日志；
- Error Response；
- Export/Word。

# 9. TikHub 出站安全

TikHub Base URL 可配置不等于任意 URL 都可以带 Bearer Secret。

当前 Transport 会把 Secret 限制到批准的 TikHub HTTPS Origin。

代码：

```text
backend/src/aima_ugc/adapters/providers/tikhub/transport.py
backend/src/aima_ugc/platform/security/
```

不能为了调试把：

```text
verify=false
任意 redirect
任意 host
```

放宽成生产默认。

# 10. 当前认证状态

当前已经有真实业务 API 和 Vue 页面，但**企业登录/正式认证授权尚未闭环**。

所以：

```text
业务功能已存在
≠ 可以安全公网暴露写 API
```

未来身份 Provider 的长期边界：

```text
External Identity Provider
→ Authentication Adapter
→ Principal / AuthContext
→ 后端 Authorization
```

业务模块不能直接把飞书 `open_id/union_id` 等 Provider 私有身份当长期业务主键。

认证、授权、Session/OIDC/飞书接入属于独立高风险变更，也是生产 Go-Live 前置条件。

详细生产路线：

# 11. Health API 当前做什么

当前 Route：

```text
GET /health/live
GET /health/ready
```

机器实现：

```text
backend/src/aima_ugc/bootstrap/api.py
backend/src/aima_ugc/platform/health.py
```

`live`：进程是否能响应。

`ready`：检查当前装配要求的关键依赖，例如 PostgreSQL、ArtifactStore 和日志目录可写边界；失败时返回简化状态，不把内部异常直接暴露给客户端。

`/ready=200` 不等于 TikHub、LLM 和全部业务流程都已生产验收。

# 14. PostgreSQL 与 Artifact 为什么不能只备份一个

业务来源可能形成：

```text
content_versions.raw_artifact_id
→ artifacts metadata
→ ArtifactStore bytes
```

只备份数据库：

```text
ID 在
→ bytes 可能丢
```

只备份文件：

```text
bytes 在
→ 业务关系/Job/Content 可能丢
```

所以长期正确恢复单位是：

```text
PostgreSQL + ArtifactStore 的协调 Backup Set
```

# 16. Migration 为什么独立进程

当前入口：

```text
backend/src/aima_ugc/entrypoints/migrate_main.py
backend/src/aima_ugc/bootstrap/migration.py
```

Schema 演进：

```text
migrations/versions/
```

不能：

- API 启动 `create_all()`；
- 多个 API 实例同时跑 Migration；
- 手工改生产库后不补 Alembic；
- 修改已发布历史 Migration。

当前没有正式 Compose Release，所以发布时怎样调用 migrate 仍是 Stage 11 待代码化流程；目标发布顺序见生产 Release 附录。
