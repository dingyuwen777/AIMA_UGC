# 日志、安全、部署与运维

这篇文档回答：**系统出问题时去哪里看、什么信息绝对不能进日志、当前已经有哪些运行保障、哪些 Release/备份能力仍然只是下一步。**

本章只保留长期规则。具体环境启动命令见 [`../环境运行与部署.md`](../环境运行与部署.md)。

## 1. 先分清四种“记录”

很多问题来自把它们都叫日志：

```text
应用 .log
→ 人工排障

Docker stdout/stderr
→ 容器启动、崩溃等辅助排障

PostgreSQL audit_events
→ 关键业务/管理操作审计

Raw Artifact
→ Provider 当时真实响应证据
```

它们不能互相替代。

Provider Raw 不能为了“查起来方便”打印进日志；审计事件也不能只靠轮转 `.log` 保存。

## 2. 当前应用日志是主要排障入口

当前 API、Worker、Scheduler 使用统一日志实现，应用 `.log` 是主要诊断来源。

人工可读格式：

```text
[2026-08-21 16:48:14.113 provider_dispatch.py L184] [WARNING] event=provider.request.failed ...
```

固定原则：

- 时间按 `Asia/Shanghai` 显示；
- 格式 `YYYY-MM-DD HH:mm:ss.SSS`；
- 前缀给真实调用文件和源码行号；
- 级别单独显示；
- 后面使用稳定 `event=` 和关联 ID；
- 日志文件名已经区分进程，所以每行不重复 `service=`；
- 机器交换时间仍使用带时区的类型/ISO-8601，不能因为日志显示格式而丢时区。

## 3. INFO、WARNING、ERROR、DEBUG 怎么用

日志不是“代码每走一步都打一行”。标准是：**这条日志能不能帮助回答发生了什么、影响谁、为什么失败、能否恢复。**

### INFO

低频、重要生命周期：

- 进程启动/停止；
- Job 开始、成功、取消；
- Collection Run 开始、成功、取消；
- Scheduler 真正初始化/入队/产生 skip；
- 重要异步任务终态。

### WARNING / ERROR

真正需要处理的问题：

- Provider 请求失败；
- Job retry / 永久失败；
- Lease/Heartbeat 异常；
- Collection partial/failed；
- Scheduler rejected Plan；
- 未预期 API 500；
- 资源释放失败。

### DEBUG

正常但高频的细节：

- Scheduler 空 tick；
- Provider request started/completed；
- 成功 Scope；
- 其他普通轮询/细节。

因此当前 Scheduler 不会每 30 秒无条件产生一条 INFO。

## 4. 日志轮转

当前应用日志默认使用 Python 标准库轮转：

```text
单文件约 20 MiB
备份 10 份
旧文件 gzip
UTF-8
重启继续追加
```

实际配置项见 `env.local.example` / 运行配置和日志实现，不在 Blueprint 再复制一套默认值事实。

多个进程不能同时写同一个普通 `RotatingFileHandler` 文件；如果未来同类服务多实例，需要稳定实例区分或改变日志收集方式。

## 5. Secret 永远不能进入业务日志

禁止记录：

- Authorization；
- Bearer Token；
- API Key；
- Cookie；
- password/secret/token/credential；
- 数据库密码；
- Provider 完整 request/query/body；
- Provider Raw body；
- 用户完整正文/评论正文作为普通诊断字段。

Formatter 会做统一脱敏、控制字符转义和长度限制，但这只是最后防线。

正确原则：

> 业务代码从一开始就不把 Secret 交给 Logger。

未预期异常使用安全调用栈：保留文件名、行号、函数和异常类型，不把可能包含 Secret 的原始异常 message/源代码行直接塞进 LogRecord。

## 6. Secret 怎么保存

本地非敏感配置用 `AIMA_*` 环境变量；真实 Secret 放 `AIMA_SECRET_DIR` 下的只读文件。

当前示例包括：

```text
postgres_password
llm_api_key
各 Cursor signing key
Provider secret_ref 对应 Secret
```

规则：

- 不提交 Git；
- 不写数据库明文；
- 不进 Job Payload；
- 不进 Run Snapshot；
- 不进 Raw；
- 不进日志。

Provider Config 只保存 `secret_ref`，运行时才解析 Secret。

## 7. Provider 出站安全

当前 TikHub Secret 只允许发送到批准的 TikHub HTTPS Origin。

Provider Transport/Dispatch 不能因为第三方返回重定向、错误 URL 或配置污染，就把 Bearer Secret 发给任意 Host。

Base URL、Secret 解析和出站限制属于安全边界，变化需要对应测试。

## 8. Raw 与日志为什么分开

Raw 可能包含大量正文、第三方字段和敏感上下文。

正确：

```text
日志
→ request_id / run_id / attempt_id / artifact_id / error_code

Raw
→ 受控 Artifact 文件
```

排障时通过关联 ID 找 Raw，而不是把 Raw 复制到 `worker.log`。

## 9. 审计和诊断日志不是一回事

`audit_events` 当前已经存在，用于保存需要长期追踪的业务/管理动作。

例如当前已经存在的 Provider 配置、关键词/Plan、人工运行等操作，可以在对应业务实现中写审计；未来登录/角色/敏感下载等能力只有在真实实现后才加入相应审计语义。

审计 Actor 使用统一 `system/principal` 语义，不提前绑死某个本地用户表。

## 10. 当前健康检查与排障顺序

最小思路：

```text
进程是否活着
→ /health/live

必要依赖是否可用
→ /health/ready

业务任务是否失败
→ Job / Run / Batch 状态

为什么失败
→ api.log / worker.log / scheduler.log

外部响应到底是什么
→ 对应 Raw Artifact

数据库事实是否正确
→ PostgreSQL
```

数据库 SQL 见 [`../appendix/PostgreSQL调试与常用SQL.md`](../appendix/PostgreSQL调试与常用SQL.md)。

## 11. 当前部署边界

长期目标仍是：

```text
CI 构建固定 Release
→ 离线包上传服务器
→ Docker Compose 导入/启动
→ Migration 单独执行
→ API / Worker / Scheduler 分进程
→ 数据和日志 bind mount 到宿主机
```

但文档必须区分“目标方案”和“当前已完成”。

当前仓库已有本地运行、环境配置和部分容器/Release 设计事实；**完整离线 Release、协调 Backup/Restore、统一写屏障尚未闭环**，不能宣称已经具备生产发布闭环。

实际当前状态和启动方式见 [`../环境运行与部署.md`](../环境运行与部署.md)。

## 12. Migration 为什么独立运行

数据库升级不能塞进 API 启动：

```text
API A 启动
API B 也启动
→ 两个进程同时尝试改 Schema
```

正确边界：

```text
备份/维护条件满足
→ migrate / alembic upgrade
→ Schema 校验
→ 再启动业务进程
```

Migration 失败和应用启动失败应该能分开诊断。

## 13. 备份为什么必须同时考虑数据库和 Artifact

如果只备份 PostgreSQL：

```text
数据库说 artifact_id=123 已存在
但实际 Raw/Excel/DOCX 文件不在恢复点
```

如果只备份文件，也会丢数据库关系。

长期设计要求一个 Backup Set 同时覆盖：

```text
PostgreSQL
+ Artifact 文件
+ 一致截止点
```

为了做到真正一致，还需要共享/独占写屏障排空在途事务和文件 rename/delete。

**这套协调写屏障/Backup-Restore 当前尚未正式实现。**

## 14. 为什么暂时不强制 Prometheus/Grafana/OpenTelemetry

当前首先保证：

- 稳定结构化日志；
- Job/Run/Batch 状态；
- request/job/run/scope/attempt 关联 ID；
- PostgreSQL 可查事实；
- 健康检查；
- Artifact/Raw 可追溯。

出现多机集中告警、跨服务 Trace 或明确指标需求后，再引入指标/Trace 系统。没有实际问题前不为了“可观测性体系”堆工具。

## 15. 当前不存在的能力不要写成已实现

截至当前机器事实：

- 企业登录/权限：未完成；
- `/api/v1/client-events` 浏览器日志上报：没有当前 Route 事实，不写成已实现；
- 完整离线 Release：未闭环；
- 协调 Backup/Restore：未闭环；
- Prometheus/Grafana/OpenTelemetry：未作为当前必需运行依赖。

未来实现时，应同步代码、Contract、测试和本章。
