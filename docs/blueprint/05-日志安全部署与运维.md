先区分两类事实：

```text

→ Dockerfile / compose.yaml

→ 当前代码和测试

→ docs/roadmap/生产上线实施路线.md
```

# 2. 当前日志实现在哪里

```text
backend/src/aima_ugc/platform/logging/
├─ formatter.py
└─ setup.py
```

当前正式进程日志：

```text
api       → api.log
worker    → worker.log
scheduler → scheduler.log
```

Migration 当前没有独立长期应用日志文件映射，执行输出以调用环境/CLI 为准。

`configure_service_logging()` 同时创建：

```text
RotatingFileHandler
+ stdout StreamHandler
```

文件日志是人工排障主入口；stdout 适合容器/平台辅助收集。

---

# 3. 当前日志一行是什么样

Formatter：

```text
backend/src/aima_ugc/platform/logging/formatter.py
```

格式概念：

```text
[YYYY-MM-DD HH:mm:ss.SSS file.py L123]
[INFO]
event=stable.event
job_id="..."
run_id="..."
message="..."
```

人工日志时间显示 `Asia/Shanghai`；数据库机器时间仍用 `timestamptz`。真实调用文件和源码行号放在前缀，是为了让人工排障可以直接跳回代码。

---

# 4. 日志脱敏是代码能力，不只是规范

`formatter.py` 当前会：

- 对敏感 key 递归替换为 `***`；
- 清理 `Bearer ...`；
- 清理 password/token/api key/cookie 等 inline 值；
- 清理 PostgreSQL URL 密码；
- 对常见邮箱/手机号/身份证形态做基础脱敏；
- 对 dict/list/tuple 递归脱敏；
- 截断过长字段/异常/整行；
- 把换行转义成单行；
- 安全 traceback 不复制可能带 Secret 的 source line/message。

精确限制常量直接看 `backend/src/aima_ugc/platform/logging/formatter.py`；不要在文档维护第二套数字 Contract。

---

# 5. 日志级别怎么用

```text
DEBUG
→ 正常轮询、空 Scheduler tick、高频成功细节

INFO
→ 低频重要生命周期、真正业务结果

WARNING
→ Retry、部分失败、需要关注但系统还能继续

ERROR
→ 永久失败、非法配置、需要人工介入或未预期异常
```

不要用 INFO 日志证明进程存活；健康由 Health 和实际 Job/Run 事实判断。

## 5.1 功能开发时怎样选择日志观测点

仓库已经具备正式应用日志体系，因此实现重要功能时要补充**最小充分**的运行过程日志：优先记录低频重要生命周期、Job/Run/Batch 状态变化、外部 I/O 安全摘要、Retry/部分失败/跳过/取消/永久失败，并复用已有 request/job/run/batch/content ID。

逐条记录、正常轮询、循环内部高频成功细节使用 DEBUG 或不记录。同一异常原则上只在拥有处理或终止责任的边界记录一次。新增日志继续经过现有 Formatter/脱敏/轮转，禁止主动记录 Secret、Token、密码、Authorization、敏感 Raw/Payload 或未脱敏 PII。

# 6. 日志轮转

`setup.py` 使用 `RotatingFileHandler`，由 `PlatformSettings` 控制：

```text
AIMA_LOG_DIR
AIMA_LOG_LEVEL
AIMA_LOG_MAX_BYTES
AIMA_LOG_BACKUP_COUNT
AIMA_LOG_COMPRESS
```

启用压缩时旧日志使用 gzip。精确默认值看 `backend/src/aima_ugc/platform/config/settings.py`；业务模块不能再创建第二套 `FileHandler`。

# 8. Secret 当前怎么进入系统

当前长期原则仍是：

```text
普通运行配置
→ 显式 AIMA_* 环境变量

Secret 值
→ Secret File

数据库/业务配置
→ 只保存 secret_ref
```

本地开发与生产 Compose 现在使用**相同的 Secret 分类语义**：

```text
AIMA 内部随机 Secret
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
→ AIMA_SECRET_DIR

外部 Provider / LLM Secret
TikHub API Key
LLM API Key
→ AIMA_EXTERNAL_SECRET_DIR
```

本地源码开发：

```text
AIMA_SECRET_DIR
→ .runtime/internal-secrets

AIMA_EXTERNAL_SECRET_DIR
→ .runtime/secrets

旧 .runtime/secrets/postgres_password
→ 已废弃
→ launcher 不读取、不迁移、不拿它决定当前数据库密码
```

如果本地已经存在 `aima-ugc-postgres-dev-data` volume/container，但新的 `.runtime/internal-secrets/postgres_password` 不存在，launcher 会 fail closed：不从旧路径恢复，也不生成一个新密码去尝试连接既有数据库。对于可丢弃的本地开发数据，开发者显式删除本地 container/volume 后重建；需要保留旧数据时，只能自行确认数据库 Role 的真实密码并把匹配值放进新的内部根。

这个边界基于 PostgreSQL 的实际语义：密码属于 Role 认证，不属于数据副本。一个 cluster 可以有多个 Role 和不同密码，并按权限访问同一或不同数据库对象；不同密码不会自动映射成不同数据。只改变应用侧密码而不改变数据库内 Role 密码，只会认证失败。

生产 Compose：

```text
内部随机 Secret
→ bootstrap 首次生成并持久保存到 AIMA_HOST_SECRET_DIR
→ Backend: AIMA_SECRET_DIR=/run/internal-secrets（只读）

外部凭据
→ 管理员写入真实 env.production
→ Compose top-level secrets
→ AIMA_EXTERNAL_SECRET_DIR=/run/secrets
→ 只授予实际需要该 Secret 的服务
```

`PlatformSettings.external_secret_root` 在调用方没有显式设置 `AIMA_EXTERNAL_SECRET_DIR` 时仍回退到 `AIMA_SECRET_DIR`，保留底层配置兼容能力；当前正式本地 launcher 与生产 Compose 都会显式设置两个根目录，不再依赖该 fallback 作为正常运行方式。

真实 `env.production` 因为可以含外部 API Key，**本身属于敏感文件**：已被 Git ignore，不能提交 Git、进入镜像/Release 明文、日志或错误响应。`env.local` 同样只作为本地 launcher 输入；TikHub/LLM Key materialize 为外部 Secret File 后不会作为正式 API/Worker/Scheduler 的普通环境变量传递。

PostgreSQL password 不由管理员或本地开发者填写。空数据库首次启动时自动生成。生产已有 PostgreSQL 18 数据但 `postgres_password` 丢失时仍必须 fail closed 并恢复与数据库匹配的原 Secret；本地开发则不再兼容旧 `.runtime/secrets/postgres_password` 路径，已有本地 volume + 新内部密码缺失时同样 fail closed，但允许开发者显式重置可丢弃的本地数据。

Secret resolver 继续拒绝 root escape、symlink、非普通文件、超限内容，并避免错误信息回显 Secret；本地随机内部 Secret 生成入口同样拒绝符号链接。

Secret 禁止进入：Git、Job Payload、Plan config、Raw、Fixture、日志、Error Response、Export/Word。

# 9. TikHub 出站安全

TikHub Base URL 可配置不等于任意 URL 都可以带 Bearer Secret。当前 Transport 会把 Secret 限制到批准的 TikHub HTTPS Origin；不能为了调试放宽 `verify=false`、任意 redirect 或任意 host。

代码：

```text
backend/src/aima_ugc/adapters/providers/tikhub/transport.py
backend/src/aima_ugc/platform/security/
```

# 10. 当前认证状态

当前已经有真实业务 API 和 Vue 页面，但**企业登录/正式认证授权尚未闭环**。

```text
业务功能已存在
≠ 可以安全公网暴露写 API
```

未来身份边界：

```text
External Identity Provider
→ Authentication Adapter
→ Principal / AuthContext
→ 后端 Authorization
```

业务模块不能直接把飞书 `open_id/union_id` 等 Provider 私有身份当长期业务主键。认证、授权、Session/OIDC/飞书接入属于独立高风险变更，也是完整 Production Go-Live 前置条件；公司受控内网 V1 已明确延期这一项。

# 11. Health API 当前做什么

当前 Route：

```text
GET /health/live
GET /health/ready
```

机器实现：

```text
backend/src/aima_ugc/bootstrap/api.py
backend/src/aima_ugc/platform/health.py
```

`live` 只表示进程能响应；`ready` 检查当前装配要求的 PostgreSQL、ArtifactStore 和日志目录等关键依赖，并避免向客户端泄露内部异常。`/ready=200` 不等于 TikHub、LLM 和全部业务流程都已生产验收。

# 12. Artifact 存储边界

当前默认是 Local ArtifactStore：

```text
ArtifactService
→ ID / metadata / 业务关联 / 生命周期

ArtifactStore
→ storage_key → bytes
```

典型 Artifact 包括 TikHub Raw、Excel Input、正式 Excel Export、离线 Word/Markdown 产物。不要把 ArtifactStore 变成会自己查 PostgreSQL 的万能服务。

# 13. Docker / Compose 当前状态与目标

## 当前机器事实

仓库根当前已经存在：

```text
Dockerfile
compose.yaml
env.production.example
```

Internal V1-A 当前管理员入口是：

```bash
cp env.production.example env.production
chmod 0600 env.production
# 编辑 env.production
docker compose --env-file env.production up -d --build --wait
```

Compose 自动编排：

```text
bootstrap（一性 root 初始化，成功后退出）
→ postgres healthy
→ migrate completed
→ configure completed
→ api / worker / scheduler
→ frontend healthy
```

`bootstrap` 只在启动阶段以 root 准备宿主持久目录和内部 Secret，成功后退出，不作为长期高权限容器常驻。Migration 仍是独立进程，API 启动不会隐式修改 Schema。

当前端口边界：Frontend 是唯一 published HTTP 入口；PostgreSQL/API 不发布宿主端口。PostgreSQL、Artifact、日志和内部 Secret 均映射到宿主持久目录。

## 完整 Production 仍待实现

当前仍没有完整 Stage 11 所需的：

```text
不可变离线 Release Bundle / images.tar
固定 image digest
SBOM / 签名 / provenance
正式 HTTPS / 企业认证授权
协调 PostgreSQL + Artifact Backup / Restore
完整真实生产服务器恢复/回滚验收
```

Stage 11 不应重造第二套业务运行时，而应在 Internal V1-A 已验证的 Docker/Compose 基础上增量加强。详细见：

# 14. PostgreSQL 与 Artifact 为什么不能只备份一个

业务来源可能形成：

```text
content_versions.raw_artifact_id
→ artifacts metadata
→ ArtifactStore bytes
```

只备份数据库会留下 ID 但可能丢 bytes；只备份文件会丢业务关系/Job/Content。所以长期正确恢复单位是 PostgreSQL + ArtifactStore 的协调 Backup Set。

---

# 15. 当前完整协调 Backup/Restore 仍未闭环

当前不能把以下能力写成已完成：

```text
业务写共享屏障
Backup 独占屏障
maintenance epoch
数据库与 Artifact 协调 backup set
正式 restore/recovery 演练
```

这是 Stage 11 的生产级工作，需要独立 Change、锁/状态语义、脚本和真实恢复演练。当前不能承诺“数据库和 Artifact 一定能恢复到完全一致的同一时刻”。

# 16. Migration 为什么独立进程

当前入口：

```text
backend/src/aima_ugc/entrypoints/migrate_main.py
backend/src/aima_ugc/bootstrap/migration.py
```

Schema 演进只通过 `migrations/versions/`。不能让 API 启动 `create_all()`、多个实例并发跑 Migration、手工改生产库后不补 Alembic，或修改已发布历史 Migration。

Internal V1-A 已把 `migrate` 作为 Compose 一次性独立服务，通过 `service_completed_successfully` 自动接入一条启动命令；“自动编排”不等于“Migration 被塞进 API”。

# 17. Provider / LLM 真实请求如何控制

真实付费调用：

- 默认不进入普通 CI；
- Probe 必须显式触发；
- 先做免费/离线校验；
- 限制请求范围；
- 记录 Pricing/Token/Cost 审计；
- 不打印 Secret；
- 不默认写生产业务库。

TikHub 人工入口：`backend/src/aima_ugc/adapters/providers/tikhub_test/`。AI 离线 Canary/并发见 [`../appendix/AI舆情打标与分析实现.md`](../appendix/AI舆情打标与分析实现.md)。当前没有统一 request/amount Budget Guard；Billing/Cost 审计不等于预算控制。
