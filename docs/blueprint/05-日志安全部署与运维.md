# 日志、安全、部署与运维

## 1. 日志结论

应用日志必须继续保存为明确的 `.log` 文件。它是生产环境人工排障的主要来源。

```text
/app/logs/api.log
/app/logs/worker.log
/app/logs/scheduler.log
/app/logs/frontend-events.log
        ↓ bind mount
/data/AIMA_UGC/runtime/logs/
```

Docker stdout/stderr 日志是辅助来源，用于容器启动失败、进程崩溃、Nginx 和 PostgreSQL 排查。审计事件单独写数据库。Raw 响应单独写 gzip 文件。这四类数据不能混为一种“日志”。

## 2. 应用日志格式

UTF-8，一行一个事件：

```text
[2026-08-12 22:08:31.291] [INFO] service=worker source=tikhub_client.py:231 event=provider.request.completed request_id=req_01 job_id=job_01 run_id=run_01 scope_id=scope_01 platform=xhs operation=search_notes duration_ms=1323 item_count=18 message="TikHub 请求完成"
```

固定部分：

```text
[北京时间，毫秒]
[级别]
service
source
event
关联 ID
业务字段
message
```

时间格式固定：

```text
YYYY-MM-DD HH:mm:ss.SSS
```

不输出 `T`、`Z` 或 `+08:00`。进程启动事件必须记录：

```text
timezone=Asia/Shanghai
```

因此日志使用者知道无偏移时间的含义。数据库和 API 仍使用带时区时间，不能模仿日志格式。

所有字段必须经过同一个结构化 Formatter：键名只允许约定字符；字符串用引号包裹，并转义 `\r`、`\n`、制表符、引号、反斜杠和其他控制字符；单字段、异常堆栈和整行都有长度上限，截断时增加 `truncated=true`。禁止直接拼接用户文本、Provider 错误或异常消息，否则会产生伪造日志行和解析歧义。Formatter 必须有 CRLF/控制字符、超长文本和敏感字段测试。

## 3. 日志文件

| 服务 | 文件 |
| --- | --- |
| API | `api.log` |
| Worker | `worker.log` |
| Scheduler | `scheduler.log` |
| 浏览器错误接收端 | `frontend-events.log` |

Nginx、PostgreSQL 使用 Docker 日志。除非有明确运维需求，不再让应用写一个混合的 `app.log`。

如果同一服务未来运行多个实例，文件名增加稳定实例 ID：

```text
worker-worker-01.log
worker-worker-02.log
```

多个进程禁止同时写同一普通 `RotatingFileHandler` 文件。

## 4. 日志轮转

应用日志默认：

```text
单文件上限：20 MiB
备份数量：10
旧文件：gzip 压缩
重启：继续追加
编码：UTF-8
```

实现使用 Python 标准库 `RotatingFileHandler`，通过 `namer/rotator` 对轮转文件 gzip。因为一个容器内每类服务只有一个进程写自己的文件，不增加并发日志依赖。

环境变量：

```text
AIMA_LOG_DIR=/app/logs
AIMA_LOG_LEVEL=INFO
AIMA_LOG_MAX_BYTES=20971520
AIMA_LOG_BACKUP_COUNT=10
AIMA_LOG_COMPRESS=true
```

Docker stdout/stderr 使用 `local` 驱动：

```yaml
logging:
  driver: local
  options:
    max-size: "10m"
    max-file: "3"
    compress: "true"
```

不得使用固定周期清空日志，不得依赖默认无限增长的 `json-file`。

## 5. stdout 行为

应用事件同时写文件和 stdout，格式相同：

- 文件：完整 INFO 及以上；
- stdout：INFO 及以上，受 Docker 10 MiB × 3 轮转；
- DEBUG 默认只写文件，并且生产默认关闭；
- 未捕获异常必须同时可在文件和 `docker compose logs` 中看到。

文件日志是长期人工排障主入口，Docker 日志是短环辅助，不互相替代。

## 7. 应该记录什么

### 7.1 HTTP

- request ID；
- method；
- route template，不记录完整敏感 Query；
- status；
- duration；
- actor ID；
- error type。

健康检查默认不逐次写 INFO，只在状态变化或异常时记录。

### 7.2 Job

- Job 入队、开始、完成、重试、失败、取消；
- job ID/type；
- attempt/max attempts；
- worker ID；
- timeout；
- duration；
- error type；
- 进度阶段。

正常 Heartbeat 不写 INFO。只有：

- Lease 续租失败；
- 进度长时间不变；
- 心跳超时；
- 任务恢复；

才写 WARNING/ERROR。DEBUG Heartbeat 采用采样，不每次刷屏。

### 7.3 Provider

- provider/platform/operation；
- Run/Scope；
- 页码或 cursor 摘要；
- 状态；
- 时长；
- 结果数量；
- 费用；
- 重试；
- TikHub request ID。

禁止写完整请求 Body、响应 Body、Cookie、Token 和用户原文。

### 7.4 Ingestion

- 输入数量；
- 新增/更新/未变化/失败数量；
- 业务版本和 Observation 数；
- 事务耗时；
- 失败身份和错误分类。

不逐条 INFO 打印每个帖子。逐条诊断放 DEBUG，并设采样。

通用字段：

```text

```

同一链路沿用相同 ID。不要每层重新生成无法关联的新 ID。

## 9. 脱敏

Formatter 在写出前递归和正则脱敏：

- Authorization；
- Bearer Token；
- API Key；
- Cookie；
- password/secret/token 字段；
- 数据库 URL 密码；
- 邮箱；
- 中国大陆手机号；
- 身份证号；
- 用户配置的敏感 Header。

原则：

> 脱敏是最后防线，不是允许业务代码主动记录 Secret 的理由。

异常对象可能包含响应 Body，Provider Error 必须先提取安全摘要再交给 Logger。

## 10. 浏览器错误

前端捕获：

- 未处理异常；
- Promise rejection；
- 关键 API 错误；
- 版本和页面路由。

通过受限接口发送：

```text
POST /api/v1/client-events
```

服务端：

- 校验大小；
- 限流；
- 去除 Cookie/Token；
- 不接受任意嵌套大对象；
- 写 `frontend-events.log`；
- 关联 request ID、用户和前端版本。

## 11. 审计

以下操作必须写 `audit_events`，不能只写轮转日志：

- 登录、登出、失败登录；
- 用户和角色变化；
- Provider 配置变化；
- 关键词和计划变化；
- 人工启动、停止、重试；
- 人工复核；
- 告警和工单状态变化；
- 下载敏感导出；
- 数据删除和保留任务；
- 备份和恢复。

审计记录包含：

```text
actor
action
target_type
target_id
result
request_id
before_summary
after_summary
created_at
```

敏感字段只记录是否变化，不记录原值。

## 12. 最小可观测性

第一版不强制引入 Prometheus、Grafana 或 OpenTelemetry。必须先具备：

- `/health/live`：进程活着；
- `/health/ready`：数据库、必要目录和配置可用；
- Job 状态和失败原因页面；
- Collection Run/Scope/Request 统计；
- 日志关联 ID；
- 磁盘容量检查；
- 备份状态；
- 数据新鲜度和最后成功采集时间。

出现多机、集中告警或跨服务链路需求时再增加指标和 Trace 系统。

## 13. 安全边界

### 13.1 Secret

Secret 不提交 Git，不写数据库明文，不进 Job Payload，不进 Raw，不进日志。

默认使用 Compose Secret 或只读 Secret 文件：

```text
/data/AIMA_UGC/shared/secrets/
├─ postgres_password
├─ tikhub_token
├─ llm_api_key
└─ session_secret
```

容器内：

```text
/run/secrets/<name>
```

业务配置表只保存：

- Provider 名称；
- endpoint；
- 非敏感开关；
- Secret Reference。

### 13.2 登录与会话

默认使用服务端 Session，不把长期访问 Token 放进浏览器 `localStorage`。

本地账号必须：

- 密码使用 Argon2id；
- 登录失败限流和短期锁定；
- Session ID 使用高强度随机值并只保存哈希；
- Cookie 设置 `HttpOnly`、`Secure`、`SameSite=Lax`；
- 修改数据的请求验证 CSRF；
- 支持主动注销、管理员撤销和绝对过期；
- 登录、失败、撤销和权限拒绝写审计。

上述行为由 `sessions`、`auth_login_attempts`、`permissions`、`role_permissions` 和 `audit_events` 落地；认证/权限表必须在业务写 API 之前完成 Migration 与集成测试。不能只依赖进程内 Session、前端角色字符串或 Nginx 隐藏路径。

接入飞书或 OIDC 时，必须验证 `state`、`nonce`，支持时使用 PKCE；不能只相信前端传回的用户信息。

### 13.3 权限

第一版最小角色：

```text
admin
operator
analyst
viewer
```

后端每个写接口必须声明权限；隐藏按钮不能代替后端授权。查询 Raw、下载导出、修改 Provider、删除数据和恢复备份使用单独权限，不因拥有普通写权限自动获得。

### 13.4 输入

必须防止：

- SQL 拼接；
- 路径穿越；
- 任意 URL SSRF；
- 任意命令执行；
- 不安全反序列化；
- Excel 公式注入；
- Zip Bomb；
- 超大上传；
- 任意 HTML 注入。

导出 CSV/XLSX 时，以 `= + - @` 开头的用户文本按公式注入规则转义。

### 13.5 Raw 和个人信息

Raw 可能包含昵称、头像、评论和平台用户 ID。必须有：

- 访问权限；
- 脱敏规则；
- 保留策略；
- 下载审计；
- 禁止公开静态目录直接暴露；
- 备份加密和访问控制。

### 13.6 网络和浏览器边界

- 生产必须使用 HTTPS；
- Nginx 和 API 显式配置允许的 Host；
- `/api/` 的 Nginx 413/502/504 等代理层错误使用与 API 兼容的 JSON 错误外形和 `X-Request-ID`，同时保留真实 HTTP 状态；应用层仍负责 FastAPI/Starlette 错误细节；
- 前后端默认同源部署；
- CORS 只列出实际来源，带凭据时禁止 `*`；
- 设置合理的 HSTS、`X-Content-Type-Options`、Referrer Policy 和 Content Security Policy；
- Provider 出站域名使用 Allowlist，用户输入 URL 不直接由服务器请求；
- 出站校验必须覆盖 DNS 解析后的所有地址和每次重定向，拒绝环回、链路本地、私网和云元数据地址；
- 数据库端口默认不对公网开放；
- 管理和备份入口只对受控网络或主机开放。

## 14. Docker Compose

生产服务：

```text
frontend
api
worker
scheduler
migrate
postgres
```

`migrate` 是一次性 Profile/命令，不作为常驻服务。

容器内部路径：

```text
/app/data
/app/logs
/run/secrets
/var/lib/postgresql
```

生产宿主机路径：

```text
/data/docker
/data/AIMA_UGC/runtime/data
/data/AIMA_UGC/runtime/logs
/data/AIMA_UGC/postgres
/data/AIMA_UGC/backups
/data/AIMA_UGC/releases
/data/AIMA_UGC/shared/env
/data/AIMA_UGC/shared/secrets
```

Docker `data-root` 使用 `/data/docker`。数据库、业务文件和 Release 不放进 Docker data-root，避免 Docker 清理和业务数据混在一起。

PostgreSQL 18 官方镜像把可持久化卷挂载点改为 `/var/lib/postgresql`，默认 `PGDATA` 位于 `/var/lib/postgresql/18/docker`。生产 Compose 必须把宿主机 `/data/AIMA_UGC/postgres` 绑定到 `/var/lib/postgresql`，不得沿用 PostgreSQL 17 及更早版本常见的 `/var/lib/postgresql/data` 挂载方式，也不得无依据覆盖镜像默认 `PGDATA`。从旧主版本迁移必须使用经过验证的逻辑备份恢复或单独设计的 `pg_upgrade` 流程，不能只改镜像标签。

宿主机目录必须在启动前显式创建并校验权限，Compose 对生产 bind mount 使用 `create_host_path: false`。应用镜像使用固定非 root UID/GID；Release 初始化脚本读取固定镜像中的实际 UID/GID并校验 `/data/AIMA_UGC/runtime/data`、`runtime/logs` 和 `postgres`。禁止用 `chmod 777` 解决权限问题，也禁止依赖 Docker 自动创建一个归属不明的空目录。

## 15. 镜像

- 多阶段构建；
- 唯一 `Dockerfile` 和 build context 均在仓库根；`backend/`、`frontend/`、根 Lock 和 Contract 按 target 选择性复制；
- 基础镜像固定 major/minor，并在 Release Manifest 固定 digest；
- Backend 不包含开发依赖；
- Frontend 构建后由 Nginx 提供静态文件；
- Playwright 浏览器版本与 Python/Node Playwright 包匹配；
- 生产不现场 `pip install`、`npm install` 或下载浏览器；
- 镜像以非 root 用户运行，确有权限需求的初始化步骤单独处理；
- Healthcheck 不依赖 Shell 中不存在的工具。

依赖和基础镜像只在显式升级任务中变更。构建时生成 SBOM，执行依赖与镜像漏洞扫描并保存结果；发现风险按严重度、可利用性和运行暴露决定阻断或有时限的例外，不得通过静默换到 `latest` 规避评审。

## 16. Release

CI 从 `main` 的固定 Git SHA 构建：

```text
AIMA_UGC-v1.0.0-deploy.tar.gz
├─ images.tar
├─ compose.yaml
├─ compose.production.yaml
├─ env.production.example
├─ release-manifest.json
├─ migration-manifest.json
├─ SHA256SUMS
├─ SBOM/
├─ SIGNATURES/
└─ DEPLOY.md
```

Manifest 包含：

- 版本；
- Git SHA；
- 构建时间；
- 平台；
- 镜像 digest；
- 数据库 Revision；
- Canonical/OpenAPI 版本；
- 最低 Docker/Compose 要求；
- 是否有破坏性 Migration；
- 回滚说明；
- SBOM、扫描结果和签名/受信来源信息。

服务器只执行：

```text
从受信渠道取得发布公钥/签名根
→ 验证 Release 签名
→ 校验 SHA-256
→ 暂停调度与高风险写入
→ 创建协调数据库+Artifact Backup Set
→ docker load
→ migrate
→ docker compose config
→ up --no-build --pull never
→ 健康检查
→ 业务冒烟
```

禁止生产服务器 `git pull` 和现场构建。SHA-256 只证明下载内容与清单一致；若 Release 和清单一起被替换，不能证明来源，因此生产必须同时验证独立受信的签名或等价的制品仓库身份与完整性证明。

## 18. 发布顺序

```text
确认目标 SHA 和 CI
→ 下载 Release
→ 验证受信签名
→ sha256sum -c
→ 检查 Manifest
→ 检查磁盘
→ 暂停 Scheduler
→ 启用维护模式，拒绝所有业务写请求
→ 停止新 Job 认领并等待/取消运行中 Job
→ 取得统一独占 PostgreSQL advisory 写屏障，等待所有在途共享写者退出并复核活动写入为零
→ 持有屏障，冻结所有 Artifact 文件及其数据库引用写入
→ 记录统一 Backup Set ID 与协调截止点
→ pg_dump 与 Artifact 文件快照/备份
→ 验证 pg_restore --list、文件清单和截止点一致性
→ 标记 Backup Set 可恢复后释放独占屏障；维护模式继续保持
→ docker load
→ 运行 migrate
→ 启动 postgres/api
→ 启动 worker/scheduler
→ 启动 frontend
→ 健康检查
→ 关键业务冒烟
→ 恢复 Worker 认领与调度
```

直到数据库备份和文件快照都成功完成前，维护模式、独占写屏障与 Artifact 文件/引用冻结必须保持。所有业务写 UoW 和 Artifact rename/delete 必须先取得同一键的共享 session-level advisory lock、再复核维护 epoch，并持有到最终提交；所以备份方取得独占锁就同时证明此前在途写入已经排空。任一备份/校验或 Migration 失败就立即停止，不启动新应用，也不自动退出维护模式或恢复 Worker/Scheduler；先确认现有 Release、数据状态和恢复方案。发布前的协调备份必须能恢复数据库与 Artifact 的同一业务截止点；仅给两个独立备份写同一个名称不算一致性协议。若阶段 0 批准的停写窗口无法接受，必须另行设计并验证存储快照/一致性协议，不能跳过排空/冻结步骤。

## 19. 回滚

### 19.1 无破坏性数据库变化

```text
切回旧 Release 目录
→ docker compose up --no-build --pull never
→ 验证
```

### 19.2 有不兼容数据库变化

应用回滚前恢复已验证的协调数据库+Artifact Backup Set，或采用提前设计的兼容窗口。必须明确从协调截止点到回滚时刻之间可能丢失的数据、处置方式和业务确认；不能只说“运行 alembic downgrade”。

### 19.3 回滚验证

- API；
- Worker 认领 Job；
- Scheduler 不重复入队；
- 前端；
- 内容/评论查询；
- 一个测试采集；
- 日志可写；
- Artifact 可下载。

## 20. 备份任务

建议：

```text
按阶段 0 批准的 RPO 创建常规协调数据库+Artifact Backup Set
至少每月完整恢复演练；高变更期每周
发布前额外创建协调数据库+Artifact Backup Set
可在两个协调点间做文件增量传输，但它只用于加速，不能单独称为可恢复点
每日备份状态检查
磁盘超过 70% WARNING
超过 85% ERROR 并暂停非必要 Raw/报告任务
```

阈值可以配置，但不能没有容量告警。

常规恢复点与发布前备份使用同一协调原则：先进入维护 epoch，再取得统一独占 advisory 写屏障并等待在途共享写者排空，之后记录截止点并同时捕获数据库和文件；两者都成功且清单/引用检查通过后，才把 Backup Set 标记为可恢复。若阶段 0 的 RPO 无法接受每次停写窗口，必须在 Release 阶段选定并实测能提供一致性截止点的文件系统/存储快照协议，不能退回“每日 pg_dump + 独立文件增量”的非协调组合。

阶段 0 必须给出日 Provider 请求量、内容/评论量、Raw 日增量、Worker 并发、最大 Run、API 延迟目标、磁盘预算、RPO 和 RTO。180 天 Raw 是保留目标，不是无限写入许可；未配置冷存储且磁盘达到停止阈值时，系统暂停非必要采集/报告并告警，不得自动删除仍在保留期或被引用的证据。

- Migration 单独执行；
- 备份可恢复；
