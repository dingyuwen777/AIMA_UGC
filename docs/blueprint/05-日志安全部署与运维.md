本文描述当前 AIMA_UGC 的运行边界：**出了问题去哪里看、日志实际怎样生成、Secret 怎样进入进程、健康检查检查什么、Docker/Artifact/数据库怎样部署，以及哪些恢复能力还没有真正闭环。**

```text

Dockerfile
```

# 2. 当前日志实现在哪里

```text
backend/src/aima_ugc/platform/logging/
├─ formatter.py
└─ setup.py
```

当前正式进程文件：

```text
api       → api.log
worker    → worker.log
scheduler → scheduler.log
```

`Migration` 当前没有独立长期应用日志文件映射，具体执行输出以调用环境/CLI 为准。

`configure_service_logging()` 同时创建：

```text
RotatingFileHandler
+ stdout StreamHandler
```

文件日志是人工排障主入口；stdout 适合 Docker/平台辅助收集。

---

# 3. 当前日志一行是什么样

Formatter：

```text
backend/src/aima_ugc/platform/logging/formatter.py
```

格式概念：

```text
[YYYY-MM-DD HH:mm:ss.SSS file.py L123]
[INFO]
event=stable.event
job_id="..."
run_id="..."
message="..."
```

时间显示：

```text
Asia/Shanghai
```

但数据库机器时间仍用 `timestamptz`，两者不要混淆。

为什么把真实调用文件和源码行号放在前缀：人工排障时可以直接跳到代码，不需要从 logger name 反推。

---

# 4. 当前日志脱敏是代码能力，不只是写作规范

`formatter.py` 当前会：

- 对敏感 key 递归替换为 `***`；
- 清理 `Bearer ...`；
- 清理 password/token/api key/cookie 等 inline 值；
- 清理 PostgreSQL URL 密码；
- 对常见邮箱/手机号/身份证形态做基础脱敏；
- 结构化 dict/list/tuple 递归脱敏；
- 截断过长字段/异常/整行；
- 把换行转义成单行日志；
- 安全异常 traceback 只保留文件/行号/函数/异常类型，不复制可能带 Secret 的异常 message/source line。

当前限制常量直接看：

```text
_FIELD_LIMIT
_EXCEPTION_LIMIT
_LINE_LIMIT
_MAX_TRACEBACK_FRAMES
```

不要在文档里把这些数字当永久 Contract。

---

# 5. 日志级别怎么用

```text
DEBUG
→ 正常轮询、空 Scheduler tick、高频成功细节

INFO
→ 低频重要生命周期、真正业务结果

WARNING
→ Retry、部分失败、需要关注但系统仍能继续

ERROR
→ 永久失败、非法配置、需要人工介入或未预期异常
```

例如 Scheduler：

```text
空 tick
→ DEBUG

初始化 cursor / enqueue / misfire skip
→ INFO

某个 Plan 失败
→ ERROR plan event
+ tick summary WARNING
```

不要用 INFO 证明“进程还活着”。健康状态由 readiness/liveness 和实际 Job/Run 事实判断。

# 6. 日志轮转

`setup.py` 使用：

```text
RotatingFileHandler
```

当前由 `PlatformSettings` 控制：

```text
AIMA_LOG_DIR
AIMA_LOG_LEVEL
AIMA_LOG_MAX_BYTES
AIMA_LOG_BACKUP_COUNT
AIMA_LOG_COMPRESS
```

启用压缩时旧日志使用 gzip。

精确默认值：

```text
backend/src/aima_ugc/platform/config/settings.py
```

不要在业务模块自己创建另一套 `FileHandler`。

```text

```

在它真正进入 Contract/Route/Test 前，不做当前能力承诺。

# 8. Secret 当前怎么进入系统

当前原则：

```text
非敏感配置
→ 环境变量 / env example

Secret 值
→ AIMA_SECRET_DIR 下只读文件

数据库/业务配置
→ 只保存 secret_ref
```

常见 Secret：

```text
postgres_password
LLM API Key
Content Cursor signing key
Import Batch Cursor signing key
Collection Runtime Cursor signing key
```

精确文件名/路径由：

```text
backend/src/aima_ugc/platform/config/settings.py
```

决定。

Worker Provider Secret 解析：

```text
backend/src/aima_ugc/bootstrap/worker.py
backend/src/aima_ugc/platform/security/
```

Secret 禁止进入：

- Git；
- Job Payload；
- Plan config；
- Raw；
- Fixture；
- 日志；
- Error Response；
- Export/Word。

# 9. TikHub 出站安全

TikHub Base URL 可配置不等于任意 URL 都可以带 Bearer Secret。

当前 Transport/配置边界负责验证目标 Origin，Secret 只能发给批准的 HTTPS TikHub Origin。

代码：

```text
backend/src/aima_ugc/adapters/providers/tikhub/transport.py
backend/src/aima_ugc/platform/security/
```

不能为了调试把：

```text
verify=false
任意 redirect
任意 host
```

放宽成生产默认。

# 10. 当前认证状态

当前已经有真实业务 API 和 Vue 页面，但**企业登录/正式认证授权尚未闭环**。

所以当前事实是：

```text
业务功能已存在
≠ 可以安全公网暴露所有写 API
```

未来身份 Provider 应通过统一：

```text
Identity Adapter
→ Principal / AuthContext
→ 后端 Authorization
```

业务模块不能直接把飞书 `open_id/union_id` 等第三方身份写成长期主键。

认证、授权、Session/OIDC/飞书接入属于独立高风险变更。

# 11. Health API 当前做什么

当前 Route：

```text
GET /health/live
GET /health/ready
```

机器实现：

```text
backend/src/aima_ugc/bootstrap/api.py
backend/src/aima_ugc/platform/health.py
```

`live`：进程是否能响应。

`ready`：当前装配会检查关键依赖，包括 PostgreSQL、ArtifactStore 和日志目录可写边界；失败时返回简化状态，不把内部异常细节返回给客户端。

不要把 readiness 当完整业务端到端测试：TikHub、LLM、所有页面业务并不会因为 `/ready=200` 就自动证明可用。

# 12. Artifact 存储边界

当前默认是 Local ArtifactStore。

职责：

```text
ArtifactService
→ ID / metadata / 业务关联 / 生命周期

ArtifactStore
→ storage_key → bytes
```

代码：

```text
backend/src/aima_ugc/platform/storage/
backend/src/aima_ugc/adapters/storage/
backend/src/aima_ugc/adapters/persistence/postgres/artifact_metadata.py
```

典型 Artifact：

- TikHub Raw；
- Excel Input；
- 正式 Excel Export；
- 离线 Word/Markdown 产物（按调用入口保存/落盘）。

不要把 ArtifactStore 变成可以自己查 PostgreSQL 的“万能文件服务”。

# 14. PostgreSQL 与 Artifact 为什么不能只备份一个

业务来源关系可能是：

```text
content_versions.raw_artifact_id
→ artifacts metadata
→ ArtifactStore bytes
```

只备份数据库：

```text
ID 还在
→ 文件丢了
```

只备份文件：

```text
bytes 还在
→ 业务关系/Job/Content 丢了
```

所以长期正确恢复单位是：

```text
PostgreSQL + ArtifactStore
```

但当前要明确区分**长期要求**与**机器已实现**。

# 15. 当前完整协调 Backup/Restore 仍未闭环

当前仓库不能把以下能力写成已完成：

```text
业务写共享屏障
Backup 独占屏障
统一 maintenance epoch
数据库与 Artifact 协调 backup set
正式恢复演练闭环
```

这些是生产级 Release/Restore 的长期方向，进入实现时需要独立 Change、Schema/锁语义、部署流程和真实演练。

因此当前发布前仍不能声称：

> “数据库和 Artifact 一定能恢复到完全一致的同一时刻。”

# 16. Migration 为什么独立进程

当前入口：

```text
backend/src/aima_ugc/entrypoints/migrate_main.py
backend/src/aima_ugc/bootstrap/migration.py
```

正式 Schema 演进：

```text
migrations/versions/
```

不能：

- API 启动 `create_all()`；
- 多个 API 实例同时跑 Migration；
- 手工改生产库后不补 Alembic；
- 修改已发布历史 Migration。

当前发布流程是否已经完整自动化，以 `docs/环境运行与部署.md + compose*.yaml + CI` 为准，不把长期 Release 目标写成当前完成。

# 17. Provider / LLM 真实请求如何控制

真实付费调用：

- 默认不进入普通 CI；
- Probe 必须显式触发；
- 先做免费/离线校验；
- 限制请求范围；
- 记录 Pricing/Token/Cost 审计；
- 不打印 Secret；
- 不默认写生产业务库。

# 18. 生产排障顺序

## API 返回 500

```text
1. request_id
2. api.log
3. 对应 Route / Application Service
4. PostgreSQL 业务父事实是否已经提交
5. Artifact/Job 状态
```

## Worker Job 卡住

```text
1. jobs
2. job_attempt_events
3. worker.log
4. lease_expires_at / attempt_deadline_at
5. 对应业务父表（Run/Batch/Analysis/Export）
```

## Scheduler 到点没跑

```text
1. collection_plans
2. collection_schedule_occurrences
3. scheduler.log
4. collection_runs / jobs
```

详细：

[`../appendix/Scheduler调度执行与停机恢复.md`](../appendix/Scheduler调度执行与停机恢复.md)

## Provider 数据不对

```text
1. Provider Attempt
2. Raw Artifact / Fixture
3. Operation extractor
4. Mapper
5. Canonical
```

## Word 报告不对

```text
数据数字错
→ excel_report.py

Markdown 文字错
→ report_template.md

Word 布局错
→ visual_docx.py

Office Chart/OOXML 错
→ chart_spec.py / docx_package.py
```
