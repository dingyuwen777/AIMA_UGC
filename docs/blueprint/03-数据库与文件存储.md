# 数据库与文件存储

这篇文档回答：**哪些东西应该进 PostgreSQL，哪些东西应该保存成文件，以及为什么内容要同时有 Current、Version 和 Metric。**

如果你只是想直接查数据库、看 Job、看最近内容或调试 SQL，请看 [`../appendix/PostgreSQL调试与常用SQL.md`](../appendix/PostgreSQL调试与常用SQL.md)。

## 1. 当前结论

AIMA_UGC 只有一个业务事实数据库：PostgreSQL 18。

```text
PostgreSQL
→ 业务身份
→ 当前状态
→ 历史版本/指标
→ 关系
→ Job
→ 配置
→ 来源账本
→ AI/Export 等持久事实

文件系统 / ArtifactStore
→ Provider Raw
→ Excel Input
→ Excel Export
→ 报告
→ 其他大文件

日志目录
→ api.log / worker.log / scheduler.log 等运行日志
```

数据库不会把所有东西塞进一个 JSONB；文件目录也不会代替数据库保存业务状态。

## 2. 为什么只使用 PostgreSQL

当前需要同时解决：

- 事务；
- 唯一约束和幂等；
- 多表关系；
- Job 认领/Lease；
- Current + 历史；
- 来源追溯；
- 查询、索引和聚合；
- Migration；
- 后续备份恢复。

一个 PostgreSQL 就能覆盖这些需求。

当前不维护 MySQL、SQLite、MongoDB 兼容层。需要验证真实事务、锁或约束时，测试使用隔离 PostgreSQL，不拿 SQLite 模拟后宣称数据库行为已验证。

## 3. 为什么大文件不直接塞数据库

Provider Raw、输入 Excel、导出 Excel、DOCX 这类对象可能很大，而且更适合按文件流读取。

当前分工：

```text
ArtifactService
→ 管 Artifact ID、元数据、业务关系、权限/生命周期

ArtifactStore
→ 只按 storage_key 存取字节
```

默认 `ArtifactStore` 是本地文件系统；以后真实需要对象存储时可以替换 S3 实现。

业务模块不应该直接拼接服务器文件路径。

## 4. 数据库类型规则

长期规则：

| 含义 | 类型原则 |
| --- | --- |
| 平台外部 ID | `text`，不强转整数 |
| 业务时间 | `timestamptz` |
| API 时间 | UTC ISO-8601 |
| 人工日志时间 | 北京时间文本 |
| 计数 | `bigint` 等足够范围类型 |
| 金额/费用 | `numeric`，不使用浮点累计 |
| 灵活扩展元数据 | 只在确实灵活时使用 `jsonb` |
| 状态 | 当前主要使用 `text + check` |
| 业务关系 | 外键/关联表，不用逗号字符串 |

“字段以后可能变化”不是把所有稳定字段塞进 JSONB 的理由。

## 5. 当前 Schema 按 Owner 怎么分

精确结构以 `backend/src/aima_ugc/database_schema.py`、各 `tables.py` 和 Alembic Migration 为准。这里只列当前主要事实，帮助建立地图。

### 5.1 System Owner

当前包括：

```text
system_settings
provider_configs
keyword_packs
keywords
keyword_pack_items
global_relevance_config
audit_events
```

Secret 不明文保存在 `provider_configs`；只保存 `secret_ref`，真实 Secret 由服务端 Secret 文件边界解析。

### 5.2 Collection Owner

主要包括：

```text
collection_plans
collection_plan_platforms
collection_plan_keyword_packs
collection_schedule_occurrences
collection_runs
collection_scopes
provider_requests
provider_request_attempts
Collection Candidate / Action / Ingestion Ledger 等采集事实
```

这些表负责“为什么采、哪次采、哪个请求、哪个 Attempt、看到了什么”，不拥有最终 Content Current。

### 5.3 Ingestion Owner

当前有正式：

```text
processing_import_batches
```

它是 Excel File Import 的父事实。

Stage 8A Migration 让 `provider_requests` 可以恰好属于：

```text
一个 Collection Scope
或
一个 Processing Import Batch
```

不能两者都有，也不能两者都没有。

### 5.4 Content Owner

当前包括账号、内容、评论及其历史：

```text
accounts
account_versions
account_metric_observations
contents
content_versions
content_metric_observations
comments
comment_versions
comment_metric_observations
以及媒体/话题/位置/coverage 等扩展关系
```

`contents` 还保存当前 relevance 投影字段，例如 `is_relevant`；默认业务查询只显示相关内容。

### 5.5 Platform

当前基础设施表包括：

```text
jobs
job_attempt_events
artifacts
```

Job 是持久任务事实，不是内存队列。

### 5.6 Analysis Owner

Analysis 已经是**当前正式机器 Schema**，不是未来规划：

```text
analysis_results
analysis_request_items
analysis_label_pairs
```

`analysis_results` 保存模型/Prompt/Token/成本、`voice_type`、sentiment、状态等父结果；一级/二级标签对由 `analysis_label_pairs` 保存。

精确业务语义见 [`../appendix/AI舆情分析与打标.md`](../appendix/AI舆情分析与打标.md)。

### 5.7 Reporting Owner

正式 Excel Export 也已经有当前机器 Schema：

```text
reporting_exports
reporting_export_items
```

它负责持久化“这次导出什么、状态如何、最终 Artifact 是谁”。离线 Word Renderer 是另一层能力，不直接拥有这些表。

## 6. 一张表为什么只能有一个写 Owner

如果 Collection 和 Content 两个 Repository 都能随意写 `contents`：

```text
Collection 的更新规则一套
Excel 导入又一套
人工操作再一套
```

很快就会出现不同的去重、Version、Metric 逻辑。

所以：

```text
Collection / Import / 其他来源
→ 产出合法 Canonical + 来源事实
→ 通过 Content Ingestion / Owner
→ 写 Content 表
```

读取则通过 Query Repository/Read Model，不要求所有模块复用一个“万能 Repository”。

## 7. Current + Version + Metric 为什么要拆开

### Current

页面和业务查询需要快速得到最新状态。

### Version

正文、标题、作者等业务内容真的发生变化时保存一个新版本。

### Metric Observation

点赞、评论、播放等数字经常变化，不应该每变一次就复制整份正文。

最小例子：

```text
10:00 正文 A，点赞 100
12:00 正文 A，点赞 120
14:00 正文 B，点赞 125
```

应该得到：

```text
Current → 正文 B / 点赞 125
Version → A、B
Metric  → 100、120、125 的必要观察历史
```

内容业务 Hash 只和当前版本比较，因此 `A → B → A` 会产生第三个版本。

## 8. 字段 freshness 解决什么问题

不同来源拿到的信息完整度不同。

例如：

```text
搜索列表拿到标题+点赞
详情接口拿到正文+作者+发布时间
下一次搜索没有返回作者字段
```

“这次没返回作者”不等于“作者被清空”。

Current 通过字段观察时间判断某个字段是不是被更近的真实观察覆盖，避免稀疏 Provider 响应把已有值错误置空。

## 9. 来源追溯怎么连回 Raw

正式数据不是只保留一个 `source='tikhub'` 字符串。

以 Collection 为例：

```text
Content Version / Metric
→ Provider Attempt
→ Provider Request
→ Scope / Run
→ Raw Artifact
```

File Import 则从 Attempt 回到 Import Batch/Input Artifact。

这样可以回答：

- 哪次 Run 发现？
- 哪个关键词/Scope？
- 哪次真实 Attempt？
- 当时的 Raw 是哪个？
- Mapper 失败前是否已经有 Candidate？

## 10. Job 为什么也放 PostgreSQL

当前规模下，任务状态和业务事实需要同一个事务边界。

例如创建一次导入：

```text
Import Batch
+ Job
```

必须保证不会只成功一个。

PostgreSQL Job 还提供：

- 原子 Claim；
- Lease；
- Heartbeat；
- Deadline；
- Fencing Token；
- Retry；
- Cancel；
- Progress；
- Attempt Event。

当前没有额外引入 Redis/RabbitMQ/Kafka。

## 11. 业务事实与下游 Job 要同事务提交

如果 Content 已写成功，但“后续分析 Job”在另一个事务创建失败，就会留下永远不会分析的数据。

所以需要下游异步动作时：

```text
业务事实
+ PostgreSQL Job
→ 同一 Unit of Work 提交
```

Job 表在这里同时承担事务型 Outbox 的作用。

## 12. Provider Billing 和 AI 成本怎么存

当前会保留执行审计：

- Provider Request/Attempt 成本；
- 单价快照；
- billing status；
- potential duplicate charge；
- Analysis input/output token；
- Analysis cost amount/currency。

但当前**没有**请求/金额 Budget Account、Reservation Ledger 或发送前预算门禁。

历史 Migration `0012/0013/0014` 曾建立过预算相关结构，`20260817_0015` 已向前删除。历史 Revision 不改写。

## 13. Migration 才是数据库结构演进方式

规则：

```text
改模型/Schema
→ 新 Alembic Revision
→ 测试从旧 Revision → head
→ 检查 downgrade 是否安全
→ alembic check
```

禁止：

- 修改已经发布的旧 Revision 来“整理历史”；
- API 启动时自动 create_all；
- 生产手工 ALTER 后不补 Migration；
- 文档写一份 DDL 当事实源。

当前 Migration 已演进到 `20260821_0023_analysis_relevance_voice_type.py`；下一次新增 Revision 时以仓库实际 `alembic heads` 为准，不在本文固定“永远是 0023”。

## 14. 数据库调试不要绕过业务边界

`SELECT` 很适合排障。

直接 `INSERT/UPDATE` 业务表则要谨慎，因为一条业务写入可能同时涉及：

```text
Current
Version
Metric
来源 Attempt/Artifact
下游 Job
```

正常写入优先走正式 Service/Repository/API/调试入口。

具体连接命令、安全 SQL、常用查询、`EXPLAIN`、Alembic 命令见 [`../appendix/PostgreSQL调试与常用SQL.md`](../appendix/PostgreSQL调试与常用SQL.md)。

## 15. 备份与恢复当前边界

长期要求是数据库 + Artifact 形成同一恢复点，而不是只备份 PostgreSQL 或只复制文件。

设计方向：

```text
统一写屏障
→ 排空在途写
→ 捕获数据库 + Artifact Backup Set
→ 校验
→ 可恢复
```

这套 Release 协调写屏障/Backup-Restore 尚未完成，不得写成当前生产能力。
