# 数据库与文件存储

## 1. 结论

业务事实使用 PostgreSQL 18。Raw 原始响应、File Import 输入、报告、导出和截图等大文件默认保存在宿主机文件系统，并通过 `ArtifactStore` 接口隔离；数据库保存文件元数据和关联关系。

```text
PostgreSQL
→ 身份、配置、状态、当前业务数据、历史、索引、关联、审计

文件系统
→ Provider Raw、File Import Input Artifact、报告、导出、截图、附件

日志目录
→ 独立的运行 `.log` 文件
```

禁止把所有东西都塞进数据库 JSON，也禁止只靠文件目录维持任务状态和业务当前值。

## 2. 为什么选择 PostgreSQL

一个数据库即可满足：

- 强事务；
- 唯一约束和幂等；
- 内容、评论和关键词关系；
- `jsonb` 灵活元数据；
- 时间序列历史；
- `FOR UPDATE SKIP LOCKED` Job 认领；
- GIN 和全文检索；
- Alembic Migration；
- 成熟备份恢复。

第一版不支持 MySQL、SQLite 或 MongoDB。测试需要真实数据库行为时使用隔离 PostgreSQL，不能用 SQLite 代替后宣称 PostgreSQL 已验证。

## 3. 数据类型规则

| 含义 | PostgreSQL 类型 | 规则 |
| --- | --- | --- |
| 内部主键 | `uuid` 或 `bigint` | 对外 ID 使用字符串序列化 |
| 平台外部 ID | `text` | 不转整数，避免溢出和前导零丢失 |
| 时间 | `timestamptz` | 数据库存 UTC |
| 日期 | `date` | 只在确实没有时刻含义时使用 |
| 布尔 | `boolean` | 禁止用 `0/1` 文本表达 |
| 计数 | `bigint` | 平台计数可能超过 32 位 |
| 金额/费用 | `numeric` | 禁止浮点累计费用 |
| 结构化扩展数据 | `jsonb` | 只保存灵活元数据，不替代稳定列 |
| 枚举状态 | `text + check` | 枚举变化较频繁时不使用 PostgreSQL ENUM |
| 校验和 | `text` | 小写十六进制 SHA-256 |
| IP | `inet` | 审计需要时使用 |
| 网络地址 | `text` | 业务 URL 保持原文和规范化 URL |

应用和 API 时间使用 ISO-8601；日志是例外，按人工排障格式显示北京时间。

## 5. 关键表

以下是字段和约束基线，不是可直接执行的完整 DDL。实际建表必须由 Alembic Revision 生成并通过集成测试验证。

### 5.1 `keyword_packs`

```text
id                  uuid primary key
name                text unique not null
description         text not null default ''
enabled             boolean not null
version             integer not null
created_at          timestamptz not null
updated_at          timestamptz not null
```

### 5.2 `keywords`

```text
id                  uuid primary key
text                text not null
normalized_text     text not null
enabled             boolean not null
created_at          timestamptz not null
updated_at          timestamptz not null

unique(normalized_text)
```

### 5.3 `keyword_pack_items`

```text
pack_id             uuid not null references keyword_packs
keyword_id          uuid not null references keywords
platform            text not null
priority            integer not null default 100
enabled             boolean not null
note                text not null default ''

primary key(pack_id, keyword_id, platform)
```

`platform='all'` 可以表达全平台词，但创建 Run 时必须展开成明确平台列表。`note` 与 `platform/priority/enabled` 一样是词包内词条的关系属性，不属于全局 `keywords` 身份。

### 5.4 `collection_plans`

```text
id                  uuid primary key
name                text unique not null
enabled             boolean not null
schedule_expr       text
timezone            text not null
schedule_version    integer not null default 1
next_run_at         timestamptz
last_scheduled_at   timestamptz
misfire_policy      text not null
max_catch_up_runs   integer not null
detail_policy       text not null
comment_policy      text not null
created_by          uuid
created_at          timestamptz not null
updated_at          timestamptz not null
```

Plan 平台和词包使用关联表，不使用 JSON 字符串作为主关系。修改影响调度语义的字段时必须递增 `schedule_version` 并重新计算 `next_run_at`。第一版 Plan `timezone` 固定 `Asia/Shanghai`。

### 5.5 `collection_schedule_occurrences`

一条 Occurrence 表示某个计划版本在一个逻辑调度时刻只允许触发一次：

```text
id                  uuid primary key
plan_id             uuid not null references collection_plans
schedule_version    integer not null
scheduled_for       timestamptz not null
job_id              uuid unique references jobs
status              text not null
skip_reason         text
created_at          timestamptz not null

unique(plan_id, schedule_version, scheduled_for)
check(status in ('enqueued', 'skipped'))
check(
  (status = 'enqueued' and job_id is not null and skip_reason is null)
  or (status = 'skipped' and job_id is null and skip_reason is not null)
)
```

Occurrence、Run、Job 与 Plan `last_scheduled_at/next_run_at` 的推进必须在同一短事务中完成；唯一约束是多 Scheduler 的最终防重事实。

### 5.6 `collection_runs`

```text
id                  uuid primary key
job_id              uuid unique not null references jobs
manual_plan_id      uuid references collection_plans
occurrence_id       uuid unique references collection_schedule_occurrences
trigger_type        text not null
config_snapshot     jsonb not null
status              text not null
started_at          timestamptz
finished_at         timestamptz
requested_count     integer not null default 0
succeeded_count     integer not null default 0
failed_count        integer not null default 0
content_count       integer not null default 0
comment_count       integer not null default 0
error_summary       text
created_at          timestamptz not null

check(
  (trigger_type = 'scheduled' and occurrence_id is not null and manual_plan_id is null)
  or (trigger_type in ('manual', 'api', 'backfill') and occurrence_id is null)
)
```

每个 Run 由一个 Job 驱动。scheduled Run 的 `config_snapshot` 冻结 Provider Config ID/Provider/Base URL/`secret_ref` 身份、平台业务配置、Decision Policy、最终关键词和 Deadline 技术执行上限；Secret 值不进入 Snapshot。人工/API/回补 Run 没有 Occurrence；需要基于一个 Plan 时可写 `manual_plan_id`。Run 当前只保存执行计数；Provider 费用事实留在 Request/Attempt Billing。

状态约束：

```text
queued
running
partial_success
succeeded
failed
cancelled
```

### 5.7A `collection_content_actions`

`collection_content_actions` 按 `(scope_id, external_content_id)` 冻结一次 Search 后续动作与恢复 checkpoint，保存 Search Attempt/Raw/观察时间、previous 最小快照、Detail/Comment Decision、目标和完成标记。其 Search 来源使用 Attempt+Raw 复合外键；所有读取/完成写入都先校验当前 Job Fence。

### 5.8 `provider_requests`

`provider_requests` 表示可幂等的逻辑请求，不代表某一次网络调用。Stage 8A 由 `20260820_0019` 把其来源父级最小一般化为 **Collection Scope XOR Processing Import Batch**：

```text
id                  uuid primary key
scope_id            uuid references collection_scopes       # nullable
import_batch_id     uuid references processing_import_batches # nullable
provider_config_id  uuid references provider_configs
provider            text not null
operation           text not null
request_fingerprint text not null
request_params      jsonb not null
pagination_input    jsonb not null default '{}'
status              text not null
attempt_count       integer not null default 0
estimated_cost      numeric(18,6) not null default 0
actual_cost         numeric(18,6) not null default 0
cost_currency       text
cost_unit           text
unit_price_snapshot numeric(18,6)
created_at          timestamptz not null
completed_at        timestamptz
error_code          text
error_detail        text

check(
  (scope_id is not null and import_batch_id is null)
  or (scope_id is null and import_batch_id is not null)
)
unique(scope_id, request_fingerprint)
unique(import_batch_id, request_fingerprint)
```

Collection Request 通过 `scope_id → collection_scopes.(run_id, platform)` 取得 Run/平台；File Import Request 不制造 Scope，而由 `import_batch_id` 指向 Processing/Import Batch。`provider_config_id` 用于外部 Provider 路由和审计；File Import 不绑定外部 Provider Config。`request_fingerprint` 由 Operation、脱敏后的稳定参数和分页状态生成。同一父级内相同逻辑请求由相应唯一约束保护。

Provider Request 已有 Attempt 后，来源父级、Provider Config、Provider 和 Operation 都不得被改写。`20260820_0019` 只向前扩展 lineage trigger，不改写历史 Revision/数据。

### 5.9 `provider_request_attempts`

`provider_request_attempts` 保存每一次真实 Provider 执行。HTTP/SDK Provider 的一次外部发送、文件/历史导入的一次受控读取分别形成独立 Attempt；HTTP 状态只在适用时填写。失败重试不能覆盖上一轮执行状态、费用或 Raw。

```text
id                  uuid primary key
provider_request_id uuid not null references provider_requests
attempt_no          integer not null
dispatch_status     text not null
dispatch_started_at timestamptz
completed_at        timestamptz
http_status         integer
external_request_id text
raw_artifact_id     uuid references artifacts
estimated_cost      numeric(18,6) not null default 0
actual_cost         numeric(18,6) not null default 0
cost_currency       text
cost_unit           text
unit_price_snapshot numeric(18,6)
billing_status      text not null
potential_duplicate_charge boolean not null default false
error_code          text
error_detail        text
created_at          timestamptz not null

unique(provider_request_id, attempt_no)
unique(id, provider_request_id)
unique(id, raw_artifact_id)
check(dispatch_status in ('reserved', 'dispatching', 'completed', 'not_sent', 'unknown'))
```

billable Attempt 在创建时保存发送前费用快照；Dispatcher 在短事务中沿 Attempt→Request→Scope→Run 验证当前 Job Fencing 后才允许 Collection Provider 发送。File Import 使用 non-billable Attempt，不通过 ProviderDispatchService 发外部请求；完成后 `raw_artifact_id` 真实绑定输入 Excel Artifact。Content/Version/Metric 等来源 FK 继续绑定 `Attempt + Raw Artifact` 复合来源，Stage 8A 没有降低这一约束。

### 5.10 `collection_candidates` 与 `collection_candidate_ingestions`

`collection_candidates` 是 **Collection 外部发现链** 的不可变逐项发现账本，不是最终内容副本：

```text
id                          uuid primary key
provider_request_attempt_id uuid not null references provider_request_attempts
item_kind                   text not null
external_item_id            text
item_locator                text not null
discovered_at               timestamptz not null
created_at                  timestamptz not null

unique(provider_request_attempt_id, item_locator)
check(item_kind in ('content', 'comment'))
```

Collection Candidate 的 Run/Scope/Raw/平台和来源通过 `Candidate → Attempt → Provider Request(scope_id) → Scope → Run` 与 `Attempt.raw_artifact_id` 推导；Candidate 在 Mapper 前建立。每次 Mapper/Ingestion 结果追加到 `collection_candidate_ingestions`，并由约束保证目标类型、平台和来源一致。

**Stage 8A File Import 不创建虚假的 Collection Candidate。** Excel 逐行定位由 Canonical `source.item_locator` 保留；其正式来源链为 `Input Artifact → ProcessingImportBatch → import-parent Provider Request/Attempt → Canonical Source → Content Owner`。这不是第二套 Content Writer，也不绕过 Attempt/Artifact 来源校验。

### 5.11 `processing_import_batches`

Stage 8A 的最小业务父事实：

```text
id                  uuid primary key
input_artifact_id   uuid not null references artifacts
job_id              uuid unique references jobs  # 当前可空
status              text not null
stats               jsonb not null default '{}'
error_summary       text
created_at          timestamptz not null
started_at          timestamptz
finished_at         timestamptz

check(status in ('processing','succeeded','failed'))
```

规则：

- Owner 为 `ingestion`；
- `input_artifact_id` 指向由 `ArtifactService` 保存的真实输入 Excel；
- Batch 不复制 Content/Comment 业务字段；
- 当前 Stage 8A 手工同步导入允许 `job_id=null`，Stage 8B 产品化上传/持久 Job 才冻结 HTTP/Job 绑定；
- `stats` 只保存 Stage 8A 实际需要的行计数，`error_summary` 只保存安全摘要；
- Batch 成功/失败不改变 PostgreSQL 作为唯一业务事实库的边界。

### 5.12 `accounts` 与公开作者资料

`accounts` 保存外部内容平台上的公开账号当前值，**不是系统登录用户、Principal 或认证账号表**。只有稳定 `external_account_id` 明确可得时才建立账号身份；只有昵称而没有稳定 ID 时，不按昵称制造账号身份。

`account_external_ids` 关系化保存备用稳定账号标识；Provider 私有临时 Token、签名和认证字段不得进入该表。账号字段遵守 Canonical `observed_fields` 稀疏合并，并由 `field_observed_at` 记录字段级最新观察时间。

### 5.13 `contents` 与 `content_versions`

`contents` 一帖/笔记/视频/微博一行，保存当前可查询值。业务唯一身份继续固定为：

```text
unique(platform, external_content_id)
```

`field_observed_at` 只保存 Canonical 字段路径 → 最新观察时间，不保存第二份业务值。Content Current 对每个 `observed_fields` 字段独立比较 freshness；较旧 Observation 可以补入此前未知字段，但不得回滚更晚已观察字段。

`content_versions` 只记录业务状态变化，Business Hash 仍只与当前版本比较，允许 `A → B → A` 产生新版本。Excel 与 TikHub 同身份 Content 进入同一个 Current；较新的合法 TikHub Observation 可以生成新的 Version/Metric，来源 Attempt/Artifact 各自保留。

### 5.14 内容指标 Observation

`content_metric_observations` 使用和 `contents.current_*` 一致的稳定指标语义。各值可空；指标 Observation 按本次 `observed_fields` 稀疏记录，不从 Current 静默复制旧值。继续使用 `initial/changed/daily_checkpoint`、来源 Attempt/Raw、`observation_key` 和 `Asia/Shanghai` 每日部分唯一约束保证历史与幂等。

### 5.15 内容子实体与来源

图片/视频/Live Photo/音频、话题、@提及和公开位置/IP 属地使用关系表：

```text
content_media
content_topics
content_mentions
content_locations
```

Collection 来源的逐次权威发现账本仍是 `collection_candidates → collection_candidate_ingestions → provider_request_attempts → Raw Artifact`；File Import 来源则由 ProcessingImportBatch/Import Request/Attempt + Input Artifact 组成。`CanonicalContentAggregateV1.lineage` 必须按来源类型从真实事实组装，不另建第二套 lineage 真相表。

### 5.16 `comments`、评论历史与覆盖

评论身份固定为 `(content_id, external_comment_id)`；评论 Current 同样按 `field_observed_at` 做字段级 freshness。`comment_versions` 保存业务变化，`comment_metric_observations` 保存指标历史，`comment_coverage_observations` 与 `comment_thread_coverage_observations` 保存采集覆盖事实。当前 Stage 8A Excel 主入口只处理当前 Excel Profile 能产生的 Content；未来 Excel Comment Profile 必须继续通过 `CanonicalCommentV1 → ContentIngestionService → Content Owner`，不能建立平行 Comment Writer。

### 5.17 Ingestion、稀疏更新和读取中间层

Mapper 不能写数据库。写入固定经过：

```text
CanonicalContentV1 / CanonicalCommentV1
→ ContentIngestionService
→ Content Owner Repository
→ PostgreSQL
```

Collection/TikHub 在此之前带有 Candidate ledger；File Import 在此之前带有 ProcessingImportBatch + Import Request/Attempt + Input Artifact。两种来源在 Canonical 后使用同一个 Content Owner。

数据库读取固定经过：

```text
PostgreSQL
→ Query Repository / Read Model
→ Query/Application Service
→ API / AI / Reporting
```

`CanonicalContentAggregateV1` 在读取时组装，不把整棵帖子+评论树作为单行巨大 JSON 保存。

### 5.18 `jobs`

`jobs` 是持久化 Job 当前快照，内部唯一键为：

```text
unique(job_type, internal_idempotency_key)
```

认领、接管、重试和终态历史追加到 `job_attempt_events`；每个 Attempt 有不可续期 Deadline，业务可见写入校验 Fencing。Stage 8A `tikhub_test` 显式 DB 模式为同步人工调试创建专用 manual Collection Run + 持久 Job/Fence；该 Job 类型使用独立 debug 前缀，不交给生产 `collection.run.v1` Worker 扫描。Excel Batch 当前同步入口 `job_id` 可空；Stage 8B 才产品化为持久 Job。

### 5.19 预算功能当前状态

当前版本**不保存 Provider Budget Account 或 Reservation Ledger**。历史 Revision `20260815_0012` 曾建立预算结构，后续 `20260817_0015` 按用户决定向前删除。`provider_requests.provider_config_id`、Billing/成本快照和 `potential_duplicate_charge` 继续保留，因为它们表达来源与执行审计，不是预算额度。

### 5.20 `artifacts`

`ArtifactService` 负责 ID、元数据和 `pending → stored → linked` 生命周期；`ArtifactStore` 只按 `storage_key` 存取字节。Stage 8A File Import 的输入 Excel 以 `kind=file-import.raw` 保存为正式 Artifact，ProcessingImportBatch 与非计费 Import Attempt 都真实引用它；不会把本地 `imports_test/output` 目录当业务数据库。

Provider HTTP Raw 的 `RawEnvelopeV1` 仍是 Collection-only `run_id/scope_id` 语义；Stage 8A 没有把 File Import 硬塞进 HTTP RawEnvelope。

### 5.21 `system_settings` 与 `audit_events`

`system_settings` 只保存非敏感设置；Secret 使用 Secret 文件/未来 Secret Provider。`audit_events` 只追加。当前仍不建立本地 `users/sessions/auth_login_attempts`。

## 6. `jsonb` 使用边界

适合：Run 配置快照、分页状态、Provider 脱敏请求参数、字段 freshness、不常查询扩展元数据、Job Payload/Result、Import Batch 最小统计、报告参数。

不适合：平台、外部内容 ID、关键词关系、状态、时间业务值、常用指标值、需要唯一约束/索引的核心字段。

原则：

> 稳定且需要查询、约束、关联的业务值用列；来源私有、变化快、低频查询的数据或内部 provenance 才用 `jsonb`。

## 7. 索引基线

必须按真实查询设计，不按“每列都加索引”。核心索引继续覆盖 Content/Comment Current/History、Collection Run/Scope、Provider Request/Attempt 和 Job。Stage 8A 由唯一约束保护 `(import_batch_id, request_fingerprint)`；当前没有页面查询需求证据，不额外为 `processing_import_batches` 预建低价值索引。

中文检索方案仍必须在阶段 0 用真实脱敏中文语料做质量/性能基准后再冻结。

## 8. 事务边界

### 8.1 Collection 内容摄取

典型 Collection 短事务包括：

- Upsert 当前内容/评论；
- 写 Version/Metric；
- 写 Candidate Ingestion；
- 更新 Run/Scope 计数；
- 如需触发下游 Job，与业务事实同一 PostgreSQL 事务提交。

Provider Raw 文件写入不放在数据库事务中，按 Artifact 生命周期衔接。

### 8.2 File Import 内容摄取

Stage 8A 文件阶段和数据库阶段明确分离：

```text
已有 Reader/Mapper/Filter/Dedup 文件产物
→ Input Artifact 落盘
→ 短事务创建 ProcessingImportBatch
→ 短事务/数据库事务建立 Import Request/Attempt 并写 Content Owner
→ Batch succeeded
```

若 Content 写入阶段中途失败，业务事务回滚，Batch 在独立失败事务中标记 `failed`；已生成的输入/调试文件和 Input Artifact 不删除。修正输入或数据库后可再次执行新 Batch，Content 稳定身份保证不会产生第二条业务 Current。

### 8.3 外部调用不能放在数据库事务中

禁止把 TikHub 等网络等待包在数据库事务内。Collection 正确边界仍是：

```text
短事务创建 reserved Attempt
→ CAS reserved → dispatching
→ 调用 Provider（同一 Attempt 最多一次）
→ Raw 落盘
→ 短事务终结 Attempt
→ Mapper
→ 业务短数据库事务
```

`tikhub_test` DB 模式使用同一正式边界，并将**同一次**响应镜像到调试 Raw 文件，不发第二次请求。

### 8.4 幂等

每个可重试操作必须有明确幂等键：

- HTTP 创建请求：`actor + operation + Idempotency-Key + request_hash + 有效期`（未来认证/API 冻结后）；
- 内部 Job：`job_type + internal_idempotency_key`；
- Collection Provider Request：`scope_id + request_fingerprint`；
- File Import Provider Request：`import_batch_id + request_fingerprint`；
- Provider Attempt：逻辑 Request + Attempt Number；
- Content：`platform + external_content_id`；
- Comment：`content_id + external_comment_id`；
- Version：只将 Business Hash 与当前版本比较；
- Observation：现有 Content Owner 稳定 Observation 规则；
- Report：报告参数 Hash + 数据截止时间。

批次内 Excel 去重只能降低重复处理，不能替代 PostgreSQL 最终唯一约束。

## 10. Migration

所有 Schema 演进使用根目录 `alembic.ini` + `migrations/`。历史 Revision 不改写。

当前末端链路重点：

```text
20260817_0017 → field_observed_at
20260818_0018 → Stage 1–7 comprehensive corrective / 复合 Attempt↔Raw 来源约束
20260820_0019 → Stage 8A ProcessingImportBatch + provider_requests 双父级
```

`20260820_0019`：

- 新建 `processing_import_batches`；
- `provider_requests.scope_id` 改为 nullable；
- 新增 nullable `import_batch_id` FK；
- 新增 exactly-one CHECK；
- 新增 `(import_batch_id, request_fingerprint)` Unique；
- 扩展 Provider Request lineage trigger，使 `scope_id/import_batch_id/provider_config_id/provider/operation` 在已有 Attempt 后不可改写；
- downgrade 先删除 Stage8A 新约束/列/表，再恢复 `scope_id NOT NULL` 与旧 lineage trigger。

Migration 门禁固定：

1. 已发布 Revision 禁止改写；
2. 应用启动不自动运行 Migration；
3. Table 定义与 Migration 用 `alembic check` 防漂移；
4. 验证 empty/base → head；
5. 验证上一正式 Revision `20260818_0018 → head`；
6. 验证 downgrade/re-upgrade；
7. 新增表声明唯一 Owner，并用真实 PostgreSQL 18 Integration 验证。

## 12. 文件存储

### 12.1 接口

当前生产接口以代码为准：

```python
class ArtifactStore(Protocol):
    @property
    def backend_name(self) -> str: ...
    def put(self, storage_key: str, data: bytes) -> StoredBytes: ...
    def read(self, storage_key: str) -> bytes: ...
    def exists(self, storage_key: str) -> bool: ...
```

Store 只处理 `storage_key` 和字节，不理解 Artifact UUID、数据库或权限。Artifact ID/元数据/生命周期由 `ArtifactService + ArtifactMetadataPort` 管理。

### 12.2 本地目录

```text
/data/AIMA_UGC/
├─ runtime/
│  ├─ data/
│  │  ├─ raw/
│  │  ├─ reports/
│  │  ├─ exports/
│  │  ├─ snapshots/
│  │  └─ temp/
│  └─ logs/
├─ postgres/
├─ backups/
├─ releases/
└─ shared/
   ├─ env/
   └─ secrets/
```

具体 Artifact `storage_key` 由 `ArtifactService`/业务 kind 生成；不要依赖调试目录作为业务事实。临时文件成功后原子移动到最终目录。

### 12.3 路径安全

- Storage Key 由系统生成；
- 用户输入不能直接成为文件路径；
- 路径必须留在配置根目录；
- 文件名不使用敏感文本；
- 下载通过 Artifact ID 查库；
- 校验文件大小和类型；
- 上传文件限制扩展名、MIME 和解压大小。

## 13. 保留策略

当前**不冻结具体天数**。自动清理前必须先批准 Retention Class 期限、访问权限、下载审计、引用保护、Dry Run 与持久 Job 机制。不得借“临时文件”名义删除 Raw、File Import 输入、报告、导出或审计业务证据。

## 14. 备份与恢复

常规/发布 Backup Set 必须协调 PostgreSQL 与 Artifact 同一截止点，并通过维护 epoch + PostgreSQL advisory 共享/独占写屏障排空在途业务写、Artifact 生命周期和文件 rename/delete。独立数据库备份或独立文件副本都不能单独宣称完整恢复点。

恢复后至少校验数据库、Artifact SHA-256、缺文件/孤儿文件/状态对账，并在隔离环境完成健康检查、内容/评论/Raw 抽查与测试 Job。RPO/RTO/保留期限仍需按正式门禁批准后才能宣称生产恢复方案已验收。

## 15. 旧系统数据迁移

新系统 Schema 稳定后的一次性 Importer 仍固定：

```text
旧库/旧文件
→ 只读导出
→ 映射到新 Canonical
→ 校验
→ 新系统 Ingestion
→ 对账报告
```

禁止让新业务代码长期兼容旧表。Importer 必须可重复运行、幂等、输出失败记录，不修改旧系统。其正式来源应复用 Stage 8A 已一般化的 File Import 来源边界，而不是新增第二套内容数据库 Writer。
