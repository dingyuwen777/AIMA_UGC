# 数据库与文件存储

## 1. 结论

业务事实使用 PostgreSQL 18。Raw 原始响应、报告、导出和截图等大文件默认保存在宿主机文件系统，并通过 `ArtifactStore` 接口隔离；数据库保存文件元数据和关联关系。

```text
PostgreSQL
→ 身份、配置、状态、当前业务数据、历史、索引、关联、审计

文件系统
→ Provider Raw、报告、导出、截图、附件

日志目录
→ 独立的运行 `.log` 文件
```

禁止把所有东西都塞进数据库 JSON，也禁止只靠文件目录维持任务状态和业务当前值。

## 2. 为什么选择 PostgreSQL

一个数据库即可满足：

- 强事务；
- 唯一约束和幂等；
- 内容、评论和关键词关系；
- `jsonb` 灵活元数据；
- 时间序列历史；
- `FOR UPDATE SKIP LOCKED` Job 认领；
- GIN 和全文检索；
- Alembic Migration；
- 成熟备份恢复。

第一版不支持 MySQL、SQLite 或 MongoDB。测试需要真实数据库行为时使用隔离 PostgreSQL，不能用 SQLite 代替后宣称 PostgreSQL 已验证。

## 3. 数据类型规则

| 含义 | PostgreSQL 类型 | 规则 |
| --- | --- | --- |
| 内部主键 | `uuid` 或 `bigint` | 对外 ID 使用字符串序列化 |
| 平台外部 ID | `text` | 不转整数，避免溢出和前导零丢失 |
| 时间 | `timestamptz` | 数据库存 UTC |
| 日期 | `date` | 只在确实没有时刻含义时使用 |
| 布尔 | `boolean` | 禁止用 `0/1` 文本表达 |
| 计数 | `bigint` | 平台计数可能超过 32 位 |
| 金额/费用 | `numeric` | 禁止浮点累计费用 |
| 结构化扩展数据 | `jsonb` | 只保存灵活元数据，不替代稳定列 |
| 枚举状态 | `text + check` | 枚举变化较频繁时不使用 PostgreSQL ENUM |
| 校验和 | `text` | 小写十六进制 SHA-256 |
| IP | `inet` | 审计需要时使用 |
| 网络地址 | `text` | 业务 URL 保持原文和规范化 URL |

应用和 API 时间使用 ISO-8601；日志是例外，按人工排障格式显示北京时间。

### 5.5 `collection_schedule_occurrences`

一条 Occurrence 表示某个计划版本在一个逻辑调度时刻只允许触发一次：

```text
id                  uuid primary key
plan_id             uuid not null references collection_plans
schedule_version    integer not null
scheduled_for       timestamptz not null
job_id              uuid unique references jobs
status              text not null
skip_reason         text
created_at          timestamptz not null

unique(plan_id, schedule_version, scheduled_for)
check(status in ('enqueued', 'skipped'))
check(
  (status = 'enqueued' and job_id is not null and skip_reason is null)
  or (status = 'skipped' and job_id is null and skip_reason is not null)
)
```

Occurrence 表只保存可提交终态：`enqueued` 必须有关联 Job/Run，`skipped` 必须有跳过原因且没有 Job/Run。Scheduler 在事务内预生成 Run/Job UUID：若入队，先插入 Job，再插入 `enqueued` Occurrence，最后插入引用它们的 Run；若按 misfire 策略跳过，只插入 `skipped` Occurrence。事务提交前，Deferred Constraint Trigger 必须验证每个 `enqueued` Occurrence 恰有一个反向 Run、该 Run 与 Occurrence 的 `job_id` 相同，而 `skipped` 没有 Run。正式关联是 `collection_runs.occurrence_id → occurrence.id`（唯一）、`occurrence.job_id → jobs.id`（唯一）和 `collection_runs.job_id → jobs.id`（唯一）；从 Occurrence 查 Run 通过反向关系，不冗余保存 `run_id`。Occurrence、Run、Job 与 Plan `last_scheduled_at`/`next_run_at` 的推进必须在同一短事务中完成。唯一约束是多 Scheduler 的最终防重事实；进程内锁或“先查询再插入”不能替代它。

### 5.6 `collection_runs`

```text
id                  uuid primary key
job_id              uuid unique not null references jobs
manual_plan_id      uuid references collection_plans
occurrence_id       uuid unique references collection_schedule_occurrences
trigger_type        text not null
config_snapshot     jsonb not null
status              text not null
started_at          timestamptz
finished_at         timestamptz
requested_count     integer not null default 0
succeeded_count     integer not null default 0
failed_count        integer not null default 0
content_count       integer not null default 0
comment_count       integer not null default 0
error_summary       text
created_at          timestamptz not null

check(
  (trigger_type = 'scheduled' and occurrence_id is not null and manual_plan_id is null)
  or (trigger_type in ('manual', 'api', 'backfill') and occurrence_id is null)
)
```

每个 Run 由一个 Job 驱动，`collection_runs.job_id` 是数据库可约束的业务绑定；Job Handler 通过该反向关系取得 Run，不依赖 Payload 中一个无法加外键的 Run ID。自动调度 Run 只通过 Occurrence 取得 Plan、Schedule Version 和 Scheduled For。scheduled Run 的 `config_snapshot` 冻结 Provider Config ID/Provider/Base URL/`secret_ref` 身份、平台业务配置、Decision Policy、最终关键词和 Deadline 技术执行上限；Secret 值不进入 Snapshot，同一 `secret_ref` 的文件内容可合规轮换。人工/API/回补 Run 没有 Occurrence；需要基于一个 Plan 时可写 `manual_plan_id`。Deferred Constraint Trigger 还必须验证 scheduled Run 的 `job_id = occurrence.job_id`；自动防重只依赖 Occurrence 唯一约束。

Run 当前只保存请求、成功、失败、内容和评论等执行计数。Provider 费用事实保留在 Request/Attempt Billing 字段；当前不建立 Run 预算或费用汇总表。

状态约束：

```text

running
partial_success
succeeded
failed
cancelled
```

### 5.7A `collection_content_actions`

`collection_content_actions` 按 `(scope_id, external_content_id)` 冻结一次 Search 后续动作与恢复 checkpoint，保存 Search Attempt/Raw/观察时间、previous 最小快照、Detail/Comment Decision、目标和完成标记。其 Search 来源使用 Attempt+Raw 复合外键；所有读取/完成写入都先校验当前 Job Fence。这样 Search 已更新 Current 后发生 Detail/Comments 失败，Job retry/takeover 仍恢复本次未完成动作，而不是重新计算后静默跳过。

### 5.8 `provider_requests`

`provider_requests` 表示可幂等的逻辑请求，不代表某一次网络调用。

```text
id                  uuid primary key
scope_id            uuid not null references collection_scopes
provider_config_id  uuid references provider_configs
provider            text not null
operation           text not null
request_fingerprint text not null
request_params      jsonb not null
pagination_input    jsonb not null default '{}'
status              text not null
attempt_count       integer not null default 0
estimated_cost      numeric(18,6) not null default 0
actual_cost         numeric(18,6) not null default 0
cost_currency       text
cost_unit           text
unit_price_snapshot numeric(18,6)
created_at          timestamptz not null
completed_at        timestamptz
error_code          text
error_detail        text

unique(scope_id, request_fingerprint)
```

`run_id` 和 `platform` 不在此表重复保存；通过 `scope_id → collection_scopes.(run_id, platform)` 取得唯一 Run/平台，避免冗余列从插入时就互相矛盾。`provider_config_id` 是 Stage 7 `20260815_0012` 增加的稳定 Provider 配置实例身份；历史和不计费 Request 可以为空，新建 billable Attempt 必须显式绑定具体 Config，且 Request 已有 Attempt 后该来源身份不可改写。该字段用于 Provider 来源与执行审计，不代表当前存在预算账户。`request_fingerprint` 由 Operation、脱敏后的稳定参数和分页状态生成。同一 Job 重试复用逻辑请求，不重复创建业务页任务。

### 5.9 `provider_request_attempts`

`provider_request_attempts` 保存每一次真实 Provider 执行。HTTP/SDK Provider 的一次外部发送、文件/历史导入的一次受控读取分别形成独立 Attempt；HTTP 状态只在适用时填写。失败重试不能覆盖上一轮执行状态、费用或 Raw。

```text
id                  uuid primary key
provider_request_id uuid not null references provider_requests
attempt_no          integer not null
dispatch_status     text not null
dispatch_started_at timestamptz
completed_at        timestamptz
http_status         integer
external_request_id text
raw_artifact_id     uuid references artifacts
estimated_cost      numeric(18,6) not null default 0
actual_cost         numeric(18,6) not null default 0
cost_currency       text
cost_unit           text
unit_price_snapshot numeric(18,6)
billing_status      text not null
potential_duplicate_charge boolean not null default false
error_code          text
error_detail        text
created_at          timestamptz not null

unique(provider_request_id, attempt_no)
unique(id, provider_request_id)
unique(id, raw_artifact_id)  # 0018 供所有业务来源复合 FK 绑定同一 Attempt/Raw
check(dispatch_status in ('reserved', 'dispatching', 'completed', 'not_sent', 'unknown'))
check(
  (dispatch_status = 'reserved' and dispatch_started_at is null and completed_at is null)
  or (dispatch_status = 'dispatching' and dispatch_started_at is not null and completed_at is null)
  or (dispatch_status = 'not_sent' and dispatch_started_at is null and completed_at is not null)
  or (dispatch_status in ('completed', 'unknown') and dispatch_started_at is not null and completed_at is not null)
)
```

`billing_status` 至少区分 `not_billable`、`estimated`、`confirmed` 和 `unknown`。billable Attempt 在创建时保存发送前实际采用的 `unit_price_snapshot/estimated_cost/currency/unit`；Dispatcher 必须把这份持久化计划快照交给 Provider Client。确定响应没有权威逐请求账单时，不能把本地估算伪装成 `actual_cost`，也不能用响应缺少 Billing 把计划费用覆盖成不计费；只有 Provider 给出权威逐请求费用时才使用 `confirmed + actual_cost`。Dispatcher 在短事务中沿 Attempt→Request→Scope→Run 锁住所属 Job，验证当前 `status=running + lease_token + lease/deadline 未过期`，再以 CAS 将 `reserved → dispatching`；只有赢得 CAS 的执行者可以调用 Provider Client。Transport 层必须关闭会在一次调用内部悄悄重发网络请求的自动重试；同一 Attempt 不能再次进入发送，任何真正重发都先建新 Attempt。活跃 Transport 明确证明请求未进入发送边界时，Dispatcher 可把已进入数据库 `dispatching` 的 Attempt 终结为 `not_sent` 并清除发送开始时间；一旦进程崩溃、超时或无法取得完整性已验证 Raw，就不能事后宣称未发送，而要保守转为 `unknown`，并禁止复用该 Attempt 发送。Collection Attempt Reconciler 在所属 Job Lease 丢失/Deadline 到达后锁住遗留 `dispatching` Attempt：对 `stored/linked` Raw 先校验 metadata SHA-256/字节数，再校验 gzip 与 Raw Envelope Contract；如果确定性文件已经落盘但 Artifact metadata 仍是 `pending`，只允许 Recovery 专用路径在 gzip/Envelope 完整校验后重新计算 SHA-256/字节数并以状态 CAS 确认为 `stored`，随后恢复 terminal 状态。文件不存在、损坏、来源不一致或状态不合法时才转为 `unknown`，并记录不包含 Raw/Secret 的安全 warning；旧 Worker 受 Job Fencing 约束，不能随后覆盖。后续真实网络重试创建新 Attempt，并把 `potential_duplicate_charge` 标记为真。逻辑请求的 `attempt_count` 和已知费用按 Attempt 汇总，Request 状态镜像最新 Attempt；创建新 Attempt 时重置为 `pending`。Canonical、版本和指标记录引用实际产生数据的 Attempt，从而保留完整来源。为保持该来源链，数据库 Trigger 必须禁止：Scope 已有 Provider Request 后修改其 `run_id/platform/source` 身份；Provider Request 已有 Attempt 后修改 `scope_id/provider_config_id/provider/operation`；Attempt 修改 `provider_request_id`，或在 terminal 一次性设置 `raw_artifact_id` 后再次改写/清除。后续计费对账只能修改计费状态/金额等允许字段，不能改来源身份。

### 5.10 `collection_candidates` 与 `collection_candidate_ingestions`

`collection_candidates` 是不可变的逐项发现账本，不是最终内容副本：

```text
id                          uuid primary key
provider_request_attempt_id uuid not null references provider_request_attempts
item_kind                   text not null
external_item_id            text
item_locator                text not null
discovered_at               timestamptz not null
created_at                  timestamptz not null

unique(provider_request_attempt_id, item_locator)
check(item_kind in ('content', 'comment'))
```

Run、Scope、Raw、平台和来源不在 Candidate 重复保存，而通过唯一链 `candidate.provider_request_attempt_id → provider_request_attempts.provider_request_id → provider_requests.scope_id → collection_scopes.run_id` 以及 `provider_request_attempts.raw_artifact_id` 推导。Candidate 插入时 Deferred Constraint Trigger 必须验证 Attempt 为 `completed`、Raw Artifact 非空且已通过完整性校验；因此数据库不能把不同 Run/Scope/Attempt/Raw 的冗余列拼成伪造来源。Candidate 与 Ingestion 表由 Owner 数据库角色只允许追加，身份/结果记录不得 UPDATE/DELETE；纠错追加新的 Ingestion 记录。`item_locator` 是 Operation 在同一 Raw 内生成的稳定位置或来源项键，不得使用易变数组下标作为唯一事实。每次 Mapper/Ingestion 的结果追加到 `collection_candidate_ingestions`：

```text
id                  uuid primary key
candidate_id        uuid not null references collection_candidates
ingestion_no        integer not null
canonical_version   text
canonical_identity  text
observed_fields     jsonb not null default '[]'
target_type         text
content_id          uuid references contents
comment_id          uuid references comments
result              text not null
error_code          text
error_detail        text
processed_at        timestamptz not null

unique(candidate_id, ingestion_no)
check(
  (target_type = 'content' and content_id is not null and comment_id is null)
  or (target_type = 'comment' and comment_id is not null and content_id is null)
  or (target_type is null and content_id is null and comment_id is null)
)
```

`item_kind` 与 `target_type` 至少区分 `content` 和 `comment`；互斥外键与 CHECK 避免不可约束的多态 `target_id`。Deferred Constraint Trigger 验证非空 `target_type = collection_candidates.item_kind`，并验证目标 Content（或 Comment 所属 Content）的 `platform` 等于沿 Candidate→Attempt→Request→Scope 推导的平台，不能把评论 Candidate 写成内容结果，也不能跨平台挂接目标。由于表说明顺序早于目标表，实际 Migration 可以在目标表建立后追加两个外键。`result` 至少区分 `ingested`、`duplicate`、`invalid`、`unsupported` 和 `failed`；没有目标行的失败结果将 `target_type/content_id/comment_id` 全部留空。聚合表 `content_discoveries` 便于查询，但不能替代这两张逐次账本；系统必须能从 Content 或 Comment 沿受约束链追溯到 Candidate、Attempt、Raw、Run 和 Scope。

### 5.11 `accounts` 与公开作者资料

`accounts` 保存外部内容平台上的公开账号当前值，**不是系统登录用户、Principal 或认证账号表**。只有稳定 `external_account_id` 明确可得时才建立账号身份；只有昵称而没有稳定 ID 时，不按昵称制造账号身份，实际观察到的作者快照仍由 Content/Comment Version 保存。

```text

profile_url           text
avatar_url             text
bio                    text
verified               boolean

current_follower_count bigint

current_content_count bigint
current_total_like_count bigint
first_seen_at          timestamptz not null
last_seen_at           timestamptz not null
field_observed_at      jsonb not null default '{}'
updated_at             timestamptz not null

unique(platform, external_account_id)
```

`account_external_ids` 关系化保存 `red_id`、`sec_uid`、B站账号 `mid`、快手用户 ID 等备用稳定账号标识；Provider 私有临时 Token、签名和认证字段不得进入该表。账号字段遵守 Canonical `observed_fields` 稀疏合并，并由 `field_observed_at` 记录每个已观察字段的最新带时区观察时间：本次没观察到的简介/头像/统计不能清空旧值；较旧 Observation 可以补入更晚 Observation 从未观察过的字段，但不能覆盖已经有更晚字段 freshness 的值。明确观察到 `null` 也会推进该字段 freshness，不能再由更旧 Observation 回填。`last_seen_at` 继续表示实体级最近看见时间，并不替代字段 freshness。稳定 `account_external_ids` 同一 `account_id + id_type` 出现不同值时 fail-closed，不按到达顺序静默覆盖。是否对粉丝数等账号统计建立独立长期 Observation，在实际账号趋势需求进入范围时另行冻结，不在 Stage 3B 偷加历史策略。

### 5.12 `contents` 与 `content_versions`

`contents` 一帖/笔记/视频/微博一行，保存当前可查询值：

```text

external_content_id     text not null
content_type            text not null

canonical_url           text
share_url               text
```

`field_observed_at` 只保存 Canonical 字段路径 → 最新观察时间，不保存第二份业务值。Content Current 对每个 `observed_fields` 字段独立比较 freshness：较旧 Detail 可以补上较新 Search 没观察到的 `text` 等字段；但较旧 Observation 不得回滚已经由更晚 Observation 明确观察过的标题、正文、作者关系或 Current 指标。`first_seen_at` 可被更早补录向前扩展，`last_seen_at/updated_at` 保持实体级单调向前。

`content_versions` 只记录业务状态变化，保留标题、正文、内容类型、URL、作者公开快照、发布时间/来源更新时间、状态和本次来源；作者快照使用版本化 `jsonb` 保存当时 `CanonicalAuthorV1` 的完整公开观察，避免账号后来改名后丢失历史上下文。字段级合并后 Current 业务状态发生变化才推进 `current_version`；较旧 Observation 补入此前未知字段也属于新的合法 Current 业务事实。Business Hash 仍只和当前版本比较，允许 `A → B → A` 产生新版本。

### 5.13 内容指标 Observation

`content_metric_observations` 与 `contents.current_*` 使用同一稳定指标语义：

```text
like_count
comment_count
share_count
repost_count
favorite_count
view_count
play_count
danmaku_count
coin_count
download_count
```

各值可空：`null` 表示未知/本次未提供，`0` 表示明确观察到零。指标 Observation 必须按本次 `observed_fields` 稀疏记录，未观察字段保持 `null`，不能从 Current 静默复制旧值伪造历史。新 Observation 可以比旧值小，禁止把指标写成单调递增或只保留最大值。较旧 `observed_at` 的补录仍可形成合法历史事实并向前扩展 `first_seen_at`；是否改变 Current 指标由该指标自己的 `field_observed_at` 决定，而不是整行 `last_seen_at`。较旧 Observation 可以填充从未观察过的指标，但不得覆盖更晚 Observation 已明确观察的同一指标，`updated_at` 与实体级 `last_seen_at` 也不得回退。继续使用 `initial`、`changed`、`daily_checkpoint`、来源 Attempt/Raw、`observation_key` 和 `Asia/Shanghai` 每日部分唯一约束保证历史与幂等。

### 5.14 内容子实体与来源

图片/视频/Live Photo/音频、话题、@提及和公开位置/IP 属地不能塞进一个不可查询的大帖子 JSON。目标关系按内容 Owner 管理：

```text
content_media
content_topics
content_mentions
content_locations
```

列表顺序需要展示语义时保存稳定 `position`。Provider 编码流、CDN 实验字段、临时签名等只留 Raw，不为了“字段多”污染业务表。

`content_discoveries` 继续保存来源聚合；逐次权威来源仍是 `collection_candidates → collection_candidate_ingestions → provider_request_attempts → Raw Artifact`，`CanonicalContentAggregateV1.lineage` 从这些事实组装，不另建第二套 lineage 真相表。

### 5.15 `comments`、评论历史与覆盖

`comments` 一评论/回复一行：

```text
id                    uuid primary key

external_comment_id   text not null
root_comment_id       text
parent_comment_id     text
author_account_id     uuid references accounts
text                  text
published_at          timestamptz
source_updated_at     timestamptz
status                text
is_by_content_author  boolean

last_seen_at           timestamptz not null
current_like_count     bigint
current_reply_count    bigint

```

评论平台由 Content 推导；`external_comment_id` 是自身身份，`root_comment_id` 表示一级线程根，`parent_comment_id` 表示直接回复对象。父/根评论可能被删除或尚未抓到，因此不凭数组层级猜关系，也不要求所有外部关系立刻能建数据库外键。

评论 Current 同样按 `field_observed_at` 做字段级 freshness：较旧页可以补入较新页未观察到的 `parent_comment_id` 等字段，但不能覆盖更晚 Observation 已明确观察的文本、关系、作者或指标。`comment_versions` 保存评论文本、root/parent 关系、作者公开快照、状态等业务变化；`comment_metric_observations` 保存 `like_count/reply_count` 的初始、变化和每日检查点。`comment_media/comment_mentions/comment_locations` 保存可查询子实体。

`comment_coverage_observations` 保存一次评论采集对某个内容或线程的覆盖事实：`complete/partial/not_requested/unavailable`、平台报告总数、已采集数、`sample_mode`、`sort_mode`、`target_count`、`stop_reason`、观察时间和 Provider Attempt/Raw 来源。同一 `content_id + provider_attempt_id + raw_artifact_id` 来源必须幂等。这样 Read Model 不仅能区分“没有评论”和“没有抓评论”，还能解释为什么停止、是否为抽样以及目标深度是多少。

### 5.15A Ingestion、稀疏更新和读取中间层

Mapper 不能写数据库。写入固定经过：

```text
CanonicalContentV1 / CanonicalCommentV1
→ ContentIngestionService
→ Content Owner Repository
→ PostgreSQL
```

Ingestion 依据 `observed_fields` 合并：只处理本次明确观察字段；未观察字段保留数据库已有值；明确 `null` 也是一次真实观察并推进该字段 freshness。`accounts/contents/comments.field_observed_at` 记录字段级最新观察时间，解决 Search/Detail/Comments 不同来源稀疏且乱序到达时的 Current 仲裁；不能再使用实体级 `last_seen_at` 一次性拒绝整条旧 Observation。Candidate Ingestion 账本继续保留 Canonical 版本、身份和本次 `observed_fields`，便于审计稀疏合并。

数据库读取固定经过：

```text
PostgreSQL
→ Query Repository / Read Model
→ Query/Application Service
→ API / AI / Reporting
```

`CanonicalContentAggregateV1` 在读取时按 `contents/accounts/media/topics/mentions/locations/comments/coverage` 和来源账本组装，包含一级评论线程、回复、无法可靠归线程的评论、`system` 和 `lineage`；**数据库不把整棵帖子+评论树作为单行巨大 JSON 保存**。

Stage 3B 冻结了持久化语义；Stage 6 通过正式 Migration/Repository 落地 Content/Comment，`20260817_0017` 加入字段级 freshness；当前 `20260818_0018` 进一步落地 Decision Policy、durable content action、Content/Comment Canonical 子实体、thread Coverage，以及 Version/Metric/Coverage/子实体到 Provider Attempt+Raw 的复合来源约束。未来结构仍必须通过向前 Migration 和 PostgreSQL 集成测试演进，不得改写历史 Revision。

### 5.15A Thread Coverage 与 Canonical 子实体

`content_external_ids/content_media/content_topics/content_mentions/content_locations` 与 `comment_media/comment_mentions/comment_locations` 保存当前 Canonical 中已观察的稳定集合字段，按父实体字段 freshness 接受新观察，旧 Raw replay 不得覆盖更新事实。`comment_thread_coverage_observations` 以 Content + root comment + Attempt + Raw 为来源幂等键；`complete` 且有 `reported_total` 时数据库要求 `captured_count >= reported_total`，`not_requested/unavailable` 要求采集数为 0。Content Owner 是这些表的唯一写入口。

### 5.15B Discovery 查询聚合（非当前独立表）

同一内容可能被多个关键词、话题或账号发现，不能只保存一个 `source_keyword`。当前机器事实由逐项 `collection_candidates/collection_candidate_ingestions` 与 Attempt/Raw 来源链保存；如果未来增加独立 Discovery 查询聚合，必须明确它只是可重建读模型，不能成为第二套来源真相。

### 5.16 `jobs`

```text

payload_version     text not null
payload             jsonb not null
result              jsonb
status              text not null
internal_idempotency_key text not null
request_id          text

attempt             integer not null
lease_takeover_count integer not null default 0
max_attempts        integer not null
timeout_seconds     integer not null
attempt_started_at  timestamptz
attempt_deadline_at timestamptz
progress            integer not null
available_at        timestamptz not null
lease_owner         text
lease_token         text
lease_expires_at    timestamptz
heartbeat_at        timestamptz
cancel_requested_at timestamptz

error_code          text

updated_at          timestamptz not null

unique(job_type, internal_idempotency_key)
check(status in ('queued', 'running', 'succeeded', 'failed', 'cancelled'))
check(attempt >= 0 and max_attempts > 0 and attempt <= max_attempts)
check(status <> 'queued' or attempt < max_attempts)
check(lease_takeover_count >= 0 and timeout_seconds > 0)
check(progress between 0 and 100)
check(
  (status = 'running'
   and attempt >= 1
   and lease_owner is not null
   and lease_token is not null
   and lease_expires_at is not null
   and attempt_started_at is not null
   and attempt_deadline_at is not null
   and lease_expires_at <= attempt_deadline_at)
  or (status <> 'running'
      and lease_owner is null
      and lease_token is null
      and lease_expires_at is null)
)
check(
  status <> 'queued'
  or (attempt_started_at is null and attempt_deadline_at is null and finished_at is null)
)
check(
  (status in ('succeeded', 'failed', 'cancelled') and finished_at is not null)
  or (status in ('queued', 'running') and finished_at is null)
)
```

这里的唯一键只用于**系统内部工作项**，例如 `collection.run:{run_id}`，不表达 HTTP 用户、Payload 或有效期语义。Job Payload 必须由 Pydantic 模型校验并带版本，不能把任意 dict 当长期契约。从 `queued` 开始新 Attempt 时递增 `attempt`，以同一语句捕获的一次 `clock_timestamp()` 设置 `attempt_started_at` 和不可被 Heartbeat 延长的 `attempt_deadline_at = attempt_started_at + timeout_seconds`；`attempt < max_attempts` 只限制开始新 Attempt。`running` 且 Lease 过期但未到 Deadline 的 Job 可由新 Worker 原子接管并保留 Attempt 计数/Deadline；达到 Deadline 后由 Platform Reaper 用状态+Token 的 CAS 事务按次数和错误策略重新排队或置为终态失败，不能永久停留在 `running`。

`jobs` 只保存当前快照；认领、接管、重试和终态历史追加到 `job_attempt_events`：

```text
job_attempt_events
  id                  uuid primary key
  job_id              uuid not null references jobs
  event_seq           integer not null
  attempt             integer not null
  lease_takeover_count integer not null
  event_type          text not null
  worker_id           text
  lease_token_fingerprint text
  reason_code         text
  safe_detail         text
  happened_at         timestamptz not null

  unique(job_id, event_seq)
  check(attempt >= 0 and lease_takeover_count >= 0)
  check(event_type in ('claimed', 'lease_taken_over', 'retry_scheduled', 'succeeded', 'failed', 'cancelled', 'timed_out', 'lease_lost'))
```

事件必须与对应 Job 状态转换在同一事务追加；Token 只保存不可逆安全指纹，不保存原值。正常 Heartbeat 不逐次写事件，续租异常写结构化日志；这样既保留每个 Attempt/接管/失败原因，又避免 Heartbeat 制造无界事件量。

### 5.17 预算功能当前状态

当前版本**不保存 Provider Budget Account 或 Reservation Ledger**。历史 Revision `20260815_0012` 曾建立 `provider_budget_accounts/provider_budget_reservations`，后续 `20260817_0015` 按用户决定向前删除这两张表，并删除 `collection_plans.request_budget`；历史 Revision 不改写。

`provider_requests.provider_config_id`、Provider Request/Attempt 的 Billing/成本快照和 `potential_duplicate_charge` 继续保留，因为它们表达来源与执行审计，而不是预算额度。未来若重新引入 Budget/Cost Guard，必须通过新的 L3 Change 建立新的 Contract/Schema/Migration/测试，不能复活已删除的 Runtime 代码。

### 5.18 `artifacts`

Stage 3A 已由 `20260813_0001` Revision 建立，机器事实以 `platform/storage/tables.py`、Migration 和测试为准：

```text
id                  uuid primary key
kind                text not null
storage_backend     text not null
storage_key         text not null
content_type        text not null
encoding            text
sha256              text
byte_size           bigint
retention_class     text not null
storage_status      text not null
created_at          timestamptz not null
stored_at           timestamptz
linked_at           timestamptz
expires_at          timestamptz
deleted_at          timestamptz
```

唯一 `(storage_backend, storage_key)`；状态只允许 `pending/stored/linked/delete_pending/deleted/error`，并有状态字段一致性 CHECK。Stage 3A PostgreSQL Repository 正式实现 Stage 2 的 `ArtifactMetadataPort`，使用 `id + 当前状态` 条件更新推进 `pending → stored → linked` 或 `pending → error`；并发或非法转换更新不到行时关闭失败，不静默覆盖状态。

正常写入顺序仍是“先登记 `pending` → ArtifactStore 原子写字节 → 写入 SHA-256/byte_size 并 CAS `pending → stored` → 业务引用成功后 `stored → linked`”。如果进程恰好在**文件已原子落盘、metadata 尚未标记 stored**的窗口崩溃，Provider Raw Recovery 可以读取确定性 storage key：只有 gzip 与 Raw Envelope Contract 全部有效时，才根据实际字节重新计算 SHA-256/byte_size 并通过 Artifact Metadata Port 的状态 CAS 确认为 `stored`。普通 Artifact replay 不接受 `pending`，损坏/缺失文件也不能借恢复路径伪造 `stored`。

`retention_class` 只是未来保留策略的分类入口，`expires_at` 当前可空。具体 Raw/报告/审计保留期限尚未批准，本阶段不自动填写统一到期日，也不实现 Artifact 删除 Job。

## 6. `jsonb` 使用边界

适合：

- Run 配置快照；
- 分页状态；
- Provider 脱敏请求参数；
- Current 字段 freshness（字段路径 → 最新观察时间）；
- 不常查询的扩展元数据；
- Job Payload/Result；
- 报告参数。

不适合：

- 平台；
- 外部内容 ID；
- 关键词关系；
- 状态；
- 时间业务值；
- 点赞、评论等常用指标值；
- 需要唯一约束或索引的核心字段。

原则：

> 稳定且需要查询、约束、关联的业务值用列；来源私有、变化快、低频查询的数据或内部 provenance 才用 `jsonb`。

`field_observed_at` 是该原则的明确例外用途：它只保存内部 provenance，不保存第二份业务值，也不能替代稳定 Current 列。

必须按真实查询设计，不按“每列都加索引”。

核心索引：

## 8. 事务边界

### 8.1 一次内容摄取

同一事务内：

- Upsert 当前内容；
- 写 Content Version；
- 写 Metric Observation；
- 写 Discovery；
- 写 Candidate Ingestion 结果；
- 更新 Run/Scope 计数。
- 如需触发 Analysis/Monitoring，把版本化 Job 与上述业务写入放在同一 PostgreSQL 事务中。

Raw 文件写入不放在数据库事务中，按 `pending → stored → linked` 生命周期衔接；数据库事务失败时保留可对账的 `stored` Artifact，并可从 Raw 重试。文件已落盘但 metadata 仍 `pending` 的特殊崩溃窗口只由受限 Recovery 路径在完整性校验后确认，不改变正常生命周期。业务提交与下游 Job 入队使用同一 Unit of Work，使 PostgreSQL Job 表同时承担事务型 Outbox 的作用，避免“内容已提交但任务未创建”。

### 8.2 外部调用不能放在数据库事务中

禁止：

```text
BEGIN
→ 调 TikHub 等待 30 秒
→ 写库
→ COMMIT
```

正确：

```text
短事务创建 reserved Attempt
→ CAS reserved → dispatching
→ 调用 Provider（同一 Attempt 最多一次）
→ Raw 落盘
→ 短事务把 Attempt 记为 completed、not_sent 或 unknown
→ Mapper
→ 业务短数据库事务
```

创建 Attempt、Dispatch CAS、网络调用和结果事务是明确的四个边界，不能把外部等待包进数据库事务。恢复时看到遗留 `dispatching` 必须先检查已校验 Raw；无法确定结果时保守转 `unknown`，不得复发同一 Attempt。只有明确证明未进入发送边界时才能终结为 `not_sent`。

### 8.3 幂等

每个可重试操作必须有明确幂等键：

- HTTP 创建请求：`actor + operation + Idempotency-Key + request_hash + 有效期`；
- 内部 Job：`job_type + internal_idempotency_key`；
- Provider Request：Scope + Request Fingerprint；
- Provider Attempt：逻辑 Request + Attempt Number；
- Content：平台 + 外部内容 ID；
- Comment：平台 + 内容 + 外部评论 ID；
- Version：只将 Business Hash 与当前版本比较；历史相同 Hash 可以再次出现；
- Observation：内容 + Request + Observation Hash；
- Report：报告参数 Hash + 数据截止时间。

## 9. 表写入所有权

每张已落地表只有一个写 Owner，机器事实维护在 SQLAlchemy `Table.info['owner']`，`scripts/quality/check_table_ownership.py` 在 CI 中不仅校验 owner 存在且属于批准模块，还对已形成稳定命名的 Platform/System/Collection/Content 表族校验期望 Owner，防止通过随意填写另一个合法 owner 绕过边界。

跨模块修改必须调用 Owner Service/Repository，禁止复制 SQL 越权写表。角色、Session、API 幂等等未建立表不应出现在“当前 Owner”清单中。

## 10. Migration

所有 Schema 演进使用根目录 `alembic.ini` + `migrations/`。当前 Alembic 链继续保持历史 Revision 不改写：`20260815_0012` 曾为 `provider_requests` 增加稳定 `provider_config_id` 并建立 Budget Ledger，`0013/0014` 建立 Plan/Scheduler 事实，`20260817_0015` 按用户决定向前删除预算两表和 `collection_plans.request_budget`，`20260817_0016` 补齐评论 Coverage 可观测字段与来源幂等，`20260817_0017` 为 `accounts/contents/comments` 增加字段级 `field_observed_at` 并按已有 `last_seen_at` 为历史非空 Current 字段做保守 backfill。`provider_config_id` 与 Provider Billing/成本审计字段保留。

规则：

1. 已发布 Revision 禁止改写；后续变化新增 Revision；
2. API/Worker/Scheduler 启动不自动运行 Migration；Migration 是独立进程/命令；
3. Table 定义是运行时 Schema/Repository 的机器结构，Revision 显式冻结已批准变化；CI 使用 `alembic check` 防止二者漂移；
4. 第二条及后续 Revision 必须同时验证上一正式 Revision → head；CI 还应保留 `base → head` 往返验证，不能只验证 `base → head`；
5. downgrade 是开发/CI 可逆性证据，不替代生产 Backup Set 与数据回滚设计；
6. 任何新增表必须同时声明唯一 Owner 并通过 PostgreSQL Integration。

## 11. 分区和归档

第一版不预先给所有历史表分区。出现以下情况再增加月分区：

- 单表进入千万级并持续增长；
- 删除/归档造成长事务；
- 时间范围查询和 Vacuum 明显恶化；
- 实际执行计划证明分区有收益。

优先候选：

- `content_metric_observations`；
- `comment_metric_observations`；
- `provider_requests`；
- `audit_events`。

## 12. 文件存储

### 12.1 接口

当前生产接口以代码为准：

```python
class ArtifactStore(Protocol):
    @property
    def backend_name(self) -> str: ...
    def put(self, storage_key: str, data: bytes) -> StoredBytes: ...
    def read(self, storage_key: str) -> bytes: ...
    def exists(self, storage_key: str) -> bool: ...
```

Store 只处理 `storage_key` 和字节，不理解 Artifact UUID、数据库或权限。Artifact ID/元数据/生命周期由 `ArtifactService + ArtifactMetadataPort` 管理。删除接口当前故意不开放，因为访问、保留和删除规则仍是 Stage 0 用户决策门禁。

### 12.2 本地目录

```text
/data/AIMA_UGC/
├─ runtime/
│  ├─ data/
│  │  ├─ raw/
│  │  ├─ reports/
│  │  ├─ exports/
│  │  ├─ snapshots/
│  │  └─ temp/
│  └─ logs/
├─ postgres/
├─ backups/
│  ├─ postgres/
│  └─ files/
├─ releases/
└─ shared/
   ├─ env/
   └─ secrets/
```

临时文件只能写 `temp/`，成功后原子移动到最终目录。失败和超时后由清理任务按年龄删除临时文件。

### 12.3 路径安全

- Storage Key 由系统生成；
- 不允许用户输入直接成为文件路径；
- 解析后路径必须仍在配置根目录下；
- 文件名不使用标题、作者、手机号等敏感文本；
- 下载通过 Artifact ID 查库，不接受任意路径；
- 校验文件大小和类型；
- 上传文件限制扩展名、MIME 和解压大小。

## 13. 保留策略

当前**不冻结具体天数**。Stage 0 仍需用户批准个人信息、Raw、报告/导出、审计等数据的访问、保留、删除与合规规则；因此 Stage 3A 只建立可表达策略的 `retention_class` 与可空 `expires_at`，不自动删除任何业务 Artifact。

后续实现自动清理前至少必须满足：

- 用户已批准各 Retention Class 的具体期限/长期保留规则；
- 有明确访问权限与下载审计；
- 清理写审计事件；
- 不删除仍被业务记录引用的 Artifact；
- 支持 Dry Run，并先输出预计数量和容量；
- 清理作为持久化 Job 执行，不在普通 HTTP 请求中执行；
- 删除/保留动作与备份写屏障、引用检查、恢复方案兼容。

临时工作文件的技术性清理可以按独立运行目录规则处理，但不得借“临时文件”名义删除 Raw、报告、导出或审计业务证据。

## 14. 备份与恢复

### 14.1 PostgreSQL

- 按阶段 0 批准的 RPO 创建常规协调 Backup Set；其中 PostgreSQL 使用 `pg_dump --format=custom`；
- 发布前额外创建同样协调的 Backup Set；
- 备份完成后执行 `pg_restore --list`；
- 定期恢复到隔离数据库并运行一致性检查；
- 备份文件不与数据库放在同一唯一磁盘；
- 备份加密和访问权限按生产 Secret 管理。

### 14.2 Raw 和 Artifact

- 使用文件系统快照、rsync 或备份软件；独立增量文件副本只用于加速，不能单独宣称为恢复点；
- 常规恢复点和发布前协调备份都进入维护模式：暂停 Scheduler，停止新 Job 认领，等待/取消运行中 Job，并拒绝所有业务写请求；只读查询可以继续；
- 所有业务写 Unit of Work、Artifact `pending/stored/linked/delete` 生命周期、文件 rename/delete、维护对账和 Migration 在开始前都必须用专用数据库会话取得同一个固定键的**共享 session-level advisory lock**，取得后再读取维护 epoch；若已维护则释放并拒绝，否则持有到文件操作及最终数据库提交都结束。连接返回池前必须显式释放，异常连接直接丢弃；进程死亡由 PostgreSQL 会话关闭释放；
- 备份方启用维护 epoch 后取得同一键的**独占 `pg_advisory_lock`**。独占锁只有在此前所有共享持有者退出后才能成功，并阻止后来写者越过屏障；取得后再次确认 Scheduler/认领已停、运行 Job 为零、维护 epoch 未变，才记录协调截止点。锁键、获取顺序和超时由 Platform 单点实现，禁止每个模块自造；
- 从独占写屏障取得并建立协调截止点开始，持续持锁并冻结所有会创建/修改 Artifact 引用或文件的写入，直到 `pg_dump` 和文件快照都完成；任一捕获失败则整个 Backup Set 失败，不恢复调度；
- 记录统一的 Backup Set ID、数据库事务截止点和 Artifact 截止时间；数据库备份与文件快照必须属于同一协调检查点，不能只写相同名称；
- 恢复后校验 Artifact 表中的 SHA-256；
- 恢复后运行缺文件、孤儿文件、`pending/stored/linked` 状态对账；
- Raw 恢复不要求重写业务库，但所有截止点之前的已引用 Artifact 必须可打开。

该屏障是 Backup Set 一致性的必要协议，不是普通“页面进入维护模式”。测试必须让 API 写事务、Artifact rename、关联事务和删除分别停在屏障前后，证明独占锁等待所有在途共享写者排空，且截止点之后没有文件/引用变化。若目标存储不允许持有数据库会话覆盖文件操作，必须先设计并验证等价的写入登记表/epoch 协议，不能省略排空屏障。

### 14.3 恢复目标

阶段 0 必须批准 RPO、RTO、允许的数据损失窗口和磁盘预算。没有这些值时可以实现备份机制，但不能宣称生产恢复方案已验收。每个被标记为可恢复的常规/发布 Backup Set 都必须包含数据库与 Artifact 的同一协调截止点；若停写频率不满足 RPO，必须另行选定并实测一致性快照协议。每次 Release 必须在 Manifest 中记录采用的目标、实际恢复演练耗时和未满足项。

### 14.4 恢复验收

至少证明：

```text
新空目录
→ 恢复 PostgreSQL
→ 恢复文件
→ 启动目标 Release
→ 健康检查
→ 随机抽查内容、评论、Raw 和报告
→ 执行一个测试 Job
```

未做恢复演练的备份不能称为“已验证备份”。

## 15. 旧系统数据迁移

新系统 Schema 稳定后再开发一次性 Importer：

```text
旧库/旧文件
→ 只读导出
→ 映射到新 Canonical
→ 校验
→ 新系统 Ingestion
→ 对账报告
```

禁止让新业务代码长期兼容旧表。Importer 必须可重复运行、幂等、输出失败记录，不修改旧系统。
