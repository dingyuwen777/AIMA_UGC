# 数据库与文件存储

## 1. 结论

业务事实使用 PostgreSQL 18。Raw 原始响应、报告、导出和截图等大文件默认保存在宿主机文件系统，并通过 `ArtifactStore` 接口隔离；数据库保存文件元数据和关联关系。

```text
PostgreSQL
→ 身份、配置、状态、当前业务数据、历史、索引、关联、审计

文件系统
→ Provider Raw、报告、导出、截图、附件

日志目录
→ 独立的运行 `.log` 文件
```

禁止把所有东西都塞进数据库 JSON，也禁止只靠文件目录维持任务状态和业务当前值。Stage 7 的采集业务策略、Capability 与五平台 Operation Matrix 见 [08-采集策略与平台能力.md](08-采集策略与平台能力.md)；本文负责把其中需要强约束/持久化的配置、评论覆盖和预算语义落到数据库目标。

## 2. 为什么选择 PostgreSQL

一个数据库即可满足：

- 强事务；
- 唯一约束和幂等；
- 内容、评论和关键词关系；
- `jsonb` 灵活元数据；
- 时间序列历史；
- `FOR UPDATE SKIP LOCKED` Job 认领；
- GIN 和全文检索；
- Alembic Migration；
- 成熟备份恢复。

第一版不支持 MySQL、SQLite 或 MongoDB。测试需要真实数据库行为时使用隔离 PostgreSQL，不能用 SQLite 代替后宣称 PostgreSQL 已验证。

## 3. 数据类型规则

| 含义 | PostgreSQL 类型 | 规则 |
| --- | --- | --- |
| 内部主键 | `uuid` 或 `bigint` | 对外 ID 使用字符串序列化 |
| 平台外部 ID | `text` | 不转整数，避免溢出和前导零丢失 |
| 时间 | `timestamptz` | 数据库存 UTC |
| 日期 | `date` | 只在确实没有时刻含义时使用 |
| 布尔 | `boolean` | 禁止用 `0/1` 文本表达 |
| 计数 | `bigint` | 平台计数可能超过 32 位 |
| 金额/费用 | `numeric` | 禁止浮点累计费用 |
| 结构化扩展数据 | `jsonb` | 只保存灵活元数据，不替代稳定列/关系 |
| 枚举状态 | `text + check` | 枚举变化较频繁时不使用 PostgreSQL ENUM |
| 校验和 | `text` | 小写十六进制 SHA-256 |
| IP | `inet` | 审计需要时使用 |
| 网络地址 | `text` | 业务 URL 保持原文和规范化 URL |

应用和 API 时间使用 ISO-8601；日志是例外，按人工排障格式显示北京时间。

`platform='all'` 可以表达全平台词，但创建 Run 时必须展开成明确平台列表。

### 5.4 `collection_plans`

Plan 只保存跨平台/调度级稳定事实；各平台 Provider 和 Search/Detail/Comment 策略放在 `collection_plan_platforms`，避免一个全局 `detail_policy/comment_policy` 无法表达五个平台不同 Capability。

```text
id                  uuid primary key
name                text unique not null
enabled             boolean not null
schedule_expr       text
timezone            text not null
schedule_version    integer not null default 1
next_run_at         timestamptz
last_scheduled_at   timestamptz
misfire_policy      text not null
max_catch_up_runs   integer not null
request_budget      integer not null
created_by          uuid
created_at          timestamptz not null
updated_at          timestamptz not null
```

Plan 平台和词包使用关联表，不使用逗号字符串或一大块不可约束平台 JSON 代替主关系。

修改影响调度语义的字段时必须递增 `schedule_version` 并重新计算 `next_run_at`。第一版 Plan 的 IANA `timezone` 必须为 `Asia/Shanghai`，与业务日和默认调度一致，再以 UTC `timestamptz` 保存。Scheduler 的 `misfire_policy/max_catch_up_runs` 尚未批准，因此 Stage 7 可以建立数据结构/验证，但在批准前不能启用自动 Scheduler。

### 5.4A `collection_plan_platforms`

每个 Plan × Platform 一行，稳定关系字段用列，平台策略用**版本化 Pydantic Contract 序列化的 JSONB**保存。JSONB 只承载有 Schema 的可替换业务策略，不保存 cursor/search_id/API Key 等运行技术状态或 Secret。

目标语义：

```text
plan_id                 uuid not null references collection_plans
platform                text not null
provider_config_id      uuid not null references provider_configs
enabled                 boolean not null
policy_version          text not null
search_policy           jsonb not null
detail_policy           jsonb not null
comment_policy          jsonb not null
budget_policy           jsonb not null
created_at              timestamptz not null
updated_at              timestamptz not null

primary key(plan_id, platform)
```

规则：

- `search_policy` 只存 Capability 已批准的规范化业务语义，例如 `sort=latest`、`published_within=1d`；
- `comment_policy` 第一版可表达 `new_or_comment_changed`、adaptive、50/50/5、排序和 Deep 默认等 08 语义；
- Provider 私有 cursor/page/search_id/backtrace/pageArea/max_id/Secret 不进 Plan Policy；
- 保存时 Pydantic + Capability 校验，不支持值返回业务校验错误；时间窗口短于调度周期只产生 Warning；
- 创建 Run 时把解析后的 Provider/平台 Policy 全量冻结进 `config_snapshot`，以后 Plan 修改不改变历史 Run。

### 5.5 `collection_schedule_occurrences`

一条 Occurrence 表示某个计划版本在一个逻辑调度时刻只允许触发一次：

```text
id                  uuid primary key
plan_id             uuid not null references collection_plans
schedule_version    integer not null
scheduled_for       timestamptz not null
job_id              uuid unique references jobs
status              text not null
skip_reason         text
created_at          timestamptz not null

unique(plan_id, schedule_version, scheduled_for)
check(status in ('enqueued', 'skipped'))
check(
  (status = 'enqueued' and job_id is not null and skip_reason is null)
  or (status = 'skipped' and job_id is null and skip_reason is not null)
)
```

Occurrence 表只保存可提交终态：`enqueued` 必须有关联 Job/Run，`skipped` 必须有跳过原因且没有 Job/Run。Scheduler 在事务内预生成 Run/Job UUID：若入队，先插入 Job，再插入 `enqueued` Occurrence，最后插入引用它们的 Run；若按批准的 misfire 策略跳过，只插入 `skipped` Occurrence。事务提交前，Deferred Constraint Trigger 必须验证每个 `enqueued` Occurrence 恰有一个反向 Run、该 Run 与 Occurrence 的 `job_id` 相同，而 `skipped` 没有 Run。正式关联是 `collection_runs.occurrence_id → occurrence.id`（唯一）、`occurrence.job_id → jobs.id`（唯一）和 `collection_runs.job_id → jobs.id`（唯一）。Occurrence、Run、Job 与 Plan `last_scheduled_at/next_run_at` 推进必须在同一短事务中完成。

### 5.6 `collection_runs`

```text
id                  uuid primary key
job_id              uuid unique not null references jobs
manual_plan_id      uuid references collection_plans
occurrence_id       uuid unique references collection_schedule_occurrences
trigger_type        text not null
config_snapshot     jsonb not null
status              text not null
started_at          timestamptz
finished_at         timestamptz
requested_count     integer not null default 0
succeeded_count     integer not null default 0
failed_count        integer not null default 0
content_count       integer not null default 0
comment_count       integer not null default 0
error_summary       text
created_at          timestamptz not null

check(
  (trigger_type = 'scheduled' and occurrence_id is not null and manual_plan_id is null)
  or (trigger_type in ('manual', 'api', 'backfill') and occurrence_id is null)
)
```

每个 Run 由一个 Job 驱动，`collection_runs.job_id` 是数据库可约束的业务绑定；Job Handler 通过该反向关系取得 Run，不依赖 Payload 中一个无法加外键的 Run ID。自动调度 Run 只通过 Occurrence 取得 Plan、Schedule Version 和 Scheduled For，不在 Run 重复三份调度事实。人工/API/回补 Run 没有 Occurrence；需要基于一个 Plan 时可写 `manual_plan_id`，临时配置则仅保存 `config_snapshot`。Deferred Constraint Trigger 还必须验证 scheduled Run 的 `job_id = occurrence.job_id`。

Run 的费用不能用一个无币种 `numeric` 跨币种相加，按币种保存汇总：

```text
collection_run_cost_totals
  run_id              uuid not null references collection_runs
  currency            text not null
  estimated_cost      numeric(18,6) not null default 0
  settled_cost        numeric(18,6) not null default 0
  unknown_cost        numeric(18,6) not null default 0
  updated_at          timestamptz not null

  primary key(run_id, currency)
```

请求次数与货币成本是不同维度，不写入此表混加；请求计数来自 Attempt/Run 计数和 `request_count` 预算账户。

状态：`queued/running/partial_success/succeeded/failed/cancelled`。


### 5.9 `provider_request_attempts`

`provider_request_attempts` 保存每一次真实 Provider 执行。失败重试不能覆盖上一轮执行状态、费用或 Raw。

```text
id                  uuid primary key
provider_request_id uuid not null references provider_requests
attempt_no          integer not null
dispatch_status     text not null
dispatch_started_at timestamptz
completed_at        timestamptz
http_status         integer
external_request_id text
raw_artifact_id     uuid references artifacts
estimated_cost      numeric(18,6) not null default 0
actual_cost         numeric(18,6) not null default 0
cost_currency       text
cost_unit           text
unit_price_snapshot numeric(18,6)
billing_status      text not null
potential_duplicate_charge boolean not null default false
error_code          text
error_detail        text
created_at          timestamptz not null

unique(provider_request_id, attempt_no)
unique(id, provider_request_id)
```

`dispatch_status` 继续限定 `reserved/dispatching/completed/not_sent/unknown`；`billing_status` 至少区分 `not_billable/estimated/confirmed/unknown`。预算预留后，Dispatcher 以 Job Fencing + CAS 保护发送；Transport 禁止在一次 Attempt 内隐藏重试；任何真正网络重发先建新 Attempt。恢复优先找确定性 Raw，缺失/损坏时保守 `unknown`，不复发同一 Attempt。

### 5.10 `collection_candidates` 与 `collection_candidate_ingestions`

`collection_candidates` 是不可变的逐项发现账本，不是最终内容副本：

```text
id                          uuid primary key
provider_request_attempt_id uuid not null references provider_request_attempts
item_kind                   text not null
external_item_id            text
item_locator                text not null
discovered_at               timestamptz not null
created_at                  timestamptz not null

unique(provider_request_attempt_id, item_locator)
check(item_kind in ('content', 'comment'))
```

Run、Scope、Raw、平台和来源通过 Candidate→Attempt→Request→Scope→Run 和 Raw Artifact 唯一链推导。Candidate/Ingestion 只追加，纠错追加新 Ingestion 记录。`item_locator` 必须是同一 Raw 内稳定来源项键，不能用易变数组下标作为唯一事实。

`collection_candidate_ingestions` 至少保存 Candidate、ingestion_no、canonical_version/identity、observed_fields、目标 Content/Comment、结果/错误和 processed_at，并用互斥外键/Trigger 保证 item_kind、target_type 和目标平台一致。

#### 当前 Stage 6 `comment_coverage_observations` 机器事实

当前 main 的 Stage 6 表已经有：

```text
content_id
provider_attempt_id
raw_artifact_id
coverage
reported_total
collected_count
observed_at
```

其中 `coverage` 只允许 `complete/partial/not_requested/unavailable`。这些当前列以实际 SQLAlchemy/Migration 为准，不改写历史 Revision。

#### Stage 7 评论抽样解释目标

为避免“最新评论 50 / 平台 1278”被误解为全量，Stage 7 必须通过**新增 Migration**扩展等价可查询事实（具体列名由实现时 Pydantic/DDL 冻结），至少能表达：

```text
sample_mode
sort_mode
target_count
collected_count
provider_reported_count
stop_reason
observed_at
```

建议 `stop_reason` 稳定语义来自 08：`provider_exhausted/provider_reported_zero/comments_disabled/known_comment_reached/policy_limit/budget_limit/page_limit/time_boundary/provider_error/cancelled`。

新增字段不替代 `coverage`；它们解释为什么是 complete/partial/not_requested/unavailable，以及使用了什么抽样策略。

### 5.15A Ingestion、稀疏更新和读取中间层

Mapper 不能写数据库。写入固定经过：

```text
CanonicalContentV1 / CanonicalCommentV1
→ ContentIngestionService
→ Content Owner Repository
→ PostgreSQL
```

Ingestion 依据 `observed_fields` 合并：只更新本次明确观察字段；未观察字段保留数据库已有值；明确 `null` 只有在字段/Operation 语义允许时才清空。Candidate Ingestion 账本应保留 Canonical 版本、身份和本次 `observed_fields`，便于审计稀疏合并。

数据库读取固定经过：

```text
PostgreSQL
→ Query Repository / Read Model
→ Query/Application Service
→ API / AI / Reporting
```

`CanonicalContentAggregateV1` 在读取时组装内容、评论线程、coverage、system 和 lineage；数据库不把整棵帖子+评论树作为单行巨大 JSON 保存。

### 5.17 Provider 预算账户与预留账本

Stage 7 最终预算必须同时解决：

1. 多 Worker 并发不能超预算；
2. 评论不能耗尽整个 Run 的发现预算；
3. 单个热门内容不能耗尽 Run 评论预算；
4. TikHub 和未来 Provider B 的账户/额度不能混在一个 global 账户。

目标模型：

```text
provider_budget_accounts
  id                  uuid primary key
  provider_config_id  uuid not null references provider_configs
  scope_type          text not null
  scope_key           text not null
  run_id              uuid references collection_runs
  content_id          uuid references contents
  period_start        timestamptz not null
  period_end          timestamptz not null
  dimension           text not null
  unit                text not null
  limit_amount        numeric(18,6) not null
  reserved_amount     numeric(18,6) not null default 0
  settled_amount      numeric(18,6) not null default 0
  unknown_amount      numeric(18,6) not null default 0

  check(period_end > period_start)
  check(dimension in ('request_count', 'monetary_cost'))
  check((dimension = 'request_count' and unit = 'request')
        or (dimension = 'monetary_cost' and char_length(unit) = 3))
  check(limit_amount >= 0 and reserved_amount >= 0
        and settled_amount >= 0 and unknown_amount >= 0)
  check(
    (scope_type = 'global' and run_id is null and content_id is null)
    or (scope_type in ('run','run_comments') and run_id is not null and content_id is null)
    or (scope_type = 'content_comments' and content_id is not null and run_id is null)
  )

  unique nulls not distinct(
    provider_config_id, scope_type, run_id, content_id,
    period_start, dimension, unit
  )

  exclude using gist (
    provider_config_id with =,
    scope_key with =,
    dimension with =,
    unit with =,
    tstzrange(period_start, period_end, '[)') with &&
  )

provider_budget_reservations
  id                          uuid primary key
  budget_account_id           uuid not null references provider_budget_accounts
  provider_request_id         uuid not null references provider_requests
  provider_request_attempt_id uuid not null references provider_request_attempts
  reserved_amount             numeric(18,6) not null
  settled_amount              numeric(18,6)
  status                      text not null
  created_at                  timestamptz not null
  updated_at                  timestamptz not null

  unique(budget_account_id, provider_request_attempt_id)
  foreign key(provider_request_attempt_id, provider_request_id)
    references provider_request_attempts(id, provider_request_id)
  check(status in ('reserved', 'settled', 'released', 'unknown'))
```

`scope_key` 生成规则至少：

```text
global              → global
run                 → run:<run_uuid>
run_comments        → run-comments:<run_uuid>
content_comments    → content:<content_uuid>
```

实际唯一/排斥作用域还包含 `provider_config_id`，因此同一 Run 若以后显式使用多个 Provider 配置也不会把账户错误合并。

#### 预留规则

每次准备真实 HTTP 调用时，先创建独立 Attempt，再按稳定 ID 顺序锁定该 Attempt 所需账户：

```text
所有 Operation
→ provider_config 对应 global + run

一级/二级评论 Operation
→ provider_config 对应 global + run + run_comments + content_comments
```

任何必需账户不存在、Provider 身份不匹配或调用时刻没有覆盖周期都关闭失败。在同一事务检查：

```text
settled + reserved + unknown + 本次预留 <= limit
```

任一层不足则全部不预留、不发请求。新的网络重试必须新建 Attempt + 新预留，因为可能再次计费；只有同一 Attempt 的预留事务重放通过 `(budget_account_id, provider_request_attempt_id)` 唯一键复用原预留。

Attempt 完成后同事务结算/释放；`dispatching` 后结果未知则转 `unknown_amount` 并继续占预算；只有确定 `not_sent` 才释放。Provider 最终实际费用高于预留时必须如实结算为超限、告警并阻止后续调用，不能拒绝记录已经发生的真实费用。

`btree_gist` 扩展和 UUID/text equality operator class 必须由 Stage 7 Migration 显式启用/验证，所有并发、缺账户、Provider 隔离、Run 评论隔离、unknown 费用场景都用 PostgreSQL 18 集成测试证明。

## 6. `jsonb` 使用边界

适合：

- Run 配置快照；
- **有版本化 Pydantic Schema 的 Plan 平台策略**；
- 分页状态；
- Provider 脱敏请求参数；
- 不常查询的扩展元数据；
- Job Payload/Result；
- 报告参数。

不适合：

- 平台/Provider 主关系；
- 外部内容 ID；
- 关键词关系；
- 状态；
- 时间；
- 点赞、评论等常用指标；
- 需要唯一约束或索引的核心字段；
- Secret。

原则：稳定且需要查询、约束、关联的字段用列；结构复杂但有机器 Contract、低频查询的配置可以用 JSONB；来源私有/低频扩展数据也可用 JSONB。

## 7. 索引基线

必须按真实查询设计，不按“每列都加索引”。核心索引至少覆盖 Content/Comment 当前与历史、Run/Scope、Provider Request/Attempt、Job、Budget Reservation。Stage 7 新表实际查询建立后再用 `EXPLAIN` 冻结额外索引，不为所有 JSONB 属性预建 GIN。

中文检索方案必须在阶段 0 用真实脱敏中文语料和明确查询集做召回质量、延迟与 `EXPLAIN` 基准；未测量前不预先承诺 `tsvector` 中文效果。

## 8. 事务边界

### 8.1 一次内容摄取

同一事务内：

- Upsert 当前内容；
- 写 Content Version；
- 写 Metric Observation；
- 写 Discovery；
- 写 Candidate Ingestion 结果；
- 更新 Run/Scope 计数；
- 如需触发 Analysis/Monitoring，把版本化 Job 与上述业务写入放在同一 PostgreSQL 事务中。

Raw 文件写入不放在数据库事务中，按 `pending → stored → linked` 生命周期衔接；业务提交与下游 Job 入队使用同一 Unit of Work。

### 8.2 外部调用不能放在数据库事务中

禁止：

```text
BEGIN
→ 调 TikHub 等待 30 秒
→ 写库
→ COMMIT
```

正确：

```text
短事务创建 reserved Attempt 并原子取得全部必需预算
→ CAS reserved → dispatching
→ 调用 Provider（同一 Attempt 最多一次）
→ Raw 落盘
→ 短事务把 Attempt/预算记为 completed/settled，或 not_sent/released、unknown/unknown_amount
→ Mapper
→ 业务短数据库事务
```

恢复时看到遗留 `dispatching` 必须先检查确定性 Raw，再按已建立规则恢复/unknown；不得复发同一 Attempt。

### 8.3 幂等

每个可重试操作必须有明确幂等键：

- HTTP 创建请求：`actor + operation + Idempotency-Key + request_hash + 有效期`；
- 内部 Job：`job_type + internal_idempotency_key`；
- Provider Request：Scope + Request Fingerprint；
- Provider Attempt：逻辑 Request + Attempt Number；
- Content：平台 + 外部内容 ID；
- Comment：平台 + 内容 + 外部评论 ID；
- Version：只将 Business Hash 与当前版本比较；历史相同 Hash 可以再次出现；
- Observation：内容 + Request + Observation Hash；
- Report：报告参数 Hash + 数据截止时间。

## 10. Migration

所有 Schema 演进使用根目录 `alembic.ini` + `migrations/`。

规则：

1. 已发布 Revision 禁止改写；后续变化新增 Revision；
2. API/Worker/Scheduler 启动不自动运行 Migration；Migration 是独立进程/命令；
3. Table 定义是运行时 Schema/Repository 的机器结构，Revision 显式冻结已批准变化；CI 使用 `alembic check` 防漂移；
4. 涉及 Stage 7 Plan、Provider Config、评论 coverage 解释字段、Budget Ledger 的变化必须从当前 `20260814_0009` 之后新增 Revision，不改写 Stage 6；
5. 必须验证 `base → head`、上一正式 Revision → head、downgrade/re-upgrade 和 `alembic check`；
6. downgrade 是开发/CI 可逆性证据，不替代生产 Backup Set；
7. 新增表必须声明唯一 Owner 并有 PostgreSQL Integration。

## 12. 文件存储

### 12.1 接口

当前生产接口以代码为准：

```python
class ArtifactStore(Protocol):
    @property
    def backend_name(self) -> str: ...
    def put(self, storage_key: str, data: bytes) -> StoredBytes: ...
    def read(self, storage_key: str) -> bytes: ...
    def exists(self, storage_key: str) -> bool: ...
```

Store 只处理 `storage_key` 和字节，不理解 Artifact UUID、数据库或权限。Artifact ID/元数据/生命周期由 `ArtifactService + ArtifactMetadataPort` 管理。删除接口当前故意不开放，因为访问、保留和删除规则仍是 Stage 0 用户决策门禁。

### 12.2 本地目录

```text
/data/AIMA_UGC/
├─ runtime/
│  ├─ data/
│  │  ├─ raw/
│  │  ├─ reports/
│  │  ├─ exports/
│  │  ├─ snapshots/
│  │  └─ temp/
│  └─ logs/
├─ postgres/
├─ backups/
│  ├─ postgres/
│  └─ files/

```

临时文件只能写 `temp/`，成功后原子移动到最终目录。失败和超时后由清理任务按年龄删除临时文件。

### 12.3 路径安全

- Storage Key 由系统生成；
- 不允许用户输入直接成为文件路径；
- 解析后路径必须仍在配置根目录下；
- 文件名不使用标题、作者、手机号等敏感文本；
- 下载通过 Artifact ID 查库，不接受任意路径；
- 校验文件大小和类型；
- 上传文件限制扩展名、MIME 和解压大小。

## 13. 保留策略

当前**不冻结具体天数**。Stage 0 仍需用户批准个人信息、Raw、报告/导出、审计等数据的访问、保留、删除与合规规则；因此只保留可表达策略的 `retention_class` 与可空 `expires_at`，不自动删除业务 Artifact。

后续实现自动清理前至少必须满足：

- 已批准各 Retention Class 的具体期限/长期保留规则；
- 有明确访问权限与下载审计；
- 清理写审计事件；
- 不删除仍被业务记录引用的 Artifact；
- 支持 Dry Run；
- 清理作为持久化 Job 执行；
- 与备份写屏障、引用检查、恢复方案兼容。

## 14. 备份与恢复

### 14.1 PostgreSQL

- 按批准 RPO 创建常规协调 Backup Set；PostgreSQL 使用 `pg_dump --format=custom`；
- 发布前额外创建协调 Backup Set；
- 备份后执行 `pg_restore --list`；
- 定期恢复到隔离数据库并运行一致性检查；
- 备份文件不与数据库放在同一唯一磁盘；
- 备份加密和访问权限按生产 Secret 管理。

### 14.2 Raw 和 Artifact

- 独立增量文件副本只用于加速，不能单独宣称为恢复点；
- 常规恢复点和发布前协调备份进入维护模式：暂停 Scheduler、停止新 Job 认领、等待/取消运行中 Job，并拒绝业务写；
- 所有业务写 Unit of Work、Artifact 生命周期、文件 rename/delete、维护对账和 Migration 在开始前都必须用专用数据库会话取得同一固定键的共享 session-level advisory lock，取得后复核维护 epoch；
- 备份方启用维护 epoch 后取得同一键独占 `pg_advisory_lock`，等待在途共享写者退出，并持有到数据库与文件捕获均完成；
- 任一捕获失败则整个 Backup Set 失败；
- 记录统一 Backup Set ID、数据库事务截止点和 Artifact 截止时间；
- 恢复后校验 SHA-256，并对账缺文件/孤儿文件/lifecycle 状态。

### 14.3 恢复目标

阶段 0 必须批准 RPO、RTO、允许的数据损失窗口和磁盘预算。没有这些值时可以实现备份机制，但不能宣称生产恢复方案已验收。

### 14.4 恢复验收

至少证明：

```text
新空目录
→ 恢复 PostgreSQL
→ 恢复文件
→ 启动目标 Release
→ 健康检查
→ 随机抽查内容、评论、Raw 和报告
→ 执行一个测试 Job
```

未做恢复演练的备份不能称为“已验证备份”。

## 15. 旧系统数据迁移

新系统 Schema 稳定后再开发一次性 Importer：

```text
旧库/旧文件
→ 只读导出
→ 映射到新 Canonical
→ 校验
→ 新系统 Ingestion
→ 对账报告
```

禁止让新业务代码长期兼容旧表。Importer 必须可重复运行、幂等、输出失败记录，不修改旧系统。
