## 1. 采集系统必须能回答哪些实际问题

对于任意一条最终 Content，系统应该能够回答：

```text
为什么发起这次采集/导入？
来自 TikHub 还是 Excel？
如果来自 Collection，是哪个 Run / Scope？
真正发了哪个 Provider Operation？
发了几次？
哪次 Attempt 返回了什么 Raw？
Raw 里哪一个 item 产生了这条 Canonical？
Mapper 用了哪个真实字段？
为什么继续/没有继续抓 Detail 或 Comments？
为什么数据库没有产生第二条重复 Content？
正文为什么变成当前版本？
点赞为什么产生了这一个 Metric Observation？
发生失败后从哪里恢复？
Provider 调用产生了什么费用事实？
```

如果这些只能靠翻日志猜，数据链就是不可靠的。

## 2. 当前两类数据入口

长期架构只区分“外部来源如何提供证据”，不要求所有入口长得一样。

### 2.1 Collection / TikHub 外部发现链

```text
Plan / API Run
→ Collection Run
→ Scope
→ Provider Request
→ Provider Attempt
→ Raw Artifact
→ Candidate
→ Operation Extractor / Mapper
→ Canonical
→ Relevance / Decision
→ ContentIngestionService
→ Content Owner
→ PostgreSQL
```

### 2.2 File Import 链

兼容的旧单文件上传：

```text
Excel Input Artifact
→ Processing Import Batch
→ import-parent Provider Request
→ non-billable Attempt
→ Excel Reader / Mapper
→ Canonical
→ Rule Relevance
→ Batch Dedup
→ ContentIngestionService
→ Content Owner
→ PostgreSQL
```

当前页面的统一数据导入仍属于 File Import。来源只决定怎样形成 Source Artifact，写入策略独立决定 Canonical 之后的语义：

```text
本地浏览器多选文件/文件夹 → 冻结清单并逐 Item 流式上传
批准根目录内相对路径 → Worker 安全枚举并快照
→ Data Import Campaign（source_kind + ingestion_policy）
→ 原文件 Artifact + SHA-256
→ 流式 Reader / Mapper
→ 有界 Chunk Artifact
→ Canonical-compatible Import Row
→ Rule Relevance / 稳定首行去重
→ Content Owner Standard Observation 或 Historical Fill-Only
→ PostgreSQL + 逐行终态/冲突账本
```

File Import 不伪造：

```text
Collection Run
Collection Scope
Collection Candidate
```

因为这些业务事实实际上没有发生。

这些入口真正汇合在 Content Owner 维护的 Content 身份和业务表；统一 Campaign 按冻结策略选择现有逐批摄取 Service 或同一 Owner 暴露的集合式 Fill-Only 写入口：

```text
standard_observation → CanonicalContentV1 → ContentIngestionService
historical_fill_only → Canonical-compatible Chunk → Content Owner Historical Fill-Only
Collection / File Import → 同一 Content 身份、Current、Version 和来源关系
```

旧 `/api/v1/import-batches` 仍保留合法行为，但当前页面不再维护第二个入口。4000 万容量门禁只适用于服务器来源的 `historical_fill_only` 集合式链路；标准观测路径不具有该规模承诺。

## 3. 为什么先保存 Raw / Input Artifact

外部数据会变，Mapper 也可能写错。

如果直接：

```text
TikHub JSON
→ Mapper
→ PostgreSQL
```

Mapper 后来发现字段取错时，无法回答 Provider 当时真实返回什么，只能重新付费请求。

所以 Collection：

```text
Provider Response
→ 先持久化不可变 Raw Artifact
→ 再 Extract / Candidate / Mapper
```

File Import：

```text
原始 XLSX
→ 先存 Input Artifact
→ 再 Reader / Mapper
```

服务器来源会先把每个源文件复制为不可变 Source Artifact；本地来源先冻结浏览器相对路径和大小清单，再逐 Item 流式上传。两者都校验 SHA-256，并在流式解析前把 Artifact 绑定到 Campaign source_file Item；绑定和 Artifact `linked` 状态同事务提交。重复本地 PUT 还必须与冻结文件名、大小和 SHA-256 一致。同一快照 Job 的技术重试复用已绑定 Artifact，再从中产生有界 Chunk Artifact。Campaign 全部预检成功后，业务导入只读 Chunk Artifact，不再读取服务器原目录或浏览器文件。未引用的 Source/Chunk Artifact 进入现有 1 天孤儿清理，已被 Campaign Item 引用的快照不进入该规则。

Artifact 身份/元数据由：

```text
backend/src/aima_ugc/platform/storage/
backend/src/aima_ugc/adapters/persistence/postgres/artifact_metadata.py
```

管理。

真正字节存储由 ArtifactStore 负责；ArtifactStore 不反向写业务数据库。

## 4. Plan、Run、Scope 分别是什么

### 4.1 Plan：长期配置

Plan 表示：

> 以后按照什么节奏、哪些平台、哪些关键词包、哪个 Provider Config 去采。

当前领域代码：

```text
backend/src/aima_ugc/modules/collection/planning.py
```

当前表：

```text
collection_plans
collection_plan_platforms
collection_plan_keyword_packs
```

Plan 不应该保存：

- 当前页 cursor；
- `search_id`；
- API Key；
- 运行时最终展开的全部关键词；
- 某次 Provider Response。

### 4.2 Run：一次具体执行

Run 表示：

> 这一次任务实际要做什么。

当前代码：

```text
modules/collection/execution.py
modules/collection/run_snapshot.py
```

创建 Run 时冻结本次执行所需的非 Secret 事实，例如：

- Provider Config identity；
- 平台；
- 关键词；
- Decision Policy；
- Relevance Snapshot；
- 技术执行上限。

后续管理员修改 Plan，不应改变已经创建的 Run。

### 4.3 Scope：最小独立执行单元

Scope 典型形状：

```text
xiaohongshu + keyword_search + 爱玛
weibo + keyword_search + 爱玛电动车
bilibili + content_discovery + 某批补采目标
```

一个 Run 可以有多个 Scope；一个 Scope 失败不应该抹掉其他 Scope 的执行事实。

领域/执行代码：

```text
modules/collection/execution.py
bootstrap/collection_scope.py
```

## 5. Provider Request 和 Attempt 为什么不能合成一张“请求表”

### 5.1 Provider Request

代表逻辑请求：

```text
在这个来源父级下，按这组业务参数完成一次 operation
```

例如：

```text
xiaohongshu search_notes keyword=爱玛 page=1
```

Request 使用稳定 `request_fingerprint` 做逻辑幂等。

### 5.2 Provider Attempt

代表一次真实执行尝试：

```text
Request A
├─ Attempt 1
└─ Attempt 2（如果明确需要重试）
```

硬规则：

```text
一个 Attempt 最多一次真实 Provider HTTP 发送
```

为什么：

- 能准确统计到底发了几次；
- 每次 HTTP 状态/外部 request ID/Raw 分开保存；
- 网络结果未知时保留 `potential_duplicate_charge`；
- 不让 Transport 的隐藏重试破坏费用审计。

当前代码：

```text
modules/collection/provider_persistence.py
modules/collection/provider_dispatch.py
modules/collection/provider_recovery.py
adapters/persistence/postgres/collection_provider_execution.py
```

## 6. File Import 的 Request/Attempt 如何复用来源账本

File Import 没有真实 HTTP，但依然要留下：

> 哪一次 Input Artifact 处理产生了这条 Content？

当前合法父级恰好一个：

```text
Collection Request
→ scope_id != null
→ import_batch_id = null

File Import Request
→ scope_id = null
→ import_batch_id != null
```

约束注册：

```text

```

File Import Attempt 使用：

```text
billing_status = not_billable
raw_artifact_id = 输入 Excel Artifact
```

它保留统一来源链，但不会伪造网络调用。

详细实现见：

## 7. Candidate 为什么要在 Mapper 前建立

Candidate 解决：

> Provider Raw 明明看到了一个 item，为什么最后数据库没有 Content？

如果只有：

```text
Raw
→ Mapper
→ Content
```

Mapper 解析失败、ID 缺失、Contract 不合法或后续过滤时，来源项本身可能消失在审计链中。

当前 Collection：

```text
Raw item
→ Candidate（Mapper 前建立）
→ Mapper
→ Canonical
→ Relevance / Decision
→ Ingestion
→ Candidate Ingestion ledger
```

Candidate 当前只保存必要来源身份，不复制 Content Current。

表：

```text
collection_candidates
collection_candidate_ingestions
```

代码：

```text
modules/collection/candidates.py
modules/collection/candidate_tables.py
adapters/persistence/postgres/candidates.py
```

File Import 不创建假 Candidate；它用 Input Artifact + Batch + Request/Attempt + Canonical `source.item_locator` 保留真实来源。

## 10. Mapper 的唯一职责：翻译事实

Mapper 输入：

```text
Provider Raw Item
+ 明确来源上下文
```

输出：

```text
CanonicalContentV1
CanonicalCommentV1
```

Mapper 禁止：

- 查数据库；
- 发 HTTP；
- 写 Artifact；
- 做 AI；
- 判断告警；
- 跨来源去重；
- 猜无法确认的父评论/发布时间/作者身份。

## 12. Content 稳定身份、Provider Lookup 身份和 Comment 身份

三种身份不能混成一个概念。

Content 稳定业务身份：

```text
(platform, external_content_id)
```

它负责数据库去重和版本收敛。Excel 可以从平台标准 URL 得到原生 ID；如果只能得到来源文章编号或规范化 URL hash，仍允许作为审计 Content 稳定身份，但这不自动代表 Provider 可以拿该值补采。

Provider Lookup 身份：

```text
CanonicalContentV1.alternate_ids
→ content_external_ids(id_type, external_id)
```

当前正式可直接进入 TikHub Batch Supplement 的类型只有：

```text
xiaohongshu → note_id
douyin      → aweme_id
weibo       → status_id
bilibili    → av_id / bv_id
kuaishou    → photo_id
```

Excel 对确定性标准链接只做本地解析，不在 Import 阶段发送付费请求。抖音 `modal_id` 可直接作为 `aweme_id`；微博常见 permalink 的 Base62 BID 本地确定性转换为数字 MID/status_id；B站 AV/BV 保留类型。短链/分享链可以识别并保留，但如果还不能保证 `Detail → 原生 ID → 原 Content` 稳定收敛，就不获得普通付费补采资格，不猜 ID。

Comment 稳定身份：

```text
(content_id, external_comment_id)
```

`external_comment_id/root_comment_id/parent_comment_id` 必须来自 Provider 评论响应；Excel 不生成评论身份。一级评论由 Content lookup identity 发起，二级回复再使用一级评论响应得到的 Comment/Root ID。

所有外部 ID 一律按字符串处理，避免大整数跨语言精度丢失。标题/正文/作者名不参与身份去重；URL 是身份解析证据和来源事实，不作为跨平台内容主键。

## 13. `observed_fields` 为什么是多来源合并的核心

Search、Detail、Comments、Excel 的字段密度不同。

例如：

```text
Detail 已经观察到完整 text

之后一个 Search 卡片没有 text
```

如果 Search 直接写：

```text
text = null
```

会错误清空更完整的 Current。

因此每条 Canonical Observation 带：

```text
observed_fields
```

规则：

```text
字段在 observed_fields
→ 本次明确观察，可参与 freshness 更新

字段不在 observed_fields
→ 本次未知，不覆盖旧值
```

数据库 Current 还保存：

```text
field_observed_at
```

做字段级时间 freshness。

## 14. 互动指标为什么允许下降

平台真实数据不是单调递增：

- 用户取消点赞；
- 内容删除评论；
- 平台纠正播放量；
- Provider 返回修订值。

所以不能：

```text
current_like_count = max(old, new)
```

当前 Metric Observation 保存真实变化，包括下降。

主要指标：

```text
like_count
comment_count
share_count
repost_count
favorite_count
view_count
play_count
danmaku_count
coin_count
download_count
reply_count
```

没有观察到不是 `0`；只有 Provider 明确返回零才写 `0`。

## 18. 分页为什么必须是可测试状态机

每个平台 Operation：

```text
初始 state
→ build request
→ send
→ save Raw
→ extract items
→ next state
→ stop decision
→ next page
```

通用停止信号包括：

- Provider 明确无下一页；
- 当前页为空；
- cursor/page 没推进；
- 页面完全重复；
- 可靠已知边界命中；
- Job 取消；
- 技术安全上限。

技术页数上限是防死循环，不是“业务最多只要这些数据”。达到安全上限应体现 partial/stop reason，不能伪装 complete。

当前每个平台分页代码就在自己的 `operations/*.py` 中。

## 19. Raw Replay 和 Provider Retry 的区别

### Raw Replay

```text
已经有完整校验 Raw
→ 修 Mapper / 重新 Ingest
→ 不发 Provider HTTP
```

当前 xiaohongshu 有专门 replay 入口；更普遍的原则由 Provider Recovery 保证。

### Provider Retry

```text
没有可用 Raw
+ 失败类型允许重试
→ 创建新的 Attempt
→ 重新发送
```

网络结果 `unknown` 时还要保留潜在重复计费事实。

不要把“重跑 Job”直接理解成“再调一遍 TikHub”。

## 20. Rule Relevance 在哪里发生

Rule Relevance 是 Collection 与 File Import 共用的**确定性关键词准入能力**，发生在 Canonical 之后、Content Ingestion 之前；但两类入口当前选择关键词的方式不同。

Collection：

```text
global_relevance_config
→ 当前全局 Relevance Keyword Pack
→ effective_keywords
→ 创建 Run 时冻结 RelevanceSnapshotV1
→ Worker 按 Run Snapshot 执行
```

Excel Import：

```text
兼容旧上传在创建 Import 时、统一数据导入在创建 Campaign 时，显式选择 1—20 个 Keyword Pack
→ 读取所选 Pack 当前版本与启用关键词
→ 合并并按现有 Relevance 匹配规则归一/去重 effective_keywords
→ 兼容旧上传冻结 ImportKeywordSelectionSnapshot 到 Batch + Job
→ 统一数据导入冻结快照到 Campaign，并由 Source/Chunk Batch 继承
→ Worker 只按对应冻结 Selection 执行
```

因此 `global_relevance_config` 当前仍是 Collection 的正式全局选择事实，但 Excel Import 不读取它来决定本次筛选词包。两种入口都冻结本次实际 Pack/版本/有效关键词，后续管理员修改词包不会改变已经创建的 Run/Import。

它们都不是 AI Semantic Relevance：

```text
Rule Relevance
→ Collection / Import 入库前的确定性筛选

AI Semantic Relevance
→ Analysis Domain 的模型判断
```

两者不能共用一个字段/表含义。精确 Snapshot 结构分别以当前 Collection/Analysis Contract、`modules/ingestion/import_job.py` 和创建入口代码为准，Blueprint 不复制第二套 Schema。

AI Semantic Relevance 的 `irrelevant` 结果属于 Analysis 审计事实：Content/Version/Analysis/来源继续保留；声音广场默认列表隐藏当前 Analysis identity 下明确 irrelevant 的内容，但按 Content UUID 的详情仍可审计读取；普通 Batch Supplement 同样排除当前明确 irrelevant 的 Content，避免继续发生无业务价值的 Provider 费用。旧 Prompt/Taxonomy/Model 结果视为 stale，不永久阻断补采。

## 21. TikHub API family 为什么不自动 fallback

同一个平台 App/Web/V1/V2/V3 可能：

- 返回不同内容集合；
- 排序不同；
- pagination 不兼容；
- 字段密度不同；
- 费用不同。

当前代码允许显式 Candidate/A-B 验证，但生产 Runtime 不自动跨 family fallback。

## 22. Provider Billing 当前是什么，不是什么

Request/Attempt 会保存：

- 价格快照；
- 预计费用；
- Provider 能提供时的实际费用；
- billing status；
- potential duplicate charge。

这是：

```text
调用事实 / 对账 / 审计
```

当前不是：

```text
请求次数 Budget
金额 Budget
Reservation Ledger
发送前 Cost Guard
```

当前没有预算硬门禁。

## 23. 当前默认采集节奏如何理解

业务默认调度可采用：

```text
00:00 / 06:00 / 12:00 / 18:00
```

但这不意味着所有 Provider 都支持“最近 6 小时”过滤。

正确理解：

```text
Scheduler 6 小时触发
→ Provider 使用自己真实 Capability 支持的时间/排序
→ 搜索窗口允许重叠
→ 内容稳定 ID 去重
→ Decision 避免重复 Detail/Comment 花费
```

## 27. 验收采集链时至少证明什么

- Provider Config/Secret 不泄露；
- Operation 使用当前批准 Endpoint；
- 分页第一页/下一页/末页/重复页/不推进可测试；
- Raw 不覆盖；
- Candidate 在 Mapper 前建立；
- Mapper 只做事实翻译；
- Canonical Contract 合法；
- 外部 ID 使用字符串；
- 稀疏字段不会清空更完整 Current；
- 指标允许真实下降；
- 评论父子关系不猜；
- Content 跨关键词/跨来源最终收敛；
- 来源 Attempt/Raw/Batch/Run 证据不因为去重丢失；
- 已有完整 Raw 的恢复不重新请求 Provider；
- 网络未知结果保留费用风险；
- File Import 不伪造 Run/Scope/Candidate；
- `tikhub_test` / `imports_test` 复用生产实现；
- 当前没有 Budget Guard 或自动 API family fallback 时，文档/API 也不能宣称存在。
