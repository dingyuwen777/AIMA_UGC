# 采集策略与平台能力

这篇文档回答：**系统拿到一个采集计划后，怎样决定用哪个 Provider、执行哪些业务动作、什么时候继续抓详情/评论，以及为什么不同平台不能假装能力完全一样。**

- [`../collection/README.md`](../collection/README.md)
- [`../appendix/TikHub真实响应结构.md`](../appendix/TikHub真实响应结构.md)
- [`../appendix/TikHub接口验证与选型台账.md`](../appendix/TikHub接口验证与选型台账.md)

## 1. 先区分 Provider 和 Platform

Platform 是业务平台，例如：

```text
xhs
 douyin
 weibo
 bilibili
 kuaishou
```

Provider 是“通过谁拿数据”，例如：

```text
TikHub
官方 API
Apify
自建采集器
```

同一个 Platform 未来可以有多个 Provider，同一个 Provider 也可以服务多个 Platform。

所以 Plan 不能只保存：

```text
provider = tikhub
```

而要选择稳定 `provider_config_id`。Provider Config 保存：

- Provider 类型；
- 显示名称；
- Base URL；
- `secret_ref`；
- enabled。

Secret 值不写进数据库。

## 2. Capability 解决什么问题

五个平台都叫“搜索、详情、评论”，但真实能力不同。

例如：

- 有的平台搜索支持时间过滤，有的平台只支持较粗时间窗；
- 有的平台一级评论能直接给回复数，有的平台字段不稳定；
- 有的平台二级回复需要另一个 Operation；
- 排序和分页参数也不同。

所以系统不让 Plan 随意构造 Provider 私有参数，而是先通过 Capability/Operation Registry 判断：

```text
这个 Provider + Platform
→ 当前支持哪些业务 Operation？
→ 接受哪些业务参数？
→ 参数怎样翻译为 Provider 私有请求？
```

Capability 是能力边界，不是把完整 endpoint JSON 暴露给前端。

## 4. 一个 Collection Plan 需要表达什么

Plan 是长期配置，不是某次请求参数堆。

它表达：

- 名称和启停；
- 调度表达式；
- 目标平台；
- 每个平台的 `provider_config_id`；
- 关键词包；
- 详情/评论策略；
- 平台业务配置；
- Decision Policy。

Plan 不保存：

- API Key/Token/Cookie；
- Provider cursor/search_id/page；
- 某次执行最终关键词快照；
- Raw；
- 某个 HTTP Attempt 的状态。

这些属于 Secret、Run Snapshot、Scope/Request/Attempt 等其他层。

## 5. 为什么创建 Run 时要冻结快照

假设一个定时任务 12:00 创建，12:01 管理员修改了关键词包。

如果 Worker 13:00 才真正开始，不能再读“最新 Plan”猜这次应该按哪版配置执行。

所以 Run 创建时冻结：

```text
Plan/Provider Config 身份
平台业务配置
最终关键词
Decision Policy
Relevance 配置版本
必要的技术 Deadline 上限
```

Secret 值不冻结，只保存稳定 `secret_ref` 身份，运行时通过受控边界解析。

## 6. 发现、详情、评论为什么要分成业务动作

外部采集不是“搜索一次就结束”。典型流程：

```text
Search / Discovery
→ 看到候选内容
→ 判断是否需要 Detail
→ 用最新 Canonical 再判断 Comments
→ 必要时抓一级评论
→ 必要时抓二级回复
```

不同动作有不同成本和恢复语义，所以不能把“搜索+详情+评论全部请求”写成一个不可恢复的大函数。

## 7. Decision Pipeline 解决什么问题

搜索卡片可能已经能告诉我们：

- 这是不是旧内容；
- 指标是否变化；
- 评论数是否增加；
- 是否可能值得抓详情。

如果每次搜索都无条件再次抓详情和全部评论，会产生大量重复费用。

Decision Pipeline 根据当前 Observation、历史 Current/Coverage 和策略决定：

```text
只摄取搜索观察
继续抓 Detail
继续抓 Comments
跳过
```

它只做业务决策，不把 Provider 私有 endpoint 逻辑塞进规则。

## 8. Detail 后为什么可能重新判断评论

搜索卡片字段经常比详情少。

例如 Search 只知道“评论数大概 80”，Detail 又拿到更准确的更新时间/状态。

因此如果第一次 Decision 是：

```text
defer_until_detail
```

Detail 摄取完成后，用**最新 Canonical**重新计算评论动作，但不会为了重决策再请求一次 Detail。

## 9. 评论 Target 是停止目标，不是截断已经返回的数据

假设 `sample_target=50`，Provider 一页返回 20 条：

```text
第 1 页 20
第 2 页 20
第 3 页 20
```

到第 3 页才超过 50。

已经付费返回的第 3 页不能只保留前 10 条再丢掉后 10 条。正确顺序：

```text
先完整 Mapper/Ingestion 当前响应页
→ 再判断是否还要请求下一页
```

所以 Target 控制“下一页还抓不抓”，不是把已经获得的数据裁剪掉。

## 10. Coverage 负责表达“抓得有多完整”

一条帖子有 1000 条评论，只抓 50 条不能写成“评论已完整”。

当前会保留：

- 内容级评论 Coverage；
- root thread 二级回复 Coverage；
- fetched/reported 数量；
- complete/partial；
- stop reason。

页面/报告如果需要解释数据完整度，应消费 Coverage，而不是只看数据库里已有多少评论行。

## 11. Deep Collection 什么时候值得做

不是所有内容都值得抓很多评论。

可按业务规则对高价值内容提高深度，例如：

- 高互动；
- 负面/风险内容；
- 人工指定；
- 特定监测事件。

但是“Deep”只改变允许继续请求的深度，不改变：

- Provider Request/Attempt 账本；
- Raw-first；
- Candidate-before-Mapper；
- Canonical；
- Content Owner；
- Coverage。

## 12. Scheduler 默认业务节奏和 Provider 时间窗不是一回事

业务上可以每 6 小时调度一次，但 Provider 可能只支持“一天内”这种更粗的时间过滤。

因此：

```text
6 小时执行一次
≠ Provider 能精确过滤最近 6 小时
```

允许查询窗口重叠，再通过稳定内容身份、历史 Observation 和 Decision Pipeline 收敛重复。

不要为了避免重叠，在 Provider 不支持的情况下伪造精确时间过滤。

## 13. 当前 Scheduler 策略

第一版固定：

```text
Asia/Shanghai
latest_only
max_catch_up_runs = 0
```

停机恢复只执行最新到期 slot，更早 slot 明确保存为 skipped。

完整解释见 [`../appendix/Scheduler运行与恢复.md`](../appendix/Scheduler运行与恢复.md)。

## 14. Provider 请求恢复原则

外部请求最难处理的情况是：

```text
请求可能已经发出
→ 对方可能已经处理/计费
→ 本机在收到/持久化结果前崩溃
```

因此：

- `not_sent`：能确定没发送；
- `unknown`：发送结果不确定；
- 完整 Raw 已存在：必须优先 replay；
- 同一 Attempt 不再次发送；
- 真正重发创建新 Attempt；
- `unknown` 保留潜在重复计费事实。

这是正确性和费用审计边界，不是普通 `requests` 重试参数。

## 15. 为什么不自动切备用 API family

App/Web/V1/V2/V3 即使都能返回“搜索结果”，也可能：

- 参数不同；
- 排序不同；
- 字段不同；
- 分页不同；
- 计费不同；
- 风控稳定性不同。

所以当前不做：

```text
主接口失败 → 静默自动换另一个 family
```

备用接口先显式验证，再通过独立变更切换。详细见 [`../appendix/TikHub接口验证与选型台账.md`](../appendix/TikHub接口验证与选型台账.md)。

## 16. Provider Billing 是审计，不是预算

当前 Request/Attempt 记录：

- estimated/actual cost；
- currency/unit；
- unit price snapshot；
- billing status；
- potential duplicate charge。

它们回答：

> 这次外部执行花了多少、是否可能重复计费？

当前不回答：

> 今天最多允许花多少钱、超过金额禁止发送？

预算能力当前未实现，未来需要单独 L3 Change。

## 17. Relevance 为什么要放在统一链路

Collection 的关键词用于“发现”，不能等同于“最终业务相关性”。

当前统一：

```text
Mapper
→ Canonical
→ Global Relevance Service
→ Ingestion
```

这样 TikHub 和 Excel 使用同一规则相关性。

AI V3 后续还会做语义 relevance，解决“关键词出现但内容实际无关”。

## 18. Provider Probe 怎么用

Probe 只在当前 Fixture/代码/一手资料不足以回答问题时使用。

必须：

- 显式人工触发；
- 请求/分页有上限；
- 复用生产 Adapter/Operation；
- 不进入普通 CI；
- 不打印 Secret；
- 产出脱敏 Fixture/测试/结论。

“刚才真实请求成功一次”不是长期生产事实。

## 19. 一个最小例子

计划：

```text
平台：小红书
关键词：爱玛
每 6 小时执行
```

一次运行可能是：

```text
Scheduler 创建 Run/Job
→ Search 爱玛
→ Raw 保存
→ Candidate
→ Mapper → Canonical
→ Relevance
→ Ingestion
→ Decision 发现是新内容
→ 请求 Detail
→ 最新 Canonical 再判断评论
→ 抓评论若干页
→ 保存 Coverage
→ Run 收敛终态
```

如果下次搜索又看到同一 `external_content_id`：

```text
不会创建第二个 Content Current
→ 只根据字段/指标变化和 Decision 判断后续动作
```

## 21. 不要做的事

- Plan 保存 API Key/Token/Provider cursor；
- 前端直接配置 TikHub 私有 endpoint；
- 每次 Search 都无条件 Detail + 全量 Comments；
- 已返回的一页评论因为达到 target 就裁一半；
- 把数据库已有评论条数当完整度；
- 一个 Attempt 自动发两次；
- `unknown` 当作肯定未发送；
- 自动跨 API family fallback；
- 把 Billing 字段叫成 Budget；
- 平台私有字段穿透 Canonical 进入公共业务 API。
