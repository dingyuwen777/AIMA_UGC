## 2. Provider Config、Platform、Provider、Operation 边界

Provider 类型与可连接的 Provider 配置实例必须区分。一个 Provider 类型可以存在多个账号/实例，每个实例使用稳定 `provider_config_id` 标识；平台或 Plan 选择具体实例，再由其 Provider 类型与平台共同选择业务 Capability/Operation：

```text
Provider Config instance
  ├─ provider_config_id
  ├─ provider
  ├─ base_url
  ├─ secret_ref
  └─ enabled
        ↓
Platform / Plan selects provider_config_id
        ↓
Provider Registry
        ↓
Provider + Platform Capability
        ↓
Business Operation
        ↓
Provider-specific endpoint / pagination
        ↓
Raw → Provider + Platform Mapper → Canonical
```

当前五个平台默认 Provider 类型均为 `tikhub`：

```text
xiaohongshu → tikhub
douyin      → tikhub
weibo       → tikhub
bilibili    → tikhub
kuaishou    → tikhub
```

但这不要求五个平台共享同一个 Provider Config。实际运行可以是：

```text
TikHub 主账号  → xiaohongshu + douyin
TikHub 备用账号 → bilibili
Provider B     → weibo
```

也可以让五个平台都引用同一个 TikHub Config。Provider Config 本身不保存平台字段；平台选择关系属于 Plan/平台策略。以后单独把某个平台改为官方 API、Apify、自建采集器或其他 Provider 时，为新的 Provider 实例建立独立 Config，并为新的 `Provider + Platform` 建立 Operation、Raw Fixture、Mapper、Capability 和 Probe；Canonical/Ingestion/数据库不因 Provider 更换而重写。

Provider Config 第一版稳定边界：

- `provider_config_id`：稳定 UUID，供 Plan、Run Snapshot、Budget、审计引用；
- `provider`：Provider 类型，例如 `tikhub`；同一 UUID 不原地改成另一 Provider 类型；
- `display_name`：便于人工识别，可修改，不作为业务外键；
- `base_url`：非 Secret，但必须为 HTTPS，且运行时仍受对应 Provider Adapter 的出站 allowlist；可配置 URL 不等于允许任意 SSRF 目标；
- `secret_ref`：只保存服务端 Secret 的安全引用，不保存原始 API Key/Token/Cookie；
- `enabled`：禁用后 Registry/执行链关闭失败，不继续发送外部请求。

同一 Provider 类型允许多个 Config。需要换 Provider 类型时创建新 Config，再显式切换平台/Plan 引用，以保持历史 Run、预算和审计稳定。

TikHub 的 App/Web/V2/V3 是**同一个 Provider 内部的 API family**，不是不同 Provider。第一版不做通用“某 endpoint 失败就静默切另一个 endpoint”的自动 fallback。若未来某个具体 Operation 需要 fallback，必须单独批准触发条件、费用、Attempt、Raw 和 Mapper/兼容语义；每次真实发送仍是新的 Attempt 和预算预留。

## 4. 前端配置分成 Provider 管理与采集业务两层

Stage 8 前端最终应把 Provider 实例管理与平台采集参数分开，不让页面把账号、平台和 TikHub 私有字段混成一张表。

### 4.1 Provider 管理

业务管理员可以维护多个 Provider Config，例如：

```text
TikHub 主账号
TikHub 备用账号
Provider B
```

每个 Config 可配置显示名称、Provider 类型和允许的 Base URL，并通过后端安全 Secret 写入能力设置/轮换凭据。凭据写入后，读取接口只返回“已配置/需更新”等状态或掩码提示，**绝不返回原始 API Key/Token**。具体可写 SecretStore/SecretService 在 Stage 8 安全 API Change 中建立；当前 Stage 7 只冻结 `secret_ref` 与只读 Secret 边界，不用数据库明文代替它。

### 4.2 平台/Plan 采集配置

每个平台选择具体 `provider_config_id`，然后只显示该 `Provider + Platform + Operation` Capability 真正支持的业务参数：

- 关键词/词包；
- 搜索排序；
- 发布时间范围；
- 内容类型等实际支持的筛选；
- 详情策略；
- 评论触发策略；
- 评论完整阈值、目标数量、排序；
- 二级回复目标；
- Deep Collection 参数；
- 请求/费用预算。

以下属于 Operation 内部技术状态或 Secret，不进入普通业务配置：

```text
cursor
page / pcursor
search_id
search_session_id
backtrace
pageArea
max_id
next_offset
Authorization / API Key / Cookie / Token
```

Provider 参数和业务语义通过 Capability 映射。例如前端只表达 `latest`，TikHub XHS Operation 可翻译为 `time_descending`，Douyin Search V2 可翻译为 `sort_type=2`；前端不能写死第三方枚举值。Provider Config 被禁用、Provider 未注册、Base URL 不在 Adapter allowlist，或所选 Provider 没有对应平台 Capability 时，后端关闭失败，不允许页面靠猜测继续运行。

## 5. Provider Capability

每个 `Provider + Platform + Business Operation` 必须声明可供后端 Contract/前端消费的 Capability，而不是让 Vue 自己维护平台 `if/else`。

Capability 至少表达：

```text
operation
supported_sort_modes
supported_time_filters
supported_content_types
native_time_filter
observes_comment_count
observes_comment_permission
comment_sort_modes
supports_reply_count
supports_sub_comments
supports_incremental_comment_sort
provider_page_size_policy
optional_enrichments
```

规则：

1. 只展示当前主 Operation 真正支持且经官方文档/Fixture 证明的业务选项；
2. Provider 没有原生时间筛选时，不把本地停止条件伪装成 Provider 原生筛选；
3. Provider 要求某参数保持默认时，该参数不开放给普通用户；
4. 后续换 Provider 时，只替换 Provider Config 引用、Capability/Operation/Mapper，上层 Plan 继续使用相同规范化业务语义；
5. Capability 是后端事实，经 Pydantic HTTP Contract → OpenAPI → Generated Client 提供给前端；
6. Provider Config 只决定“使用哪个 Provider 实例”，Capability 决定“这个实例对应的平台能配置什么”，两者不能合并成前端静态 `if/else`。

## 6. 统一采集 Decision Pipeline

每个关键词发现结果都按同一顺序进入决策：

```text
SEARCH
→ 保存 Search Raw
→ Mapper 得到当前 Observation
→ IDENTITY（platform + external_content_id）
→ COMPARE（与上次当前值比较）
→ DETAIL DECISION
→ COMMENT ELIGIBILITY
→ COMMENT DEPTH
→ REPLY DECISION
→ BUDGET RESERVATION
→ Provider Request
→ Raw
→ Mapper
→ Canonical
→ Ingestion
```

任何后续 HTTP 都必须由前一阶段明确产生动作；不能因为“搜到一条内容”就无脑抓详情、全部一级评论和全部二级回复。

## 7. 内容去重与变化判断

内容唯一身份继续使用：

```text
(platform, external_content_id)
```

搜索重叠、不同关键词命中或回补再次发现同一内容时，不删除本次 Candidate/来源证据，但后续付费动作按当前值判断。

默认规则：

| 当前情况 | 详情动作 | 评论动作 |
| --- | --- | --- |
| 新内容 | 搜索字段不足/策略要求时抓 | 继续按评论资格判断 |
| 重复内容，业务字段和有效指标均未变化 | 默认跳过 | 跳过 |
| 点赞/分享/收藏/播放等变化，`comment_count` 未变化 | 按详情策略决定 | **默认跳过评论** |
| `comment_count` 增加 | 按详情策略决定 | 增量抓评论 |
| `comment_count` 减少 | 按详情策略决定 | 记录下降并受控刷新；不能凭部分样本猜具体评论删除 |
| 评论数未知 | 按 Capability 决定是否用详情补足 | 不把未知当 0；必要时最多做受预算的评论首屏探测 |

“有效指标无变化”不是删除本次 Observation，而是避免继续花钱调用外部详情/评论接口。

## 8. 评论资格的短路规则

评论是否采集不依赖模糊“高价值”概念。按以下优先级判断：

1. Plan 明确关闭评论 → `not_requested`；
2. Provider 明确评论关闭/不可用 → `unavailable`；
3. 当前 Operation **可靠观察到** `comment_count == 0` → 不调用评论接口；
4. 已有内容且 `comment_count` 与上次相同 → 默认不重新抓评论；
5. 新内容且 `comment_count > 0` → 进入普通评论策略；
6. 已有内容且 `comment_count` 增加 → 优先增量抓取；
7. 已有内容且 `comment_count` 减少 → 受控刷新；
8. `comment_count` 未观察到/不可靠 → 按 Capability 决定详情补足或受预算首屏探测。

必须区分：

```text
comment_count = 0   → 明确观察到零
comment_count = null → 当前 Operation 未提供/未知
```

## 9. 自适应评论默认策略

第一版默认：

```text
comment_trigger = new_or_comment_changed
comment_mode = adaptive
full_fetch_threshold = 50
sample_target = 50
comment_sort = latest_if_supported
reply_target_per_root = 5
comment_refresh_when_count_unchanged = false
auto_deep_collection = false
```

这些是业务默认值，除不能被 Provider 支持的选项外都应由前端可配置。

### 9.1 一级评论

- 平台报告评论数 `1..50`：尽量抓到 Provider 末页，只有真实到达末页才能标记 `complete`；
- 平台报告评论数 `>50`：按用户选定且 Capability 支持的排序，目标采集 50 条，通常标记 `partial`；
- 目标数量是**软目标**。例如每页 20 条，为达到 50 请求第三页后实际得到 60 条，则完整保留 60 条和 Raw；不能扔掉已经付费返回的 10 条；
- 真正硬停止由 Provider 末页、请求预算、费用预算、技术安全页数、取消或错误等决定。

### 9.2 二级回复

- 一级评论明确 `reply_count == 0` 时不请求二级回复；
- 有回复时，默认每个一级线程目标 5 条；
- 同样保留整页已返回数据，不为凑目标数字裁剪 Raw/Canonical；
- 单线程回复预算不能突破 Run 评论预算和单内容评论预算。

## 10. 增量评论

当 `comment_count` 增加且该平台有经验证的稳定“最新”评论排序时：

```text
从最新第一页开始
→ 保存每页 Raw
→ 摄取新 comment_id
→ 遇到已知 comment_id
→ 达到安全停止条件
→ 停止
```

如果 Provider 没有稳定时间排序或 Fixture 不能证明该停止条件可靠，则 Capability 不声明增量能力，改为受控部分刷新。

`comment_count` 下降只表示平台总量发生变化，可能是删除、审核或统计校正。如果以前或当前 coverage 不是完整集合，不得把“这次没看到某条旧评论”解释成具体删除。

## 11. 评论覆盖和抽样透明度

现有 `complete / partial / not_requested / unavailable` 保持不变。Stage 7 读取/API/报告还必须能够解释：

```text
sample_mode
sort_mode
target_count
collected_count
provider_reported_count
observed_at
stop_reason
```

建议稳定 `stop_reason` 语义：

```text
provider_exhausted
provider_reported_zero
comments_disabled
known_comment_reached
policy_limit
budget_limit
page_limit
time_boundary
provider_error
cancelled
```

报告和页面不能把“最新评论 50 / 平台显示 1278”描述成“已分析全部 1278 条”。

## 12. Detail 策略

详情默认不是每轮都抓。触发条件保持简单：

```text
new
or search_missing_required_fields
or configured_business_change
or manual_deep_collection
or scheduled_refresh_checkpoint
```

重复内容搜索卡片已经提供足够字段、且需要监控的业务字段/指标没有变化时，不再为“刷新一下”重复请求详情。

Provider 额外统计也视为独立 enrichment。例如某平台播放量需要单独付费 Operation 时默认关闭，仅在 Plan 明确需要、Deep Collection 或业务规则触发时执行。

## 13. 时间范围与调度周期

时间窗口与调度周期只做**风险提示**，不替用户阻止业务选择：

```text
search_window < schedule_interval
→ Warning：存在发现盲区风险
→ 用户仍可保存和运行
```

只有以下情况才 Error：

- 参数无法映射到当前 Capability；
- Provider 明确不支持该值；
- 类型/范围非法；
- 必需参数缺失。

如果 Provider 的最小原生时间窗大于调度周期，例如 6 小时调度只能查询 24 小时窗口，则允许产生重叠；依靠内容身份去重和本 Decision Pipeline 避免重复详情/评论费用。

没有 Provider 原生时间筛选的平台必须显式标记 `native_time_filter=false`。若实现基于发布时间的本地停止条件，UI/日志要标明它是本地边界，不得宣称 Provider 已原生过滤。

## 14. Deep Collection

普通自动采集和深度抓取分开：

```text
NORMAL
→ 默认自动策略

DEEP
→ 人工或以后由分析/监控规则触发的加深采集
```

Stage 7 `auto_deep_collection=false`。内容已经入库时，用户从内容页点击“深度抓取”只提交内部 `content_id`；后端查询当前内容得到 platform、external_content_id 和当前 Provider，再建立正式 Job。用户不需要复制 note_id/aweme_id/photo_id。

高级“按外部 ID / 分享链接直接采集”用于系统尚未发现但人工已经掌握的内容。解析到稳定外部 ID 后，同样走正式 Operation → Budget → Raw → Mapper → Canonical → Ingestion，不允许浏览器直接调用 TikHub。

Deep Collection 仍必须显示预计成本并受数据库硬预算限制。

## 15. 费用预测与硬预算

前端必须区分三个概念：

| 类型 | 用途 | 是否保证不超 |
| --- | --- | --- |
| 预计费用 | 根据历史 Run；无历史时按当前配置保守估算 | 否 |
| 理论请求上限 | 从 `max_*`、关键词/平台/分页策略推导最坏请求数 | 只是计划上限 |
| 数据库硬预算 | 真实 HTTP Attempt 发送前原子预留 | **是，除已发生的未知/超预留真实费用必须如实记录** |

TikHub 单价不硬编码在长期 Blueprint。Provider Pricing 实现应按当前 endpoint 信息维护单价快照；TikHub 官方提供 Endpoint Info 和 `calculate_price` 能力，可用于校验当前基础价/阶梯计费：

- Endpoint Info：https://docs.tikhub.io/186826054e0
- Calculate Price：https://docs.tikhub.io/186826052e0

每个 Attempt 仍保存实际使用的单价/费用快照，历史费用不能随 TikHub 后续调价被重算。

有足够历史后，预计费用可使用：平均搜索页数、重复率、新内容比例、零评论比例、评论数变化比例、平均评论页数和平均二级请求数。无历史时只给保守范围，不制造虚假的精确金额。

## 16. Budget Ledger 的 Stage 7 最终语义

评论不能耗尽整个 Run 的发现预算。最终账户层级冻结为：

```text
global
run
run_comments
content_comments
```

每个真实 HTTP Attempt：

```text
所有 Operation
→ global + run

评论 / 二级评论 Operation
→ global + run + run_comments + content_comments
```

`provider_budget_accounts` 必须通过 `provider_config_id` 绑定稳定 Provider 配置实例。这样同一 TikHub Config 被多个平台共享时，共享同一个 global Provider 账户；不同 TikHub 账号/不同 Provider Config 则天然隔离额度和费用，不能只按 `provider='tikhub'` 混成一个账户。

预算消费优先级：

```text
1. 关键词发现
2. 必要详情
3. 一级评论
4. 二级回复
5. 可选 enrichment / Deep Collection
```

数据库 Migration 实现时必须继续遵守现有 Attempt/Reservation/Fencing 原则：缺任一必需账户关闭失败；网络重试是新 Attempt/新预留；同一 Attempt 只有预留事务重放可复用唯一 Reservation；未知计费继续占用预算。

## 17. Business Pipeline Probe

Stage 7 保留两种独立调试：

### 17.1 Operation Probe

验证单个正式 endpoint/分页/Mapper：

```text
Provider Config + Platform + Operation + explicit parameters
→ Registry / Capability
→ 生产 Client / Operation
→ Raw
→ Mapper
→ Canonical
```

真实 Probe 通过 `provider_config_id → secret_ref` 取得凭据，并继续受 Provider Base URL allowlist、请求上限和费用上限保护。Probe 不接受原始 Secret 作为持久配置或输出字段。

### 17.2 Business Pipeline Probe

验证本文件整套业务决策：

```text
真实/Fixture Search
→ Observation
→ previous state
→ Decision Service
→ Detail / Comment / Reply Actions
→ Budget Limits
→ Raw / Canonical
→ decisions.jsonl
→ 人工 XLSX
```

生产系统的 previous state 来自 PostgreSQL；Business Probe 可以从上一次 Probe Snapshot 读取 previous state，但两者必须调用**同一个生产 Decision Service**。

例如第二次运行必须能够观察：

```text
existing + comment_count 35 → 35
→ SKIP_COMMENTS
→ reason=comment_count_unchanged

existing + comment_count 35 → 41
→ FETCH_INCREMENTAL_COMMENTS

new + comment_count=0
→ SKIP_COMMENTS
→ reason=provider_reported_zero
```

`decisions.jsonl` 和人工 XLSX 至少显示：新/旧内容、上次/本次评论数、详情动作、评论动作和原因，便于确认系统为什么没有继续花钱。

## 18. 五平台能力差异摘要

### 18.1 小红书

- 搜索 App V2 有排序、内容类型、发布时间等业务筛选；分页使用 page + search session 状态；
- 评论 App V2 支持 `latest_v2` 等排序，首版默认最新；
- 当前仓库 Stage 6 已实现 Operation/Mapper，但当前评论 Operation 的 `latest_v2` 仍是代码固定值；Stage 7 前端 Capability/Plan 实现时再把经批准的评论排序业务选项接入，不改写 Stage 6 历史 Migration。

### 18.2 抖音

- 当前仓库已实现 Search V2 与 App V3 详情/一级评论/评论回复的请求构造和基础分页状态机；尚未实现 Mapper、非空真实 Fixture、Real Probe 或默认 Registry Capability，因此不能宣称平台兼容完成；
- Search V2 提供综合/点赞/最新和发布时间筛选；cursor/search_id/backtrace 属技术分页；
- App V3 评论/回复接口文档要求 `count` 保持默认，当前 Operation 不传该参数，普通 UI 也不暴露 page size；
- Search Observation 可利用可靠的 comment_count/评论许可字段做零评论/关闭短路，但具体 Mapper 字段必须由合法 Fixture 固化；在此之前 Operation 不猜评论数组或稳定增量停止字段。

### 18.3 微博

- 当前仓库已实现 Web Search、App 详情/一级评论、Web V2 二级评论的请求构造和有证据的分页状态；尚未实现 Mapper、非空真实 Fixture、Real Probe 或默认 Registry Capability，因此不能宣称平台兼容完成；
- Web Search 当前 Operation 对上层暴露统一的 `general/latest/hot/video/image/article` 业务语义，其中 `latest` 映射 Provider “实时/最新优先” `search_type=61`；同时支持 hour/day/week/month 时间范围。page 属技术分页，搜索结果列表位置与空页字段仍待合法 Fixture 固化；
- App 一级评论支持热度/时间排序，并只按官方 `data.moreInfo.params.max_id` 路径推进；当前 Operation 默认 `latest → sort_type=1`，稳定增量停止仍需 Fixture/Real Probe 证明；
- 二级评论使用 Web V2 `id/max_id`，当前不覆盖可选 `count`，也不猜尚未被 Fixture 证明的返回 max_id JSON path。

### 18.4 B站

- 当前 `main` 已完成 `aima_ugc.adapters.providers.tikhub.operations.bilibili` 的搜索、视频详情、一级评论和回复请求构造与有证据分页；搜索只按当前官方 `data.data.pagination.next` 推进，评论/回复只消费调用方可靠提取的 `next_offset`；
- 当前机器实现只冻结其代码和测试实际支持的请求/分页边界；Mapper、非空真实 Fixture、Real Probe、Capability/Registry 仍未闭环；
- 没有原生时间过滤时，Capability 仍必须遵守本文件已有 `native_time_filter=false` 设计，不得因为 Operation 代码存在就伪造服务端时间筛选；
- 弹幕仍是独立可选 enrichment，不等同评论，默认关闭并单独受预算控制。

### 18.5 快手

- App Search V2 当前只有 keyword + pcursor，官方说明该接口相对更贵但稳定性更高，因此第一版优先利用去重、零评论判断、预算和下游短路省钱；
- 当前批准的搜索 Operation 没有排序/发布时间参数，前端不能显示不存在的原生选项；
- App Detail 使用 photo_id；评论首版固定用 Web 一级/二级评论 pcursor 链，属于明确 Operation 选型，不是运行时 fallback。

详细平台规则、官方链接和当前代码路径见 [`../collection/README.md`](../collection/README.md)。

## 19. Stage 7 开发门禁

本设计批准后，以下工作**可以开始**并按边界清楚的 Stage 7 PR 推进：

- Collection Decision Service 与测试；
- Provider Capability/规范化业务参数 Contract；
- Provider Config/Registry/平台路由；
- Plan 平台配置与 Run Snapshot；
- 最终多级预算账户/Reservation Migration 与并发测试；
- Kuaishou Operation 构造与分页状态机；
- 抖音、微博、B站、快手获得合法脱敏真实 Fixture 后实现对应 Mapper、Ingestion 纵切与可运行 Capability/Registry 接线；
- Operation Probe / Business Pipeline Probe。

当前 Provider Config/Route 单元的机器事实只允许登记已有完整实现证据的 `tikhub + xhs` Capability。抖音、微博和B站虽然已经有 Operation/分页机器代码，但 Mapper/Fixture/Probe 尚未闭环，因此均不能加入默认 Registry 冒充可运行平台能力。快手不能在 Operation 尚未进入 `main` 时提前注册。

以下仍然**不能宣称完成/启用**：

1. 抖音、微博、B站、快手平台兼容验收：每个平台仍需合法脱敏非空真实 Fixture + Mapper Contract Test + Real Probe；
2. Scheduler 自动调度启用：仍需批准 `misfire_policy`、`max_catch_up_runs` 和补跑费用/容量保护；
3. Stage 8 正式业务页面：Stage 7 先建立后端 Provider Config/Capability/Plan Contract，Stage 8 再按生成 OpenAPI Client 建页面；Provider 凭据编辑还必须先建立安全可写 SecretStore/SecretService，不能把数据库 Secret 明文或“读回 API Key”作为捷径。

不要为了等待 Scheduler 决策而阻塞与 Scheduler 无关的 Stage 7 Provider/Collection 工作；也不要因为 Operation 已实现就把未做真实 Fixture/Mapper/Probe 的平台称为“已兼容”。
