## 2. Provider Config、Platform、Provider、Operation 边界

Provider 类型与可连接的 Provider 配置实例必须区分。一个 Provider 类型可以存在多个账号/实例，每个实例使用稳定 `provider_config_id` 标识；平台或 Plan 选择具体实例，再由其 Provider 类型与平台共同选择业务 Capability/Operation：

```text
Provider Config instance
  ├─ provider_config_id
  ├─ provider
  ├─ base_url
  ├─ secret_ref
  └─ enabled
        ↓
Platform / Plan selects provider_config_id
        ↓
Provider Registry
        ↓
Provider + Platform Capability
        ↓
Business Operation
        ↓
Provider-specific endpoint / pagination
        ↓
Raw → Provider + Platform Mapper → Canonical
```

当前五个平台默认 Provider 类型均为 `tikhub`：

```text
xiaohongshu → tikhub
douyin      → tikhub
weibo       → tikhub
bilibili    → tikhub
kuaishou    → tikhub
```

但这不要求五个平台共享同一个 Provider Config。实际运行可以是：

```text
TikHub 主账号  → xiaohongshu + douyin
TikHub 备用账号 → bilibili
Provider B     → weibo
```

也可以让五个平台都引用同一个 TikHub Config。Provider Config 本身不保存平台字段；平台选择关系属于 Plan/平台策略。以后单独把某个平台改为官方 API、Apify、自建采集器或其他 Provider 时，为新的 Provider 实例建立独立 Config，并为新的 `Provider + Platform` 建立 Operation、Raw Fixture、Mapper、Capability 和 Probe；Canonical/Ingestion/数据库不因 Provider 更换而重写。

Provider Config 第一版稳定边界：

- `provider_config_id`：稳定 UUID，供 Plan、Run Snapshot、Provider Request 与审计引用；
- `provider`：Provider 类型，例如 `tikhub`；同一 UUID 不原地改成另一 Provider 类型；
- `display_name`：便于人工识别，可修改，不作为业务外键；
- `base_url`：非 Secret，但必须为 HTTPS，且运行时仍受对应 Provider Adapter 的出站 allowlist；可配置 URL 不等于允许任意 SSRF 目标；
- `secret_ref`：只保存服务端 Secret 的安全引用，不保存原始 API Key/Token/Cookie；
- `enabled`：禁用后 Registry/执行链关闭失败，不继续发送外部请求。

同一 Provider 类型允许多个 Config。需要换 Provider 类型时创建新 Config，再显式切换平台/Plan 引用，以保持历史 Run、Provider 来源和审计稳定。

TikHub 的 App/Web/V2/V3 是**同一个 Provider 内部的 API family**，不是不同 Provider。第一版不做通用“某 endpoint 失败就静默切另一个 endpoint”的自动 fallback。若未来某个具体 Operation 需要 fallback，必须单独批准触发条件、费用、Attempt、Raw 和 Mapper/兼容语义；每次真实发送仍必须创建新的 Attempt，不能复用已经进入发送边界的 Attempt。

## 4. 前端配置分成 Provider 管理与采集业务两层

Stage 8 前端最终应把 Provider 实例管理与平台采集参数分开，不让页面把账号、平台和 TikHub 私有字段混成一张表。

### 4.1 Provider 管理

业务管理员可以维护多个 Provider Config，例如：

```text
TikHub 主账号
TikHub 备用账号
Provider B
```

每个 Config 可配置显示名称、Provider 类型和允许的 Base URL，并通过后端安全 Secret 写入能力设置/轮换凭据。凭据写入后，读取接口只返回“已配置/需更新”等状态或掩码提示，**绝不返回原始 API Key/Token**。具体可写 SecretStore/SecretService 在 Stage 8 安全 API Change 中建立；当前 Stage 7 只冻结 `secret_ref` 与只读 Secret 边界，不用数据库明文代替它。

### 4.2 平台/Plan 采集配置

每个平台选择具体 `provider_config_id`，然后只显示该 `Provider + Platform + Operation` Capability 真正支持的业务参数：

- 关键词/词包；
- 搜索排序；
- 发布时间范围；
- 内容类型等实际支持的筛选；
- 详情策略；
- 评论触发策略；
- 评论完整阈值、目标数量、排序；
- 二级回复目标；
- Deep Collection 参数；

以下属于 Operation 内部技术状态、Provider 定价事实或 Secret，不进入普通业务配置：

```text
cursor
page / pcursor
search_id
search_session_id
backtrace
pageArea
max_id
next_offset
TikHub endpoint base_price / discount tiers / pricing_version
Authorization / API Key / Cookie / Token
```

Provider 参数和业务语义通过 Capability 映射。例如前端只表达 `latest`，TikHub XHS Operation 可翻译为 `time_descending`，Douyin Search V2 可翻译为 `sort_type=2`；前端不能写死第三方枚举值。Provider Config 被禁用、Provider 未注册、Base URL 不在 Adapter allowlist，或所选 Provider 没有对应平台 Capability 时，后端关闭失败，不允许页面靠猜测继续运行。

## 5. Provider Capability

每个 `Provider + Platform + Business Operation` 必须声明可供后端 Contract/前端消费的 Capability，而不是让 Vue 自己维护平台 `if/else`。

Capability 至少表达：

```text
operation
supported_sort_modes
supported_time_filters
supported_content_types
native_time_filter
observes_comment_count
observes_comment_permission
comment_sort_modes
supports_reply_count
supports_sub_comments
supports_incremental_comment_sort
provider_page_size_policy
optional_enrichments
```

规则：

1. 只展示当前主 Operation 真正支持且经官方文档/Fixture 证明的业务选项；
2. Provider 没有原生时间筛选时，不把本地停止条件伪装成 Provider 原生筛选；
3. Provider 要求某参数保持默认时，该参数不开放给普通用户；
4. 后续换 Provider 时，只替换 Provider Config 引用、Capability/Operation/Mapper，上层 Plan 继续使用相同规范化业务语义；
5. Capability 是后端事实，经 Pydantic HTTP Contract → OpenAPI → Generated Client 提供给前端；
6. Provider Config 只决定“使用哪个 Provider 实例”，Capability 决定“这个实例对应的平台能配置什么”，两者不能合并成前端静态 `if/else`。

## 6. 统一采集 Decision Pipeline

每个关键词发现结果都按同一顺序进入决策：

```text
SEARCH
→ 保存 Search Raw
→ Mapper 得到当前 Observation
→ IDENTITY（platform + external_content_id）
→ COMPARE（与上次当前值比较）
→ DETAIL DECISION
→ COMMENT ELIGIBILITY
→ COMMENT DEPTH
→ REPLY DECISION
→ Provider Request
→ Raw
→ Mapper
→ Canonical
→ Ingestion
```

任何后续 HTTP 都必须由前一阶段明确产生动作；不能因为“搜到一条内容”就无脑抓详情、全部一级评论和全部二级回复。

## 7. 内容去重与变化判断

内容唯一身份继续使用：

```text
(platform, external_content_id)
```

搜索重叠、不同关键词命中或回补再次发现同一内容时，不删除本次 Candidate/来源证据，但后续付费动作按当前值判断。

默认规则：

| 当前情况 | 详情动作 | 评论动作 |
| --- | --- | --- |
| 新内容 | 搜索字段不足/策略要求时抓 | 继续按评论资格判断 |
| 重复内容，业务字段和有效指标均未变化 | 默认跳过 | 跳过 |
| 点赞/分享/收藏/播放等变化，`comment_count` 未变化 | 按详情策略决定 | **默认跳过评论** |
| `comment_count` 增加 | 按详情策略决定 | 增量抓评论 |
| `comment_count` 减少 | 按详情策略决定 | 记录下降并受控刷新；不能凭部分样本猜具体评论删除 |
| 评论数未知 | 按 Capability 决定是否用详情补足 | 不把未知当 0；必要时最多做一次受控评论首屏探测 |

“有效指标无变化”不是删除本次 Observation，而是避免继续花钱调用外部详情/评论接口。

## 8. 评论资格的短路规则

评论是否采集不依赖模糊“高价值”概念。按以下优先级判断：

1. Plan 明确关闭评论 → `not_requested`；
2. Provider 明确评论关闭/不可用 → `unavailable`；
3. 当前 Operation **可靠观察到** `comment_count == 0` → 不调用评论接口；
4. 已有内容且 `comment_count` 与上次相同 → 默认不重新抓评论；
5. 新内容且 `comment_count > 0` → 进入普通评论策略；
6. 已有内容且 `comment_count` 增加 → 优先增量抓取；
7. 已有内容且 `comment_count` 减少 → 受控刷新；
8. `comment_count` 未观察到/不可靠 → 按 Capability 决定详情补足或受控首屏探测。

必须区分：

```text
comment_count = 0   → 明确观察到零
comment_count = null → 当前 Operation 未提供/未知
```

## 9. 自适应评论默认策略

第一版默认：

```text
comment_trigger = new_or_comment_changed
comment_mode = adaptive
full_fetch_threshold = 50
sample_target = 50
comment_sort = latest_if_supported
reply_target_per_root = 5
comment_refresh_when_count_unchanged = false
auto_deep_collection = false
```

这些是业务默认值，除不能被 Provider 支持的选项外都应由前端可配置。

### 9.1 一级评论

- 平台报告评论数 `1..50`：尽量抓到 Provider 末页，只有真实到达末页才能标记 `complete`；
- 平台报告评论数 `>50`：按用户选定且 Capability 支持的排序，目标采集 50 条，通常标记 `partial`；
- 目标数量是**软目标**。例如每页 20 条，为达到 50 请求第三页后实际得到 60 条，则完整保留 60 条和 Raw；不能扔掉已经付费返回的 10 条；
- 真正停止由 Provider 末页、已批准的业务目标、技术安全页数、取消或错误等决定；当前版本不实现预算停止条件。

### 9.2 二级回复

- 一级评论明确 `reply_count == 0` 时不请求二级回复；
- 有回复时，默认每个一级线程目标 5 条；
- 同样保留整页已返回数据，不为凑目标数字裁剪 Raw/Canonical；
- 二级回复继续受目标数量、Provider 末页、技术安全页数、取消和错误等停止条件约束；当前版本没有独立评论预算。

## 10. 增量评论

当 `comment_count` 增加且该平台有经验证的稳定“最新”评论排序时：

```text
从最新第一页开始
→ 保存每页 Raw
→ 摄取新 comment_id
→ 遇到已知 comment_id
→ 达到安全停止条件
→ 停止
```

如果 Provider 没有稳定时间排序或 Fixture/真实 Probe 不能证明该停止条件可靠，则 Capability 不声明增量能力，改为受控部分刷新。已付费返回的当前页必须完整保存、映射和摄取；历史边界只决定“是否继续付费请求下一页”。

当前五平台正式 Capability：

| 平台 | 评论排序事实 | `supports_incremental_comment_sort` | 原因 |
| --- | --- | --- | --- |
| 小红书 | App V2 固定 `latest_v2` | `true` | 官方最新优先语义 + 当前真实页时间严格非增 |
| B站 | App `mode=2`，首屏显式 `next_offset=0` | `true` | 官方时间排序语义 + 当前真实首屏 20/20 唯一 ID、20 个时间戳严格非增 |
| 抖音 | App V3 评论无已批准的最新评论排序参数 | `false` | 无法证明 comment ID 可作为安全时间边界 |
| 微博 | App `sort_type=1` | `false` | 当前真实 20 条有效评论时间顺序并非严格非增 |
| 快手 | App `pcursor`，无已批准的最新评论排序参数 | `false` | 当前真实 94 条一级评论时间顺序并非严格非增 |

增量安全停止使用生产共享规则：某页出现已知历史评论后，只有从**第一个已知评论到该页末尾全部都是已知评论**，才记录 `known_comment_reached` 并停止下一页；如果旧评论后又出现新评论，则继续翻页，避免置顶/混排导致误停。

`comment_count` 下降只表示平台总量发生变化，可能是删除、审核或统计校正。如果以前或当前 coverage 不是完整集合，不得把“这次没看到某条旧评论”解释成具体删除。

## 11. 评论覆盖和抽样透明度

现有 `complete / partial / not_requested / unavailable` 保持不变。Stage 7 读取/API/报告还必须能够解释：

```text
sample_mode
sort_mode
target_count
collected_count
provider_reported_count
observed_at
stop_reason
```

建议稳定 `stop_reason` 语义：

```text
provider_exhausted
provider_reported_zero
comments_disabled
known_comment_reached
policy_limit
page_limit
time_boundary
provider_error
cancelled
```

报告和页面不能把“最新评论 50 / 平台显示 1278”描述成“已分析全部 1278 条”。

## 12. Detail 策略

详情默认不是每轮都抓。触发条件保持简单：

```text
new
or search_missing_required_fields
or configured_business_change
or manual_deep_collection
or scheduled_refresh_checkpoint
```

重复内容搜索卡片已经提供足够字段、且需要监控的业务字段/指标没有变化时，不再为“刷新一下”重复请求详情。

Provider 额外统计也视为独立 enrichment。例如某平台播放量需要单独付费 Operation 时默认关闭，仅在 Plan 明确需要、Deep Collection 或业务规则触发时执行。

## 13. 时间范围与调度周期

时间窗口与调度周期只做**风险提示**，不替用户阻止业务选择：

```text
search_window < schedule_interval
→ Warning：存在发现盲区风险
→ 用户仍可保存和运行
```

只有以下情况才 Error：

- 参数无法映射到当前 Capability；
- Provider 明确不支持该值；
- 类型/范围非法；
- 必需参数缺失。

如果 Provider 的最小原生时间窗大于调度周期，例如 6 小时调度只能查询 24 小时窗口，则允许产生重叠；依靠内容身份去重和本 Decision Pipeline 避免重复详情/评论费用。

没有 Provider 原生时间筛选的平台必须显式标记 `native_time_filter=false`。若实现基于发布时间的本地停止条件，UI/日志要标明它是本地边界，不得宣称 Provider 已原生过滤。

## 14. Deep Collection

普通自动采集和深度抓取分开：

```text
NORMAL
→ 默认自动策略

DEEP
→ 人工或以后由分析/监控规则触发的加深采集
```

Stage 7 `auto_deep_collection=false`。内容已经入库时，用户从内容页点击“深度抓取”只提交内部 `content_id`；后端查询当前内容得到 platform、external_content_id 和当前 Provider，再建立正式 Job。用户不需要复制 note_id/aweme_id/photo_id。

高级“按外部 ID / 分享链接直接采集”用于系统尚未发现但人工已经掌握的内容。解析到稳定外部 ID 后，同样走正式 Operation → Raw → Mapper → Canonical → Ingestion，不允许浏览器直接调用 TikHub。

Deep Collection 当前不附加预算/额度功能，但仍必须遵守正式 Job、Provider Routing、Fencing、一次 Attempt 一次发送、Raw 与 Ingestion 边界。若未来需要 Budget/Cost Guard 或聚合预计成本，必须通过新的 L3 Change 单独设计；不得把 Provider Pricing 配置复制到前端。

## 15. Provider Billing 与成本事实

当前系统保留 Provider Request/Attempt 的 Billing 与成本字段，用于记录一次外部调用在发送前采用的价格快照、Provider 明确返回的实际费用（若存在），以及网络结果未知时的潜在重复计费风险。这些字段属于**执行与审计事实**，不是预算额度。

TikHub Pricing 继续作为 Provider Adapter 的版本化成本事实来源。它可以产生可审计的 `estimated_cost / currency / unit_price_snapshot`，但不能把本地估算值伪装成 Provider 权威账单；Pricing 不保存 Secret，也不是普通业务前端配置。

当前版本没有 Plan 请求次数上限、金额上限、评论预算、Budget Account 或 Reservation Ledger，也不根据这些额度阻断网络请求。Provider Billing 的完整性要求与“预算功能”是两件不同的事情。

## 16. 未来 Budget / Cost Guard 扩展方向

预算功能已于 2026-08-17 由用户明确撤回。当前生产代码、当前 SQLAlchemy Schema 和 Plan Contract **不得保留 Budget Service、Budget Repository、Budget Account、Reservation Ledger、`request_budget` 或空实现接口**。历史 Migration 保持不可变，由新的向前 Migration `20260817_0015` 删除已落地预算结构。

以后如果业务确实需要限额能力，必须创建新的 L3 Change，从真实业务需求重新冻结限制对象、周期、维度、超限行为、对账、迁移和 UI。候选接入位置只作为架构方向保留：

```text
已准备 Provider Attempt
→ 可选 Budget / Cost Guard（未来独立能力）
→ Dispatch CAS
→ Provider Transport
```

未来 Guard 可以读取 `provider_config_id`、Run/Content/Operation 身份和 Provider Billing estimate 等稳定事实，但在新 Change 批准前不定义 Contract、Schema、默认额度或前端配置，也不在生产代码中预留空接口。

## 17. Business Pipeline Probe

Stage 7 保留两种独立调试：

### 17.1 Operation Probe

验证单个正式 endpoint/分页/Mapper：

```text
Provider Config + Platform + Operation + explicit parameters
→ Registry / Capability
→ 生产 Client / Operation
→ Raw
→ Mapper
→ Canonical
```

真实 Probe 通过 `provider_config_id → secret_ref` 取得凭据，并继续受 Provider Base URL allowlist、显式 Probe 请求上限和 Secret 边界保护。Probe 不接受原始 Secret 作为持久配置或输出字段。

真实 billable Probe 继续使用生产 Provider Billing/Pricing 路径记录成本事实；不得为了 Probe 猜测 endpoint 价格或伪造 `actual_cost`。这属于计费事实完整性，不表示当前存在预算额度功能。

### 17.2 Business Pipeline Probe

验证本文件整套业务决策：

```text
真实/Fixture Search
→ Observation
→ previous state
→ Decision Service
→ Detail / Comment / Reply Actions
→ Raw / Canonical
→ decisions.jsonl
→ 原始数据 Excel
```

生产系统的 previous state 来自 PostgreSQL；Business Probe 可以从上一次 Probe Snapshot 读取 previous state，但两者必须调用**同一个生产 Decision Service**。

例如第二次运行必须能够观察：

```text
existing + comment_count 35 → 35
→ SKIP_COMMENTS
→ reason=comment_count_unchanged

existing + comment_count 35 → 41
→ FETCH_INCREMENTAL_COMMENTS

new + comment_count=0
→ SKIP_COMMENTS
→ reason=provider_reported_zero
```

运行摘要/决策证据和原始数据 Excel 至少显示：新/旧内容、上次/本次评论数、详情动作、评论动作和原因，便于确认系统为什么没有继续花钱。


## 18. 五平台能力差异摘要

### 18.1 小红书

- Search App V2 支持排序、内容类型和发布时间筛选；评论 App V2 固定 `sort_strategy=latest_v2`；
- 当前真实 Runner 观察到一级评论 ID 唯一且时间严格非增；Capability 已开启安全增量；
- `comment_count` 增加时生产 Decision 进入 `fetch_incremental`，正式 Scope 从 PostgreSQL 读取已知一级评论 ID，并使用共享 `known_comment_reached` 边界停止下一页。

### 18.2 抖音

- Search V2、App V3 Detail/Comments/Replies、Mapper、真实 Fixture、Capability/Registry 和生产纵切均已建立；
- 真实兼容验证确认生产 extractor 会过滤不含稳定 `aweme_id` 的混合搜索卡片；
- App V3 评论没有已批准的“最新评论排序”业务参数，因此 `supports_incremental_comment_sort=false`；评论数增加走 `refresh_controlled`。

### 18.3 微博

- Web Search、App Detail/一级评论、Web V2 二级评论、Mapper、真实 Fixture、Capability/Registry 均已建立；
- App 一级评论可发送 `sort_type=1`，但当前真实样本的 20 条有效评论时间顺序不是严格非增；生产 extractor 同时过滤没有稳定评论 ID 的展示卡片；
- 因此 `supports_incremental_comment_sort=false`，不能因为参数名叫“latest”就提前停止分页。

### 18.4 B站

- App Search/Detail/Comments/Reply、Mapper、真实 Fixture、Capability/Registry 均已建立；Search 当前没有 Provider 原生时间范围，`native_time_filter=false`；
- 评论 `latest` 映射 `mode=2`；真实 Probe 证明首屏必须显式 `next_offset=0`，生产 Runtime 已固定该首屏语义；
- 2026-08-18 当前真实 Runner 在 Provider 报告 105 条评论的样本上返回 20 条，20/20 ID 唯一、20 个时间戳严格非增；结合官方 `mode=2=time` 语义，Capability 开启 `supports_incremental_comment_sort=true`。

### 18.5 快手

- 正式主链为 App Search V2 / Detail / 一级评论 / 二级回复；Web 评论链只保留显式 `verified_backup`，不自动 fallback；
- 当前正式 App 评论没有已批准的最新评论排序参数；真实 Probe 的 94 条一级评论时间顺序不是严格非增；
- 因此 `supports_incremental_comment_sort=false`，评论数增加继续受控刷新。

## 19. Stage 7 当前实现状态与一致性门禁

Stage 7 的基础采集/调度闭环已经合入 `main` 并归档；本节不再把历史 PR #55 的“待合并”步骤描述成当前工作。当前正式机器实现包括五平台 TikHub Operation/Mapper/Capability/Registry、Provider Config/Secret、Decision、Plan/Occurrence/Run Snapshot、Scheduler、`collection.run.v1` Worker、Raw/Canonical/Ingestion 与 Provider Billing 审计。

2026-08-18 的系统一致性复核发现并修复了一个已批准 Blueprint 未完整落地的缺口：增量评论 Decision 已存在，但生产 Scope 最初没有历史 comment ID 边界，且 XHS Capability 保守关闭。当前规则已经收敛为：

- 当前没有请求/金额 Budget Runtime，也不以预算作为评论停止条件。

后续任何平台若要从 `false` 改成 `true`，必须取得同等级“官方排序语义 + 当前真实多评论页顺序 + 稳定 comment ID”的证据，并同步 Capability、平台文档和回归测试；不能只依据参数名称或单条样本。
