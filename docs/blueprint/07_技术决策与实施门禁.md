# 技术决策与实施门禁

本文只记录**普通任务不能静默改变的长期技术决定**。精确字段、Route、表、Job 注册和版本仍以当前机器事实为准；历史 Stage/PR/CI 不在这里维护。

需要改变本页任一长期边界时，至少先恢复当前代码事实，再按影响等级建立正式 Change、明确真实方案与取舍、同步 Contract/Schema/测试/文档，并以当前 PR HEAD 新鲜证据完成 Review。

## 1. 决策 A：当前使用模块化单体，不主动拆微服务

业务模块在同一仓库/应用体系中，通过 Domain、Service、Contract、Repository、Table Owner 隔离变化；API/Worker/Scheduler/Migration 已按运行职责分进程。没有真实性能、组织或隔离证据时，不新增微服务、Kafka/Redis、第二业务数据库或 Kubernetes 复杂度。

## 2. 决策 B：外部 Provider 格式不是系统公共语言

固定主链：

```text
Provider / File Reader
→ Raw / Source Artifact
→ Operation / Mapper
→ Canonical
→ Decision
→ Owner
→ PostgreSQL
```

Provider 私有 JSON 只能在 Adapter/Fixture 边界存在，业务层不直接依赖。

## 3. 决策 C：前端以真实 Contract 为约束，不从原型虚构 API

HTTP 类型链固定为 Pydantic → FastAPI OpenAPI → Orval generated client → Feature API/Store/Page。生成 Client 禁止手改；Figma 的示例数据、下拉项和状态必须回到当前 Contract/后端事实。

当前 Route exact block：

```text
/
/admin/configuration
/collection-runtime
/collection-strategy
/voice-plaza
```
<!-- docs-facts:frontend-routes:end -->

精确 Route 唯一机器事实是 [`frontend/src/app/routes.ts`](../../frontend/src/app/routes.ts)。

## 4. 决策 D：PostgreSQL 是唯一业务事实库，Schema 只通过 Alembic 演进

API/Worker/Scheduler 共享同一 PostgreSQL 事实。历史 Migration 不改写；结构变化新增 Migration。SQLite 不能替代 PostgreSQL 约束、锁、事务、Fencing 等真实验证。

## 5. 决策 E：业务表由单一 Owner 写入

模块可以读取必要公共事实，但写业务表必须通过该表 Owner 的 Service/Repository；跨 Owner 原子操作由 Bootstrap/应用服务显式编排。Router、调试脚本和其他模块不得为了方便直接 SQL 写别人的业务表。

## 6. 决策 F：所有正式长任务复用 PostgreSQL Durable Job Runtime

采集、导入、Analysis、Export 使用同一持久 Job Runtime 和 Registry。Lease、Heartbeat、Deadline、Fencing、Retry、Cancel、Reaper、Progress、Result/Error 等公共语义不得在业务模块复制第二套。

## 7. 决策 G：Scheduler 只产生调度事实，不执行 Provider/AI

固定链：Plan → logical slot → Occurrence → Run/Scope → Job。当前停机恢复使用已实现的 `latest_only` 等语义；改变 misfire/catch-up 必须同时验证领域算法、并发事务、持久状态和恢复行为。

## 8. 决策 H：Provider 请求必须可追溯，重试不能隐瞒计费风险

Provider Request/Attempt、Raw Artifact、Job/Fencing 共同记录外部调用事实。已有完整 Raw 时接管不重复发送；发送结果不确定时必须保留 `unknown`/潜在重复计费风险，而不是假装请求一定没发出。

## 9. 决策 I：Canonical 只表达系统真正观察到的字段

Mapper 不用缺失猜 `0/false/空字符串`；`observed_fields`/字段观测时间用于防止稀疏 Search 或旧 Observation 清空更新的 Detail。外部 ID 进入 Canonical 时保持稳定字符串身份。

## 10. 决策 J：Content 身份与 Current/Version/Metric/Coverage 分层

Content 业务身份固定由平台 + 外部内容 ID 收敛；Comment 使用 Content 身份 + 外部评论 ID。稳定字段历史、互动指标历史和评论覆盖度分别存储，不能用一个“最后更新时间”替代所有新鲜度语义。

## 11. 决策 K：平台机器身份只允许五个完整值

```text
xiaohongshu
douyin
weibo
bilibili
kuaishou
```

缩写、品牌别名、大小写变体和 `all` 不进入平台身份字段。Excel 中文媒体名只在入口映射一次；跨平台词包范围使用独立 scope 语义。

## 12. 决策 L：Provider Capability/备用接口由显式事实驱动

不同 App/Web/V1/V2/V3 接口不因为某次失败自动猜测切换。正式 Operation、Capability、分页和备用策略必须有真实 Fixture/Probe/价格/失败语义证据，并通过版本化公共边界暴露。

## 13. 决策 M：Collection Candidate 在 Mapper 前形成持久来源事实

Collection 先保留 Provider Request/Attempt/Raw/Candidate，再做 Mapper/Decision/Ingestion。这样 Mapper 失败或业务过滤不会擦除“Provider 曾返回什么、为什么没入库”的可追溯事实。

## 14. 决策 N：API 只做短事务，Worker 执行长任务

API 创建父事实/Job、做查询和下载；分钟级采集、大批量 AI、导出等由 Worker 执行。HTTP timeout 不能成为长任务成败边界。

## 15. 决策 O：Artifact 先保证证据身份，再进入业务引用

Raw、输入、Chunk、导出等文件通过 ArtifactService/Store 管理；业务表引用 Artifact ID/metadata，不把临时宿主路径当稳定业务身份。未引用 Artifact 按生命周期清理，已引用 Artifact 受业务保留策略约束。

## 16. 决策 P：运行时 Analysis Scheme 以数据库唯一 active 版本为完整事实

仓库 Prompt 只承担空库 bootstrap/灾备基线；实际运行冻结 active Analysis Scheme、Prompt/Taxonomy hash、模型和生成配置身份。前端 Taxonomy 通过正式只读 Contract 获取，不复制一套枚举。

## 17. 决策 Q：人工相关性复核与 AI 原判分层

AI 原判保留审计；查询层使用有效相关性及来源投影。人工复核针对当前 Content Version，有撤销/继承 AI 的正式语义；前端不重写后端状态机。

## 18. 决策 R：Analysis Run 冻结目标，Planner/Shard 有界执行

新 Analysis Run 冻结目标 Content Version 和运行身份，由 Planner 有界创建 `analysis.content-label.v1` Shard Job。Worker 不在执行时重新解释“现在最新内容”。较新的用户意图不能被较早 Run 更晚完成后反向覆盖。

## 19. 决策 S：AI irrelevant 的离线与数据库保留语义不同

离线 JSONL 可把 irrelevant 从最终业务文件移除并在 checkpoint 保留恢复事实；正式 PostgreSQL 保留 Content/Raw/History 与 Analysis Result，通过默认查询/导出语义排除，不物理删除 Content。

## 20. 决策 T：File Import 不伪造 Collection Run/Scope/Candidate

兼容单文件 Import 和统一 Data Import Campaign 都有自己的真实父事实，最终经过 Reader/Mapper/Canonical/Content Owner。不能为了表结构对称制造假的 Collection Run/Scope/Candidate。

## 21. 决策 U：Excel 只有一个 Provider-neutral 共享 Exporter

正式 PostgreSQL Export、离线调试等复用同一 Excel Contract/Renderer。调用方可以选择已有列/顺序，但不能复制 Workbook、字段语义、Formula Injection、ID 和样式规则。

## 22. 决策 V：正式 Excel Export 冻结 Content Version

创建 Export 时冻结目标 Content ID/Version/Ordinal，Worker 严格读取冻结版本；队列等待期间 Current 更新不改变用户提交时的导出语义。

## 23. 决策 W：离线 Word 报告消费统一 Excel，不建立第二套业务事实

当前 Word 报告从统一 Excel 形成 Report Context，再生成 Markdown/DOCX。它不直接 SQL、不重新调用 LLM、不拥有新的 Content/Analysis Schema；当前没有正式 Web Report PostgreSQL Job/API。

## 24. 决策 X：ArtifactService 与 ArtifactStore 分层

ArtifactService 负责业务 ID、metadata、lifecycle、linking；ArtifactStore 只负责 `storage_key ↔ bytes`。未来替换 S3/MinIO 只能替换 Store Adapter，不改变业务 Artifact Contract。

## 25. 决策 Y：业务授权使用 Provider-neutral Principal，飞书仅作为 Identity Adapter

当前角色只有 `administrator` 和 `user`。管理员配置写操作由后端校验角色；前端 Route 守卫不能替代授权。本地 Development Identity 不是 Production 认证。

未来企业身份固定走：

```text
Feishu / 其他正式 IdP
→ 验证 Claims
→ Identity Adapter
→ Principal
→ 后端 Authorization
```

业务表不以 `feishu_open_id/union_id` 等 Provider 私有身份作公共主键。真实企业登录、会话、撤销/过期属于 Production L3 门禁。

## 26. 决策 Z：应用文件日志是主要人工排障入口

API/Worker/Scheduler 继续保留可轮转 `.log` 并辅以 stdout。日志必须保持北京时间可读时间、稳定 event、真实调用位置、结构化上下文、Secret/PII 递归脱敏和长度边界。

## 27. 决策 AA：离线 Release 基础已实现，完整 Production 仍未闭环

当前 [`.github/workflows/release.yml`](../../.github/workflows/release.yml) 已建立 Linux/AMD64 Backend/Frontend + PostgreSQL 镜像 Bundle、`images.tar`、manifest、`SHA256SUMS`、`DEPLOY.md` 和 `--no-build --pull never` 回放，正式路径具备 GHCR digest、Tag/Release 基础。

仍未完成的 Production 门禁包括企业认证/HTTPS、协调 Backup/Restore、SBOM/独立签名/provenance、生产服务器发布/回滚和真实生产安全/容量/恢复验收。详见 [`docs/roadmap/02_生产上线实施路线.md`](../roadmap/02_生产上线实施路线.md)。

## 28. 决策 AB：调试入口必须复用生产实现

`tikhub_test`、`imports_test`、Mapper/Provider Probe、Ingestion 调试只能改变触发方式和人工输出，不复制正式 endpoint、pagination、Mapper、去重、AI、Excel 或 Content SQL。

## 29. 决策 AC：正式文档按职责分层

当前长期结构：

```text
docs/README.md
→ 总导航与 Source of Truth

docs/product/
→ 当前产品能力与用户语言

docs/blueprint/01—08
→ 长期架构/稳定跨模块边界

docs/01—04
→ 开发、运行、API、测试快速入口

docs/appendix/ + docs/collection/
→ 深入技术专题与 Provider 实测

docs/guides/
→ 开发/协作操作

docs/operations/
→ 部署、Release、生产迁移运行手册

docs/roadmap/
→ 已批准且尚未完成的目标

changes/archive/ + Git
→ 历史施工、决策与验收证据
```

不新增第二套 docs history/archive；已完成 Stage 从 live docs 退出前先迁移仍有效知识。

## 30. 决策 AD：正式文档必须能导航到事实和实践

技术文档应说明问题、输入输出、调用链、Owner、失败/恢复、修改入口、验证方法和当前限制。完整 Schema/OpenAPI/Taxonomy/generated client 等高频漂移精确事实不复制第二份；直接导航机器事实。

## 31. 决策 AE：历史迁移只补空值，非空冲突不覆盖

`historical_fill_only` 命中已有业务身份时：Current 字段为空才允许补齐；非空相同不推进新鲜度；非空不同保留 Current 并记录冲突；历史空值不能清空 Current。无可信来源观测时间的历史 Metric 不伪造成当前观测。

该策略必须由每个 Campaign 冻结的版本化 payload 显式启用，并继续经过 Mapper → Canonical → Content Owner；临时 SQL/外部 ETL 不得绕过 Owner。

## 32. 决策 AF：数据导入统一入口，来源与写入策略正交

用户只看到一个“导入数据”入口：

```text
source_kind
→ local_upload / server_path

ingestion_policy
→ standard_observation / historical_fill_only
```

来源决定文件如何形成不可变 Artifact；策略决定进入 Content Owner 后的写入语义。两维分别选择并冻结，禁止从来源静默推导业务语义。4000 万容量结论目前只覆盖 `server_path + historical_fill_only`。

## 33. 完整生产与 4000 万执行是不同 Roadmap

Production Hardening 负责认证、HTTPS、Backup/Restore、供应链和生产上线门禁；4000 万 Roadmap 负责目标服务器容量、生产写授权、正式 Campaign 和全量对账。二者可以有依赖，但不能用“历史导入完成”证明 Production Go-Live，也不能用“Production 能运行”证明 4000 万数据已迁移。

## 34. 改变长期决定的最低门禁

涉及模块拆分、数据库种类、Canonical、Content 身份、表 Owner、Job Runtime、Scheduler misfire、Provider Retry、API fallback、AI 枚举/数据保留、正式认证、Backup/Restore、统一导入语义等长期边界时，至少：

1. 从当前代码/Contract/Migration/测试恢复事实；
2. 建立与风险相称的 L2/L3 Change；
3. 存在实质取舍时给出 2–3 个真实方案及代价；
4. 明确业务/Owner 上游决定；
5. 同步 Contract/Schema/Migration/兼容设计（适用时）；
6. 做与变更相称的 Red → Green → Refactor；
7. 同步当前文档 Owner；
8. 在 PR 最新 HEAD 取得完整相关 CI；
9. 完成独立 Review、合并和 Change 归档。

普通任务不得以“顺手优化”为理由绕过这些边界。
