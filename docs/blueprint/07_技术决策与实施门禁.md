# 技术决策与实施门禁

本文只记录**已经影响多个模块、普通任务不能静默改变的长期决定**。

它不是：

- 第二份完整架构说明；
- 所有表/接口字段清单；
- 历史 Stage 进度日志；
- 未来功能愿望清单。

每条决定都应能落到当前代码、Contract、Migration、锁文件或测试。某个任务确实要改变这里的决定时，通常至少是 L2，涉及 API/Schema/安全/破坏性兼容时通常是 L3。

---

# 1. 当前事实和本文发生冲突怎么办

优先顺序：

```text
本轮用户明确批准的上游决定 / 正式 Change
→ 当前代码、Contract、Migration、generated、tests、locks
→ 本文已确认跨模块决定
→ 对应领域 Blueprint
→ 模块 README / Appendix / Guide
→ 历史 Change / 聊天
```

但不能看到代码和本文不一致就自动让本文追随代码。

先判断：

```text
代码误实现？
→ 修代码

设计已经正式改变，但本文落后？
→ 修本文

没有足够证据？
→ 先调查/提请决策
```

# 2. 决策 A：模块化单体，不先拆微服务

当前固定：

```text
一个仓库
一个 PostgreSQL
一套业务 Contract
模块化单体
API / Worker / Scheduler / Migration 分进程
```

真实代码：

```text
backend/src/aima_ugc/entrypoints/
backend/src/aima_ugc/bootstrap/
backend/src/aima_ugc/modules/
```

为什么：

- 当前主要耗时来自 Provider/LLM/数据库，不是模块函数调用；
- PostgreSQL 同事务能可靠提交 Job + 业务父事实；
- 单仓更容易维护 Contract/Migration/测试；
- API/Worker/Scheduler 分进程已经隔离主要运行风险。

普通任务禁止因“可扩展”引入：

```text
Redis
Kafka
RabbitMQ
MongoDB
OpenSearch
Kubernetes
微服务 RPC
```

什么时候可以重新评估：有可测的数据库争用、单体发布组织瓶颈、单机容量/恢复瓶颈，并且先优化现有边界仍无法解决。

# 8. 决策 G：Canonical 不保存 AI 派生事实

Canonical 只表达外部可观察 UGC 事实。

AI：

```text
relevance
voice_type
sentiment
labels
```

属于 Analysis Domain。

当前 PostgreSQL：

```text
analysis_content_results
analysis_content_label_pairs
analysis_content_relevance_reviews
```

`contents` 当前没有：

```text
is_relevant
voice_type
sentiment
primary_label
secondary_label
```

平行 AI 列。

改变这一边界是跨域 Schema/Contract 决策，不能为页面查询方便直接加列。

人工对 AI 相关性的纠正也属于 Analysis Domain：不得 UPDATE/DELETE `analysis_content_results.relevance`，也不得向 `contents` 加平行布尔列。`analysis_content_relevance_reviews` 是按 `content_id + content_version` 追加的人工决定账本，`review_no` 决定同一版本事件顺序，`decision` 只允许 `relevant / irrelevant / inherit_ai`。最新 `relevant/irrelevant` 会覆盖该版本的 AI 业务相关性，`inherit_ai` 表示撤销人工覆盖并回到当前 AI 基线；已有人工覆盖要改成相反人工结论时必须先撤销，不能一次请求隐式改写历史。模型原始结果始终保留，新 Content Version 不继承旧版本人工决定。`GET /api/v1/contents` 返回的 `effective_relevance / relevance_source` 只是 Query Repository 从 AI 原判和最新人工事件计算出的只读投影，不是新的数据库写事实；即使当前 AI 因 Prompt/Model 身份变化进入 `stale`，活动人工覆盖仍可被识别和撤销。

# 10. 决策 I：外部 HTTP 不放在数据库事务里

禁止：

```text

→ SELECT ... FOR UPDATE
→ 等 TikHub 10 秒
→ UPDATE
→ COMMIT
```

```text

→ commit
→ 外部 HTTP
→ 保存 Raw/调用结果
→ 短事务提交业务结果
```

这样避免长时间持锁和数据库连接占用。

# 12. 决策 K：业务父事实与必须触发的 Job 同事务创建

例如：

```text
Import Batch + Import Job
Data Import Campaign/Item + Discover/Snapshot/Chunk Job（按各阶段事务边界）
Analysis Run + Planner Job
Analysis Request/Shard + Label Job
Export + Export Job
Scheduled Occurrence + Run + Job
```

必须在各自设计的 PostgreSQL Unit of Work 中原子提交“业务父事实 + 本阶段必须存在的 Job”，不能留下已经可见但永远无人执行的业务父记录。

禁止：

```text
先 commit 业务父记录
→ 再另一个事务 enqueue 本阶段必须触发的 Job
```

否则中间崩溃会留下“永远没人执行”的业务记录。

# 17. 决策 P：已发布 Analysis Scheme Version 是运行时唯一配置事实

当前运行时把 Prompt 模板、相关性规则、情感、`voice_type`、一级/二级标签和 Validator 所需 Taxonomy 作为一个不可拆分的 Analysis Scheme Version 管理。管理员只能保存草稿、发布一个完整版本或回滚到一个完整历史版本；不能分别激活 Prompt 和分类枚举。草稿保存也追加新版本并退役旧草稿，避免并发编辑静默覆盖。

首次部署到空数据库时，系统从下列 Git 文件建立并审计一个发布版：

- [`backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md`](../../backend/src/aima_ugc/modules/analysis/prompts/content_labeling_v3.md)

完成 bootstrap 后，数据库中的唯一 active Scheme Version 是新 Run、查询 Taxonomy 和 Worker 的运行事实；Git 文件只承担初始化/灾备基线，不与数据库形成双写主事实源。每个 Run 冻结 `analysis_scheme_version_id`、编译后的 Prompt 快照和 Hash，后续发布不改变历史 Run。

Python 负责结构校验、受控 Taxonomy 占位符编译、Hash、membership、父子标签关系和 Retry；数据库负责版本、active 指针和审计。

禁止在：

```text
Python
Blueprint
Excel 文档
Frontend
```

复制一套完整标签表长期维护。

`voice_type` 的合法机器值直接使用中文业务名称，同样不得在 Blueprint 复制；当前集合以 active Scheme Version 为准，初始集合和规则来自上述 Git bootstrap 文件。Python Contract 和数据库只保留结构约束，运行时 Validator 对 Run 冻结版本执行 membership。

真实用户发声唯一判断：

```text
voice_type == "真实用户发声"
```

# 26. 决策 Y：业务授权使用 Provider-neutral Principal，飞书仅预留 Adapter

当前已建立统一 `Principal/AuthContext` 边界，角色只允许 `administrator` 和 `user`。车型、词包、全局相关性、采集计划和 Analysis Scheme 等配置写路由由后端校验管理员角色；业务只读目录仍可供普通用户页面消费。前端路由守卫只改善交互，不能代替后端授权。

本地开发通过 development Identity Adapter 提供 Principal；企业身份尚未接入，后续固定走：

```text
Feishu
→ Identity Adapter
→ Principal/AuthContext
→ 后端 Authorization
```

业务表不提前绑定：

```text
feishu_open_id
union_id
```

等 Provider 私有身份为主键。

第一版不强制双人审批；所有发布、回滚和配置修改必须在同一业务事务写入 `audit_events`，审计只保存 Principal、请求身份、对象身份和安全差异/Hash，不保存 Prompt 全文或 Secret。

# 33. 决策 AE：历史迁移只补空值，非空冲突不覆盖

2026-08-26 为 Stage 12 4000 万历史数据迁移确认以下长期业务写入边界：

```text
历史数据命中新业务身份
→ 按当前 Content 身份规则创建 Current + 初始 Version

历史数据命中已有业务身份
→ Current 字段为空：允许补齐
→ Current 字段非空且相同：不写 Current、不推进字段新鲜度/last_seen_at
→ Current 字段非空且不同：保留 Current，冲突留痕
→ 历史字段为空：不得清空 Current
```

该规则适用于 Content、Author 和历史输入实际承载的稳定扩展事实。没有可信来源观测时间的历史 Metric 不得伪造当前观测时间后更新 Current/Metric。

历史规则只能由每个 Data Import Campaign 冻结的 `historical_fill_only` 策略通过版本化 Job Payload 显式启用；选择本地或服务器来源本身不能改变写入语义。`standard_observation`、Collection、补采和其他标准摄取继续使用既有字段级新鲜度语义。实现必须经过 Mapper → Canonical → Content Owner，并由逐行来源账本证明 `created / filled / updated / unchanged / conflict / filtered / duplicate / invalid / failed` 中适用的终态，不能用临时 SQL 或外部 ETL 绕过 Owner。

详细实施、容量与回滚门禁见 [`docs/roadmap/03_4000万历史数据迁移实施方案.md`](../roadmap/03_4000万历史数据迁移实施方案.md)。


# 34. 决策 AF：数据导入统一入口，来源与写入策略正交

2026-08-27 确认采集运行中心只保留一个用户可见“导入数据”入口。统一的不是让浏览器和服务器共享路径权限，而是让两种来源在形成不可变 Source Artifact 后共用同一个 Campaign、预检、Chunk、Job、进度、取消、重试和逐行账本：

```text
source_kind
→ local_upload：浏览器显式多选文件或选择文件夹；只上传安全相对路径和文件字节
→ server_path：只枚举管理员批准、只读挂载根目录；HTTP 只收发相对路径

ingestion_policy
→ standard_observation：普通字段新鲜度、Version 与可信 Metric 语义
→ historical_fill_only：决策 AE 的只补空、不覆盖与冲突留痕语义
```

两维必须在 Campaign 创建时分别选择并冻结，禁止从来源静默推导不可变业务语义，也禁止用全局开关切换所有导入。页面可以给出“本地默认标准观测、服务器默认历史补空”的可修改初始建议。

浏览器不会获得本机绝对路径，也不能在用户只选择一个文件后扫描它的父目录；本地目录递归必须使用浏览器显式文件夹选择器。服务器目录能力继续拒绝绝对路径、路径逃逸、符号链接/Junction/Reparse Point 和文件管理操作。

既有 `/api/v1/import-batches` 与 `/api/v1/historical-import-*` 在兼容期保留，当前页面只使用 `/api/v1/data-import-*`。数据库表、Job type 和内部文件沿用 `historical_*` 物理名称，以避免为了命名产生高风险 Schema/运行时迁移；这不构成第二业务入口。

4000 万历史迁移的容量和生产授权只覆盖 `server_path + historical_fill_only`。`standard_observation` 虽共用有界 Chunk 和账本，但当前逐记录复用 Content Owner，未通过 4000 万吞吐门禁；不得把“统一入口”解释为所有组合具有相同容量承诺。
