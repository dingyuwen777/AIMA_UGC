# 采集策略与平台能力

本文解释当前 AIMA_UGC **怎样把“业务想采什么”翻译成每个平台真正支持的 TikHub Operation，以及何时继续抓 Detail / Comments / SubComments，何时停止，为什么不同平台不能共用一套假想参数。**

如果要直接改平台代码，配合阅读：

- [`docs/appendix/02_TikHub五平台真实响应与字段映射.md`](../appendix/02_TikHub五平台真实响应与字段映射.md)
- [`docs/appendix/03_TikHub多接口验证与备用策略.md`](../appendix/03_TikHub多接口验证与备用策略.md)
- [`docs/collection/README.md`](../collection/README.md)

## 1. 先区分 Provider Config、Platform、Capability、Operation

这四个概念不是一回事。

```text
Provider Config
→ “用哪个 TikHub 实例/账号配置？”

Platform
→ xiaohongshu / douyin / weibo / bilibili / kuaishou

Capability
→ “这个 Provider + Platform 当前支持哪些业务动作/参数？”

Operation
→ “某个业务动作具体调用哪个 Endpoint、怎么分页、怎么取 item？”
```

当前关系：

```text
Provider Config
  ├─ id
  ├─ provider=tikhub
  ├─ base_url
  ├─ secret_ref
  └─ enabled
        │
        ▼
Plan / API Run 选择 provider_config_id + platform
        │
        ▼
Provider Registry
        │
        ▼
TikHub Capability
        │
        ▼
Operation Builder / Pagination / Extractor
        │
        ▼
Raw → Mapper → Canonical
```

Provider Config 代码/表主要由 System Owner 管理；当前 Capability 机器事实：

- [`backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py)

## 2. 为什么前端不能自己维护平台 `if/else`

错误做法：

```ts
if (platform === 'xiaohongshu') {
  showTimeFilter()
}
if (platform === 'bilibili') {
  showTimeFilter()
}
```

问题：B站当前主 Search 的 `native_time_filter=false`，而 xiaohongshu 为 true；平台 API 变化后前端静态表也会漂移。

正确方向：

```text
后端 Capability
→ Pydantic HTTP Contract
→ OpenAPI
→ generated Client
→ 前端按 Capability 展示合法选项
```

当前 Capability 公开：

```text
business_operation
provider_operations
supported_sort_modes
supported_time_filters
supported_duration_filters
supported_content_types
native_time_filter
observes_comment_count
comment_sort_modes
supports_reply_count
supports_sub_comments
supports_incremental_comment_sort
provider_page_size_policy
```

精确字段：

```text
backend/src/aima_ugc/contracts/collection/
```

当前 HTTP `CollectionCapabilityResponse.search` 只投影前端真正需要的四组合法值：排序、发布时间、时长、内容类型，并携带 `manual_default`。公共请求统一使用 `CollectionSearchConfig`，不暴露 Provider 私有的 `search_type`、cursor、`search_id` 或 endpoint 参数。

# 5. Comments Capability 真实差异

当前机器事实：

| 平台 | Comment sort | reply_count | sub comments | incremental comment sort |
| --- | --- | --- | --- | --- |
| xiaohongshu | `latest` | 是 | 是 | **是** |
| Douyin | 当前不公开额外 sort | 是 | 是 | 否 |
| Weibo | `hot` / `latest` | 是 | 是 | 否 |
| Bilibili | `latest` / `hot` | 是 | 是 | **是** |
| Kuaishou | 当前不公开额外 sort | 是 | 是 | 否 |

这张表直接来自 [`backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py)。

## 为什么只有 xiaohongshu / B站声明 incremental

`supports_incremental_comment_sort=true` 的含义不是：

> 这个接口有 cursor，所以可以增量。

而是：

> 当前正式 Operation、排序参数和真实样本足以支持“从最新开始，遇到已知稳定 Comment ID 后安全停止后续页”。

当前：

```text
xiaohongshu
→ latest comment operation
→ capability=true

Bilibili
→ latest mode + 已验证分页/时间排序
→ capability=true
```

当前 Douyin/Weibo/Kuaishou 均为 false，所以不能在通用 Decision 里把它们当成同样的“最新评论增量流”。

# 6. 统一 Decision Pipeline

发现一条 Search item 后，并不是直接无脑抓完所有详情和评论。

当前长期流程：

```text
SEARCH
→ 保存 Search Raw
→ Candidate
→ Search Mapper / Canonical Observation
→ Rule Relevance
→ Identity / Compare
→ Decision Pipeline
   ├─ 是否需要 Detail
   ├─ 是否需要 Comments
   └─ 是否需要 SubComments
→ durable content action/checkpoint
→ Provider Request / Attempt / Raw
→ Candidate / Mapper / Canonical
→ Content Ingestion
→ 完成 action/checkpoint
```

Decision 代码：

- [`backend/src/aima_ugc/modules/collection/decision.py`](../../backend/src/aima_ugc/modules/collection/decision.py)

持久执行账本：

```text
collection_content_actions
```

生产串联：

- [`backend/src/aima_ugc/bootstrap/collection_scope.py`](../../backend/src/aima_ugc/bootstrap/collection_scope.py)

为什么 Action 要持久化：Worker 崩溃后需要知道：

```text
Detail 是否已经发过？
Comments 是否已经完成？
哪一步有可复用 Raw？
恢复时应该继续哪一步？
```

不能只靠内存变量。

# 7. Rule Relevance 如何进入 Collection

当前全局 Rule Relevance：

```text
global_relevance_config
→ Keyword Pack
→ effective_keywords
```

Run 创建时冻结：

- Pack ID；
- Pack Version；
- Config Version；
- 最终有效关键词。

执行时不再读取一套变化后的全局配置。

Search Observation 先判断 Rule Relevance。

如果 Search 卡片字段不足以终判，生产链可以按当前 Decision/运行实现使用 Detail 重新 Mapper 后终判；如果 Detail 已为相关性判定获取，后续需要 Detail 时复用它，不重复请求同一候选详情。

最终规则无关：

```text
Raw 保留
Candidate 保留
filtered 来源账本保留
Content 不写入
Comment/Reply 不继续请求
```

这和 AI Semantic Relevance 完全不同。

# 8. Detail 决策怎么理解

不是每次 Search 都必须 Detail。

是否需要 Detail 取决于：

- Search 卡片字段是否已经足够；
- 新内容/旧内容；
- `detail_policy`；
- Current 已有事实；
- 指标/字段变化；
- Relevance 是否需要补充正文终判；
- 已有 Action/Raw 是否可恢复。

关键原则：

```text
需要更多事实才发 Detail
而不是“搜索到了就固定发一次 Detail”
```

当前默认 `detail_policy` 的精确合法值和算法以 `planning.py / decision.py` 为准；普通前端配置不能绕过后端 Capability/Domain 校验。

# 9. Comments 决策为什么依赖 `comment_count` 和 Coverage

评论请求成本通常比 Search 更容易放大。

当前决策会综合：

- Provider 是否允许 Comments；
- Search/Detail 是否真实观察到 `comment_count`；
- Current comment_count 是否变化；
- 最近 Coverage；
- `comment_policy`；
- incremental capability；
- 已持久化 Action/Checkpoint。

如果 Provider 本次根本没返回 comment_count：

```text
unknown
```

不能当：

```text
0
```

也不能用“数据库里评论条数”冒充 Provider 报告总数，因为数据库可能只采了 partial。

# 10. Comment Coverage 如何影响后续刷新

当前 Coverage：

```text

partial
not_requested

```

并记录：

```text

collected_count

stop_reason

```

典型逻辑：

```text
上次 complete
+ Provider comment_count 没变化
→ 不必重复抓全部评论

上次 partial
+ 业务需要更完整覆盖
→ 可以继续刷新/补采

Provider 当前不可评论
→ unavailable / not_requested
→ 不伪装 complete
```

# 11. 增量评论怎样安全停止

只有 Capability 明确：

```text
supports_incremental_comment_sort = true
```

才允许按“最新评论优先 + 已知 Comment ID 边界”做增量停止。

通用语义：

```text
请求第一页 latest comments
→ 当前页完整 Raw 保存
→ 当前页所有 items 先 Mapper/Ingest
→ 如果遇到可靠 known_comment boundary
→ 不再请求下一页
```

边界不能用：

- 评论文本；
- 作者名；
- 时间相等；

只能使用稳定 Comment ID/明确分页语义。

即使当前页已经命中旧 Comment，也要先处理本页其他新评论；“遇到一条旧评论立即 break 当前页”可能漏掉同页后面的新项。

---

# 12. 非增量平台怎样刷新评论

Douyin / Weibo / Kuaishou 当前：

```text
supports_incremental_comment_sort = false
```

意味着不能用统一 known-comment stop 假装安全增量。

当前应：

```text
按 Decision/技术上限执行受控刷新
→ 保存实际 Coverage
→ 不把 partial 写 complete
```

如果以后真实证明某个正式 Operation 支持可靠 newest-first 增量：

```text
Real Fixture / A-B
→ Operation/Capability
→ Incremental Tests
→ 再改 capability=true
```

不是改一个布尔就完成。

# 13. 二级回复怎样决定

只有：

```text
supports_sub_comments = true
```

才允许进入 SubComments/Replies Operation。

根评论还需要有真实回复存在证据，例如：

- `reply_count > 0`；
- Provider 明确给出可展开回复；
- 当前 Operation 返回结构可证明存在 thread。

不能：

```text
每条根评论都盲目请求二级回复
```

快手尤其要区分：

```text
subCommentCount       → integer 实际回复数

displaySubCommentCount
→ boolean UI 显示信号
→ 不能当回复数
```

详细字段见 TikHub 字段附录。

# 14. 分页技术上限不是业务完整度

每个 Operation 必须有防死循环/无限账单的安全上限，例如：

- Search 最大页；
- Comments 最大页；
- SubComments 最大页。

这些技术值由当前执行限制代码/配置决定，并可冻结到 Run Snapshot。

达到上限：

```text
stop_reason = safety/page limit
coverage = partial（如果未证明完整）
```

禁止：

```text
因为程序主动停了
→ 写 complete
```

完整与否由真实业务证据决定，不由“代码没报错”决定。

# 15. Scheduler 策略和采集策略不是同一层

Scheduler 只决定：

```text
什么时候创建一个 Run
```

Collection Decision 决定：

```text
这个 Run 内某一 Content 下一步还要不要 Detail/Comments/Replies
```

当前 Scheduler：

```text
Asia/Shanghai
latest_only
max_catch_up_runs=0
```

详见：

[`docs/appendix/05_Scheduler调度执行与停机恢复.md`](../appendix/05_Scheduler调度执行与停机恢复.md)

不要因为 Scheduler 6 小时一次，就得出“每条旧 Content 6 小时抓一次详情和全部评论”。

# 16. 当前 API/前端如何配置采集

当前产品面主要分两块。

## 16.1 `/collection-strategy`

真实前端 Feature：

```text
frontend/src/features/collection-strategy/
```

后端：

- [`backend/src/aima_ugc/bootstrap/collection_strategy_http.py`](../../backend/src/aima_ugc/bootstrap/collection_strategy_http.py)

负责：

- Keyword Pack；
- Global Relevance；
- Collection Plan；
- Plan enabled 状态。

新建 Plan 时，每个已选平台必须根据 `CollectionCapabilityResponse.search` 显式完成所有受支持维度；后端再按同一 Capability 校验并把配置写入 `collection_plan_platforms.config`。只有一个合法选项的维度可以由界面直接固定，多选维度必须由用户选择。

升级前已经存在的 Plan 可能保存 `config={}`。它们继续可读、可重新启用、可被 Scheduler 执行，并沿用原先 Adapter 默认值；本次变化不做数据迁移，也不把历史 Plan 改写成新默认。

## 16.2 `/collection-runtime`

真实前端 Feature：

```text
frontend/src/features/import-batches/
```

后端：

- [`backend/src/aima_ugc/bootstrap/collection_http.py`](../../backend/src/aima_ugc/bootstrap/collection_http.py)
- [`backend/src/aima_ugc/adapters/persistence/postgres/collection_runtime_queries.py`](../../backend/src/aima_ugc/adapters/persistence/postgres/collection_runtime_queries.py)

负责：

- Excel Import 运行记录；
- TikHub Discovery Run；
- Batch Supplement Run；
- 进度/状态/统计；
- 手工创建 Run。

手工 Discovery 打开后，前端使用后端 Capability 提供的 `manual_default` 初始化逐平台参数，默认意图是：

```text
latest + 1d + all
```

平台不支持某个维度时不伪造该参数，例如没有原生时间筛选的平台不会发送 `1d`。用户可以在提交前逐平台调整；即使旧 Client 不传 `search_config`，后端仍会补齐同一默认并把最终值冻结到 Run Provider Snapshot。Batch Supplement 不使用 Search 参数，也不接受 `search_config`。

这两类页面只操作业务语义，不让用户直接填 Provider cursor、`search_id`、endpoint URL 或 Pricing。

# 17. Provider Secret 和 Base URL 的边界

Provider Config 可以保存：

```text
provider
base_url
secret_ref
enabled
```

不能保存明文：

- API Key；
- Authorization；
- Cookie；
- Password。

Transport 只有在目标 Origin 通过 Adapter 安全校验时才附带 Secret。

可配置 `base_url` 不等于任意 URL 都允许；不能通过 Provider 配置制造 SSRF。

# 18. Pricing / Billing 为什么不属于普通业务参数

当前 TikHub Pricing：

- [`backend/src/aima_ugc/adapters/providers/tikhub/pricing.toml`](../../backend/src/aima_ugc/adapters/providers/tikhub/pricing.toml)

Request/Attempt 可以保存价格/费用审计事实。

业务页面不应该提供：

```text
“这个 endpoint 每次多少钱”可编辑输入框
```

否则用户配置可能和真实 Provider Price Snapshot 事实冲突。

当前没有：

- 请求次数预算；
- 金额预算；
- 发送前 Cost Guard；
- Budget Account / Reservation Ledger。

如果未来产品化预算，需要单独设计。

# 19. TikHub API family 候选为什么不放进 Capability

例如当前代码存在：

- Douyin Search V1 Candidate；
- Weibo App Search Candidate；
- Bilibili Web Candidate；
- Kuaishou Web Comments backup；
- xiaohongshu App V1/Web V3 Search Candidate。

这些只是：

```text
显式 A/B / 备用验证入口
```

生产 Capability 只登记当前主链。

原因：Capability 是业务承诺。如果把所有“能构造 HTTP 请求”的 Candidate 都写进 Capability，前端会把未经真实闭环的接口暴露成正式产品能力。

验证方法：

[`docs/appendix/03_TikHub多接口验证与备用策略.md`](../appendix/03_TikHub多接口验证与备用策略.md)

# 20. 修改一个平台 Capability 应该怎么做

例如要让 B站支持原生时间筛选。

不能只改：

```python
native_time_filter=True
```

必须先证明：

```text
当前正式 Search Operation
→ TikHub 参数确实支持对应时间范围
→ Request Builder 能表达
→ Real Fixture/Probe 证明结构可用
→ Pagination 不受破坏
→ Contract/Capability Test
```

然后才修改 Capability。

同样：

- 打开新 content_type；
- 增加 sort；
- 声明 comment_count；
- 开启 incremental；

都必须有生产 Operation/真实响应证据。

# 24. 验收平台采集策略时至少检查

- Capability 与正式 Operation 一致；
- Capability 只公开真实证明过的选项；
- Provider Config 禁用时关闭失败；
- Secret 不进入业务配置/日志；
- Rule Relevance 使用冻结 Snapshot；
- Candidate / Raw 保留；
- Decision Pipeline 有持久 Action/Checkpoint；
- Detail 不无条件重复请求；
- Comment Coverage 不伪装完整；
- incremental 只对 capability=true 平台启用；
- Replies 只对真实支持平台/根评论触发；
- 技术页数上限不会被写成 complete；
- Retry 创建新 Attempt；
- 已有完整 Raw 的恢复不重发；
- Pricing/Billing 事实可审计但当前不声称 Budget Guard。

# 25. Batch Supplement 的身份与资格边界

基于 Excel Import Batch 的补采不是“Batch 里有 Content 就能请求 TikHub”。创建 Run 前必须同时满足：

```text
Content 属于目标 Import Batch
+ 当前 AI Analysis identity 未明确判为 irrelevant
+ Content 存在当前正式 Runtime 可消费的 typed Provider lookup identity
+ 所选 Provider Config / Platform Capability 支持本次操作
```

前端通过专用只读资格接口读取每个平台真实 `target_count`，不再用声音广场列表或 `relevance=irrelevant` 二次查询猜资格；后端 `create_run()` 仍重新冻结同一事实作为最终守卫。

当前首次 Batch Supplement 固定执行 Content Detail；一级评论默认可选开启，二级回复依赖一级评论。即：

```text
Detail（固定）
→ Comments（可选）
→ SubComments（可选，依赖 Comments）
```

当前不支持 Comment-only Supplement。以后若要对“详情已成功、评论失败/需刷新”的 Content 单独刷新评论，应建立独立 Change，复用已确认 Provider Content ID，而不是默认重复 Detail。

短链/分享链即使 Provider 提供 URL Detail 接口，也只有在系统能够把解析得到的原生 ID 安全固化并保证仍收敛到原 Content 后，才能成为普通 Batch Supplement 入口；在此之前识别并保留链接，但付费补采关闭失败。
