本文解释当前 AIMA_UGC **怎样把“业务想采什么”翻译成每个平台真正支持的 TikHub Operation，以及何时继续抓 Detail / Comments / SubComments，何时停止，为什么不同平台不能共用一套假想参数。**

## 1. 先区分 Provider Config、Platform、Capability、Operation

这四个概念不是一回事。

```text
Provider Config
→ “用哪个 TikHub 实例/账号配置？”

Platform
→ xiaohongshu / douyin / weibo / bilibili / kuaishou

Capability
→ “这个 Provider + Platform 当前支持哪些业务动作/参数？”

Operation
→ “某个业务动作具体调用哪个 Endpoint、怎么分页、怎么取 item？”
```

当前关系：

```text
Provider Config
  ├─ id
  ├─ provider=tikhub
  ├─ base_url
  ├─ secret_ref
  └─ enabled
        │
        ▼
Plan / API Run 选择 provider_config_id + platform
        │
        ▼
Provider Registry
        │
        ▼
TikHub Capability
        │
        ▼
Operation Builder / Pagination / Extractor
        │
        ▼
Raw → Mapper → Canonical
```

Provider Config 代码/表主要由 System Owner 管理；当前 Capability 机器事实：

- [`backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py)

## 2. 为什么前端不能自己维护平台 `if/else`

错误做法：

```ts
if (platform === 'xiaohongshu') {
  showTimeFilter()
}
if (platform === 'bilibili') {
  showTimeFilter()
}
```

问题：B站当前主 Search 的 `native_time_filter=false`，而 xiaohongshu 为 true；平台 API 变化后前端静态表也会漂移。

正确方向：

```text
后端 Capability
→ Pydantic HTTP Contract
→ OpenAPI
→ generated Client
→ 前端按 Capability 展示合法选项
```

当前 Capability 公开：

```text
business_operation
provider_operations
supported_sort_modes
supported_time_filters
supported_duration_filters
supported_content_types
native_time_filter
observes_comment_count
comment_sort_modes
supports_reply_count
supports_sub_comments
supports_incremental_comment_sort
provider_page_size_policy
```

精确字段：

```text
backend/src/aima_ugc/contracts/collection/
```

当前 HTTP `CollectionCapabilityResponse.search` 只投影前端真正需要的四组合法值：排序、发布时间、时长、内容类型，并携带 `manual_default`。公共请求统一使用 `CollectionSearchConfig`，不暴露 Provider 私有的 `search_type`、cursor、`search_id` 或 endpoint 参数。

## 为什么只有 xiaohongshu / B站声明 incremental

`supports_incremental_comment_sort=true` 的含义不是：

> 这个接口有 cursor，所以可以增量。

而是：

> 当前正式 Operation、排序参数和真实样本足以支持“从最新开始，遇到已知稳定 Comment ID 后安全停止后续页”。

当前：

```text
xiaohongshu
→ latest comment operation
→ capability=true

Bilibili
→ latest mode + 已验证分页/时间排序
→ capability=true
```

当前 Douyin/Weibo/Kuaishou 均为 false，所以不能在通用 Decision 里把它们当成同样的“最新评论增量流”。

# 6. 统一 Decision Pipeline

发现一条 Search item 后，并不是直接无脑抓完所有详情和评论。

当前长期流程：

```text
SEARCH
→ 保存 Search Raw
→ Candidate
→ Search Mapper / Canonical Observation
→ BrandVehicleResolver
→ Identity / Compare
→ Decision Pipeline
   ├─ 是否需要 Detail
   ├─ 是否需要 Comments
   └─ 是否需要 SubComments
→ durable content action/checkpoint
→ Provider Request / Attempt / Raw
→ Candidate / Mapper / Canonical
→ Content Ingestion
→ 完成 action/checkpoint
```

Decision 代码：

- [`backend/src/aima_ugc/modules/collection/decision.py`](../../backend/src/aima_ugc/modules/collection/decision.py)

持久执行账本：

```text
collection_content_actions
```

生产串联：

- [`backend/src/aima_ugc/bootstrap/collection_scope.py`](../../backend/src/aima_ugc/bootstrap/collection_scope.py)

为什么 Action 要持久化：Worker 崩溃后需要知道：

```text
Detail 是否已经发过？
Comments 是否已经完成？
哪一步有可复用 Raw？
恢复时应该继续哪一步？
```

不能只靠内存变量。

# 7. Search Terms 与 Brand Filter 如何进入 Collection

新建 TikHub Discovery 固定分成两套输入：

```text
Keyword Pack → Search Terms → platform × keyword Scope
Brand Scope → Brand/Vehicle Catalog Snapshot → Canonical 后过滤与分类
```

Vehicle Alias 只参与 `BrandVehicleResolver`，不会扩展为 Provider Search Query。Plan 和手工 Run 可以选择 0..N 个 Brand；空集合表示在任务创建时冻结全部 active Brand，显式 Brand 选择自动包含其全部 active Vehicle。Collection 创建 Contract 不再接收 `vehicle_model_ids`；车型仍可作为 Content 查询维度，但不是 Discovery Search Resource。

Run 创建时冻结：

- Pack ID、Pack Version 与逐词 Search Terms；
- Brand/Vehicle Catalog Version、Brand Scope、Brand/Vehicle/Alias；
- Provider Config 与 Decision Policy。

新建 Discovery 使用显式 TikHub 类型与评论策略的 `collection-run-config.v4`；已持久化的历史 v2 只按原冻结语义读取和恢复，不改写快照。旧 `collection-run-config.v1`、Global Relevance Snapshot、`global_relevance_config` 及其 API 已退出当前 Contract、Worker 和 Schema；Migration 在发现任何旧 Run 或旧表数据时会拒绝升级，避免静默改义或丢数。

### 7.1 配置资源生命周期不改写历史冻结事实

Keyword Pack、Collection Plan 和 Provider Config 都可以退出当前业务目录，但“停用”和“归档”语义不同：停用仍是当前可管理配置，归档则退出新的 Import/Scheduler/Plan/Provider 选择。恢复后保持停用，必须再次显式启用才参与运行。

历史 Run/Campaign 已冻结的 Pack/Plan/Provider 身份和版本不因后续编辑、归档、恢复或重命名漂移。永久删除采用保守资格：只要存在历史计划、运行、导入、Provider Request 等引用，就只允许保留归档记录。

Search Observation 先使用冻结 Brand/Vehicle Snapshot 判断是否命中监测对象。

如果 Search 卡片字段不足以终判，生产链可以按当前 Decision/运行实现使用 Detail 重新 Mapper 后终判；如果 Detail 已为相关性判定获取，后续需要 Detail 时复用它，不重复请求同一候选详情。

最终未命中：

```text
Raw 保留
Candidate 保留
filtered 来源账本保留
Content 不写入
Comment/Reply 不继续请求
```

这和 AI Semantic Relevance 完全不同；AI/人工 relevance 仍在 Analysis/查询层保留。

# 8. Detail 决策怎么理解

不是每次 Search 都必须 Detail。

是否需要 Detail 取决于：

- Search 卡片字段是否已经足够；
- 新内容/旧内容；
- `detail_policy`；
- Current 已有事实；
- 指标/字段变化；
- Brand/Vehicle Filter 是否需要补充正文终判；
- 已有 Action/Raw 是否可恢复。

关键原则：

```text
需要更多事实才发 Detail
而不是“搜索到了就固定发一次 Detail”
```

当前默认 `detail_policy` 的精确合法值和算法以 `planning.py / decision.py` 为准；普通前端配置不能绕过后端 Capability/Domain 校验。

# 9. Comments 决策为什么依赖 `comment_count` 和 Coverage

评论请求成本通常比 Search 更容易放大。

当前决策会综合：

- Provider 是否允许 Comments；
- Search/Detail 是否真实观察到 `comment_count`；
- Current comment_count 是否变化；
- 最近 Coverage；
- `comment_policy`；
- incremental capability；
- 已持久化 Action/Checkpoint。

如果 Provider 本次根本没返回 comment_count：

```text
unknown
```

不能当：

```text
0
```

也不能用“数据库里评论条数”冒充 Provider 报告总数，因为数据库可能只采了 partial。

# 10. Comment Coverage 如何影响后续刷新

当前 Coverage：

```text
complete
partial
not_requested
unavailable
```

并记录：

```text
reported_total
collected_count
sample_mode
sort_mode
target_count
stop_reason
observed_at
```

典型逻辑：

```text
上次 complete
+ Provider comment_count 没变化
→ 不必重复抓全部评论

上次 partial
+ 业务需要更完整覆盖
→ 可以继续刷新/补采

Provider 当前不可评论
→ unavailable / not_requested
→ 不伪装 complete
```

精确表结构：

- [`backend/src/aima_ugc/modules/content/tables.py`](../../backend/src/aima_ugc/modules/content/tables.py)

计划支持 `adaptive`（默认）和 `full` 两种评论策略。自适应对不超过默认根评论目标的内容尽量采完整，超过目标时采样；回复也使用默认采样目标。默认值与决策由 [backend/src/aima_ugc/contracts/collection/models.py](../../backend/src/aima_ugc/contracts/collection/models.py) 和 [backend/src/aima_ugc/modules/collection/decision.py](../../backend/src/aima_ugc/modules/collection/decision.py) 维护。已付费请求返回的整页都摄取，因此实际条数可能超过采样目标。采样达到目标不表示所有评论已采完整。

全量采集持续读取根评论和必要回复线程，未知数量也读取到接口结束；已确认数量为零时不请求评论并记录完整空覆盖。“上次采完整”需要根评论实际覆盖为 `complete`，所有当前必要回复线程也完整；根或任一线程为 `partial`、线程缺失或已知数量不匹配时，都继续补齐。该判断从 Content Owner 的既有 Coverage 聚合，`not_requested` 的跳过记录不覆盖已有实际采集结果；不建立另一张完整状态表。读模型入口为 [backend/src/aima_ugc/adapters/persistence/postgres/content_coverage.py](../../backend/src/aima_ugc/adapters/persistence/postgres/content_coverage.py)。

全量在先前完整且本次已知评论数量相同时跳过；先前不完整时，即使数量相同也刷新。单条 Action 保存决策时使用的完整度输入，以便恢复继续解释同一次决策；它不是当前内容完整度的独立事实源。内容详情仍在变化时更新。评论数量相同不能证明评论正文从未编辑或删除，当前策略不承诺发现这种没有数量变化的外部变化。

# 11. 增量评论怎样安全停止

只有 Capability 明确：

```text
supports_incremental_comment_sort = true
```

才允许按“最新评论优先 + 已知 Comment ID 边界”做增量停止。

通用语义：

```text
请求第一页 latest comments
→ 当前页完整 Raw 保存
→ 当前页所有 items 先 Mapper/Ingest
→ 如果遇到可靠 known_comment boundary
→ 不再请求下一页
```

边界不能用：

- 评论文本；
- 作者名；
- 时间相等；

只能使用稳定 Comment ID/明确分页语义。

即使当前页已经命中旧 Comment，也要先处理本页其他新评论；“遇到一条旧评论立即 break 当前页”可能漏掉同页后面的新项。

全量只有先前根评论和必要回复全部完整时才进入可靠增量。命中稳定边界后，还要证明旧根集合与旧数量一致、旧集合与本次整页新项的并集符合当前报告数量，以及必要线程仍完整；证据充分才保存完整覆盖。证明不足时继续分页，若仍无法证明完整则保存 `partial`。自适应继续沿用原采样增量规则。

# 12. 非增量平台怎样刷新评论

Douyin / Weibo / Kuaishou 当前：

```text
supports_incremental_comment_sort = false
```

意味着不能用统一 known-comment stop 假装安全增量。

当前应：

```text
按 Decision/技术上限执行受控刷新
→ 保存实际 Coverage
→ 不把 partial 写 complete
```

如果以后真实证明某个正式 Operation 支持可靠 newest-first 增量：

```text
Real Fixture / A-B
→ Operation/Capability
→ Incremental Tests
→ 再改 capability=true
```

不是改一个布尔就完成。

全量计划在这些平台数量改变时刷新全部可获取评论，直到接口结束或技术保护边界；摄取按稳定身份去重，不退回自适应采样目标。

# 13. 二级回复怎样决定

只有：

```text
supports_sub_comments = true
```

才允许进入 SubComments/Replies Operation。

根评论还需要有真实回复存在证据，例如：

- `reply_count > 0`；
- Provider 明确给出可展开回复；
- 当前 Operation 返回结构可证明存在 thread。

不能：

```text
每条根评论都盲目请求二级回复
```

快手尤其要区分：

```text
subCommentCount       → integer 实际回复数

displaySubCommentCount
→ boolean UI 显示信号
→ 不能当回复数
```

详细字段见 TikHub 字段附录。

全量模式对回复数未知的线程继续分页；已完整采集且本次已知回复数量未变的线程复用已有结果，不再次请求。数量变化、数量未知、先前部分完成或缺少覆盖证据时重新补齐。根评论数变化后的增量页也执行该线程规则，不能因遇到旧根评论而遗漏变化后的回复。

# 14. 分页技术上限不是业务完整度

每个 Operation 必须有防死循环/无限账单的安全上限，例如：

- Search 最大页；
- Comments 最大页；
- SubComments 最大页。

这些技术值由当前执行限制代码/配置决定，并可冻结到 Run Snapshot。

达到上限：

```text
stop_reason = safety/page limit
coverage = partial（如果未证明完整）
```

禁止：

```text
因为程序主动停了
→ 写 complete
```

完整与否由真实业务证据决定，不由“代码没报错”决定。

# 15. Scheduler 策略和采集策略不是同一层

Scheduler 只决定：

```text
什么时候创建一个 Run
```

Collection Decision 决定：

```text
这个 Run 内某一 Content 下一步还要不要 Detail/Comments/Replies
```

当前 Scheduler：

```text
Asia/Shanghai
latest_only
max_catch_up_runs=0
```

详见：

[`docs/appendix/05_Scheduler调度执行与停机恢复.md`](../appendix/05_Scheduler调度执行与停机恢复.md)

不要因为 Scheduler 6 小时一次，就得出“每条旧 Content 6 小时抓一次详情和全部评论”。

# 16. 当前 API/前端如何配置采集

当前产品面主要分两块。

## 16.1 `/collection-strategy`

真实前端 Feature：

```text
frontend/src/features/collection-strategy/
```

后端：

- [`backend/src/aima_ugc/bootstrap/collection_strategy_http.py`](../../backend/src/aima_ugc/bootstrap/collection_strategy_http.py)

负责：

- Keyword Pack；
- Brand Filter 的 Plan 引用；
- Collection Plan；
- Plan enabled 状态。

车型目录本身由 Vehicle Catalog Owner 管理；本 Feature 只消费稳定 ID 和版本，并复用公共车型选择器，不复制别名或显示名列表。

新建 Plan 时，每个已选平台必须根据 `CollectionCapabilityResponse.search` 显式完成所有受支持维度；后端再按同一 Capability 校验并把配置写入 `collection_plan_platforms.config`。只有一个合法选项的维度可以由界面直接固定，多选维度必须由用户选择。

Plan 父事实使用显式 `plan_type=tikhub|wisersone`，领域/API 把类型特有配置与通用名称、品牌、启停、频率、调度版本区分，不由 Provider 名称推断类型。创建、编辑、复制、Scheduler 拒绝未知类型，编辑不可更换类型。既有计划为 TikHub，保留策略和子表；WisersOne 不创建 TikHub 平台/词包/策略子表，也不伪造 Collection Run。它在既有唯一 Occurrence 事务中创建下载和持久 Job，并自动接入统一导入，品牌目录在每次执行时冻结。详细流程见[统一数据入口](../appendix/08_数据入口与统一入库实现.md)。

创建/更新统一同步 `comment_policy` 与执行策略中的 `comment_mode`；复制保留类型和策略，副本停用。新的 Run 使用 `collection-run-config.v4` 冻结类型、评论策略及一致的执行参数，计划运行还冻结调度版本。历史 v2 缺类型只按既有 TikHub 解释；已投产 v3 的定向 `content_supplement` 格式保留同一历史兼容边界，其余缺类型快照拒绝执行，历史 JSON 不改写。全量计划与现有补采共用 [backend/src/aima_ugc/modules/collection/run_policy.py](../../backend/src/aima_ugc/modules/collection/run_policy.py) 和正式评论分页、Mapper、摄取、Raw 恢复及 Coverage；补采的选择资格与冻结目标保持原语义。

前端创建/编辑复用 [frontend/src/features/collection-strategy/pages/CollectionStrategyPage/components/TikHubPlanDialog.vue](../../frontend/src/features/collection-strategy/pages/CollectionStrategyPage/components/TikHubPlanDialog.vue) 和现有 Modal 容器，约 960×820 并受视口减 48 px 限制；固定头尾、正文滚动，基本信息和范围采用两列，窄屏改一列。目标平台只展开所选平台的真实配置。自适应/全量 Radio Card 和详情使用同一规则说明，显示费用与当前无预算限制；保存期间禁止重复提交或关闭，失败保留草稿。通用列表显示名称、类型、状态、采集范围、评论策略、频率与下次运行、操作，平台属于采集范围。

升级前已经存在的 Plan 可能保存 `config={}`。它们继续可读、可重新启用、可被 Scheduler 执行，并沿用原先 Adapter 默认值；本次变化不做数据迁移，也不把历史 Plan 改写成新默认。

# 17. Provider Secret 和 Base URL 的边界

Provider Config 可以保存：

```text
provider
base_url
secret_ref
enabled
```

不能保存明文：

- API Key；
- Authorization；
- Cookie；
- Password。

Transport 只有在目标 Origin 通过 Adapter 安全校验时才附带 Secret。

可配置 `base_url` 不等于任意 URL 都允许；不能通过 Provider 配置制造 SSRF。

# 19. TikHub API family 候选为什么不放进 Capability

例如当前代码存在：

- Douyin Search V1 Candidate；
- Weibo App Search Candidate；
- Bilibili Web Candidate；
- Kuaishou Web Comments backup；
- xiaohongshu App V1/Web V3 Search Candidate。

这些只是：

```text
显式 A/B / 备用验证入口
```

生产 Capability 只登记当前主链。

原因：Capability 是业务承诺。如果把所有“能构造 HTTP 请求”的 Candidate 都写进 Capability，前端会把未经真实闭环的接口暴露成正式产品能力。

验证方法：

[`docs/appendix/03_TikHub多接口验证与备用策略.md`](../appendix/03_TikHub多接口验证与备用策略.md)

# 20. 修改一个平台 Capability 应该怎么做

例如要让 B站支持原生时间筛选。

不能只改：

```python
native_time_filter=True
```

必须先证明：

```text
当前正式 Search Operation
→ TikHub 参数确实支持对应时间范围
→ Request Builder 能表达
→ Real Fixture/Probe 证明结构可用
→ Pagination 不受破坏
→ Contract/Capability Test
```

然后才修改 Capability。

同样：

- 打开新 content_type；
- 增加 sort；
- 声明 comment_count；
- 开启 incremental；

都必须有生产 Operation/真实响应证据。

# 25. 辅助补采的范围、冻结与身份资格

采集运行中心的新建辅助补采使用与“导入数据”相同的居中弹窗。用户可以按已入库内容的发布时间补采，或继续发起主动发现。日期范围采用北京时间自然日闭区间，包含开始日与结束日全天；没有发布时间的内容不入选。范围覆盖所有来源的当前 Content，不要求关联某个导入 Batch/Campaign，也不再次应用品牌或关键词搜索过滤。

日期与声音广场的“评论补采”共用 `content_supplement`：`supplement_targets.kind` 分别为 `published_date_range` 与 `selected`。日期入口排除无发布时间、范围外和当前内容版本最新 AI 明确不相关的内容；显式勾选入口保留全部所选内容，包括 AI 不相关内容，请求接受 1～1000 个 UUID 并去重，不接收任意声音广场筛选查询。采集运行中心不再提供基于导入批次的新建按钮，旧 Batch/Campaign 接口与历史任务仍兼容。

`POST /api/v1/collection-supplements/preview` 读取正式目标、数量、稳定指纹与五平台身份诊断。日期预览可随所选平台收敛总数和指纹；显式勾选必须覆盖全部内容平台，不能静默丢弃不支持的平台或已删除的 ID。创建时在同一事务重新核对 `expected_target_count`、`expected_target_fingerprint` 与当前选择及评论选项，范围改变返回 409，不写 Job/Run/Scope。页面重新预览并要求用户再次确认，不自动创建变化后的范围。

每条已确认内容冻结为一个 `source_type=content`、`operation_group=content_enrichment` Scope。当前 v4 配置的 `supplement_selection` 只保存 kind、数量、指纹和适用的日期边界，不重复保存所选 UUID；既有 v3 快照保留兼容。执行时只恢复 Scope 中固定的 Content ID，不重新按日期或 AI 筛选；排队后来源或发布时间变化不改变目标，删除或身份缺口保留明确失败原因。新运行记录统一为 `tikhub_content_supplement`，显示名称分别说明日期或勾选数量。

声音广场“评论补采”按钮位于 AI 分析与导出记录之间，沿用已有勾选状态，打开共享居中弹窗。详情和一级评论固定执行，二级回复默认开启且可取消。任务创建后立即刷新任务中心；在本页跟进到成功、部分完成、失败或取消后，重新读取服务端列表窗口及当前打开详情和评论，再停止跟进。筛选变化导致内容不再命中时使用服务器结果，不强留旧行；离开页面停止本页跟进。

“查看补采结果”按成功入库来源账本关联该次 Run。重复采集未改变内容时不会产生新业务版本，但仍属于本次结果；列表、数量和按结果筛选的后续分析使用相同关联。旧内容版本来源及导入来源继续兼容。

API、Worker 与前端须同步发布；回滚旧 Worker 前暂停新建统一补采并结清已创建任务。无需 Migration 或依赖升级。

精确字段以 [backend/src/aima_ugc/contracts/http.py](../../backend/src/aima_ugc/contracts/http.py) 为准；读取和执行分别由 [backend/src/aima_ugc/adapters/persistence/postgres/collection_targets.py](../../backend/src/aima_ugc/adapters/persistence/postgres/collection_targets.py) 与 [backend/src/aima_ugc/bootstrap/collection_scope.py](../../backend/src/aima_ugc/bootstrap/collection_scope.py) 维护。日期补采沿用以下统一身份和评论覆盖边界。

补采仍须由正式 Provider Capability 支持详情及所选评论层级，不能把“已入库”当成可以直接请求 TikHub。共享身份判断区分 typed ID、已验证的精确解析短链和身份阻塞，不把来源文章 ID 或合成 ID 发送给 Provider。

预览数量包含全部已选内容，分别显示直采、待解析、阻塞及原因。统一补采即使全部内容存在身份缺口也保留完整 Scope；不可执行项以 `identity_unavailable` 或 `exact_resolution_unavailable` 失败，零 Provider 请求。旧 Batch/Campaign 创建仍保持原有资格规则。这样不会把只处理可执行子集伪装成全部完成。

四个用户主动入口（一次性发现、日期补采、账号补采、选中内容评论补采）默认开启一级评论与二级回复。辅助补采弹窗保留独立发现、按发布时间补采，并将按账号补采作为第三个并列选项。日期、账号与发现允许关闭一级评论，此时同时关闭回复；重新开启一级不会自动恢复用户已关闭的回复。选中内容的一级评论固定开启。辅助补采固定执行 Content Detail，二级回复始终依赖一级评论。即：

```text
Detail（固定）
→ Comments（可选）
→ SubComments（可选，依赖 Comments）
```

当前不支持 Comment-only Supplement。以后若要对“详情已成功、评论失败/需刷新”的 Content 单独刷新评论，应建立独立 Change，复用已确认 Provider Content ID，而不是默认重复 Detail。

当前只对真实详情请求已证明可返回唯一原生 ID 的小红书 `share_text` 和抖音分享短链接入解析：先独立保存 Provider Attempt/Raw，再把 typed ID 作为原 Content 的外部身份保存，随后用该 ID 请求评论。详情返回零个或多个候选、或该 typed ID 已归属于另一条 Content 时，分别记录不可获取、歧义或 `identity_conflict`，不请求评论；网络结果未知保留独立 Attempt 与潜在重复计费事实。快手短链、微博视频链接和 B站 `b23.tv` 短链尚无精确归属证据，按已批准边界标为不可获取；微博 `ttarticle` 长文章始终不补采评论。

新手动 Run 在创建时冻结 Full 评论策略，并与 Decision Policy 的评论模式和开关保持一致；即使帖子评论数未变，用户主动创建的评论采集仍会重新读取。周期计划继续按自身已保存的 Adaptive/Full 策略执行，历史 Run 不重写。

Full 按 Provider 分页终止判断全部可访问一级评论和回复，不在 50 条一级或 5 条回复抽样目标处停止。达到 100 页安全上限、分页停滞、接口不可访问或回复短缺时，Coverage 与 Scope/Run 如实保留部分完成及停止原因；“全量”不承诺获取平台未开放的数据。默认 Full 及二级开启可能增加请求、费用和耗时，当前没有请求或金额预算控制。

Run/Scope 读取模型从持久 Candidate/Comment 事实汇总一级评论与回复计数。Scope 的身份状态与评论阶段随检查点持久化，运行详情轮询可分别显示身份解析中、一级评论抓取中、回复抓取中和终态覆盖；回复缺口不会以已抓到的一级评论数量伪装成完整覆盖。

当平台详情报告总评论数时，Full 覆盖核对使用实际一级评论与回复的合计，包括已有完整且数量未变的回复线程；两种计数仍分别显示。接口游标耗尽但实际可见合计低于报告数时，保留部分覆盖，不将删除、隐藏或限制访问的差额修饰为已采集。

# 26. 按账号发现作品的持久链

`account_discovery` 接受五平台多个带类型的账号 ID 和必填的北京时间发布时间闭区间。昵称可选，仅用于辨认。小红书支持 red_id 精确搜索解析和 user_id，抖音支持 unique_id 解析及 sec_uid，微博与 B站支持 uid；快手公开数字 user_id。快手 kuaishou_id/eid 的内部诊断保留，但当前用户搜索接口实测失败，未经真实唯一归属验证的类型不进入正式 Capability。每个所选平台至少一个账号，重复的同平台/同类型/同 ID 在创建前拒绝。

每个账号建立独立 `source_type=account`、`source_value=类型:ID`、`operation_group=content_discovery` Scope。新账号任务使用 `collection-run-config.v5` 冻结目标、日期、Provider revision 和当前品牌车型目录；既有 v2/v3/v4 解释保持。身份解析与每页作品都使用正式 Request/Attempt/Billing/Raw；身份结果、重复页事实和分页检查点持久保存，评论进度更新不会覆盖作品游标。微博非空页即使没有 since_id 也继续请求下一页；任何平台都不根据当前页最旧日期猜测后续作品排序而提前停止。重复页、缺少继续游标、接口不可用或技术页保护保留明确停止原因。

作品必须符合已验证账号归属和发布时间；符合的内容不要求命中品牌关键词。品牌车型 Evidence 仍用冻结目录补充，写入沿用 Content/Comment Owner、业务去重和来源账本。详情不可用时保留已验证作品，并记录评论覆盖不可用。不同来源或账号别名发现相同作品时不会形成第二条业务内容，仍保留本次来源。

一个账号失败不阻塞其他账号。自动重试沿用既有 Job 有界次数；失败或部分完成任务可由用户二次确认费用后调用 `retry-failed`，只重开失败/部分完成 Scope，在原 Run/Job 中重放成功 Raw，对允许重发的失败请求创建新 Attempt。`cancel` 沿用 Job Owner：排队立即取消，运行中协作取消或由 Reaper 收敛；已写入业务事实保留。Job 终态回调在同一事务结清账号 Run 和未完成 Scope，完成/取消竞态也服从 Job 的最终裁决。

运行中心以 `tikhub_account_discovery` 单独筛选，展示账号 ID、昵称、冻结日期、身份/作品/评论阶段及终态原因。查看结果按原 Run 来源账本进入声音广场。详情、评论、导出、报告和工作台沿用各自已有资格与品牌筛选；账号来源不会自动触发 AI。AI 派生统计在用户主动创建 Analysis Run 后才可用。
