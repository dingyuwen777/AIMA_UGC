# 数据库与文件存储

本文解释 AIMA_UGC 的长期持久化模型：**什么是业务事实、什么是大文件证据，Current / Version / Metric 为什么分开，每个领域由谁写，Schema 怎样演进和排障。**

精确表、列、索引、约束和 Migration 不在本文复制第二份。机器事实入口：

- [backend/src/aima_ugc/database_schema.py](../../backend/src/aima_ugc/database_schema.py)
- [migrations/versions/](../../migrations/versions/)
- 各模块 tables.py
- [scripts/quality/check_table_ownership.py](../../scripts/quality/check_table_ownership.py)

直接查库排障见 [docs/appendix/01_PostgreSQL查询与调试实战.md](../appendix/01_PostgreSQL查询与调试实战.md)。

## 1. 为什么 PostgreSQL 和 ArtifactStore 同时存在

PostgreSQL 保存需要事务、查询、引用和审计的业务事实：

- 业务身份；
- Current；
- Version / Observation；
- Job / Run / Campaign 状态；
- Analysis；
- Export/Report 父事实；
- Artifact metadata 与引用；
- 配置、审计与来源账本。

ArtifactStore 保存更适合文件生命周期管理的大字节：

- Provider Raw；
- Excel 输入；
- Canonical Chunk；
- Excel 导出；
- Markdown / DOCX 报告；
- 媒体缓存等派生文件。

如果所有大字节都进入数据库，备份、膨胀和文件处理成本会变重；如果业务状态只留文件目录，又无法可靠做事务、唯一约束、并发和来源追溯。

因此模型是：

~~~text
PostgreSQL
→ “这个事实是什么、属于谁、现在是什么状态、引用哪个 Artifact”

ArtifactStore
→ “这些原始/导出/缓存字节实际放在哪里”
~~~

## 2. 数据库长期规则

### 2.1 Schema 只通过 Alembic 演进

正式 Schema 变化必须有 Migration。应用启动不能把隐式 create_all 当生产升级机制。

Migration 负责结构和必要的有界数据变换；大规模历史回填如果会让 DDL 事务不可控，应交给持久 Job，而不是在 Migration 中全表扫描。

### 2.2 一个业务表只有一个写 Owner

跨领域可以读，但不能任意 UPDATE 别人的表。

原因是 Current、版本、幂等、审计和撤销规则必须由一个领域负责。如果两个模块都能“顺手写一下”，就无法定义哪套状态机才是正确事实。

机器检查：[scripts/quality/check_table_ownership.py](../../scripts/quality/check_table_ownership.py)。

### 2.3 时间、ID 和 JSON

稳定实体使用 UUID 等明确业务身份；时间使用带时区的数据库时间语义；JSONB 只保存确实具有半结构化价值的快照/统计/上下文，不用来逃避应该正式建模的高频关系和查询。

精确类型继续看当前 Table/Migration。

## 4. Content 不是“一张帖子表”

一条 UGC 同时包含几类不同变化速度和审计需求的信息：

~~~text
稳定身份
→ platform + external identity

当前展示值
→ title / text / author / media 等 Current

历史内容状态
→ Content Version

互动指标
→ Metric Observation

评论完整性
→ Coverage

来源与撤销
→ Source Contribution / Lineage
~~~

把这些全部覆盖写进一行，会失去“为什么变成现在这样”“点赞从多少变到多少”“哪个来源仍然支持这条内容”的能力。

## 5. Current：业务读取的当前视图

Current 用于声音广场、筛选、详情和下游任务定位。

它不是“最后一次输入 JSON 的复制”。多来源写入需要考虑：

- 稳定 identity；
- 字段是否真的被本次来源观察到；
- 字段新鲜度；
- 明确空值与未观察的区别；
- 人工锁；
- 来源撤销/后续接管。

真正的合并语义由 Content Owner 维护。

## 6. Version：可解释的内容历史

当影响内容业务语义的 Current 发生有效变化，需要按 Content Owner 规则形成 Version。

Version 用于：

- 解释历史；
- Analysis 绑定；
- Export 冻结；
- 撤销/Replay 后的可审计状态变化。

不是每次看到同一帖子都创建 Version，也不能因为只变了点赞就复制整份内容版本。

## 7. Metric Observation：互动指标单独保存

点赞、评论、收藏、转发等指标会频繁变化，而且可能下降。

下降可能来自：

- 用户删除互动；
- 平台修正；
- Provider 口径变化；
- 内容状态变化。

因此不能用“只接受更大值”当通用规则。可信的每次观察应按正式 Metric 语义保存，当前值与历史趋势分开。

## 8. observed_fields / field freshness

跨来源合并时，最危险的是把“来源没有返回这个字段”解释成“字段现在为空”。

所以 Canonical / Ingestion 要区分：

~~~text
没有观察到
vs
明确观察到空值
vs
明确观察到非空值
~~~

Content Owner 再结合字段新鲜度决定 Current 是否更新。

这也是历史补空 historical_fill_only 能安全工作的基础：旧历史输入只能补当前缺失，不把无时间依据的旧值覆盖新事实。

## 9. Content / Comment 身份

### Content

跨入口收敛依赖平台 + 稳定外部内容 identity，并可维护已经证明的 alternate identity。

URL hash、标题和作者名只能在特定受控场景做辅助，不应冒充 Provider 原生业务 ID。

### Comment

评论身份同样依赖平台原生稳定 ID。父子关系必须保存 root/parent identity；不能在查询时根据文本或作者猜回复关系。

评论树和 Coverage 的采集边界见 [docs/blueprint/02_采集系统与数据标准化.md](02_采集系统与数据标准化.md)。

## 10. Source Contribution 与撤销

同一个 Content 可以被多个来源共同支持：

~~~text
Excel Campaign A
+ TikHub Collection B
+ Replay C
→ 同一个 Content Current
~~~

所以撤销某个来源不能直接删除 Content。

需要先知道：

- 当前字段/可见性由哪些来源贡献；
- 后续来源是否已经接管；
- 是否存在人工锁；
- 是否仍有其它有效来源。

Data Import 与 Replay 的具体可逆账本和撤销语义见 [docs/appendix/08_数据入口与统一入库实现.md](../appendix/08_数据入口与统一入库实现.md)。

## 11. Provider Request / Attempt 分层

Request 表达“业务为什么要调用 Provider”；Attempt 表达“某一次真实 HTTP 尝试发生了什么”。

一份业务 Request 可以因为网络/限流发生多个 Attempt。

分开后才能回答：

- 为什么发起；
- 实际发了几次；
- 哪次收费；
- 哪次失败；
- Raw 属于哪次；
- Retry 是否改变业务身份。

Collection 详细链路见 [docs/blueprint/02_采集系统与数据标准化.md](02_采集系统与数据标准化.md)。

## 12. Artifact：字节可以清理，业务事实不能跟着消失

数据库只保存 Artifact identity、路径/对象键、校验信息、类型、生命周期和业务引用；字节进入 ArtifactStore。

例如：

~~~text
Import Campaign
→ Source Artifact

Provider Attempt
→ Raw Artifact

Export Request
→ Output Artifact
~~~

Artifact 文件到期不等于删除 Content、Analysis 或历史运行事实。文件生命周期见 [docs/appendix/12_Artifact生命周期与保留策略.md](../appendix/12_Artifact生命周期与保留策略.md)。

## 13. Read Model 是派生事实，不是新的业务 Owner

为了查询性能，AIMA 可以有声音广场等派生 Read Model。

Read Model 可以复制查询所需的可见性、当前分析和筛选键，但：

- 不成为 Content/Analysis/Evidence 的新写 Owner；
- 必须能由业务事实重建；
- Migration 建结构不应无界回填历史大表；
- 大规模回填通过持久 Job；
- 切换查询路径前要有完整性状态。

精确表/Trigger/Index 以 Migration 与集成测试为准。

## 14. Analysis 绑定 Content Version

AI 结论必须对应明确的输入版本。

如果只绑定 Content ID，正文变化以后就无法知道旧分析针对的是哪一版。

因此 Analysis Result、Run/Target 和人工复核要保留版本语义；Current 可以选择当前有效分析，但不能抹掉历史结果。

Analysis 具体实现见 [docs/appendix/07_AI舆情打标与分析实现.md](../appendix/07_AI舆情打标与分析实现.md)。

## 15. Export 冻结 Content Version

正式导出如果边生成边读取 Current，长任务执行期间内容变化会让一个文件混入多个时点的事实。

所以 Export Request 先冻结目标 Content Version，再由后台生成文件。

Excel Contract 见 [docs/appendix/06_Excel统一数据导出与离线调试.md](../appendix/06_Excel统一数据导出与离线调试.md)。

## 16. Durable Job 为什么持久化

分钟级任务如果只存在进程内存：

- Worker 崩溃后不知道做过什么；
- 无法安全接管；
- 取消/重试不可审计；
- API/前端不能可靠查询真实进度。

持久 Job 保存身份、Lease、Fence、Deadline、Attempt、Progress 和 Result 等恢复事实。完整 Job type 集合以 [backend/src/aima_ugc/bootstrap/worker.py](../../backend/src/aima_ugc/bootstrap/worker.py) 为机器事实。

## 17. Scheduler 为什么保存 Occurrence

周期计划不能只存 next_run_at。

停机恢复、重复触发和 schedule_version 需要一个稳定的逻辑执行身份，因此 Scheduler 用 Occurrence 表达“这个计划的这个逻辑时槽”。

Scheduler 详情见 [docs/appendix/05_Scheduler调度执行与停机恢复.md](../appendix/05_Scheduler调度执行与停机恢复.md)。

## 18. Migration 是正式 Schema 演进方式

修改数据库结构时：

~~~text
当前 Table / Contract
→ Alembic Migration
→ 兼容性 / 回滚分析
→ PostgreSQL Integration
→ 文档语义同步
~~~

不要：

- 在应用启动时偷偷修表；
- 改旧 Migration 来伪造历史；
- 用 SQLite 证明 PostgreSQL 锁/约束语义；
- 在大型 DDL 事务中做无界历史回填。

## 19. 排障时先查什么

如果页面值不对：

~~~text
Read Model / Query
→ Current
→ Version / Metric
→ Source Contribution
→ 上游 Run / Campaign / Attempt
→ Artifact / Raw
~~~

如果任务卡住：

~~~text
业务父事实
→ Job
→ Lease / Attempt / Error
→ Worker log
→ PostgreSQL lock / constraint
~~~

如果 Migration 失败：

~~~text
当前 revision
→ Migration head
→ 数据前置条件
→ SQLAlchemy metadata
→ Alembic check / compatibility test
~~~

SQL 示例统一见 [docs/appendix/01_PostgreSQL查询与调试实战.md](../appendix/01_PostgreSQL查询与调试实战.md)，不在 Blueprint 维护第二套查询手册。

## 20. 修改数据库时先找 Owner

| 想改什么 | 先找 |
| --- | --- |
| Content / Comment | Content Domain / tables / Repository / Migration |
| Import / Campaign / Replay | Ingestion Domain + Content Owner |
| Collection Run / Provider Request | Collection Domain |
| AI Result / Scheme | Analysis Domain |
| Export | Reporting Domain |
| Brand / Vehicle | Vehicles Domain |
| Job Runtime | Platform Job Owner |
| Identity / Session | Identity Domain |

跨 Owner 原子操作放在明确 Service/Bootstrap 边界，由各 Owner Repository 完成自己的写入。

## 21. 本文明确不承担什么

- 完整表名、字段、索引、约束清单；
- 当前 Migration head 的手工镜像；
- 全量 SQL 调试命令；
- 每次性能调优形成的临时索引建议；
- 历史 Stage / PR / CI。

这些信息分别由机器 Schema、Appendix、changes/archive 与 Git 持有。
