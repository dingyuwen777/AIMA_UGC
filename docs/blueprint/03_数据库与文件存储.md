## 1. 为什么 PostgreSQL 和文件系统同时存在

当前职责：

```text
PostgreSQL
→ 业务身份
→ Current
→ 历史版本
→ 指标观察
→ Job / Run / Batch 状态
→ Analysis
→ Export 父事实
→ Artifact 元数据和关系

ArtifactStore / 本地文件系统
→ Provider Raw
→ Excel 输入
→ Excel 导出
→ Markdown / DOCX 报告
→ 其他大文件产物

日志目录
→ api.log / worker.log / scheduler.log 等运行日志
```

如果把所有 Raw 和大文件塞进数据库：

- 数据库膨胀；
- 备份/恢复更重；
- 文件处理不方便。

如果只靠文件目录保存业务状态：

- 无法可靠做事务；
- 难以跨批次去重；
- 无法稳定查询 Current；
- Job 重启/恢复语义混乱。

所以：**PostgreSQL 保存业务事实和元数据，ArtifactStore 保存大字节对象。**

## 2. 当前数据库技术规则

### 2.1 数据类型

| 业务含义 | PostgreSQL 选择 | 原因 |
| --- | --- | --- |
| 内部 ID | `uuid` | 稳定跨进程创建 |
| 外部平台 ID | `text` | 不假设数字，不丢前导零，不受 JS 安全整数影响 |
| 时间 | `timestamptz` | 明确时区语义 |
| 业务日期 | `date` | 只有确实没有时刻含义时使用 |
| 计数 | `bigint` | 平台指标可能很大 |
| 金额/费用 | `numeric` | 不用浮点累计金额 |
| 灵活元数据 | `jsonb` | 只放真正灵活结构，不代替稳定列 |
| 状态枚举 | `text + check` | 便于通过 Migration 演进 |
| SHA-256 | `text` | 保存小写十六进制摘要 |

数据库时间统一用带时区时间；人工日志显示北京时间不改变数据库机器时间语义。

### 2.2 一个表只有一个写 Owner

当前 Owner 由 `Table.info["owner"]` 和质量门禁约束。

例如：

```text
contents / comments
→ content Owner

collection_plans / collection_runs / provider_requests
→ collection Owner

processing_import_batches
→ ingestion Owner

analysis_content_*
→ analysis Owner

reporting_data_*
→ reporting Owner

jobs
→ jobs/platform Owner

artifacts
→ storage/platform Owner
```

为什么这样做：如果两个模块都能随意 UPDATE 同一张表，就无法知道 Current、版本和幂等规则到底由谁决定。

检查脚本：

```text
scripts/quality/check_table_ownership.py
```

## 4. Content 为什么不是“一张帖子表”

同一帖子会被反复观察。

例如：

```text
10:00 第一次抓到
标题=A
点赞=100

12:00 再抓到
标题=A
点赞=180

第二天
标题=B
点赞=300
```

如果每次都插一整行：

- 当前值要自己找最新一条；
- 正文变化和指标变化混在一起；
- 数据量膨胀；
- 页面查询很重。

如果永远只 UPDATE 一行：

- 历史被覆盖；
- 无法解释什么时候正文变过；
- 无法做指标趋势。

所以当前采用：

```text
Current
+ Version
+ Metric Observation
```

## 6. Version：什么时候创建新版本

内容版本：

```text
content_versions
```

评论版本：

```text
comment_versions
```

保存的是稳定业务字段历史，不是每次抓取的完整拷贝。

典型会触发新 Content Version：

```text
标题变化
正文变化
内容类型变化
URL/状态等受版本 Hash 管理的业务字段变化
```

仅点赞从 100 变 120，不应该制造新的正文版本。

版本比较只和**当前 Business Hash**比较，所以：

```text
A → B → A
```

会形成三个业务时点中的新版本，而不是因为历史出现过 A 就拒绝记录。

生产摄取入口：

```text
backend/src/aima_ugc/modules/content/ingestion.py
```

PostgreSQL Owner 实现位于：

```text
backend/src/aima_ugc/adapters/persistence/postgres/
```

## 7. Metric Observation：为什么指标单独保存

当前内容指标历史：

```text
content_metric_observations
```

评论指标历史：

```text
comment_metric_observations
```

当前 `reason` 合法值由表约束定义：

```text
initial
changed
daily_checkpoint
```

含义：

```text
initial
→ 第一次观察

changed
→ 指标相对 Current 发生变化

daily_checkpoint
→ 当天还没有指标点，即使值没变也保留一次日级检查点
```

这样可以兼顾趋势分析和数据量控制。

## 8. `observed_fields` 和 `field_observed_at` 为什么重要

不同 Provider Operation 返回字段不一样。

例如 Search 可能只返回：

```text
标题
作者
点赞
```

Detail 才返回完整正文。

如果 Search 后直接把“没返回正文”当成 `text = null` 更新数据库，就可能把 Detail 已经拿到的正文抹掉。

所以 Canonical Observation 显式声明：

```text
observed_fields
```

Current 保存字段级最近观察时间：

```text
field_observed_at JSONB
```

规则：

- 本次未观察字段不参与覆盖；
- 更旧 Observation 不覆盖更新的字段；
- 明确观察到 `null` 和“没观察到”是两件不同事情。

这个机制是多 Operation、多来源合并的核心。

## 9. Provider Request / Attempt 为什么分两层

```text
Provider Request
→ 逻辑请求

Provider Attempt
→ 一次真实发送尝试
```

一个 Request 可以有多个 Attempt，但同一个 Attempt 最多一次真实网络发送。

这样可以区分：

```text
业务想请求什么
vs
实际发送了几次
```

如果网络结果未知：

```text
dispatch_status = unknown
potential_duplicate_charge = true（需要时）
```

不能偷偷在 Transport 内自动重试同一个 Attempt，因为那会丢失真实计费/发送审计。

相关表：

```text
provider_requests
provider_request_attempts
```

代码：

```text
backend/src/aima_ugc/modules/collection/tables.py
backend/src/aima_ugc/adapters/persistence/postgres/collection_provider_execution.py
```

### 9.1 Request 的来源父级

当前 Provider Request 恰好属于一个来源父级：

```text
Collection
→ scope_id

File Import
→ import_batch_id
```

约束注册在：

```text
backend/src/aima_ugc/modules/ingestion/tables.py
```

File Import 不为了目录对称伪造 Collection Scope。

```text
ArtifactService
→ 管 ID、元数据、生命周期、业务关联

ArtifactStore
```

## 11. Analysis 为什么引用 Content Version

AI 分析的是某个时刻的内容文本，不是一个永远不变的 `content_id`。

所以 Analysis 身份至少包含：

```text
content_id
content_version
input_hash
prompt_sha256
taxonomy_sha256
model_provider
model
```

当前唯一约束在：

```text
backend/src/aima_ugc/modules/analysis/tables.py
```

这样正文从 V1 变成 V2 后：

- V1 Analysis 历史仍保留；
- Current Query 不会把 V1 的结果误当成 V2 当前分析；
- 当前版本没分析时可以显示 `stale`。

Content Query 当前怎样选择 Analysis：

```text
backend/src/aima_ugc/adapters/persistence/postgres/content_queries.py
```

## 16. Migration 是唯一正式 Schema 演进方式

禁止：

- API 启动自动 `create_all()` 修改生产结构；
- 手工进生产库改列后不补 Migration；
- 修改已经发布的历史 Migration 来伪装没有变化。

正确流程：

```text
修改当前 tables.py / Domain
→ 新增 Alembic Revision
→ upgrade old → head
→ downgrade / upgrade（适用时）
→ alembic check
→ PostgreSQL Integration Test
```

历史 Migration 保存当时演进事实，所以旧 Migration 中出现已删除的 Budget 表不表示 Budget 仍是当前 Schema；要看后续 Revision 和当前 `database_schema.py`。
