# 日志、安全、部署与运维

本文只维护 AIMA_UGC **长期稳定的运行边界**。日常命令看 [`docs/02_环境运行与部署.md`](../02_环境运行与部署.md)，正式发布操作看 [`docs/operations/01_生产部署与离线Release方案.md`](../operations/01_生产部署与离线Release方案.md)，生产尚未完成的门禁看 [`docs/roadmap/02_生产上线实施路线.md`](../roadmap/02_生产上线实施路线.md)。

---

## 1. 运维事实分三类

```text
PostgreSQL
→ Job / Run / Batch / Content / Analysis / Export 等业务状态

应用日志
→ 某一步为什么失败、哪个调用位置、稳定 event 和安全上下文

Artifact
→ Raw、输入、导出、报告等文件字节及生命周期
```

不能用日志替代数据库终态，也不能用“文件存在”替代业务成功。

数据库排障见 [`docs/appendix/01_PostgreSQL查询与调试实战.md`](../appendix/01_PostgreSQL查询与调试实战.md)。

## 2. 日志边界

当前 API、Worker、Scheduler 使用统一日志基础设施：

- [`backend/src/aima_ugc/platform/logging/formatter.py`](../../backend/src/aima_ugc/platform/logging/formatter.py)
- [`backend/src/aima_ugc/platform/logging/setup.py`](../../backend/src/aima_ugc/platform/logging/setup.py)

当前人工排障文件为 `api.log / worker.log / scheduler.log`，同时允许 stdout 作为容器辅助日志。人类可读时间使用 `Asia/Shanghai`；数据库时间继续使用有时区的绝对时间事实。

日志必须保持：

- 真实调用文件和源码行号；
- 稳定 `event` 与必要 request/job/run/batch/content 等关联 ID；
- 单行、长度受控；
- Token、密码、Authorization、Cookie、Secret、敏感 Raw/Payload 和未脱敏 PII 不进入日志；
- 正常轮询、高频成功细节使用 DEBUG 或不记录；
- Retry/部分失败使用 WARNING，永久失败和未预期异常使用 ERROR；
- 低频重要生命周期和业务结果使用 INFO。

文件日志由现有 `RotatingFileHandler` 与 gzip 能力负责轮转。精确默认值直接看 [`backend/src/aima_ugc/platform/config/settings.py`](../../backend/src/aima_ugc/platform/config/settings.py)，业务模块不能创建第二套日志体系。

## 3. Secret 边界

固定原则：

```text
普通运行配置
→ 显式 AIMA_* 配置

Secret 值
→ 只读 Secret File

数据库业务配置
→ 只保存 secret_ref
```

内部随机 Secret 与外部 Provider/LLM Secret 分开：

```text
AIMA_SECRET_DIR
→ PostgreSQL password、Cursor signing key 等内部 Secret

AIMA_EXTERNAL_SECRET_DIR
→ TikHub / LLM 等外部凭据
```

Secret 禁止进入 Git、镜像/Release 明文、Job Payload、Plan config、Raw、Fixture、日志、错误响应和导出/报告。

完整 Compose 的 bootstrap 只负责准备目录、生成或校验内部 Secret；已有 PostgreSQL 数据但匹配的数据库密码 Secret 丢失时必须 fail closed，不能静默生成新值冒充恢复。

Windows Docker Desktop 的 storage-only override 只改变宿主持久化来源，不改变上述 Secret 分类和容器内 target。详细运行方式见 [`docs/02_环境运行与部署.md`](../02_环境运行与部署.md)。

## 4. 外部出站安全

TikHub 等带 Secret 的 HTTP 调用必须限制到批准的 HTTPS Origin，不能因为 Base URL 可配置就允许任意主机携带凭据。Transport 不得通过关闭 TLS 校验、无界 redirect 或隐藏的跨 API family fallback 来“提高可用性”。

实现入口：

- [`backend/src/aima_ugc/adapters/providers/tikhub/transport.py`](../../backend/src/aima_ugc/adapters/providers/tikhub/transport.py)
- [`backend/src/aima_ugc/platform/security/`](../../backend/src/aima_ugc/platform/security/)

## 5. 身份与授权

当前已经建立 Provider-neutral 的 `Principal/AuthContext` 与后端角色授权边界，角色写守卫必须由后端执行；前端路由守卫只改善交互，不能替代后端判断。

当前默认开发运行使用 `DevelopmentIdentityResolver`，把请求解析为固定开发 Principal。这个机制用于本地/当前受控环境装配，**不是真实企业 Authentication**。

完整 Production 仍需独立 L3 Change 完成：

```text
企业 Identity Provider / Feishu / OIDC 等
→ 验证登录或 Claims
→ Identity Adapter
→ Principal/AuthContext
→ Session / Token 生命周期与撤销
→ 后端 Authorization / 对象级授权
→ 安全与审计验收
```

业务模块不得把飞书 `open_id / union_id` 等 Provider 私有身份扩散成长期业务主键。当前身份事实见 [`backend/src/aima_ugc/modules/identity/`](../../backend/src/aima_ugc/modules/identity/) 与 [`backend/src/aima_ugc/bootstrap/api.py`](../../backend/src/aima_ugc/bootstrap/api.py)。

## 6. Health 与运行状态

当前正式健康入口：

```text
GET /health/live
GET /health/ready
```

`live` 只证明进程能响应；`ready` 才用于判断当前装配需要的 PostgreSQL、ArtifactStore、日志目录等依赖是否满足服务条件。

Health 不能替代：

- Migration 是否到目标 revision；
- Worker 是否能完成 Job；
- Provider/LLM 是否已配置；
- 一条真实业务链是否成功。

因此发布验收仍需由 Migration、Runtime、业务 Smoke 和相应 CI/运维证据共同承担。

## 7. Artifact 边界

长期分层固定为：

```text
ArtifactService
→ Artifact ID、metadata、link/lifecycle、业务关联

ArtifactStore
→ storage_key 与 bytes
```

默认 Local Store；未来切换 S3/MinIO 等只能通过 Adapter 替换存储实现，不能改变业务 Artifact Contract。下载必须经过业务状态和对象级授权边界，不能让 Store 自己决定业务权限。

Raw、导入 Source/Chunk、Excel Export、Word Report 等文件的保留策略见 [`docs/appendix/12_Artifact生命周期与保留策略.md`](../appendix/12_Artifact生命周期与保留策略.md)。

## 8. 部署与 Release

当前 canonical Runtime 是：

```text
Dockerfile
+ compose.yaml
+ env.production
```

Linux/WSL/公司服务器共用同一业务 Runtime；Windows Docker Desktop 只叠加 [`compose.windows.yaml`](../../compose.windows.yaml) 适配本地 storage source。

当前离线 Release 基线已经实际存在：

```text
linux/amd64 application images
+ 固定 PostgreSQL image
→ images.tar
→ release-manifest.json / migration-manifest.json
→ SHA256SUMS / DEPLOY.md
→ docker load
→ canonical Compose --no-build --pull never 回放
```

因此“离线 Bundle/Manifest 尚未实现”已经不是当前事实。详细构建、目录、Secret、Replay 和服务器步骤统一由 [`docs/operations/01_生产部署与离线Release方案.md`](../operations/01_生产部署与离线Release方案.md) 承担。

## 9. Backup / Restore 与完整 Production

当前完整 Production 仍是 **No-Go**。未完成的生产运行门禁包括：

- 企业 Authentication 与正式授权验收；
- HTTPS/浏览器安全与对象级授权验收；
- PostgreSQL + Artifact 同时点协调 Backup Set；
- Restore、reconciliation、RPO/RTO 与恢复演练；
- SBOM、独立签名/完整 provenance 与兼容矩阵；
- 正式生产服务器 preflight、backup、migrate、start、health/smoke、rollback；
- 真实生产容量、安全、Soak 和恢复验收。

这些是 [`docs/roadmap/02_生产上线实施路线.md`](../roadmap/02_生产上线实施路线.md) 的 Active 工作，不得因为公司内网 V1 已完成而写成已满足。

## 10. 4000 万历史数据的运维边界

历史导入软件能力已完成，但生产全量执行不是普通应用启动的一部分。生产前仍需公司服务器 500 万或业务 Owner 批准的等效比例容量演练、真实输入剖析、资源/存储/WAL 余量、备份/恢复事实和独立生产写授权。

容量与生产门禁只覆盖：

```text
server_path + historical_fill_only
```

不能外推到 `standard_observation` 的 4000 万吞吐能力。

当前运行手册：[`docs/operations/02_4000万历史迁移与Analysis Run运行手册.md`](../operations/02_4000万历史迁移与Analysis%20Run运行手册.md)。
当前未完成计划：[`docs/roadmap/03_4000万历史数据迁移实施方案.md`](../roadmap/03_4000万历史数据迁移实施方案.md)。

## 11. 修改运行边界时

下列变化通常需要独立高风险 Change：

- Authentication / Authorization / Session；
- Secret 分类或传输方式；
- 日志敏感信息策略；
- Artifact 存储/权限边界；
- Backup/Restore/RPO/RTO；
- Production 网络入口；
- Release signing/provenance；
- PostgreSQL/Runtime 版本和部署拓扑；
- 生产数据不可逆操作。

修改时必须从当前代码、Contract、Compose/Workflow 和真实运行证据恢复事实；不能从历史 Stage 文档恢复已经被替代的方案。
