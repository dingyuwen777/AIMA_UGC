# 日志、安全、部署与运维

本文描述 AIMA_UGC 的长期运行边界：**出了问题去哪里看、日志怎样生成、Secret 怎样进入进程、健康检查检查什么、生产部署最终怎样组织，以及哪些能力当前仍未实现。**

先区分两类事实：

```text
当前机器事实
→ backend/src/aima_ugc/platform/
→ entrypoints / bootstrap
→ Dockerfile / compose.yaml / compose.windows.yaml
→ env.local.example / env.production.example
→ 当前代码和测试

已批准但待实现的完整生产设计
→ docs/roadmap/02_生产上线实施路线.md
→ docs/appendix/11_生产部署与离线Release方案.md
```

Internal V1-A 已实现根 `Dockerfile`、canonical `compose.yaml`、`env.production.example` 与最小可部署容器栈；Windows Docker Desktop 只增加 storage-only override，不形成第二套业务 Runtime。这仍不等于完整 Stage 11 Production Release 已完成。

# 2. 当前日志实现在哪里

```text
backend/src/aima_ugc/platform/logging/
├─ formatter.py
└─ setup.py
```

当前正式进程日志：

```text
api       → api.log
worker    → worker.log
scheduler → scheduler.log
```

Migration 当前没有独立长期应用日志文件映射，执行输出以调用环境/CLI 为准。

`configure_service_logging()` 同时创建：

```text
RotatingFileHandler
+ stdout StreamHandler
```

文件日志是人工排障主入口；stdout 适合容器/平台辅助收集。

# 3. 当前日志一行是什么样

Formatter：

```text
backend/src/aima_ugc/platform/logging/formatter.py
```

格式概念：

```text
[YYYY-MM-DD HH:mm:ss.SSS file.py L123]
[INFO]
event=stable.event
job_id="..."
run_id="..."
message="..."
```

人工日志时间显示 `Asia/Shanghai`；数据库机器时间仍用 `timestamptz`。真实调用文件和源码行号放在前缀，是为了让人工排障可以直接跳回代码。

---

# 4. 日志脱敏是代码能力，不只是规范

`formatter.py` 当前会：

- 对敏感 key 递归替换为 `***`；
- 清理 `Bearer ...`；
- 清理 password/token/api key/cookie 等 inline 值；
- 清理 PostgreSQL URL 密码；
- 对常见邮箱/手机号/身份证形态做基础脱敏；
- 对 dict/list/tuple 递归脱敏；
- 截断过长字段/异常/整行；
- 把换行转义成单行；
- 安全 traceback 不复制可能带 Secret 的 source line/message。

精确限制常量直接看 `backend/src/aima_ugc/platform/logging/formatter.py`；不要在文档维护第二套数字 Contract。

---

# 5. 日志级别怎么用

```text
DEBUG
→ 正常轮询、空 Scheduler tick、高频成功细节

INFO
→ 低频重要生命周期、真正业务结果

WARNING
→ Retry、部分失败、需要关注但系统还能继续

ERROR
→ 永久失败、非法配置、需要人工介入或未预期异常
```

不要用 INFO 日志证明进程存活；健康由 Health 和实际 Job/Run 事实判断。

## 5.1 功能开发时怎样选择日志观测点

仓库已经具备正式应用日志体系，因此实现重要功能时要补充**最小充分**的运行过程日志：优先记录低频重要生命周期、Job/Run/Batch 状态变化、外部 I/O 安全摘要、Retry/部分失败/跳过/取消/永久失败，并复用已有 request/job/run/batch/content ID。

逐条记录、正常轮询、循环内部高频成功细节使用 DEBUG 或不记录。同一异常原则上只在拥有处理或终止责任的边界记录一次。新增日志继续经过现有 Formatter/脱敏/轮转，禁止主动记录 Secret、Token、密码、Authorization、敏感 Raw/Payload 或未脱敏 PII。

# 8. Secret 当前怎么进入系统

当前长期原则：

```text
普通运行配置
→ 显式 AIMA_* 环境变量

Secret 值
→ Secret File

数据库/业务配置
→ 只保存 secret_ref
```

内部与外部 Secret 分类在源码开发、Linux Compose、Windows Docker Desktop 和服务器之间保持一致：

```text
AIMA 内部随机 Secret
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
→ AIMA_SECRET_DIR=/run/internal-secrets

外部 Provider / LLM Secret
TikHub API Key
LLM API Key
→ AIMA_EXTERNAL_SECRET_DIR=/run/secrets
```

## 8.1 本地源码开发

```text
AIMA_SECRET_DIR
→ .runtime/internal-secrets

AIMA_EXTERNAL_SECRET_DIR
→ .runtime/secrets

旧 .runtime/secrets/postgres_password
→ 已废弃
→ launcher 不读取、不迁移、不拿它决定当前数据库密码
```

如果本地已经存在 `aima-ugc-postgres-dev-data` volume/container，但新的 `.runtime/internal-secrets/postgres_password` 不存在，launcher 会 fail closed：不从旧路径恢复，也不生成一个新密码去尝试连接既有数据库。对于可丢弃的本地源码开发数据，开发者显式删除本地 container/volume 后重建；需要保留旧数据时，只能自行确认数据库 Role 的真实密码并把匹配值放进新的内部根。

PostgreSQL 密码属于 Role 认证，不属于数据副本。不同密码不会自动映射不同数据；只改变应用侧密码而不改变数据库内 Role 密码，只会认证失败。

## 8.2 Linux / WSL / 公司服务器 Compose

canonical `compose.yaml` 使用：

```text
AIMA_HOST_ROOT
→ Linux/WSL 本地可设 ./.runtime/compose
→ 公司服务器 / Production 固定推荐 /data/AIMA_UGC

内部随机 Secret
→ bootstrap 首次生成并持久保存到 ${AIMA_HOST_ROOT}/shared/secrets
→ Backend 只读 /run/internal-secrets

外部凭据
→ env.production
→ Compose top-level secrets
→ /run/secrets
→ 只授予需要该 Secret 的服务
```

服务器已有 PostgreSQL 18 数据但 `postgres_password` 丢失时必须 fail closed 并恢复与数据库匹配的原 Secret；Host Root 收敛不改变恢复语义。

## 8.3 Windows Docker Desktop 原生 CMD / PowerShell

Windows 原生模式仍使用同一个 `env.production` 和 canonical `compose.yaml`，但叠加：

```text
compose.windows.yaml
```

该文件只替换四类持久 storage source：

```text
Artifact          → Docker named volume windows_runtime_data
应用日志          → Docker named volume windows_runtime_logs
PostgreSQL        → Docker named volume windows_postgres
AIMA 内部 Secret → Docker named volume windows_internal_secrets
```

原因不是降低要求，而是避免让 NTFS/Windows 文件共享层承担 Linux PostgreSQL 和 Secret 的 UID/GID/mode 语义。`scripts/deploy/prepare_host.py` **不增加 desktop 弱权限模式**；bootstrap 仍在 Linux 容器管理的 named volume 上执行原有 owner/mode 校验与收紧，因此内部 Secret 仍要求 `root:11001 / 0440`。

Windows override 不修改：

```text
PostgreSQL 版本
API / Worker / Scheduler / Migration command
Health / depends_on
网络 / 端口
外部 Compose Secret
业务环境变量
Provider / LLM 行为
```

Windows CMD/PowerShell wrapper 只是把 `compose.yaml + compose.windows.yaml + env.production` 组合起来，不是第二套 Runtime 实现。

`docker compose down` 保留 named volumes；`down -v` 会破坏性删除 Windows 本地 PostgreSQL、Artifact、日志和内部 Secret。这个 reset 语义不能用于服务器。

`PlatformSettings.external_secret_root` 在调用方没有显式设置 `AIMA_EXTERNAL_SECRET_DIR` 时仍回退到 `AIMA_SECRET_DIR`，保留底层配置兼容能力；正常源码 launcher 与 Compose 都显式设置内部/外部根，不依赖 fallback 作为运行方式。

真实 `env.production` 因为可以含外部 API Key，本身属于敏感文件：已被 Git ignore，不能提交 Git、进入镜像/Release 明文、日志或错误响应。`env.local` 同样只作为源码 launcher 输入。

Secret resolver 继续拒绝 root escape、symlink、非普通文件、超限内容，并避免错误信息回显 Secret。

Secret 禁止进入：Git、Job Payload、Plan config、Raw、Fixture、日志、Error Response、Export/Word。

# 10. 当前认证状态

当前已经有真实业务 API 和 Vue 页面，但**企业登录/正式认证授权尚未闭环**。


```text

→ Authentication Adapter
→ Principal / AuthContext
→ 后端 Authorization
```

# 11. Health API 当前做什么

当前 Route：

```text
GET /health/live
GET /health/ready
```

机器实现：

```text
backend/src/aima_ugc/bootstrap/api.py
backend/src/aima_ugc/platform/health.py
```

`live` 只表示进程能响应；`ready` 检查当前装配要求的 PostgreSQL、ArtifactStore 和日志目录等关键依赖，并避免向客户端泄露内部异常。`/ready=200` 不等于 TikHub、LLM 和全部业务流程都已生产验收。

# 13. Docker / Compose 当前状态与目标

## 13.1 一个 canonical Runtime，按宿主存储能力适配

仓库根当前存在：

```text
Dockerfile
compose.yaml
compose.windows.yaml
env.production.example
```

运行入口：

```text
源码开发
→ env.local
→ backend.py / frontend.py

Linux / WSL 完整容器 Runtime
→ env.production + compose.yaml
→ AIMA_HOST_ROOT bind mounts

Windows Docker Desktop 原生
→ 同一个 env.production
→ compose.yaml + compose.windows.yaml
→ Docker named volumes

公司服务器 / Production Runtime
→ env.production + canonical compose.yaml
→ AIMA_HOST_ROOT=/data/AIMA_UGC
```

`compose.windows.yaml` 是 storage-only override，不允许复制/分叉业务服务定义。若 Windows 需要业务行为变化，应修改 canonical `compose.yaml`，不能只改 override。

## 13.2 Linux / Production 持久根

```text
AIMA_HOST_ROOT
├─ postgres
├─ runtime/data
├─ runtime/logs
└─ shared/secrets
```

Linux/WSL 本地可设 `./.runtime/compose`；公司服务器和 Production 推荐 `/data/AIMA_UGC`。Production 的持久 Host Root 不能指向 `/data/AIMA_UGC/releases/<version>`。

Internal V1-A/B Linux 管理员入口：

```bash
cp env.production.example env.production
chmod 0600 env.production
docker compose --env-file env.production up -d --build --wait
```

## 13.3 Windows Docker Desktop 启动入口

CMD：

```cmd
scripts\dev\compose_windows.cmd
```

PowerShell：

```powershell
.\scripts\dev\compose_windows.ps1
```

两个 wrapper 默认组合：

```text
compose.yaml
+ compose.windows.yaml
+ env.production
→ up -d --build --wait
```

Windows 原生持久数据由 Docker Desktop named volumes 管理，而不是 `.runtime/compose`。需要宿主可见的仓库相对 bind 数据时，应在 Linux/WSL 文件系统使用 canonical Compose。

## 13.4 不因 Windows 支持降低 Production 门禁

Compose 自动编排仍是：

```text
bootstrap（一次性 root 初始化，成功后退出）
→ postgres healthy
→ migrate completed
→ configure completed
→ api / worker / scheduler
→ frontend healthy
```

Migration 仍是独立进程；Frontend 仍是唯一 published HTTP 入口；PostgreSQL/API 不发布宿主端口；Backend/Frontend 正式 Runtime 继续非 root。

永久验证必须分层陈述：

- Linux Internal V1-A Golden Path：真实 bind-mount Production-like 生命周期；
- Windows Runner：实际执行 CMD/PowerShell wrapper，证明路径和参数；
- Docker Engine named-volume Golden Path：真实 merged Compose、严格 Secret mode、PostgreSQL/Migration/Readiness/重启持久化；
- GitHub Hosted Windows Runner 没有被当作真实 Docker Desktop Linux-container Runtime，因此不能把上述证据写成“已在真实个人 Windows Docker Desktop 跑完”。

# 14. PostgreSQL 与 Artifact 为什么不能只备份一个

业务来源可能形成：

```text
content_versions.raw_artifact_id
→ artifacts metadata
→ ArtifactStore bytes
```

只备份数据库会留下 ID 但可能丢 bytes；只备份文件会丢业务关系/Job/Content。所以长期正确恢复单位是 PostgreSQL + ArtifactStore 的协调 Backup Set。

Windows 本地 named volumes 只是开发环境持久化，不是 Production Backup Set，也不改变协调恢复设计。

# 16. Migration 为什么独立进程

当前入口：

```text
backend/src/aima_ugc/entrypoints/migrate_main.py
backend/src/aima_ugc/bootstrap/migration.py
```

Schema 演进只通过 `migrations/versions/`。不能让 API 启动 `create_all()`、多个实例并发跑 Migration、手工改生产库后不补 Alembic，或修改已发布历史 Migration。

Internal V1-A 已把 `migrate` 作为 Compose 一次性独立服务，通过 `service_completed_successfully` 自动接入启动链；“自动编排”不等于“Migration 被塞进 API”。Windows override 不改变这个边界。
