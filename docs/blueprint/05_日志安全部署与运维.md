# 3. 当前日志一行是什么样

Formatter：

- [`backend/src/aima_ugc/platform/logging/formatter.py`](../../backend/src/aima_ugc/platform/logging/formatter.py)

格式概念：

```text
[YYYY-MM-DD HH:mm:ss.SSS file.py L123]
[INFO]
event=stable.event
job_id="..."
run_id="..."
message="..."
```

人工日志时间显示 `Asia/Shanghai`，但前缀不额外输出 `timezone` 字段或 `Asia/Shanghai` 文本；看到的墙钟即为北京时间。数据库继续用 `timestamptz` 表达绝对时间点，应用 PostgreSQL Session 默认 timezone 显式固定为 `Asia/Shanghai`。第三方 Raw 或外部协议必须保留原始时间语义时按原协议保存/传输，在 AIMA 自有展示边界再转换。真实调用文件和源码行号放在前缀，是为了让人工排障可以直接跳回代码。

# 4. 日志脱敏是代码能力，不只是规范

[`backend/src/aima_ugc/platform/logging/formatter.py`](../../backend/src/aima_ugc/platform/logging/formatter.py) 当前会：

- 对敏感 key 递归替换为 `***`；
- 清理 `Bearer ...`；
- 清理 password/token/api key/cookie 等 inline 值；
- 清理 PostgreSQL URL 密码；
- 对常见邮箱/手机号/身份证形态做基础脱敏；
- 对 dict/list/tuple 递归脱敏；
- 截断过长字段/异常/整行；
- 把换行转义成单行；
- 安全 traceback 不复制可能带 Secret 的 source line/message。

精确限制常量直接看 [`backend/src/aima_ugc/platform/logging/formatter.py`](../../backend/src/aima_ugc/platform/logging/formatter.py)；不要在文档维护第二套数字 Contract。

# 5. 日志级别怎么用

```text
DEBUG
→ 正常轮询、空 Scheduler tick、高频成功细节

INFO
→ 低频重要生命周期、真正业务结果

WARNING
→ Retry、部分失败、需要关注但系统还能继续

ERROR
→ 永久失败、非法配置、需要人工介入或未预期异常
```

不要用 INFO 日志证明进程存活；健康由 Health 和实际 Job/Run 事实判断。

## 5.1 功能开发时怎样选择日志观测点

仓库已经具备正式应用日志体系，因此实现重要功能时要补充**最小充分**的运行过程日志：优先记录低频重要生命周期、Job/Run/Batch 状态变化、外部 I/O 安全摘要、Retry/部分失败/跳过/取消/永久失败，并复用已有 request/job/run/batch/content ID。

逐条记录、正常轮询、循环内部高频成功细节使用 DEBUG 或不记录。同一异常原则上只在拥有处理或终止责任的边界记录一次。新增日志继续经过现有 Formatter/脱敏/轮转，禁止主动记录 Secret、Token、密码、Authorization、敏感 Raw/Payload 或未脱敏 PII。

# 8. Secret 当前怎么进入系统

当前长期原则：

```text
普通运行配置
→ 显式 AIMA_* 环境变量

Secret 值
→ Secret File

数据库/业务配置
→ 只保存 secret_ref
```

内部与外部 Secret 分类在源码开发、Linux Compose、Windows Docker Desktop 和服务器之间保持一致：

```text
AIMA 内部随机 Secret
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
→ AIMA_SECRET_DIR=/run/internal-secrets

外部 Provider / LLM Secret
TikHub API Key
LLM API Key
→ AIMA_EXTERNAL_SECRET_DIR=/run/secrets
```

## 8.1 本地源码开发

```text
AIMA_SECRET_DIR
→ .runtime/internal-secrets

AIMA_EXTERNAL_SECRET_DIR
→ .runtime/secrets

旧 .runtime/secrets/postgres_password
→ 已废弃
→ launcher 不读取、不迁移、不拿它决定当前数据库密码
```

如果本地已经存在 `aima-ugc-postgres-dev-data` volume/container，但新的 `.runtime/internal-secrets/postgres_password` 不存在，launcher 会 fail closed：不从旧路径恢复，也不生成一个新密码去尝试连接既有数据库。对于可丢弃的本地源码开发数据，开发者显式删除本地 container/volume 后重建；需要保留旧数据时，只能自行确认数据库 Role 的真实密码并把匹配值放进新的内部根。

PostgreSQL 密码属于 Role 认证，不属于数据副本。不同密码不会自动映射不同数据；只改变应用侧密码而不改变数据库内 Role 密码，只会认证失败。

## 8.2 Linux / WSL / 公司服务器 Compose

canonical [`compose.yaml`](../../compose.yaml) 使用：

```text
AIMA_HOST_ROOT
→ Linux/WSL 本地可设 ./.runtime/compose
→ 公司服务器 / Production 固定推荐 /data/AIMA_UGC

内部随机 Secret
→ bootstrap 首次生成并持久保存到 ${AIMA_HOST_ROOT}/shared/secrets
→ Backend 只读 /run/internal-secrets

外部凭据
→ env.production
→ Compose top-level secrets
→ /run/secrets
→ 只授予需要该 Secret 的服务
```

服务器已有 PostgreSQL 18 数据但 `postgres_password` 丢失时必须 fail closed 并恢复与数据库匹配的原 Secret；Host Root 收敛不改变恢复语义。

## 8.3 Windows Docker Desktop 原生 CMD / PowerShell

Windows 原生模式仍使用同一个 `env.production` 和 canonical [`compose.yaml`](../../compose.yaml)，但叠加：

- [`compose.windows.yaml`](../../compose.windows.yaml)

该文件只适配 Windows 宿主持久 storage：

```text
Artifact          → ${AIMA_HOST_ROOT}/runtime/data bind mount
应用日志          → ${AIMA_HOST_ROOT}/runtime/logs bind mount
PostgreSQL        → Docker named volume windows_postgres
AIMA 内部 Secret → Docker named volume windows_internal_secrets
```

这里的边界是有意区分的：Artifact 与 `.log` 是开发机需要直接查看的普通文件；PostgreSQL 与内部 Secret 则继续保留在 Docker Desktop 管理的 Linux 文件系统，避免让 NTFS/Windows 文件共享层承担数据库和 Secret 的严格 UID/GID/mode 语义。

[`scripts/deploy/prepare_host.py`](../../scripts/deploy/prepare_host.py) 的 Windows bind-compatible 模式**只作用于 `runtime/data` 和 `runtime/logs`**：仍检查路径存在、目录类型和 symlink 边界，并尽力设置既有 UID/GID/mode；如果文件共享层无法准确表达/回显 POSIX owner/mode，不因这两个普通目录失败。PostgreSQL 目录和内部 Secret 不进入该例外，内部 Secret 仍严格要求 `root:11001 / 0440`。

Windows override 不修改：

```text
PostgreSQL 版本
API / Worker / Scheduler / Migration command
Health / depends_on
网络 / 端口
外部 Compose Secret
业务环境变量
Provider / LLM 行为
```

Windows CMD / PowerShell 直接执行标准 Docker Compose CLI，显式组合 `compose.yaml + compose.windows.yaml + env.production`；不再维护额外 wrapper，也不形成第二套 Runtime 实现。

`docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down` 同时保留 Host Root 文件和 named volumes；加 `-v` 只破坏性删除 Windows 本地 PostgreSQL 与内部 Secret named volumes，**不会删除 bind-mounted Artifact/日志**。如果要完全清空 Windows 本地文件，还必须显式删除 `${AIMA_HOST_ROOT}/runtime/data` 与 `${AIMA_HOST_ROOT}/runtime/logs`。这个 reset 语义不能用于服务器。

`PlatformSettings.external_secret_root` 在调用方没有显式设置 `AIMA_EXTERNAL_SECRET_DIR` 时仍回退到 `AIMA_SECRET_DIR`，保留底层配置兼容能力；正常源码 launcher 与 Compose 都显式设置内部/外部根，不依赖 fallback 作为运行方式。

真实 `env.production` 因为可以含外部 API Key，本身属于敏感文件：已被 Git ignore，不能提交 Git、进入镜像/Release 明文、日志或错误响应。[`env.local`](../../env.local) 同样只作为源码 launcher 输入。

Secret resolver 继续拒绝 root escape、symlink、非普通文件、超限内容，并避免错误信息回显 Secret。

Secret 禁止进入：Git、Job Payload、Plan config、Raw、Fixture、日志、Error Response、Export/Word。

# 13. Docker / Compose 当前状态与目标

## 13.1 一个 canonical Runtime，按宿主存储能力适配

仓库根当前存在：

- [`Dockerfile`](../../Dockerfile)
- [`compose.yaml`](../../compose.yaml)
- [`compose.windows.yaml`](../../compose.windows.yaml)
- [`env.production.example`](../../env.production.example)

运行入口：

```text
源码开发
→ env.local
→ backend.py / frontend.py

Linux / WSL 完整容器 Runtime
→ env.production + compose.yaml
→ AIMA_HOST_ROOT bind mounts

Windows Docker Desktop 原生
→ 同一个 env.production
→ compose.yaml + compose.windows.yaml
→ AIMA_HOST_ROOT bind Artifact/日志 + named volume PostgreSQL/内部 Secret

公司服务器 / Production Runtime
→ env.production + canonical compose.yaml
→ AIMA_HOST_ROOT=/data/AIMA_UGC
```

[`compose.windows.yaml`](../../compose.windows.yaml) 是 storage-only override；只允许做宿主存储适配和与该存储直接相关的 bootstrap 权限兼容，不允许复制/分叉业务服务定义。若 Windows 需要业务行为变化，应修改 canonical [`compose.yaml`](../../compose.yaml)，不能只改 override。

## 13.2 Linux / Production 持久根

```text
AIMA_HOST_ROOT
├─ postgres
├─ runtime/data
├─ runtime/logs
└─ shared/secrets
```

Linux/WSL 本地可设 `./.runtime/compose`；公司服务器和 Production 推荐 `/data/AIMA_UGC`。Production 的持久 Host Root 不能指向 `/data/AIMA_UGC/releases/<version>`。

Internal V1-A/B Linux 管理员入口：

```bash
cp env.production.example env.production
chmod 0600 env.production
docker compose --env-file env.production up -d --build --wait
```

## 13.3 Windows Docker Desktop 启动入口

第一次从仓库根创建本机配置：

```cmd
copy env.production.example env.production
```

或：

```powershell
Copy-Item env.production.example env.production
```

Windows 本地推荐：

```dotenv
AIMA_HOST_ROOT=./.runtime
```

编辑后，CMD / PowerShell 统一使用：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production up -d --build --wait
```

日常停止并保留全部持久状态：

```powershell
docker compose -f compose.yaml -f compose.windows.yaml --env-file env.production down
```

Windows 原生 Artifact/日志由 `${AIMA_HOST_ROOT}/runtime/data` 与 `${AIMA_HOST_ROOT}/runtime/logs` 管理；PostgreSQL/内部 Secret 由 Docker named volumes 管理。这样本地可以直接查看 Excel/Raw/Export/Report Artifact 与 `api.log`/`worker.log`/`scheduler.log`，同时不降低数据库/Secret 权限边界。

## 13.4 不因 Windows 支持降低 Production 门禁

Compose 自动编排仍是：

```text
bootstrap（一次性 root 初始化，成功后退出）
→ postgres healthy
→ migrate completed
→ configure completed
→ api / worker / scheduler
→ frontend healthy
```

Migration 仍是独立进程；Frontend 仍是唯一 published HTTP 入口；PostgreSQL/API 不发布宿主端口；Backend/Frontend 正式 Runtime 继续非 root。

永久验证必须分层陈述：

- Linux Internal V1-A Golden Path：真实 bind-mount Production-like 生命周期；
- Windows Runner：直接执行标准 Compose CLI，证明 CMD/PowerShell 都可解析 `compose.yaml + compose.windows.yaml + env.production`；
- Docker Engine hybrid Golden Path：真实 merged Compose、Artifact/日志 bind、host-visible 文件、严格 Secret mode、PostgreSQL/Migration/Readiness/重启持久化与 `down -v` 生命周期边界；
- GitHub Hosted Windows Runner 没有被当作真实 Docker Desktop Linux-container Runtime，因此不能把上述证据写成“已在真实个人 Windows Docker Desktop 跑完”。

# 14. PostgreSQL 与 Artifact 为什么不能只备份一个

业务来源可能形成：

```text
content_versions.raw_artifact_id
→ artifacts metadata
→ ArtifactStore bytes
```

只备份数据库会留下 ID 但可能丢 bytes；只备份文件会丢业务关系/Job/Content。所以长期正确恢复单位是 PostgreSQL + ArtifactStore 的协调 Backup Set。

Windows 本地混合存储只是开发环境持久化，不是 Production Backup Set，也不改变协调恢复设计。

# 16. Migration 为什么独立进程

- [`backend/src/aima_ugc/entrypoints/migrate_main.py`](../../backend/src/aima_ugc/entrypoints/migrate_main.py)

# 18. 生产/开发排障顺序

## API 返回 500

```text
1. request_id
2. api.log
3. 对应 Route / Application Service
4. PostgreSQL 业务父事实是否已提交

4. lease_expires_at / attempt_deadline_at

```

# 21. 历史目录与全量迁移运维边界

服务器历史目录不是应用可写数据目录。宿主只配置 `AIMA_HISTORICAL_IMPORT_HOST_ROOT`，Compose 将其以只读 bind mount 暴露给 API/Worker 的 `/data/aima-historical-input`；HTTP 只使用相对路径，应用拒绝链接组件和根目录逃逸。不要把该目录挂到公网共享盘，也不要授予页面文件管理能力。

历史 Campaign 创建、start、cancel、retry 和 Analysis Run create/cancel 写 `audit_events`，但当前 actor 仍是 `system`，因为 Authentication/Principal 尚未接入。真实企业身份接入后再把 actor 绑定到统一 Principal，业务模块不能自行依赖身份 Provider 私有字段。

容量测试使用 [`scripts/performance/benchmark_stage12_historical.py`](../../scripts/performance/benchmark_stage12_historical.py) 和数据库名后缀 `_stage12_capacity` 的隔离库；脚本会拒绝清理其他数据库。它只证明测试环境软件链路，不授权生产 4000 万写入。全量前仍需至少 30% 的批准存储余量、真实输入剖析、备份/恢复事实和独立生产操作授权。完整步骤见 `docs/appendix/14_4000万历史迁移与Analysis Run运行手册.md`。
