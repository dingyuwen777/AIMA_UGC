# 测试与调试说明

本文面向真正需要**验证代码、复现问题、调试一条业务链**的开发者。

目标不是列一堆测试名，而是让你知道：

```text
改了什么
→ 应先跑哪一层测试
→ 失败时先看哪个真实代码/数据事实
→ 哪些情况必须用 PostgreSQL
→ 哪些情况应该用 Fixture/Fake
→ 哪些真实付费 Probe 不能进普通 CI
→ 最终怎样判断“这个修改真的可以合并”
```

仓库统一开发规则先读：

- [`../AGENTS.md`](../AGENTS.md)
- [`01_代码结构与修改导航.md`](01_代码结构与修改导航.md)

---

# 1. 测试分层不是为了形式，而是隔离失败原因

当前主要测试层：

```text
tests/
├─ unit/
├─ contracts/
├─ api/
├─ integration/
└─ fixtures/
```

另外还有：

```text
frontend/
→ Vue / TypeScript / E2E 相关测试

.github/workflows/
→ CI 组合门禁

scripts/quality/
→ 架构、Owner、Secret、文档等仓库级检查
```

## 1.1 Unit Test

回答：

> 这一小块领域逻辑本身对不对？

适合：

- Scheduler Cron / latest-only；
- Pagination；
- TikHub Operation Builder；
- Mapper；
- Decision Pipeline；
- Cursor；
- AI Validator；
- Prompt Taxonomy Parser；
- Excel Renderer；
- Word Report 统计/OOXML；
- 日志 Formatter。

Unit Test 应尽量：

- 不访问真实网络；
- 不依赖生产数据库；
- 输入可复现；
- 失败原因明确。

## 1.2 Contract Test

回答：

> 公开数据结构、API、Schema、序列化边界有没有漂移？

重点覆盖：

- Pydantic Contract；
- OpenAPI；
- JSON Schema；
- generated client；
- HTTP Request / Response；
- Provider payload；
- Excel 导出列；
- Artifact metadata。

Contract Test 的意义不是重复 Unit，而是保护消费者可见边界。

## 1.3 API Test

回答：

> 在不启动完整服务的情况下，HTTP 路由、状态码、序列化和关键业务分支是否正确？

适合验证：

- 路由是否注册；
- 参数校验；
- 状态码；
- 错误响应；
- API 层与领域服务接线；
- 不依赖真实 PostgreSQL 的 HTTP 行为。

## 1.4 PostgreSQL Integration

如果逻辑依赖以下语义，就不能只靠 SQLite/Fake：

- PostgreSQL JSON/JSONB；
- UUID / timestamp；
- unique / partial index；
- row locking；
- transaction / concurrency；
- Alembic Migration；
- SQLAlchemy PostgreSQL 方言；
- repository 查询行为。

这类验证应进入真实 PostgreSQL Integration。

## 1.5 Browser / E2E

前端测试分两类理解：

1. **Browser Mock / 页面验收**：验证页面、组件、交互和请求语义；
2. **Real Full-stack**：真实前端 + 后端 + PostgreSQL，验证关键链路真的接通。

不要把 Browser Mock 写成“真实后端已经验证”，也不要把 API Integration 写成“用户页面已经验证”。

# 2. 先从改动范围选测试，不要一上来全跑

建议顺序：

```text
最小目标测试
→ 邻近模块回归
→ Contract / DB / Browser 等受影响层
→ 仓库级静态门禁
→ 完成前按 Change/风险执行完整验证
```

例如：

- 只改一个纯函数：先跑对应 Unit；
- 改 Pydantic 模型：Unit + Contract；
- 改 repository SQL：Unit + PostgreSQL Integration；
- 改 API：API + Contract，必要时 DB；
- 改 Vue 页面：Vitest/Browser Mock，关键链路再跑 Full-stack；
- 改 Docker/Compose/Workflow：必须跑对应 Runtime/CI/部署边界验证。

# 3. Python 验证入口

仓库当前 Python 测试和静态检查都应从根目录执行。

常见定向验证：

```bash
uv run pytest tests/unit/<目标测试>.py -q
uv run pytest tests/contracts/<目标测试>.py -q
uv run pytest tests/api/<目标测试>.py -q
```

仓库级 Python 静态门禁：

```bash
uv run ruff format --check backend tests scripts
uv run ruff check backend tests scripts
uv run mypy backend/src
```

完整测试层以当前 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) 为准，不要在文档里维护第二套容易漂移的完整命令清单。

# 4. 仓库级质量检查

以下脚本负责不同证明责任：

- [`check_architecture.py`](../scripts/quality/check_architecture.py)：长期目录骨架与模块边界；
- [`check_table_ownership.py`](../scripts/quality/check_table_ownership.py)：数据库表 Owner；
- [`scan_secrets.py`](../scripts/quality/scan_secrets.py)：Secret 泄漏；
- [`check_docs.py`](../scripts/quality/check_docs.py)：当前项目文档入口、链接和治理边界。

执行方式：

```bash
uv run python scripts/quality/check_architecture.py
uv run python scripts/quality/check_table_ownership.py
uv run python scripts/quality/scan_secrets.py
uv run python scripts/quality/check_docs.py
```

这些检查不能互相替代。例如：Secret 扫描通过，不代表 API Contract 正确；文档链接通过，也不代表文档正文与实现语义一致。

# 6. PostgreSQL 调试

数据库问题建议按下列顺序：

1. 确认连接目标；
2. 确认 Migration 已到当前 head；
3. 确认实际表/索引/约束；
4. 用最小 SQL 重现；
5. 再回到 repository/service 层定位。

完整查询示例与表结构调试见 [`appendix/01_PostgreSQL查询与调试实战.md`](appendix/01_PostgreSQL查询与调试实战.md)。

其停止方式、数据卷和环境准备仍以 [`02_环境运行与部署.md`](02_环境运行与部署.md) 当前说明为准。

# 7. Provider / TikHub 调试

普通 CI 不访问真实付费 Provider。

优先层级：

```text
Operation / Mapper Unit
→ Sanitized Fixture
→ Provider Contract
→ 本地 Replay
→ 有明确必要时才做真实 Probe
```

真实 TikHub Probe 只用于确认当前外部事实，例如：

- 上游接口是否仍可用；
- 实际响应字段是否变化；
- Cursor/分页行为是否变化；
- 文档中的 Provider 能力是否仍成立。

它不能成为普通 CI 的硬依赖，也不能把 Secret 写入日志、Fixture 或仓库。

TikHub 相关实现与已沉淀证据主要看：

- [`adapters/providers/tikhub/capabilities.py`](../backend/src/aima_ugc/adapters/providers/tikhub/capabilities.py)

- [`appendix/03_TikHub多接口验证与备用策略.md`](appendix/03_TikHub多接口验证与备用策略.md)

# 13. CI 怎么看

永久 Workflow 当前包括多个独立证明层。不要只看总的“CI 绿色”，要看本次风险对应的那一层是否真的执行。

主要入口：

- [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)：仓库质量、Unit/Contract/API、PostgreSQL、前端等；
- [`.github/workflows/fullstack.yml`](../.github/workflows/fullstack.yml)：真实 Full-stack Golden Path；
- [`.github/workflows/runtime.yml`](../.github/workflows/runtime.yml)：Runtime Acceptance；
- [`.github/workflows/change-completion-gate.yml`](../.github/workflows/change-completion-gate.yml)：Change 完成门禁；
- [`.github/workflows/release.yml`](../.github/workflows/release.yml)：Release/Artifact 相关验证与发布。

CI 失败时：

1. 找到第一个真实失败 Step；
2. 读取完整日志；
3. 判断失败属于代码、Contract、数据、依赖、环境还是测试本身；
4. 修根因；
5. 在新 HEAD 重新取得对应 fresh evidence。

不要通过删除测试、放宽断言、吞异常或把失败步骤 `continue-on-error` 来制造绿色。

# 14. 什么叫“验证通过”

必须同时满足：

- 命令/Workflow 在当前 HEAD 实际运行；
- 退出码成功；
- 失败数为 0；
- 执行的是能证明目标风险的层；
- 没有把关键检查 skip 掉；
- 没有用 Fake/Mock 冒充真实依赖；
- 结论只覆盖证据实际证明的范围。

例如：

- Unit 绿 ≠ PostgreSQL 绿；
- Browser Mock 绿 ≠ Real Full-stack 绿；
- Contract 绿 ≠ Provider 当前真实可用；
- 文档链接检查绿 ≠ 文档正文事实正确；
- PR CI 绿 ≠ 合并后 `main` 已验证。

# 15. 完成前检查

准备说“可以合并”前，至少重新确认：

1. 当前 HEAD；
2. 需求/Change 成功标准；
3. affected scope；
4. required Validation Matrix；
5. 文档是否与当前实现同步；
6. required CI 是否都跑在当前 HEAD；
7. 是否还有未解决 warning / skipped / blocker；
8. PR mergeable、保护规则和 reviewed head 是否没有漂移。

最终原则：

> **测试不是为了数量，而是为了给当前修改的每个独立风险提供正确层级的新鲜证据。**
