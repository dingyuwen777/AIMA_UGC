# 测试与调试说明

本文面向真正需要**验证代码、复现问题、调试一条业务链**的开发者。

目标不是列一堆测试名，而是让你知道：

```text
改了什么
→ 应先跑哪一层测试
→ 失败时先看哪个真实代码/数据事实
→ 哪些情况必须用 PostgreSQL
→ 哪些情况应该用 Fixture/Fake
→ 哪些真实付费 Probe 不能进普通 CI
→ 最终怎样判断“这个修改真的可以合并”
```

仓库统一开发规则先读：

- [`../AGENTS.md`](../AGENTS.md)
- [`.agents/skills/reliable-vibe-coding/SKILL.md`](../.agents/skills/reliable-vibe-coding/SKILL.md)
- [`01_代码结构与修改导航.md`](01_代码结构与修改导航.md)

# 1. 测试分层不是为了形式，而是隔离失败原因

当前主要测试层：

```text
tests/
├─ unit/
├─ contracts/
├─ api/
├─ integration/
└─ fixtures/
```

另外还有：

```text
frontend/
→ Vue / TypeScript / E2E 相关测试

.github/workflows/
→ CI 组合门禁

scripts/quality/
→ 架构、Owner、Secret、文档等仓库级检查
```

## 1.1 Unit Test

回答：

> 这一小块领域逻辑本身对不对？

适合：

- Scheduler Cron / latest-only；
- Pagination；
- TikHub Operation Builder；
- Mapper；
- Decision Pipeline；
- Cursor；
- AI Validator；
- Prompt Taxonomy Parser；
- Excel Renderer；
- Word Report 统计/OOXML；
- 日志 Formatter。

Unit Test 应尽量：

- 不访问真实网络；
- 不依赖生产数据库；
- 输入可复现；
- 失败原因明确。

## 1.2 Contract Test

回答：

> 两个模块/系统之间约定的数据形状是否仍兼容？

当前重点：

```text
Canonical
HTTP Pydantic
Job Payload
Prompt/Taxonomy
TikHub Sanitized Fixture → Canonical
OpenAPI / generated Client
```

## 1.3 Integration Test

回答：

> PostgreSQL 的真实约束、事务、锁、Repository 组合起来是否正确？

必须使用真实 PostgreSQL 语义验证：

- UNIQUE / FK / CHECK；
- Deferred Constraint；
- `SELECT ... FOR UPDATE`；
- `SKIP LOCKED`；
- Job Lease/Fencing；
- Scheduler 并发；
- Content Current/Version/Metric；
- Analysis/Export 持久化；
- Alembic Migration。

**不能用 SQLite 通过后宣称 PostgreSQL 已验证。**

## 1.4 API Test

回答：

> HTTP Contract、状态码、业务错误和事务入口是否正确？

重点：

- 200/202/404/409/422/500；
- Request/Response；
- Problem Detail；
- Cursor；
- multipart；
- Job 创建；
- 下载未就绪；
- 资源大小边界。

## 1.5 E2E / Runtime Test

回答：

> 用户实际操作链是否能从页面/入口一直走通？

不应拿 E2E 代替 Unit/Contract；否则任何失败都只能得到“页面坏了”而不知道根因。

# 2. 从仓库根运行后端测试

后端唯一 Python 工程根是仓库根，不在 `backend/` 里维护第二套项目。

常用：

```bash
uv run pytest tests/unit -q
uv run pytest tests/contracts -q
uv run pytest tests/api -q
uv run pytest tests/integration -q
```

只改一个功能时，先跑目标文件/关键字，而不是每次第一步就全仓：

```bash
uv run pytest tests/unit/collection -q
uv run pytest tests/unit -q -k scheduler
uv run pytest tests/unit -q -k content_label
```

具体目标文件以当前 `tests/` 目录为准。

最终交付仍需要根据影响面跑完整相关门禁和 PR 最新 HEAD CI。

# 3. 静态检查和仓库级质量门禁

当前常用：

```bash
uv run ruff format --check backend tests scripts
uv run ruff check backend tests scripts
uv run mypy backend/src
python scripts/quality/check_architecture.py
python scripts/quality/check_table_ownership.py
python scripts/quality/scan_secrets.py

```

这些分别防：

```text
Ruff
→ 格式/静态问题

mypy
→ 类型边界漂移

check_architecture.py
→ 违反仓库模块依赖/结构约束

check_table_ownership.py
→ 多模块写同一业务表

→ Secret/敏感内容误提交

check_docs.py
→ 文档链接/要求的文档一致性
```

如果某个检查失败，修真实根因，不删除门禁或降低断言。

# 4. PostgreSQL Integration 怎么准备

当前本地数据库连接/config 事实源只有：

```text
env.local.example
backend/src/aima_ugc/platform/config/settings.py
```

**当前仓库没有 `compose.yaml` 或 `compose.local.yaml`，也没有仓库内的一键本地 PostgreSQL Compose。** 不要按旧文档去找这些文件。开发者需要自行提供一个可访问的 PostgreSQL 18 实例；CI 会使用隔离 PostgreSQL 18 验证数据库语义，但 CI 的 Service Container 不等于仓库已经提供本地/生产 Compose。

Secret 通过：

```text
AIMA_SECRET_DIR
```

下的只读文件提供，不把数据库密码直接写进测试代码或命令历史。

当前 PostgreSQL 主版本：

```text
18
```

第一次跑 Integration Test 前，应先：

1. 按 [`02_环境运行与部署.md`](02_环境运行与部署.md) 配好环境变量和 Secret，并准备一个可访问的隔离 PostgreSQL 18 实例；
2. 确认 Migration 已到测试要求的 Revision；
3. 确认测试数据库是隔离库，不连接生产/真实业务库；
4. 再跑 `tests/integration/`。

如果 Integration Test 失败，先区分：

```text
连接/环境失败
vs
Migration 失败
vs
数据库约束正确地拒绝了错误代码
vs
业务逻辑失败
```

不要为了本地连接方便改成 SQLite，也不要为了“补齐文档中的命令”提前伪造未实现的 Compose 配置；正式 Docker/Compose 属于 Roadmap Stage 11A。

# 5. Migration 变化怎么验证

数据库结构变化至少检查：

```bash
uv run alembic current
uv run alembic heads
uv run alembic history
uv run alembic check
```

在隔离 PostgreSQL 中验证：

```text
旧 Revision
→ upgrade head
→ 目标 Integration Tests
```

如果该 Migration 支持安全 downgrade，再验证：

```text
head
→ downgrade 前一 Revision
→ upgrade head
```

有些 Migration 在已经存在新业务事实时应**故意拒绝危险 downgrade**；不能为了“测试全绿”删保护。

历史 Migration 不改写。

# 6. TikHub Operation / Mapper 怎么测试

## 6.1 默认不用真实 TikHub

测试输入优先：

```text
tests/fixtures/providers/tikhub/
```

典型链：

```text
Sanitized Raw Fixture
→ production Operation Extractor
→ production Mapper
→ Canonical Contract
```

这样可以验证：

- JSON 路径；
- 稳定 ID；
- Pagination；
- `observed_fields`；
- 评论树；
- 真实字段类型；

而不产生真实费用。

## 6.2 Endpoint 变化时

推荐 Red：

```text
新真实 Sanitized Fixture
→ 当前 Extractor/Mapper 测试失败
```

Green：

```text
修改 operations/<platform>.py / mappers/<platform>.py
```

再跑：

- Operation Unit；
- Mapper Unit/Contract；
- Canonical；
- 必要的 PostgreSQL Ingestion Vertical Slice。

## 6.3 不要伪造“真实 Fixture”

禁止从：

- TikHub 官网示例；
- 历史聊天；
- 自己脑补字段；

拼一个 JSON 然后称为 Real Fixture。

真实 Fixture 只能来自受控 Real Probe，脱敏后入库。

详细结构：

[`appendix/03_TikHub五平台真实响应与字段映射.md`](appendix/03_TikHub五平台真实响应与字段映射.md)

# 7. TikHub Real Probe 怎么做

真实 Probe 不是普通测试。

必须满足：

- 用户/任务明确需要真实验证；

- Secret 不写日志/Fixture；

# 15. 离线 AI 9 万条怎么验证

当前 `offline_labeling.py` 默认最大并发：

```text
250
```

但验证重点不是只看速度。

至少观察：

```text
preflight
canary
checkpoint
attempts
failed
peak_in_flight
llm_http_requests
transport_retries
input/output/cache tokens
cost totals
irrelevant removed
```

### 第一条 Canary 必须先过

错误 Secret/Base URL/Model/余额问题应在大并发开始前暴露。

### Checkpoint 恢复

中途停止后重新运行，已经成功且 identity/hash 一致的内容不应重新付费调用。

### 不要为了压测直接把并发继续加大

先确认：

- Provider 限流；
- 网络延迟；
- HTTP pool；
- Retry；
- checkpoint I/O；
- 账户并发限制。

# 21. CI 怎么理解

`.github/workflows/` 当前有主 CI 和若干 Stage/专项工作流，例如：

```text
ci.yml
stage1-stage7-audit-correctness.yml
stage4-job-runtime.yml
stage5a-provider-raw.yml
stage5b-collection-execution.yml
stage5c-provider-persistence.yml
stage5d-provider-dispatch.yml
stage6-xiaohongshu-vertical-slice.yml
stage7-keyword-packs.yml
stage7-plan-occurrence-run-snapshot.yml
stage7-provider-config-routing.yml
stage7-scheduler-runtime.yml
stage7-tikhub-real-shape.yml
```

工作流名字带历史 Stage，不代表只保护历史代码；其中很多已经成为当前长期回归门禁。

最终判断必须用：

```text
PR 最新 HEAD
```

对应的新鲜 Workflow Run。

不能：

- 引用旧 commit 的绿灯；
- 只说“主 CI 绿了”而忽略同 HEAD 专项失败；
- 把 cancelled/queued 当通过。

# 22. CI 失败怎么查

顺序：

```text
Workflow Run
→ Failed Job
→ Failed Step
→ Job Log
→ 找第一条真实错误
```

不要只看最后一句：

```text
Process completed with exit code 1
```

例如文档重构后多个 Stage Workflow 同时失败，可能是它们共同引用一个旧路径测试；应修共同根因，而不是逐 Workflow 关检查。

---

# 23. 测试失败时不要做什么

禁止：

- `pytest.skip()` 掩盖真实回归；
- 删除断言；
- 把严格 Contract 改成 `extra=ignore`；
- 去掉数据库 CHECK/UNIQUE；
- 给 Test 环境专门硬编码成功路径；
- 降低 Secret Scan；
- 为通过文档测试恢复已经废弃的旧文档结构；
- 用 Sleep 修并发竞态而不修同步/事务。

如果门禁本身绑死了已经正式改变的文档路径/架构，应该**同步更新门禁测试的长期语义**，而不是恢复过期结构。

---

# 24. 一次修改的推荐验证顺序

例如改 TikHub Mapper：

```text
目标 Fixture/Mapper Unit
→ Canonical Contract
→ Collection Unit
→ 必要 PostgreSQL Vertical Slice
→ Ruff / mypy
→ docs/quality
→ PR CI
```

改 Analysis Contract：

```text
Prompt/Contract/Validator Unit
→ Analysis Persistence Integration
→ API Contract
→ OpenAPI / Client
→ Frontend
→ Excel projection
→ CI
```

改 Word：

```text
Reporting Unit
→ OOXML structure
→ imports_test wiring
→ 生成代表性 DOCX
→ 目标办公软件视觉抽查
→ CI
```

改文档：

```text
当前机器事实对照
→ check_docs
→ 旧路径/旧事实检查
→ 受文档结构约束的回归测试
→ CI
```

# 25. 什么证据才支持“完成”

最终报告至少要有：

```text
改了什么
为什么改
哪些文件
哪些 Contract/Schema/Migration 受影响
实际跑了哪些验证
结果是什么
哪些没验证
PR 最新 HEAD CI
Git/PR/merge 状态
```

只有当前 HEAD 的实际结果，才能宣称：

```text
通过
可合并
完成
```

测试/调试的目标不是“让绿色勾变多”，而是让错误尽量在最接近根因的层被发现。
