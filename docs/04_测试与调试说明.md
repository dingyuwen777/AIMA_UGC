# 测试与调试说明

本文只维护 **AIMA_UGC 自己有哪些验证资产、命令、真实依赖和排障入口**。

通用“怎样设计测试、怎样从风险选择证据、怎样判断完成”的方法由 Agent_Skills 通过 [AGENTS.md](../AGENTS.md) 提供；本页不再维护第二套 Testing 方法论。

代码定位先看 [docs/01_代码结构与修改导航.md](01_代码结构与修改导航.md)。

## 1. AIMA 当前验证资产

仓库主要资产：

~~~text
tests/unit/
tests/contracts/
tests/api/
tests/integration/
tests/fixtures/

frontend/tests/
frontend/e2e/
frontend/e2e-fullstack/

scripts/quality/
.github/workflows/
~~~

它们分别覆盖局部行为、公共 Contract、HTTP、真实 PostgreSQL、稳定 Fixture、前端组件/页面、Browser Acceptance、真实跨组件链和仓库治理。

哪几层对本次任务是 required，由当前 Agent_Skills 和项目 changed-scope CI 共同决定；不要机械全跑，也不要把一层绿色外推成另一层已经证明。

## 2. 后端测试从仓库根运行

AIMA 只有一个 Python / uv 工程根。

常用入口：

~~~bash
uv run pytest tests/unit -q
uv run pytest tests/contracts -q
uv run pytest tests/api -q
uv run pytest tests/integration -q
~~~

针对性调试优先定位到目标目录、文件或 -k 表达式；当前真实测试名以 tests/ 目录为准。

## 3. 静态和仓库质量门禁

当前主要机器检查：

~~~bash
uv run ruff format --check backend tests scripts
uv run ruff check backend tests scripts
uv run mypy backend/src
python scripts/quality/check_architecture.py
python scripts/quality/check_table_ownership.py
python scripts/quality/scan_secrets.py
python scripts/quality/check_docs.py
python scripts/quality/check_docs_facts.py
python scripts/quality/check_agent_governance.py
python scripts/quality/check_change_completion.py --root .
~~~

职责：

| 入口 | 主要证明 |
| --- | --- |
| Ruff / mypy | Python 格式、静态和类型边界 |
| [scripts/quality/check_architecture.py](../scripts/quality/check_architecture.py) | 模块结构和依赖约束 |
| [scripts/quality/check_table_ownership.py](../scripts/quality/check_table_ownership.py) | 业务表单一写 Owner |
| [scripts/quality/scan_secrets.py](../scripts/quality/scan_secrets.py) | Secret/敏感内容不误提交 |
| [scripts/quality/check_docs.py](../scripts/quality/check_docs.py) | 文档入口、链接和项目文档治理 |
| [scripts/quality/check_docs_facts.py](../scripts/quality/check_docs_facts.py) | 少量适合机器同步的文档事实与生命周期 |
| [scripts/quality/check_agent_governance.py](../scripts/quality/check_agent_governance.py) | AIMA 项目治理接线 |
| [scripts/quality/check_change_completion.py](../scripts/quality/check_change_completion.py) | AIMA Change carrier Ready/Completion 门禁 |

门禁绑错长期语义时应修门禁；不要为了通过而恢复已经正式退役的旧结构。

## 4. PostgreSQL Integration

真实数据库语义必须使用 PostgreSQL 验证，例如：

- UNIQUE / FK / CHECK；
- Row lock；
- SKIP LOCKED；
- Job Lease / Fencing；
- Scheduler 并发；
- Content Current / Version / Metric；
- Import / Replay / Revocation；
- Analysis / Export 持久化；
- Migration。

本地开发环境入口：

- [scripts/dev/backend.py](../scripts/dev/backend.py)
- [env.local.example](../env.local.example)
- [compose.yaml](../compose.yaml)

CI 会根据 changed scope 选择 PostgreSQL suite；测试代码继续以 [tests/integration/](../tests/integration/) 为机器事实。

SQLite/Fake 可以用于局部逻辑，但不能冒充 PostgreSQL 锁、约束和事务证据。

## 5. Migration

Schema/Migration 变化至少核对：

~~~text
SQLAlchemy metadata
→ Alembic revision
→ upgrade / downgrade 边界
→ alembic check
→ 相关 PostgreSQL Integration
→ 部署/回滚说明
~~~

Migration 机器事实位于 [migrations/versions/](../migrations/versions/)。

大规模历史回填不应为了“跟 Migration 一起”塞进 DDL 事务；这类能力使用持久 Job 和 Operations 验证。

## 20. CI 当前职责

永久 Workflow 的精确集合由 [docs/README.md](README.md) 的受控事实块与 [.github/workflows/](../.github/workflows/) 持有。

主要职责：

| Workflow | 责任 |
| --- | --- |
| CI | Requirement/Change、文档/Secret、changed-scope 质量、后端/前端/Contract/PostgreSQL 证据 |
| Full-stack | 少量真实 Browser → API → DB/Worker Golden Path |
| Runtime | Dockerfile / Compose / bootstrap / readiness / persistence 等 Runtime 交付边界 |
| Tooling | 本地 launcher、Windows 工具链、Compose CLI 等开发环境兼容 |
| Change Archive | merged Change 的 active → archive/done |
| Release | 离线 Bundle replay、镜像/manifest 和 GitHub Release |

Draft、metadata-only 和 changed-scope 优化的精确条件以 Workflow 和 [scripts/quality/classify_ci_scope.py](../scripts/quality/classify_ci_scope.py) 为机器事实，不在本页复制完整 if 表达式。

最终合并判断使用当前 PR Head 对应的 required checks；不要引用旧 SHA 的 Green。

## 21. 失败怎么定位

优先找第一层真实失败：

~~~text
Requirement / Contract 不一致
→ 先修需求或实现

Unit / Component
→ 查局部逻辑

Contract / OpenAPI
→ 查生产者消费者

PostgreSQL Integration
→ 查事务、锁、约束、Repository

Browser Mock
→ 查前端状态和交互

Real Full-stack
→ 查真实跨组件组装

Runtime
→ 查镜像、Compose、Secret、Readiness、持久化

Provider Probe
→ 查外部当前事实
~~~

CI 日志从 Failed Job → Failed Step → 第一条真实错误开始，不以最后一句 exit code 1 作为根因。

## 22. 本页不再维护什么

以下通用方法回到 Agent_Skills：

- Unit/Contract/Integration/E2E 的通用定义；
- 固定“先跑哪层再跑哪层”的跨项目模板；
- 如何判断最小充分验证；
- Review 的测试充分性方法；
- “测试通过是否等于完成”的通用完成定义；
- 通用禁止降低断言/删测试规则。

AIMA 本页长期只保留：**有什么测试资产、怎么运行、哪些真实依赖不能被 Mock 冒充、每个业务域从哪里开始验证。**
