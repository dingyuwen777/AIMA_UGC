# AIMA_UGC 代码结构与修改导航

本文是给开发者和接手项目的人看的**代码学习入口**。它不替代 Blueprint、模块 README 或 Appendix，而是解决一个更实用的问题：

> 我知道业务要改什么，但仓库这么多目录，我应该从哪里开始读、改哪些文件、哪些地方不能乱动、改完跑什么测试？

如果你只想先理解系统全貌，先读 `docs/blueprint/01-总体架构与技术选型.md`；如果准备真正改代码，再回到本文。

---

## 1. 先建立最小代码地图

后端核心目录：

```text
backend/src/aima_ugc/
├─ entrypoints/   # 进程启动入口
├─ bootstrap/     # 把真实数据库、Provider、Repository、Service、Job 装配起来
├─ modules/       # 业务规则、状态机、领域模型
├─ adapters/      # TikHub、LLM、PostgreSQL 等外部实现
├─ platform/      # Job、Artifact、数据库、日志、Export、Reporting 等公共能力
└─ contracts/     # Pydantic 业务/HTTP Contract
```

前端核心目录：

```text
frontend/src/
├─ app/           # Router、Layout
├─ features/      # 正式业务 Feature
├─ generated/     # OpenAPI 自动生成 Client，禁止手改
├─ shared/        # 公共前端能力
└─ views/         # 顶层 View
```

数据库结构：

```text
migrations/versions/   # Alembic 向前 Migration
```

测试：

```text
tests/
├─ unit/
├─ contracts/
├─ api/
└─ integration/
```

### 1.1 五类代码分别负责什么

| 层 | 你应该在这里找什么 | 不应该在这里做什么 |
| --- | --- | --- |
| `entrypoints/` | API / Worker / Scheduler / Migration 进程入口 | 放业务规则 |
| `bootstrap/` | 把真实依赖接起来、事务编排、生产 Service 装配 | 复制领域规则 |
| `modules/` | 领域规则、状态机、Service Port、表 Owner 定义 | 直接访问第三方 HTTP |
| `adapters/` | TikHub、LLM、PostgreSQL 等具体实现 | 改公共业务 Contract |
| `platform/` | Job、Artifact、数据库、导出、日志等通用能力 | 写某个平台私有业务逻辑 |

判断一个文件是不是“真入口”，先看它属于哪一层，不要只凭类名猜。

## 2. 四个正式进程从哪里启动

| 进程 | 入口 | 真实装配 | 作用 |
| --- | --- | --- | --- |
| API | `backend/src/aima_ugc/entrypoints/api_main.py` | `backend/src/aima_ugc/bootstrap/api.py` | HTTP 查询、创建 Job、下载结果 |
| Worker | `backend/src/aima_ugc/entrypoints/worker_main.py` | `backend/src/aima_ugc/bootstrap/worker.py` | 执行 Collection / Import / Analysis / Export 等长任务 |
| Scheduler | `backend/src/aima_ugc/entrypoints/scheduler_main.py` | `backend/src/aima_ugc/bootstrap/scheduler.py` | 把到期 Plan 变成 Occurrence / Run / Job |
| Migration | `backend/src/aima_ugc/entrypoints/migrate_main.py` | `backend/src/aima_ugc/bootstrap/migration.py` | 升级 PostgreSQL Schema |

### 2.1 为什么长任务不在 API 请求里直接执行

正式链路：

```text
HTTP 请求
→ Service 校验
→ PostgreSQL 同事务创建业务父事实 + Job
→ HTTP 202 返回
→ Worker 认领 Job
→ 真正执行 TikHub / Excel / AI / Export
```

所以浏览器关闭或 API 重启，不会把长任务事实丢掉。

Job Runtime 代码：

```text
backend/src/aima_ugc/platform/jobs/
```

当前关键 Job 类型：

```text
collection.run.v1
ingestion.import-excel.v1
analysis.content-label.v1
reporting.content-export-excel.v1
```

如果你要改“重试、Lease、Heartbeat、Deadline、Fencing”，优先看 `platform/jobs/` 和相关 Job handler，不要在某个业务 Router 里临时加循环重试。

## 11. 调试时如何判断应该看哪层

### Provider 返回字段不对

```text
Raw / Fixture
→ Operation / Extractor
→ Mapper
```

### 数据库里同一帖子重复

```text
Canonical stable identity
→ ContentIngestionService
→ Content Owner Repository
→ Unique Constraint / Migration
```

### 旧值把新值覆盖了

```text
observed_at
→ observed_fields
→ field_observed_at
→ Ingestion freshness 逻辑
```

### Scheduler 重复入队

```text
resolve_scheduler_plan()
→ Plan 行锁
→ collection_schedule_occurrences 唯一约束
→ Job / Occurrence / Run 同事务
```

### AI 输出结构不合法

```text
Prompt
→ LLM raw response
→ RuntimeTaxonomyValidator
→ Validation Retry
```

### 前端筛选结果不对

```text
HTTP Query Contract
→ Query Service / Repository
→ Cursor snapshot
→ generated Client
→ Feature Store / Page
```

## 12. 改完代码最少要做什么验证

具体测试以任务影响面为准，但至少遵守：

```text
先跑目标 unit / contract / api / integration
→ 再跑静态检查
→ Schema 变化跑 Alembic old→head / downgrade-upgrade / alembic check
→ HTTP Contract 变化重新生成并检查 OpenAPI / frontend Client
→ 文档路径变化跑 check_docs.py
→ 最终以 PR 最新 head 的新鲜 CI 为准
```

常用质量入口：

```bash
uv run ruff format --check backend tests scripts
uv run ruff check backend tests scripts
uv run mypy backend/src
python scripts/quality/check_architecture.py
python scripts/quality/check_table_ownership.py
python scripts/quality/scan_secrets.py
```
