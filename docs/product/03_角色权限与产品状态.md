# 角色权限与产品状态

## 1. 当前角色模型

后端已经建立 Provider-neutral Principal 边界，当前业务角色只有：

- `administrator`：负责采集、AI 分析、人工复核、报告和全局配置等数据生产、运行与治理；
- `user`：查看、筛选、分析已有结果，保存自己的工作台布局和默认 Excel 字段，导出并下载自己的结果。

角色与企业身份提供方解耦。业务表和权限规则不以飞书 `open_id`、`union_id` 等 Provider 私有身份作为公共主键。

后端统一身份模型见 [`backend/src/aima_ugc/modules/identity/models.py`](../../backend/src/aima_ugc/modules/identity/models.py)。

## 2. 当前认证状态

当前代码同时支持两种装配：明确的本地开发/隔离测试使用 `AIMA_IDENTITY_MODE=development` 与 Development Identity Resolver；正式 Compose 默认 `feishu`，缺少完整 Connector/用户组/回调配置时 API 启动失败；配置单企业或多企业飞书 Connector 时，使用飞书 OAuth 登录、AIMA 自有 Session 和 Provider-neutral Principal 映射。**代码能力已接入，但仍不能等同于完整企业 Production 认证已经验收。**

当前企业认证链路遵循：

```text
企业身份提供方（当前计划为飞书）
→ OAuth 授权码与飞书用户/用户组校验
→ Identity Adapter
→ Principal
→ 后端 Authorization
```

因此当前状态应准确描述为：

- 角色语义和后端管理员授权边界：**已建立**；
- 最终业务 API 的显式认证、管理员权限与 Export 归属检查：**代码已实现，仍需对应环境验收**；
- 前端菜单、Route、声音广场操作和任务来源按当前角色控制；
- 飞书登录/回调、一次性 state、用户组角色判定、Principal 映射、Session 过期和主动登出撤销：**代码已实现**；
- 会话存续期内对飞书远端撤权/移组的周期复核：**尚未实现**，最迟在默认 8 小时会话过期后重新判定；
- 两家真实企业应用、浏览器回调与普通用户/管理员正反向授权：**仍待生产候选环境正式验收**；
- 对公网或扩大访问范围的完整认证安全验收：**尚未完成**。

Production 前置事项见 [`docs/roadmap/01_生产上线实施路线.md`](../roadmap/01_生产上线实施路线.md)。

## 3. 产品权限原则

1. **前端隐藏/禁用不等于授权。** 所有真正受保护的写操作必须由后端再次校验 Principal。
2. **普通用户不接触 Secret。** Provider/LLM API Key、Secret 路径和内部签名 Key 不能通过普通业务页面或日志暴露。
3. **管理员页面不等于系统管理后台万能入口。** 只有当前 Contract/后端真实支持的配置才能展示和修改。
4. **审计记录业务身份和安全差异，不保存 Secret 原值。**
5. **企业身份接入不能重写业务角色。** 飞书只是 Identity Adapter，不把 Provider 私有字段扩散到业务模块。

## 4. 两角色的业务边界

| 能力 | administrator | user |
| --- | --- | --- |
| 工作台、声音广场、内容、评论、有效 AI 结果与业务品牌车型目录 | 允许 | 允许 |
| 保存自己的工作台布局、默认 Excel 字段、读取和标记自己的通知 | 允许 | 允许 |
| 创建 Excel 导出 | 允许完整字段 | 允许业务字段 |
| Export 历史、详情与下载 | 全部合法记录 | 仅自己的合法记录 |
| 采集运行/策略/导入、AI Run、人工相关性/车型/情感/标签修订 | 允许 | 禁止 |
| Provider、模型、Prompt、品牌车型治理、管理报告、审计 | 允许 | 禁止 |

普通用户仅显示工作台和声音广场；直接访问管理 URL 显示“当前账号无管理员权限”，不加载管理数据。选择复选框、AI 信息列、评论和人工修订只读摘要仍可用。任务中心仅请求自己的 Export，不轮询采集与 Analysis Run；业务页面继续按原刷新周期、窗口恢复可见和手动刷新读取共享结果。

工作台布局与个人默认字段以 AIMA `principal_id` 跨设备保存。工作台和声音广场筛选仍使用 sessionStorage：同账号刷新保留，首次无法确认归属的旧缓存、登出和身份变化清理。账号重新验证后，旧身份的在途响应与 Pinia 缓存失效。

## 6. 什么时候需要新增角色或权限

只有出现真实业务职责差异，并且后端需要做不同授权判断时，才新增角色/权限模型。不要因为页面上有不同菜单就提前设计复杂 RBAC，也不要为了接入某个身份提供方把 Provider 的组织结构直接变成业务权限模型。
