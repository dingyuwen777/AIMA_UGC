# 前端与 Figma 工作流

这篇指南解决：**页面先在 Figma 里设计以后，怎样尽量顺畅地变成当前 Vue 代码，又怎样避免“设计稿看起来对，但生成的代码绕过现有 API/模块边界”。**

系统前端架构原则见 [`../blueprint/04-后端任务API与前端.md`](../blueprint/04-后端任务API与前端.md)。这里讲工作方法。

## 1. Figma 解决的不是“能不能写出页面”

只给 AI 一张截图，也可以生成 HTML/CSS/Vue。Figma 的主要价值是：

- 多个页面共享同一套视觉规则；
- 组件和状态可以复用；
- 设计改动有明确位置；
- 多人能讨论同一个设计事实；
- 页面越来越多时，不需要靠历史截图猜按钮、间距和组件关系。

所以：

```text
快速试一个单页想法
→ 截图/低保真原型就够

长期维护、多页面、多人协作
→ Figma 更值得作为设计资产
```

## 2. 当前前端真正的代码边界

当前仓库前端已经有正式业务结构，不是一个空 Demo：

```text
frontend/src/
├─ app/
├─ pages/
├─ features/
│  ├─ analysis/
│  ├─ export/
│  ├─ import-excel/
│  ├─ jobs/
│  ├─ keyword-planning/
│  ├─ overview/
│  ├─ providers/
│  ├─ runs/
│  ├─ settings/
│  └─ voice-plaza/
├─ shared/
└─ generated/
   └─ api/
```

白话理解：

- `pages/`：一个完整页面怎么组合；
- `features/`：一个具体业务能力，例如声音广场、运行列表；
- `shared/`：真正跨业务复用的通用组件/工具；
- `generated/api/`：从后端 OpenAPI 自动生成的调用代码，禁止手改；
- `app/`：应用级路由和装配。

Figma 只能决定“页面长什么样、有哪些交互状态”，不能替代这些业务边界。

## 3. 推荐工作流

```text
需求/现有页面
→ Figma 画页面和状态
→ 标注可复用组件/Token
→ 核对现有 API 是否支持交互
→ Design-to-Code 生成/辅助生成 Vue
→ 放入正确 Page/Feature/Shared
→ 接生成 Client
→ 视觉与行为验证
```

顺序中最重要的一步是：**生成代码前先核对 API 和已有 Feature。**

否则很容易生成：

- 假数据；
- 页面直接 `fetch()` 另造 Client；
- 前端自己猜后端字段；
- 同一个 Run 列表写两套 Store；
- 按钮看起来能点，实际后端没有对应行为。

## 4. Figma 里应该画到什么程度

### 至少要有

- 页面整体布局；
- 导航和页面标题；
- 筛选/搜索区；
- 表格/卡片/图表区域；
- 按钮和操作入口；
- 空数据；
- Loading；
- Error；
- Disabled；
- 弹窗/抽屉；
- 关键响应式变化。

### 不必在 Figma 里复制后端事实

例如：

- 完整 OpenAPI 字段；
- SQL 表结构；
- Job Lease/Fencing；
- Provider 私有参数。

设计稿可以写“运行状态”“来源平台”这些人类字段，但精确类型和合法值仍由生成 Client/Contract 提供。

## 5. 一个页面有很多按钮和子页面怎么办

Figma 可以把同一页面的不同状态做成多个 Frame/Component Variant，例如：

```text
采集运行中心 / 默认
采集运行中心 / 筛选展开
采集运行中心 / Run 详情抽屉
采集运行中心 / 空数据
采集运行中心 / 加载失败
```

如果网页端 Figma 插件一次只能捕获当前 DOM 状态，就逐状态打开后分别导入，不要期待一个静态页面自动推断所有隐藏状态。

真正的交互关系再用 Prototype 连线表达。

## 6. 什么是交互原型

交互原型不是“已经写好的前端代码”。它表达：

```text
点击哪里
→ 页面发生什么变化
→ 去哪个页面/弹哪个抽屉
→ 哪些状态可返回
```

例如：

```text
声音广场卡片
→ 点击“查看详情”
→ 右侧 Detail Drawer
→ 点击“AI 打标”
→ Loading
→ 成功后显示 sentiment / voice_type / labels
```

这能让开发者/AI 知道真正需要实现的状态，不只看到一张漂亮截图。

## 7. Figma 组件怎么对应 Vue 组件

不要机械做到“一层 Figma Frame = 一个 Vue 文件”。

更实用的判断：

### 适合做公共组件

- 多个页面真实重复；
- 输入/输出稳定；
- 视觉和行为确实一致。

例如：

```text
状态 Badge
空状态
标准页面标题
日期筛选
```

### 只属于一个 Feature

例如“声音广场舆情卡片”虽然内部复杂，但只有 Voice Plaza 使用，就先放该 Feature，不要为了“组件化”过早搬到 `shared/`。

## 8. Design Token 用来解决什么

Token 可以理解成：**给反复出现的视觉值起统一名字。**

例如：

```text
页面横向间距
卡片圆角
标题字号
品牌主色
危险状态色
表格密度
```

它的价值不是术语，而是避免：

```text
页面 A 的蓝色 #1677ff
页面 B 的蓝色 #1a73e8
页面 C 又凭感觉写一个
```

如果现有代码已经有 CSS variables/主题变量，应优先映射现有事实，不在 Figma 和代码里各维护一套同义 Token。

## 9. 从现有网页反向导入 Figma

适合：

- 代码里已经有页面，想形成设计基线；
- 旧页面要重新设计；
- 想让后续新页面复用已有视觉。

建议流程：

```text
1. 打开一个确定状态的页面
2. 导入 Figma
3. 清理自动生成的无意义嵌套
4. 抽取真正共享的组件/Token
5. 逐个导入其他重要状态/页面
6. 建立 Prototype 关系
```

自动导入只是“把像素/DOM 变成可编辑图层”的起点，不等于已经形成高质量设计系统。

## 10. 代码改了，能不能自动同步回 Figma

不要把 Figma 和代码理解成双向实时数据库。

实际可行模式通常是：

```text
设计主导的改动
Figma → 代码

代码里临时修正/新状态
→ 再把实际页面捕获回 Figma
→ 人工确认并沉淀为新设计事实
```

小改动不必每次立刻反向同步；影响公共组件、布局规则或长期页面状态时应该同步，否则设计资产会逐渐失真。

## 11. 当前项目推荐的页面交付单位

一份完整页面设计最好同时给：

```text
1. 默认状态
2. Loading
3. Empty
4. Error
5. 关键筛选/交互状态
6. 详情 Drawer/Dialog
7. 桌面主要分辨率
8. 必要的窄屏行为
9. 使用到的现有/新增组件
10. 对应后端 API/Feature
```

这样 Design-to-Code 才是在明确约束下生成，而不是让模型猜业务。

## 12. 视觉验收不要只看“差不多”

建议至少检查：

- 页面宽高与主要区域；
- 间距；
- 字号/字重；
- 颜色；
- 表格密度；
- 文本截断；
- Loading/Empty/Error；
- Drawer/Dialog；
- 真实数据长文本；
- 响应式断点。

对关键页面可以用 Playwright 截图/视觉基线辅助验证，但不要让截图测试替代功能测试。

## 13. 什么时候可以直接截图 + AI，不走 Figma

适合：

- 一次性 Demo；
- 单页面快速探索；
- 只改很小一块样式；
- 还没确定是否保留的功能；
- 用几小时验证一个想法。

不适合：

- 页面已经很多；
- 多人并行；
- 同一组件反复出现；
- 未来会长期维护；
- 页面需要统一品牌风格；
- 需要稳定的交互状态说明。

## 14. 当前实现必须保持的边界

无论 Figma 怎么画：

```text
Page
→ Feature Store / Feature API
→ OpenAPI Generated Client
→ 后端 HTTP API
```

禁止：

- 页面直接访问 PostgreSQL；
- 手写第二个业务 HTTP Client；
- 修改 `frontend/src/generated/api/`；
- Feature 复制另一个 Feature 的 Store/API；
- 仅为了还原 Figma 就改变后端 Contract；
- 设计稿不存在的后端能力由前端“模拟成已实现”。
