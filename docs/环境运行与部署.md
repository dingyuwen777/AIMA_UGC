# 环境、运行与部署

本文是 AIMA_UGC 的日常运行入口。优先回答：**拿到源码以后，怎样用最少步骤在 Windows 或 Linux 上把真实后端、PostgreSQL、Worker 和 Vue 前端跑起来。**

架构、Schema、Contract 和生产部署边界仍分别以 `AGENTS.md`、`docs/blueprint/`、Migration、代码和 Roadmap 为准。本文不把本地源码调试入口描述成生产部署方案。

---

# 1. 本地开发快速开始

本地源码调试只需要记两个命令。Windows 和 Linux 使用**完全相同**的正式入口。

## 1.1 前提

开发机已经具备仓库锁定版本的：

```text
Python
uv
Node.js
npm
Docker CLI + Docker Engine
```

精确版本事实源：

```text
.python-version
.uv-version
.node-version
frontend/package.json
uv.lock
frontend/package-lock.json
```

Windows 第一次准备工具链可继续使用：

```powershell
scripts\setup_dev_environment.cmd
```

Linux 的工具链安装与应用启动是两件事。仓库现有 `scripts/setup_dev_environment.sh` 是 CentOS Stream 9 x86_64 的特定宿主初始化脚本；不应把它当成应用日常启动命令。只要目标 Linux 已准备正确版本的 Python/uv/Node/npm/Docker，下面两个 Python launcher 与 Windows 共用同一实现。

## 1.2 终端 1：启动完整本地后端

从仓库根执行：

```bash
uv run python scripts/dev/backend.py
```

这个命令不是“只启动 FastAPI”。它会把本地业务运行所需的基础组件准备好，再启动正式 API/Worker。

成功后主要地址：

```text
API          http://127.0.0.1:8090
Readiness    http://127.0.0.1:8090/health/ready
```

## 1.3 终端 2：启动前端

从仓库根执行：

```bash
uv run python scripts/dev/frontend.py
```

浏览器访问：

```text
http://127.0.0.1:5173/
```

Vite 会把 `/api` 和 `/health` 代理到本地 FastAPI。

因此日常源码开发的心智模型固定为：

```text
终端 1：backend.py
终端 2：frontend.py
浏览器：127.0.0.1:5173
```

不再要求开发者手工拼接 PostgreSQL、Migration、多个 Secret 和 Worker 启动命令。

# 2. 第一次运行 Backend 会自动做什么

第一次执行：

```bash
uv run python scripts/dev/backend.py
```

启动器按顺序处理：

```text
检查/创建 env.local
→ 创建 .runtime 本地目录
→ 如发现旧单 Secret 根，原值迁移 AIMA 内部 Secret 到 .runtime/internal-secrets
→ 自动生成仍缺失的数据库密码和三个 Cursor signing key
→ 检查 Docker Engine
→ 创建或启动 PostgreSQL 18.4 本地容器
→ 等 PostgreSQL ready
→ alembic upgrade head
→ 按 env.local 准备 TikHub / LLM 外部 Secret
→ 幂等维护本地 TikHub Provider Config
→ 启动正式 Worker
→ 按需启动 Scheduler
→ 启动 FastAPI
→ 等待 /health/ready = 200
→ 输出当前功能可用状态
```

本地 PostgreSQL 固定使用：

```text
image      postgres:18.4
container  aima-ugc-postgres-dev
volume     aima-ugc-postgres-dev-data
host       127.0.0.1
port       5432
database   aima_ugc
user       aima_ugc
```

数据库密码由启动器随机生成，不要求开发者填写，也不写入 Git。密码文件固定为：

```text
.runtime/internal-secrets/postgres_password
```

PostgreSQL 数据保存在 Docker named volume 中；关闭 `backend.py` 不删除容器数据。

## 2.1 后续启动

以后再次运行同一命令时：

```text
既有 PostgreSQL 容器在运行
→ 直接复用

容器已停止
→ 自动启动

Migration 已在 head
→ upgrade head 幂等返回

已有 Secret
→ 继续复用，不静默轮换
```

因此不需要每次重新配置数据库。

### 从旧本地目录升级

旧版本把内部 Secret 和 TikHub/LLM Secret 都放在 `.runtime/secrets/`。当前 launcher 第一次启动时会把以下四个内部 Secret **保持原值**迁移到 `.runtime/internal-secrets/`：

```text
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
```

这样已有 `aima-ugc-postgres-dev-data` volume 仍使用原数据库密码，不会因为目录升级重新生成密码。若新旧目录同时存在同名内部 Secret 且内容不同，launcher 会 fail closed，要求人工确认，不会覆盖或轮换任何一边。

# 3. `env.local` 到底是什么

仓库提交的是：

```text
env.local.example
```

真实本地文件：

```text
env.local
```

已经加入 `.gitignore`。

第一次运行 Backend 或 Frontend 时，如果 `env.local` 不存在，launcher 会自动从 `env.local.example` 复制一份；开发者不需要先手工创建。

`env.local` **只属于源码开发 launcher 的输入界面，不是生产运行时 Contract**。

正式 API/Worker/Scheduler 在本地和生产都使用同一类双 Secret 根语义：

```text
非敏感运行配置
→ AIMA_* 子进程环境

AIMA 内部 Secret
→ AIMA_SECRET_DIR
→ 本地 .runtime/internal-secrets/

外部 Provider / LLM Secret
→ AIMA_EXTERNAL_SECRET_DIR
→ 本地 .runtime/secrets/

Provider Config
→ PostgreSQL 只保存 secret_ref
```

Dev launcher 读取 `env.local` 后会把 TikHub/LLM API Key 写到 `.runtime/secrets/`，并从正式子进程环境中移除本地明文 Key。PostgreSQL password 和三个 Cursor signing key 只位于 `.runtime/internal-secrets/`。生产部署由 Internal V1-A 的 Compose/Secret mount 实现同样的内部/外部分层，不读取 `env.local`。

---

# 4. `env.local` 现在只需要配置什么

默认文件非常短：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=

AIMA_LLM_BASE_URL=
AIMA_LLM_PROVIDER_NAME=
AIMA_LLM_MODEL=
AIMA_LLM_API_KEY=

AIMA_DEV_ENABLE_SCHEDULER=false
```

数据库 Host、Port、用户名、密码、数据目录、日志轮转、Cursor Key、Migration、Worker lease 等内部运行细节不属于日常本地配置，不再要求开发者填写。

## 4.1 什么都不填也能做什么

TikHub 和 LLM 都留空时，Backend 仍正常启动：

```text
Excel Import     AVAILABLE
Voice Plaza      AVAILABLE
Excel Export     AVAILABLE
TikHub           NOT CONFIGURED
AI Analysis      NOT CONFIGURED
Scheduler        DISABLED
```

`NOT CONFIGURED` 是 Warning，不是整个系统的启动错误。

真正会阻止 Backend 启动的是基础依赖失败，例如：

```text
Docker CLI / Docker Engine 不可用
PostgreSQL 容器创建或启动失败
PostgreSQL 无法 ready
Alembic Migration 失败
Worker/API 启动失败
/health/ready 无法通过
```

# 5. 要测试 TikHub 时怎么配置

只修改本机 `env.local`：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=<你的本地调试 Key>
```

然后重启：

```bash
uv run python scripts/dev/backend.py
```

启动器会：

```text
env.local 的 Key
→ .runtime/secrets/tikhub_api_key

PostgreSQL Provider Config
→ provider=tikhub
→ display_name=TikHub Local Dev
→ base_url=<env.local>
→ secret_ref=tikhub_api_key
→ enabled=true
```

数据库不保存真实 API Key。

如果把 `AIMA_TIKHUB_API_KEY` 再清空并重启，launcher 会删除对应本地 Secret，并禁用自己的 `TikHub Local Dev` Provider Config，避免前端继续把一个不可执行的本地 Provider 暴露成可用配置。

普通 CI 不读取你的真实 Key，也不会因为本地启动功能增加付费 TikHub 请求。

# 6. 要测试 AI 打标时怎么配置

只修改本机 `env.local`：

```dotenv
AIMA_LLM_BASE_URL=https://your-provider.example/v1
AIMA_LLM_PROVIDER_NAME=your-provider
AIMA_LLM_MODEL=your-model
AIMA_LLM_API_KEY=<你的本地调试 Key>
```

其中 `AIMA_LLM_PROVIDER_NAME` 可以在当前 Adapter 能从 Base URL 明确推导时留空；Base URL、Model、API Key 是实际启用 AI 所需的核心项。

重启 Backend 后：

```text
API Key
→ .runtime/secrets/llm_api_key

Base URL / Provider / Model
→ 正式 AIMA_LLM_* Runtime 配置

Worker
→ 正式 Content Analysis Job
→ LLM Adapter
```

如果只填了一部分 LLM 配置，Backend 会显示 Warning，并把 AI 视为未配置；不会让一组半完成配置污染正式 Worker Runtime。

声音广场同时通过正式能力接口读取安全布尔能力；浏览器不会收到 Secret 原值。Import 和普通 TikHub Collection 不会因为 LLM 配置存在就自动发起 AI 付费调用，只有显式创建 AI Analysis Job 才调用模型。

---

# 7. Scheduler 为什么默认关闭

本地默认：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=false
```

原因是本地数据库可能保留 enabled Collection Plan。若启动源码环境时自动开启 Scheduler，旧 Plan 可能立即创建真实 TikHub Run 并产生费用。

需要专门调试周期采集时才改为：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=true
```

然后重启同一个 `backend.py`。不需要记第三条 Scheduler 启动命令。

手工 TikHub Discovery / Batch Supplement 不依赖 Scheduler；它们依赖 API + Worker。

# 8. 前端第一次运行需要“编译”吗

本地开发不需要先执行 production build。

第一次执行：

```bash
uv run python scripts/dev/frontend.py
```

launcher 会：

```text
检查 Node/npm 精确版本
→ 检查 frontend/node_modules
→ 检查 package-lock.json 指纹
→ 首次或 lock 变化时自动 npm ci
→ npm run dev
→ Vite Development Server
```

Vite 在开发时实时处理 Vue / TypeScript / CSS，并提供热更新。修改 `.vue` / `.ts` 后保存，浏览器会自动更新。

只有正式构建才执行：

```bash
npm --prefix frontend run build
```

它会生成生产 `frontend/dist/`。CI 会直接验证这个构建；Internal V1-A 的根 `Dockerfile` 也在 Frontend build stage 执行同一构建，并只把 `dist` 复制到 Nginx Runtime。日常源码调试不需要先做 production build。

# 9. 本地数据、文件、日志和 Secret 在哪里

本地源码调试的主要持久状态：

```text
PostgreSQL
→ Docker volume: aima-ugc-postgres-dev-data

Excel 输入 / Raw / Export 等 Artifact
→ .runtime/data/artifacts/

应用日志
→ .runtime/logs/
   ├─ api.log
   ├─ worker.log
   └─ scheduler.log（启用时）

AIMA 内部 Secret
→ .runtime/internal-secrets/
   ├─ postgres_password
   ├─ import_batch_cursor_signing_key
   ├─ content_cursor_signing_key
   └─ collection_runtime_cursor_signing_key

外部 Provider / LLM Secret
→ .runtime/secrets/
   ├─ tikhub_api_key（配置时）
   └─ llm_api_key（配置时）

Frontend 依赖锁指纹
→ .runtime/dev/frontend-package-lock.sha256
```

`.runtime/` 和 `env.local` 都被 Git 忽略。

上传的 Excel 原文件作为 Input Artifact 保存到 Local ArtifactStore，Import Batch、Job、Content 等业务事实保存到 PostgreSQL；因此完整 Excel Web 调试确实需要 PostgreSQL + Worker，而 `backend.py` 已自动把这两者包含在启动流程里。

# 10. 第一次导入 Excel 前还需要一个业务配置

本地运行配置可以自动准备，但**业务配置不能被 launcher 猜测**。

正式 Import/Collection 使用全局 Rule Relevance。一个全新数据库第一次使用时，请在前端：

```text
采集策略
→ 新建关键词包
→ 添加业务关键词（例如当前真正要监测的关键词）
→ 全局相关性
→ 选择该关键词包
```

然后再去：

```text
采集运行中心
→ 导入 Excel
```

不自动创建“爱玛”默认词包，是为了避免 dev launcher 变成业务配置的第二事实源。

# 11. 本地联调 Smoke

Backend 和 Frontend 都启动后，第三个终端可以执行：

```bash
uv run python scripts/dev/check_local_stack.py
```

它验证 FastAPI `/health/ready`、PostgreSQL/Artifact/log 可用，以及 Vite 与后端代理真实接通。页面能打开但 `/health/ready` 失败，不应被描述成完整本地业务环境已经可用。

# 12. 停止、重新启动和重置本地数据库

Backend 终端按 `Ctrl+C` 会停止 API、Worker 和本次启动的 Scheduler；PostgreSQL 容器与 named volume 默认保留。Frontend 终端按 `Ctrl+C` 停止 Vite。

如果明确要**破坏性清空本地开发数据库**，先停止 Backend，再手工执行：

```bash
docker rm -f aima-ugc-postgres-dev
docker volume rm aima-ugc-postgres-dev-data
```

随后删除与这个本地数据库绑定的自动密码：

```text
.runtime/internal-secrets/postgres_password
```

下次 `backend.py` 会重新创建空数据库、随机密码并执行全部 Migration。这只允许用于本地开发数据，不要把这组命令用于包含真实业务数据的服务器。

# 13. 高级开发：直接启动正式进程

日常优先使用两个 launcher。只有调试具体进程边界时才直接运行正式进程。

API：

```bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090 --reload --reload-dir backend/src
```

Worker：

```bash
uv run python -m aima_ugc.entrypoints.worker_main
```

Scheduler：

```bash
uv run python -m aima_ugc.entrypoints.scheduler_main
```

Migration：

```bash
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

直接启动这些正式进程时，调用者仍需自己提供它们要求的 `AIMA_*` 和 Secret File；这是高级调试路径，不是普通开发者快速开始。

# 15. 本地开发与 Internal V1-A 的边界

`scripts/dev/backend.py` / `frontend.py` 是**源码开发入口**，正式服务器不应长期使用 `uvicorn --reload`、`npm run dev` 或 `scripts/dev/*.py`。

本地和生产当前使用相同的 Secret 分类语义：`AIMA_SECRET_DIR` 保存 AIMA 内部随机 Secret，`AIMA_EXTERNAL_SECRET_DIR` 保存 Provider/LLM 外部 Secret；区别只在于本地由 launcher 管理 `.runtime/`，生产由 Compose Secret/bind mount 管理容器路径。

Internal V1-A 当前容器拓扑：

```text
bootstrap
→ 只负责宿主持久目录和内部随机 Secret

postgres
→ PostgreSQL 18.4

migrate
→ alembic upgrade head，一次性独立进程

configure
→ 幂等维护 Internal V1 Provider Config / 校验 LLM 配置，一次性独立进程

api / worker / scheduler
→ 正式后端进程

frontend
→ Vue build + 非 root Nginx，同源代理 /api 与 /health
```

持久目录继续由 `env.production` 指定，默认：

```text
PostgreSQL: /data/AIMA_UGC/postgres
Artifact:   /data/AIMA_UGC/runtime/data
日志:       /data/AIMA_UGC/runtime/logs
内部 Secret: /data/AIMA_UGC/shared/secrets
```

## 15.1 正式启动：一个配置文件 + 一条 Compose 命令

目标 Linux 已安装 Docker Engine + Docker Compose Plugin，并且仓库代码位于受控发布/验收目录时，从仓库根执行：

```bash
cp env.production.example env.production
chmod 0600 env.production
```

编辑 `env.production` 后，只执行：

```bash
docker compose --env-file env.production up -d --build --wait
```

`env.production` 是**敏感生产配置**，因为可以包含 TikHub/LLM API Key。它已经被 `.gitignore` 忽略；不得提交 Git、放进镜像/Release 明文、打印到日志或工单。

Compose 会自动完成：

```text
bootstrap 准备 data/log/postgres/internal-secret 目录
→ 首次自动生成 PostgreSQL password + 三个 Cursor signing key
→ postgres healthy
→ migrate 完成
→ configure 完成
→ api / worker / scheduler 启动
→ api healthy
→ frontend 启动并 healthy
```

管理员不再需要手工运行 `prepare_host.py`、创建 PostgreSQL/Cursor Secret、单独运行 migrate/configure 或逐个启动业务服务。`scripts/deploy/prepare_host.py` 保留为诊断/运维入口，例如需要独立检查时使用 `--check-only`；它不是日常启动前置命令。

## 15.2 Secret 为什么仍然分层

人工只维护一个 `env.production`，但运行时仍保持 Secret File 边界：

```text
内部随机 Secret
postgres_password
import_batch_cursor_signing_key
content_cursor_signing_key
collection_runtime_cursor_signing_key
→ bootstrap 首次生成
→ 宿主 AIMA_HOST_SECRET_DIR 持久保存
→ Backend 只读 /run/internal-secrets

外部凭据
AIMA_TIKHUB_API_KEY
AIMA_LLM_API_KEY
→ 管理员写 env.production
→ Docker Compose Secret
→ 只授予需要它的服务
→ /run/secrets/tikhub_api_key 或 llm_api_key
```

TikHub/LLM Key **不是**业务容器环境变量；应用仍通过受控 Secret File resolver 读取。Provider Config 仍只保存 `secret_ref`，不保存真实 Key。

PostgreSQL password 不要求管理员配置。它首次生成后必须与数据库一起保留：

```text
空数据库 + 密码不存在
→ bootstrap 自动生成

已有 PostgreSQL 18 数据 + postgres_password 存在
→ 复用原密码，不轮换

已有 PostgreSQL 18 数据 + postgres_password 丢失
→ bootstrap fail closed
→ 明确要求恢复原 Secret
→ 禁止生成一个无法与既有数据库匹配的新密码
```

因此服务器备份/恢复时，`postgres_password` 属于数据库可恢复运行所需的关键 Secret；不能只保留 PostgreSQL 数据目录而丢掉该 Secret。

## 15.3 网络默认与 Internal V1-B

默认：

```dotenv
AIMA_HTTP_BIND_IP=127.0.0.1
AIMA_HTTP_PORT=8080
```

因此 V1-A 默认只允许宿主机本地访问。进入 Internal V1-B 做真实公司服务器验收时，再把 `AIMA_HTTP_BIND_IP` 调整为管理员批准的公司内网地址，并验证真实网络可达性；PostgreSQL/API 仍不得发布到普通公司网络。

## 15.4 V1-A 仍不等于完整 Production Release

当前 V1-A 是**仓库级最小可部署环境**。永久 Compose Golden Path 从空宿主状态使用与管理员相同的一条 `docker compose ... up -d --build --wait`，验证 bootstrap、空库 Migration、configure、正式进程、Nginx→API readiness、持久挂载、只读 Secret、内部 Secret 幂等、数据库密码丢失 fail-closed 与端口边界。

它仍不包含：

```text
Internal V1-B 的真实公司服务器 / 浏览器 / 容器重启与宿主机 reboot 验收
真实 TikHub / LLM 有界 Smoke
完整离线 Release Bundle、images.tar、Manifest、SBOM、签名与 Digest 固化
企业认证 / 授权 / HTTPS 正式入口
PostgreSQL + Artifact 同时点协调 Backup / Restore
```

这些继续按 Roadmap 的后续正式单元实施，不能因为 V1-A 启动体验已经收敛就提前宣称完整生产上线完成。

# 16. 常见问题

## Docker 未启动

源码开发 Backend 会直接报错并停止。正式 Compose 启动同样要求 Docker Engine 正常且当前用户有执行 Docker Compose 的权限。

## 本地升级后提示新旧内部 Secret 冲突

不要删除或覆盖任一密码文件。launcher 检测到 `.runtime/internal-secrets/<name>` 与旧 `.runtime/secrets/<name>` 同名但值不同，因此主动停止。先确认哪份 Secret 与现有本地 PostgreSQL/签名事实匹配，再人工清理错误副本；`postgres_password` 尤其不能通过猜测或重新生成解决。

## 正式 Compose 启动失败并提示已有 PostgreSQL 数据但缺少 `postgres_password`

不要删除数据库目录，也不要手工生成新密码。恢复与这份 PostgreSQL 数据匹配的原 `postgres_password`，再重新执行同一条 Compose 启动命令。自动生成新值不能修改既有数据库账户密码，只会造成应用与数据库不匹配，因此系统会主动拒绝这种恢复方式。

## `/health/live` 正常但 `/health/ready` 失败

`live` 只表示 API 能响应；`ready` 才检查 PostgreSQL、ArtifactStore 和日志目录。本地源码开发查看 `.runtime/logs/`；正式 Compose 查看 `AIMA_HOST_LOG_DIR` 对应宿主日志目录与容器状态。

## AI/TikHub 显示未配置

源码开发按本文第 5/6 节填写 `env.local`；正式 Compose 填写 `env.production` 中相应 Base URL/Model/API Key 后重新执行同一条 Compose 启动命令。没有显式业务动作时不会因为 Key 存在就自动发起 AI 付费调用。

## Excel 上传后一直 queued

正常源码开发与正式 Compose 都会启动 Worker。持续 queued 时检查 Worker 进程/容器和对应 `worker.log`，不要用历史测试 harness 代替正式 Worker。
