# 环境、运行与部署

本文是 AIMA_UGC 的**操作入口**，回答三个问题：

1. 新开发机需要什么环境，如何一键或手工准备依赖；
2. 本地如何启动后端和前端，并验证前后端联调；
3. 当前代码能否部署到生产，以及生产部署最终按什么方式落地。

架构和版本决策仍以 `AGENTS.md`、`docs/blueprint/`、版本声明、锁文件和代码为准。本文只描述当前仓库已经存在或已经批准的操作方式；尚未实现的能力不会写成可执行命令。

## 1. 当前可运行范围

当前仓库已经支持：

```text
准备锁定的 Python / Node / npm / uv 开发环境
→ 安装锁定项目依赖
→ 启动 FastAPI 开发服务器
→ 启动 Vite 开发服务器
→ 浏览器访问前端
→ Vite 将 /health 和 /api 转发到 FastAPI
→ 用 smoke 脚本验证本地前后端联调
```

当前状态：

- **Windows x64 一键开发环境初始化：Go**；
- **本地前后端开发启动：Go**；
- **Stage 2 Platform 本地配置、PostgreSQL 连接与 `/health/ready`：Go**；
- **Stage 3A Alembic Migration 与基础 Repository 开发：Go**；
- **Linux/macOS 手工准备运行时 + 锁定依赖安装：Go**；
- **当前源码直接作为生产系统部署：No-Go**。

生产 No-Go 的原因是 Canonical/其余业务 Schema、认证授权、Job Runtime、正式 Scheduler、Docker Compose 和生产 Release 等后续能力尚未完整落地和验收。Stage 3A 已建立 Alembic 和三张基础表，但这只证明数据库基础可开发、可迁移，不等于生产 Schema 或部署已完成。

## 3. Windows x64 一键初始化（推荐）

### 3.1 怎么运行

仓库提供不依赖 Python/Node 预先存在的入口：

```text
scripts\setup_dev_environment.cmd
```

最简单的使用方式：

1. 克隆或解压仓库；
2. 双击 `scripts\setup_dev_environment.cmd`；
3. 按安装界面和询问提示操作；
4. 看到 `AIMA_UGC environment setup completed successfully.` 后关闭窗口。

也可以从 CMD / PowerShell 执行：

```powershell
scripts\setup_dev_environment.cmd
```

`.cmd` 只负责调用：

```text
scripts/setup_dev_environment.ps1
```

核心逻辑使用 Windows PowerShell，因此本机即使没有 Python、Node、npm 或 uv，也可以先运行环境检查。

当前自动引导**仅支持 Windows x64**。Linux/macOS 使用第 4 节的手工路径。

### 3.2 中国大陆国内源策略

一键脚本面向中国大陆开发机，固定使用以下国内源：

| 用途 | 国内源 |
| --- | --- |
| Python Windows 安装包 | 清华 TUNA Python 镜像 |
| PyPI、uv 自身、Python 项目依赖 | 清华 TUNA PyPI |
| Node.js Windows MSI / `SHASUMS256.txt` | npmmirror Node 二进制镜像 |
| npm 自身和前端依赖 | `registry.npmmirror.com` |

原则：

- 不在运行时解析 `latest`，版本仍完全来自仓库版本事实；
- 不永久写入全局 pip、uv 或 npm Registry 配置；
- Python/Node 下载地址、PyPI/npm 源只在当前脚本或当前命令内生效；
- `uv sync` 和 `npm ci` 使用临时环境变量，脚本结束后恢复原值；
- **不自动回退境外源**。国内镜像不可用时直接报错并显示具体镜像 URL，避免出现不可追踪的混合下载路径。

使用镜像不降低完整性检查：

- Python `.exe` 安装包必须通过 Windows Authenticode 有效签名检查；
- Node `.msi` 必须同时通过镜像 `SHASUMS256.txt` 的 SHA-256 校验和 Windows Authenticode 有效签名检查。

### 3.3 脚本会做什么

脚本读取：

```text
.python-version
.node-version
.uv-version
frontend/package.json
```

然后检测：

```text
Python
Node.js
npm
uv
```

处理规则：

| 情况 | 行为 |
| --- | --- |
| 已安装且版本符合 | 不重复安装 |
| Python 缺失/目标版本不存在 | 从 TUNA Python 镜像下载目标安装包并打开官方 GUI |
| Node 缺失/版本不符 | 从 npmmirror 下载目标 MSI，并校验 SHA-256 + Authenticode |
| npm 版本不符 | 明确询问是否把当前 npm 替换为仓库目标版本；使用 npmmirror |
| uv 缺失/版本不符 | 通过目标 Python + TUNA PyPI 精确安装目标 uv |
| Python/Node 存在旧版本 | 先列出 Windows 已注册旧安装，再询问是否主动卸载；默认保留 |
| uv 有旧版本 | 询问是否删除；只对 `%USERPROFILE%\.local\bin` 中的独立 uv 自动删除，其他来源不自动删 |

### 3.4 Python 旧版本与安装

Python 支持多版本并存。

检测到其他已注册 Python 时会询问：

```text
Uninstall these old Python installation(s) first? [y/N]
```

默认 `N`，即保留旧版本。

如果保留：

- 仍安装 `.python-version` 指定的目标 Python；
- 旧的 `python.exe` 可以继续位于全局 PATH 前面；
- 脚本通过直接路径或 Windows Python Launcher 确认目标 Python 确实存在；
- AIMA_UGC 最终通过 `.python-version + uv` 使用目标解释器，不需要为了本项目破坏其他项目的 Python 环境。

Python 安装包来源：

```text
https://mirrors.tuna.tsinghua.edu.cn/python/<version>/python-<version>-amd64.exe
```

脚本下载后先校验 Authenticode，然后打开安装界面。安装 UI 正常显示，用户可以看到安装过程。

如果用户选择卸载旧 Python，脚本只根据 Windows Uninstall Registry 已注册信息调用对应卸载器，**不使用 `Win32_Product`**。

### 3.5 Node.js 与 npm

Node 目标版本来自 `.node-version`。

脚本从：

```text
https://npmmirror.com/mirrors/node/v<version>/
```

取得：

```text
node-v<version>-x64.msi
SHASUMS256.txt
```

安装前必须满足：

```text
SHA-256 匹配
+
Windows Authenticode = Valid
```

然后打开 MSI 安装流程。

检测到旧 Node.js 时默认不主动卸载，但标准 Node.js MSI 通常使用统一安装位置，所以官方 MSI 本身仍可能执行产品升级。脚本不会承诺 Node 多版本长期并存。

npm 随 Node 提供。若 Node 已正确但 npm 版本不符，脚本会明确询问：

```text
Replace the currently resolved npm with npm@<version>? [Y/n]
```

标准全局 npm 不采用并行版本模型，因此用户拒绝后脚本会停止并说明仓库工具链尚未就绪；同意后使用：

```text
registry.npmmirror.com
```

精确安装目标 npm。

### 3.6 uv

uv 目标版本来自 `.uv-version`。

一键脚本**不再调用境外 Astral 安装器**。目标 Python 就绪后，使用：

```text
清华 TUNA PyPI
→ python -m pip install uv==<仓库版本>
```

安装完成后读取目标 Python 的 `Scripts` 目录；如该目录不在当前用户 PATH 中，只把这个目录加入**当前用户 PATH**，不删除其他 PATH 项，也不修改 Machine PATH。

若存在旧 uv，脚本会询问是否删除。只有当前 `uv.exe` 位于：

```text
%USERPROFILE%\.local\bin
```

才允许自动删除该独立安装目录中的 `uv.exe / uvx.exe / uvw.exe`。其他目录视为可能由第三方包管理器所有，不自动删除。

### 3.7 项目依赖也走国内源

系统工具满足后，脚本从仓库根继续执行：

```text
uv lock --check
uv sync --locked
npm ci --prefix frontend
uv run python -c "import aima_ugc; print(aima_ugc.__version__)"
```

这一阶段临时使用：

```text
UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple
npm_config_registry=https://registry.npmmirror.com
npm_config_replace_registry_host=always
```

脚本结束时恢复运行前原有环境变量，因此不会永久改变开发机其他项目的包源配置。

临时安装包保存在系统临时目录下的独立子目录中，脚本结束时尝试清理。

### 3.8 Windows CI 验证边界

GitHub Actions 有独立的 `Windows bootstrap` 门禁，使用 Windows PowerShell 5.1 验证：

- `.ps1` 能被 PowerShell 5.1 解析；
- `.cmd` 正确调用 `.ps1`；
- Python/Node/npm/uv 目标版本从仓库机器事实读取；
- 目标 Python 3.14.7 可以被运行时发现；
- Python `Scripts` 目录发现逻辑可执行；
- 国内 Python/Node/PyPI/npm 地址是预期精确地址；
- 一键脚本源码没有 `www.python.org/ftp/python`、`nodejs.org/dist`、`astral.sh/uv/` 等境外运行时下载源；
- 没有使用 `Win32_Product`；
- 没有永久调用 `Set-ExecutionPolicy`。

CI **不会**真的卸载 Runner 软件，也不会自动点击 Python/Node GUI，因此结论应准确表述为：

> PowerShell 5.1 兼容性、版本发现、国内源选择和非破坏性安全边界已有自动化验证；真实 GUI 安装/卸载仍由开发者本机交互完成。

CI 自身的 `actions/setup-python` 属于 GitHub Actions 测试基础设施，不是开发机一键脚本的下载路径，不受上述“脚本只用国内源”约束。

## 4. 手工初始化（Windows 回退 / Linux / macOS）

### 4.1 先确认版本

```bash
python --version
node --version
npm --version
uv --version
```

目标以第 2 节机器事实文件为准。

Windows 用户如果不用一键脚本，可手工安装精确版本；Linux/macOS 当前也按平台官方方式准备相同版本。不要修改 `.python-version`、`.node-version`、`.uv-version` 或 Lock 来迁就本机已有版本。

### 4.2 安装项目依赖

从仓库根执行：

```bash
uv sync --locked
npm ci --prefix frontend
```

如果开发机位于中国大陆且需要手工使用国内源，可在当前终端临时设置对应 PyPI/npm 源；不要把私人机器的全局镜像设置提交进仓库。

验证：

```bash
uv run python -c "import aima_ugc; print(aima_ugc.__version__)"
```

当前预期：

```text
0.1.0
```

### 4.3 Stage 2 Platform 本地配置

`env.local.example` 是非敏感配置示例，**当前代码不会自动读取该文件，也不会自动加载 `.env`**。运行 API/Worker/Scheduler/Migration 前，需要把实际 `AIMA_*` 值注入对应进程环境。

默认开发目录：

```text
AIMA_DATA_DIR=.runtime/data
AIMA_LOG_DIR=.runtime/logs
AIMA_SECRET_DIR=.runtime/secrets
```

`.runtime/` 已被 Git 忽略。PostgreSQL 默认连接参数见 `env.local.example`；密码不允许放进环境变量，固定从：

```text
<AIMA_SECRET_DIR>/postgres_password
```

读取。开发者应在本机创建该文件并确保不会提交到 Git。当前仓库还没有提供本地 PostgreSQL Compose，所以需要开发者提供一个可访问的 PostgreSQL 18 实例；CI 使用隔离 PostgreSQL 18.4 验证连接，但这不代表生产镜像 variant 已冻结。

健康检查语义：

```text
GET /health/live
→ 只表示 API 进程存活，不依赖 PostgreSQL

GET /health/ready
→ PostgreSQL + Artifact 根目录 + 日志目录全部可用时 200
→ 任一依赖不可用时 503
```

`/health/ready` 只返回各组件 `ok/error`，不会返回密码、连接串、Secret 内容或原始异常。

Platform 本地运行目录和 Secret 准备完成后，再按第 5 节启动 API；如果 PostgreSQL 尚未准备好，`/health/live` 仍可用于确认进程已启动，而 `/health/ready` 应保持 503。

### 4.4 Stage 3A 本地 Migration

Migration 与 API 启动严格分离。准备好同一组 `AIMA_DB_*` 和 `<AIMA_SECRET_DIR>/postgres_password` 后，从仓库根执行：

```bash
uv run alembic current
uv run alembic upgrade head
uv run alembic check
```

开发/CI 可验证回滚：

```bash
uv run alembic downgrade base
uv run alembic upgrade head
uv run alembic check
```

`downgrade base` 会删除 Stage 3A 当前三张应用表，只用于空库/隔离开发数据库和 CI 验证；未来有真实数据的生产回滚必须按 Release/备份方案执行，不能机械 downgrade。API/Worker/Scheduler 启动不会自动执行这些命令。

## 5. 本地启动

本地开发使用两个终端，均从仓库根执行。

### 5.1 后端

```bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090 --reload --reload-dir backend/src
```

后端直接健康检查：

```text
http://127.0.0.1:8090/health/live
```

预期：

```json
{"status":"ok"}
```

### 5.2 前端

```bash
npm --prefix frontend run dev
```

固定入口：

```text
http://127.0.0.1:5173/
```

Vite 使用 `strictPort=true`，端口占用时失败而不静默切换。

### 5.3 前后端联调

```text
Browser
→ http://127.0.0.1:5173
→ /health/* 或 /api/*
→ Vite dev proxy
→ http://127.0.0.1:8090
→ FastAPI
```

代理：

```text
/health → http://127.0.0.1:8090
/api    → http://127.0.0.1:8090
```

通过前端 Origin 验证：

```text
http://127.0.0.1:5173/health/live
```

## 6. 本地启动 smoke

两个服务启动后，在第三个终端执行：

```bash
uv run python scripts/dev/check_local_stack.py
```

它验证：

1. `8090/health/live`；
2. `5173/`；
3. `5173/health/live` 经 Vite 代理。

全部通过会输出：

```text
本地前后端启动与代理联调检查通过。
```

## 7. 常见问题

### 7.1 国内镜像下载失败

一键脚本不会自动回退境外源，错误中会显示失败的镜像 URL。先确认：

- 本机 DNS / 网络 / 代理；
- 对应 TUNA 或 npmmirror 是否可访问；
- HTTPS 证书链是否正常。

不要为了临时通过而在脚本里混入不透明的随机镜像。

### 7.2 旧 Python 仍然是 `python --version` 的结果

这是允许的。Python 可以并存，AIMA_UGC 的最终标准是目标解释器可被发现且：

```bash
uv sync --locked
uv run python -c "import aima_ugc"
```

成功。

### 7.3 `uvicorn` 找不到

```bash
uv sync --locked
uv run uvicorn --version
```

不要用全局 `pip install uvicorn` 作为项目修复方式。

### 7.4 `5173` 被占用

结束旧进程后重启，不修改端口绕过固定开发入口。

### 7.5 前端能打开，但 `/health/live` 失败

依次检查：

1. 后端是否仍运行；
2. `8090/health/live` 是否成功；
3. `frontend/vite.config.ts` 代理是否被修改；
4. 运行 `scripts/dev/check_local_stack.py` 确认失败边界。

### 7.6 `uv sync --locked` / `npm ci` 失败

不要删除 Lock 或改成非锁定安装。先检查版本事实、网络/代理/证书、PyPI/npm 源以及 Lock 是否同步。

## 9. 生产环境部署

### 9.1 当前状态：No-Go

当前仓库**不能把本地开发命令或 Windows 一键环境脚本当成生产部署方式**。

尚未落地/验收：

- 根 `Dockerfile` 与最终多 target 镜像；
- 生产 Compose；
- API/Worker/Scheduler/Migration 四进程的后续业务运行逻辑；
- Canonical 与其余业务 Schema/Migration；
- 第三方认证/授权、Job Runtime 和正式 Scheduler；
- 生产 Env/Secret 模板；
- Release Bundle、镜像 digest、SBOM、签名和 SHA256；
- 数据库 + Artifact 协调备份、Migration、回滚和恢复演练；
- 生产 smoke / E2E / Release CI。

生产服务器现在不要执行：

```text
git pull → uvicorn --reload
npm run dev
scripts/setup_dev_environment.cmd
```

### 9.2 已批准目标形态

以 `docs/blueprint/05-日志安全部署与运维.md` 为准：

```text
frontend
api
worker
scheduler
migrate
postgres
```

目标原则：

- Nginx 对外提供同源前端和 `/api`；
- API/Worker/Scheduler/Migration 使用同版本后端镜像、不同 entrypoint；
- PostgreSQL 18 为业务事实库；
- `/data/AIMA_UGC/` 保存运行数据、日志、PostgreSQL、备份和 Release；
- 生产服务器不现场 `git pull`、不现场构建；
- 可信构建机生成离线 Release；
- Release 校验签名和 SHA，先备份，再 Migration，再启动，再 health/smoke；
- 回滚同时考虑应用、Migration 和 Artifact 兼容边界。

这仍是**目标部署 Contract**，不是当前可执行生产手册。

### 9.3 什么时候补真实生产步骤

Stage 11 Release 真正实现并通过 CI / 恢复验证后，再补：

```text
新服务器准备
→ 目录创建
→ Docker / Compose 安装
→ Release 上传与校验
→ Env / Secret
→ 数据库/Artifact 备份
→ Migration
→ docker compose up
→ health / smoke
→ 回滚
```
