# 环境、运行与部署

本文是 AIMA_UGC 的**操作入口**，回答三个问题：

1. 新开发机需要什么环境，如何一键或手工安装项目依赖；
2. 本地如何启动后端和前端，并验证前后端联调；
3. 当前代码是否可以部署到生产，以及生产部署最终按什么方式落地。

架构和版本决策仍以 `AGENTS.md`、`docs/blueprint/`、版本声明、锁文件和代码为准。本文只描述当前仓库已经存在或已经批准的操作方式；尚未实现的能力不会写成可执行命令。

## 1. 当前可运行范围

当前仓库已经支持：

```text
准备锁定的 Python / Node / npm / uv 开发环境
→ 安装锁定项目依赖
→ 启动 FastAPI 开发服务器
→ 启动 Vite 开发服务器
→ 浏览器访问前端
→ Vite 将 /health 和 /api 转发到 FastAPI
→ 用 smoke 脚本验证本地前后端联调
```

当前状态：

- **Windows x64 一键开发环境初始化：Go**；
- **本地前后端开发启动：Go**；
- **Linux/macOS 手工准备运行时 + 锁定依赖安装：Go**；
- **当前源码直接作为生产系统部署：No-Go**。

生产 No-Go 的原因是 PostgreSQL 业务 Schema、Worker、Scheduler、Migration、Docker Compose 和生产 Release 等能力尚未完整落地和验收。

## 2. 版本事实源

当前开发基线：

| 工具 | 版本 | 机器事实源 |
| --- | ---: | --- |
| Python | `3.14.7` | `.python-version` |
| Node.js | `24.19.0` | `.node-version` |
| npm | `11.17.0` | `frontend/package.json` |
| uv | `0.12.3` | `.uv-version` |

其余版本不要在本文维护第二份快照：

- Python 直接依赖：`pyproject.toml`；
- Python 完整解析结果：`uv.lock`；
- 前端直接依赖：`frontend/package.json`；
- 前端完整解析结果：`frontend/package-lock.json`；
- 初始化版本快照和技术门禁：`docs/blueprint/07-技术决策与实施门禁.md`。

不要因为本机存在更新版本就自动升级仓库版本声明。运行时或依赖升级必须作为独立 Change / PR 处理。

## 3. Windows x64 一键初始化（推荐）

### 3.1 怎么运行

仓库已经提供不依赖 Python/Node 预先存在的入口：

```text
scripts\setup_dev_environment.cmd
```

最简单的使用方式：

1. 克隆或解压仓库；
2. 双击 `scripts\setup_dev_environment.cmd`；
3. 按安装界面和询问提示操作；
4. 看到 `AIMA_UGC environment setup completed successfully.` 后关闭窗口。

也可以从 CMD / PowerShell 调用：

```powershell
scripts\setup_dev_environment.cmd
```

`.cmd` 只负责启动仓库内的：

```text
scripts/setup_dev_environment.ps1
```

核心逻辑使用 Windows PowerShell，因而即使机器上没有 Python、Node、npm 或 uv 也能启动检查。

当前自动引导**仅支持 Windows x64**。Linux/macOS 继续使用本文第 4 节的手工路径。

### 3.2 脚本会做什么

脚本先从仓库机器事实读取目标版本：

```text
.python-version
.node-version
.uv-version
frontend/package.json
```

然后检测：

```text
Python
Node.js
npm
uv
```

处理规则：

| 情况 | 行为 |
| --- | --- |
| 已安装且版本符合 | 不重复安装 |
| 未安装 | 从固定官方来源准备目标版本 |
| Python 版本不符 | 列出已注册的旧 Python，询问是否卸载；默认保留，然后安装目标 Python |
| Node 版本不符 | 列出已注册的旧 Node.js，询问是否卸载；默认不主动卸载，然后运行目标 Node 官方 MSI |
| npm 版本不符 | 使用目标 `npm@<version>` 更新当前标准全局 npm |
| uv 版本不符 | 询问是否删除当前 uv；只有官方默认独立安装目录才自动删除，其他来源不自动删除，然后安装目标 uv |

### 3.3 Python 旧版本如何处理

Python 可以多版本并存。

检测到其他 Python 时，脚本会显示旧版本，并询问：

```text
Uninstall these old Python installation(s) first? [y/N]
```

默认 `N`，即**保留旧版本**。

如果保留旧版本：

- 脚本仍安装仓库目标 Python；
- 不要求把旧 Python 从机器上删除；
- 目标 Python 可以通过 Windows Python Launcher 被确认存在；
- 项目使用 `.python-version + uv` 选择仓库需要的 Python，不需要为了 AIMA_UGC 强行改变其他项目使用的 Python。

因此看到：

```powershell
python --version
```

仍显示另一套旧 Python，并不自动代表 AIMA_UGC 环境失败。最终项目验收以：

```powershell
uv sync --locked
uv run python -c "import aima_ugc; print(aima_ugc.__version__)"
```

为准。

如果用户选择 `Y`，脚本只根据 Windows 已注册的卸载信息调用对应卸载器，不使用 `Win32_Product` 扫描或修复 MSI 产品。

### 3.4 Python 怎么安装

Python 目标版本从 `.python-version` 读取。

脚本下载 python.org 对应的 Windows x64 传统安装器，并校验 Windows Authenticode 状态。安装器界面**会正常显示**，开发者可以看到并完成官方安装流程。

脚本不会静默关闭安装界面，也不会为了安装 Python 永久修改系统 PowerShell 执行策略。

### 3.5 Node.js / npm 怎么处理

Node 目标版本来自 `.node-version`。

脚本：

1. 下载 nodejs.org 对应精确版本的 x64 MSI；
2. 下载同目录官方 `SHASUMS256.txt`；
3. 校验 MSI 的 SHA-256；
4. 打开 Windows MSI 安装流程并等待完成；
5. 重新检测 Node 和 npm。

如果发现旧 Node.js，脚本会先询问是否卸载，默认不主动卸载。

需要注意：标准 Node.js Windows MSI 通常使用统一安装位置，因此即使选择“不卸载旧版本”，官方 MSI 本身仍可能执行产品升级，而不是长期并存多套 Node。这是 Node 安装模型的限制，不由脚本伪造“并存保证”。

npm 随 Node.js 提供。若 Node 已是正确版本而 npm 单独漂移，脚本执行精确版本更新：

```text
npm install --global npm@<仓库目标版本>
```

标准全局 npm 不采用多版本并存模型，因此这里的“升级”会替换当前解析到的全局 npm，而不是保留另一套旧 npm。若权限不足，脚本明确失败并提示重新以管理员方式运行，而不是静默降低检查标准。

### 3.6 uv 怎么处理

uv 目标版本来自 `.uv-version`。

脚本使用 Astral 官方支持的**精确版本安装器 URL**，不是运行时解析 `latest`。

检测到旧 uv 时会询问是否删除当前版本，默认保留。如果当前 `uv.exe` 位于标准独立安装目录：

```text
%USERPROFILE%\.local\bin
```

用户选择删除时，脚本只删除该目录中的 uv 独立可执行文件。若 uv 来自其他目录，可能由其他包管理器管理，脚本不会自动删除，以免破坏其他工具的所有权。

### 3.7 安装完成后自动做什么

工具版本满足后，脚本自动从仓库根执行：

```text
uv lock --check
uv sync --locked
npm ci --prefix frontend
uv run python -c "import aima_ugc; print(aima_ugc.__version__)"
```

也就是说，一键脚本不仅准备系统运行时，还会把 AIMA_UGC 的 Python 和前端项目依赖按锁文件安装好。

临时下载的安装文件保存在系统临时目录下的独立临时目录中；脚本结束时会尝试删除该临时目录，不把安装包提交或长期保存在仓库中。

### 3.8 CI 验证边界

GitHub Actions 有单独的 `Windows bootstrap` 门禁，在 Windows PowerShell 5.1 下验证：

- PowerShell 文件可以解析；
- `.cmd` 正确调用 `.ps1`；
- Python/Node/npm/uv 目标版本能从仓库事实源读取；
- 版本解析和 Python launcher selector 逻辑正确；
- Python/Node/uv 的精确官方下载 URL 构造正确；
- 脚本没有使用 `Win32_Product`；
- 脚本没有永久调用 `Set-ExecutionPolicy`。

CI **不会**真的卸载 GitHub Runner 上的软件，也不会自动点 Python/Node 安装界面。因此正式结论是：

> 安装引导器的 PowerShell 5.1 兼容性、纯逻辑、来源构造和安全边界已自动验证；真实 GUI 安装/卸载仍属于开发者本机的交互操作。

## 4. 手工初始化（Windows 回退 / Linux / macOS）

### 4.1 先确认版本

```bash
python --version
node --version
npm --version
uv --version
```

目标以第 2 节列出的机器事实文件为准。

Windows 用户如果不使用一键脚本，可自行安装这些精确版本；Linux/macOS 当前也按各自官方安装方式准备相同版本。

不要通过修改 `.python-version`、`.node-version`、`.uv-version` 或 Lock 来迁就本机已有版本。

### 4.2 安装项目依赖

从仓库根目录执行：

```bash
uv sync --locked
npm ci --prefix frontend
```

使用的是：

```text
pyproject.toml + uv.lock
frontend/package.json + frontend/package-lock.json
```

不要用临时 `pip install` 补项目运行依赖，也不要用 `npm install` 静默重算前端依赖树。

验证 Python package：

```bash
uv run python -c "import aima_ugc; print(aima_ugc.__version__)"
```

当前预期输出：

```text
0.1.0
```

## 5. 本地启动

本地开发使用两个终端，两个命令都从仓库根目录执行。

### 5.1 终端 1：启动后端

```bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090 --reload --reload-dir backend/src
```

含义：

- 使用仓库锁定的 Uvicorn，不依赖系统全局安装；
- 只监听本机回环地址 `127.0.0.1`；
- 本地开发端口固定 `8090`；
- 修改 `backend/src` 下 Python 文件时自动重新加载；
- 入口复用正式 FastAPI 对象 `aima_ugc.entrypoints.api_main:app`。

后端直接健康检查：

```text
http://127.0.0.1:8090/health/live
```

预期：

```json
{"status":"ok"}
```

### 5.2 终端 2：启动前端

```bash
npm --prefix frontend run dev
```

固定入口：

```text
http://127.0.0.1:5173/
```

Vite 使用 `strictPort=true`。如果 `5173` 已被占用，启动失败并提示端口冲突，不静默换端口。

### 5.3 前后端联调

```text
Browser
→ http://127.0.0.1:5173
→ /health/* 或 /api/*
→ Vite dev proxy
→ http://127.0.0.1:8090
→ FastAPI
```

开发代理：

```text
/health → http://127.0.0.1:8090
/api    → http://127.0.0.1:8090
```

前端生成 Client 继续使用相对 URL，不为了本地开发增加第二套 API Base URL，也不通过放宽 CORS 解决联调。

通过前端 Origin 验证：

```text
http://127.0.0.1:5173/health/live
```

应返回：

```json
{"status":"ok"}
```

## 6. 本地启动 smoke

后端和前端都启动后，在第三个终端执行：

```bash
uv run python scripts/dev/check_local_stack.py
```

验证：

1. `8090/health/live`：FastAPI 可直接访问；
2. `5173/`：Vite 首页可访问；
3. `5173/health/live`：Vite → FastAPI 代理可用。

通过时输出：

```text
本地前后端启动与代理联调检查通过。
```

停止开发服务器时，在两个运行终端分别按 `Ctrl+C`。

## 7. 常见问题

### 7.1 一键脚本提示版本仍不符合

先看脚本打印的 `current` 和 `target`。

Python 允许旧版本继续存在；只要目标 Python 已安装且 `uv sync --locked` 能使用 `.python-version` 完成环境，旧 `python.exe` 在 PATH 中仍可保留。

Node/npm/uv 属于全局命令，最终解析到的命令必须符合仓库目标版本。如果旧安装仍优先，检查 Windows PATH 和对应安装来源，不要通过修改仓库版本声明制造通过。

### 7.2 `uvicorn` 找不到

```bash
uv sync --locked
uv run uvicorn --version
```

不要改成全局 `pip install uvicorn` 作为项目修复方式。

### 7.3 `5173` 端口被占用

结束占用 `5173` 的旧进程后重新启动，不要临时修改端口绕过固定开发入口。

### 7.4 前端能打开，但 `/health/live` 失败

依次检查：

1. 后端终端是否仍在运行；
2. `http://127.0.0.1:8090/health/live` 是否成功；
3. `frontend/vite.config.ts` 代理是否被修改；
4. 运行 `uv run python scripts/dev/check_local_stack.py` 查看失败边界。

### 7.5 `uv sync --locked` 或 `npm ci` 失败

不要删除 Lock 或改用非锁定安装制造通过。先检查：

- 版本事实文件是否与当前分支一致；
- `pyproject.toml` 与 `uv.lock` 是否同步；
- `package.json` 与 `package-lock.json` 是否同步；
- 网络、代理、证书和 Registry 是否可访问。

需要修改依赖时，按仓库 Change / PR / CI 流程更新声明和 Lock。

## 8. 开发完成前的基本验证

完整门禁由 `.github/workflows/ci.yml` 执行。

涉及本地启动、前后端调用路径或 Vite 配置时，额外执行：

```bash
uv run python scripts/dev/check_local_stack.py
```

该命令要求后端和前端已经启动。

Windows 环境引导器发生变化时，必须同时通过 CI 的：

```text
Windows bootstrap
```

门禁。

## 9. 生产环境部署

### 9.1 当前状态：No-Go

当前仓库**不能把本地开发启动命令或 Windows 一键环境脚本当成生产部署方式**。

以下生产能力尚未真正落地或验收：

- 根 `Dockerfile` 与最终多 target 镜像构建；
- 生产 `compose.yaml` / `compose.production.yaml`；
- API、Worker、Scheduler、Migration 四进程完整实现；
- PostgreSQL 业务 Schema 与 Alembic Revision；
- `/health/ready` 及数据库、Artifact 等 readiness；
- Config、Secret、统一日志、Artifact 生命周期；
- 生产环境变量 / Secret 模板；
- Release Bundle、镜像 digest、SBOM、签名与 `SHA256SUMS`；
- 数据库 + Artifact 协调备份、Migration、回滚与恢复演练；
- 生产 smoke / E2E 和 Release CI 门禁。

生产服务器现在不要执行：

```text
git pull → uvicorn --reload
npm run dev
scripts/setup_dev_environment.cmd
```

也不要把当前源码目录直接当正式 Release。

### 9.2 已批准的目标部署形态

生产最终形态由 `docs/blueprint/05-日志安全部署与运维.md` 约束，目标服务：

```text
frontend
api
worker
scheduler
migrate
postgres
```

目标原则：

- Nginx 对外提供同源前端和 `/api`；
- API、Worker、Scheduler、Migration 使用同一版本后端镜像、不同 entrypoint；
- PostgreSQL 18 是业务事实库；
- `/data/AIMA_UGC/` 保存运行数据、日志、PostgreSQL、备份和 Release；
- 生产服务器不现场 `git pull`、不现场构建；
- 在可信构建机生成离线 Release Bundle；
- Release 验证签名和 SHA 后，先备份，再 Migration，再启动应用，再执行 health / smoke；
- 回滚同时考虑应用、数据库 Migration 和 Artifact 兼容边界。

上述内容当前是**目标部署 Contract**，不是已经可以执行的部署步骤。

### 9.3 什么时候变成可执行生产手册

Stage 11 Release 真正落地并通过 CI / 恢复验证后，再在本文补充真实命令：

```text
新服务器准备
→ 目录创建
→ Docker / Compose 安装要求
→ Release 包上传与校验
→ 环境和 Secret 配置
→ 数据库/Artifact 备份
→ Migration
→ docker compose up
→ health / smoke
→ 回滚
```

在制品和命令真实存在之前，不写占位命令假装生产部署已支持。
