# 环境、运行与部署

本文是 AIMA_UGC 的日常运行入口。优先回答：**拿到源码以后，怎样用最少步骤在 Windows 或 Linux 上把真实后端、PostgreSQL、Worker 和 Vue 前端跑起来。**

架构、Schema、Contract 和生产部署边界仍分别以 `AGENTS.md`、`docs/blueprint/`、Migration、代码和 Roadmap 为准。本文不把本地源码调试入口描述成生产部署方案。

---

# 1. 本地开发快速开始

本地源码调试只需要记两个命令。Windows 和 Linux 使用**完全相同**的正式入口。

## 1.1 前提

开发机已经具备仓库锁定版本的：

```text
Python
uv
Node.js
npm
Docker CLI + Docker Engine
```

精确版本事实源：

```text
.python-version
.uv-version
.node-version
frontend/package.json
uv.lock
frontend/package-lock.json
```

Windows 第一次准备工具链可继续使用：

```powershell
scripts\setup_dev_environment.cmd
```

Linux 的工具链安装与应用启动是两件事。仓库现有 `scripts/setup_dev_environment.sh` 是 CentOS Stream 9 x86_64 的特定宿主初始化脚本；不应把它当成应用日常启动命令。只要目标 Linux 已准备正确版本的 Python/uv/Node/npm/Docker，下面两个 Python launcher 与 Windows 共用同一实现。

## 1.2 终端 1：启动完整本地后端

从仓库根执行：

```bash
uv run python scripts/dev/backend.py
```

这个命令不是“只启动 FastAPI”。它会把本地业务运行所需的基础组件准备好，再启动正式 API/Worker。

成功后主要地址：

```text
API          http://127.0.0.1:8090
Readiness    http://127.0.0.1:8090/health/ready
```

## 1.3 终端 2：启动前端

从仓库根执行：

```bash
uv run python scripts/dev/frontend.py
```

浏览器访问：

```text
http://127.0.0.1:5173/
```

Vite 会把 `/api` 和 `/health` 代理到本地 FastAPI。

因此日常源码开发的心智模型固定为：

```text
终端 1：backend.py
终端 2：frontend.py
浏览器：127.0.0.1:5173
```

不再要求开发者手工拼接 PostgreSQL、Migration、多个 Secret 和 Worker 启动命令。

---

# 2. 第一次运行 Backend 会自动做什么

第一次执行：

```bash
uv run python scripts/dev/backend.py
```

启动器按顺序处理：

```text
检查/创建 env.local
→ 创建 .runtime 本地目录
→ 自动生成数据库密码和三个 Cursor signing key
→ 检查 Docker Engine
→ 创建或启动 PostgreSQL 18.4 本地容器
→ 等 PostgreSQL ready
→ alembic upgrade head
→ 按 env.local 准备 TikHub / LLM Secret
→ 幂等维护本地 TikHub Provider Config
→ 启动正式 Worker
→ 按需启动 Scheduler
→ 启动 FastAPI
→ 等待 /health/ready = 200
→ 输出当前功能可用状态
```

本地 PostgreSQL 固定使用：

```text
image      postgres:18.4
container  aima-ugc-postgres-dev
volume     aima-ugc-postgres-dev-data
host       127.0.0.1
port       5432
database   aima_ugc
user       aima_ugc
```

数据库密码由启动器随机生成，不要求开发者填写，也不写入 Git。密码文件固定为：

```text
.runtime/secrets/postgres_password
```

PostgreSQL 数据保存在 Docker named volume 中；关闭 `backend.py` 不删除容器数据。

## 2.1 后续启动

以后再次运行同一命令时：

```text
既有 PostgreSQL 容器在运行
→ 直接复用

容器已停止
→ 自动启动

Migration 已在 head
→ upgrade head 幂等返回

已有 Secret
→ 继续复用，不静默轮换
```

因此不需要每次重新配置数据库。

---

# 3. `env.local` 到底是什么

仓库提交的是：

```text
env.local.example
```

真实本地文件：

```text
env.local
```

已经加入 `.gitignore`。

第一次运行 Backend 或 Frontend 时，如果 `env.local` 不存在，launcher 会自动从 `env.local.example` 复制一份；开发者不需要先手工创建。

`env.local` **只属于源码开发 launcher 的输入界面，不是生产运行时 Contract**。

正式 API/Worker/Scheduler 仍然使用原有架构：

```text
非敏感运行配置
→ AIMA_* 子进程环境

Secret
→ AIMA_SECRET_DIR 下 Secret File

Provider Config
→ PostgreSQL 只保存 secret_ref
```

Dev launcher 读取 `env.local` 后会把 TikHub/LLM API Key 写到 `.runtime/secrets/`，并从正式子进程环境中移除本地明文 Key。生产部署仍由 Internal V1-A 的 Compose/Secret mount 负责，不读取 `env.local`。

---

# 4. `env.local` 现在只需要配置什么

默认文件非常短：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=

AIMA_LLM_BASE_URL=
AIMA_LLM_PROVIDER_NAME=
AIMA_LLM_MODEL=
AIMA_LLM_API_KEY=

AIMA_DEV_ENABLE_SCHEDULER=false
```

数据库 Host、Port、用户名、密码、数据目录、日志轮转、Cursor Key、Migration、Worker lease 等内部运行细节不属于日常本地配置，不再要求开发者填写。

## 4.1 什么都不填也能做什么

TikHub 和 LLM 都留空时，Backend 仍正常启动：

```text
Excel Import     AVAILABLE
Voice Plaza      AVAILABLE
Excel Export     AVAILABLE
TikHub           NOT CONFIGURED
AI Analysis      NOT CONFIGURED
Scheduler        DISABLED
```

`NOT CONFIGURED` 是 Warning，不是整个系统的启动错误。

真正会阻止 Backend 启动的是基础依赖失败，例如：

```text
Docker CLI / Docker Engine 不可用
PostgreSQL 容器创建或启动失败
PostgreSQL 无法 ready
Alembic Migration 失败
Worker/API 启动失败
/health/ready 无法通过
```

# 5. 要测试 TikHub 时怎么配置

只修改本机 `env.local`：

```dotenv
AIMA_TIKHUB_BASE_URL=https://api.tikhub.io
AIMA_TIKHUB_API_KEY=<你的本地调试 Key>
```

然后重启：

```bash
uv run python scripts/dev/backend.py
```

启动器会：

```text
env.local 的 Key
→ .runtime/secrets/tikhub_api_key

PostgreSQL Provider Config
→ provider=tikhub
→ display_name=TikHub Local Dev
→ base_url=<env.local>
→ secret_ref=tikhub_api_key
→ enabled=true
```

数据库不保存真实 API Key。

如果把 `AIMA_TIKHUB_API_KEY` 再清空并重启，launcher 会删除对应本地 Secret，并禁用自己的 `TikHub Local Dev` Provider Config，避免前端继续把一个不可执行的本地 Provider 暴露成可用配置。

普通 CI 不读取你的真实 Key，也不会因为本地启动功能增加付费 TikHub 请求。

---

# 6. 要测试 AI 打标时怎么配置

只修改本机 `env.local`：

```dotenv
AIMA_LLM_BASE_URL=https://your-provider.example/v1
AIMA_LLM_PROVIDER_NAME=your-provider
AIMA_LLM_MODEL=your-model
AIMA_LLM_API_KEY=<你的本地调试 Key>
```

其中 `AIMA_LLM_PROVIDER_NAME` 可以在当前 Adapter 能从 Base URL 明确推导时留空；Base URL、Model、API Key 是实际启用 AI 所需的核心项。

重启 Backend 后：

```text
API Key
→ .runtime/secrets/llm_api_key

Base URL / Provider / Model
→ 正式 AIMA_LLM_* Runtime 配置

Worker
→ 正式 Content Analysis Job
→ LLM Adapter
```

如果只填了一部分 LLM 配置，Backend 会显示 Warning，并把 AI 视为未配置；不会让一组半完成配置污染正式 Worker Runtime。

声音广场同时通过正式 `GET /api/v1/content-analysis-capabilities` 读取安全布尔能力：

```text
configured=false
→ 页面提示当前环境未配置可用 LLM Runtime
→ AI 打标按钮 disabled
→ 不创建注定失败的 Analysis Job

configured=true
→ 保持现有 selected/query Analysis Job 流程
```

这个 HTTP 能力只返回 `configured`，不会把 `env.local`、Base URL、Model、Secret 路径或 API Key 发给浏览器；它也不替代 Worker 对运行配置的最终校验。

Import 和普通 TikHub Collection 不会因为 LLM 配置存在就自动发起 AI 付费调用。只有用户在声音广场显式创建 AI Analysis Job 才调用模型。

# 7. Scheduler 为什么默认关闭

本地默认：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=false
```

原因是本地数据库可能保留 enabled Collection Plan。若启动源码环境时自动开启 Scheduler，旧 Plan 可能立即创建真实 TikHub Run 并产生费用。

需要专门调试周期采集时才改为：

```dotenv
AIMA_DEV_ENABLE_SCHEDULER=true
```

然后重启同一个 `backend.py`。不需要记第三条 Scheduler 启动命令。

手工 TikHub Discovery / Batch Supplement 不依赖 Scheduler；它们依赖 API + Worker。

# 8. 前端第一次运行需要“编译”吗

本地开发不需要先执行 production build。

第一次执行：

```bash
uv run python scripts/dev/frontend.py
```

launcher 会：

```text
检查 Node/npm 精确版本
→ 检查 frontend/node_modules
→ 检查 package-lock.json 指纹
→ 首次或 lock 变化时自动 npm ci
→ npm run dev
→ Vite Development Server
```

Vite 在开发时实时处理 Vue / TypeScript / CSS，并提供热更新。修改 `.vue` / `.ts` 后保存，浏览器会自动更新。

只有正式构建才执行：

```bash
npm --prefix frontend run build
```

它会生成生产 `frontend/dist/`。这属于 CI 和未来 Internal V1-A 的正式前端镜像构建，不是日常源码调试前置步骤。

# 9. 本地数据、文件、日志和 Secret 在哪里

本地源码调试的主要持久状态：

```text
PostgreSQL
→ Docker volume: aima-ugc-postgres-dev-data

Excel 输入 / Raw / Export 等 Artifact
→ .runtime/data/artifacts/

应用日志
→ .runtime/logs/
   ├─ api.log
   ├─ worker.log
   └─ scheduler.log（启用时）

本地 Secret
→ .runtime/secrets/

Frontend 依赖锁指纹
→ .runtime/dev/frontend-package-lock.sha256
```

`.runtime/` 和 `env.local` 都被 Git 忽略。

上传的 Excel 原文件作为 Input Artifact 保存到 Local ArtifactStore，Import Batch、Job、Content 等业务事实保存到 PostgreSQL；因此完整 Excel Web 调试确实需要 PostgreSQL + Worker，而 `backend.py` 已自动把这两者包含在启动流程里。

# 10. 第一次导入 Excel 前还需要一个业务配置

本地运行配置可以自动准备，但**业务配置不能被 launcher 猜测**。

正式 Import/Collection 使用全局 Rule Relevance。一个全新数据库第一次使用时，请在前端：

```text
采集策略
→ 新建关键词包
→ 添加业务关键词（例如当前真正要监测的关键词）
→ 全局相关性
→ 选择该关键词包
```

然后再去：

```text
采集运行中心
→ 导入 Excel
```

不自动创建“爱玛”默认词包，是为了避免 dev launcher 变成业务配置的第二事实源。

# 11. 本地联调 Smoke

Backend 和 Frontend 都启动后，第三个终端可以执行：

```bash
uv run python scripts/dev/check_local_stack.py
```

它验证：

```text
FastAPI /health/ready
→ PostgreSQL + ArtifactStore + 日志目录真实可用

Vite 首页
→ Vue dev server 可访问

Vite /health/ready 代理
→ 前后端代理真实接通
```

页面能打开但 `/health/ready` 失败，不应被描述成完整本地业务环境已经可用。

# 12. 停止、重新启动和重置本地数据库

Backend 终端按 `Ctrl+C`：

```text
停止 API
停止 Worker
停止本次启动的 Scheduler（如果开启）
```

PostgreSQL 容器和 named volume 默认保留，便于下次快速继续开发。

Frontend 终端按 `Ctrl+C` 停止 Vite。

如果明确要**破坏性清空本地开发数据库**，先停止 Backend，再手工执行：

```bash
docker rm -f aima-ugc-postgres-dev
docker volume rm aima-ugc-postgres-dev-data
```

随后删除与这个本地数据库绑定的自动密码：

```text
.runtime/secrets/postgres_password
```

下次 `backend.py` 会重新创建空数据库、随机密码并执行全部 Migration。

这只允许用于本地开发数据。不要把这组命令用于包含真实业务数据的服务器。

# 13. 高级开发：直接启动正式进程

日常优先使用两个 launcher。只有调试具体进程边界时才直接运行正式进程。

API：

```bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090 --reload --reload-dir backend/src
```

Worker：

```bash
uv run python -m aima_ugc.entrypoints.worker_main
```

Scheduler：

```bash
uv run python -m aima_ugc.entrypoints.scheduler_main
```

Migration：

```bash
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

直接启动这些正式进程时，调用者仍需自己提供它们要求的 `AIMA_*` 和 Secret File；这是高级调试路径，不是普通开发者快速开始。

# 14. 开发环境安装与依赖

项目依赖仍按锁文件安装。

Python：

```bash
uv lock --check
uv sync --locked
uv run python -c "import aima_ugc; print(aima_ugc.__version__)"
```

前端依赖日常由 `scripts/dev/frontend.py` 自动判断是否需要 `npm ci`。需要人工验证锁定环境时可执行：

```bash
npm ci --prefix frontend
```

Windows x64 的一次性工具链安装逻辑仍由：

```text
scripts/setup_dev_environment.cmd
scripts/setup_dev_environment.ps1
```

维护；它负责 Python/Node/npm/uv 版本和国内镜像安装，不负责每日启动 PostgreSQL/API/Worker/Vite。

当前 Linux 的 `scripts/setup_dev_environment.sh` 是特定 CentOS Stream 9 x86_64 宿主初始化脚本。应用 launcher 本身不复制 Linux/Windows 两套业务逻辑。

# 15. 本地开发与 Internal V1-A 的边界

当前 `scripts/dev/backend.py` / `frontend.py` 是**源码开发入口**：

```text
本机 Python / Node
+ 本地 Docker PostgreSQL
+ Vite dev server
+ uvicorn --reload
```

它们不等于生产部署。

Internal V1-A 仍负责：

```text
Dockerfile
Compose
正式 frontend runtime / Nginx
api / worker / scheduler / migrate 服务
PostgreSQL 持久目录
Artifact / 日志持久目录
生产 env
只读 Secret mount
Health / dependency
公司内网网络边界
```

正式服务器不应该以 `uvicorn --reload`、`npm run dev` 或 `scripts/dev/*.py` 作为长期运行方式。

长期生产/离线 Release 方案见：

- [`roadmap/生产上线实施路线.md`](roadmap/生产上线实施路线.md)
- [`roadmap/内网V1上线实施计划.md`](roadmap/内网V1上线实施计划.md)
- [`appendix/生产部署与离线Release方案.md`](appendix/生产部署与离线Release方案.md)

# 16. 常见问题

## Docker 未启动

Backend 会直接报错并停止。Windows 启动 Docker Desktop；Linux 确认 Docker Engine 正常且当前用户有权限执行 `docker info`。Launcher 不会尝试修改系统级 Docker 权限。

## 5432 被其他 PostgreSQL 占用

本地开发容器固定绑定 `127.0.0.1:5432`。如果端口已被其他服务占用，Backend 会在容器创建/启动阶段失败并显示 Docker 错误；不要静默换端口制造第二套本地事实，先决定哪个 PostgreSQL 实例应继续使用。

## `/health/live` 正常但 `/health/ready` 失败

`live` 只表示 API 能响应；`ready` 才检查 PostgreSQL、ArtifactStore 和日志目录。查看 Backend 终端和：

```text
.runtime/logs/api.log
.runtime/logs/worker.log
```

## AI/TikHub 显示 NOT CONFIGURED

这是可选能力提示，不影响 Excel/声音广场/Excel Export。按本文第 5/6 节填写 `env.local` 后重启 Backend。LLM 未配置时声音广场也会通过正式 capability API 显示“AI 打标暂不可用”并禁用按钮。

## Excel 上传后一直 queued

正常本地入口会同时启动正式 Worker。如果持续 queued，先确认 Backend 终端里 Worker 没有退出，并查看 `.runtime/logs/worker.log`。不要再单独运行历史测试 harness 代替正式 Worker。

## 前端依赖安装很慢或失败

`frontend.py` 只在首次或 `package-lock.json` 变化时运行 `npm ci`。失败时检查仓库要求的 Node/npm 版本、网络和 npm Registry；不要删除 lock 或手工改依赖版本绕过。
