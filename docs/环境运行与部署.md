# 环境、运行与部署

本文是 AIMA_UGC 的**操作入口**，回答三个问题：

1. 新开发机需要什么运行环境，如何安装项目依赖；
2. 本地如何启动后端和前端，并验证前后端联调；
3. 当前代码是否可以部署到生产，以及生产部署最终应按什么方式落地。

架构和版本决策仍以 `AGENTS.md`、`docs/blueprint/`、锁文件和代码为准。本文只描述当前仓库已经存在或已经明确批准的操作方式；尚未实现的能力不会写成可执行命令。

## 1. 当前可运行范围

当前仓库已经支持：

```text
安装锁定的 Python / Node 依赖
→ 启动 FastAPI 开发服务器
→ 启动 Vite 开发服务器
→ 浏览器访问前端
→ Vite 将 /health 和 /api 转发到 FastAPI
→ 用 smoke 脚本验证本地前后端联调
```

当前仓库尚未进入 PostgreSQL 业务 Schema、Worker、Scheduler、Migration、Docker Compose 和生产 Release 的完整实现阶段。因此：

- **本地前后端开发启动：Go**；
- **当前源码直接作为生产系统部署：No-Go**。

## 2. 开发机环境

### 2.1 固定版本

当前开发基线：

| 工具 | 版本 | 事实源 |
| --- | ---: | --- |
| Python | `3.14.7` | `.python-version` |
| Node.js | `24.19.0` | `.node-version` |
| npm | `11.17.0` | `frontend/package.json` / CI |
| uv | `0.12.3` | `docs/blueprint/07-技术决策与实施门禁.md` / CI |

其余 Python 与前端依赖不要在本文维护第二份版本表：

- Python 直接依赖：`pyproject.toml`；
- Python 完整解析结果：`uv.lock`；
- 前端直接依赖：`frontend/package.json`；
- 前端完整解析结果：`frontend/package-lock.json`；
- 初始化冻结快照：`docs/blueprint/07-技术决策与实施门禁.md`。

不要因为本机存在更新版本就自动升级。升级运行时或依赖必须作为独立变更处理。

### 2.2 Windows PowerShell 检查

在仓库根目录执行：

```powershell
python --version
node --version
npm --version
```

预期：

```text
Python 3.14.7
v24.19.0
11.17.0
```

如果版本不同，先安装仓库要求的 Python 3.14.7 和 Node 24.19.0，再继续。不要通过修改 `.python-version`、`.node-version` 或 Lock 来迁就本机已有版本。

安装仓库当前固定的 uv：

```powershell
python -m pip install "uv==0.12.3"
```

验证：

```powershell
uv --version
```

### 2.3 Linux / macOS 检查

同样先确认：

```bash
python --version
node --version
npm --version
```

然后安装固定 uv：

```bash
python -m pip install "uv==0.12.3"
```

项目命令始终从**仓库根目录**执行。不要 `cd backend` 建第二套 Python 项目，也不要使用 `uv --project backend`。

## 3. 首次安装项目依赖

从仓库根目录执行：

```bash
uv sync --locked
npm ci --prefix frontend
```

这两个命令分别使用已经提交的：

```text
pyproject.toml + uv.lock
frontend/package.json + frontend/package-lock.json
```

不要用临时 `pip install` 补项目运行依赖，也不要用 `npm install` 静默重算前端依赖树。

安装后可验证 Python package：

```bash
uv run python -c "import aima_ugc; print(aima_ugc.__version__)"
```

当前预期输出：

```text
0.1.0
```

## 4. 本地启动

本地开发使用两个终端。两个命令都从仓库根目录执行。

### 4.1 终端 1：启动后端

Windows PowerShell、Linux 和 macOS 均使用：

```bash
uv run uvicorn aima_ugc.entrypoints.api_main:app --host 127.0.0.1 --port 8090 --reload --reload-dir backend/src
```

含义：

- 使用仓库锁定的 Uvicorn，而不是系统全局安装；
- 后端只监听本机回环地址 `127.0.0.1`；
- 本地开发端口固定为 `8090`；
- 修改 `backend/src` 下 Python 文件时自动重新加载；
- 入口始终复用生产 FastAPI 对象 `aima_ugc.entrypoints.api_main:app`，不复制另一套调试应用。

后端直接健康检查：

```text
http://127.0.0.1:8090/health/live
```

预期：

```json
{"status":"ok"}
```

### 4.2 终端 2：启动前端

```bash
npm --prefix frontend run dev
```

开发服务器固定监听：

```text
http://127.0.0.1:5173/
```

Vite 使用 `strictPort=true`。如果 `5173` 已被占用，启动会失败并提示端口冲突，不会静默切换到另一个端口。

### 4.3 前后端联调方式

开发环境中的浏览器以 Vite 为同源入口：

```text
Browser
→ http://127.0.0.1:5173
→ /health/* 或 /api/*
→ Vite dev proxy
→ http://127.0.0.1:8090
→ FastAPI
```

Vite 当前代理：

```text
/health → http://127.0.0.1:8090
/api    → http://127.0.0.1:8090
```

因此前端生成 Client 继续使用相对 URL，不需要为了本地开发增加另一套 API Base URL，也不需要通过放宽 CORS 来解决开发期联调。

通过前端 Origin 验证后端：

```text
http://127.0.0.1:5173/health/live
```

同样应返回：

```json
{"status":"ok"}
```

## 5. 本地启动验证

后端和前端都启动后，在第三个终端执行：

```bash
uv run python scripts/dev/check_local_stack.py
```

该脚本只做 HTTP 观察，不复制业务实现。它验证：

1. `8090/health/live`：FastAPI 可直接访问；
2. `5173/`：Vite 首页可访问；
3. `5173/health/live`：Vite → FastAPI 代理可用。

全部通过时会输出：

```text
本地前后端启动与代理联调检查通过。
```

停止开发服务器时，在两个运行终端分别按 `Ctrl+C`。

## 6. 常见本地问题

### 6.1 `uvicorn` 找不到

先确认没有绕过锁文件：

```bash
uv sync --locked
uv run uvicorn --version
```

不要改成全局 `pip install uvicorn` 作为项目修复方式。

### 6.2 `5173` 端口被占用

当前前端故意使用固定端口。先结束占用 `5173` 的旧进程，再重新启动，不要修改端口来绕过问题。

### 6.3 前端能打开，但 `/health/live` 失败

依次检查：

1. 后端终端是否仍在运行；
2. `http://127.0.0.1:8090/health/live` 是否成功；
3. `frontend/vite.config.ts` 的代理配置是否被当前分支修改；
4. 再运行 `uv run python scripts/dev/check_local_stack.py` 查看失败边界。

### 6.4 `uv sync --locked` 或 `npm ci` 失败

不要删除 Lock 或改用非锁定安装制造通过。先检查：

- Python / Node / npm 是否为仓库固定版本；
- `pyproject.toml` 与 `uv.lock` 是否同步；
- `package.json` 与 `package-lock.json` 是否同步；
- 网络、代理、证书和 Registry 是否可访问。

如果确实需要修改依赖，按仓库 Change / PR / CI 流程更新声明和 Lock。

## 7. 开发完成前的基本验证

完整质量门禁由 `.github/workflows/ci.yml` 执行。开发者至少应按影响范围运行 README 中列出的检查。

涉及本地启动、前后端调用路径或 Vite 配置时，额外必须运行：

```bash
uv run python scripts/dev/check_local_stack.py
```

该命令要求后端和前端已经启动。

## 8. 生产环境部署

### 8.1 当前状态：No-Go

当前仓库**不能把本地开发启动命令当成生产部署方式**。以下生产能力尚未真正落地或验收：

- 根 `Dockerfile` 与最终多 target 镜像构建；
- 生产 `compose.yaml` / `compose.production.yaml`；
- API、Worker、Scheduler、Migration 四进程完整实现；
- PostgreSQL 业务 Schema 与 Alembic Revision；
- `/health/ready` 及数据库、Artifact 等 readiness；
- Config、Secret、统一日志、Artifact 生命周期；
- 生产环境变量 / Secret 模板；
- Release Bundle、镜像 digest、SBOM、签名与 `SHA256SUMS`；
- 数据库 + Artifact 协调备份、Migration、回滚与恢复演练；
- 生产 smoke / E2E 和 Release CI 门禁。

因此现在不要在生产服务器执行：

```text
git pull → uvicorn --reload
npm run dev
```

也不要把当前源码目录直接当作正式 Release。

### 8.2 已批准的目标部署形态

生产最终形态由 `docs/blueprint/05-日志安全部署与运维.md` 约束，目标服务为：

```text
frontend
api
worker
scheduler
migrate
postgres
```

目标原则：

- Nginx 对外提供同源前端和 `/api`；
- API、Worker、Scheduler、Migration 使用同一版本后端镜像、不同 entrypoint；
- PostgreSQL 18 是业务事实库；
- `/data/AIMA_UGC/` 保存运行数据、日志、PostgreSQL、备份和 Release；
- 生产服务器不现场 `git pull`、不现场构建；
- 在可信构建机生成离线 Release Bundle；
- Release 验证签名和 SHA 后，先备份，再 Migration，再启动应用，再执行 health / smoke；
- 回滚必须同时考虑应用、数据库 Migration 和 Artifact 兼容边界。

上述内容现在是**目标部署 Contract**，不是当前代码已经可以执行的部署步骤。

### 8.3 什么时候本节会变成可执行部署手册

当 Stage 11 Release 真正落地并通过 CI / 恢复验证后，本节再补充实际命令，包括：

```text
新服务器准备
→ 目录创建
→ Docker / Compose 安装要求
→ Release 包上传与校验
→ 环境和 Secret 配置
→ 数据库/Artifact 备份
→ Migration
→ docker compose up
→ health / smoke
→ 回滚
```

在这些制品和命令真实存在之前，不用占位命令假装“生产部署已支持”。
